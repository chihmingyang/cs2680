先看這裡

Model 沒有記憶，所以 agent 每一步都把整個 context 重送一次，錢多半花在重讀。這堂要帶走的不是一串省錢技巧，而是先把帳算對，再決定動哪一項：算每個成功任務的成本，先保住 cache 命中，再算每個省法的淨節省。

  • 帳要算到成功的任務。便宜的設定每次省，每個成功任務可能更貴；要比平均，也要比多成功一次得多花多少。
  • 先保住 cache，再談別的。重讀是最大的一筆花費，沒命中的 token 貴 12 到 50 倍，而每個省法都有反向成本，compaction 也要走幾步才回本。
  • 時間和邊界是另外兩個決定。完成時間只看 critical path，平行買到的是時間，不是錢。Harness 的邊界看要隔離什麼、什麼要活得久，不看 agent 有幾個。

1成本公式：六個乘數，分母要算成功的任務

這堂問一件事：agent 的錢花在哪裡，怎麼花才值得。規模感可以看 Claude Code 的官方文件：企業部署平均每位開發者每個活躍日約 $13，每月 $150–250（2026-11 查）。先定單位和公式，再談怎麼省。這裡只算 LLM 的費用，不算其他計算資源。

三個單位。Session 是你和 agent 的一段對話，從開啟到關閉。Turn 從你送出一則訊息開始，到 agent 回覆你結束。一個 turn 裡 model 通常要跑好幾次：它看完訊息決定呼叫一個 tool，harness 執行完把結果送回去，它再看一次。一次 model call 加上它要求的 tool call，就是一個 step。

成本是六項相乘。有了單位，一個產品的 agent 總花費可以寫成一條乘法：

乘法的好處是每一項可以單獨優化，任何一項減半，總成本就減半。Uber 用同一條公式管全公司的 agent 支出：2026 年 8 月的文章說，半年內週活躍使用者成長 7 倍，固定 model 的每 session 成本從 6 月高峰降了 52%，前兩項讓它長，中間幾項才是優化目標。乘法的陷阱是一項省下的錢，可能從另一項補回來，第 4 章專門算這件事。

本文補的：公式少了分母。這條公式算花了多少，沒有算買到什麼。L1 說過，agent 的目標是每個成功任務的成本；一個便宜的設定如果常常失敗，失敗那幾次的錢還是要付。要算它，先定義三項：

  • 每次嘗試的平均花費 c。成功和失敗的 run 都算進去。
  • 成功率 p。成功的 run 佔全部的比例，由測試或 grader 判定，量法是 L7 的主題。
  • Retry tax 1 ÷ p。平均要試幾次才成功一次。成功率 25%，就是 4 次的錢換 1 次成功。

2錢花在哪裡：大宗是重讀的 context

六個乘數裡，哪一項最值得動？先看錢實際花在哪裡。

每一步都重送整個 context。Model 沒有記憶，它只知道這次 request 裡寫了什麼，所以每一步 harness 都把 system prompt、tool 定義和整段歷史再送一次。

教授用全班的 Claude Code session log 量過。主 agent 每一步送進 model 的 token，中位數 200K–300K（Assignment 1 是 208K，Assignment 2 是 301K），p90 到 600K–700K；subagent 從乾淨的 context 開始，中位數約 80K，p90 約 200K。到第 500 步左右，context 累積到 650K–670K。

三種 token：量和單價方向相反。開頭和上一步完全相同的部分，serving 系統直接讀 prefix cache，叫 cache read。上一步沒出現過的內容要重新算一次，叫 fresh input，算完會寫進 cache，所以也叫 cache write。Model 自己產生的回覆叫 output。全班 Assignment 1 的 token 裡，97.6% 是 cache read。單價的方向相反，output 最貴，原因在 decode。把量乘上單價，才知道錢花在哪裡：

留在 context 裡的 token，之後每一步都再付一次。重送的另一面是：一段內容進了 context，留多久就付多少次。一份 20K token 的測試 log 留在 context 裡，又走了 50 步，光重讀就是 1M token；只留 500 token 的錯誤摘要，50 步是 25K，差 40 倍，model 需要的資訊都還在。換成錢，定義 T 是這段內容的 token 數，n 是之後還要走幾步，r 是 cache read 的倍率，寫入收 1.25×：

所以處理要在源頭：內容一進來就決定留多少，不要等 context 滿了再補救。怎麼做是 L4 的主題，這裡只看每個方向切在哪一段：

前情Compaction 與 L4 的四種 context 管理策略

L4 把 context 管理分成四種策略，依成本由低到高排：

  • Admission。決定什麼可以進來。
  • Offloading。把內容放在 context 外面，只留一個指標。
  • Transformation。依固定規則改寫已經在裡面的內容，例如截短、遮掉。
  • Compaction。請 model 把歷史摘要成一段狀態，取代原文。

前三種不呼叫 LLM，也幾乎無損。Compaction 要多一次 model call，而且不可逆。細節見 L4〈Context 管理〉。

3Prompt cache：沒命中的 token 貴 12 到 50 倍

第 2 章說重讀是大宗。重讀付得起，靠的是 prefix cache；它一失效，帳單就變成另一個數字。機制 L2 和 L4 講過，這裡只帶過，重點是把帳算完。

只比開頭，差一個字就從那裡開始重算。Model 讀 prompt 時，每個 token 都會算出一組中間結果，叫 KV cache，這些結果只和它前面的 token 有關。所以 provider 把算過的結果留一段時間，下一次 request 從第一個 token 開始比對，相同的那一段直接重用。L2 叫它 prefix cache，API 文件叫 prompt caching，是同一件事。Claude API 的順序是 tools → system → messages，越前面的東西改了，影響越大。

前情Prefill 與 decode：output 為什麼比 input 貴

L1 講過一個 request 分兩段。Prefill 一次處理整段輸入，幾千個 token 一起算，GPU 的算力用得滿。Decode 一次只產生 1 個 token，每產生一個都要把整個 model 的權重從記憶體讀一遍，瓶頸在記憶體頻寬，GPU 大半時間在等資料。

所以同樣一個 token，當 output 的成本比當 input 高得多，API 的定價把這個差距反映成約 5 倍。Cache read 連 prefill 都省了，只剩讀快取，所以更便宜。細節見 L1〈Prefill 與 decode〉。

算一次：compaction 幾步回本。假設 context 到了 200K，其中 20K 是 system prompt 和 tool 定義，留著。Compaction 把其餘的摘要成 5K，後面又重讀 15K 丟掉的檔案，所以 context 變成 40K。一次要付四筆（單位是 base input token，r = 0.1）：

  2. 摘要本身是 output。假設 3K，3K × 5 = 15K。

5少走幾步：先問要不要 LLM，再減 turn 與 step

第 2 章說長任務的成本由 model call 的次數決定。所以最有效的省法是少呼叫幾次，最徹底的做法是一次都不呼叫。

先問這一步需要 LLM 嗎。這是所有槓桿裡最大的一個：拿掉一步，等於這一步的成本歸零，而且沒有 model 的不確定性。

Claude Code 的 hook 就是這種步驟放的地方：格式化、跑測試、擋危險指令，都不必問 model。

少回頭：減少 turn。全班只有一個 prompt 的 session，Assignment 1 佔 68%，Assignment 2 佔 75%，多數同學一個任務開一個 session；少數同學跑 100 個 turn 以上的 marathon session，付的是第 2 章的平方。使用者會回來追問，通常是下面三個原因，目標是同一句話：agent 一次做完，不需要使用者中途介入。

8完成時間：看 critical path，錢看全部

前面都在講錢。時間是另一本帳：錢把每條分支加起來，時間只看最長的那一條。所以快和省常常同向，但不一定。

完成時間看 critical path。序列執行時，完成時間約等於每一步相加：排隊、環境準備、prefill、推理、tool 執行。平行執行時，把任務畫成相依圖，最長的那條路徑叫 critical path，它決定總時間，這個名字來自專案管理。

所以優化前先找最長的鏈。拆成幾份最划算要連派工的成本一起算，見 L5〈拆多細〉；加 agent 的上限見 L3〈Amdahl's law〉。

背景Speculative：這個名字從 CPU 和 speculative decoding 來

Speculative execution 是 CPU 的老技巧：遇到分支時先猜一邊執行，猜錯就丟掉結果。Speculative decoding 把它搬到 LLM serving：一個小的 draft model 先猜後面幾個 token，大 model 一次驗證整串。Part II 有一堂專門講它。

Speculative action 是同一個想法再往上一層：猜的對象從 token 變成 agent 的下一個動作。三者共同的代價都是猜錯時白做的工，共同的條件都是猜錯要能丟掉。

  1. 第 1 章 · 成本公式與分母

    成本公式的哪幾項是 agent 設計要壓低的？為什麼只看每次嘗試的花費，會選錯 model？

    參考答案與重點複習

    答案：設計要壓低後四項：Turns/Session、Steps/Turn、Tokens/Step、Price/Token。前兩項 Users、Sessions/User 隨採用度成長，代表有人用，不去壓它（第 1 章）。

    公式沒有成功率。失敗的 run 也要付錢，所以要算每個成功任務的成本，也就是每次嘗試的平均花費 ÷ 成功率。每次嘗試便宜的 model，成功率低時，每個成功任務可能更貴。

    重點拆解

    先分清單位。Session 是一段對話，turn 從使用者訊息到 agent 回覆，step 是一次 model call 加上它要求的 tool call。成本公式是乘法，任何一項減半，總成本就減半。

    上圖要這樣讀：c ÷ p 把失敗的錢也算進去，1 ÷ p 是平均要試幾次才成功一次，叫 retry tax。但只比 c ÷ p 也會選錯：gpt-oss-120b 最便宜，40 題裡穩定解出的只有 8 題，GPT-5.5 是 25 題。所以換強的設定之前，要算多成功一次得多花多少：($0.424 − $0.018) ÷ (0.67 − 0.33) ≈ $1.19，再拿它比這個任務成功一次值多少。

    背景補充

    製造業早就這樣算：每個良品的成本 = 每片的成本 ÷ 良率，所以晶片廠最盯良率。Retry tax 的 1 ÷ p 假設每次嘗試互相獨立；真實情況是有些題不管試幾次都不會過，這是 L7 分開看 pass@k 與 pass^k 的原因。

    常見誤解

    「單價低的 model 一定比較省。」單價只是公式的一項。便宜 model 多走幾步會把 Steps 和 Tokens 補回來，失敗多了分母又變小。要比每個成功任務的成本，再比多成功一次的成本。

    帶走這幾點
    1. 成本是乘法，設計只壓 turn、step、每步 token、單價四項。
    2. 每個成功任務的成本 = 每次嘗試的平均花費 ÷ 成功率 → 失敗的錢也算進去。
    3. 比完平均還要比邊際：多成功一次要多花多少，值不值得。

    相關：核心觀念〈成本公式：六個乘數，分母要算成功的任務〉；L1〈優化目標〉；L7〈pass@k〉。

  2. 第 2、3 章 · 重讀與 cache

    全班的 token 有幾 % 是 cache read？為什麼單價最低的 cache read 仍是最大一筆，而 cache 沒命中又更要緊？

    參考答案與重點複習

    答案：Assignment 1 的 token 有 97.6% 是 cache read。Model 沒有記憶，每一步都重送整個 context，所以重讀的量多約 100 倍；單價只低 10 倍，算下來仍佔約八成的花費（第 2 章）。

    沒命中的 token 要用寫入價重算，比命中的貴 12.5 倍（cache read 0.1×）到 50 倍（0.025×）。命中率從 99% 掉到 95%，input 的花費就多 41%（第 3 章）。

    重點拆解

    每一步的 token 分三種：cache read、fresh input、output。用課程給的典型比例，量是 100 : 1 : 0.2，單價是 1 : 10 : 50，花費就是 100 : 10 : 10，約 83%、8%、8%。較新的 model cache read 更便宜，比例會降到 56%–71%，但重讀仍是最大一筆。

    所以順序是先保住命中率，再縮小 context，最後才管 output。常見的破壞者：system prompt 放時間戳、中途改 tool 定義、換 model、改 messages 中間的一筆、停頓超過 TTL。TraceLab 量到新 input 裡有 81% 是 cache 過期後的重算，所以會停頓的互動 session 值得用 1 小時 TTL。

    重送還帶來平方：第 k 個 turn 送 kL，k 個 turn 共 L × k(k + 1) ÷ 2，turn 數加倍，總量約 4 倍。Cache 改的是係數，形狀不變。

    背景補充

    帳的形狀和計算機結構的平均記憶體存取時間（AMAT）相同：平均時間 = 命中時間 + miss rate × miss penalty。所以看 miss rate 比看 hit rate 準：99% 到 95% 看起來只差 4 個百分點，miss rate 卻從 1% 變成 5%，是 5 倍。

    常見誤解

    「開了 prompt caching，input 就自動省 90%。」只有開頭完全相同才會命中。System prompt 開頭放了時間戳，每個 request 都沒命中，寫入還要加價，比不開 cache 還貴 25%。用回應裡的 cache_read_input_tokens 確認。

    帶走這幾點
    1. 每一步重送整個 context → 大部分 token 是 cache read，算下來仍是最大一筆花費。
    2. 沒命中貴 12 到 50 倍 → 先保住命中率：不變的放前面、只在尾端加、會停頓就用長 TTL。
    3. 留在 context 的 token 每一步都再付一次 → 處理要在源頭。

  3. 第 4、7 章 · 反向成本與上限

    淨節省要怎麼算？為什麼 compaction 可能不划算？為什麼失敗的任務要早點停？

    參考答案與重點複習

    答案：淨節省 = 毛節省 − 反向成本，兩者要在同一組任務上量。Compaction 要先付一次摘要、寫入、重讀檔案的錢，之後每步才省，任務快結束時壓會虧；摘要漏了細節或 cache 已過期，回本點會再往後推（第 4 章）。

    每個成功任務的成本 = cs + cf × (1 − p) ÷ p，失敗的 run 常常走到上限才停，佔掉大半花費。把失敗早點停，比把成功的任務再省 20% 有效（第 7 章）。

    重點拆解

    省法當下看得到後面才付的
    Compactioncontext 變小丟掉的檔案要重讀，多一次摘要的 call
    Routing單價變低一個壞計畫多走很多步，或整次失敗
    Subagent主 agent 的 context 變小每個 subagent 重讀共用的檔案與指示
    Speculation少等 model猜錯的 token 白花，還搶同一批 tool

    反向成本常常比毛節省晚出現，所以只量一個時間點會高估節省。Agent 又有隨機性，比較兩個設定要用同一組任務、每題跑多次，一次只改一件事，看成功率、花費、p95 延遲三個指標。

    上限的數字從 trace 來：成功任務 p95 的 2 倍。上限之前還有進展檢查：verifier 通過、連續 N 步沒有新的測試通過、同一個錯誤重複出現。停下時交摘要：做了什麼、卡在哪裡、建議下一步。沒人看的任務一定要有硬上限；互動 session 有人在看，可見度比硬上限合適。

    背景補充

    Compaction 的帳和 garbage collection 同一個形狀：先付一次暫停，換之後每次配置變便宜；程式快結束時，那次暫停就賺不回來。Claude Code 的文件給的建議相同：/compact 挑告一段落的時候，換任務就用 /clear，它不花錢。

    常見誤解

    「上限訂得越低越省。」太低會切到本來會成功的任務，分母變小，每個成功任務反而更貴。所以上限從成功任務的 p95 往上留餘裕，再看切掉的 run 裡有多少本來會成功。

    帶走這幾點
    1. 淨節省 = 毛節省 − 反向成本 → 同一組任務、跑多次、一次改一件事。
    2. Compaction 要走幾步才回本 → 長任務趁 cache 還熱時壓，快結束不要壓。
    3. 失敗的錢佔大半 → 上限訂在成功任務 p95 的 2 倍，加上進展檢查，停下交摘要。

    相關：核心觀念〈淨節省：每個省法都有反向成本，要在同一組任務上量〉、〈上限：失控的任務要有人喊停〉；註〈Compaction〉；L6〈失敗分層〉；L7〈雜訊〉。進階題第 2 題從 trace 訂上限。

  4. 第 5、6 章 · 少走幾步與換 model

    最大的省錢槓桿是什麼？為什麼同一段對話中途換便宜的 model 可能更貴，交給 subagent 反而划算？

    參考答案與重點複習

    答案：最大的槓桿是把不需要推理的步驟從 model 手上拿走：步驟固定寫成 script，格式固定用 regex，窄的判斷用小的分類器。拿掉一步，這一步的成本就歸零（第 5 章）。

    Cache 綁 model。同一段對話換 model，整段 context 要用新 model 的寫入價重算，可能比留在原 model 讀 cache 還貴，換回來又重算一次。Subagent 從乾淨的小 context 開始，主對話的 cache 不動，所以便宜（第 6 章）。

    重點拆解

    少走幾步分兩層。Turn：使用者回來追問，通常是沒有計畫、agent 太早停、或沒檢查結果，對應的解法是先確認計畫、拆成附 done check 的子任務、交回前自我驗證。Step：互相獨立的動作放在同一步，4 次 model call 變 2 次，重讀的量就少一半。

    單步的選擇也分層：routing 選 model，effort 調想多久，output 管寫多長。第 6 章的表代入 2026-11-03 的單價，context 200K：留在 Opus 5.5 讀 cache 是 $0.04，換到 Haiku 5.5 是 $0.125，再換回來是 $1.00，開一個 20K context 的 subagent 只要 $0.0025。判準是同一句話：錯了也便宜的步驟才值得省，所以規劃留給大 model。

    Output 約佔花費的 8% 到 22%，不要從這裡開始。第一步是 schema：tool call 周圍的散文是純成本。

    背景補充

    「失敗才升級」是機器學習裡的 cascade：便宜的模型先過濾，難的才交給貴的，2001 年的 Viola–Jones 人臉偵測就這樣做。它的前提是有可靠的檢查，agent 的檢查常常就是測試有沒有過。

    常見誤解

    「每一步都選最便宜的 model 最省。」每換一次，context 就重新 prefill；一個便宜的規劃錯誤，還會浪費後面很多步。先算切換那一次的錢，再算切換之後能省幾步。

    帶走這幾點
    1. 先問這一步要不要 LLM → 拿掉一步，成本歸零，也沒有 model 的不確定性。
    2. 獨立的動作放同一步、換任務開新 session → 少重讀幾次整個 context。
    3. 換 model 選在 context 小的時候 → 便宜的工作交給 subagent，規劃留給大 model。

    相關：核心觀念〈少走幾步：先問要不要 LLM，再減 turn 與 step〉、〈Model、effort 與 output：錯了也便宜的步驟才值得省〉；L2〈Skill、MCP、hook〉；L3〈回答寫短真的好嗎〉。

  5. 第 8、9 章 · 時間與邊界

    平行執行時，完成時間由什麼決定？選 harness 架構時，為什麼不能只看 agent 的數量？

    參考答案與重點複習

    答案：由 critical path 決定，也就是最長的那條相依鏈。序列執行時才是每一步相加。錢把每條分支加起來，時間只看最長的一條，所以平行買到的是時間，不是錢（第 8 章）。

    課程的選法是單一 agent 用 monolithic，multi-agent 基礎設施用 microkernel。但把邊界推出去的理由不只共用：不可信的 code 要和 credential 隔開、session 要活得比 process 久，一個 agent 也會碰到。Anthropic 的 Managed Agents 就是這樣拆的（第 9 章）。

    重點拆解

    例子：plan 5 秒、A 20 秒、B 30 秒、merge 5 秒。序列 60 秒；平行 40 秒，路徑是 plan → B → merge。把 A 加速一倍仍是 40 秒，把 B 縮短 10 秒變 30 秒。所以先量再調：TraceLab 量到超過 1 分鐘的 tool call 只佔 4%，卻用掉 85% 的 tool 時間。

    三種架構的差別是呼叫跨過的邊界：函式呼叫、介面、協定。Monolithic 最簡單；modular 換 provider 不用改 agent；microkernel 的核心只留狀態、排程、安全，其他能力是外部服務。要不要把一條邊界推出去，問三個問題：不可信的東西要和秘密隔開嗎？狀態要活得比 process 久嗎？多個 agent 要共用同一份基礎設施嗎？

    背景補充

    Critical path 來自專案管理的 critical path method，不在路徑上的工作有空檔（slack）。三個架構的名字借自作業系統：Linux 是 monolithic kernel，檔案系統與 driver 都在 kernel 裡；MINIX 3、seL4 是 microkernel，driver 跑在 user space，用訊息溝通，換到隔離，付出 IPC 開銷。Modular 對應軟體設計的 dependency injection：程式依賴介面，不依賴實作。

    常見誤解

    「開 4 個平行 subagent，就快 4 倍，而且每個 context 更小，所以更省。」時間的下限是最長的分支加上 plan 與 merge；每個 subagent 又要重讀共用的檔案與指示，token 總量通常變多。

    常見誤解

    「Modular 抽出了 SandboxProvider，執行就隔離了。」介面是程式碼的邊界，不是安全邊界。Provider 在本機跑 Python，就和 monolithic 一樣沒有隔離。

    帶走這幾點
    1. 時間看 critical path，錢看全部 → 平行與 speculation 用 token 換等待。
    2. 調 model 之前先量 tool 時間 → 少數幾個慢的 call 佔掉大部分。
    3. 邊界一條一條判斷：隔離什麼、什麼要活得久、誰要共用 → 不是三選一，也不只看 agent 數量。

    相關：核心觀念〈完成時間：看 critical path，錢看全部〉、〈Harness 架構：邊界放在哪裡，看要隔離什麼、什麼要活得久〉；L3〈Amdahl's law〉；L5〈拆多細〉、〈Partial failure〉。進階題第 3 題替團隊選架構。

    三個槓桿：prefix 穩定讓 cache 生效、刪過時指令、按任務設 effort。成本與準確率不必互換。

    導讀數字來自廠商：當「存在證明」，不當規劃基線。對照 slides 的成本公式，問每個槓桿動的是哪個因子。

    摘要讀約 3 分；原文約 15 分

    一句話：三個槓桿：讓 prompt cache 命中、刪掉為舊 model 寫的指令、依任務調 effort。作者用自家 benchmark 證明成本可以降、準確率不降。

    跟這堂課的關係

    Slides p.21–24 的單價槓桿就是這三招：穩定 prefix、cache read、effort。見〈Prompt cache：沒命中的 token 貴 12 到 50 倍〉與註〈單價〉。文中的 hillclimb 把 eval 分成 train 與 test，對應核心觀念〈淨節省只能在同一組任務上量〉。Slides 把 compaction 列為反向成本的來源；這篇只提醒 compaction 會破 cache，沒有量它的代價。

    壓縮後的重點

    1. Cache 要 prefix 逐 byte 相同。Cache 綁 model，有 TTL。中途改 effort、system prompt 放時間戳、重排 tool 定義，都會打斷。Cache 重寫收 1.25× 的 input 價（1 小時 cache 收 2×）。靜態內容放最前面，tool 與 subagent 等超過 5 分鐘就改用 1 小時 TTL。
    2. 舊指令是成本也是錯誤。驗證儀式、強調語、強制 scratchpad、過期的 few-shot、互相矛盾的規則，都是為舊 model 打的補丁。案例：一個手動 scratchpad 讓 3 個 tool call 只寫在推理裡，沒有執行。
    3. 升級 model 先只換 ID，再審 prompt。6 個舊 prompt 從 Opus 4.8 搬到 Opus 5.5：只換 model ID 省約 18%，再跑 prompt-audit 多省 9%，準確率升約 2 個百分點。
    4. Effort 有報酬遞減。Fable 5 在 FrontierCode Diamond 最難的 50 題：low 11.5%、每題 $5.35；max 30.9%、每題 $19.00。Fable 5.1 在 Humanity's Last Exam：low 約 53%、每題約 $0.30；max 約 61%、約 $2.23。最後一級只多 0.5 分，多花 46% 成本。
    5. 換 model 可能比調 effort 更省。CursorBench 3.2 上，Fable 5.1 的 low effort 追平 Fable 5 的 high effort，成本約 1/3。Cache read 單價 $0.25/M 對 $1.00/M。
    6. 用 held-out 資料驗證每一次優化。客服 benchmark：Opus 5 low effort 加 prompt-audit 維持 98.9%，每張 ticket 2.6 美分。Sonnet 5 降到 1 美分但只有 88.9%，補兩條規則後回到 98.9%。14 張 held-out ticket：90.5% 對原設定的 78.6%，成本約 1/5。
    7. 公開 benchmark 的自動優化結果。以 Opus 5.5 為基線：LegalBench 省約 67%，thinking token 少 84%，準確率變動不到 1 分。tau2-bench retail 省約 73%，93% 的 prompt 可 cache。OfficeQA Pro 省約 72%。SWE-bench Verified 本來就有 cache，只省約 24%。

    原文怎麼讀

    • 可以跳過：Prompt cache 一節的機制說明，slides p.21 與本文第 3 章已講。Getting started 是指令清單。
    • 值得看原文：Instructions 一節的 anti-pattern 清單與 3 個失敗案例。Effort 一節的兩張成本對分數曲線。Automating cost reduction 的 4 個 benchmark 表，看每個案例動了哪幾個槓桿。
    • 時間：只讀摘要約 3 分；挑 Instructions、Effort、benchmark 表約 15 分。
    別誤讀

    「照做就能省 70%」不對。LegalBench 與 tau2 的節省來自 93% 可 cache 的 prompt 與 Batch API，條件是 prefix 穩定、工作能等。SWE-bench Verified 本來就有 cache，只省 24%。你的 workload 能省多少，取決於原本浪費了多少。

    用偏好資料學會把請求分流到便宜或強的模型。（11/30 routing 那一講會再用到）

    導讀它量的是單一請求的品質。Agent 裡便宜模型的早期錯誤會傳染到後面，要 end-to-end 再驗一次。

    摘要讀約 3 分；原文約 20 分

    跟這堂課的關係

    Slides p.22 的「開始前選」就是這篇，p.24 也列了它。見〈Model、effort 與 output：錯了也便宜的步驟才值得省〉與〈Routing：三種時機〉。這篇算成本時，GPT-4 每百萬 token $24.7，Mixtral $0.24，正好差約 100 倍。它只量單一請求的品質；slides p.22 與 p.25 說便宜 model 的一個壞計畫會多出很多步，這篇沒有量。節省多少看任務分布：同一套方法在 MT Bench 省 3.66×，在 MMLU 只省 1.41×。這呼應核心觀念〈淨節省只能在同一組任務上量〉。

    1. Router 只做一件事：估這題強 model 會贏的機率。機率低於門檻 α 就送弱 model。調 α 就在成本與品質之間移動。
    2. 資料來自 Chatbot Arena 的 80K 場對戰。依排行榜分數把 64 個 model 分成 10 層，前 2 層算強、第 3 層算弱。清理後剩約 65K 組比較，留 5K 驗證。

    5. 只用 Arena 資料，MT Bench 有效，MMLU 與 GSM8K 無效。Model 對是 GPT-4 與 Mixtral 8x7B。MT Bench 上 matrix factorization 的 CPT(50%) 是 25.32%，random 是 49.03%。MMLU 與 GSM8K 上四種 router 都接近或輸給 random，因為 Arena 的問題和這兩個 benchmark 不像。

    • 可以跳過：Section 2 Related Work；Section 4.2 的 router 公式；Section 5.3。
    • 值得看原文：Figure 1 右圖，看 PGR、CPT、APGR 怎麼從一條曲線讀出來。Table 1–3 的三組數字，對照有無增強的差距。Table 6 的成本比與 Table 7 的 router 開銷。

    「RouteLLM 比只用 GPT-4 省 3.66 倍」不對。Table 6 的比值相對 random router 算：同樣達到 50% PGR，random 送 49% 給 GPT-4，最佳 router 只送 13%。品質也只有 GPT-4 的 95%，而且只在 MT Bench；MMLU 與 GSM8K 只有 1.4× 到 1.5×。

  3. 推薦Beyond Accuracy: Unveiling Inefficiency Patterns in Tool-Integrated ReasoningarXiv 2604.05404 · 論文 · 2026 · 挑段約 20 分

    提出 Prefill Token Equivalents：把 tool call 的等待、臃腫的 tool 回應，都折算成硬體工作量。

    導讀實驗只有一組（256 請求、DeepSeek-V3.2、8×H200）。帶走指標的想法，不帶走數字。

    摘要讀約 3 分；原文約 20 分

    一句話：Token 數量不等於硬體成本。這篇提出 PTE（Prefill Token Equivalents），把每一輪重算的 context 和 decode 時讀 KV cache 的開銷，折算成 prefill token 的數量。用它量 13 個 model、5 個 benchmark，找出 4 種 tool 使用的低效模式，每種讓成本多 1.77× 到 2.42×。

    跟這堂課的關係

    Slides p.13–15 說每一步重讀整個 context 是成本大宗，見〈錢花在哪裡：大宗是重讀的 context〉。PTE 的第一項就是每輪重讀的 context。差別在假設：slides 的資料有 97.6% 是 cache read，這篇假設 tool call 的停頓讓 KV cache 失效，每輪全部重算。PTE 的第二項量留在 context 裡的 tool 回應，之後每個 decode step 都再讀一次，是 p.16 的道理，見〈留在 context 裡的 token，之後每一步都再付一次〉。p.32 說 tool 可能比 model 慢，要先量 tool 時間，見〈先量：時間常常花在 tool〉；這篇刻意排除 tool 執行與網路時間。Prefill 與 decode 的背景在 L1 p.30。

    壓縮後的重點

    1. PTE 把 decode 的記憶體開銷換算成 prefill token。公式是 PTE = Σ (D_prefill_i + γ · L_seq_i · D_decode_i)。D_prefill_i 是第 i 輪的全部 context，D_decode_i 是這一輪生成的 token。γ 由 model 的 KV cache 大小與 GPU 的算力頻寬比算出，H100 是 756.5 FLOPs/Byte。
    2. γ 很小，但乘上長 context 就不小。Qwen2.5-7B 的 γ 是 0.00329，DeepSeek-V3.1 只有 0.00068。每一步的 PTE 隨 context 成長，token 數反而集中在第一步。
    3. PTE 和實際延遲的相關係數 0.93，token 數只有 0.63。設定是 DeepSeek-V3.2、vLLM、8×H200、256 個請求同時送。用 API 價格加權的指標是 0.68 到 0.76。換 GPU，model 排名的 Spearman 都高於 0.95。
    4. 準確率相近的 model，PTE 可以差 10 倍以上。AIME24 上多個 model 約 70%，PTE 從幾千到 292,724（DeepSeek-V3.1-Terminus）。
    5. 4 種低效模式，各有偵測規則與成本倍數。Confirmatory tool usage：答案先出現、再呼叫 Python 確認，Qwen3-235B-Instruct 在 MATH500 有 81% 這樣做，PTE 1.77×。Tool-mixing：同一條 trajectory 混用搜尋與 Python，DeepSeek-V3.1-Terminus 在 WebInstruct 有 59%，PTE 2.42×。Lack of tool priors：tool 回傳空值或錯誤，例如忘了 print，Qwen2.5-72B 在 AIME24 有 33%，PTE 2.15×。Tool format collapse：tool 改名就出錯，Tongyi-DeepResearch 在 SimpleQA 100% 失敗，準確率 4.8%。
    6. 答錯的 trajectory 比答對的 PTE 高。5 個 benchmark 都如此，控制題目難度後仍成立。作者只說相關，不說因果。
    7. 這篇沒有提出解法。貢獻是指標與診斷。作者建議 agent 基礎設施解決 tool call 造成的 KV cache 失效，但沒有實驗。Limitations 承認 PTE 不含 API 延遲。

    原文怎麼讀

    • 可以跳過：Section 2 Related Work；Section 3.1，L1 已講；Appendix A 的 γ 推導；Appendix B.4 的 prompt 全文。
    • 值得看原文：Figure 1 的 KV cache 失效示意。Figure 4 的準確率對 PTE 散布圖。Table 7 的模式表。Appendix D 的 4 個案例。
    • 時間：只讀摘要約 3 分；挑 Section 3.2、Figure 4、Table 7、Appendix D 約 20 分。
    別誤讀

    「PTE 量的是整個 agent 的延遲」不對。它只算 transformer 的計算量，tool 執行與網路等待排除在外。它還假設每次 tool call 之後 context 全部重算；有 prefix cache 的服務不會這麼貴。帶走的是「context 變長後每個 decode token 都更貴」這個觀念，不是 PTE 的絕對值。

  4. 必讀Running a Software Factory Efficiently at Uber ScaleUber · 工程案例 · 2026 · 約 20 分

    組織規模的量產證據。成本拆成 users × sessions × turns × requests × tokens × price 的乘法。

    導讀用乘法拆解帶討論：你會先動哪個因子？cost per session 和 adoption 要分開看。

    摘要讀約 3 分；原文約 20 分

    一句話：Uber 把 agent 總支出拆成 6 個乘數，只壓中間 3 項。結果：用量成長 7 倍，固定 model 的每 session 成本從高峰降 52%，總支出自 4 月起持平。

    跟這堂課的關係

    Slides p.6–7 的成本乘法公式與這篇相同，見〈成本公式：六個乘數，分母要算成功的任務〉；差別是這篇把 steps/turn 叫 requests/turn，並明說前兩項要成長。文中的 tool schema 佔 50K–70K token、compaction 在 400K 觸發，對應〈留在 context 裡的 token，之後每一步都再付一次〉。Subagent 預設用便宜 model，對應 p.22 的 routing，見〈Routing：三種時機〉。

    壓縮後的重點

    1. 規模與結果。超過 70% 的 PR 由 agent 產出。2026 年 2 到 8 月，週活躍使用者成長 7 倍，週請求數成長 9.4 倍。固定同一個 model，每 1,000 次請求的成本降近 34%，每 session 成本從 6 月高峰降 52%。
    2. 公式：users × sessions/user × turns/session × requests/turn × tokens/request × price/token。前兩項是採用率，要成長。中間三項是 agent 在使用者要求之外多做的工，是優化目標。
    3. 每個 model 都要重新選。用真實工作建 benchmark，跑過能接任何 model 的 harness，選 Pareto 最佳的，frontier 變了就重跑。Subagent 預設用便宜的 model，主 model 負責拆解與評估。作者說這是影響最大的槓桿。
    4. Tokens/request 的四個預設。Compaction 在 400K token 自動觸發，1M window 的 model 也一樣。Effort 預設 Medium。互動 session 的 cache TTL 從 5 分鐘改為 1 小時，因為工程師常停超過 5 分鐘；subagent 維持 5 分鐘。Cache read 0.1×，5 分鐘寫入 1.25×，1 小時寫入 2×。
    5. MCP schema 不進 context。超過 100 個 tool 時，預載 schema 每個 prompt 多 50K–70K token，每個 turn 重送。解法：1,000 多個內部 tool 全做成 CLI 指令，加上 tool search 按需載入。一套 SaaS 工作套件的 49 個 tool 就佔約 22K token。
    6. Code-mode 讓 model 寫 script 批次呼叫。同一個 session 量 SQL 查詢：1 列結果從 903 token 降到 402，20 列從 1,600 降到 457，50 列寬表從 1,431,594 降到 900。批次工作省超過 90%。
    7. Requests/turn 靠 context graph。Agent 多數 turn 在找資料。AI Context Graph 有 2,400 萬個節點、8,000 萬條邊，接 30 多個內部系統。同一題有 graph 38 秒答對；沒有 graph 跑 20 分 9 秒，還答錯。
    8. 可見性代替硬上限。Status line 即時顯示 session 花費。Spend tier 是共用池，在 50%、80%、100% 發 Slack 提醒，沒有硬 cap。Session dashboard 自動標 16 種 anti-pattern，例如 40KB 的 MCP 回應留在 context、開場預載約 100,000 token 的定義。
