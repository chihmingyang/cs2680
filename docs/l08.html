導讀

先看一個例子。團隊的 agent（會自己讀檔、跑指令、連做很多步的 AI 程式）這個月的帳單比預期高出一大截。你把它用的語言模型（下面叫 model）換成便宜一級的，每個 token（model 計費的單位）的單價降了。下個月的帳單沒有降，做成的任務還變少了：便宜的 model 比較常失敗，失敗的任務要重跑，重跑的錢照付。

省錢的直覺常常是錯的，因為帳沒有算對。這堂不給一串省錢技巧，回答的問題是：帳要怎麼算，才知道該動哪一項。下面三條是這堂的判斷。

  • 帳要算到成功的任務。把全部的花費（失敗的那幾次也算）除以做成的任務數，得到每個成功任務的成本。例子裡總花費沒降、做成的任務變少，所以每個成功的任務反而更貴，換 model 是虧的（第 1 章）。
  • 最大的一筆是重送，先讓它便宜。Agent 每走一步，都要把到目前為止的全部內容重送給 model 一次，錢多半花在這裡。提供 model 的廠商會把你上一次送過、它已經處理過的開頭存起來，叫 cache。下一步送出的內容，開頭和上一次一字不差，這一段就是 cache hit，照折扣價收；讀不到 cache 的部分是 cache miss，cache miss 的 token 比 cache hit 的貴 12 到 50 倍。保住 cache hit 要讓開頭不變、cache 也還沒過期，不必丟掉任何內容，所以先做這件事（第 2、3 章）。
  • 其他的省法都有代價，要算扣掉代價之後省多少。例如把舊的對話濃縮成一段摘要：之後每一步重送的內容變少，這是省的；但做摘要本身要多呼叫一次 model，這是多付的。要再走幾步，省的才超過多付的。每個省法都這樣算 net savings（第 4 章）。

第 5 到 7 章是其他可以動的項目：少走幾步、換便宜的 model、替失控的任務設上限。完成時間是另一筆帳：幾個步驟同時跑能縮短時間，不能省錢（第 8 章）。Harness（包在 model 外面、替它執行動作的程式）的元件之間邊界放在哪裡，是另一個問題，在 L8b〈Harness Architecture〉。

核心觀念

帳怎麼算，錢和時間怎麼花才值得

八章：前四章把帳算對，接著兩章是壓低成本的槓桿，第 7、8 章分別講防止失控和完成時間。相關論文、系統層的手段和 speculation 的研究收在最後的〈查閱〉，需要時再查。

1成本：六個乘數，分母要算成功的任務

這堂問一件事：agent 的錢花在哪裡，怎麼花才值得。規模感可以看 Claude Code 的官方文件：企業部署平均每位開發者每個活躍日約 $13，每月 $150–250（2026-11 查）。先定單位和公式，再談怎麼省。這裡只算 LLM 的費用，不算其他計算資源。

三個單位。Session 是你和 agent 的一段對話，從開啟到關閉。Turn 從你送出一則訊息開始，到 agent 回覆你結束。一個 turn 裡 model 通常要跑好幾次：它看完訊息決定呼叫一個 tool，harness 執行完把結果送回去，它再看一次。一次 model call 加上它要求的 tool call，就是一個 step。

成本是六項相乘。有了單位，一個產品的 agent 總花費可以寫成一條六項的乘法（下圖上排）。中間三項（Turns、Steps、Tokens）取決於 agent 做一個任務時實際走過的路，也就是依序走過的 turn 與 step，叫 trajectory：少繞路、少回頭，這三項就小。

乘法的好處是每一項可以單獨優化，任何一項減半，總成本就減半。但一項省下的錢，可能從另一項補回來，第 4 章專門算這件事。

成功率。上圖的上排算的是花了多少錢，沒算換到幾次成功。Agent 做一次任務，從開始到結束叫一次 run；這裡把一個 session 當成一個任務，所以一次 run 就是一個 session。Run 可能成功也可能失敗，失敗的 run 一樣要付錢。所以 L1 說 agent 要看的是每個成功任務的成本，也就是上圖的下排：拿掉 Users 和 Sessions，從一個 session 的花費算起，再除以成功率。先看一個例子：

本文的判斷：c ÷ p 最低的，不一定該選。上表 c ÷ p 那一欄最低的是 gpt-oss-120b，約是 GPT-5.5 的 1/12。但 c ÷ p 背後有一個假設：每一題的成功率都是 p，失敗了就重跑，平均跑 1 ÷ p 次就成功一次。實際上 p 是 40 題混在一起的平均：同一個 model，有些題幾乎每次都對，有些題幾乎每次都錯。幾乎每次都錯的題，重跑多少次也難得成功一次，c ÷ p 卻看不出這件事。

上表最後一欄「穩定解出」就是在分這兩種題：6 次過 4 次的題，下面叫做得穩的題。Arize 的作者也提醒，gpt-oss-120b 便宜，部分原因是它只拿下自己做得穩的題。40 題裡，gpt-oss-120b 穩定解出 8 題，GPT-5.5 穩定解出 25 題，所以至少有 17 題是 GPT-5.5 做得穩、gpt-oss-120b 做不穩的。gpt-oss-120b 每次 run 很便宜，在這些題上失敗再多次，也只多付一點錢，所以它的 c ÷ p 很低。GPT-5.5 的成功裡，則有一部分來自這至少 17 題，而這些難題通常要跑更多步、花更多 token（作者沒有公布每題的花費，這是本文的推論）。所以兩個 c ÷ p 買到的是不同的成功，不能直接比大小：換成 gpt-oss-120b，帳單變小，產品做得到的事也一起變少。

那要怎麼比？兩個平均不能直接比，就改比差額：換成強的 model，多出來的那幾次成功，每一次多花多少錢。經濟學把這叫 marginal cost（邊際成本）：多買一單位，要多付多少。用 100 個任務、每個跑一次來算：

$1.19 值不值，要拿它比這個任務成功一次值多少。一個工程師自己做要半小時的任務，半小時的薪水遠超過 $1.19，多付這筆錢換一次成功很值得；一批可以重跑、錯了也無妨的分類，如果便宜的 model 多跑幾次也能做對，就不必多付這 $1.19。後面每一種省錢的做法，都分開看 c 和 p 怎麼變：它讓每次 run 的花費 c 少了多少，又讓成功率 p 掉了多少。p 沒掉，省下的就是淨省；p 掉了，就把省錢前的設定當「強」、省錢後的當「弱」，用上面的公式算每少成功一次省下多少錢，再拿它比成功一次值多少。

2每一步重送的舊內容最貴

第 1 章的六個乘數裡，哪一項最值得動？先看錢實際花在哪裡。

每一步都重送整個 context。一次 request 送給 model 的全部內容叫 context。Model 沒有記憶，它只知道這次 request 裡寫了什麼，所以每一步 harness 都把 system prompt（給 model 的固定指示）、tool 定義（它能呼叫哪些工具的說明）和整段歷史再送一次。從 harness 這邊看是重送，從 model 那邊看是重讀，下面這兩個詞指同一件事。

Context 就這樣越滾越大：開頭的 system prompt 和 tool 定義是固定的一段，之後每走一步，就再接上這一步新進來的內容（使用者的訊息或 tool 結果）和 model 的 output。Coding agent 讀一個檔案、跑一次測試，新進來的就是幾千 token；走個幾十步，context 就到幾十萬 token。

三種 token：重送的內容不必每次都從頭算。提供 model 的廠商（下面叫 provider）會把處理過的 context 留一段時間。下一步送來的 context，開頭和上一步完全相同的那一段，直接讀留下來的結果。這個機制叫 prefix cache。有了它，每一步的 token 分成三種，名字是 API 帳單上的叫法，各有各的單價：

先看量和單價這兩欄，方向相反：量最多的 cache read 單價最低，單價最高的 output 量最少。Cache read 便宜，是因為 provider 只要讀留下來的結果，不用重算。Output 為什麼最貴，要從 GPU 的帳算起，在第 3 章〈單價從哪裡來〉。兩欄相乘就是「花的錢」那一欄：cache read 的單價最低，仍佔約八成的花費。

圖上的單價是一組常見的比例。較新的 model 把 cache read 收得更低，只有圖上的一半到四分之一（見單價註）。這時 cache read 佔的比例會降到五到七成，仍是最大的一筆。

Cache 會過期，過期的舊內容要重算一次。Cache 只留幾分鐘，使用者停下來的時間常常更久。過期之後，同一段舊內容讀不到 cache，變成 cache miss，要重算一次，照 cache write 收錢。所以 cache write 裝了兩種內容：真正的新內容，和過期之後重算的舊內容。在上圖的單價欄，這等於同一個 token 從 cache read 那一列掉到 cache write 那一列：cache miss 的 token，錢是 cache read 的 12.5 倍。Cache read 收得更低的 model，最多差到 50 倍。

帳單上只看得到 cache write 的總量，分不出裡面哪些是新內容、哪些是過期之後重算的舊內容。華盛頓大學的 TraceLab（2026-06）分析自己實驗室的 coding agent session，逐段比對內容之前有沒有送過，把 cache write 拆開看：81% 是過期之後重算的舊內容，真正的新內容不到兩成。換算成花費：

Cache read 和重算的舊內容，付的都是重讀同一批舊內容的錢，兩項合計約佔花費的八成。

這決定了先動哪一筆。過期之後重算的那一部分，可以不丟任何內容就變便宜：cache 留多久可以設定（第 3 章算要多付多少），讓 cache 撐過使用者的停頓，這些舊內容就還是 cache hit，從 cache write 的價錢降成 cache read 的價錢。縮小 context 也能省，但要決定丟什麼，丟錯了要重做（本章最後一節與第 4 章）。Output 只佔一成上下，省掉一半也動不了多少。所以先保住 cache hit，再縮小 context，最後才管 output。

重送的總量隨 turn 數的平方成長。第 k 個 turn 要把前面 k − 1 個 turn 的內容重送一次。定義 L 是每個 turn 新增的 token 數，k 是 turn 數，第 k 個 turn 送 kL，全部加起來：

這個平方來自計費的方式：API 依 token 數線性收費，但每個 turn 都重送一次歷史，加總之後才變成平方。Prefix cache 讓重送的每個 token 變便宜，平方的形狀不變。同一條算式對 step 也成立，而且 step 比 turn 多得多，所以長任務的成本由 model call 的總次數決定。實務上，換任務就開新 session：一個 20 turn 的 session 送 210L，拆成兩個 10 turn 的 session 只送 110L，少了將近一半，代價是第二個 session 不記得第一個做過什麼。第 5 章講怎麼少走幾步。

留在 context 裡的 token，之後每一步都再付一次。重送的另一面是：一段內容進了 context，留多久就付多少次。一份 20K token 的測試 log 留在 context 裡，後面每一步都要再付一次它的錢。換成 500 token 的錯誤摘要，之後每一步重送的量就少 40 倍，model 需要的資訊都還在。

所以處理要在源頭：內容一進來就決定留多少，不要等它在 context 裡陪著走了幾十步才補救。做法是 L4〈Context 管理〉的主題，順序是先擋在外面（或存成檔案，context 裡只留檔案路徑），其次照固定規則截短，最後才請 model 把歷史摘要成一段。最後這一招叫 compaction，它要多一次 model call，丟掉的內容也拿不回來。第 4 章會算它幾步才回本。

前情Compaction 與 L4 的四種 context 管理策略

L4 把 context 管理分成四種策略，依成本由低到高排：

  • Admission。決定什麼可以進來。
  • Offloading。把內容放在 context 外面，context 裡只留檔案路徑這類指標。
  • Transformation。依固定規則改寫已經在裡面的內容，例如截短、遮掉。
  • Compaction。請 model 把歷史摘要成一段狀態，取代原文。

前三種照固定的規則做，不呼叫 model。Compaction 要多一次 model call，而且不可逆：摘要漏掉的內容拿不回來。細節見 L4〈Context 管理〉。

3Prefix cache

第 2 章說重讀是大宗。重讀付得起，靠的是第 2 章那個 prefix cache；它一失效，帳單就變成另一個數字。這一章先把它的帳算完：它怎麼比對開頭、幾個百分點的 cache miss 佔多少錢、什麼會打斷它、cache 該留多久、怎麼看自己的數字。最後換到價目表本身：能等的工作排隊處理可以打折，以及每一種 token 的單價從哪裡來。

只比開頭，差一個字就從那裡開始重算。Model 讀 context 時，每個 token 都會算出一組中間結果，這些結果只和它前面的 token 有關。所以 provider 留下來的結果只能從頭對起：下一次 request 從第一個 token 開始比對，相同的那一段直接重用，第一個不同的地方之後全部重算。Claude API 把 context 依 tools（tool 定義）→ system（system prompt）→ messages（對話歷史）的順序排，所以越前面的東西改了，要重算的越多。

Hit rate: 每一步送進去的 context 裡，cache hit 的 token 佔多少比例，叫 hit rate。第 2 章〈Cache 會過期〉算過：同一個 token，cache miss 時付的錢是 cache hit 時的 12.5 倍。所以 cache miss 的 token 就算很少，也會佔掉一大塊錢：

看上圖：hit rate 95% 聽起來很高，但 cache miss 的那 5% 付了四成的錢。Cache read 收得越低的 model，同樣的 5% 佔的比例越高。

Cache miss 收的比原價還高。Claude API 的 prefix cache 可以不開；不開時，每個送進去的 token 照原價收，這個原價叫 base input。開了之後，cache miss 的 token 要寫進 cache，收 base input 的 1.25×。所以每次都 cache miss，比不開 cache 還貴 25%。Claude Code 團隊因此對 hit rate 設告警，太低就當事故處理（他們的文章）。

實測也看得到這筆差距。Don't Break the Cache（2026-01）在同一組任務上故意破壞 cache 當對照組：開著 cache 的那一邊，成本低 28% 到 81%，依 model 而定；第一個 token 的等待時間（TTFT）則從進步 31% 到退步 9% 都有。省錢比較有把握，變快要自己量。

什麼會打斷它。從上面的機制可以直接推出來。要 cache hit，三件事都要成立：算的是同一個 model、開頭一字不差、上次留下的結果還沒過期。所以打斷它的動作也只有三類：

  • 開頭變了。例如 system prompt 裡放了時間戳、中途增減 tool 定義、改了 messages 中間的一筆（compaction 也算）。變的那一點之後全部重算，所以會變的內容只加在尾端。
  • 換了 model。中間結果是某一個 model 算出來的，別的 model 不能用，所以每個 model 各有一份 cache；換過去，整段 context 要重算（第 6 章算這筆帳）。
  • 等太久。停頓超過 cache 的壽命，留下的結果就丟了，見下面的〈TTL 的帳〉。

hit rate: 不要只看設定開了沒有，要看實際的數字。每個 API 回應的 usage 都分開列出 cache read 和 cache write 的 token 數，cache read 佔 input 總量的比例就是 hit rate。自架時看 server 自己的計數：以 vLLM（常見的開源 model 服務程式）為例，它的 /metrics 有 vllm:prefix_cache_queries 和 vllm:prefix_cache_hits，分別是查過 cache 的 token 數和其中 cache hit 的 token 數，兩者相除就是 hit rate（依 2026-11 的 vLLM 文件）。這兩個數字是整台 server 從啟動到現在、所有 request 的累計，所以要看某一段時間的 hit rate，就取前後兩個時間點的差再相除。

batch job : Batch 把 request 排隊處理，input 和 output 都打 5 折，多數在 1 小時內跑完，最長要等 24 小時。它適合批次跑評估題（eval）、回頭補算舊資料這類離線工作，正在和使用者互動的 agent 用不上。Batch 的折扣可以和 cache 疊，但同一批 request 什麼時候跑由 provider 決定，同時跑的讀不到彼此還沒寫好的 cache，所以 hit rate 不穩。一批常常跑超過 5 分鐘，所以共用同一段開頭的 batch 要搭配 1 小時 TTL。

單價從哪裡來：同一組 GPU，每秒處理幾個 token。上圖的倍率不是隨便訂的。Provider 的成本主要是 GPU 的時間，所以一個 token 的成本，約等於 GPU 每秒的花費除以它每秒處理幾個 token。Model 處理一個 request 分兩個階段：讀 input 的階段叫 prefill，產生回覆的階段叫 decode。比 input 和 output 的單價，就是比同一組 GPU 每秒能 prefill 幾個 token、能 decode 幾個 token。下面借 L9 算帳的那一組設定：Llama 3 70B，一個 700 億參數的 model，跑在 2 張 NVIDIA H200 GPU 上。Provider 不公開自己的成本，所以下面的數字是本文的推算，是理論上限，只看量級。

Prefill 卡在算力，叫 compute-bound。每個 input token 都要和全部權重各做一次乘法、一次加法。Prompt 裡的幾千個 token 一起算，權重從記憶體讀一次就給它們全部用，所以讀的時間不是問題，GPU 的運算單元一直是忙的。每秒能算幾個 token，看 GPU 每秒能做幾次運算。

Decode 卡在記憶體頻寬，叫 memory-bound。Decode 每一輪只替一個 request 產生一個 token，卻要把全部權重從 GPU 記憶體讀一遍。這裡的「一輪」是 GPU 算出一個 token 的一次計算，不是 agent 的一步；agent 的一步要跑幾百輪才產生一段回覆。運算單元多半在等資料，每秒能產生幾個 token，看 GPU 每秒能從記憶體讀幾 byte。batch 只有一個 request 時，兩個上限算出來差約兩百倍：

Batching 攤掉權重，攤不掉 KV cache。這裡的 batching 是 serving 系統把同時在跑的很多 request 排成一批、一起 decode，和上一節打折的 Batch API 是兩件事。權重讀一次，batch 裡每個 request 都拿它算出自己的下一個 token，權重的成本就攤給整個 batch。但每個 request 還要讀自己的 KV cache。KV cache 就是 3.1 說的「每個 token 算出的一組中間結果」，兩組向量，叫 K 和 V；新的 token 要回頭讀前文全部的 K、V，才算得出下一個 token，這一步叫 attention。Prefix cache 存的也是它。KV cache 只服務自己的 request，batch 再大也攤不掉。看下圖：

同一筆帳也解釋了價目表上的另外三個價格。三個都是本文的解讀，provider 沒有公開成本：

  • Cache read 最便宜。Prefix 的 KV cache 已經算好，連 prefill 的運算都省了。Provider 付的是把 KV cache 存著、再搬回 GPU 的成本。
  • Fast mode 比較貴。Batch 放滿時，每個 request 每秒約拿到 34 個 token，batch 只有它一個時約 68 個。要每個 request 都快，batch 就要小，同一組 GPU 服務的 request 變少，每個 token 分到的成本就高。官方沒說 fast mode 怎麼做，只說價格 2 倍、output 速度最多 2.5 倍。縮小 batch 是方向一致的一種方式，但它最多只換到 68 ÷ 34 = 2 倍的速度，2.5 倍還要靠別的手法。
  • Batch API 打 5 折。上面的帳假設 batch 一直放滿，實際上互動的 request 隨使用者來去，離峰時湊不滿；尖峰時 provider 還要留餘裕，因為 batch 越滿，每個 request 越慢（上一項）。Batch API 不用顧延遲，provider 可以把它排進離峰的空檔、湊滿再跑，GPU 的時間用得更滿。

GPU 為什麼算得快、讀得慢，以及 attention 讀 KV cache 為什麼吃不到 batching 的好處，見 L10〈Decode〉。

4Net savings：每個省法都有 added cost，要在同一組任務上量

前三章把帳算清楚，也講完了 cache。其他的省法多半有代價，這一章先講怎麼判斷一個省法真的有省：算 net savings、在同一組任務上量，最後把所有省法（cache 也算在內）排出先後，第 5、6 章講其中還沒講的幾項。紀律只有一條：每一招都能省，但帳面上省的不一定是真的。

每個省法都有 added cost。一個做法當下省了一筆，之後常常要多付另一筆，這一筆叫 added cost。最常見的是下面四個做法，前三個省錢，speculation 省的是時間：

  • Compaction。把歷史摘要成一段，取代原文。
  • Routing。依步驟改用便宜的 model（第 6 章）。
  • Subagent。把子任務交給另一個從乾淨 context 開始的 agent。
  • Speculation。先猜 model 的下一個動作，提早執行（第 8 章）。

數字是假設的，算法才是重點。本文的判斷：compaction 是長任務才回本的投資。任務快結束時不要壓；換任務時用 /clear，它清掉整段對話，下一則訊息從空的 context 開始，不需要 model 寫摘要，所以官方文件說它不花錢，代價是之前的內容全部不見；要繼續的長任務趁 cache 還熱時壓。還有一個趨勢值得注意：r 降到 0.05 時每步省的減半，三種情境的回本點變成 7、17、30 步。Cache read 越便宜，縮小 context 的回報越小，保住 hit rate 的回報越大。

真實系統的選擇也不同：Hermes Agent 在 context 用到 50% 就壓，Uber 等到 400K。OpenClaw 在壓之前，先讓 agent 跑一個使用者看不到的 turn，把重要的事寫進有日期的筆記檔（例如 memory/2026-11-06.md，存在 context 外面）。摘要漏掉的細節，之後還能從檔案搜回來，不必重做，等於替 added cost 買保險。

Net savings 只能在同一組任務上量。不同的任務本身步數就差很多，兩個設定若各跑一組任務，差別可能來自題目，而不是設定；同一個任務也有隨機性，跑兩次 step 數可能差一倍。所以比較兩個設定要用同一組任務、每題跑多次、看分布，方法見 L7〈雜訊〉與〈標準誤〉。題目還要分兩份：一份拿來調參，另一份沒用過的拿來報成績。Anthropic 的客服 benchmark 是例子：調參題上做到 98.9% 的新設定，在 14 張沒拿來調參的工單（held-out）上只有 90.5%，仍高於原設定的 78.6%，成本約是原設定的 1/5。拿來調參的題目不能拿來報成績，這是 L7 講的 leakage。

5少走幾步：先問要不要 LLM，再減 turn 與 step

第 2 章說長任務的成本由 model call 的次數決定。所以最有效的省法是少呼叫幾次，最徹底的做法是一次都不呼叫。

先問這一步需要 LLM 嗎。這是所有槓桿裡最大的一個：拿掉一步，等於這一步的成本歸零，而且沒有 model 的不確定性。

Claude Code 的 hook 就是這種步驟放的地方。Hook 是你在設定檔裡登記的 shell 指令，harness 在固定的時機自動執行它，例如每次編輯檔案之後、agent 要結束回合之前。格式化、跑測試、擋危險指令寫成 hook，就由 harness 直接跑指令，不必問 model。

少回頭：減少 turn。使用者每回來追問一次，就多一個 turn，整段歷史又重送一次。第 2 章算過，重送的總量隨 turn 數的平方成長：一個 100 turn 的 session，重送的總量將近十個 10 turn session 的十倍。使用者會回來追問，通常是下面三個原因，目標是同一句話：agent 一次做完，不需要使用者中途介入。

重用計畫與 skill，任務重複才回本。上次做過類似的任務，就把計畫或步驟拿回來，不要每次從頭推導，L2 的 skill 和 L6b 的 memory 都是放這些東西的地方。結論是一句取捨：任務重複出現時才回本，維護的成本和過期的條目可能把省下的吃掉。讓 agent 少找資料也屬於這一類，重用的是別人整理好的知識。Uber 的 context graph 把內部資料的 metadata 與使用紀錄整理成一張可以查詢的圖，約 2,400 萬個節點、8,000 萬條邊；agent 直接查哪張表最多人用，不必自己翻服務的程式碼。接上它之後，同一個問題 38 秒答對，沒接時跑了 20 分 9 秒還答錯，這是文章裡的單一案例，不是對照實驗。

6Model、effort 與 output：錯了也便宜的步驟才值得省

少走幾步之後，剩下的每一步還可以問三件事：用多強的 model、想多久、寫多長。三個都能省錢，也都可能讓成功率掉下來，所以這一章的判準只有一條：錯了也便宜的步驟才值得省。

Routing：三種時機。大 model 和小 model 的單價可以差幾十倍，而一個任務裡步驟的難度不一：找檔案、整理格式不需要最強的 model，規劃和除錯才需要。Routing 就是依步驟選 model：

三種時機都把一部分工作交給便宜的 model，所以都有同一個風險，一句話就是：便宜的 model 規劃錯一次，後面很多步都白走。所以規劃留給大 model，routing 只省執行的步驟。Uber 的做法指向同一邊：主 model 負責拆解與評估，subagent 預設用便宜的 model，作者說這個預設是他們影響最大的槓桿，但沒有單獨列出它省了多少（一家公司的經驗，不是對照實驗）。該不該換，用第 1 章的 c ÷ p 在自己的任務上算：換成便宜的 model，c 少了多少、p 掉了多少。

本文的判斷：換 model 要選在 context 小的時候。Cache 綁 model，每個 model 各有一份；換 model 時，整段 context 要照新 model 的 cache write 單價重算。換回原 model 時，原來那份 cache 若還沒過期（5 分鐘內），只要寫入換走之後新增的部分；若已過期，又要全部重算。下表代入 2026-11-03 的單價，context 200K：

單價會變，算法不變：大 model 的 cache read 可能比小 model 的 cache write 還便宜，換走太久再換回來更貴。所以「每一步重選」要算得過才用，便宜的工作交給一個乾淨 context 的 subagent 最划算，這也解釋了 Uber 那個槓桿為什麼有效。Claude Code 的 opusplan（規劃用 Opus、執行用 Sonnet）每切一次也是一次 model switch，官方文件有寫。

前情Reasoning model 與 effort：thinking token 也是 output

L4 講過 reasoning model：回答前先產生一段 thinking token，在裡面推理，再寫答案。能推理的 model 多半有一個 effort 參數，例如 Claude 的 output_config.effort，有的 API 用 thinking token 的預算。Thinking token 以 output 的價格計費。max_tokens 是一次回應最多能產生幾個 output token 的上限，thinking 也算在裡面，所以想得越多，留給答案的額度越少。Claude Code 用 /effort 調整。

Output：量最少、單價最高，但不要從這裡開始。第 2 章算過，output 只佔花費的一成上下，就算少一半，總花費也只少 5% 左右（L3 也用這個帳討論過回答寫短值不值得）。四層手段收在下表；第 4 層 effort 上一節講過，前三層裡第 3 層對 agent 最有用：schema 由 API 強制，不像 prompt 只是請求，而 tool call 周圍的散文是純成本：model 寫的「我接下來要搜尋……」沒有人讀，下一步還要重讀。

8完成時間：看 critical path，錢看全部

前面都在講錢。時間是另一本帳：錢把每條分支加起來，時間只看最長的那一條。工作只有一條鏈時，兩本帳算的是同一串步驟，少一步就同時省錢又省時間，所以快和省常常同向。工作拆成平行的分支之後，兩本帳才分開：加分支可能變快，但每條分支都要重讀共用的內容，錢通常變多。

完成時間看 critical path。序列執行時，完成時間約等於每一步相加：排隊、環境準備、prefill、推理、tool 執行。平行執行時，把任務畫成相依圖，最長的那條路徑叫 critical path，它決定總時間，這個名字來自專案管理。

所以優化前先找最長的鏈。拆成幾份最划算要連派工的成本一起算，見 L5〈拆多細〉；加 agent 的上限見 L3〈Amdahl's law〉。

先量：時間常常花在 tool。大家習慣先想換快一點的 model，但 build、測試、載入網頁可能比 model call 還慢。TraceLab 量到一次 model 生成平均約 13 秒，一次 tool call 平均約 18 秒；而且 tool 時間集中在少數幾次很長的 call：超過 1 分鐘的 call 只佔 4%，卻用掉 85% 的 tool 時間，1 秒內的 call 佔 61%，只用掉 1%。所以調 model 之前，先把每一次 tool call 的時間記下來，找出那幾次長的 call 是哪個 tool、在做什麼：

背景Speculative：這個名字從 CPU 和 speculative decoding 來

Speculative execution 是 CPU 的老技巧：遇到分支時先猜一邊執行，猜錯就丟掉結果。Speculative decoding 把它搬到 LLM serving：一個小的 draft model 先猜後面幾個 token，大 model 一次驗證整串。Part II 有一堂專門講它。

Speculative action 是同一個想法再往上一層：猜的對象從 token 變成 agent 的下一個動作。三者共同的代價都是猜錯時白做的工，共同的條件都是猜錯要能丟掉。

Tool 資料不進 contextCode execution with MCP 2025 從 150K 降到 2K token；Tool Search 2025 少 85% tool 定義的 token；Programmatic Tool Calling 2025 讓 model 寫程式呼叫 tool，在複雜的研究任務上 token 用量少 37%。
OutputConcise CoT 與 CCoT 2024 限制 chain of thought（CoT，model 回答前寫出的逐步推理）的長度；Chain of Draft 2025 草稿式推理；TALE 2024 推理預算；Ares 2026 每步選 effort；When to Plan 2025 只在有用時規劃；s1 與 L1 2025（兩篇論文的名字，這裡的 L1 不是第 1 講）強制 thinking 預算；Let Me Speak Freely? 2024 發現太嚴的格式可能傷推理；XGrammar、SGLang 2024、JSONSchemaBench 2025 是 schema 解碼工具；AdaEdit 2026 選 diff 或整檔；CodeStruct 2026 在 AST 層編輯；Tool-making agents 2026 把常用動作做成工具，output 少 58%。

查閱系統層的手段：單價的底線由誰決定

這三層 agent 設計者碰不到，但它們決定 Price/Token 的底線，Part II 會逐一講：

  • Model 本身。MoE 與 sparsity（每個 token 只用一部分參數）、quantization（權重用更少的 bit 存）、pruning（砍掉不重要的參數）、distillation（用大 model 教小 model）、針對 workload 的 fine-tuning。
  • Serving engine。Speculative decoding、KV cache 的優化、更好的 request 排程。
  • 硬體。更快的 kernel（在 GPU 上執行一個運算的程式，例如矩陣乘法；不是作業系統的核心）、更好的 kernel 排程、專用的加速器。

預測的來源有三種。Model-based：小的 draft model 預測大 model 的下一步。Self-speculative：同一個 model 在推理早期分一個叉，預測自己稍後的 tool call（SPORK）。History-based：用過去的 trace 預測下一個 tool，參數綁到上一步的結果（PASTE、Speculate with Memory）。無損的方法一律先驗證再保留結果；SPAgent 跳過一部分檢查換速度。
