先看這裡

這堂把 agent 的花費拆成一串乘數，再逐項壓低：turn 數、step 數、每一步的 input 與 output token、每個 token 的單價。全班 Claude Code 的資料給了基準：每一步送進 model 的 token 中位數 200K–300K，而且 97.6% 是重讀的 cache read，所以省錢先縮小 context。每個省法都有反向成本，淨節省要在同一組任務上量，每個任務都要有上限。後半講時間與結構：完成時間由 critical path 決定，平行與 speculation 用 token 換等待；harness 的架構決定邊界放在函式、介面還是協定，也就決定你能換什麼、能隔離什麼。

  • 大部分 token 是重讀的 context。每一步都重送整個 context，所以 cache read 的量是新內容的 100 倍；單價低 10 倍，算下來仍佔約八成的花費。省錢先縮小 context（丟掉過期的、縮小進來的、只載入需要的），再管 output（prompt、上限、schema、effort）。
  • 每個省錢手段都有反向成本。Compaction 要重讀檔案、重寫 cache；便宜 model 的壞計畫多走很多步；subagent 重讀共用的 context；speculation 猜錯就白花。淨節省 = 毛節省 − 反向成本，在同一組任務上量，再替每個任務設上限、訂停止規則。
  • 快和省是兩件事。完成時間由 critical path 決定，所以要先找最長的那條鏈再優化。平行與 speculative action 用更多 token 換更少等待；而 harness 的架構（monolithic、modular、microkernel）決定這些槓桿有沒有地方放。

A · 成本公式：錢花在哪裡

2.1成本公式：成本是一串乘數，設計只能壓低後四項，大宗是重讀的 context p.5–7、p.13–15

這一章先把三個單位分清楚，再把成本寫成一條公式，最後用全班的 Claude Code 資料看錢花在哪裡。這堂只算 LLM 的費用，不算 GPU 以外的計算資源（p.5）。

先分清 session、turn、step。一個 session 是你和 agent 的一段對話，從開啟到關閉。一個 turn 從你送出一則訊息開始，到 agent 回覆你結束。一個 turn 裡面，model 通常要跑好幾次：它先看你的訊息，決定呼叫一個 tool，harness 執行完把結果送回去，它再看一次，再決定下一步。每一次 model call，加上它要求的 tool call，就是一個 step。所以一個 turn 包含好幾個 step，一個 session 包含好幾個 turn（p.6）。下圖把三層畫出來。

成本是六項相乘。有了單位，成本可以寫成一條乘法（p.7）：Cost = Users × Sessions/User × Turns/Session × Steps/Turn × Tokens/Step × Price/Token。六項分三種性質：

  • Users、Sessions/User，隨採用度成長。人越多、每個人用得越勤，這兩項越大。它們代表產品有人用，所以 agent 的設計不去壓它們。
  • Turns/Session、Steps/Turn、Tokens/Step，隨 trajectory 的品質縮小。Trajectory 是 agent 從開始到完成走過的整條路：每個 turn、每個 step、每次送進 model 的內容。路走得越直，這三項越小。
  • Price/Token，隨單價縮小。同樣的 token，放在 cache 裡、放進 batch、交給便宜的 model，價格都不同。

乘法有一個好處：每一項可以單獨優化，而且 任何一項減半，總成本就減半。所以後面四章一章一個槓桿：turn 與 step（2.2）、input token（2.3）、output token（2.4）、單價（2.5）。乘法也有一個陷阱：一個槓桿省下的，可能從另一項補回來，2.6 專門講這件事。

全班的資料：每一步送多少 token。教授用全班 Claude Code 的 session log 畫了幾張圖。先看每個 step 送進 model 的 token 數（p.13）：主 agent 的中位數是 200K–300K，Assignment 1 是 208K，Assignment 2 是 301K；p90 到 600K–700K。Subagent 從乾淨的 context 開始，中位數約 80K，p90 約 200K。這些數字幾乎都是重送的 context：每一步只新增上一步的回覆和 tool 結果，其餘的 system prompt、tool 定義、整段歷史，每一步都原封不動再送一次。所以 context 會隨 step 數一路累積，到第 500 步左右，兩次作業的 context 都在 650K–670K（p.14）。

三種 token：量與價。每一步送進去的 token 分三種（p.15）。開頭和上一步完全相同的部分，serving 系統直接讀 prefix cache，叫 cache read；上一步沒出現過的新內容，model 要重新算一次，叫 fresh input，也叫 cache write，因為算完會寫進 cache；model 自己產生的回覆叫 output。三者的量差很多：fresh input 比 cache read 少約 100 倍，output 又比 fresh input 少約 5 倍。全班 Assignment 1 的 token 裡，97.6% 是 cache read。價格的方向相反：典型的比例是 cache read : input : output = 1 : 10 : 50。Output 貴，是因為它靠 decode 一個 token 一個 token 產生，每一步都要重讀整個 model 的權重。

前情Cache read 與 batch 的計價：兩種折扣怎麼疊

Prefix cache 從第一個 token 開始比對。開頭相同的部分直接讀快取，收 0.1× 的價格。中間改了一個 token，後面全部重算，寫入 cache 還要加價（Claude API 的 5 分鐘 cache 是 1.25×）p.21。

Batch 把能等的 request 排隊處理，input 與 output 都打 5 折，多數在 1 小時內完成。兩種折扣可以疊加，得到 0.05×。Opus 5.5 與 Sonnet 5.5 的 cache read 更低，是 0.05×。

前情Prefill 與 decode：input 和 output 為什麼價差 10 倍

L1 講過一個 request 分兩段。Prefill 一次處理整段輸入，幾千個 token 一起算，GPU 的算力用得滿，瓶頸在算力。Decode 一次只產生 1 個 token，每產生一個都要把整個 model 的權重從記憶體讀一遍，瓶頸在記憶體頻寬，GPU 大半時間在等資料。

所以同樣一個 token，當 output 的成本比當 input 高很多，API 的定價把這個差距反映成 5× 到 10×。Cache read 連 prefill 都省了，只剩讀快取，所以更便宜。細節見 L1 的註〈Prefill 與 decode〉。

把量和價相乘，才知道錢花在哪裡。下表用 slide 的兩組比例算一次：cache read 的單價最低，但量多 100 倍，算下來仍佔約八成的花費。這是整堂課第一個結論：省錢先縮小 context，再管 output。

這一章帶走什麼。成本是乘法，設計只能壓後四項；而在每一步的 token 裡，重讀的 context 是大宗。接下來的四章就照公式的順序走：先把 turn 和 step 的數量壓下來（2.2），再讓每一步的 input（2.3）和 output（2.4）變少，最後讓每個 token 更便宜（2.5）。每一章的技巧都附全班資料或論文的數字，讓你知道這個槓桿能省多少。

2.2Turn 與 step：turn 數是平方，step 要先規劃再批次 p.8–12

這一章看公式的前兩個槓桿。先用全班資料看 turn 數和 step 數的分布，再解釋為什麼 turn 數的影響是平方，最後講減少 turn 與 step 的具體做法。

全班的 turn 數：多數 session 只有一個 prompt。Slide p.8 統計每個 session 有幾個 turn。只有一個 prompt 的 session，Assignment 1 佔 68%，Assignment 2 佔 75%。教授說這是好事：多數同學一個任務開一個新 session。少數同學跑 marathon session，定義是 100 個 turn 以上。從 68% 到 75%，表示大家在第二次作業時更習慣一個任務開一個 session。為什麼這是好事，要先看 turn 的成本怎麼算。

為什麼 turn 數是平方。第 k 個 turn 開始時，harness 會把前 k − 1 個 turn 的內容全部放進 context 再送給 model，因為 model 沒有記憶，它要靠重讀歷史才知道前面做過什麼。假設每個 turn 新增 L 個 token，第 1 個 turn 送 L，第 2 個送 2L，第 k 個送 kL。加起來是 L × (1 + 2 + … + k)，約 k²/2 個 L。10 個 turn 送 55L，20 個 turn 送 210L，210 ÷ 55 ≈ 3.8，所以 turn 數加倍，總量約變 4 倍（p.9）。算式和圖在下面的註與第 3 段 Q1 的參考答案。

背景為什麼 turn 數是平方：p.9 背後的算式

假設每個 turn 新增 L 個 token。第 1 個 turn 送 L，第 2 個送 2L，第 k 個送 kL。總量是 1 到 k 的和乘上 L，約 k²/2 個 L。10 個 turn 送 55L；20 個 turn 送 210L，約 4 倍 p.9。

Prefix cache 讓重讀便宜 10 倍，但平方關係不變。所以換任務就用 /clear 開一段乾淨的對話。

這裡的平方來自計費，不是 model 內部的計算。API 按 token 數線性收費，但每個 turn 都把歷史重送一次，加總之後才變成平方。Prefix cache 讓重讀的部分只收 0.1×，它改變的是係數，形狀仍是平方。所以減少 turn 數有兩個方向：同一個任務要少追問，不同的任務要開新 session。

使用者為什麼回來追問，三個原因三個解法。Slide p.9 列出使用者回來的三種情況，每一種對應一個解法：

  • 沒有計畫。Agent 一開始就動手，做到一半才發現方向錯，使用者只好再講一次。解法是 front-load planning：先確認目標、列出計畫，再開始行動，而且只做一次。
  • Agent 太早停。它做完一部分就回覆，使用者看完再說「繼續」。解法是 structured task decomposition：把任務拆成子任務，每個子任務附一個「完成」的檢查，全部通過才算做完。
  • 沒有人檢查結果。Agent 交回來的程式碼沒跑過測試，使用者跑了才發現壞掉，又回來追問。解法是 self-verification before handoff：交回之前先跑測試、檢查輸出。

三個解法的目標是同一句話：agent 一次做完，不需要使用者中途介入。L2 的 plan mode 和 L3 的 Superpowers 流程，做的都是前兩件事。

全班的 step 數：中位數 3 到 4，長尾近 1,000。Slide p.10 統計每個 turn 有幾個 step。中位數只有 3（Assignment 1）和 4（Assignment 2），多數 turn 很短，教授認為原因是大家把 effort 設在 medium 或 high，model 一次就想得比較完整。但分布有長尾：有些 turn 跑了將近 1,000 步。這種 turn 的成本和 marathon session 一樣是平方成長，因為每一個 step 也要重讀整個 context。

一次 call 一個動作，還是先規劃再批次。Slide p.11 用同一個任務比較兩種做法。左邊是一次 call 一個動作：model 決定一個 tool call，harness 執行，model 再決定下一個，四個動作就是 4 次 model call。右邊是先規劃再批次：model 在第一次 call 就列出三個互相獨立的 tool call，harness 平行執行，結果一起送回去，model 再做一次 call 收尾。同樣的工作，4 次 model call 變成 2 次，而每一次 model call 都要重讀整個 context，所以省下的是兩次完整的 prefill。

四個減少 step 的做法。Slide p.11 把做法列成四條，前面的圖是第一條的例子：

  1. 批次獨立的 call。要讀五個檔案，就在一個 step 裡發五個 read，不要一步讀一個。條件是這五個動作互相獨立，一個的結果不影響另一個的參數。
  2. 重用計畫與 skill。上次做過類似的任務，就把那次的計畫或步驟拿回來照做，不要每次從頭推導。L2 的 skill 和 L6 的 memory 都是存放這些東西的地方。
  3. 一開始就載入 context。任務需要的檔案在第一步一起讀進來，不要做到一半才一個一個補。這和第一條是同一個道理，差別在時機。
  4. 每一次 model call 都重讀整個 context，所以 call 越少越便宜。這一條是前三條的理由，也是 2.1 公式裡 Steps/Turn 這一項的意義。

B · 槓桿：每一步少送一點，每個 token 更便宜

2.3Input token：留在 context 裡的 token，之後每一步都再付一次 p.16–17

這一章講第三個槓桿的 input 那一半。先講一條原則，再把 slide 的三個方向、七種做法逐一講清楚，最後看論文量到的數字。

一條原則：留在 context 裡的 token，之後每一步都再付一次。2.1 說過，每一步都重送整個 context。所以一段內容進了 context，不是付一次錢就結束：它留多久，就付多少次。算一個例子：一份 20K token 的測試 log 留在 context 裡，之後又跑了 50 步，光重讀它就要 1M token。如果只留 500 token 的錯誤摘要，50 步只要 25K，差 40 倍，而 model 需要的資訊都還在。這條原則有一個推論：處理要在源頭，內容一進來就決定留多少，不要等 context 滿了再補救。Slide p.16 把做法分成三個方向，下圖標出它們各在哪個位置動手。

方向 1：丟掉過期的。這是針對中段，前幾步留下、現在已經用不到的內容。Slide 列三種做法，harness 對 messages 陣列做的事不同：

  • 截短過期的結果。一個 tool 結果 model 已經讀過、也依它做了決定，harness 就把那一筆的內容換成前幾行加一句「… 共 2,000 行，已截短」。Model 還知道有這筆，但不再付整份的錢。
  • 遮掉用過的 tool 輸出。和截短類似，但更徹底：整筆內容換成一個佔位符，只留 tool 名稱和參數。L4 的 offloading 就是這一招。
  • 把歷史 compaction。把前面好幾個 turn 的內容請 model 摘要成一段「目前的狀態」，用它取代整段歷史。這是三種裡最有效的，也是唯一有損的：摘要可能漏掉後面要用的細節。
前情Compaction 與 L4 的四種 context 管理策略

L4 把 context 管理分成四種策略，依成本由低到高排：

  1. Admission。決定什麼可以進來。
  2. Offloading。把內容搬到 context 外面，只留指標。
  3. Transformation。改寫已經在裡面的內容，例如截短。
  4. Compaction。請 model 把歷史摘要成一段狀態，取代原文。

前三種不呼叫 LLM，也幾乎無損；compaction 要多一次 model call，而且不可逆。這堂 p.16 的「丟掉過期的」對應後三種，「只載入需要的」對應 admission。細節見 L4 的〈Context 管理〉。

方向 2：縮小進來的。這是針對右段，這一步新進來的 tool 結果。做法有兩種。第一種是壓縮 observation：測試跑完有 3,000 行輸出，只留失敗的那幾行和錯誤訊息，通過的部分一行「passed 212」帶過。第二種是 offload 到檔案：大的輸出先寫進一個檔案，context 裡只放路徑和一句摘要，model 需要時再用 read 去看它要的那一段。兩種做法都在內容進 context 的那一刻就動手，所以它們省下的是「每一步都再付一次」的全部。

方向 3：只載入需要的。這是針對左段，每一步都在的 system prompt、tool 定義與 memory。做法也有兩種。第一種是選擇性載入：只放這個任務相關的 tool 定義和 memory 條目，不把一百個 tool 全部塞進每個 request。L2 講的 skill 漸進載入就是這個想法：先只放名稱和描述，用到才載入全文。第二種是把探索隔離在 subagent 裡：找檔案、讀文件這類探索工作交給一個從乾淨 context 開始的 subagent，中間讀的幾十個檔案都留在它那裡，主 agent 只收到最後的摘要。2.1 的數字說明了效果：subagent 每一步的中位數約 80K，主 agent 是 200K–300K。

論文量到的數字。Slide p.17 列了四組研究，標 ADVANCED。這裡只記數字，因為它們告訴你每個方向大約能省多少：

  • 壓縮 agent 的歷史。
    • ACON（2025）。把 context 的峰值砍掉 26–54%。
    • Active Context Compression（2026）。讓 agent 自己決定何時 compaction，少用 23% 的 token。
    • TRACE（2026）。量到反面：摘要本身會造成重工，model 丟了細節之後要重做。
  • 把 context 當外部記憶。
    • MemGPT（2023）。把 context 當成快的那一層記憶，其餘放外面。
    • Scroll（2026）。保留一份無損的外部 log，由程式決定 model 看到哪一段。
  • 壓縮 prompt 本身。
    • LLMLingua（2023）。最多少 20 倍的 token，後續有 LongLLMLingua 與 LLMLingua-2（2024）。

  • 讓 tool 的資料不進 context。
    • Code execution with MCP（2025）。在程式裡先過濾結果，150K 降到 2K token。
    • Tool Search（2025）。少 85% 的 tool 定義 token。
    • Programmatic Tool Calling。少 37%。

四組數字指向同一個順序：最大的節省來自讓資料根本不進 context（第四組），其次是丟掉已經進來的（第一組）；而第一組裡 TRACE 的反例提醒你，有損的做法要量反向成本，2.6 會回到這裡。

2.4Output token：要求少一點，用 schema 與 effort 把範圍框住 p.18–20

這一章講第三個槓桿的 output 那一半。Output 的量最小，單價卻最高，而且它的長度完全由 model 決定，所以控制的方法和 input 不同：你要用 prompt、API 參數、schema、effort 四層把它框住。

Output 量最小，單價最高。2.1 的比例裡，output 的量只有 fresh input 的五分之一，單價卻是 input 的 5 倍、cache read 的 50 倍。原因在 decode：output 一個 token 一個 token 產生，每產生一個都要重讀整個 model 的權重（2.1 的註）。所以 output 不會是花費的大宗，但它是每一步的時間大宗，也是最容易白花的部分：model 多寫的每一句解釋、每一段重述問題，你都付 5 倍的價格，而且下一步還會當成 context 再讀一次。

2.5單價：同樣的 token，價格可以差 100 倍 p.21–24

這一章講第四個槓桿。前三章讓 token 變少，這一章讓每個 token 變便宜：先看價格表，再講拿到折扣的兩個條件，然後講 routing 把步驟分給便宜的 model，最後是留給後面課程的系統層手段。

價格表：從 0.05× 到 5×。Slide p.21 用 Claude API 的定價畫了一張相對價格表，以一般的 input token 為 1×，其他四種的價格：

  • Output。5×。
  • 放進 batch 的 input。0.5×。
  • 命中 cache 的 input。0.1×。
  • Batch 加 cache 疊起來。0.05×。

最貴和最便宜之間，5 ÷ 0.05 = 100 倍。同一個 token，送的時機和放的位置不同，價格就差兩個數量級。

條件 1：prefix 穩定，才有 cache。Prefix cache 的比對方式決定了它的條件。Serving 系統把上一次 request 算過的 KV cache 留著，下一次 request 從第一個 token 開始逐一比對，開頭完全相同的那一段直接重用，只收 0.1×；中間改了一個 token，後面全部重算，而且重算的部分寫入 cache 還要加價（2.1 的註）。所以 slide 的建議是維持穩定的 prefix：system prompt、tool 定義、早期的歷史放最前面，而且不要動它們；會變的內容，例如這一步的新訊息，放最後面。一個常見的失誤是在 system prompt 開頭放時間戳記，每個 request 從前幾個 token 就不同，cache 永遠不會命中。用 API 回傳的 cache read 數量確認命中率，不要只看設定。

條件 2：工作能等，才有 batch。Batch 把 request 排隊，serving 系統在 GPU 有空時一起處理，所以 能等的工作打 5 折（Claude API 多數在 1 小時內完成）。條件是這個工作能等：eval、backfill（回頭補算舊資料）、大量的離線任務都可以；正在和使用者互動的 agent 不行，它要即時回應。兩種折扣可以疊加，所以離線的 eval 跑在穩定的 prefix 上，就是 0.05×。

Routing：便宜的 model 做簡單的步驟。價格表裡還有一個沒畫出來的維度：model 本身。大 model 和小 model 的單價可以差十幾倍，而一個任務裡的步驟難度不一：找檔案、整理格式不需要最強的 model，規劃和除錯才需要。Routing 就是依步驟選 model。Slide p.22 列三種時機，決定的方式不同：

時機（p.22）怎麼決定適合風險
開始前選每個 turn 開始時，由一個 router 選定 model；router 可以用偏好資料訓練，也可以同時選 agent 的角色任務難度在開頭就看得出來一開始猜錯，整個 turn 都用錯的 model
失敗才升級先用便宜的 model，一個檢查沒過再換大的；檢查可以是學出來的 scorer、model 的自我驗證、或執行結果（測試有沒有過）有可靠的檢查可用失敗那次的花費白付，還要加時間
每一步重選trajectory 變長時依歷史和剩餘預算重選；一個 orchestrator 把各個 model 當 tool 呼叫長任務，難度隨步驟變化每次換 model，context 要重新 prefill

名詞Routing 的三種時機：便宜與貴的 model 怎麼分工

開始前選：每個 turn 開始時，由 router 選定一個 model。失敗才升級：先用便宜的 model，verifier 沒過再換大的。每一步重選：trajectory 變長時，依歷史與預算重選 p.22。

隱藏成本：KV cache 由 model 的權重算出，不能跨 model 共用。換 model 後，整個 context 要以 fresh input 的價格重新 prefill。「錯了很貴」的規劃步驟，值得直接用大 model。

系統層的手段，留給後面的課。單價還有一整層是 serving 系統決定的，slide p.23 先列出來，Part II 會逐一講：

2.6反向成本與上限：淨節省 = 毛節省 − 反向成本，每個任務都要有上限 p.25–27

前面四章每一招都能省，這一章講為什麼不能只看省了多少。先把四個主要的反向成本講清楚，再講替每個任務設上限和停止規則，最後問一個更根本的問題：這一步需要 LLM 嗎？

每個省法都有反向成本。Slide p.25 用四組對照把它說清楚，每一組的左邊是毛節省，右邊是它帶來的新花費：

  • Compaction 對 reconstruction。摘要讓 context 變小，但摘要丟掉的檔案內容，model 後面需要時要重新 read 一次；而且摘要取代了歷史，prefix 變了，cache 要整個重寫。
  • Routing 對更長的失敗。便宜的 model 單價低，但它一個壞的計畫會讓後面多出很多步，或整次失敗重來，這些步驟的錢加起來可能超過省下的差價。
  • Subagent 對重複的 context。主 agent 的 context 變小了，但每個 subagent 都要重讀共用的檔案和指示。開三個 subagent，共用的那部分就讀三次。
  • Speculation 對白做的工。先猜先跑省了等待，但猜錯的那次 token 全部白花，而且猜的動作和真的動作搶同一批 tool，可能讓真的那個變慢。

所以 slide 的公式是 淨節省 = 毛節省 − 反向成本，而且兩邊要在同一組任務上量。反向成本有一個性質：它常常比毛節省晚出現。Compaction 當下就看到 context 變小，重讀檔案發生在十步以後；routing 當下就看到單價變低，失敗的代價在任務結束才算得出來。只量一個時間點，會高估節省。下面的本文延伸講怎麼量才準。

替每個任務設上限。反向成本最大的形式是失控的任務：一個 agent 卡在同一個錯誤上重試，每一步都重讀越來越大的 context，花掉的錢比十個正常任務還多。Slide p.26 的做法是替每個任務設四個上限，數字從過去的 trace 定。先把成功任務依花費排序，取第 95 百分位的值，也就是 p95：95% 的成功任務花得比它少。上限訂在 成功任務 p95 的 2 倍：留一點餘裕給難一點的任務，再多就是失控。

C · 時間：快不等於省

2.7完成時間：看 critical path，平行與 speculation 用 token 換等待 p.28–38

前六章講錢，這一章講時間。先講為什麼兩者不同、完成時間由什麼決定，再把加速的四類槓桿講清楚，然後講 speculative action 這個用錢換時間的極端做法，最後是把這一切串起來的優化迴圈。

快和省是兩件事。Slide p.28 的副標題說：快的 agent 通常也比較省，但不一定。原因在 p.29 的兩條時間軸。序列執行時，一個 step 依序經過排隊、環境準備、prefill、推理、tool 執行、orchestration，完成時間約等於所有步驟相加，所以省掉的每一步都省時間。平行執行時，plan 之後兩個 worker 同時跑，最後 merge，完成時間等於最長的那一條相依鏈，叫 critical path；不在這條鏈上的工作有空檔，縮短它們不會讓任務提早完成。兩者於是分開：小 model 單價低，但可能多走幾步，結果更慢；平行減少等待，但每個 worker 都重讀共用的 context，token 總量變多。所以 總時間是最長的那條相依鏈，而錢是所有鏈的總和。

名詞Critical path：平行時決定總時間的那條鏈

把任務畫成相依圖，最長的那條路徑就是 critical path。例：plan 5 秒、A 20 秒、B 30 秒、merge 5 秒。序列 60 秒；平行 40 秒，路徑是 plan → B → merge p.29。

把 A 加速一倍，總時間不變。把 B 縮短 10 秒，總時間就少 10 秒。所以優化前先找出哪一條鏈最長。這個概念來自專案管理的 critical path method，第 3 段 Q4 的參考答案有圖。

槓桿 1：serving 層，省錢的手段都省時間。Slide p.30 只有一句話：前面講的每一個降低成本的技巧，同時也降低延遲。四個例子：

  • Turn 少、step 少。就少等幾次 model。
  • Token 少。Prefill 就短。
  • Cache 命中。Prefill 幾乎不用算。
  • 小 model。每個 token 的 decode 更快。

所以優化時間的第一步，就是先做完前六章。

槓桿 2：orchestration，harness 怎麼安排步驟。Slide p.31 列四招，都是 harness 的事，和 model 無關：

  • 非同步執行。一個 tool call 在跑的時候，harness 不要停下來等，先開始下一個不相依的步驟。
  • 持久的 session。讓一個 shell 或 browser 在整個任務期間保持開著，每一步都在同一個 process 裡執行；不要每個 tool call 都重新啟動一個 shell、重新 cd、重新載入環境。oh-my-pi 的做法就是這樣，2.8 會提到。
  • 串流中就開始。Model 的回覆是一個 token 一個 token 串流出來的。Tool call 的 JSON 一旦完整，harness 就可以先執行它，不必等整則回覆結束。
  • Tool 和 model 放在一起。把 tool 跑在 model 所在的同一台主機或同一個資料中心，每一步省掉一段網路來回。

槓桿 3：tool 本身，先量再調。Slide p.32 提醒一件大家常忽略的事：build、測試、載入網頁可能比 model call 還慢。所以在調 model 之前，先量每一步花在 tool 上的時間。有五招：

  • 快取 tool 的結果。重複的 read 和 search 直接命中。
  • 用更快的硬體。重的計算放在 server，不放在筆電。
  • 用更好的 tool。同一件事用更快、更便宜的 tool，而且只在需要時呼叫。
  • Fail fast。卡住的呼叫設 timeout，不要等。
  • 量每一步的 tool 時間。也就是上面說的，調 model 之前先量。

槓桿 4：平行，只對獨立的工作有效。Slide p.33 的例子：依序讀檔案 A、B、C，要等三次；三個一起讀，工作量相同，等待只剩三分之一。平行有兩個層次：一個 step 裡發出多個獨立的 tool call（2.2 的批次），以及把獨立的子任務交給平行的 subagent，各自做完回傳摘要再合併。條件只有一個：只有互相獨立的工作能平行；共用狀態的工作需要一個 merge 的步驟，而 merge 就在 critical path 上。

Speculative action：先猜、先跑、再比對。平行只能用在已知獨立的工作上。Slide p.34 再往前一步：連 model 還沒決定的下一個動作，也可以先猜先跑。做法分三步。第一，predict：一個便宜的 model 猜主 model 接下來會做什麼動作。第二，run early：主 model 還在想的時候，就先執行這個猜測。第三，compare：主 model 決定了，和猜測比對。猜中，結果已經在手上，等待整段省掉；猜錯，丟掉它，代價是一次白跑的 call。這個做法划算的條件有兩個：猜中的機率要夠高，而且動作要能撤銷，刪檔案、送出表單這類有副作用的動作不能先做。Slide 留了一個開放問題：GPU、CPU、API 的預算有限時，怎麼排程這些投機的呼叫，讓省下的 critical path 時間大於白做的工。名字的由來在下面的註。

背景Speculative：這個名字從 CPU 和 speculative decoding 來

Speculative execution 是 CPU 的老技巧：遇到分支時先猜一邊執行，猜錯就丟掉結果。Speculative decoding 把它搬到 LLM serving：一個小的 draft model 先猜後面幾個 token，大 model 一次驗證整串，對的留下，錯的從第一個錯處重來；因為驗證一串的成本和產生一個差不多，所以 decode 變快而結果不變。Part II 有一堂專門講它。

Speculative action 是同一個想法再往上一層：猜的對象從 token 變成 agent 的下一個動作。三者共同的代價都是猜錯時白做的工，共同的條件都是猜錯要能無痛丟掉。

三種架構，一句話：責任從程式碼移到介面，再移到服務。Slide p.40 把 harness 分成三種。Monolithic：所有東西在一個 runtime 裡，agent 自己包含 memory、tool、context、planning、execution。Modular：一個 controller 管 loop，但每個元件透過介面取用，provider 可以換。Microkernel：核心只留協調（狀態、排程、安全），memory、tool、execution 都是外部服務，透過標準協定連接。三者的差別可以用一句話概括：責任從 agent 的程式碼，移到介面，再移到服務。

Monolithic：agent 擁有一切。Slide p.41 的程式骨架長這樣：

優點：實作和除錯最簡單，元件之間沒有通訊開銷，內部狀態直接共用，執行開銷最低。缺點：換掉一個元件很難，因為它們耦合在一起；多個 agent 之間難以共用基礎設施；隔離難以強制，agent 的程式碼和它執行的程式碼在同一個 process。一句話：agent 擁有一切，全部在一個 runtime。

Modular：一個 controller 透過介面委派。Slide p.42 把同一個 agent 改成接收 provider：

Agent 仍然控制 loop，但每個元件透過一個介面取用，所以 換 provider，不用改 agent：把 Docker 換成 Firecracker（AWS 的輕量 microVM，啟動比 container 慢一點，隔離更強），只改一個 provider。優點：元件好替換、好測試、好擴充，責任分得清楚，第三方的實作可以接上。缺點：controller 仍然擁有所有元件的生命週期，協調的邏輯會越長越複雜；大家仍在同一個 process，一個 provider 掛了可能拖垮整個 agent；要同時調整幾個元件，還是要改 controller。

Microkernel：runtime 只協調，能力由服務提供。名字借自作業系統：microkernel 的核心只做最少的事，檔案系統、驅動程式都是核心外的服務。Slide p.43 的 agent runtime 只保留狀態、協調、排程、安全，透過一個標準協定連到三個服務：memory 服務（後面是資料庫）、tool 服務（後面是各種 tool API）、execution 服務（後面是一池 sandbox）。服務可以跑在不同的 container，甚至不同的機器。L2 講的 MCP 就是這種標準協定的例子，tool 那一條線已經有現成的協定可用。優點：每個服務獨立擴展，一個服務掛了不影響其他；隔離可以在架構層強制；基礎設施集中管理，多個 agent 共用。缺點：每次呼叫多一段網路來回，故障模式變多，一個任務的 log 散在好幾個服務裡，端到端除錯更難；而且要先有標準的協定和生命週期。所以 隔離、共用與擴展，換來的是通訊開銷與更多故障模式。

名詞Compare-and-swap 編輯：檔案改過就拒絕寫入

名稱來自 CPU 的 compare-and-swap 指令：先比對目前的值是否仍是預期值，相同才寫入。DeepSeek Harness 記下 model 讀檔時的版本，寫入前再比對一次 p.48。

Model 讀過之後，你或另一個 subagent 可能改了檔案。沒有檢查時，這次編輯會蓋掉別人的改動。oh-my-pi 的 hashline 編輯用行號指定位置，同樣需要這種檢查 p.51。

幾個設計直接對到這堂的公式。Pi 的 cache 預熱是 2.5 和 2.6 的合體：keep-alive 讓 cache 不過期，但它本身也要錢，所以 省下 $0.05 以上才送 keep-alive，這是把淨節省寫進程式碼。Hermes 在 50% 就 compaction，是把 2.3 的「丟掉過期的」做到最早，代價是 2.6 說的重讀；OpenClaw 在 compaction 之前先寫記憶，就是在付這個反向成本之前先保險。oh-my-pi 的持久 shell 是 2.7 orchestration 的第二招，hashline 則是 2.4 的「只輸出變動的部分」。Codex 先 sandbox 再問人，和 Claude Code 把判斷交給人或分類器，是兩種不同的假設，下面的本文延伸講這一點。讀 p.46–53 時，可以替每一個設計問同一個問題：它省了公式裡的哪一項，又付了什麼反向成本。

  1. p.7–9 · 成本公式與 turn

    成本公式的哪幾項是 agent 設計要壓低的？為什麼總成本隨 turn 數的平方成長？

    參考答案與重點複習

    答案：Agent 設計要壓低後四項：Turns/Session、Steps/Turn、Tokens/Step、Price/Token。前兩項 Users、Sessions/User 隨產品的採用度成長（p.7）。每一步都重送整個 context，所以第 k 個 turn 要重讀第 1 到 k−1 個 turn。加總是 1 + 2 + … + k，約 k²/2 個 turn 的量（p.9）。

    重點拆解

    先分清兩個單位。一個 turn 從使用者訊息開始，到 agent 回覆結束。一個 step 是一次 model call，加上它要求的 tool call。一個 turn 通常有好幾個 step（p.6）。

    成本公式是乘法（p.7）。任何一項減半，總成本就減半。Users 與 Sessions/User 變多，代表產品有人用，agent 設計不去壓它。設計能控制的是後四項：turn 數、step 數、每步的 token 數、單價。

    平方的算式：假設每個 turn 新增 L 個 token。第 1 個 turn 送 L，第 2 個送 2L，第 k 個送 kL。k 個 turn 共送 L × (1 + 2 + … + k) = L × k(k+1)/2。10 個 turn 是 55L，20 個 turn 是 210L。210 ÷ 55 ≈ 3.8，所以 turn 數加倍，總量約變 4 倍。

    全班的資料：只有一個 prompt 的 session，Assignment 1 佔 68%，Assignment 2 佔 75%；少數 marathon session 超過 100 個 turn（p.8）。使用者回來追問，原因是沒有計畫、agent 太早停、或沒檢查結果。對應的解法：先確認目標與計畫、拆成附 done check 的子任務、交回前自我驗證（p.9）。

    背景補充

    1 + 2 + … + k = k(k+1)/2 是等差級數的和。圖上的長條疊成三角形，而三角形面積和邊長的平方成正比，所以總量是 k 的平方。

    Prefix cache 讓重讀的部分只收 0.1× 的價格。它只改變係數，不改變形狀：總量仍是平方。一個 turn 裡的 step 也一樣：每次 model call 都重讀整個 context（p.11），所以 step 數多的 turn 也是平方成長。實務上，換任務就用 Claude Code 的 /clear 開一段乾淨的對話。

    常見誤解

    「平方成長是因為 attention 的計算量是 O(n²)。」不是同一件事。這裡的平方來自計費：API 依 token 數線性收費，但每個 turn 都把歷史重送一次，加總起來才變成平方。Attention 的 O(n²) 是 model 內部的計算量。

    帶走這幾點
    1. 成本是乘法：設計只壓低 turn、step、每步 token、單價這四項，任一項減半，總成本就減半。
    2. 第 k 個 turn 送 kL → 總量 L × k(k+1)/2 → turn 數加倍，成本約 4 倍。
    3. 減少追問：先規劃、拆成附 done check 的子任務、交回前自我驗證；換任務就開新 session。

    相關：核心觀念〈成本公式：成本是一串乘數，設計只能壓低後四項，大宗是重讀的 context〉、〈Turn 與 step：turn 數是平方，step 要先規劃再批次〉；註〈為什麼 turn 數是平方〉；L2〈一個 prompt，很多圈 loop〉。進階題第 1 題用實際單價再算一次。

  2. p.15–16 · 每一步的 token

    全班的 token 有幾 % 是 cache read？精簡 context 有哪三個方向？

    參考答案與重點複習

    答案：Assignment 1 的 token 有 97.6% 是 cache read（p.15）。p.16 的三個方向：

    • 丟掉過期的。截短舊 tool 結果、遮掉用過的 tool 輸出、compaction。
    • 縮小進來的。只留錯誤、大輸出寫進檔案。
    • 只載入需要的。相關的 tool 與 memory、探索交給 subagent。

    重點拆解

    Agent 每一步都重送整個 context。這一步新增的只有上一步的回覆與 tool 輸出。其餘部分和上一個 request 相同，所以直接讀 prefix cache。全班主 agent 每一步的 token 數，中位數 200K–300K，p90 600K–700K（p.13）。到第 500 步左右，context 約 650K–670K（p.14）。

    p.15 給了數量的比例：fresh prefill 比 cache read 少約 100 倍，output 又比 fresh prefill 少約 5 倍。價格比是 cache read : input : output = 1 : 10 : 50。Cache read 的單價只低 10 倍，量卻多約 100 倍，所以它仍是成本大宗。

    三個方向背後是同一句話（p.16）：留在 context 的 token，之後每一步都再付一次。所以要在源頭處理，不要等 context 滿了才處理。

    方向做法（p.16）省在哪裡
    丟掉過期的截短舊 tool 結果、遮掉用過的 tool 輸出、compaction、把舊 turn 摘要成狀態用過的內容，之後不再每步重付
    縮小進來的壓縮 observation、只留錯誤不留整份 log、大輸出寫進檔案只傳路徑新內容一進來就小
    只載入需要的只載入相關的 tool 與 memory；探索交給 subagent，只拿回摘要不需要的內容從頭就不進來
    例子

    一份 20K token 的測試 log 留在 context 50 步：20K × 50 = 1,000K，重讀 1M token。只留 500 token 的錯誤摘要：500 × 50 = 25K。差 40 倍，而且 model 需要的資訊都還在。

    背景補充

    Subagent 是第三個方向最常見的做法。它從乾淨的 context 開始，每一步的中位數約 80K，p90 約 200K（p.13）。讀檔、搜尋的中間結果留在 subagent 裡，主 agent 只收到最後的摘要。Skill 的漸進載入也是同一個想法：先只放名稱與描述，用到才載入全文。

    三個方向的風險不同。截短與只留錯誤，丟的是確定用不到的內容。Compaction 是有損的：摘要可能漏掉之後需要的細節，而且摘要改了 prefix，cache 要重寫。這是 B3 的反向成本。

    常見誤解

    「Cache read 只要 0.1×，所以 context 大一點沒關係。」單價低 10 倍，量卻多約 100 倍，cache read 仍是大宗。Context 變長，prefill 也變慢，model 也更難找到中間的資訊。

    帶走這幾點
    1. 每一步重送整個 context → 大部分 token 是 cache read（Assignment 1：97.6%）。
    2. 單價最低，不代表花費最少：量多約 100 倍 → 先縮小 context，再管 output。
    3. 丟掉過期的、縮小進來的、只載入需要的：留下的 token 每一步都要再付一次。

    相關：核心觀念〈成本公式：成本是一串乘數，設計只能壓低後四項，大宗是重讀的 context〉、〈Input token：留在 context 裡的 token，之後每一步都再付一次〉；L2〈漸進載入〉；L4〈Context 的成本〉、〈無損與有損的排序〉。

  3. p.21–25 · 單價與反向成本

    Cache read 與 batch 各把單價降到幾倍？為什麼每個省法都要算反向成本？

    參考答案與重點複習

    答案：Cache read 降到 base input 的 0.1×，前提是 prefix 保持穩定：system prompt、tool 定義、早期歷史放最前面，而且不改。Batch 降到 0.5×，前提是工作可以等，例如 eval、backfill（p.21）。每個省法都帶來新的花費，可能讓總花費變多，例如 compaction 後要重讀檔案、重寫 cache。所以淨節省 = 毛節省 − 反向成本，兩者要在同一組任務上量（p.25）。

    重點拆解

    p.21 的價格以 base input 為 1×：output 5×、batch input 0.5×、cached input 0.1×，batch 加 cache 是 0.05×。最貴和最便宜差 5 ÷ 0.05 = 100 倍。同樣的 token，放的位置和送的時機不同，價格就差兩個數量級。

    Cache 的條件來自它的比對方式。Prefix cache 從第一個 token 往後比對，相同的部分才讀快取。中間改了一個 token，後面全部以 fresh input 的價格重算。所以不變的內容放前面，會變的內容放最後。Batch 的條件是能等：eval、backfill、大量的離線工作。互動中的 agent 要即時回應，用不上 batch。

    p.25 列出四個省法各自的反向成本：

    省法毛節省反向成本（p.25）
    Compactioncontext 變小丟掉的檔案要重讀；摘要改了 prefix，cache 要重寫
    Routing便宜 model 的單價低一個壞計畫多出很多步，或整次失敗
    Subagent主 agent 的 context 變小每個 subagent 都重讀共用的檔案與指示
    Speculation少等待猜錯就浪費 token，還搶同一批 tool

    反向成本常常比毛節省晚出現，也更難看到。所以 p.26 再加一道保險：替每個任務設上限，數字從 trace 定，例如成功任務 p95 的 2 倍。

    背景補充

    寫入 cache 不是免費的。Claude API 寫入 5 分鐘的 cache，要付 1.25× 的價格。Cache 一段時間沒被讀到就失效，下一次又要重寫。Batch 在 Claude API 上 input 與 output 都打 5 折，多數在 1 小時內完成。

    Routing 還有一個隱藏的價格成本。KV cache 由 model 的權重算出，不能跨 model 共用。換 model 後，整個 context 要以 fresh input 的價格重新 prefill。

    常見誤解

    「開了 prompt caching，input 就自動省 90%。」只有開頭完全相同才會命中。System prompt 開頭放了時間戳記，每個 request 從前幾個 token 就不同，cache 永遠不會命中。用 API 回傳的 cache_read_input_tokens 確認命中率，不要只看設定。

    帶走這幾點
    1. 以 base input 為 1×：output 5×、batch 0.5×、cache read 0.1×、疊加 0.05× → 單價差 100 倍。
    2. Cache 要 prefix 穩定 → 不變的放前面，會變的放最後；batch 要工作能等。
    3. 淨節省 = 毛節省 − 反向成本 → 在同一組任務上量，再替每個任務設上限。

    相關：核心觀念〈單價：同樣的 token，價格可以差 100 倍〉、〈反向成本與上限：淨節省 = 毛節省 − 反向成本，每個任務都要有上限〉；註〈Cache read 與 batch 的計價〉、〈Routing 的三種時機〉；本文延伸〈淨節省只能在同一組任務上量〉；L2〈Prefix cache〉。進階題第 2 題從 trace 訂上限。

  4. p.29 · 完成時間

    平行執行時，完成時間由什麼決定？為什麼省錢和省時間會衝突？

    參考答案與重點複習

    答案：由 critical path 決定，也就是最長的那條相依鏈。序列執行時，完成時間才是每一步相加（p.29）。兩者會衝突：小 model 單價低，但可能多走幾步，結果更慢。平行減少等待，但 token 總量變多（p.29）。

    重點拆解

    p.29 畫了兩條時間軸。序列時，一個請求依序經過排隊、setup、prefill、推理、tool、orchestration，總時間約等於每段相加。平行時，plan 之後 worker A 與 B 同時跑，最後 merge。Merge 要等兩個 worker 都做完，所以總時間由較長的那條決定。

    下圖用 2.5 的註〈Critical path〉的數字算一次。A 不在 critical path 上，它做完後還要等 B 10 秒。把 A 加速一倍，總時間不變；把 B 縮短 10 秒，總時間就少 10 秒。所以優化前先找出最長的那條鏈。

    速度的槓桿分四類。省錢的手段多半也省時間：turn、step、token 變少，prefill 與 decode 都變短（p.30）。Orchestration：非同步執行、持久的 shell、串流中就開始 tool call、tool 與 model 放在一起（p.31）。Tool：快取結果、卡住就早點失敗，調 model 之前先量每一步的 tool 時間（p.32）。平行：獨立的 tool call 放在同一步，獨立的子任務交給平行的 subagent（p.33）。

    背景補充

    Critical path 來自專案管理的 critical path method。不在 critical path 上的工作有空檔（slack），縮短它們不會讓專案提早完成。把 agent 的 trace 畫成相依圖，就能用同一套方法找瓶頸。

    Speculative action 是用錢換時間的極端例子（p.34）。便宜的 model 先猜下一個動作並提前執行，主 model 決定後再比對。猜中就省下等待；猜錯，token 和 tool 時間都白花，而且有副作用的動作不能先做。

    常見誤解

    「開 4 個平行 subagent，就快 4 倍，而且每個 context 更小，所以更省。」時間的下限是最長的那條分支，加上 plan 與 merge。Token 方面，每個 subagent 都要重讀共用的檔案與指示（p.25），總量通常變多。平行買到的是時間，不是錢。

    帶走這幾點
    1. 序列：時間 = 每一步相加；平行：時間 = critical path，也就是最長的相依鏈。
    2. 只有縮短 critical path 上的步驟，完成時間才會變短 → 先找出最長的鏈，再優化。
    3. 便宜不一定快（小 model 多走幾步），快不一定便宜（平行與 speculation 多花 token）→ 時間與花費要分開量。

    相關：核心觀念〈完成時間：看 critical path，平行與 speculation 用 token 換等待〉；註〈Critical path〉；本文延伸〈便宜不一定快，平行不一定便宜〉；L3〈協調開銷決定平行加速的上限〉。

  5. p.40–44 · 三種 harness 架構

    三種架構的邊界各在哪裡？執行一段 Python 時，三者的路徑差在哪裡？

    參考答案與重點複習

    答案：Monolithic 沒有內部邊界：memory、tools、context、planning、execution 全在一個 runtime。Modular 的邊界是介面，controller 透過 SandboxProvider 這類介面使用元件。Microkernel 的邊界是協定，核心只留狀態、排程、安全，其他能力交給外部服務（p.40–43）。執行 Python 時，monolithic 在本機直接執行；modular 呼叫 SandboxProvider.run(code)；microkernel 送執行請求給執行服務，由它配置 sandbox、執行、回傳結果（p.44）。

    重點拆解

    p.40 用一句話串起三者：責任從 agent 移到介面，再移到服務。Monolithic 的 agent class 自己建立 memory、tools、context、planner、executor（p.41）。它簡單、好除錯、開銷低，但元件難替換，也難和別的 agent 共用。Modular 的 agent 接收可抽換的 provider：把 Docker 換成 Firecracker，只改一個 provider（p.42）。但 controller 仍管 lifecycle，元件仍可能在同一個 failure domain。Microkernel 的核心透過標準協定呼叫外部服務，服務可以放在不同機器（p.43）。它換到獨立擴展與故障隔離，代價是通訊開銷、更多故障模式、端對端除錯更難。

    p.44 用同一個動作比較三者。差別在誰負責 sandbox：monolithic 由 agent 自己執行；modular 由 provider 負責，但 controller 仍管它的 lifecycle；只有 microkernel 把 sandbox 的配置、隔離、lifecycle 交給獨立的服務。

    背景補充

    這三個名稱借自作業系統。Linux 是 monolithic kernel：檔案系統與 driver 都在 kernel 裡，彼此用函式呼叫。Microkernel（如 MINIX 3、seL4）只在 kernel 留排程、IPC、記憶體管理，driver 跑在 user space，用訊息溝通。取捨和 harness 一樣：隔離與可替換，換來每次呼叫的 IPC 開銷。

    Modular 對應軟體設計的 dependency injection：程式依賴介面，不依賴實作。Microkernel 需要的「標準協定」，在 tool 這一層就是 MCP 這類協定。Firecracker 是 AWS 開源的 microVM，隔離比一般 container 更強。

    常見誤解

    「Modular 抽出了 SandboxProvider，執行就隔離了。」介面是程式碼的邊界，不是安全邊界。p.45 把 modular 的執行隔離標為可選：provider 若在本機跑 Python，就和 monolithic 一樣沒有隔離。隔離來自 provider 的實作，例如 container 或 microVM。

    帶走這幾點
    1. 三種架構的差別是呼叫跨過的邊界：函式呼叫 → 介面 → 協定。
    2. 邊界越外面 → 隔離、替換、獨立擴展越強 → 每次呼叫的跳數與除錯成本也越高。
    3. p.45 的典型用途：單一 agent 用 monolithic，agent framework 用 modular，multi-agent 基礎設施用 microkernel。

    相關：第 1 段的三種 harness 架構圖；核心觀念〈Harness 架構：邊界放在函式、介面或協定，換來隔離與擴展，付出通訊與除錯〉；本文延伸〈Harness 的設計把假設寫進結構裡〉、〈Microkernel 只在共用基礎設施時回本〉；L2〈N×M 整合問題〉；L5〈Partial failure〉。進階題第 3 題替團隊選架構。

    4. Effort 有報酬遞減。Fable 5 在 FrontierCode Diamond 最難的 50 題：low 11.5%、每題 $5.35；max 30.9%、每題 $19.00。Fable 5.1 在 Humanity's Last Exam：low 約 53%、每題約 $0.30；max 約 61%、約 $2.23。最後一級只多 0.5 分，多花 46% 成本。
    5. 換 model 可能比調 effort 更省。CursorBench 3.2 上，Fable 5.1 的 low effort 追平 Fable 5 的 high effort，成本約 1/3。Cache read 單價 $0.25/M 對 $1.00/M。
    6. 用 held-out 資料驗證每一次優化。客服 benchmark：Opus 5 low effort 加 prompt-audit 維持 98.9%，每張 ticket 2.6 美分。Sonnet 5 降到 1 美分但只有 88.9%，補兩條規則後回到 98.9%。14 張 held-out ticket：90.5% 對原設定的 78.6%，成本約 1/5。
    7. 公開 benchmark 的自動優化結果。以 Opus 5.5 為基線：LegalBench 省約 67%，thinking token 少 84%，準確率變動不到 1 分。tau2-bench retail 省約 73%，93% 的 prompt 可 cache。OfficeQA Pro 省約 72%。SWE-bench Verified 本來就有 cache，只省約 24%。

    原文怎麼讀

    • 可以跳過：Prompt cache 一節的機制說明，slides p.21 與 t2 已講。Getting started 是指令清單。
    • 值得看原文：Instructions 一節的 anti-pattern 清單與 3 個失敗案例。Effort 一節的兩張成本對分數曲線。Automating cost reduction 的 4 個 benchmark 表，看每個案例動了哪幾個槓桿。
    • 時間：只讀摘要約 3 分；挑 Instructions、Effort、benchmark 表約 15 分。
    別誤讀

    「照做就能省 70%」不對。LegalBench 與 tau2 的節省來自 93% 可 cache 的 prompt 與 Batch API，條件是 prefix 穩定、工作能等。SWE-bench Verified 本來就有 cache，只省 24%。你的 workload 能省多少，取決於原本浪費了多少。

  2. 推薦RouteLLM: Learning to Route LLMs with Preference DataarXiv 2406.18665 · 論文 · 2024 · 挑段約 20 分

    用偏好資料學會把請求分流到便宜或強的模型。（11/23 routing 那一講會再用到）

    導讀它量的是單一請求的品質。Agent 裡便宜模型的早期錯誤會傳染到後面，要 end-to-end 再驗一次。

    摘要讀約 3 分；原文約 20 分

    一句話：用 Chatbot Arena 的人類偏好資料訓練 router，逐題決定送強 model 或弱 model。MT Bench 上達到 GPT-4 95% 的品質時，GPT-4 的呼叫次數只有 random router 的 1/3.66；換成別的 model 對，不用重訓也有效。

    跟這堂課的關係

    Slides p.22 的「開始前選」就是這篇，p.24 也列了它。見〈單價：同樣的 token，價格可以差 100 倍〉與註〈Routing 的三種時機〉。這篇算成本時，GPT-4 每百萬 token $24.7，Mixtral $0.24，正好差約 100 倍。它只量單一請求的品質；slides p.22 與 p.25 說便宜 model 的一個壞計畫會多出很多步，這篇沒有量。節省多少看任務分布：同一套方法在 MT Bench 省 3.66×，在 MMLU 只省 1.41×。這呼應本文延伸〈淨節省只能在同一組任務上量〉。

    壓縮後的重點

    1. Router 只做一件事：估這題強 model 會贏的機率。機率低於門檻 α 就送弱 model。調 α 就在成本與品質之間移動。
    2. 資料來自 Chatbot Arena 的 80K 場對戰。依排行榜分數把 64 個 model 分成 10 層，前 2 層算強、第 3 層算弱。清理後剩約 65K 組比較，留 5K 驗證。
    3. 四種 router。SW ranking 用 embedding 相似度加權 Bradley-Terry，不用訓練。Matrix factorization 學 model 與 query 的 embedding，BERT classifier 微調 BERT-base，causal LLM 微調 Llama 3 8B。最貴的 SW ranking 每百萬請求 $39.26，不到 GPT-4 生成成本的 0.4%。
    4. 指標是 CPT 與 APGR。PGR 是 router 補回的強弱差距比例。CPT(x%) 是達到 x% PGR 時，要送強 model 的最低比例。APGR 是 PGR 對成本曲線下的面積。
    5. 只用 Arena 資料，MT Bench 有效，MMLU 與 GSM8K 無效。Model 對是 GPT-4 與 Mixtral 8x7B。MT Bench 上 matrix factorization 的 CPT(50%) 是 25.32%，random 是 49.03%。MMLU 與 GSM8K 上四種 router 都接近或輸給 random，因為 Arena 的問題和這兩個 benchmark 不像。
    6. 資料增強後三個 benchmark 都贏。D_gold 是約 1,500 題 MMLU 驗證集，D_judge 是約 120K 筆由 GPT-4 判定的比較，花約 $700。增強後 MT Bench 的 CPT(50%) 降到 13.40%、CPT(80%) 31.31%。MMLU 最好約 35%，GSM8K 的 causal LLM 是 33.64%。
    7. 成本數字：MT Bench 3.66×、MMLU 1.41×、GSM8K 1.49×。這是 CPT(50%) 時 random router 與最佳 router 的 GPT-4 呼叫比。對應的品質是 GPT-4 的 95%、92%、87%（例如 MT Bench 8.8 分對 9.3 分）。CPT(80%) 時是 2.49×、1.14×、1.27×。
    8. 換 model 對不用重訓。Claude 3 Opus 對 Sonnet、Llama 3.1 70B 對 8B，MT Bench 上最佳 router 的 CPT(50%) 是 23.27% 與 21.18%，random 約 48–50%。和商用 router Martian、Unify AI 比，同品質下 GPT-4 呼叫最多少 40%。

    原文怎麼讀

    • 可以跳過：Section 2 Related Work；Section 4.2 的 router 公式；Section 5.3。
    • 值得看原文：Figure 1 右圖，看 PGR、CPT、APGR 怎麼從一條曲線讀出來。Table 1–3 的三組數字，對照有無增強的差距。Table 6 的成本比與 Table 7 的 router 開銷。
    • 時間：只讀摘要約 3 分；挑 Figure 1、Table 1–3、Table 6 約 20 分。
    別誤讀

    「RouteLLM 比只用 GPT-4 省 3.66 倍」不對。Table 6 的比值相對 random router 算：同樣達到 50% PGR，random 送 49% 給 GPT-4，最佳 router 只送 13%。品質也只有 GPT-4 的 95%，而且只在 MT Bench；MMLU 與 GSM8K 只有 1.4× 到 1.5×。

  3. 推薦Beyond Accuracy: Unveiling Inefficiency Patterns in Tool-Integrated ReasoningarXiv 2604.05404 · 論文 · 2026 · 挑段約 20 分

    提出 Prefill Token Equivalents：把 tool call 的等待、臃腫的 tool 回應，都折算成硬體工作量。

    導讀實驗只有一組（256 請求、DeepSeek-V3.2、8×H200）。帶走指標的想法，不帶走數字。

    摘要讀約 3 分；原文約 20 分

    一句話：Token 數量不等於硬體成本。這篇提出 PTE（Prefill Token Equivalents），把每一輪重算的 context 和 decode 時讀 KV cache 的開銷，折算成 prefill token 的數量。用它量 13 個 model、5 個 benchmark，找出 4 種 tool 使用的低效模式，每種讓成本多 1.77× 到 2.42×。

    跟這堂課的關係

    Slides p.13–15 說每一步重讀整個 context 是成本大宗，見〈成本公式：成本是一串乘數，設計只能壓低後四項，大宗是重讀的 context〉。PTE 的第一項就是每輪重讀的 context。差別在假設：slides 的資料有 97.6% 是 cache read，這篇假設 tool call 的停頓讓 KV cache 失效，每輪全部重算。PTE 的第二項量留在 context 裡的 tool 回應，之後每個 decode step 都再讀一次，是 p.16 的道理，見〈Input token：留在 context 裡的 token，之後每一步都再付一次〉。p.32 說 tool 可能比 model 慢，要先量 tool 時間，見〈完成時間：看 critical path，平行與 speculation 用 token 換等待〉；這篇刻意排除 tool 執行與網路時間。Prefill 與 decode 的背景在 L1 p.30。

    壓縮後的重點

    1. PTE 把 decode 的記憶體開銷換算成 prefill token。公式是 PTE = Σ (D_prefill_i + γ · L_seq_i · D_decode_i)。D_prefill_i 是第 i 輪的全部 context，D_decode_i 是這一輪生成的 token。γ 由 model 的 KV cache 大小與 GPU 的算力頻寬比算出，H100 是 756.5 FLOPs/Byte。
    2. γ 很小，但乘上長 context 就不小。Qwen2.5-7B 的 γ 是 0.00329，DeepSeek-V3.1 只有 0.00068。每一步的 PTE 隨 context 成長，token 數反而集中在第一步。
    3. PTE 和實際延遲的相關係數 0.93，token 數只有 0.63。設定是 DeepSeek-V3.2、vLLM、8×H200、256 個請求同時送。用 API 價格加權的指標是 0.68 到 0.76。換 GPU，model 排名的 Spearman 都高於 0.95。
    4. 準確率相近的 model，PTE 可以差 10 倍以上。AIME24 上多個 model 約 70%，PTE 從幾千到 292,724（DeepSeek-V3.1-Terminus）。
    5. 4 種低效模式，各有偵測規則與成本倍數。Confirmatory tool usage：答案先出現、再呼叫 Python 確認，Qwen3-235B-Instruct 在 MATH500 有 81% 這樣做，PTE 1.77×。Tool-mixing：同一條 trajectory 混用搜尋與 Python，DeepSeek-V3.1-Terminus 在 WebInstruct 有 59%，PTE 2.42×。Lack of tool priors：tool 回傳空值或錯誤，例如忘了 print，Qwen2.5-72B 在 AIME24 有 33%，PTE 2.15×。Tool format collapse：tool 改名就出錯，Tongyi-DeepResearch 在 SimpleQA 100% 失敗，準確率 4.8%。
    6. 答錯的 trajectory 比答對的 PTE 高。5 個 benchmark 都如此，控制題目難度後仍成立。作者只說相關，不說因果。
    7. 這篇沒有提出解法。貢獻是指標與診斷。作者建議 agent 基礎設施解決 tool call 造成的 KV cache 失效，但沒有實驗。Limitations 承認 PTE 不含 API 延遲。

    原文怎麼讀

    • 可以跳過：Section 2 Related Work；Section 3.1，L1 已講；Appendix A 的 γ 推導；Appendix B.4 的 prompt 全文。
    • 值得看原文：Figure 1 的 KV cache 失效示意。Figure 4 的準確率對 PTE 散布圖。Table 7 的模式表。Appendix D 的 4 個案例。
    • 時間：只讀摘要約 3 分；挑 Section 3.2、Figure 4、Table 7、Appendix D 約 20 分。
    別誤讀

    「PTE 量的是整個 agent 的延遲」不對。它只算 transformer 的計算量，tool 執行與網路等待排除在外。它還假設每次 tool call 之後 context 全部重算；有 prefix cache 的服務不會這麼貴。帶走的是「context 變長後每個 decode token 都更貴」這個觀念，不是 PTE 的絕對值。

  4. 必讀Running a Software Factory Efficiently at Uber ScaleUber · 工程案例 · 2026 · 約 20 分

    組織規模的量產證據。成本拆成 users × sessions × turns × requests × tokens × price 的乘法。

    導讀用乘法拆解帶討論：你會先動哪個因子？cost per session 和 adoption 要分開看。

    摘要讀約 3 分；原文約 20 分

    一句話：Uber 把 agent 總支出拆成 6 個乘數，只壓中間 3 項。結果：用量成長 7 倍，固定 model 的每 session 成本從高峰降 52%，總支出自 4 月起持平。

    跟這堂課的關係

    Slides p.6–7 的成本乘法公式與這篇相同，見〈成本公式：成本是一串乘數，設計只能壓低後四項，大宗是重讀的 context〉；差別是這篇把 steps/turn 叫 requests/turn，並明說前兩項要成長。文中的 tool schema 佔 50K–70K token、compaction 在 400K 觸發，對應〈Input token：留在 context 裡的 token，之後每一步都再付一次〉。Subagent 預設用便宜 model，對應 p.22 的 routing，見〈Routing 的三種時機〉。

    壓縮後的重點

    1. 規模與結果。超過 70% 的 PR 由 agent 產出。2026 年 2 到 8 月，週活躍使用者成長 7 倍，週請求數成長 9.4 倍。固定同一個 model，每 1,000 次請求的成本降近 34%，每 session 成本從 6 月高峰降 52%。
    2. 公式：users × sessions/user × turns/session × requests/turn × tokens/request × price/token。前兩項是採用率，要成長。中間三項是 agent 在使用者要求之外多做的工，是優化目標。
    3. 每個 model 都要重新選。用真實工作建 benchmark，跑過能接任何 model 的 harness，選 Pareto 最佳的，frontier 變了就重跑。Subagent 預設用便宜的 model，主 model 負責拆解與評估。作者說這是影響最大的槓桿。
    4. Tokens/request 的四個預設。Compaction 在 400K token 自動觸發，1M window 的 model 也一樣。Effort 預設 Medium。互動 session 的 cache TTL 從 5 分鐘改為 1 小時，因為工程師常停超過 5 分鐘；subagent 維持 5 分鐘。Cache read 0.1×，5 分鐘寫入 1.25×，1 小時寫入 2×。
    5. MCP schema 不進 context。超過 100 個 tool 時，預載 schema 每個 prompt 多 50K–70K token，每個 turn 重送。解法：1,000 多個內部 tool 全做成 CLI 指令，加上 tool search 按需載入。一套 SaaS 工作套件的 49 個 tool 就佔約 22K token。
    6. Code-mode 讓 model 寫 script 批次呼叫。同一個 session 量 SQL 查詢：1 列結果從 903 token 降到 402，20 列從 1,600 降到 457，50 列寬表從 1,431,594 降到 900。批次工作省超過 90%。
    7. Requests/turn 靠 context graph。Agent 多數 turn 在找資料。AI Context Graph 有 2,400 萬個節點、8,000 萬條邊，接 30 多個內部系統。同一題有 graph 38 秒答對；沒有 graph 跑 20 分 9 秒，還答錯。
    8. 可見性代替硬上限。Status line 即時顯示 session 花費。Spend tier 是共用池，在 50%、80%、100% 發 Slack 提醒，沒有硬 cap。Session dashboard 自動標 16 種 anti-pattern，例如 40KB 的 MCP 回應留在 context、開場預載約 100,000 token 的定義。

    原文怎麼讀

    • 可以跳過：Introduction 的成長敘事。Cost Equation 一節的公式推導，slides p.7 已講。What's Next。
    • 值得看原文：How We Measure 的 5 層指標表，是一份可以直接抄的儀表板清單。Code-mode 那張 5 列的 token 對照表。Figure 10 的 context graph 前後對照。Figure 12 的 dashboard 截圖（433 個 session、95% cache 命中）。
    • 時間：只讀摘要約 3 分；挑指標表、code-mode 表、Visibility 一節約 20 分。
    別誤讀

    「Uber 把 AI 總支出砍了一半」不對。降 52% 的是固定 model 下的每 session 成本，總支出只是持平，因為使用量同時成長 7 倍。Cost per session 與 adoption 是兩個指標，這篇刻意讓前者降、後者升。
