Harness Architecture

Advanced agent design I: Cost and performance — harness architecture

  • 同一份 slides另一半是 L8 Cost & Latency

先看這裡

先看一個例子。Anthropic 有一個替使用者在雲端跑 agent 的服務，叫 Managed Agents。Agent 是會自己讀檔、跑指令、連做很多步的 AI 程式；包在語言模型（下面叫 model）外面、替它執行動作的那一層程式叫 harness。這個服務一開始把三樣東西放在同一個 container（把程式和它要用的檔案包在一起、和別的程式隔開的執行環境）裡：這段對話的紀錄（session）、harness、跑 model 寫的程式碼的隔離環境（sandbox）。他們碰到三個問題。Container 一掛，整段對話就沒了。出了問題，從外面分不出是 harness 有 bug 還是 container 死了，要登進一個放著使用者資料的環境除錯。Model 寫的程式碼和登入用的憑證（credential）放在同一個地方，agent 讀到的網頁裡只要藏一段騙 model 的文字（這叫 prompt injection），model 就可能照著寫出讀取憑證的程式碼。這三個問題，只跑一個 agent 也會碰到。

這堂回答的問題是：跑 agent 的系統要拆成哪幾塊，塊和塊之間的邊界放在哪裡。例子裡的 session、harness、sandbox 就是三塊可以拆開的元件。L8 算的是錢和時間；邊界決定的是能換掉哪個元件、能隔離什麼、什麼掛了還能續跑。下面三條是這堂的判斷。

  • 邊界有三種：函式呼叫、介面、協定。例子裡三樣東西在同一個 container 的同一個程式裡，彼此是函式呼叫，最簡單也最快，但一個壞了全部一起壞，也分不出是哪一個壞了。抽成介面，元件可以換，但還在同一個程式裡，沒有隔離。用協定拆成獨立的服務，才能各自掛掉、各自換機器，代價是服務之間多了呼叫和故障，一個 request 出錯要到好幾個服務找 log（第 1 章）。
  • 拆邊界先看失敗與安全，agent 有幾個只是其中一題。例子裡 Anthropic 把這個服務拆成三塊：對話紀錄只追加、不修改，活得比另外兩塊久；harness 不存狀態，掛了就開一個新的，讀紀錄接著做；sandbox 碰不到憑證。拆完之後，第一個回應反而來得更快：快的不是每一次呼叫，而是用不到 sandbox 的對話，不必再等它準備好（第 2 章）。
  • 每一條邊界各問三個問題。不可信的東西要和秘密隔開嗎？狀態要活得比程式本身久嗎？多個 agent 要共用同一份基礎設施嗎？三題都答「否」，例如自己筆電上跑的小工具：不讀外部網頁也不碰秘密、對話斷了重開就好、只有這一個 agent 在用，函式呼叫就夠了（第 3 章）。

八個開源 harness 的設計重心在第 4 章，需要時查。這堂假設讀過 L2〈How Claude Code Works〉：harness 每一步做什麼，tool、hook、subagent、MCP 是什麼。

1 · 核心觀念

Harness 的邊界放在哪裡

四章：第 1 章是三種邊界，第 2 章是一個真實的拆法和它的理由，第 3 章是本文的判斷，第 4 章是八個 harness 的目錄，需要時再查。

1三種架構：邊界是函式呼叫、介面，還是協定

跑 agent 的系統有幾個元件：決定下一步的迴圈（狹義的 harness）、tool、memory、執行程式碼的 sandbox。它們之間，邊界放在哪裡？邊界可以是同一個程式裡的函式呼叫、可以抽換的介面，或跨機器的協定。它決定你能換掉哪個元件，也決定三件事：不可信的程式碼能不能和秘密隔開、狀態能不能活得比 process 久（harness 掛了還能續跑）、多個 agent 能不能共用同一份基礎設施；而且改起來比調參數貴得多。把一個元件搬到另一個 process 或服務、中間改用協定溝通，下面叫「把邊界推出去」。第 3 章用這三個問題決定每一條邊界。

三種架構，差在呼叫跨過什麼邊界。Monolithic 把一切放在同一個 process，modular 讓一個 controller 透過介面委派，microkernel 的核心只留協調，能力都是外部服務。決定下一步的迴圈在三種架構裡名字不同：monolithic 裡是 planner（決定下一步）加 executor（照著執行），modular 裡是 controller，microkernel 裡是 core 的 runtime；執行程式碼的元件則分別是 executor、sandbox provider、execution 服務：

Microkernel 的名字借自作業系統：核心只做最少的事，檔案系統和驅動程式都是核心外的服務。L2 講的 MCP 就是讓 tool 跑在 agent 程式外面的標準協定。Modular 的程式裡也可以用 MCP 接 tool：那一條邊界是協定，其他元件仍在同一個 process。

同一個動作，三條路徑。用「執行一段 Python」比較三者：

Execution 服務如果還是很抽象，可以先玩互動導讀〈Execution 服務：誰替 agent 真正動手〉：同一段 Python 在三種架構裡一步一步跑、故意讓它當掉或刪檔、看 sandbox 被回收，大約 15 分鐘。

取捨在哪裡。結論是 microkernel 用簡單和低開銷，換隔離、共用與擴展；常見的選法是看 agent 的數量：單一 agent 用 monolithic，multi-agent 基礎設施用 microkernel，modular 是中間最常見的起點。第 2 章是這條選法的反例。

2拆邊界的理由：失敗與安全，不是 agent 的數量

一個 agent 也可能要把邊界推出去。第 1 章用 agent 的數量當選擇依據。「先看這裡」的例子，Anthropic 的 Managed Agents（2026-04），是一個反例。他們一開始把 session、harness、sandbox 放在同一個 container，碰到三個和 agent 數量無關的問題：container 掛了，session 就沒了；harness 的 bug、斷線、死掉的 container 從外面看都一樣，除錯要 shell 進一個可能放著使用者資料的環境；model 寫的 code 和 credential（API key、OAuth token 這類登入憑證）在同一個地方，一次 prompt injection（藏在網頁或檔案裡的指令，騙 model 照著做）就能叫 code 讀出 credential。於是拆成三塊（下圖的 harness，就是第 1 章那個決定下一步的迴圈）：

結果和第 1 章的表有一處相反：跨邊界之後反而變快，第一個 token 的等待時間（time to first token，TTFT）p50 降約 60%、p95 降超過 90%。原因不在跨邊界本身：以前每個 session 都要先等 container 準備好，連用不到 sandbox 的 session 也一樣，拆開之後要用時才配。這是一家公司的經驗，不是對照實驗，文章也沒有談多出來的服務邊界要多少維運成本。

3三個問題：每一條邊界各問一次，不數 agent

本文的判斷：問三個問題，不數 agent。邊界不必一次全推出去，也不必三種架構選一種。每一條邊界各問它值不值得：

問題答「是」就推出去代價
不可信的東西要和秘密隔開嗎？Sandbox 和 credential 分開，秘密放在 sandbox 外面多一段 proxy，多一種故障
狀態要活得比 process 久嗎？Session log 放在 harness 外面，掛了能續跑每一步多一次寫入，要設計 log 的介面
多個 agent 要共用同一份基礎設施嗎？Tool、memory、sandbox 池做成服務要有協定與版本，一掛全部受影響

三題都答「否」，例如自己筆電上跑的小工具：不讀外部網頁也不碰秘密、對話斷了重開就好、只有這一個 agent 在用，函式呼叫就夠了，microkernel 的優點用不到，只付代價。至於大家最擔心的通訊開銷，數字上通常不是問題：華盛頓大學分析 coding agent session 的 TraceLab（L8 第 2 章）量到一次 model 生成約 13 秒，資料中心內的一次 RPC 通常是毫秒級，差上千倍。真正的代價是故障模式和除錯：一個 request 經過好幾個服務，出錯時 log 散在各處。所以每個 request 要帶 trace id，也就是在第一站產生、往下每個服務都原樣傳下去並寫進 log 的一個 ID；出事時用它把各服務的 log 串回同一個 request，見 L5〈Observability〉。

4目錄：八個 harness 的設計重心

每個 harness 都把一個假設寫進結構。第 3 章的同一個問題，各家 harness 的答案不同，因為它們假設的部署環境不同。以第一題（不可信的東西要和秘密隔開嗎）為例：Codex CLI 先 sandbox 再詢問，假設隔離比詢問可靠，人問多了會不看就同意；Claude Code 的權限模式把判斷交給人或分類器，假設環境不一定能隔離。兩種假設都可能成立。讀下面八個 harness 時，可以問每個設計背後假設了什麼。

Pi最小核心：四個 tool，沒有 MCP、subagent、核准，其他都靠 extension。Cache 預熱有價格檢查：每送一次 keep-alive 都要付錢，所以只在預期省下 $0.05 以上時才送 keep-alive（在 prompt cache 過期前送一個 request 續命，見 L8〈TTL 的帳〉）。函式庫給別的專案用：pi-ai 支援 42 家 model 供應商、10 種 wire API。功能一多，核心就難維護，所以功能交給使用者用 extension 自己換（第 1 章的 modular）；keep-alive 本身要錢，送了可能不划算；同一套程式要能接很多家 model 供應商，也讓別的專案重用
oh-my-piHashline 編輯：每個 edit 帶一個 4 位 hex 的內容雜湊和行號，model 不必重打舊文字。IDE 在 process 裡：一個 shell 跨所有呼叫保持開著，原生 tool 提供搜尋、AST、LSP、debugger。特殊的 context 方法：snapcompact 把舊的 turn 畫成密集的文字圖片，能讀圖的 model 讀它約只要原文 1/3 的 input token；TTSR（Time Traveling Stream Rules）的規則平常不放進 context，model 的 output 一出現符合某個 regex 的內容，就停下生成、把那條規則加進對話、重新生成。舊的 edit 要 model 把整段舊文字重打一次，output token 多；每次呼叫都重開 shell 要等；context 成本：舊歷史變便宜，規則只在用到時才佔 context
OpenClaw聊天 gateway 加 queue lane：27 種聊天頻道的訊息都可以進來；每個 session 只有一條 lane（佇列），不管訊息來自哪個頻道，都排進同一條，一次只跑一個 turn；queue mode 決定 agent 執行中收到的新訊息是插進目前這一輪、排到下一輪，還是中斷目前這一輪。Compaction 之前先寫記憶：先跑一個使用者看不到的 turn（silent turn），寫下有日期的筆記；之後的 recall 結合全文搜尋和向量搜尋。Fence、taint、sentinel：fence 隔離不可信的文字；讀過網路的 turn 標成 taint；agent 監看 secret 的 sentinel。同一個 session 同時收到很多訊息時，兩個 turn 同時跑、互相搶 session 狀態；compaction 丟掉的細節之後找不回來；prompt injection 與洩密
Hermes Agent會學習的 fork：harness 每隔一段時間發一次提醒（nudge），這時背景另開一個 agent 的分身（執行時複製出來的 agent，不是程式碼的 fork），回顧剛才的 turn，再修改 memory 和 skill，不碰正在進行的對話。最早的 compaction：context 用到 50% 就 compaction，八個裡最早。執行前先存：tool call 先寫進 session 資料庫，才允許副作用發生。同一類任務每次都要重新摸索做法；context 塞滿之前就壓，控制成本；tool call 中途斷掉時，從資料庫知道做到哪裡

「解什麼問題」是本文的對照。Claude Code 的機制在 L2。

名詞Compare-and-swap 編輯：檔案改過就拒絕寫入

名稱來自 CPU 的 compare-and-swap 指令：先比對目前的值是否仍是預期值，相同才寫入。DeepSeek Harness 記下 model 讀檔時的版本，寫入前再比對一次。

Model 讀過之後，你或另一個 subagent 可能改了檔案。沒有檢查時，這次編輯會蓋掉別人的改動。oh-my-pi 的 hashline 編輯用行號指定位置，而檔案一改，行號就可能指到別的行，所以同樣需要這種檢查。它的 edit 除了行號，還帶一個從檔案內容算出的 4 位 hex 雜湊；雜湊和檔案目前的內容對不上，harness 就拒絕這次 edit。L5〈Consistency〉用同一個機制處理這種互相蓋掉的寫入（lost update）。

2 · 動手試試

照著做一次

兩項都不用寫程式，合計約 25 分鐘。

玩互動導讀：execution 服務

同一段 Python 在三種架構裡一步一步跑、故意讓它當掉或刪檔、看 sandbox 怎麼回收：Execution 服務：誰替 agent 真正動手，大約 15 分鐘。玩完再回頭看第 1 章那張「同一段 Python 的三條路徑」。

替你自己的 agent 回答三個問題

挑一個你在用或想做的 agent，照第 3 章的三個問題，一題寫一段：答案、要推出去的是什麼、多出來的代價是什麼。答「否」的題目不推，元件之間留著函式呼叫。

寫完拿第 4 章的八個 harness 對照：你的答案和哪一個 harness 的設計最像。
