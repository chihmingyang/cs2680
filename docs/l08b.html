Harness Architecture

Advanced agent design I: Cost and performance — harness architecture

導讀

Anthropic 有一個替使用者在雲端跑 agent 的服務，叫 Managed Agents。它一開始把三樣東西放在同一個 container 裡：這段對話的紀錄（session）、包在 model 外面替它執行動作的程式（harness）、執行 model 寫的程式碼的地方（sandbox）。他們碰到三個問題。Container 一掛，session 就跟著沒了。出了問題，從外面只看得到它沒回應，分不出是 harness 有 bug 還是 container 死了，工程師要登進這個放著使用者資料的 container 才能除錯。使用者交給 agent 的登入憑證（credential）也在這個 container 裡：agent 讀到的網頁只要藏一段騙 model 的文字（這叫 prompt injection），model 在 sandbox 裡寫出來的程式碼就可能把憑證讀走。這三個問題，只跑一個 agent 也會碰到。

這堂回答的問題是：跑 agent 的系統要拆成哪幾塊，塊和塊之間用哪一種邊界。例子裡的 session、harness、sandbox 就是三塊可以拆開的元件。邊界指的是兩塊之間怎麼互相呼叫；它決定能換掉哪個元件、能隔離什麼、什麼掛了還能續跑。

  • 邊界有三種：函式呼叫、介面、協定。例子裡三樣東西在同一個 container 裡直接互相呼叫，這是函式呼叫：最簡單也最快，但一個壞了全部一起壞，也分不出是哪一個壞了。抽成介面，元件可以換，但還在同一個程式裡，沒有隔離。用協定拆成獨立的服務，才能各自掛掉、各自換機器、給好幾個 agent 共用，代價是服務之間多了呼叫和故障，一個 request 出錯要到好幾個服務找 log（第 1 章）。
  • 拆不拆先看失敗與安全，不先數 agent 有幾個。例子裡 Anthropic 把這個服務拆成三塊：對話紀錄只追加、不修改，活得比另外兩塊久；harness 不存狀態，掛了就開一個新的，讀紀錄接著做；sandbox 碰不到憑證。拆完之後，第一個回應反而來得更快（第 2 章）。
  • 每一條邊界各問三個問題。外部網頁、email 和 model 寫的程式碼都不可信，要讓它們碰不到憑證嗎？狀態要活得比程式本身久嗎？多個 agent 要共用同一套 tool 和 sandbox 嗎？三題都答「否」，例如只在自己筆電上跑的小工具，函式呼叫就夠了（第 3 章）。

八個開源 harness 各自的設計重心，整理在最後的〈查閱〉一章，需要時再翻。這堂假設讀過 L2〈How Claude Code Works〉：harness 每一步做什麼，tool、hook、subagent、MCP 是什麼。

核心觀念

Harness 的邊界放在哪裡

三章：第 1 章是三種邊界，第 2 章是一個真實的拆法和它的理由，第 3 章是本文的判斷。

1Harness 架構：Monolithic、Modular、Microkernel

跑 agent 的系統（廣義的 harness）有幾個元件：agent loop（狹義的 harness：反覆呼叫 model、執行它要的動作）、tool、memory、執行程式碼的 sandbox。這一章的問題是：它們之間的邊界放在哪裡。邊界有三種：同一個程式裡的函式呼叫、可以抽換的介面、跨 process 或跨機器的協定。把一個元件搬到另一個 process 或服務、中間改用協定溝通，下面叫「拆出去」。

邊界決定你能換掉哪個元件，也決定三件事：不可信的程式碼能不能和秘密（例如 credential，也就是 API key、OAuth token 這類登入憑證）隔開；狀態能不能活得比 process 久（harness 掛了還能續跑）；多個 agent 能不能共用同一份基礎設施。第 3 章就用這三件事決定每一條邊界。邊界寫進了程式的結構，事後要改就得重寫元件之間的呼叫。

邊界的種類：函式呼叫（monolithic）、介面（modular）、協定（microkernel）。三種架構的差別，是元件之間的呼叫跨過哪一種邊界。同一個角色在三種架構裡名字不同，對照如下；表後是同一件事的圖。

比較項目MonolithicModularMicrokernel
邊界函式呼叫介面協定

Microkernel 的名字借自作業系統：核心只做最少的事，檔案系統和驅動程式都是核心外的服務。後端工程師熟悉的對應是 monolith 與 microservices：microkernel 的 harness 就是把 tool、memory、execution 拆成 microservices，留下一個小核心。L2 講的 MCP 是圖裡那種標準協定的一例，它讓 tool 跑在 agent 程式外面。Modular 的 provider 背後也可以是程式外面的服務，例如上面的 RedisMemory，或用 MCP 接的 tool：那一條邊界是協定，其他元件仍在同一個 process。

執行一段 Python 的路徑：只有 microkernel 規定 sandbox 交給獨立的服務。用「執行一段 Python」比較三者，看 sandbox 歸誰管。Monolithic 在 agent 自己的 process 裡直接執行，這段 code 讀得到 agent 讀得到的一切，包括檔案和環境變數裡的 credential，所以隔離很難強制。Modular 多了一層介面，但介面只是程式碼的邊界，不是安全邊界：有沒有隔離，看接上的是哪一個 provider，換成直接在本機執行的 provider 就沒有。Microkernel 不留這個選擇：執行請求一律用協定送給 execution 服務，sandbox 的配置、隔離、生命週期都歸這個服務：

Execution 服務如果還是很抽象，可以先玩互動導讀〈Execution 服務：誰替 agent 真正動手〉：同一段 Python 在三種架構裡一步一步跑、故意讓它當掉或刪檔、看 sandbox 被回收，大約 15 分鐘。

架構的取捨：microkernel 放棄簡單與低開銷，換到隔離、共用、擴展。能共用，是因為函式呼叫只在同一個 process 裡有效：好幾個 agent 要用同一套 tool 或 sandbox，它就得是獨立的服務。擴展指某個元件不夠用時，只加那個服務的機器。

比較項目MonolithicModularMicrokernel
換元件困難容易容易，協定相符時
執行隔離難強制選用架構上的重點
獨立擴展有限可能，provider 背後是外部服務時強
通訊成本低低到中可能較高
主要的新代價元件耦合所有 provider 都由 controller 協調，controller 越寫越複雜故障模式變多、端到端除錯更難

常見的選法是看 agent 的數量，理由是 agent 多了才需要共用和獨立擴展：單一 agent 用 monolithic，multi-agent 的基礎設施用 microkernel，modular 介於兩者之間，是最常見的起點。第 2 章是這條選法的反例。

2拆成獨立服務的理由：失敗與安全，不是 agent 的數量

Managed Agents 拆之前：container 掛了 session 就沒了、故障分不出來源、code 讀得到 credential。「導讀」的例子，Anthropic 的 Managed Agents（2026-04），是第 1 章「看 agent 的數量選架構」的反例。他們一開始把 session、harness、sandbox 放在同一個 container，碰到的三個問題都和 agent 數量無關：container 掛了，session 就沒了；harness 的 bug、斷線、死掉的 container 從外面看都一樣，除錯要 shell 進一個可能放著使用者資料的環境；model 寫的 code 和 credential 在同一個地方，一次 prompt injection（藏在網頁或檔案裡的指令，騙 model 照著做）就能叫 code 讀出 credential。

Managed Agents 拆之後：session 只追加、harness 不存狀態、sandbox 碰不到 credential。Anthropic 把這三樣拆成三塊（下圖的 harness，就是第 1 章的 agent loop）：

  • Session。只追加、不修改的 event log，放在 harness 和 sandbox 外面。它們死了，log 還在。
  • Harness。不存狀態。掛了就開一個新的，讀 log 接著做。
  • Sandbox。掛了，harness 把它當成一次失敗的 tool call 回報給 model；model 決定要重試，才配一個新的。Credential 放在它外面，裡面的 code 碰不到。

拆開後的 time to first token（TTFT）：反而變快，因為 sandbox 要用時才配。第 1 章的表說協定的通訊成本可能較高，照這樣推，拆開之後應該變慢。這個案例卻變快了：第一個 token 的等待時間（time to first token，TTFT）p50 降約 60%、p95 降超過 90%。原因不在協定本身：以前每個 session 都要先等 container 準備好，連用不到 sandbox 的 session 也一樣，拆開之後要用時才配。這是一家公司的經驗，不是對照實驗，Anthropic 這篇文章也沒有談多出來的服務邊界要多少維運成本。

3邊界的選法：每一條邊界問隔離、持久、共用，不數 agent

三個問題：秘密要隔離嗎、狀態要活得比 process 久嗎、多個 agent 要共用嗎。本文的判斷是：元件不必一次全拆出去，也不必在第 1 章的三種架構裡選一種。每一條邊界各問它值不值得：

問題答「是」就拆出去代價
要讓外部內容（網頁、email）和 model 寫的程式碼碰不到 credential 嗎？Credential 放在 sandbox 外面多一段 proxy，多一種故障
狀態要活得比 process 久嗎？Session log 放在 harness 外面，掛了能續跑每一步多一次寫入，要設計 log 的介面
多個 agent 要共用同一份基礎設施嗎？Tool、memory、sandbox 池做成服務要有協定與版本，一掛全部受影響

三題都答「否」，例如自己筆電上跑的小工具：不讀外部網頁也不碰秘密、對話斷了重開就好、只有這一個 agent 在用，函式呼叫就夠了，microkernel 的優點用不到，只付代價。

跨服務的代價：故障模式與除錯，不是通訊開銷。大家最擔心的通訊開銷，數字上通常不是問題：華盛頓大學分析 coding agent session 的 TraceLab（L8 第 2 章）量到一次 model 生成約 13 秒，資料中心內的一次 RPC 通常是毫秒級，差上千倍。真正的代價是故障模式和除錯：一個 request 經過好幾個服務，出錯時 log 散在各處。所以每個 request 要帶 trace id：第一站產生一個 ID，往下每個服務原樣傳下去，並寫進自己的 log。出事時用它把各服務的 log 串回同一個 request（L5〈Observability〉）。

查閱：八個 harness 的設計重心

每個 harness 都把一個假設寫進結構。第 3 章的同一個問題，各家 harness 的答案不同，因為它們的假設不同。以第一題（要讓外部內容和 model 寫的程式碼碰不到 credential 嗎）為例：Codex CLI 先把指令關進 sandbox，要出 sandbox 才問人，假設隔離比問人可靠（人被問多了會不看就同意）；Claude Code 預設不開 sandbox，有風險的動作預設交給一個自動判斷風險的分類器（這個模式叫 auto mode），也可以改成每次先問人；它假設環境不一定能隔離。兩種假設都可能成立。讀下面八個 harness 時，可以問每個設計背後假設了什麼。

OpenClaw聊天 gateway 加 queue lane：27 種聊天頻道的訊息都可以進來；每個 session 只有一條 lane（佇列），不管訊息來自哪個頻道，都排進同一條，一次只跑一個 turn；queue mode 決定 agent 執行中收到的新訊息是插進目前的 turn、排到下一個 turn，還是中斷目前的 turn。Compaction 之前先寫記憶：先跑一個使用者看不到的 turn（silent turn），寫下有日期的筆記；之後的 recall 結合全文搜尋和向量搜尋。Fence、taint、sentinel：fence 隔離不可信的文字；讀過網路的 turn 標成 taint；agent 監看 secret 的 sentinel。同一個 session 同時收到很多訊息時，兩個 turn 同時跑、互相搶 session 狀態；compaction 丟掉的細節之後找不回來；prompt injection 與洩密
Hermes Agent會學習的 fork：harness 每隔一段時間發一次提醒（nudge），這時背景另開一個 agent 的分身（執行時複製出來的 agent，不是程式碼的 fork），回顧剛才的 turn，再修改 memory 和 skill，不碰正在進行的對話。最早的 compaction：context 用到 50% 就 compaction，八個裡最早。執行前先存（write-ahead log 的做法）：tool call 先寫進 session 資料庫，才允許副作用發生。同一類任務每次都要重新摸索做法；context 越大每一步越貴，等塞滿才 compaction 太晚；tool call 中途斷掉時，從資料庫知道做到哪裡

「解什麼問題」這一欄是本文的歸納，不是各家自己的說法。Claude Code 的機制在 L2。

名詞Compare-and-swap 編輯：檔案改過就拒絕寫入

名稱來自 CPU 的 compare-and-swap 指令：先比對目前的值是否仍是預期值，相同才寫入。DeepSeek Harness 記下 model 讀檔時的版本，寫入前再比對一次。

Model 讀過之後，你或另一個 subagent 可能改了檔案。沒有檢查時，這次編輯會蓋掉別人的改動。oh-my-pi 的 hashline 編輯用行號指定位置，而檔案一改，行號就可能指到別的行，所以同樣需要這種檢查。它的 edit 除了行號，還帶一個從檔案內容算出的 4 位 hex 雜湊；雜湊和檔案目前的內容對不上，harness 就拒絕這次 edit。L5〈Consistency〉用同一個機制處理這種互相蓋掉的寫入（lost update）。
