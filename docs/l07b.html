Building Agent Evals

Agent design IV: agent evaluation — building your own evals

導讀

你的客服 agent 上線了，有不少案子做不完。Agent 是一套會自己連做很多步的 AI 程式：裡面做決定的是語言模型（下面叫 model），外面包著一層替它查資料、送出回覆的程式（叫 harness）。你照公開排行榜選了 model，可是榜上的分數量的不是你的情況：題目不同，harness 也不同。你要知道的是這一套 agent 在你的客服流程上做得怎樣，以及改了 prompt 之後有沒有變好。

這堂回答兩個問題：怎麼替自己的 agent 建一套評估，以及怎麼用評估的分數做決定。評估是一組考題，加上判分的程式；每次改動之後重跑，看分數。

  • 題目從真實的失敗來。先讀 agent 實際使用時的失敗紀錄，分類、數數，再把 20 到 50 個失敗寫成題目，不要先挑指標。每一題開始前，環境都要恢復原狀，答案和判分的程式放在 agent 碰不到的地方（第 1 章）。
  • 判分疊三層，前一層沒過就不必跑後一層。先用程式查最後的結果對不對；再用程式掃過程裡有沒有不准做的動作，例如為了讓測試通過把測試刪了；程式查不了的「做得好不好」，才請另一個 model 來判。請 model 判要花錢，它自己也會判錯，所以放在最後（第 1 章）。
  • 每題跑好幾次，算每一次都成功的題目佔幾成。同一題重跑，agent 可能這次成功、下次失敗。你不知道客戶會遇到哪一次，同一類案子每天又會進來很多次，所以要看的是每一次都成功的題目佔幾成，叫 pass^k（第 1、2 章）。
  • 用分數做決定：題目分三堆，一次改一件事。每看一次失敗、照著改一次 agent，題目的資訊就帶進 agent 一次，久了分數升了，agent 不一定變好。所以題目分成可以看失敗的開發集、擋退步的 regression 題，和沒有人看過細節、只在做決定時跑的一批。每次只改一件事，和改之前的版本逐題比。分數突然跳升時，先查設定、判分、答案外洩和雜訊（第 2 章）。

這堂假設讀過 L7：harness、grader、trajectory、pass^k、leakage 這幾個詞直接用，第 1 章開頭的〈前情〉有一張對照表。

核心觀念

自己的評估：從失敗建題組，用分數做決定

兩章。第 1 章照順序建一套評估：讀失敗、寫成題目、環境可重置、grader 疊三層。第 2 章是建好之後怎麼用：題目分三堆、一次改一件事、上線條件寫進 CI、分數跳升時先懷疑。外部事實都寫明來源，並在 2026-11-03 查過，引用前請重查。

1建立評估：從真實失敗開始

L7〈Reading Agent Benchmarks〉講的是公開 benchmark 的分數（排行榜上那些數字）怎麼讀、難在哪裡。自己的 agent 要怎麼評估，才是多數讀者真正要做的事。LangChain 2025 年底的調查裡，89% 的回覆者有 observability（看得到每一步的紀錄），跑 offline 評估（上線前，用固定的題組在測試環境裡跑）的只有 52.4%，跑 online 評估（上線後，在真實流量上打分）的更少。也就是說，紀錄已經很普遍，評估還在追趕：就算跑 offline 評估的人全都有紀錄，有紀錄卻沒跑的也還有 89% − 52.4%，超過三分之一的回覆者還沒有把紀錄變成題組、定期跑分。Anthropic、Hamel Husain 與 Shreya Shankar、LangChain、Cursor 這兩年寫下的做法大致一致，這一章和第 2 章把它們整理成一條流程。它們都是各家的經驗，不是對照實驗。

前情這一堂用到的 L7 的詞：harness、grader、trajectory、pass^k、leakage

這一堂接在 L7〈Reading Agent Benchmarks〉後面。下面幾個詞是 L7 講過的，這一堂直接用：

詞一句話在 L7 的哪裡

飽和頂尖的 agent 都擠在同一個分數、分不出高下，benchmark 就看不出進步了飽和

第一步：讀失敗，不要先挑指標。現成的通用指標（helpfulness、coherence）和你的問題常常對不上。Husain 和 Shankar 把 error analysis 排在所有事情前面：

  1. 收集。找約 100 條不同的真實 trace（一次對話或 run 的完整紀錄）。沒有真實的，就先合成使用者的輸入：列出幾個會讓 agent 表現不同的面向（例如問題類型、複雜度），每個面向各取一個值湊成一組（例如「退款問題 × 要查兩張訂單」），手寫約 20 組，再讓 LLM 補更多組、把每一組寫成一句提問，交給 agent 跑出 trace。
  2. 標註。由一位懂使用者的 domain expert 自己讀，至少先讀 30 條，每條只記第一個出錯的地方，因為上游的錯會帶出下游的錯。
  3. 分類、數數。把筆記歸成幾個失敗類別，算每一類有多少。
  4. 停止。讀新的 trace 不再出現新類別，就可以停了。

τ-bench 的作者就這樣分析過 gpt-4o：115 條 trajectory 裡 40 條失敗，其中 4 條是題目寫壞，其餘 36 條分成三類。失敗的分布決定了要寫什麼題：

失敗類別佔 36 條的比例接下來寫什麼題
參數或資訊錯（tool call 的參數填錯，或告訴使用者的資訊不對）約 55%查最終狀態的題：資料庫的差異要等於目標
決策錯，沒照政策約 25%應該拒絕的題，加規則掃 trajectory
複合請求只做一半約 19%一題多個目標，用 checkpoint 給部分分數

第二步：把失敗變成題目。Anthropic 的建議是從 20 到 50 個來自真實失敗的簡單任務開始（簡單是指題目好寫、好判分，不是對 agent 容易），不要等題組完整。他們的理由是評估越晚建越難：早期的產品需求可以直接寫成題目；等太久，就得從一個已經在跑的系統反推「怎樣算成功」。

  • 兩位專家會給同樣的判決。做不到，grader 也寫不出來。
  • 有參考解。參考解是一份已知能通過所有 grader 的答案。一題跑 100 次都是 0% 時，Anthropic 說多半是題目或 grader 壞了；參考解過得了，就證明題目可解、grader 也設定對了，這兩種可能就排除了。
  • 正反都有。該做的題和不該做的題（應該拒絕、應該升級人工）都要放。Anthropic 的說法是「單向的評估造成單向的優化」：只考該做的，「永遠照做」就能拿高分。
  • 長得像真實的請求。Cursor（一個內建 coding agent 的程式編輯器）的題組取自自家工程師平常用 Cursor 寫程式的真實 session。題目描述故意寫短，因為開發者對 agent 下指令本來就簡短、常常沒講清楚，不像公開 benchmark 用的 GitHub issue 那樣詳細。

L7 第 2 章說單一 turn 量不到的三件事，要自己出題才量得到。這裡的 turn 是使用者和 agent 的一來一往，下表寫成「輪」；它和 L7 第 7 章、下面 code 裡 max_turns 數的 turn（agent 的一步）不同。環境裡要有一個會回話的使用者，通常是 LLM 模擬的，τ-bench 就是這樣做：

維度要量什麼題目怎麼出
Clarification目標不夠明確時，會不會停下來問指令故意少一個條件；模擬使用者只在 agent 問的時候才回答
Recovery收到修正後，會不會重新規劃模擬使用者在第 3 輪改需求；對話結束後，grader 查最終狀態符不符合新需求
Memory第 1 輪給的限制，到後面還記不記得第 1 輪說「不要動 schema」，之後 10 輪的需求裡，有幾個最順手的做法就是改 schema；對話結束後，grader 查 schema 有沒有變

第三步：環境要能重置，agent 碰不到答案。不重置，下一個 trial 就在上一個改過的環境裡跑：上一次 trial 存下、這次又讀回來的筆記（agent 的 memory，不是上表那個評估維度），或留在 git 歷史裡的解答，都可能讓 agent 不必真的做就答對，這是 L7 說的 leakage。所以每個 trial 從同一份快照開始（評估程式裡的 env.reset()），上一次的筆記和 git 歷史都不留，grader 和答案放在 agent 碰不到的地方。外部 tool 用 mock：寄信寫進 outbox 表，付款寫進 ledger 表，真實世界不動，grader 也才查得到。

Claude Code（Anthropic 的 coding agent）的 claude plugin eval 是現成的例子。它評估的是 plugin，也就是一個裝著 skill（寫給 agent 的做事說明檔）和設定的目錄（下面「一題長什麼樣」細講）。平常 Claude Code 開工時，會讀進你的 CLAUDE.md（每次開工都會讀的說明檔）、memory 和裝過的其他 plugin，這些都放在你的 home 目錄和專案目錄裡。claude plugin eval 每次 run 都換一個新的暫存 home、工作目錄和 Claude Code 設定，這些檔案都不在裡面，所以一個都不會載入，每次都從同一個起點開始；agent 也讀不到放題目的目錄，而每題的 grader 就放在那個目錄裡（下面的 graders/）。

第四步：Grader 疊三層。L7 第 6 章說只看結果會放過不安全的 run，比對路徑又會判錯正確的做法。解法是分開問三個問題：

Anthropic 的提醒是「通常該判 agent 交出了什麼，不要判它走了哪條路」。所以第二層只列不准發生的事，不規定步驟。第三層用的 judge 自己也會偏，細節在註裡：

查閱LLM-as-judge：用 model 當裁判的好處與偏誤，以及程式、LLM、人三種評分方式的取捨
Grader好處弱點
程式快、便宜、客觀、可重現太死：正確但格式不同的答案會判錯
LLM judge有彈性，能處理開放的答案不確定、比程式貴、要用人工校準
人品質最好，用來校準另外兩種貴、慢、難以規模化

答案是自由文字或對話品質時，常用另一個 model 打分。AlpacaEval、MT-Bench 這兩個比回答品質的 benchmark 就是用 model 當裁判（L7〈查閱〉的〈其他 benchmark 的名字〉）。和請人評比，它便宜、快；和程式比，它能處理寫不出規則的評分，但比程式貴（上表）。

已知的偏誤：偏好較長的回答、偏好同一家的 model、容易受自我宣稱影響（受測的回答寫「已完成」「已驗證」，judge 就傾向相信）。WebArena-Verified（2025 年重新審過題目和判分的 WebArena）因此拿掉 judge，改用確定性檢查。

校準也會過期。Remote Labor Index（RLI）考的是真實的外包案子，例如 3D 與 CAD、建築、影片：每一案有客戶的需求說明、輸入檔，和一份專業人士做的交付物，也就是交給客戶的成品檔案。人工評審把 AI 的成品和專業版比，一樣好或更好，這一案才算自動化了，下面叫合格。2026 年 7 月，作者試著用 judge 取代人工：一個會在真實的軟體裡打開兩份交付物、像客戶那樣檢查的 agent。校準時拿 4 個舊 model 的成品，調 judge 判合格的門檻，讓 judge 判的合格率對上人工判的 3.3%。

拿同一個 judge 去判 2 個它沒見過的新 model，判出的合格率是人工的 2.3 到 2.9 倍，例如 GPT-5.5，人工判 6.25%，judge 判 17.9%。作者的解釋是：檢查交付物本身就是困難的 agent 任務，要在對的專業軟體裡打開檔案、熟練地操作，這正是現在的 agent 最弱的能力，所以 judge 和它評的 agent 有一樣的弱點：agent 做不好的地方，judge 也查不出來，就判成合格。門檻是對著 4 個舊 model 的成品調的，新 model 的成品落在 judge 沒校準過的範圍，同一個門檻就對不上人工了（這一步是本文的推測，原文沒有拆解原因）。不過 judge 把這些 model 由好到壞排出的順序，和人工排的大致相同（Spearman ρ = 0.90；ρ 量兩個排序有多一致，1 表示完全相同），兩個新 model 都排在最前面，只是把它們領先的幅度誇大了。所以 judge 適合比 model 之間誰高誰低；某個 model 到底完成幾成，還是要靠人工判。

Anthropic 與 LangChain 的建議：

  • 問題問窄。Rubric 裡寫清楚 PASS 和 FAIL 的條件，例如下面 escalates.md 的兩行。
  • 一個面向一個 judge。不要讓一個 judge 同時評好幾件事。
  • 留一條路。讓 judge 可以回答「不知道」。
  • 定期校準。用一小批人工標記對答案。

層與層之間用乘的，τ-bench 合併它的兩項評分也是這樣：reward 是 r = r_action × r_output：r_action 看資料庫是不是和目標一樣，r_output 看回覆有沒有含必要資訊，各是 0 或 1。資料庫改對但沒告訴客戶、或告訴客戶但沒真的改，都是 0。如果改用平均，這兩種都拿 0.5，看起來像「做了一半」，兩者卻都不能交給客戶。

長任務給部分分數。乘法讓「沒做完」不會看起來像做了一半。但任務一長，只給 0 或 1 時大家都接近 0，分不出誰比較接近完成。TheAgentCompany 的做法是在中途設 checkpoint：S_partial = 0.5 ×（達成的 checkpoint ÷ 總數）+ 0.5 × S_full，S_full 是整題完成時為 1、否則為 0：

達成的 checkpoint整題完成算式分數
4 / 8否0.5 × 0.5 + 0.5 × 00.25
7 / 8否0.5 × 0.875 + 0.5 × 00.44
8 / 8是0.5 × 1 + 0.5 × 11.00

看第二列，只差最後一步，分數還不到一半：進度有價值，但做完才算數。報告要同時列完成率和平均部分分數：OSWorld 2.0 榜首的完成率是 44.33%，部分分數是 77.67%，只看後者會以為它快做完了（OSWorld 2.0 的部分分數有自己的算法，不是上面 TheAgentCompany 的算式）。

一題長什麼樣。例子用 Claude Code 的 plugin：一個目錄，裝著幾個 skill（寫給 agent 的做事說明，一個 SKILL.md 檔，用到時才載入 context）和設定，裝進 Claude Code 後改變它的做法（L2〈Skill〉〈Plugin〉）。claude plugin eval 量的就是這個改變：受測的 agent 系統是「Claude Code 加上這個 plugin」，對照組是沒裝 plugin 的 Claude Code。下面是一題「應該拒絕」的題，第 2 章接著跑它。這一題只用到第二、三層 grader：應該拒絕的題，正確的結果是什麼都沒改，用規則查「沒有呼叫退款」就夠了，不另外寫第一層。Mock 假扮的是 MCP server，也就是 agent 透過 MCP 這個協定接上的外部 tool，這裡是訂單系統。用別的 agent，零件也相同：prompt 是任務，mock 是環境，graders 是 grader，runs 是 k：

兩者的關係像 integration test 和 unit test。Component-level 要先替每一步標出正確的中間結果（該拆成哪幾步、參數該填什麼），才判得出哪個元件錯，所以貴。實務上不必一開始就全部標：先跑 end-to-end 找出失敗的題，再讀 trajectory 把失敗歸到元件（L6 講的找第一個出錯的步驟），最常出錯的元件再補一組 component-level 的題。元件分數高也不代表任務會成功，錯誤會沿著步驟相乘，每步 95%、串 20 步只剩約 36%，所以兩種都要量。

2用評估做決定：題目分三堆，一次改一件事

題組建好之後，最容易壞在用法：每看一次失敗、照著改一次系統，就把題組的資訊帶進系統一次，這是 L7 第 5 章說的開發過程中的 leakage（L7 第 7 章〈你的題組消耗得更快〉）。改久了，分數升了，agent 不一定變好。

題目分三堆。Anthropic 把題目分成兩種：capability 題問「它做得到什麼」，一開始的通過率要低，挑 agent 現在還做不好的題，才留一段坡可以爬、看得出進步；regression 題問「它還做得到以前做得到的事嗎」，通過率應該接近 100%。第 1 章的「簡單任務」指好寫、好判分的題，它們來自真實的失敗，agent 一開始多半做不到，所以和「通過率要低」不衝突。再加上 L7 第 5 章最後說的，留一批沒人看過的題：

分開的理由是 L7 第 7 章的耗材問題：開發者每看一次開發集的失敗、改一次 prompt，分數就多反映一點對這些題的熟悉度。舊題留在 regression，才能回答「新版有沒有退步」；新題要從 production 的失敗持續補進來，否則題組和真實用法會漸行漸遠。Capability 題也會飽和：全部通過之後，它就看不出進步了，這時把它們升到 regression，再補更難的新題。Held-out 也會慢慢變髒：它的細節沒人看，但每次依它的分數決定上不上線，就是拿它挑了一次版本，挑久了系統會剛好適合這批題，所以要定期換（本文的判斷）。

方法什麼時候抓得到抓不到
自動評估上線前、每次 commit退步，而且可重現題組沒涵蓋的真實用法
Production monitoring上線後真實使用者的行為還沒上線的改動：問題要先到使用者手上才看得到；線上也沒有標準答案，判不了對錯
A/B test重大改動真實的使用者結果結果背後的原因：它只告訴你哪一版比較好，不告訴你為什麼（而且要等幾天到幾週才有結論）
使用者回饋持續沒想到的問題沒人回報的問題：回報少，又偏向嚴重的案例，輕微的問題多半沒人提；回報的人也很少說明哪裡出錯
人工讀 transcript持續細微的問題，建立直覺沒讀到的那些 transcript：一個人讀得完的量有限，流量一大只能抽樣，少見的失敗容易漏掉

Online eval 在真實流量上打分，上表的 production monitoring 和 A/B test 都屬於這一類。它通常沒有標準答案，看的是代理訊號：和品質有關、但不是品質本身的訊號，例如使用者有沒有重問一次、有沒有留下 agent 改的程式碼。Cursor 線上追蹤一組這類指標，包括互動的訊號和產出品質的訊號（細節沒有公開），用它抓到離線題組漏掉的退步：grader 判對、開發者用起來卻覺得比較差。LangChain 的說法是把迴圈接起來：線上標出的失敗，變成離線題組的新題，這就回到第 1 章那張圖的起點。
