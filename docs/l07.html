先看這裡

這堂回答一個問題：你怎麼知道一個 agent 真的會做事？答案是一個系統：可重置的環境、固定的任務、明確的 grader，加上多次執行。這篇文章從評估目標怎麼從「答對」變成「做完」講起，把 slide 的 8 個 benchmark 拆成「agent 在哪裡做事」和「grader 檢查什麼」兩件事逐一讀過，再講評估的四個陷阱。分數只是起點，還要看可靠性、成本、速度，並提防 leakage。

  • 評估對象是整個系統，不只是 model。表現 = f（LLM、prompt、scaffold、tools、memory、environment）。換掉任何一塊，分數都會變，leakage 也能從任何一塊進來。
  • 上線看 pass^k，不看 pass@k。單次成功率 0.8 的 agent，pass@4 是 0.998，pass^4 只有 0.41。客戶只給你一次機會。
  • 每個 benchmark 只量一種動作空間。選和你的 agent 動作空間相同的 benchmark，再確認它還沒飽和。比較真實 agent 時用 Pareto frontier，同時看能力、成本、速度。

A · 對象與指標：評估什麼、怎麼量

2.1評估的對象：從預測文字變成完成互動任務 p.5–9

這一章先回答「評估 agent 到底在評估什麼」：先分 component-level 與 end-to-end 兩個層級，再回顧 benchmark 八年的演進，最後把評估目標排成五層，看 agent 落在哪一層。下一章講指標。

為什麼要從外面評估。L6 說 agent 常常沒驗證就宣布完成：它跑完一串 tool，回一句「已修好」，但測試根本沒跑。所以 agent 能不能用，不能問 agent 自己，要由 harness 外面的一套程序來量。Slide p.5 把這套程序拆成四個問題：評估的歷史與趨勢、用什麼指標、有哪些代表性的 benchmark、評估難在哪裡。這一組的兩章回答前兩個，B 組回答第三個，C 組回答最後一個。

兩個層級：component-level 與 end-to-end。Slide p.6 先把評估分成兩個層級。Component-level 打開 agent 看裡面的單一能力：

  • Planning。任務有沒有拆對：「修 login 的 timeout」拆成找設定、改值、跑測試，還是直接亂改。
  • Tool use。三件事：找到有這個 tool（discovery）、選對 tool（selection）、參數填對（parameterization）。
  • Memory。該記的有沒有記下來（extraction）、重複的有沒有合併（consolidation）、需要時有沒有取回（retrieval），L6 講過這三步。
  • Error recovery。Tool 回錯誤後，有沒有改做法，還是重複同一個錯誤。

End-to-end 把 agent 當黑箱，只記三個數字：任務做完了沒（success rate）、每個任務花多少錢（cost）、花多久（latency）。這三個數字是使用者感受到的東西，所以它回答「能不能用」；component-level 回答「為什麼失敗」。兩種像 unit test 和 integration test，缺一不可：只有 end-to-end，你只能盲調 prompt；只有 component-level，你不知道元件串起來後還剩多少成功率。這堂課的 benchmark 多數是 end-to-end，component-level 要自己標註中間結果，所以貴。

前三個時代量的是 model 本身：先是預測下一個字的能力（PTB、WikiText），再是讀懂一段話的能力（GLUE 這類 語言理解題組），再是知識與推理（MMLU 的選擇題、GSM8K 的小學數學、HumanEval 的程式題）。2023 年起題目變了：SWE-bench 要修 repo，WebArena 要操作網站，GAIA 要自己查資料。這些題目沒有 tool 做不到，所以受測的不再只是 model，而是 model 加上 tool 與 harness。2024 年起的兩個時代則在修補 benchmark 自己的問題：model 很快把舊題目做到滿分（2.8 會講飽和），所以出更難、更新、範圍更大的題。

  • PTB（Penn Treebank）與 WikiText。整理過的文字語料，量 model 預測下一個字的能力。
  • SQuAD。閱讀理解：給一段 Wikipedia，問一個答案在文中的問題。
  • GLUE 與 SuperGLUE。九個左右的語言理解小題組合，例如判斷兩句話是否同義。
  • ARC、HellaSwag、WinoGrande。常識推理的選擇題。
  • MMLU。57 個學科的選擇題。
  • GSM8K。小學文字數學題。
  • MATH。競賽數學。
  • HumanEval。164 題 Python 函式，用測試判對錯。
  • GPQA。研究生等級的科學題。
  • Humanity's Last Exam（HLE）。專家出的最難題。
  • MT-Bench、Chatbot Arena、AlpacaEval。比的是回答偏好，由人或 model 當裁判。

  • GDPval。用真實職業的工作產出評分。
  • BrowseComp。很難查的網路搜尋題。

最右一欄是本文補的，它說明為什麼 agent 評估比 model 評估難。由上到下，每一層的 grader 要的東西：

  1. 前兩層。Grader 是幾行比對程式。
  2. 第三層。要找人或另一個 model。
  3. 第四層。要有能跑程式的環境。
  4. 最後一層。要先架好網站、資料庫或桌面，跑完再檢查狀態，而且下一題開始前要把環境恢復原狀。

所以 agent 評估本身是一個系統工程問題：第 1 段的架構圖裡，環境、重置、預算、grader 四個零件，缺一個分數就沒有意義。

這堂課只管最後一層。「完成互動任務」的意思是：agent 收到一句指令，在一個真的環境裡反覆觀察、行動，最後環境要變成指令要求的樣子。它和「寫出能跑的程式」的差別在副作用：程式題的輸出是一段文字，環境不變；互動任務會改資料庫、改檔案、送出表單，所以 grader 要看的是環境，不是輸出。接下來的指標與 benchmark，全部圍繞這一層。

2.2指標：一個成功率不夠，pass^k、成本、latency 各量一件事 p.10–11、p.19

這一章從早期指標講起，重點放在 pass@k 和 pass^k 的差別，再看 benchmark 的評估 loop 怎麼跑、τ-bench 的分數怎麼算，最後講成本與 latency 要算哪些東西。

早期指標：perplexity、accuracy、win rate。Slide p.10 先列 model 時代的指標。Perplexity 量預測文字：對一段沒看過的文字，把每個字的負對數機率平均再取指數，數字越小表示 model 越不「驚訝」；它只用於 2.1 的第一層。Accuracy 是答對的比例；F1 用在答案是一組東西時（例如抽出的關鍵字），同時看抓到的比例與抓錯的比例。Preference 或 win rate 是把兩個回答放在一起，問人或 judge model 偏好哪一個，Arena 的排行榜就是這樣算的。這三種指標有一個共同點：一題只跑一次，因為 model 時代的輸出短、便宜，大家假設跑第二次結果差不多。Agent 把這個假設打破了。

pass@k：k 次裡至少一次成功。pass@k 來自程式題：HumanEval 的評分方式是讓 model 產生 k 個解答，只要有一個通過測試就算這題過。它量的是「能力的上限」：k 越大，撞到正確解的機會越高。這個指標適合「失敗可以重來」的場合：產生 5 個 patch，用測試挑一個，就是 pass@5 的世界。

pass^k：k 次全部成功。τ-bench 提出 pass^k，問的是「同一題跑 k 次，是不是每次都成功」。它量的是可靠性。兩者的差距就是 agent 不穩定的部分。設單次成功率 0.8、各次獨立：pass@4 = 1 − 0.2⁴ = 0.998，pass^4 = 0.8⁴ = 0.41。同一個 agent，一個指標說它幾乎不會失敗，另一個說它十次有六次至少漏一次。下圖把 k 從 1 畫到 16：

名詞pass@k 與 pass^k 的估計式：為什麼不能把整體成功率取 k 次方

一題跑 n 次，成功 c 次。從 n 次裡任取 k 次全部成功的機率是 C（c，k） / C（n，k），這是 pass^k。至少 1 次成功是 1 − C（n−c，k） / C（n，k），這是 pass@k。兩個都要逐題算，再對所有題目取平均 p.11。

不能先算整體成功率再取 k 次方，因為每題難度不同。用第 1 段第二張圖的資料：8/12 取 4 次方得 0.20；逐題算再平均得 0.33。

選法：失敗能不能重試。該看哪一個，取決於失敗能不能重試。寫程式時可以產生好幾個 patch 再用測試挑，失敗的版本沒有人看到，所以看 pass@k。客服每位客戶只來一次，改錯一張機票就是一次事故，沒有「再來一次」，所以看 pass^k；τ-bench 提出 pass^k，就是因為它量的是客服。上線前的問題幾乎都是第二種：客戶只給你一次機會。

三個地方值得停一下。第一，重置是 benchmark 的成本大宗：WebArena 要自架網站並存快照，Terminal-Bench 要替每題建 container，因為不重置，第二題就在第一題改過的環境裡跑。第二，預算保證評估會結束，agent 卡在迴圈裡也只會花到上限。第三，evaluator 可以看三種輸出，看哪一種決定了 benchmark 的性格，2.3 到 2.5 會逐一對照。

τ-bench 的分數：兩個條件相乘。Slide p.19 給了一個 evaluator 的具體寫法。τ-bench 的 reward 是 r = r_action × r_output。r_action 只在最終資料庫和標註的目標狀態相同時是 1：讀取的 API call 怎麼叫都可以，但多寫了一筆、少寫了一筆，整題 0 分。r_output 只在回覆使用者的話裡包含必要資訊時是 1，例如改票後的票價差。相乘的意思是兩個都要對：資料庫改對但沒告訴客戶，或告訴客戶但沒真的改，都算失敗。這個設計把「做」和「說」分開驗證，2.4 講 τ-bench 時會再用到。

成本與 latency 要算全部。Slide p.10 提醒兩個大家常漏算的指標。成本不只 LLM 的 token 費：每次 tool call 本身可能要錢（搜尋 API、瀏覽器服務），而 prefix cache 沒命中時，整段 context 要重新 prefill，帳單會跳一截（L8 會算）。Latency 也不只 model 的時間：跑一次測試可能 30 秒，等一個網頁載入可能 5 秒，這些都在使用者的等待裡。Slide p.31 的對比是：一次 200 步、花 40 美元的 run，和一次 12 步、花 0.30 美元的 run，兩次都「成功」，只看成功率的 benchmark 分不出它們。下表把這一章的指標排在一起：

GAIA：自備 tool，只看最終答案。GAIA（General AI Assistant，Mialon 等人，2023）有 466 題人寫的問題，題目要用到網頁瀏覽、試算表、PDF、圖片、音訊和計算。它沒有固定的 tool API：每個受測的 agent 自己帶搜尋、瀏覽器、Python 和 shell，所以它測的是整個 agent 系統，不只是 model。題目分三級：

  1. Level 1。不超過 5 步，最多用一個 tool。
  2. Level 2。要 5 到 10 步，用多個 tool。
  3. Level 3。步數不限，要用很多 tool。

答案很短，一個數字、一個字串或一個清單，例如 17.4 或 4,381，這是刻意的設計，下一段會說為什麼。

名詞答案正規化與 exact match：GAIA 怎麼把「比對文字」做乾淨

GAIA 的答案只有三種型別：短字串、數字、逗號分隔的清單。評分用 quasi exact match：依型別正規化，再完全比對。所以 4381 和 4,381 相同，大小寫與多餘空白也不計 p.13。

代價是題目要能用短答案回答。自己做評估時，先把答案格式限制死，grader 就能是幾行程式；答案一旦是自由文字，就需要 judge model。

評分有兩種：AST 檢查把 model 輸出的 call 解析成樹（L4 講過的 AST），比對 function 名稱和每個參數的值；執行檢查則真的叫一次，比對結果。多輪的題目在每一個 turn 都檢查狀態和回覆，所以中途編一個 ID，grader 當場就抓到。V4 版加了 web search 和 memory 兩類題。Slide 提醒一件事：看分類分數，不要看總分，因為總分把單輪、多輪、平行 call、無關 call 混在一起，一個 model 可能單輪很強、多輪很弱。

前情AST：L4 講過的語法樹，這裡拿來比對 function call

L4 2.3 講 edit tool 時介紹過 AST（abstract syntax tree）：parser 把一串字元讀成一棵樹，節點是語法單位，空格與換行不在樹上。BFCL 用它比對 call：book_flight(flight_id="UA123", passenger_id=1) 和參數順序不同、空格不同的寫法，樹是一樣的，所以不會因為格式扣分；但值錯了（"UA124"）樹就不同。

AST 檢查不用真的執行，所以快、沒有副作用；執行檢查能抓到「語法對但結果錯」的 call。BFCL 兩種都用。

兩個 benchmark 各量一件事，都量不到副作用。把這兩個放在一起看：GAIA 看 agent 最後說了什麼，BFCL 看 agent 中途叫了什麼；前者量推理與檢索，後者量介面。它們都不要求環境真的改變，所以建置便宜、評分確定。但真實的 agent 工作多數要改東西，改東西的對錯只有環境知道，這就是下一章四個 benchmark 的起點。另外，兩個都避開了自由文字的答案：GAIA 限制答案型別，BFCL 比對結構。答案一旦是一段話，就得靠 LLM-as-judge，而裁判自己會出錯。

名詞LLM-as-judge：用 model 當裁判的好處與偏誤

答案是自由文字或對話品質時，常用另一個 model 打分。Arena、AlpacaEval、MT-Bench 都是這一類 p.8。它便宜、快，能處理人寫不出規則的評分。

已知的偏誤：偏好較長的回答、偏好同一家的 model、容易受自我宣稱影響。WebArena-Verified 因此拿掉 judge，改用確定性檢查 p.15。要用 judge 時，先拿一小批人工標記校準它。

本文延伸｜Grader 是程式，程式需要測試不是 slide 的內容

Grader 錯了，整個評估就在量錯的東西，而且沒有人會發現。SWE-bench 要出 Verified 版本，原因就是原始題目裡有描述不清、測試不合理的案例。

實務上給 grader 兩組測試：已知正確的 trajectory 必須得 1 分，已知不安全的必須得 0 分。再加一條規則：分數大幅跳升時，先懷疑 grader，再懷疑 leakage，最後才相信 agent 變強。

2.4檢查狀態的 benchmark：WebArena、OSWorld、SWE-bench、τ-bench 各量一種動作空間 p.15–19

這一章讀四個「跑完檢查環境」的 benchmark。它們的動作空間不同：點網頁、動滑鼠、改 repo、和客戶對話；grader 卻是同一個思路，先重置，跑完比對狀態。先講這個思路，再逐一看四個。

為什麼改成檢查狀態。2.3 說 GAIA 看不到副作用。要量「有沒有真的把事做完」，grader 就得看環境：issue 建了沒、檔案存了沒、資料庫改對了沒。檢查狀態的好處是路徑自由：先搜尋再點，或直接打網址，只要最後狀態對，都得分；這比比對 trajectory 公平，因為正確的做法不只一種。代價是環境要能重置到同一個起點，否則第二個 agent 跑的是第一個 agent 改過的環境。所以這四個 benchmark 都自己架環境：自架網站、桌面 VM、repo 的快照、客服資料庫。Benchmark 的建置成本主要花在環境，不在題目。

名詞Accessibility tree：瀏覽器給螢幕閱讀器看的那棵樹

瀏覽器把網頁畫成畫面之前，先建一棵 DOM 樹；為了讓視障者的螢幕閱讀器能用，它再從 DOM 整理出一棵只留「有意義的元素」的樹，叫 accessibility tree：每個節點有角色（button、link、textbox）、名稱（按鈕上的字）和狀態（勾選、展開）。裝飾用的 div、純排版的元素不在樹上。

WebArena 把這棵樹轉成文字給 agent，每個節點加一個編號，agent 用編號指定要點哪裡。好處是 token 少、不用看圖；代價是靠 canvas 畫的、沒有語意標記的頁面，樹上看不到。OSWorld 改用截圖，就是為了這些樹上看不到的東西。

OSWorld：能不能操作一台真的電腦。OSWorld（Xie 等人，NeurIPS 2024）把動作空間再放大：agent 看到的是整個桌面的截圖，動作是滑鼠和鍵盤，369 題跨瀏覽器、辦公軟體、檔案與系統設定。Slide p.16 的例子：在試算表加一個計算欄、排序、存成 result.xlsx。Agent 的 trajectory 大致是點開 LibreOffice、點儲存格、打公式、存檔，每一步都是座標和按鍵。評分和 WebArena 同一個思路：先跑設定腳本（有些設定步驟不算分），記錄 trajectory，取最終狀態，交給 evaluator f 算 reward R；檢查的對象是檔案的儲存格與公式、app 的設定、系統的狀態，跨 app 的工作流程也能查。2026 年的 OSWorld 2.0 把題目加長到 108 個常常超過一小時、幾百步的工作流程，並設約 27 個 checkpoint 給部分分數；為什麼要 checkpoint，2.5 會講。

8 / 8是0.5 × 1 + 0.5 × 11.00

部分分數的設計意圖。看第二列：做到 7/8、只差最後一步，分數是 0.44，不到一半。公式把一半的權重留給「整題完成」，意思是中途的進度有價值，但做完才算數，否則 agent 會學到做到 90% 就停。OSWorld 2.0 的 27 個 checkpoint 也是同一個思路。自己設計長任務的評估時，這條公式可以直接拿去用：checkpoint 讓你看出 agent 卡在哪一步，S_full 讓分數仍然反映能不能交差。

怎麼挑：動作空間要相同，任務長度要有 checkpoint。回到 p.23 的總表（2.3 的那一張），8 個 benchmark 看完，挑選的原則有三條。第一，挑動作空間和你的 agent 相同的，2.4 的最後一列已經對好。第二，看 grader 檢查的東西是不是你在乎的：只看答案的 benchmark 量不到副作用，只看最終狀態的量不到過程中的危險動作。第三，任務長的要有 checkpoint，否則所有 agent 都是 0 分，你什麼都學不到。還有一條來自 2.1：這些 benchmark 都是 end-to-end，它們告訴你分數，不告訴你為什麼；要找原因，還是得自己標註中間結果。

C · 陷阱：leakage、雜訊與飽和

2.6Leakage：走整個 stack，「沒用測試集訓練」不足以證明分數乾淨 p.25–26

這一章講評估的第一個陷阱：答案從不該有的地方進了系統。先定義 leakage，再看 slide 的四層與整個 stack 的表，最後講怎麼防。

Leakage 是什麼。Benchmark 要量的是「沒看過這題也能做對」的能力。如果答案或答案的線索，在評估之前或之中就進了系統，分數量到的是記憶或抄寫，不是能力，這就是 leakage，也叫 contamination。它的危險在於分數看起來完全正常：agent 真的交出了對的 patch、真的改對了資料庫，只是它不是算出來的。所以 leakage 不會讓分數變低，只會讓分數說謊。

四層，不只訓練。Slide p.25 說大家通常只想到第一層，slide 列了四層：

  • 訓練 leakage。題目或它的人工修正在訓練資料裡。SWE-bench 的題目來自公開 repo，修 bug 的 PR 早就 merge 了，爬下整個 GitHub 訓練的 model 看過答案。
  • 評估時 leakage。Agent 有 web search，搜到了那個 issue 的討論串和後來的修正，直接抄。
  • 環境 leakage。Sandbox 裡的 repo 帶著完整的 git 歷史，git log 就能看到未來的 commit；或者隱藏的測試檔就在目錄裡，agent 讀了測試再寫答案。
  • Benchmark overfitting。開發者用公開的測試集調 prompt 和 scaffold：每看一次失敗案例、改一句 prompt，就把那題的資訊寫進系統。沒有人抄答案，但系統是對著這幾百題磨出來的。

這裡有一個取捨：越真實的 tool，leakage 的面越大。給 agent 真的 web search，它的能力更接近真實使用；但 benchmark 需要的資訊可能就搜得到。拿掉 search，分數乾淨了，agent 卻不像真的。

整個 stack 都能漏。Slide p.26 把這件事寫成一條式子：表現 P = f（LLM、prompt、scaffold、tools、retriever、memory、environment），scaffold 就是 L2 講的 harness。這條式子的意思是，分數是整個 stack 的函數，所以每一個輸入都是 leakage 的入口：

怎麼防：每一層各一招。Slide 沒有給防法，本文依上表整理（本文的判斷，2026-10）。訓練與 fine-tuning 這兩層靠「新題」：用 model 訓練截止日之後才出現的 issue（LiveCodeBench、SWE-bench Live 都這樣做），或用沒公開的題。Prompt 與 scaffold 靠「分集」：調整時只看開發集，測試集封起來，發版前才跑一次；2.7 的本文延伸會講評估集怎麼新陳代謝。Retrieval 與 memory 靠「清空」：跑評估前重建索引、清掉 memory，每個 trial 從空白開始。Web search 靠「斷網或白名單」：或至少記錄 agent 搜了什麼、讀了什麼，事後抽查。Environment 靠「剪歷史」：repo 只留題目當時的 commit，測試檔不放進 sandbox，Terminal-Bench 把解法藏起來就是這一招。最後一層靠紀律：分數突然跳升，先問是不是有人看了測試集。

本文延伸｜評估集是耗材，要有新陳代謝不是 slide 的內容

p.32 說公開 benchmark 從推出到飽和只要幾個月到三年。團隊內部的評估集更快，原因是 p.26 的最後一列：開發者每看一次失敗案例、改一次 prompt，就把評估集的資訊帶進系統。幾週後，分數反映的是對這幾十題的熟悉度。

所以要固定一份 held-out 集，開發時不看，發版前才跑。每個 sprint 從 production 的失敗案例補新題，全員都做對的題目刪掉。舊題也要留著，才能回答「新版有沒有退步」。

2.7單一 turn 與其他難處：單一 turn 獎勵亂猜，一次執行只是雜訊，副作用沒人扣分 p.27–31

這一章講 leakage 之外的四個陷阱：benchmark 的世界裡沒有使用者、agent 每次跑結果都不同、過程中的破壞沒人扣分、評分方式本身有兩難。每一個都先說 benchmark 怎麼做、為什麼不像真的，再說該怎麼量。

單一 turn：benchmark 的世界裡沒有使用者。Slide p.27 指出多數 benchmark 的形狀都一樣：一句寫完整的指令進去，最終狀態出來，中間沒有人。真實的工作不是這樣：需求缺了條件、做到一半有人改需求、目標中途移動。這個形狀會獎勵一種行為：有自信地猜。指令少了一個條件時，問一句「你要 A 還是 B」要多花一步，而且 benchmark 裡沒有人會回答，這一步拿不到任何分數；直接猜一個做下去，猜對就得分。於是在 benchmark 上最好的 agent，是最不問問題的 agent，這和你希望它在團隊裡的樣子相反。

多輪評估要量三件事。Slide p.28 放了一張 Assignment 1 的 Claude Code 對話截圖，說「你們就是這樣用它的」：一句話起頭，中途補條件、改方向。要評估這種用法，p.30 給了三個維度：

  • Clarification。目標不夠明確時，agent 會不會停下來問，而不是猜。
  • Recovery。做到一半收到修正，它會不會重新規劃，而不是把舊計畫做完再說。
  • Memory。第一個 turn 給的限制（「不要動資料庫 schema」），到第十個 turn 還記不記得。

要量這三件事，環境裡得有一個會回話的使用者。τ-bench 用 LLM 扮客戶就是這個方向，但它的客戶照腳本走；更難的是讓模擬使用者在中途改需求，而且改得像真人。這是 2.8 的 p.34 表裡「互動」那一列從靜態走向多輪的原因。

非確定性：一次執行只是雜訊。Slide p.31 的第二點：同一個 agent 跑同一題，結果可能不同。來源不只 temperature，還有四個：

  • 浮點數。L1 講過浮點數加總順序讓 T = 0 也不保證重現。
  • Tool 的回傳。每次不同（搜尋結果、時間戳）。
  • 環境。環境的狀態有細微差異。
  • 路徑。一步走偏，後面整條路都不同。

所以只跑一次的分數大多是雜訊，兩個版本差 3 個百分點，可能只是運氣。該怎麼做，2.2 已經講了一半：每題跑 k 次，報 pass^k 或平均值；另一半是題數，題目太少，平均也不準，註裡有算式。報分數要附跑了幾次、幾題，否則讀者無法判斷差距是不是真的。

背景Benchmark 分數的標準誤：50 題的分數，有多大的雜訊

把每題的分數當成一個樣本，benchmark 分數就是樣本平均。若每題成功率約 p、各題獨立，平均的標準誤是 √（p（1−p）/N）。N = 50、p = 0.8 時約 0.057，95% 範圍約 ±0.11 p.31。所以 80% 和 84% 的差距很可能是雜訊。

縮小雜訊有三招。加題目：N 要變 4 倍，標準誤才減半。每題多跑幾次：只能消掉同一題的執行變異。比較兩版時用配對：在同一組題目上看哪些題翻盤。

副作用：通往成功的路上刪了什麼，沒人扣分。第三點：agent 為了讓測試通過，把失敗的測試刪了；為了清出空間，刪了不該刪的檔；中途寄出一封信、花了一筆錢。只看最終狀態的 grader 看到「測試全過」就給 1 分。2.4 的 τ-bench 擋了一部分：多寫一筆資料庫就 0 分；但刪檔、寄信、花錢這類不在目標狀態裡的事，多數 benchmark 不量。要量它，grader 得看 trajectory：用規則掃每一步的 action，碰到 rm -rf、刪測試、對外送出東西，直接判 0。這就是第 1 段架構圖裡 grader 的第三種輸入。

評分方式的兩難。第四點把前面的矛盾講明：只看結果，會放過靠運氣和不安全的 run；比對 trajectory，又會判錯其他正確的做法，因為到同一個狀態的路不只一條。Slide 沒有給答案，本文的整理是三層疊起來：先檢查狀態（結果對不對），再用規則掃 trajectory 的危險動作（過程安不安全），最後才用 judge 看品質（做得好不好）。2.8 的本文延伸會把這三層放進一份團隊自己的評估裡。

2.8飽和與 Pareto：benchmark 幾個月就飽和，真實 agent 要用多個維度比 p.32–35

這一章先看 benchmark 飽和得多快、飽和是什麼意思、出題的人怎麼應對；再看 slide 用一張表總結評估怎麼演進；最後講真實 agent 要同時看好幾個維度，用 Pareto 比，不用權重。

飽和的速度：六張圖。Slide p.32 用六個 benchmark 各畫一條線：推出時 frontier model 的分數，和追上基準線（人類、專家、或作者定的門檻）花了幾個月：

飽和是什麼意思。Slide p.33 的定義有兩種：frontier model 追上了人類基準線，或者頂尖的幾個 model 分數擠在一起，分不出高下。飽和的 benchmark 還能用，但只能證明「這個 model 不差」，不能回答「哪一個比較好」，因為 95 分和 96 分的差距在雜訊範圍裡（2.7 的註）。p.33 把 2016 到 2026 年的 benchmark 排成時間軸，分五類：單一任務、語言理解題組、知識與推理、助理、agent。前四類幾乎全部飽和；agent 類裡 WebArena、SWE-bench、OSWorld 已飽和或接近，還開著的是 Terminal-Bench、GDPval、SWE-bench Pro、Remote Labor Index、ARC-AGI-3、OSWorld 2.0，也就是 2.1 時間軸的最後一格。

出題的人怎麼應對。從前幾章的例子可以歸納三種對策，再加上 2.6 講 leakage 時碰過的兩招，共五招：

  • 出更難的版本。SWE-bench Pro 要改多個檔案。
  • 刪掉飽和的題。Terminal-Bench 從 89 題刪到 66 題。
  • 把任務拉長。OSWorld 2.0 的題動輒一小時。
  • 用新題。LiveBench 定期換題。
  • 把解法藏起來。Terminal-Bench 的 hidden solutions。

這五招的共同點是和 model 賽跑，benchmark 是耗材，2.6 的本文延伸說團隊內部的評估集消耗得更快。

評估怎麼演進：六個維度。Slide p.34 用一張表把這堂課總結成「以前」和「現在」：

每一列都對到前面某一章，6 列各對到：

  • 互動。2.7 的單一 turn。

真實 agent：四個軸，用 Pareto 比。Slide p.35 說比較真實的 agent 至少看四個軸：能力、成本、速度、對使用者好不好用。Assignment 3 用其中三個評分：能力越高越好，成本越低越好，第三個是速度。四個數字怎麼比成一個排名？一種做法是加權平均，但權重由誰定：客服 agent 的使用者在乎速度，研究用的 agent 在乎能力，沒有一組權重對每個人都對。Slide 用的是 Pareto dominance：A 在每個維度都不比 B 差，而且至少一個維度更好，就說 A 支配 B。沒有任何人支配得了的那一群是 Pareto frontier，slide 叫 Rank 1；拿掉 Rank 1 後剩下的不受支配者是 Rank 2，依此類推。

名詞Pareto dominance：多個維度怎麼比，又不用決定權重

A 支配 B：A 在每個維度都不比 B 差，且至少一個更好。所有不受支配的點是 Pareto frontier，也就是 Rank 1。拿掉 Rank 1 後，剩下不受支配的點是 Rank 2，依此類推 p.35。

加權成一個分數要先決定權重，而每個使用者不同。Pareto 不需要權重，只排除不值得考慮的選項；frontier 上的點之間，靠預算或 SLA 來選。

這個方法的用途是排除，不是排名：Rank 2、3 的點可以直接不考慮，因為有人在每個維度都比它好；Rank 1 的點之間沒有客觀的高下，frontier 上怎麼選，看你的預算與 SLA。這也是這堂課的結尾：一個分數回答不了「哪個 agent 比較好」，要先把可靠性、成本、速度各量出來，再依你的限制在 frontier 上挑。

本文延伸｜公開 benchmark 回答「model 多強」，production 評估回答「我的 agent 能不能上線」不是 slide 的內容

公開 benchmark 要跨團隊可比，所以題目固定、環境通用。你的 agent 要回答的問題不同：在你的 tool、資料、政策下，它會不會出錯。p.26 的公式說表現是整個 stack 的函數；換成你的 stack，分數就要重量。

所以 production 評估的任務該來自真實流量：匿名化的客戶請求、出過事的案例、政策的邊界條件。公開 benchmark 仍然有用，但用途是挑 model 與 harness 的起點，不是上線的證據。

本文延伸｜你們團隊自己的 agent 評估，該長什麼樣不是 slide 的內容

一份夠用的評估有五樣東西。可重置的環境：資料庫快照、mock 掉的外部 tool、清空的 memory。任務集：50 到 100 題，含「應該拒絕」的負面題。Grader：先檢查狀態，再掃 trajectory 的危險動作，最後才用 judge 看品質。Metrics：pass^k、每題成本、p95 latency 一起報。流程：一次只改一件事，用同一組任務重跑（L8）。

最後一個提醒來自 L6：agent 常常「沒驗證就宣布完成」。評估是 harness 外面的驗證，不依賴 agent 的自我報告。

  1. p.6 · 兩種評估層級

    Component-level 和 end-to-end 評估各看什麼？哪一種能找出失敗的原因？

    參考答案與重點複習

    答案：Component-level 看 agent 內部的四種能力：planning（拆解任務）、tool use（找 tool、選 tool、填參數）、memory（萃取、整併、取回）、error recovery。End-to-end 只看結果：success rate、每個任務的 cost、完成任務的 latency（p.6）。能找出失敗原因的是 component-level，例如拆錯步驟、選錯 tool 或填錯參數。End-to-end 只告訴你任務有沒有完成。

    重點拆解

    End-to-end 把 agent 當成黑箱。你給它一個任務，記下三個數字：成功了沒、花多少錢、花多久。這就是使用者感受到的東西，所以它回答「能不能用」。問題是一個任務只產生一個「成功或失敗」。一次 20 步的 run 可能壞在任何一步，這個結果不會告訴你是哪一步。

    Component-level 打開黑箱，拿中間結果去對標準答案：任務拆對了嗎？選的 tool 和參數對嗎？取回的是需要的那一筆記憶嗎？出錯後有沒有修回來？代價是要先標註「正確的中間結果」，建置成本比 end-to-end 高。BFCL 很接近 tool use 這一層的評估：它用 AST 或實際執行，檢查 call 的名稱與參數（p.14）。

    兩者互補，像 unit test 和 integration test。End-to-end 告訴你「有問題」，component-level 告訴你「問題在哪」。只有 end-to-end，你只能盲調 prompt。只有 component-level，你不知道元件串起來後還剩多少成功率。

    背景補充

    元件分數高，不代表任務會成功，因為錯誤會沿著步驟相乘（L6）。每一步都對，整個任務才對。所以 component-level 的 95% 和 end-to-end 的 36% 可以同時成立，下面的例子算給你看。

    實務上兩種評估共用同一份資料：trajectory。先跑 end-to-end 找出失敗的任務，再讀這些任務的 trajectory，把每次失敗歸到一個元件。Tracing 工具記錄每一次 LLM call 與 tool call，這一步就不必手動整理。最常出錯的元件，再補一組 component-level 的測試題。

    例子

    假設任務有 20 步，每步成功率 0.95，各步獨立。任務成功率 = 0.95²⁰。逐步算：0.95² = 0.9025；0.95⁴ ≈ 0.8145；0.95⁵ ≈ 0.7738；0.95¹⁰ = （0.95⁵）² ≈ 0.5987；0.95²⁰ = （0.95¹⁰）² ≈ 0.358。每一步看起來都很好，任務卻只有約 36% 成功。

    帶走這幾點
    1. End-to-end：agent 是黑箱，只看 success、cost、latency → 回答「能不能用」。
    2. Component-level：逐一檢查 planning、tool use、memory、error recovery → 回答「為什麼失敗」。
    3. 每步 95%、串 20 步只剩約 36% → 兩種都要量，再用 trajectory 把兩者接起來。

    相關：核心觀念〈評估的對象：從預測文字變成完成互動任務〉、第 1 段架構圖底部的兩個層級、L6〈錯誤相乘：每步 95%，50 步只剩 8%〉與〈獨立假設〉。

  2. p.11–13 · 評估 loop 與 GAIA

    評估 loop 的最後一步，grader 依哪三種東西打分？GAIA 只看答案，它量不到什麼？

    參考答案與重點複習

    答案：Grader 依三種東西打分：最終答案、最終環境狀態、trajectory。每個 benchmark 選的不同（p.11）。GAIA 只比對正規化後的最終答案，中間步驟不計分。所以它量不到改變外界的動作，例如寄 email、訂機票、改資料庫（p.13）。

    重點拆解

    p.11 把評估寫成一個 loop。每個任務開始前，先把環境重置到初始狀態。接著在預算內反覆執行：環境給 observation，agent 依指令、observation、歷史與 tools 選一個 action，環境執行它。Loop 結束後，grader 才打分。它能拿到的輸出只有三種，各回答一個不同的問題：

    Grader 看什麼回答的問題例子盲點
    最終答案有沒有算對、查對GAIA（p.13）有沒有真的做事
    最終環境狀態事情做成了嗎WebArena、τ-bench（p.15、p.19）檢查範圍外的副作用，例如寄出的信（p.31）
    Trajectory怎麼做到的、安不安全BFCL 檢查每個 call 的名稱與參數（p.14）會判錯做法不同但正確的執行（p.31）

    GAIA 有 466 題人寫的題目，涵蓋網頁、試算表、PDF、圖片、音訊與計算（p.12）。答案很短：一個數字、字串或清單，例如 17.4 或 4,381。它沒有固定的 tool API，每個 agent 自備 search、browser、Python、shell。難度分三級：

    1. Level 1。不超過 5 步，最多 1 個 tool。
    2. Level 2。要 5–10 步，用多個 tool。
    3. Level 3。長度不限，tool 很多。

    評分公式是 score = (1/N) Σᵢ 1[normalize(ŷᵢ) = normalize(yᵢ)]（p.13）。意思是：每題的答案正規化後和標準答案完全相同，得 1；否則得 0；再對 N 題取平均。所以 GAIA 量得到推理、檢索、選 tool、整合資訊，量不到動作。Agent 途中寄了一封錯的信，只要最後的數字對，這題仍然得 1 分。

    背景補充

    GAIA 只看答案，有一個實際的理由：每個 agent 自備 tool，各家的 trajectory 長得完全不同，能公平比較的共同輸出只剩答案。答案限制成短格式，grader 就只是幾行程式：結果確定、成本低、能重現，不需要 judge model。GAIA 論文把這種「依型別正規化，再完全比對」的做法稱為 quasi exact match。

    自己設計評估時，三種輸入可以疊加，不必只選一種。能比答案就比答案；要量「做事」，就查狀態；要量「安全」，再加上掃 trajectory 的規則。

    常見誤解

    「GAIA 分數高，代表 agent 能替我把事情辦完。」GAIA 量的是「找到並算出正確答案」。你的 agent 若要寄信、改資料、下單，要看檢查狀態的 benchmark，例如 WebArena 或 τ-bench，或自己架環境去檢查狀態。

    帶走這幾點
    1. Grader 只有三種輸入：答案、狀態、trajectory → benchmark 的性格，由它看哪一種決定。
    2. GAIA：短答案 → 正規化 → 完全比對；便宜又確定，但看不到動作與副作用。
    3. 要量做事就查狀態，要量安全再加 trajectory 檢查。

    相關：第 1 段架構圖的 grader 與三種輸出、註〈答案正規化與 exact match〉、〈LLM-as-judge〉、核心觀念〈Benchmark 怎麼讀：只問兩件事〉。

  3. p.19–22 · τ-bench 與 TheAgentCompany 的計分

    τ-bench 的 reward 為何相乘？TheAgentCompany 拿 7/8 為何只得 0.44？

    參考答案與重點複習

    答案：τ-bench 的 r = r_action × r_output（p.19）。r_action 要求最終資料庫和目標狀態一致，r_output 要求回覆含必要資訊；相乘代表任一項是 0，總分就是 0。TheAgentCompany 的 S_partial = 0.5 × earned/total + 0.5 × S_full（p.22）。7/8 沒完成時 S_full = 0，只得 0.5 × 0.875 ≈ 0.44，因為「完成」占一半分數。

    重點拆解

    τ-bench 的兩項都只有 0 或 1。r_action：最終資料庫和標註的目標狀態一致才是 1。唯讀的 call 可以不同，但多出不該有的寫入就失敗（p.19）。r_output：給客戶的回覆含必要資訊才是 1。兩個 0/1 相乘，等於邏輯上的 AND：兩項都過才得分。

    情況（示意）r_actionr_output相乘若改成平均
    改對資料庫，也告知了客戶1111
    改對資料庫，沒說明票價差額1000.5
    回覆「已改好」，資料庫沒改0100.5
    改好了，途中多寫了一筆不該寫的0100.5

    客服任務裡，這兩件事缺一不可。平均會讓後三列各拿 0.5，看起來像「做了一半」，但這三種都不能交給客戶。相乘讓「不能上線」直接得 0。

    TheAgentCompany 有 175 個任務，在模擬公司裡跑：GitLab、Plane 工單、ownCloud 文件、RocketChat 聊天，還有 LLM 模擬的同事（p.22）。任務很長。若只給 0 或 1，多數 agent 可能都是 0 分，benchmark 就分不出誰比較接近完成。所以它用 checkpoint 給部分分數，但部分分數最多占一半，另一半只給完成的任務。Slide 沒有明寫 S_full 的定義；從三個例子看，完成時是 1，沒完成是 0。

    背景補充

    兩種設計回答同一個問題：grader 要獎勵什麼。只給 0/1 最嚴格，但任務一長，大家都接近 0，分數就沒有鑑別力。部分分數提供梯度，代價是「做了很多但沒做完」也能拿分。OSWorld 2.0 也走這條路：108 個長流程，約 27 個 checkpoint 給部分分數（p.16）。

    乘法可以繼續延伸：任何「一項不過就不能上線」的條件，都適合乘進 grader。有部分分數時，報告要同時列「完成率」和「平均部分分數」。平均 0.44 可能是每題都卡在 7/8，也可能是一半滿分、一半 0 分。

    常見誤解

    「8 個 checkpoint 過了 7 個，分數應該是 0.875。」Checkpoint 只占一半權重。7/8 先乘 0.5 得 0.4375；沒完成，完成分是 0。最後一個 checkpoint 加上完成，一共值 0.5625，比前 7 個加起來的 0.4375 還多。

    帶走這幾點
    1. τ-bench：兩個 0/1 相乘 = AND → 資料庫和回覆缺一項，就是 0 分。
    2. TheAgentCompany：checkpoint 分上限 0.5，完成再給 0.5 → 7/8 未完成 = 0.5 × 0.875 ≈ 0.44。
    3. 乘法讓「不能上線」得 0；部分分數讓長任務有梯度。兩者都是 grader 的設計選擇。

    相關：核心觀念〈Benchmark 怎麼讀：只問兩件事〉、〈指標：一個成功率不夠〉（τ-bench 也提出 pass^k）。進階題第 2 題會用乘法替客服 agent 設計 grader。

  4. p.26–27 · Leakage 與單一 user turn

    為什麼「model 沒用測試集訓練」不能證明分數乾淨？單一 user turn 的評分會獎勵什麼？

    參考答案與重點複習

    答案：Agent 的表現 P = f（LLM、prompt、scaffold、tools、retriever、memory、environment），model 只是其中一個輸入（p.26）。其他輸入也能帶進答案，例如 few-shot 範例取自測試題、memory 存了先前的紀錄、web search 搜到公開解答。單一 user turn 的評分會獎勵「有自信地猜」（p.27）。Agent 問一個釐清問題要多花步數，卻拿不到分數。

    重點拆解

    p.25 把 leakage 分成四層：training、eval-time（上網搜到修正）、environment（sandbox 露出未來的 commit）、benchmark overfitting（在公開測試集上調 prompt 與 scaffold）。Tool 越真實，可洩漏的面越大。p.26 再把它攤到 stack 的每一個元件。依「什麼時候漏」分成三組，比較好記：

    什麼時候漏元件（p.26）例子
    訓練時Base model、fine-tuning預訓練資料含題目；拿 benchmark 解答當 agent 的訓練 trajectory
    評估執行時Prompt、retrieval、memory、web search、environmentFew-shot 範例取自測試題；RAG 語料收了答案；memory 存了上一輪的嘗試；搜到公開解答；看得到未來的 Git commit
    開發過程中Scaffold、agent development手寫的規則針對 benchmark 調過；研究者反覆看失敗案例再調系統

    「Model 沒用測試集訓練」只排除了第一組。換一個從沒看過題目的 model，它一樣能從 web search 或 memory 拿到答案。

    第二個問題是互動。多數 benchmark 只給一個完整的指令，中間沒有使用者（p.27）。真實工作卻會缺條件、中途被糾正、目標會變。沒有使用者，問問題只會用掉步數與預算。p.30 因此建議用多輪 probe 測三件事：目標不明時會不會問（clarification）、被糾正後會不會重新規劃（recovery）、跨 turn 會不會記得限制（memory）。

    例子

    一個指令有兩種解讀，機率各半。直接猜：期望分數 = 0.5 × 1 + 0.5 × 0 = 0.5。先問：沒人回答，最後還是得猜，期望分數最多 0.5，還多花步數。所以在單一 turn 的 grader 下，「問」不會比「猜」得分高。有真實使用者回答時，問一句就能把成功率拉近 1。

    背景補充

    Benchmark overfitting 是 Goodhart's law 的例子：指標一旦變成目標，就不再是好指標。機器學習用 train、validation、test 三份資料防它：調參只看 validation，test 只在最後跑一次。開發者反覆看測試集的失敗案例，等於把 test set 當 validation 用。

    查 leakage 的常見做法：一次關掉一條管道再重跑，例如關掉 web search、清空 memory，看分數掉多少；讀 trajectory 裡的網址與搜尋字串；再用沒人看過的新題目跑一次。

    常見誤解

    「Model 的 training cutoff 早於 benchmark 發布，就沒有 leakage。」Cutoff 只處理訓練時的那一組。Web search、memory、environment 的洩漏發生在評估當下，跟 model 何時訓練無關。

    帶走這幾點
    1. 表現是整個 stack 的函數 → leakage 能從任何元件進來，不只訓練資料。
    2. 「沒用測試集訓練」只排除訓練時的洩漏；評估時與開發過程的洩漏要另外查。
    3. 單一 turn 沒人回答 → 問問題只花步數 → 獎勵自信地猜；多輪 probe 才測得到 clarification、recovery、memory。

    相關：核心觀念〈Leakage〉、本文延伸〈評估集是耗材，要有新陳代謝〉、L4〈評估時要固定 harness〉。進階題第 3 題會設計防止 leakage 的工作方式。

  5. p.32–35 · 飽和與 Pareto frontier

    新 benchmark 推出後多久就飽和？哪些 agent 屬於 Pareto frontier？

    參考答案與重點複習

    答案：p.32 列了 6 個 benchmark：frontier model 只花 6 到 39 個月，就追上人類基準線或大幅拉高分數。例如 SWE-bench Verified 用 22 個月從 33% 升到 95%。A 在每個 metric 都不比 B 差，而且至少一個更好，就是 A 支配 B（p.35）。沒有任何 agent 能支配的那一群，就是 Pareto frontier（Rank 1）。

    重點拆解

    p.32 的 6 個例子：

    Benchmark（推出年）門檻或分數變化花多久最後分數
    GLUE（2018）人類水準 87.114 個月91.1
    MMLU（2020）專家水準 89.839 個月92.3
    GPQA Diamond（2023）博士專家 69.710 個月96.0
    SWE-bench Verified（2024）33% → 95%22 個月95.0
    ARC-AGI-2（2025）一般人 6011 個月95.0
    ARC-AGI-3（2026）0.5% → 62.7%6 個月（slide 標 *）62.7

    p.33 說的飽和有兩種：frontier 追上人類基準線，或頂尖 model 的分數不再拉開。飽和後，頂尖 model 的分數擠在一起，差距落在雜訊裡，benchmark 就失去鑑別力。對策有三種：出更難的版本（SWE-bench Pro）、刪掉飽和的題目（Terminal-Bench 從 2.0 的 89 題減到 4.0 的 66 題，p.20）、出更長的任務（OSWorld 2.0 的 108 個長流程，p.16）。

    比較真實 agent 時，p.35 列出能力、成本、速度等維度。只看能力，常會選到最貴的那個。Pareto 的做法是先刪掉「有別人更便宜又不比它差」的選項。剩下的不受支配的一群是 Rank 1。把 Rank 1 拿掉，再找一次不受支配的點，就是 Rank 2，依此類推。

    背景補充

    Pareto 的概念來自經濟學，在多目標最佳化裡很常用。「拿掉 Rank 1 再找下一層」的做法叫 non-dominated sorting，NSGA-II 這類演算法就用它排序。Agent 評估也走向這個方向：2024 年的論文「AI Agents That Matter」主張 agent 的成績要和成本一起報，用 frontier 比較。

    飽和的另一面是汙染。題目公開越久，越可能進到訓練資料或網路上的解答裡。p.7 把 LiveBench、LiveCodeBench 放在重視 freshness 的那一代：它們持續加入新題。p.34 也說評估資料正從固定、公開，走向新鮮、隱藏、動態。

    常見誤解

    「Benchmark 飽和，代表這類工作 AI 已經做得好了。」飽和只代表這組題目分不出強弱。題目通常條件完整、只有一個 turn（p.27）。同樣是修 repo，換成更難、要改多個檔案的 SWE-bench Pro（p.17），就是另一回事。

    帶走這幾點
    1. 新 benchmark 6–39 個月就被追上 → 分數擠在一起 → 要出更難、更長或刪題的新版。
    2. A 支配 B：每個維度都不差，至少一個更好；不受支配的一群就是 Rank 1。
    3. Pareto 不需要權重，只刪掉不值得考慮的選項；frontier 上要選哪一個，看預算或 SLA。

    相關：核心觀念〈飽和與 Pareto：benchmark 幾個月就飽和，真實 agent 要用多個維度比〉、註〈Pareto dominance〉、〈Benchmark 分數的標準誤〉。第 4 段的練習會加上 latency 當第三個維度。

    一句話：τ-bench 用模擬客戶、真實 API 與一份政策文件測客服 agent，評分看最終資料庫狀態。它提出 pass^k 量「每次都要對」：gpt-4o 在 retail 單次成功 61.2%，連續 8 次都成功低於 25%。

    跟這堂課的關係

    Slides p.10–11 的 pass^k 定義與 p.12–23 裡的 τ-bench 介紹都來自這篇 §3。核心觀念〈指標：一個成功率不夠〉與註〈pass@k 與 pass^k 的估計式〉（p.11）用的公式就是這篇的。〈Benchmark 怎麼讀：只問兩件事〉的表裡，τ-bench 是唯一同時檢查狀態與回覆內容的。第 1 段第二張圖的 pass^4 例子是這篇 Figure 4 的簡化版。

    壓縮後的重點

    1. 環境有三樣東西：資料庫、API、政策。Retail 有 500 個使用者、50 項商品、1,000 筆訂單，7 個寫入 API、8 個讀取 API，115 題。Airline 有 500 個使用者、300 班航班、2,000 筆訂位，6 個寫入 API、7 個讀取 API，50 題。政策是一份 markdown，例如每筆已送達的訂單只能退換一次。
    2. 客戶由 LLM 模擬，agent 看不到他的指令。模擬客戶用 gpt-4-0613、temperature 1.0；agent 用 temperature 0。每題的客戶指令寫到只有一種正確的資料庫結果。客戶看得到對話，看不到 agent 的 tool call。
    3. Reward 是兩個 0/1 相乘。r_action：最終資料庫完全等於唯一的標準狀態。r_output：agent 的回覆含必要字串，例如價格。作者說這是必要條件，不是充分條件：agent 沒問客戶確認就退款，資料庫一樣對。
    4. pass^k 的定義。一題跑 n 次、成功 c 次，pass^k = C（c，k） / C（n，k），再對所有題目平均。pass@k = 1 − C（n−c，k） / C（n，k）。k = 1 時兩者相同，就是平均成功率。
    5. 最好的 model 也不到一半，而且不穩定。Function calling 下，gpt-4o 在 retail 61.2%、airline 35.2%；claude-3-opus 44.2% 與 34.7%；gpt-3.5-turbo 20.0% 與 10.8%。Retail 的 pass^k 隨 k 快速下降，gpt-4o 的 pass^8 低於 25%。Function calling 優於 ReAct，ReAct 優於 Act。
    6. 失敗原因有三類。抽 115 條 gpt-4o retail 軌跡，40 條失敗，其中 4 條是客戶指令寫壞。剩下的失敗：參數錯或資訊錯約 55%、決策錯（沒照政策）約 25%、複合請求只做一半約 19%。拿掉政策文件後，retail 從 61.2% 降到 56.8%，airline 從 33.2% 降到 10.8%。

    原文怎麼讀

    • 可以跳過：§2 Related Work；§4.1 兩個 domain 的建構過程；§5.1 Table 2 的全部 model，看 gpt-4o 與 claude-3-opus 兩列就夠；Appendix B。
    • 值得看原文：§3 的 reward 與 pass^k 定義（半頁）；Figure 4 的 pass^k 與 pass@k 曲線，兩條線的張開程度就是不穩定的量；Appendix C.2 的完整對話軌跡，看一次 agent 怎麼在政策與客戶之間失敗。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「pass^8 低於 25%，代表 gpt-4o 只做對四分之一的題目。」不對。它的平均成功率是 61.2%。pass^8 是「同一題連續 8 次都對」的比例，低於 25% 說的是穩定性，不是能力。兩個數字的差距就是 slides p.11 要你看的那一塊。

  2. 推薦Dapper: A Large-Scale Distributed Systems Tracing InfrastructureGoogle · 系統論文 · 2010 · 挑段約 20 分

    分散式 tracing 的奠基之作。把 agent 的步驟與 tool call 當 span，整套方法直接搬用。

    導讀適合系統背景的人導讀。重點：sampling rate 是主要的成本控制。

    摘要讀約 3 分；原文約 20 分

    一句話：Dapper 是 Google 的分散式 tracing 系統：把一個請求經過的所有 RPC 記成一棵 span 樹，只在幾個共用 library 裡埋點，靠抽樣把 overhead 壓到看不見。它是 OpenTelemetry 這類工具的原型。

    跟這堂課的關係

    這篇不談 agent，放在這一講的原因是 trajectory。Slides p.11 說 evaluator 看最終答案、環境狀態、trajectory；p.31 說只看結果會放過不安全的執行。要看 trajectory，就要先把每一步記下來，Dapper 的 span 樹就是記法。核心觀念〈指標：一個成功率不夠〉要的成本與 latency（p.10），每個 span 都帶時間戳，可以逐步加總。本文延伸〈公開 benchmark 回答「model 多強」〉說 production 評估要用真實流量；Dapper 就是從真實流量取樣的機制。

    壓縮後的重點

    1. 一個 trace 是一棵樹，節點是 span。每個 span 有名稱、span id、parent id，共用一個 64-bit 的 trace id。換成 agent：一次 session 是 trace，每次 LLM 呼叫與 tool call 是 span。
    2. 只在三個地方埋點，應用程式不用改。Thread：trace context 放在 thread-local storage。Control flow：callback 建立時存下 context，執行時還原。RPC：所有 RPC 自動包成 span。Google 的程式都走這幾個 library，覆蓋率接近全部。
    3. Annotation 讓應用程式加自己的資料。帶時間戳的文字或 key-value，每個 span 有容量上限。70% 的 span、90% 的 trace 至少有一個 annotation。換成 agent：prompt、tool 參數、token 數都是 annotation。
    4. Overhead 的數字。建一個 root span 204 ns，非 root 176 ns，沒抽中時加 annotation 約 9 ns。收集 daemon 最多用一個 core 的 0.3%；trace 流量低於 production 網路的 0.01%。全抽（1/1）時 latency 增加 16.3%、throughput 降 1.48%；1/16 時 latency 增 2.12%，已在實驗誤差 2.5% 內。
    5. 抽樣是主要的成本控制。第一版 production 統一抽 1/1024；高流量服務低到 0.01%；每秒幾十個請求的服務可以全記。後來改成 adaptive sampling，目標是每單位時間固定的 trace 數。收集端再抽一次：依 trace id 的 hash 決定整棵樹留或丟。
    6. 收集是 out-of-band。Span 先寫本機 log，daemon 拉走，collector 寫進 Bigtable，一列一個 trace、一欄一個 span。中位延遲 15 秒以內。抽樣後每天仍超過 1 TB，要留至少 2 週。
    7. 用途超出原本的設計。約 200 位工程師每個工作天用 UI。Ads Review 團隊靠它把 latency 改善兩個數量級。

    原文怎麼讀

    • 可以跳過：§2.6 安全與隱私；§3 部署狀況；§5.1 DAPI；§8 Related Work。
    • 值得看原文：§2.1 的三張圖（五個 server 的請求、它的 span 樹、一個 span 的內容）；§4.3 的 Table 2（6 種抽樣率對 latency 與 throughput 的影響）；§6.2 long tail latency 的案例。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「Dapper 抽 1/1024，所以 agent 的 trace 也該抽樣。」不對。1/1024 是給每秒數萬個請求的服務用的；論文說每秒幾十個請求的服務可以全部記錄。Agent 的請求少、每次又貴，評估又要逐筆看 trajectory，所以全記。要省的是儲存，用整棵保留或丟棄的二次抽樣。
