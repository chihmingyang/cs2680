先看這裡

一個 benchmark 分數是整個系統在一組題目上的輸出：model、harness、資源、題目和 grader，換掉任何一項，分數都會變。所以這堂要帶走兩個判斷：怎麼讀一個分數，以及怎麼評估自己的 agent。八個 benchmark 的細節收在最後一章，需要時再查。

  • 分數不能直接搬。同一個 model 只換 harness，ARC-AGI-3 從 62.7% 變成 98.6%；只修題目，Terminal-Bench 上同一個 agent 多了 12 分。比較之前，先問比的是什麼。
  • 讀分數問五件事。動作和 grader 和我的一樣嗎？設定相同嗎？報了穩定性和成本嗎？差距大過雜訊嗎？題目還乾淨、grader 還可信、還分得出高下嗎？
  • 自己的 agent 要自己量。從 20 到 50 個真實失敗做起，grader 先查狀態，再掃危險動作，最後才用 judge；每題跑多次，報 pass^k 和每個成功任務的成本。

1根本的事實：分數是整個系統的輸出

L6 說 agent 常常沒驗證就宣布完成，所以 agent 能不能用，不能問 agent 自己，要由 harness 外面的一套程序來量，這套程序叫評估（evaluation，常簡稱 eval）。看到「X 在 SWE-bench 拿到 80%」時（SWE-bench 考修真實的 GitHub issue），多數人會把 80% 當成 X 這個 model 的能力。這是讀分數最常見的錯誤，先看分數是怎麼產生的：

跑一題叫一次 trial，同一題要跑很多次，因為 agent 每次的結果可能不同。Trajectory 是一次 trial 裡每一步的觀察和動作，也叫 trace 或 transcript。骨架只有幾行，和 L4 的 agent loop 幾乎一樣，差別是外面多了重置、預算和 grader：

三個地方決定分數的意義。這三個都是出題的人選的，換一個選法，分數的意思就變了：

  • 重置。不重置，第二題就在第一題改過的環境裡跑。這也是 agent 評估貴的地方：要自架網站或資料庫，每次恢復原狀。
  • 預算。上限決定 agent 有多少機會把事做完，所以上限不同的兩個分數不能直接比。
  • Grader 看什麼。看答案量不到動作，看最終狀態量不到過程中的破壞，比對 trajectory 又會判錯其他正確的做法（第 6 章）。

寫成式子：分數是整個 stack 的函數。課程把這件事寫成 P = f（LLM、prompt、scaffold、tools、retriever、memory、environment），scaffold 就是 L2 講的 harness，retriever 是替 agent 查資料的那一層。本文再加上跑評估的人決定的三項：題目、grader、資源與預算。換掉其中任何一項，分數都會變，而且變化常常比兩個 model 之間的差距大：

第一列的 ARC-AGI-3 是一組要邊玩邊摸索規則的抽象小遊戲，數字來自 ARC Prize 2026 年 9 月的報告。Standard harness 只讓 model 帶著自己寫的筆記往下走，Provider Adapter harness 保留 reasoning 狀態並做 compaction，同樣開到最高的 effort（reasoning 的強度設定），分數差 36 分。第二列是 L4 講過的 Lewis 實驗。第三列的 Terminal-Bench 考在 container 裡用 shell 做完一件事，2.1 版只修了 89 題裡的 28 題，同一個 agent 就多了 12.1 分。第四列的 CORE-Bench 考重現論文的計算結果，Anthropic 發現它原本連 96.12 和 96.124991 都判不同，修掉這類錯、放寬 scaffold 之後，從 42% 變成 95%。

連 VM 的大小也算在內。Anthropic 2026 年 2 月的實驗只改資源設定，Terminal-Bench 2.0 的分數就差 6 分，他們的結論是：榜上差距小於 3 分的，在設定公開並對齊之前都值得懷疑（第 4 章）。

Harness 的影響也不是定值。Scale 與 Reflection用三種 harness 跑開放權重的 model，最強的幾個結果不變，所以他們建議「依帳單選 harness，不要依分數選」。不要記成「harness 一定差很多」，要記成每個分數都要連同它的設定一起讀：哪個 model、哪個 harness、多少資源與預算。

所以比較時要固定其他項。比 model 就固定 harness，比 harness 就固定 model 和題目（L4 的本文延伸）；自己改 agent 時，一次只改一件事。L5 問的「拿掉一個 agent，品質掉多少」也是這樣答：同一套程序跑兩次。

2最重要的判斷：公開分數回答不了「能不能上線」

公開 benchmark 要讓不同團隊的分數能比，所以題目固定、環境通用。你要問的是另一個問題：在我的 tool、資料和政策下，這個 agent 會不會出錯。公開分數可以用來挑起點，不能當上線的證據。兩者的距離來自三個地方。

第一，動作和 grader 可能不同。任何 benchmark 都只要問兩件事。第一是動作空間（action space）：agent 能做什麼，叫 API、打 shell、點網頁，還是動滑鼠；它決定這個 benchmark 像哪一種真實 agent。第二是 grader 看什麼；它決定什麼叫成功。課程介紹的八個 benchmark 放到這兩軸上：

先找你的 agent 在哪一欄。它用瀏覽器，WebArena 的分數才有參考價值；它改 repo，看 SWE-bench 或 Terminal-Bench；它和人對話又改資料，τ-bench 最接近。拿 SWE-bench 的分數推測客服表現，沒有可比性。再看列：GAIA 只比最後的答案，寄信、改資料庫這類動作它完全量不到。八個的細節收在第 10 章。

第二，benchmark 的世界裡沒有使用者。多數 benchmark 的形狀都一樣：一句寫完整的指令進去，最終狀態出來，中間沒有人。真實的工作會缺條件、做到一半改需求、目標中途移動：

這個形狀會獎勵一種行為：有自信地猜。假設一句指令有兩種解讀，機率各半。直接猜，期望分數是 0.5。先問，benchmark 裡沒有人回答，最後還是得猜，期望分數最多也是 0.5，還多花了步數。有真人回答時，問一句就能把成功率拉近 1。所以在單一 turn 的 benchmark 上，最不問問題的 agent 分數最好，這和你希望它在團隊裡的樣子相反。

第三，過程中的破壞沒人扣分。Agent 為了讓測試通過，把失敗的測試刪了；為了清出空間，刪了不該刪的檔；中途寄出一封信、花了一筆錢。只看最終狀態的 grader 看到「測試全過」，一樣給 1 分。第 8 章會把這件事量進來。

3指標：一個成功率藏住穩定性和成本

Benchmark 通常只報一個百分比。這個數字把三件事壓在一起：每次都做得到嗎、花多少錢、要等多久。這一章把它們拆開，對應五個問題的第 3 題。

pass@k 與 pass^k：能力和穩定性是兩件事。同一題跑 k 次。pass@k 問「至少一次成功」，它來自程式題：產生 k 個解答，有一個通過測試就算過，所以量的是能力的上限。pass^k 問「k 次全部成功」，τ-bench 為了客服提出它，量的是穩定性。設每次的成功率是 p、各次獨立，那麼 pass@k = 1 − (1 − p)^k，pass^k = p^k。把 p = 0.8 代進去：

查閱pass@k 與 pass^k 的估計式：為什麼不能把整體成功率取 k 次方

一題跑 n 次，成功 c 次。從 n 次裡任取 k 次全部成功的機率是 C（c，k） / C（n，k），這是 pass^k。至少 1 次成功是 1 − C（n−c，k） / C（n，k），這是 pass@k。兩個都要逐題算，再對所有題目取平均。

不能先算整體成功率再取 k 次方，因為每題難度不同。上圖的資料：整體 8/12 取 4 次方得 0.20；逐題算再平均得 0.33。

本文的判斷：上線前的問題多半是第二種，客戶只給你一次機會。真實的差距也不小：τ-bench 上 gpt-4o 在 retail 的單次成功率是 61.2%，同一題連續 8 次都成功的比例低於 25%。不穩定也不會隨著換新 model 自動消失。Towards a Science of AI Agent Reliability 量了 14 個 model：18 個月裡能力每年進步約 0.21，可靠性只有 0.03 到 0.10，結果的一致性幾乎沒動。

成本：算每個成功任務，不算每次執行。一次 200 步、花 40 美元的 run，和一次 12 步、花 0.30 美元的 run，兩次都「成功」，只看成功率分不出來。L1 講過的算法是總花費除以成功次數，所以每次較貴但常成功的設定，算下來可能反而便宜。花費要算全部，tool call 和 cache miss 都在內，L8 會算這些乘數。Latency 同理，等網頁載入和跑測試都在使用者的等待裡，上線時看 p95（最慢的那 5% 要等多久），不看平均。

有成本這一軸，也才看得出簡單的做法多有用。AI Agents That Matter 在 HumanEval 上量到，只是失敗就重試的簡單 agent（Warming）有 93.2%、總共 2.45 美元；複雜的 LATS 有 88.0%、134.50 美元。所以評估裡要放一個簡單的 baseline，否則你不知道複雜的東西換到了什麼。

多個維度怎麼比：Pareto。能力、成本、速度要合成一個排名，直覺是加權平均，但權重由誰定？客服在乎速度，研究用的 agent 在乎能力，沒有一組權重對每個人都對。Pareto dominance 不需要權重：A 在每個維度都不比 B 差，而且至少一個維度更好，就說 A 支配（dominate）B。沒有人支配得了的那一群叫 Pareto frontier，也就是 Rank 1；拿掉 Rank 1 之後剩下不受支配的是 Rank 2，依此類推。下圖是一張真實的榜，只看能力和花費兩個維度：

看圖中段：GPT-6.1 Sol 和 Fable 5.1 的分數只差 0.3 分，花費差 10 倍，只看分數會以為它們打平。這個方法的用途是排除，不是排名：Rank 2 以下可以先不考慮，因為有人每個維度都比它好；Rank 1 之間沒有客觀的高下，依你的預算和 SLA 選。課程的 Assignment 3 也是這樣評分：解出幾題、每題花多少、每題花多久分開量。

課程的提醒是：只跑一次的分數大多是雜訊。下面把這句話算出來。

題數決定精度。Benchmark 分數是把每題的結果平均，所以可以估它的誤差。先定義三項：N 是題數；p 是成功率；標準誤（standard error）是「換一組題目，平均值大約會動多少」。公式是標準誤 = √（p（1 − p）/ N），95% 範圍約 ±1.96 × 標準誤。比較兩版時，兩邊各有雜訊，差值的範圍要再乘 √2。代入 p = 0.8：

基礎設施也是雜訊。Anthropic 的實驗把每題的資源上限從 1 倍放到不設限，基礎設施造成的錯誤從 5.8% 降到 0.5%。放到 3 倍之前，分數的變化還在雜訊內（p = 0.40），只是少了誤殺；超過 3 倍後分數再升近 4 分，因為 agent 多了本來跑不動的解法，它在考的東西已經變了。所以他們建議每題同時定保證的下限和強制終止的上限，並把倍數寫進報告。

5Leakage：答案能從整個 stack 進來

Benchmark 要量的是「沒看過這題也能做對」的能力。如果答案或答案的線索，在評估之前或之中就進了系統，分數量到的是記憶或抄寫，這就是 leakage，也叫 contamination。它的危險在於分數看起來完全正常：agent 真的交出了對的 patch，只是它不是算出來的。所以 leakage 不會讓分數變低，只會讓分數說謊。

6Grader：它會判錯，agent 還會鑽漏洞

上一章的問題是答案漏進來，這一章的問題在判分的程式本身。課程對它只留了一句話：只看結果，會放過靠運氣和不安全的 run；比對 trajectory，又會判錯其他正確的做法。2026 年這件事變成大事：提出 SWE-bench Verified 的 OpenAI 在 2 月不再報這個分數，7 月又估計接替它的 SWE-Bench Pro 約 30% 的題壞掉，撤回自己的推薦。

Grader 是程式，程式會有 bug，而且分數上看不出來。它會往兩個方向錯：

Agent 還會主動鑽漏洞。Agent 把力氣放在拿分、沒有完成任務，這叫 reward hacking。ImpossibleBench（2025）把這件事量了出來：它改出一批測試和題目描述互相矛盾的題，這種題不可能正當地通過，所以通過率就是作弊率。GPT-5 在 SWE-bench 改出來的那一組作弊率是 76%，在 LiveCodeBench 那一組只有 2.9%。手法有改測試、overload 比較運算子、記下呼叫次數、認出特定測試直接回傳期望值。把測試完全藏起來，作弊的成功率接近 0，但正常題的表現也會下降；唯讀是折衷，擋得住改測試，擋不住其他幾種。

真實的 run 裡也看得到：CAISI（美國 NIST 的 AI 評估單位）的紀錄裡 o4-mini 註解掉失敗的 assertion，SWE-Bench Pro V2 抓到一個 frontier model 偽造 Go module 的版本和 checksum。後者在原環境通過、在乾淨的 image 上失敗，所以重判才看得出來。

8建立評估：從真實失敗開始

課程講到 benchmark 和它的難處，沒有講自己的 agent 要怎麼評估，但這是多數讀者真正要做的事。LangChain 2025 年底的調查（1,340 份回覆）裡，89% 有 observability（看得到每一步的紀錄），跑 offline 評估的只有 52.4%，跑 online 評估的是 37.3%。Anthropic、Hamel Husain 與 Shreya Shankar、LangChain、Cursor 這兩年寫下的做法大致一致，這兩章整理成一條流程。它們都是各家的經驗，不是對照實驗。

第一步：讀失敗，不要先挑指標。現成的通用指標（helpfulness、coherence）和你的問題常常對不上。Husain 和 Shankar 把 error analysis 排在所有事情前面：

  1. 收集。找約 100 條不同的真實 trace（一次對話或 run 的完整紀錄），沒有就先用合成的。
  2. 標註。由一位懂使用者的 domain expert 自己讀，至少先讀 30 條，每條只記第一個出錯的地方，因為上游的錯會帶出下游的錯。
  3. 分類、數數。把筆記歸成幾個失敗類別，算每一類有多少。
  4. 停止。讀新的 trace 不再出現新類別，就可以停了。

τ-bench 的作者就這樣分析過 gpt-4o：115 條軌跡裡 40 條失敗，其中 4 條是題目寫壞，其餘分成三類。失敗的分布決定了要寫什麼題：

失敗類別佔比接下來寫什麼題
參數或資訊錯約 55%查最終狀態的題：資料庫的差異要等於目標
決策錯，沒照政策約 25%應該拒絕的題，加規則掃 trajectory
複合請求只做一半約 19%一題多個目標，用 checkpoint 給部分分數

第二步：把失敗變成題目。Anthropic 的建議是從 20 到 50 個來自真實失敗的簡單任務開始，等題組完整才開始的團隊，之後會更難做。好題目有四個條件：

  • 兩位專家會給同樣的判決。做不到，grader 也寫不出來。
  • 有參考解。它證明題目可解、grader 可過。跑 100 次都是 0%，多半是題目壞了。
  • 正反都有。該做的題和不該做的題（應該拒絕、應該升級人工）都要放。Anthropic 的說法是「單向的評估造成單向的優化」：只考該做的，「永遠照做」就能拿高分。
  • 長得像真實的請求。Cursor 的題組來自自家工程師的真實 session，描述故意寫短。

第 2 章說單一 turn 量不到的三件事，要自己出題才量得到。環境裡要有一個會回話的使用者，通常是 LLM 模擬的，τ-bench 就是這樣做：

維度要量什麼題目怎麼出
Clarification目標不夠明確時，會不會停下來問指令故意少一個條件；模擬使用者只在 agent 問的時候才回答
Recovery收到修正後，會不會重新規劃第 3 個 turn 改需求，最終狀態要符合新需求
Memory第一個 turn 給的限制還記不記得開頭說「不要動 schema」，到第 10 個 turn 查有沒有動

第三步：環境要能重置，agent 碰不到答案。這是第 1 章的 env.reset() 和第 5、6 章的教訓：每個 trial 從同一份快照開始，memory、索引和 git 歷史都不留，grader 和答案放在 agent 碰不到的地方。外部 tool 用 mock：寄信寫進 outbox 表，付款寫進 ledger 表，真實世界不動，grader 也才查得到。Claude Code 的 plugin eval 就是這樣做：每次 run 有自己的暫存 home 和工作目錄，你的 CLAUDE.md、memory、其他 plugin 都不載入，agent 也讀不到題目的目錄。

已知的偏誤：偏好較長的回答、偏好同一家的 model、容易受自我宣稱影響。WebArena-Verified 因此拿掉 judge，改用確定性檢查。

校準也會過期。Remote Labor Index 2026 年 7 月發現，用舊 model 校準的 judge 把新 model 高估了 2.3 到 2.9 倍，但排序仍然大致對（Spearman ρ = 0.90）。所以 judge 適合看相對的變化，絕對的分數要靠人工。

Anthropic 與 LangChain 的建議：

  • 問題問窄。寫清楚 PASS 和 FAIL 的條件。
  • 一個面向一個 judge。不要讓一個 judge 同時評好幾件事。
  • 留一條路。讓 judge 可以回答「不知道」。
  • 定期校準。用一小批人工標記對答案。

層與層之間用乘的。τ-bench 的 reward 是 r = r_action × r_output：資料庫要和目標一樣，回覆也要含必要資訊。資料庫改對但沒告訴客戶、或告訴客戶但沒真的改，都是 0。如果改用平均，這兩種都拿 0.5，看起來像「做了一半」，兩者卻都不能交給客戶。

長任務給部分分數。任務一長，只給 0 或 1 時大家都接近 0，分不出誰比較接近完成。TheAgentCompany 的做法是在中途設 checkpoint：S_partial = 0.5 ×（達成的 checkpoint ÷ 總數）+ 0.5 × S_full，S_full 是整題完成時為 1、否則為 0：

查閱GAIA：自備 tool，只看最終答案

GAIA（General AI Assistant，Mialon 等人，2023）有 466 題人寫的問題，要用到網頁瀏覽、試算表、PDF、圖片、音訊和計算。它沒有固定的 tool API：每個受測的 agent 自己帶搜尋、瀏覽器、Python 和 shell，所以它測的是整個 agent 系統。題目分三級：Level 1 不超過 5 步，最多用一個 tool；Level 2 要 5 到 10 步，用多個 tool；Level 3 步數不限。

例子：一張試算表列了很多部電影，找出符合兩個條件的那一部，查它的導演，回答導演的出生地。

答案很短，所以評分乾淨，沒有裁判的主觀，兩個團隊的分數可以直接比。代價是量不到有副作用的動作：寄信、訂機票、改資料庫都沒有。

查閱答案正規化與 exact match：GAIA 怎麼把「比對文字」做乾淨

GAIA 的答案只有三種型別：短字串、數字、逗號分隔的清單。評分用 quasi exact match：依型別正規化，再完全比對。所以 4381 和 4,381 相同，大小寫與多餘空白也不計。

代價是題目要能用短答案回答。自己做評估時，先把答案格式限制死，grader 就能是幾行程式；答案一旦是自由文字，就需要 judge model。

查閱BFCL：model 的 tool 介面可靠嗎

BFCL（Berkeley Function Calling Leaderboard，Patil 等人，ICML 2025）量的是 L4 講的那一層：model 看到 tool 的名稱、描述與參數 schema 後，能不能發出正確的 call。例子是「訂下週一從 Boston 到 Chicago 最便宜的航班」：

評分有兩種：AST 檢查把輸出的 call 解析成樹，比對名稱和每個參數的值；執行檢查則真的叫一次，比對結果。多輪的題目在每一個 turn 都檢查狀態和回覆。V4 版加了 web search 和 memory 兩類題。要看分類分數，不要看總分，因為總分把單輪、多輪、平行 call、無關 call 混在一起。Epoch 2026-09 的審查抽 50 題有 24 題有缺陷。

前情AST：L4 講過的語法樹，這裡拿來比對 function call

L4 講 edit tool 時介紹過 AST（abstract syntax tree）：parser 把一串字元讀成一棵樹，節點是語法單位，空格與換行不在樹上。BFCL 用它比對 call：book_flight(flight_id="UA123", passenger_id=1) 和參數順序不同、空格不同的寫法，樹是一樣的，所以不會因為格式扣分；但值錯了（"UA124"）樹就不同。

AST 檢查不用真的執行，所以快、沒有副作用；執行檢查能抓到「語法對但結果錯」的 call。BFCL 兩種都用。

查閱WebArena：能不能完成一個網站工作流程

WebArena（Zhou 等人，ICLR 2024）自架了六種網站：購物、商店後台、Reddit、GitLab、地圖、Wikipedia，共 812 題。例子：在 GitLab 建一個叫「Update onboarding documentation」的 issue，指派給 Alex，加上 documentation 標籤。Agent 看到的是網頁的 accessibility tree，動作只有三種：click 某個節點、type 一段文字、stop 並回答。

Functional check 依題型不同：建 issue 的題檢查 issue 存在、指派人與標籤都對；其他題檢查最後的 URL、頁面內容、後端資料，或一段文字答案。2025 年 ServiceNow 出了 WebArena-Verified：把答案改成結構化輸出，檢查改成對 HTTP 紀錄的確定性比對，拿掉 LLM-as-judge。

查閱Accessibility tree：瀏覽器給螢幕閱讀器看的那棵樹

瀏覽器把網頁畫成畫面之前，先建一棵 DOM 樹；為了讓視障者的螢幕閱讀器能用，它再從 DOM 整理出一棵只留「有意義的元素」的樹，叫 accessibility tree：每個節點有角色（button、link、textbox）、名稱（按鈕上的字）和狀態（勾選、展開）。裝飾用的 div、純排版的元素不在樹上。

WebArena 把這棵樹轉成文字給 agent，每個節點加一個編號，agent 用編號指定要點哪裡。好處是 token 少、不用看圖；代價是靠 canvas 畫的、沒有語意標記的頁面，樹上看不到。OSWorld 改用截圖，就是為了這些樹上看不到的東西。

查閱OSWorld：能不能操作一台真的電腦

OSWorld（Xie 等人，NeurIPS 2024）把動作空間再放大：agent 看到的是整個桌面的截圖，動作是滑鼠和鍵盤，369 題跨瀏覽器、辦公軟體、檔案與系統設定。例子：在試算表加一個計算欄、排序、存成 result.xlsx。每一步都是座標和按鍵。

評分先跑設定腳本（有些設定步驟不算分），記錄 trajectory，取最終狀態，交給 evaluator 算 reward；檢查的對象是檔案的儲存格與公式、app 的設定、系統的狀態。

OSWorld 2.0（2026）改成 108 個長流程，跨 31 個自架網站與專業軟體，每題 300 步以上，平均 27 個 checkpoint 給部分分數，因為原版已接近飽和。

Epoch 2025 年的分析提醒，原版量到的不全是「操作電腦」：約 15% 的題只要 terminal，再 30% 可以用 terminal 和 Python 代替大部分 GUI 操作，約 10% 的題有嚴重錯誤。

查閱SWE-bench 一家：能不能修好真實 repo 的 issue

SWE-bench（Jimenez 等人，2024）的題目來自 GitHub 上真的 issue：給 agent 一個 repo 和 issue 描述，要它交出一份 patch。例子：某個函式碰到空的索引會丟例外，改成回傳空結果，而且既有的行為不能壞。

Grader 只做一件事：套用 patch、跑測試。它們的現況在第 7 章。變體有五個：

  • Verified。OpenAI 人工篩出的 500 題。
  • Lite。300 題的子集。
  • Multilingual。9 種語言。
  • Multimodal。Issue 附圖片。
  • Pro。更難、要改多個檔案。
查閱τ-bench：和使用者對話、守政策、改後端

τ-bench（Yao 等人，2024）加了一個會說話的對手：一個 LLM 扮演客戶，agent 要和它對話，同時守一份航空公司的政策，並透過 API 改一個真的資料庫。政策的例子是「basic economy 的機票不能改」。

一題的典型流程：客戶說「我要把明天的航班改成晚班」，agent 先驗證身分、查訂位、搜航班、說明票價差、取得確認，再叫 change_booking，訂位更新。評分看最終的資料庫狀態，加上回覆內容：r = r_action × r_output。讀取的 call 怎麼叫都可以，多寫了一筆就是 0。

後續的 τ³-bench（Sierra，2026-03）修正了原本的題目，加上銀行領域的知識檢索（698 份文件）和語音。

查閱Terminal-Bench：透過 shell 做完一件事

Terminal-Bench（Merrill 等人，2.0 版 2026）的題目不限於修 bug：程式、系統管理與伺服器設定、資料處理、訓練模型、資安、科學計算流程，都是從頭到尾做完一件事。代表題目：在線上的 KV service 部署新協定，過程中不能掉連線、延遲要維持。

查閱TheAgentCompany：模擬一間公司

  7. 在 RocketChat 回報結果。

  • Perplexity。量預測文字：對一段沒看過的文字，把每個字的負對數機率平均再取指數，數字越小表示 model 越不「驚訝」。
  • Accuracy。答對的比例。
  • F1。用在答案是一組東西時（例如抽出的關鍵字），同時看抓到的比例與抓錯的比例。
  • Preference 或 win rate。把兩個回答放在一起，問人或 judge model 偏好哪一個，Arena 的排行榜就是這樣算的。

  1. 第 1、2 章 · 分數量的是什麼

    同一個 model，兩份報告的分數差了 30 分，可能是哪些原因？公開分數可以拿來做什麼，不能拿來做什麼？

    參考答案與重點複習

    答案：分數是整個系統的輸出，model 只是其中一項。Harness、資源與預算、題目的版本、grader，換掉任何一項，分數都會變（第 1 章）。

    公開分數可以用來挑起點：哪個 model、哪個 harness 值得試。它不能當上線的證據，因為它沒有量你的 tool、資料和政策（第 2 章）。

    重點拆解

    一次評估有固定的骨架：重置環境，在預算內跑 agent loop，最後由 grader 打分。Grader 只看得到三種輸出：最終答案、最終狀態、trajectory。所以分數量到什麼，由出題的人選的東西決定。

    換了什麼例子差多少
    HarnessARC-AGI-3，GPT-6 Astra，同樣最高 effort62.7% → 98.6%
    題目Terminal-Bench 2.0 → 2.1，Opus 4.658.0% → 70.1%
    Grader 與 scaffoldCORE-Bench，Opus 4.542% → 95%
    資源Terminal-Bench 2.0，同一個 agent最多差 6 分

    公開 benchmark 和真實工作還有三個距離。第一，動作空間和 grader 可能和你的不同。第二，多數 benchmark 只有一個 user turn，問問題沒有人回答，所以有自信地猜最划算。第三，只看最終狀態時，過程中刪檔、寄信都不扣分。

    背景補充

    傳統系統的 benchmark 早就有這個規矩。SPEC CPU 的規則要求公開硬體、軟體和編譯器旗標，成績才算數。Agent 的分數也一樣，少了 harness、effort、資源和預算，數字就不能比。

    不同 benchmark 上 harness 的影響也不同。SWE-Bench Pro V2 的研究裡，最強的幾個 model 換 harness 結果不變。所以要看報告寫了什麼，不能用一個固定的倍數換算。

    常見誤解

    「這個 model 在 SWE-bench 拿到 80%，所以它能解 80% 的真實 bug。」這個數字屬於一個系統、一組題目、一種 grader。換成你的 repo 和 harness，要重量。第 6 章還會講到，過了測試也不等於能 merge。

    帶走這幾點
    1. 分數 = 整個系統 × 題目 × grader × 資源與預算 → 比較時固定其他項。
    2. 公開分數挑起點，不是上線的證據。
    3. 三個距離：動作和 grader 不同、沒有使用者、副作用沒人扣分。

    相關：核心觀念〈根本的事實：分數是整個系統的輸出〉、〈最重要的判斷：公開分數回答不了「能不能上線」〉；L4〈評估時要固定 harness〉。

  2. 第 3 章 · 穩定性與成本

    pass@k 和 pass^k 各量什麼？什麼情況該看哪一個？成本為什麼要算每個成功任務？

    參考答案與重點複習

    答案：同一題跑 k 次，pass@k 問「至少一次成功」，量能力的上限；pass^k 問「k 次全部成功」，量穩定性。失敗可以重試、又能自動挑選時看 pass@k。失敗不能重來時看 pass^k，例如客服改資料。

    成本要算每個成功任務，因為失敗的花費也要有人付。每次較貴但常成功的設定，算下來可能反而便宜。

    重點拆解

    設每次的成功率是 p、各次獨立，pass@k = 1 − (1 − p)^k，pass^k = p^k。代入 p = 0.8：

    kpass@kpass^k
    10.800.80
    20.960.64
    40.9980.41
    8約 1.000.17
    16約 1.000.03

    實際計算要逐題算再平均，不能拿整體成功率取次方，因為題目有難有易。兩個指標的張開程度，就是 agent 不穩定的部分。

    比較好幾個維度時用 Pareto：A 每個維度都不比 B 差、且至少一個更好，就是 A 支配 B。沒有人支配的一群是 Rank 1。它不需要權重，只排除不值得考慮的選項；Rank 1 之間依預算和 SLA 選。

    背景補充

    這和 L6 講的錯誤相乘是同一個算式：每步 95%、串 20 步只剩約 36%。pass^k 是同一題重複 k 次，L6 是一題裡的 k 步。

    METR 量 model 能做多長的任務時，也把兩件事分開：50% horizon 和 80% horizon 差 4 到 6 倍。判斷能不能上線，要看成功率要求高的那條線。

    常見誤解

    「pass^8 低於 25%，代表它只做對四分之一的題。」不對。τ-bench 上 gpt-4o 的平均成功率是 61.2%。pass^8 是同一題連續 8 次都對的比例，它說的是穩定性，不是能力。

    帶走這幾點
    1. pass@k 看上限，pass^k 看穩定 → 依失敗能不能重試選。
    2. 成本看每個成功任務，latency 看 p95，要放一個簡單的 baseline。
    3. Pareto 不用權重：先排除受支配的，再依預算和 SLA 選。

    相關：核心觀念〈指標：一個成功率藏住穩定性和成本〉、註〈pass@k 與 pass^k 的估計式〉；L1〈優化目標〉、L6〈錯誤相乘〉與〈獨立假設〉。動手試試的第 3 題會加上 latency 當第三個維度。

  3. 第 4 章 · 雜訊

    兩個 agent 在榜上差 3 分。要先確認哪幾件事，才能說誰比較好？

    參考答案與重點複習

    答案：先確認四件事。第一，題數和誤差範圍：差距有沒有超過雜訊。第二，每題跑了幾次：只跑一次的分數大多是雜訊。第三，設定是否相同：model、harness、資源、預算。第四，兩邊是不是跑同一組題，有沒有逐題配對比較。

    重點拆解

    題數決定精度。N 是題數，p 是成功率，標準誤 = √（p（1 − p）/ N），95% 範圍約 ±1.96 × 標準誤。p = 0.8、N = 50 時約 ±11 分；兩版比較時，差距要超過約 16 分才算數。N 要變 4 倍，標準誤才減半。

    雜訊的來源怎麼壓
    題目抽樣加題目
    每次執行不同：temperature、tool 回傳、路徑走偏每題跑 k 次
    基礎設施：VM 資源、API 錯誤固定並公開設定；換時段重跑

    配對比較只看翻盤的題。兩版都過或都不過的題，對「誰比較好」沒有貢獻。200 題上同樣多 4 分：翻盤 40 題、16 比 24，看不出差別（p = 0.27）；翻盤 12 題、2 比 10，新版較好（p = 0.04）。

    背景補充

    榜單還有一個陷阱：贏家的詛咒（winner's curse）。很多設定一起比時，第一名的分數通常含有一部分好運，重跑一次多半會下降。所以榜首領先一點點時，先重跑再下結論。

    Anthropic 的基礎設施實驗得到一個實用的門檻：差距小於 3 分的，在設定公開並對齊之前都值得懷疑。

    常見誤解

    「每題多跑幾次，雜訊就消掉了。」每題多跑只能壓低同一題的執行變異。抽到哪些題目的雜訊還在，要靠加題目或配對比較。

    帶走這幾點
    1. 先看範圍：範圍重疊的名次可以當同分。
    2. 50 題的題組看不出 10 分以內的進步 → 用配對，列出翻盤的題。
    3. 報分數要附題數、次數、誤差範圍、版本、資源與預算。

    相關：核心觀念〈雜訊：差幾分常常只是運氣〉、〈根本的事實〉。進階題第 1 題會把這些算一次。

  4. 第 5、6 章 · Leakage 與 grader

    為什麼「model 沒用測試集訓練」不能證明分數乾淨？Grader 會往哪兩個方向判錯？

    參考答案與重點複習

    答案：因為分數是整個 stack 的函數，每一層都能帶進答案：few-shot 取自測試題、memory 存了上一輪的嘗試、web search 搜到公開解答、sandbox 留著 git 歷史，開發者反覆看失敗案例再調系統。「沒用測試集訓練」只排除了訓練時那一組（第 5 章）。

    Grader 會往兩個方向錯。False positive：沒做對卻判過，分數高估。False negative：做對卻判不過，分數低估。方向相反，所以分數不能一律打折（第 6 章）。

    重點拆解

    什麼時候漏元件例子
    訓練時Base model、fine-tuning預訓練資料含題目；解答當訓練 trajectory
    評估執行時Prompt、retrieval、memory、web search、environmentFew-shot 取自測試題；memory 存了上一輪；搜到解答；看得到未來的 commit
    開發過程中Scaffold、agent 開發手寫規則針對題目調過；看失敗再調系統

    2026 年的例子：BrowseComp 上，Claude Opus 4.6 懷疑自己在考試，找到評估的原始碼，自己解開加密的答案。SWE-Bench Pro V2 的公開題 99.4%、私有題 81.6%，作者認為更可能的原因是訓練時看過公開的 repo。

    Agent 還會主動鑽漏洞，這叫 reward hacking：改測試、overload 比較運算子、認出特定測試直接回傳期望值。Grader 和 agent 跑在同一個 container 時最容易中招。就算 grader 沒有 bug，過了測試也不等於能 merge：METR 的研究裡，約一半過了測試的 PR，maintainer 不會 merge。

    給 grader 寫四個測試：標準解要過、另一種正確做法要過、什麼都不做要 0 分、改測試要 0 分。

    背景補充

    Benchmark overfitting 是 Goodhart's law 的例子：指標一旦變成目標，就不再是好指標。機器學習用 train、validation、test 三份資料防它：調參只看 validation，test 只在最後跑一次。開發者反覆看測試集的失敗案例，等於把 test set 當 validation 用。

    查 leakage 的常見做法：一次關掉一條管道再重跑，看分數掉多少；讀 trajectory 裡的網址與搜尋字串；再用沒人看過的新題跑一次。查 grader 可以看第三方的審查，例如 Epoch AI 的 Benchmark Reviews。

    常見誤解

    「Model 的 training cutoff 早於 benchmark 發布，就沒有 leakage。」Cutoff 只處理訓練時的那一組。Web search、memory、environment 的洩漏發生在評估當下，跟 model 何時訓練無關。

    帶走這幾點
    1. Leakage 能從 stack 的任何一層進來，而且分數看起來完全正常。
    2. Grader 是程式，會往兩個方向錯；agent 還會主動鑽漏洞 → 把 grader 隔開，給它寫測試。
    3. 引用分數前先查：有私有題嗎？差多少？有人審過嗎？

    相關：核心觀念〈Leakage：答案能從整個 stack 進來〉、〈Grader：它會判錯，agent 還會鑽漏洞〉；L4〈評估時要固定 harness〉。進階題第 3 題會設計防止 leakage 的工作方式。

  5. 第 7、8、9 章 · 飽和與自己的評估

    為什麼 benchmark 是耗材？要評估自己的 agent，第一步做什麼？Grader 怎麼疊、題目怎麼分？

    參考答案與重點複習

    答案：公開題幾個月到幾年就會追上、會有人背下來，缺陷也會浮出來，分數就分不開了（第 7 章）。

    評估自己的 agent，第一步是讀真實的失敗，分類、數數，再把它們變成 20 到 50 個任務（第 8 章）。Grader 疊三層：先查狀態，再用規則掃危險動作，最後才用 judge 看品質，任何一層是 0 就是 0。題目分三堆：開發集可以看失敗；regression 接近 100%，每次改動都跑；held-out 封起來，只看分數（第 9 章）。

    重點拆解

    飽和有兩種意思：追上了人類基準線，或頂尖的 model 分不開。SWE-bench 這條線三年換了四版：Verified 因為飽和和汙染退役，接手的 Pro 在 2026 年 7 月又估計約 30% 的題壞掉，V2 修過之後公開題已到 99.4%。

    Error analysis 的做法：由一位懂使用者的人自己讀至少 30 條 trace，每條只記第一個出錯的地方，歸類後數每一類有多少。這樣寫出來的題才對得上你的問題，不必先挑通用指標。

    Grader 的層問什麼用什麼
    狀態做完了嗎程式查資料庫差異、檔案、測試
    規則過程安全嗎程式掃 trajectory：刪測試、對外送出
    Judge做得好嗎LLM 依 rubric 打分，用人工校準

    長任務用 checkpoint 給部分分數，但要保留一半權重給完成：S_partial = 0.5 ×（達成 ÷ 總數）+ 0.5 × S_full。7/8 沒完成只得 0.44。報告要同時列完成率和平均部分分數。

    背景補充

    這一套和測試金字塔相近：regression 像 CI 裡的測試，held-out 像機器學習的 test set，online eval 像 production 的監控。Anthropic 用瑞士起司比喻：每一層都有洞，疊起來才擋得住。

    課程的 Assignment 3 用解出幾題、每題花多少、每題花多久三個數字排名，也是這樣分開量。

    常見誤解

    「Benchmark 飽和，代表這類工作 AI 已經做得好了。」飽和只代表這組題目分不出強弱。題目通常條件完整、只有一個 turn。同樣是修 repo，SWE-Bench Pro V2 的私有題就只有 81.6%。

    帶走這幾點
    1. 引用分數要寫版本，也要知道它是不是已經退役。
    2. 讀失敗 → 分類 → 寫題：從 20 到 50 題開始，正反都要有。
    3. Grader 疊三層、題目分三堆，線上的失敗再變成新題。

    相關：核心觀念〈飽和：benchmark 是耗材〉、〈建立評估：從真實失敗開始〉、〈用評估做決定：題目分三堆，一次改一件事〉；L6〈失敗的五層〉。動手試試的第 1 題是一個評估 loop 的骨架，進階題第 2 題會替客服 agent 設計評估。

  1. 估算 · 非確定性與樣本數 · p.10、p.31

    算出 pass@4 與 pass^4，再估算 50 題 benchmark 分數的標準誤。新版比舊版高 4 個百分點，算不算進步？

    情境：單次成功率 p = 0.8，各次執行獨立。Benchmark 有 50 題，每題只跑 1 次。舊版得 80%，新版得 84%，團隊想據此宣布新版更好。

    回答時請涵蓋
    • 寫出 pass@4 與 pass^4 的算式與結果。提示：pass@4 = 1 − （1 − p）⁴，pass^4 = p⁴。代入 p = 0.8，先算 0.2⁴ 和 0.8⁴。

    Slides p.10–11 與 p.19 只用 pass^k 一個數字量可靠性；這篇把它擴成 12 個指標，pass^k 對應其中的 outcome consistency。核心觀念〈雜訊〉說一次執行只是雜訊（p.31），這篇每題跑 5 次。〈指標〉的 Pareto 看能力、成本、速度（p.35）；這篇主張可靠性要當獨立的軸。第 9 章〈一份夠用的評估〉列的 pass^k 與成本，這裡都有對應的指標。

    壓縮後的重點

    1. 環境有三樣東西：資料庫、API、政策。Retail 有 500 個使用者、50 項商品、1,000 筆訂單，7 個寫入 API、8 個讀取 API，115 題。Airline 有 500 個使用者、300 班航班、2,000 筆訂位，6 個寫入 API、7 個讀取 API，50 題。政策是一份 markdown，例如每筆已送達的訂單只能退換一次。

    4. pass^k 的定義。一題跑 n 次、成功 c 次，pass^k = C（c，k） / C（n，k），再對所有題目平均。pass@k = 1 − C（n−c，k） / C（n，k）。k = 1 時兩者相同，就是平均成功率。
    5. 最好的 model 也不到一半，而且不穩定。Function calling 下，gpt-4o 在 retail 61.2%、airline 35.2%；claude-3-opus 44.2% 與 34.7%；gpt-3.5-turbo 20.0% 與 10.8%。Retail 的 pass^k 隨 k 快速下降，gpt-4o 的 pass^8 低於 25%。Function calling 優於 ReAct，ReAct 優於 Act。
    6. 失敗原因有三類。抽 115 條 gpt-4o retail 軌跡，40 條失敗，其中 4 條是客戶指令寫壞。剩下的失敗：參數錯或資訊錯約 55%、決策錯（沒照政策）約 25%、複合請求只做一半約 19%。拿掉政策文件後，retail 從 61.2% 降到 56.8%，airline 從 33.2% 降到 10.8%。

    原文怎麼讀

    • 可以跳過：§2 Related Work；§4.1 兩個 domain 的建構過程；§5.1 Table 2 的全部 model，看 gpt-4o 與 claude-3-opus 兩列就夠；Appendix B。
    • 值得看原文：§3 的 reward 與 pass^k 定義（半頁）；Figure 4 的 pass^k 與 pass@k 曲線，兩條線的張開程度就是不穩定的量；Appendix C.2 的完整對話軌跡，看一次 agent 怎麼在政策與客戶之間失敗。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「pass^8 低於 25%，代表 gpt-4o 只做對四分之一的題目。」不對。它的平均成功率是 61.2%。pass^8 是「同一題連續 8 次都對」的比例，低於 25% 說的是穩定性，不是能力。兩個數字的差距就是 slides p.11 要你看的那一塊。

持久 agent 與可觀測性 Persistence, tracing, and isolation

  2. 推薦Dapper: A Large-Scale Distributed Systems Tracing InfrastructureGoogle · 系統論文 · 2010 · 挑段約 20 分

    分散式 tracing 的奠基之作。把 agent 的步驟與 tool call 當 span，整套方法直接搬用。

    導讀適合系統背景的人導讀。重點：sampling rate 是主要的成本控制。

    摘要讀約 3 分；原文約 20 分

    一句話：Dapper 是 Google 的分散式 tracing 系統：把一個請求經過的所有 RPC 記成一棵 span 樹，只在幾個共用 library 裡埋點，靠抽樣把 overhead 壓到看不見。它是 OpenTelemetry 這類工具的原型。

    跟這堂課的關係

    這篇不談 agent，放在這一講的原因是 trajectory。Slides p.11 說 evaluator 看最終答案、環境狀態、trajectory；p.31 說只看結果會放過不安全的執行。要看 trajectory，就要先把每一步記下來，Dapper 的 span 樹就是記法。核心觀念〈指標〉要的成本與 latency（p.10），每個 span 都帶時間戳，可以逐步加總。第 2 章說公開分數回答不了「能不能上線」，第 9 章說線上要用真實流量評估；Dapper 就是從真實流量取樣的機制。

    壓縮後的重點

    1. 一個 trace 是一棵樹，節點是 span。每個 span 有名稱、span id、parent id，共用一個 64-bit 的 trace id。換成 agent：一次 session 是 trace，每次 LLM 呼叫與 tool call 是 span。
    2. 只在三個地方埋點，應用程式不用改。Thread：trace context 放在 thread-local storage。Control flow：callback 建立時存下 context，執行時還原。RPC：所有 RPC 自動包成 span。Google 的程式都走這幾個 library，覆蓋率接近全部。
    3. Annotation 讓應用程式加自己的資料。帶時間戳的文字或 key-value，每個 span 有容量上限。70% 的 span、90% 的 trace 至少有一個 annotation。換成 agent：prompt、tool 參數、token 數都是 annotation。
    4. Overhead 的數字。建一個 root span 204 ns，非 root 176 ns，沒抽中時加 annotation 約 9 ns。收集 daemon 最多用一個 core 的 0.3%；trace 流量低於 production 網路的 0.01%。全抽（1/1）時 latency 增加 16.3%、throughput 降 1.48%；1/16 時 latency 增 2.12%，已在實驗誤差 2.5% 內。
    5. 抽樣是主要的成本控制。第一版 production 統一抽 1/1024；高流量服務低到 0.01%；每秒幾十個請求的服務可以全記。後來改成 adaptive sampling，目標是每單位時間固定的 trace 數。收集端再抽一次：依 trace id 的 hash 決定整棵樹留或丟。
    6. 收集是 out-of-band。Span 先寫本機 log，daemon 拉走，collector 寫進 Bigtable，一列一個 trace、一欄一個 span。中位延遲 15 秒以內。抽樣後每天仍超過 1 TB，要留至少 2 週。
    7. 用途超出原本的設計。約 200 位工程師每個工作天用 UI。Ads Review 團隊靠它把 latency 改善兩個數量級。

    原文怎麼讀

    • 可以跳過：§2.6 安全與隱私；§3 部署狀況；§5.1 DAPI；§8 Related Work。
    • 值得看原文：§2.1 的三張圖（五個 server 的請求、它的 span 樹、一個 span 的內容）；§4.3 的 Table 2（6 種抽樣率對 latency 與 throughput 的影響）；§6.2 long tail latency 的案例。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「Dapper 抽 1/1024，所以 agent 的 trace 也該抽樣。」不對。1/1024 是給每秒數萬個請求的服務用的；論文說每秒幾十個請求的服務可以全部記錄。Agent 的請求少、每次又貴，評估又要逐筆看 trajectory，所以全記。要省的是儲存，用整棵保留或丟棄的二次抽樣。
