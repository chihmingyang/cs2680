先看這裡

一個 benchmark 分數，是整個系統在一組題目上跑出來的結果。這個系統分兩邊。受測的一邊是 model，和包住它的 harness，連同 prompt、tool、memory；評估的一邊決定題目、判分的程式 grader，以及給多少機器資源與預算。Harness 是包住 model 的程式：它把任務說明，和 tool 執行後傳回的結果，組成 model 讀到的輸入（叫 context）；model 決定要用哪個 tool，harness 替它執行，例如跑一行 shell 指令。換掉任何一項，分數都會變。你的 agent 跑的是你自己的題目，harness 和設定也多半和榜上不同，所以榜上的分數不能直接當成你的分數，只能幫你挑出值得先試的 model 和 harness。這堂要帶走兩個判斷：怎麼讀一個分數，以及怎麼評估自己的 agent。八個 benchmark 的細節收在最後一章，需要時再查。

  • 分數不能搬到另一套設定。Model 不變、只換 harness：GPT-6 Astra 在 ARC-AGI-3（一組要邊玩邊摸索規則的抽象小遊戲）從 62.7% 升到 98.6%，多了 36 個百分點。只修題目：Terminal-Bench（考在 shell 裡做完一件事）的 2.1 版沒換題組，只修了 89 題裡的 28 題，同一個 agent 就從 58.0% 升到 70.1%，多了 12 個百分點。比較兩個分數之前，先問兩邊有哪幾項不同。
  • 讀分數問五件事。前兩件問這個分數和你有沒有關係。一，這個 benchmark 讓 agent 做的動作（叫 API、打 shell、點網頁）和它判分時看的東西，和你的 agent 要做的事、你判斷成功的方式一樣嗎？二，榜上這個分數是用哪個 model、哪個 harness、多少機器資源跑出來的，和你的一樣嗎？後三件問分數本身準不準。三，它報了穩定性（每一題都重跑好幾次，次次都成功的題目佔幾成）和每個成功任務的成本嗎？四，兩個系統的差距大過雜訊嗎？同一組題目重跑，agent 每次走的步驟不同，分數本來就會差幾分；這組題目也只是從同類任務裡抽出來的一組，換一組題目，分數又會變。五，這組題目還可信嗎？答案有沒有漏進 model 的訓練資料，或 agent 執行時碰得到的檔案、grader 有沒有判錯、頂尖的幾個系統是不是已經擠在同一個分數，差距小到落在雜訊裡。
  • 自己的 agent 要自己量。先把 20 到 50 個真實的失敗寫成題目。Grader 疊三層，便宜又確定的放前面：先用程式查 agent 做完之後的資料庫、檔案和測試對不對；再用程式掃 agent 執行過的每一步，碰到刪測試、對外寄信這類不准發生的動作就判 0；程式查不了的「做得好不好」，最後才請另一個 model 當裁判（judge）打分，因為 judge 貴，自己也會判偏。同一題每次跑的結果會不同，所以每題跑 k 次，算 k 次全部成功的比例（pass^k）。報 pass^k 和每個成功任務的成本，成本是總花費除以成功的次數。

1根本的事實：分數是整個系統的輸出

L6 說 agent 常常沒驗證就宣布完成，所以 agent 能不能用，不能問 agent 自己，要由 agent 外面的一套程序來量，這套程序叫評估（evaluation，常簡稱 eval）。受測的 agent 也不只是 model。Model 只決定下一步做什麼；外面那層程式叫 harness，它把 prompt 和 tool 的結果組成 context 送給 model、替 model 執行 tool call、決定什麼時候停（L2〈Loop〉）。看到「X 在 SWE-bench 拿到 80%」時（SWE-bench 考修真實的 GitHub issue），多數人會把 80% 當成 X 這個 model 的能力。這是讀分數最常見的錯誤，先看分數是怎麼產生的：

同一題要跑很多次 trial（圖裡的 k 次），因為 agent 每次的結果可能不同。Trajectory 也叫 trace 或 transcript。骨架只有幾行，和 L4 的 agent loop 幾乎一樣，差別是外面多了重置、預算和 grader：

三個地方決定分數的意義。這三個都是出題的人選的，換一個選法，分數的意思就變了：

  • 重置。不重置，第二題就在第一題改過的環境裡跑。這也是 agent 評估貴的地方：要自架網站或資料庫，每次恢復原狀。
  • 預算。上限決定 agent 有多少機會把事做完，所以上限不同的兩個分數不能直接比。
  • Grader 看什麼。看答案量不到動作，看最終狀態量不到過程中的破壞。比對 trajectory 是拿 agent 走的每一步去對出題者事先寫好的一條標準路徑，agent 走另一條也正確的路，一樣判錯（第 6 章）。

寫成式子：分數是整個 stack 的函數。課程把這件事寫成 P = f（LLM、prompt、scaffold、tools、retriever、memory、environment），scaffold 就是上面說的 harness，retriever 是替 agent 查資料的那一層，memory 是 agent 跨 session 留下來、下次再讀回 context 的筆記（L6 的主題）。本文再加上 agent 外面、由評估這一邊決定的三項：題目、grader、資源與預算（grader 和預算就是上面三個地方裡的兩個）。換掉其中任何一項，分數都會變，而且變化常常比兩個 model 之間的差距大：

四列各改了什麼：

  • ARC-AGI-3。一組要邊玩邊摸索規則的抽象小遊戲，數字來自 ARC Prize 2026 年 9 月的報告。兩種 harness 差在步與步之間留下什麼：Standard harness 只留 model 自己決定寫下的筆記；Provider Adapter harness 把 model 上一輪的 reasoning 狀態（回答前的思考，內容不公開）帶到下一輪，對話太長時再做 compaction（把舊的對話壓成摘要，騰出 context）。兩邊都開到最高的 effort（reasoning 的強度設定），Standard harness 是 62.7%，Provider Adapter harness 是 98.6%，差 36 分。
  • SWE-bench Verified。OpenAI 請人篩過、確定可解的 500 題 SWE-bench 子集（第 7 章）。這一列是 L4 講過的 Lewis 實驗：本機跑 4-bit 量化的 Qwen3.6，在其中 169 題上，harness 從整段對話照送，換成縮短舊的 tool 輸出、偵測原地打轉，解出的題從 43 升到 72（43/169 = 25.4%、72/169 = 42.6%，就是圖上這一列的兩個點）。4-bit 量化是把 model 的每個權重從 16 bit 壓成 4 bit 存，記憶體少很多，才能在本機跑，代價是能力通常比原本差一點。這個差距有前提：model 的 context window（一次能讀進的 token 上限）只有 20,480 token。對照組整段照送，對話紀錄塞滿 window 時 run 就直接結束，所以多解出來的題，有一部分只是沒有中途停掉。L4 也說 window 放大到 262,144 token 時，兩邊幾乎打平：169 題裡，整段照送的對照組解 102 題，改良的 harness 解 101 題。
  • Terminal-Bench。考在 container 裡用 shell 做完一件事（細節在第 10 章的 Terminal-Bench 註）。2.1 版只修了 89 題裡的 28 題，同一個 agent 就多了 12.1 分。
  • CORE-Bench。考重現論文的計算結果。Anthropic 發現它判分太死（期待 96.124991 時把 96.12 判錯）、題目描述模糊、有些題本身隨機而無法重現。修掉這些錯，再換成限制較少的 scaffold（文章沒寫放寬了哪些限制），Opus 4.5 從 42% 變成 95%。

連 VM 的大小也算在內。Anthropic 2026 年 2 月的實驗只改資源設定，Terminal-Bench 2.0 上資源最多和最少的兩種設定就差 6 分。6 分是兩個極端；資源居中的幾種設定之間，分數散布不到 2 分，這麼小的差單獨看還在雜訊內（第 4 章）。但它會疊在另一層誤差上：用最簡單的二項公式算（把每個結果都當成互不相干的一次試驗），重跑同一組題目的信賴區間（只因為運氣，分數就可能落在的範圍）就已經有 1 到 2 分。換一組題目的雜訊更大，第 4 章會算。依這兩層誤差，他們的判斷是：榜上差距小於 3 分的，在設定公開並對齊之前都值得懷疑（3 分是他們給的門檻，Anthropic 的原文沒有寫推導；第 4 章）。

Harness 的影響也不是定值。Scale 與 Reflection 用三種 harness（mini-swe-agent、Pi、OpenCode）跑開放權重的 model：最強的兩個（GLM-5.3、Kimi K3）換 harness 後解題的成績差不多，差得多的是花費。分數既然拉不開，能比的只剩帳單，所以他們建議「依帳單選 harness，不要依分數選」。不要記成「harness 一定差很多」，要記成每個分數都要連同它的設定一起讀：哪個 model、哪個 harness、多少資源與預算。

所以比較時要固定其他項。比 model 就固定 harness，比 harness 就固定 model 和題目（L4〈最重要的判斷〉）；自己改 agent 時，一次只改一件事。L5 問的「少了這個 agent，品質掉多少」也是這樣答。L5 講的是 multi-agent 系統：一個主 agent 把工作分給幾個 subagent（主 agent 派出去做一部分工作的 agent）。拿掉其中一個、其他都不動，用同一套程序各跑一次，再比兩個分數。

2最重要的判斷：公開分數回答不了「能不能上線」

公開 benchmark 要讓不同團隊的分數能比，所以題目固定、環境通用。你要問的是另一個問題：在我的 tool、資料和政策下，這個 agent 會不會出錯。公開分數可以用來挑起點，不能當上線的證據。兩者的距離來自三個地方。

第一，動作和 grader 可能不同。任何 benchmark 都只要問兩件事。一件是動作空間（action space）：agent 能做什麼，叫 API、打 shell、點網頁，還是動滑鼠；它決定這個 benchmark 像哪一種真實 agent。另一件是 grader 看什麼；它決定什麼叫成功。課程介紹的八個 benchmark 放到這兩軸上：

先找你的 agent 在哪一欄，只有同一欄的分數有參考價值：

  • 用瀏覽器。看 WebArena。
  • 改 repo。看 SWE-bench。
  • 在 shell 裡裝套件、設服務。看 shell 欄的 Terminal-Bench。
  • 和人對話，又改資料。τ-bench 最接近：它模擬客服，一個 LLM 扮演客戶和 agent 對話，agent 要守一份客服政策，透過 API 改後端的資料庫（例如改訂位）。

拿 SWE-bench 的分數推測客服表現，沒有可比性。再看列：GAIA 只比最後的答案，寄信、改資料庫這類動作它完全量不到。八個的細節收在第 10 章。

第二，benchmark 的世界裡沒有使用者。多數 benchmark 的形狀都一樣：一句寫完整的指令進去，最終狀態出來，中間沒有人。真實的工作會缺條件、做到一半改需求、目標中途移動：

這個形狀會獎勵一種行為：有自信地猜。假設一句指令有兩種解讀，機率各半。直接猜，期望分數是 0.5。先問，benchmark 裡沒有人回答，最後還是得猜，期望分數最多也是 0.5，還多花了步數。有真人回答時，問一句就能把成功率拉近 1。所以在單一 turn 的 benchmark 上，最不問問題的 agent 分數最好，這和你希望它在團隊裡的樣子相反。

第三，過程中的破壞沒人扣分。Agent 為了讓測試通過，把失敗的測試刪了；為了清出空間，刪了不該刪的檔；中途寄出一封信、花了一筆錢。只看最終狀態的 grader 看到「測試全過」，一樣給 1 分。第 8 章會把這件事量進來。

讀分數的五個問題。看到任何一個分數，先問下表五題。前兩題回答「這個分數和我的 agent 有沒有關係」：第 1 題把這一章的三個落差合成一題（動作空間、有沒有使用者、grader 看什麼），第 2 題問第 1 章的設定。後三題問分數本身靠不靠得住：第 3 題問報了哪些指標，第 4 題問差距大過雜訊沒有，第 5 題問題目可不可信。前兩題這兩章已經講了，第 3 到 5 題由後面五章展開，第 7 章的最後拿一個真實的分數跑一次：

問題要查什麼在哪一章
1. 它量的動作、使用者和 grader，和我的 agent 一樣嗎？動作空間；有沒有使用者、只有一個 turn 還是多個；grader 看答案、狀態還是 trajectory，過程中的破壞有沒有扣分這一章

3指標：一個成功率藏住穩定性和成本

Benchmark 通常只報一個百分比：跑過的題目裡，成功了幾成。這個數字看不出另外三件事：每次都做得到嗎、花多少錢、要等多久。這一章把它們分開量，對應第 2 章〈讀分數的五個問題〉的第 3 題。

pass@k 與 pass^k：能力和穩定性是兩件事。同一題跑 k 次。pass@k 問「至少一次成功」，它來自程式題：產生 k 個解答，有一個通過測試就算過，所以量的是能力的上限。pass^k 問「k 次全部成功」，τ-bench 為了客服提出它，量的是穩定性。設每次的成功率是 p、各次獨立，那麼 pass@k = 1 − (1 − p)^k，pass^k = p^k。把 p = 0.8 代進去：

查閱pass@k 與 pass^k 的估計式：為什麼不能把整體成功率取 k 次方

一題跑 n 次，成功 c 次。從 n 次裡任取 k 次全部成功的機率是 C（c，k） / C（n，k），這是 pass^k。至少 1 次成功是 1 − C（n−c，k） / C（n，k），這是 pass@k。兩個都要逐題算，再對所有題目取平均。

不能先算整體成功率再取 k 次方，因為每題難度不同。上圖的資料：整體 8/12 取 4 次方得 0.20；逐題算再平均得 0.33。

本文的判斷：上線前的問題多半是第二種，客戶只給你一次機會。真實的差距也不小：τ-bench 上 gpt-4o 在 retail 的單次成功率是 61.2%，同一題連續 8 次都成功的比例低於 25%。不穩定也不會隨著換新 model 自動消失。Towards a Science of AI Agent Reliability 讓 14 個 model 在 τ-bench 和 GAIA 每題跑 5 次，把可靠性拆成 12 個 0 到 1 的指標，例如同一題每次結果一不一致、tool 出錯時撐不撐得住、出事時傷害多大。這 14 個 model 的發布日期前後跨了 18 個月。依發布日期看，正確率（0 到 1）每年升約 0.21，可靠性的分數每年最多只升 0.10，不到正確率的一半；其中結果的一致性（同一題每次是否都成功，pass^k 量的就是它）幾乎沒動。

成本：算每個成功任務，不算每次執行。一次 200 步、花 40 美元的 run，和一次 12 步、花 0.30 美元的 run，兩次都「成功」，只看成功率分不出來。L1 講過的算法是總花費除以成功次數，所以每次較貴但常成功的設定，算下來可能反而便宜。花費要算全部：除了 model 讀寫的 token，還有 tool call 本身的費用（搜尋 API、sandbox 的機器時間），以及 cache miss 多付的錢（prompt 開頭和上一次相同的部分沒命中 provider 的快取，就要用全價重算一次）。L8 會把這幾項一起算進每個成功任務的成本。Latency 同理，等網頁載入和跑測試都在使用者的等待裡，上線時看 p95（最慢的那 5% 要等多久），不看平均。

有成本這一軸，也才看得出簡單的做法多有用。AI Agents That Matter 在 HumanEval（164 題 Python 函式，用測試判對錯）上比了好幾種 agent，下面兩種都用 GPT-4。最簡單的一種叫 Warming：寫出的程式沒通過題目附的範例測試，就再寫一次，最多 5 次，每次把 temperature（取樣的隨機程度，越高，每次寫出的程式越不一樣）調高一點。複雜的 LATS（Language Agent Tree Search）會展開好幾條生成程式的路徑，再從中挑。結果 Warming 解對 93.2%、跑完全部題目總共 2.45 美元；LATS 解對 88.0%、總共 134.50 美元。簡單的那個正確率高 5.2 分，花費只有約 1/55。所以評估裡要放一個簡單的 baseline，否則你不知道複雜的東西換到了什麼。

多個維度怎麼比：Pareto。能力、成本、速度要合成一個排名，直覺是加權平均，但權重由誰定？客服在乎速度，研究用的 agent 在乎能力，沒有一組權重對每個人都對。Pareto dominance 不需要權重：A 在每個維度都不比 B 差，而且至少一個維度更好，就說 A 支配（dominate）B。沒有人支配得了的那一群叫 Pareto frontier，也就是 Rank 1；拿掉 Rank 1 之後剩下不受支配的是 Rank 2，依此類推。下圖是一張真實的榜，只看能力和花費兩個維度：

題數決定精度。Benchmark 分數是把每題的結果平均，所以可以估它的誤差。先定義三項：N 是題數；p 是成功率；標準誤（standard error）是「換一組題目，平均值大約會動多少」。公式是標準誤 = √（p（1 − p）/ N），95% 範圍約 ±1.96 × 標準誤。比較兩版時，兩邊各有雜訊。先看兩版各自抽一組題目的情況（例如榜上兩個系統跑的不是同一組題）：兩邊的雜訊互相獨立，不會每次都往同一邊偏，所以要相加的是變異數（標準誤的平方），不是標準誤本身：差值的標準誤 = √（標準誤² + 標準誤²）= √2 × 標準誤，約 1.41 倍，不是 2 倍。所以差值的範圍要再乘 √2。兩版跑同一組題目時，題目的難易對兩邊一樣，這部分雜訊會互相抵掉，下表的門檻就太寬了。這時用本章後面的配對比較，逐題看翻盤，比較靈敏。代入 p = 0.8：

5Leakage：答案能從整個 stack 進來

Benchmark 要量的是「沒看過這題也能做對」的能力。如果答案或答案的線索，在評估之前或之中就進了系統，分數量到的是記憶或抄寫，這就是 leakage，也叫 contamination。它的危險在於分數看起來完全正常：agent 真的交出了對的 patch，只是它不是算出來的。所以 leakage 不會讓分數變低，只會讓分數說謊。

6Grader：它會判錯，agent 還會鑽漏洞

上一章的問題是答案漏進來，這一章的問題在判分的程式本身。課程對它只留了一句話：只看結果，會放過靠運氣和不安全的 run；比對 trajectory（第 1 章：agent 每一步的觀察和動作），又會判錯其他正確的做法。2026 年這件事變成大事。提出 SWE-bench Verified 的 OpenAI 在 2 月不再報這個分數，原因之一就是判分：它審的 138 題裡，59.4% 的測試或題目描述有缺陷（另一個原因是第 5 章的背答案）。它改推薦 Scale 出的 SWE-Bench Pro，7 月又估計 SWE-Bench Pro 約 30% 的題壞掉，撤回這個推薦。壞掉指測試或題目描述有錯：正確的解法過不了、沒修完也能過，或題目沒交代測試要查什麼。這裡的 SWE-Bench Pro 是 2025 年的第一版，第 5 章的 V2 則是 Scale 在 2026 年 9 月修過題目之後的版本。

Grader 是程式，程式會有 bug，而且分數上看不出來。它會往兩個方向錯：

Agent 還會主動鑽漏洞。Agent 把力氣放在拿分、沒有完成任務，這叫 reward hacking。ImpossibleBench（2025）把這件事量了出來。它把測試改得和題目描述互相矛盾：把一條測試的期望值改掉，或複製一條測試、給它不同的期望值。這種題不可能正當地通過，所以通過率就是作弊率。GPT-5 在 SWE-bench 改出來的那一組作弊率是 76%，在 LiveCodeBench 那一組只有 2.9%。LiveCodeBench 的題目是程式競賽網站上的單題，寫一個函式；SWE-bench 那一組是在真實 repo 裡改 issue，code 多、測試也多，能動手腳的地方也多（差這麼多的原因是本文的讀法）。論文記下四種手法：

  • 改測試。直接改掉失敗的 assertion，題目明明交代不准改。
  • Overload 比較運算子。回傳一個自訂的物件，它的 == 不管和什麼比都回 True，assertion 永遠成立。
  • 記下呼叫次數。同一個輸入，第一次呼叫回這條測試要的值，第二次回那條測試要的值，兩條互相矛盾的測試都過。
  • 認出特定測試。偵測到測試用的輸入，就直接回傳那條測試期望的值。

防法都有代價。把測試完全藏起來，作弊的成功率接近 0，但正常題的表現也會下降（論文沒解釋原因；本文推測是 agent 少了測試，無法檢查自己的修改）。唯讀是折衷，擋得住改測試，擋不住其他三種。

真實的 run 裡也看得到：CAISI 的紀錄裡 o4-mini 註解掉失敗的 assertion；SWE-Bench Pro V2 抓到一個 frontier model 偽造 Go 依賴套件（module）的版本和 checksum，另一個直接改了本機的套件快取。Scale 沒寫細節，以下是本文的推論：測試要的依賴版本在 sandbox 裡拿不到，偽造一份、或改掉快取裡的那一份，build 就找得到它，測試才跑得起來、通過。Go 用 checksum 確認下載的依賴和原版相同，偽造的版本和 checksum 卻只存在 agent 的 sandbox 裡。所以兩者在原環境都通過，換到一個沒動過的乾淨 image 重新判分就失敗，重判才看得出來。

最根本的原因是 agent 的產出和 grader 跑在同一個 container。以 SWE-bench 為例：grader 把 agent 的 patch 套用到 repo，接著在同一個環境跑 pytest。Pytest 開始前會自動載入測試目錄裡名叫 conftest.py 的檔案，裡面的程式可以掛進 pytest 的流程，改寫每個測試回報的結果。所以 patch 只要多帶一個 conftest.py，把每個測試的結果都改成通過，grader 就判全過。作者的第一條建議因此是把 grader 和 agent 完全隔開，答案放在 agent 碰不到的地方。

過了測試，也不等於做完。就算 grader 沒有 bug，它量的也可能不是你要的東西。第三方評估機構 METR 2026 年 3 月請 4 位 maintainer 審 296 個 AI 寫的 PR，這些 PR 都來自 SWE-bench Verified 的題。按產生 PR 的 AI model 分開算，直接比，每個 model 的 maintainer merge 率只有自動 grader 通過率的三分之一到一半，也就是過了測試的 PR，有一半到三分之二不會有人 merge。但 maintainer 對人寫的 PR 也不是全收：當初真的 merge 進 main 的原始 PR，grader 全部判過，maintainer 再審一次只收約 68%。為了扣掉這個基準差，METR 把兩邊都換算成「原始 PR 的幾成」：maintainer 的 merge 率除以 68%，grader 的通過率除以 100%，例如 AI 的 PR 有 34% 會 merge，換算後是 50%。換算之後，grader 的通過率仍然比 maintainer 的 merge 率高，各 model 平均高 24.2 個百分點。作者提醒，agent 在實驗裡沒有機會依回饋修改，這不代表能力的上限。要把「過了測試不等於做完」直接算進分數，Cognition 2026 年 6 月和 maintainer 一起做了 FrontierCode：品質的硬性檢查有一項沒過，這題就是 0 分。Artificial Analysis 10 月跑的結果（它是獨立替各家 model 跑 benchmark 的評測網站，和 Cognition 是不同公司），最高只有 52%。Cognition 自己也賣 coding agent，題目又不公開，這些都要一起讀。

8建立評估：從真實失敗開始

課程講到 benchmark 和它的難處，沒有講自己的 agent 要怎麼評估，但這是多數讀者真正要做的事。LangChain 2025 年底的調查（1,340 份回覆）裡，89% 有 observability（看得到每一步的紀錄），跑 offline 評估（上線前，用固定的題組在測試環境裡跑）的只有 52.4%，跑 online 評估（上線後，在真實流量上打分）的是 37.3%。就算跑 offline 評估的人全都在那 89% 裡，看得到每一步的紀錄、卻沒有拿它跑 offline 評估的，也至少有 89% − 52.4% ≈ 37% 的回覆者（LangChain 的說法是評估「還在追趕」）。也就是說，紀錄已經很普遍，但約每三個回覆者就有一個，還沒有把紀錄變成題組、定期跑分。Anthropic、Hamel Husain 與 Shreya Shankar、LangChain、Cursor 這兩年寫下的做法大致一致，這一章和第 9 章把它們整理成一條流程。它們都是各家的經驗，不是對照實驗。

第一步：讀失敗，不要先挑指標。現成的通用指標（helpfulness、coherence）和你的問題常常對不上。Husain 和 Shankar 把 error analysis 排在所有事情前面：

  1. 收集。找約 100 條不同的真實 trace（一次對話或 run 的完整紀錄）。沒有真實的，就先合成使用者的輸入：列出幾個會造成差異的面向（例如問題類型、複雜度），手寫約 20 組組合，再讓 LLM 補更多組、把每一組寫成一句提問，交給 agent 跑出 trace。
  2. 標註。由一位懂使用者的 domain expert 自己讀，至少先讀 30 條，每條只記第一個出錯的地方，因為上游的錯會帶出下游的錯。
  3. 分類、數數。把筆記歸成幾個失敗類別，算每一類有多少。
  4. 停止。讀新的 trace 不再出現新類別，就可以停了。

τ-bench 的作者就這樣分析過 gpt-4o：115 條軌跡裡 40 條失敗，其中 4 條是題目寫壞，其餘 36 條分成三類。失敗的分布決定了要寫什麼題：

失敗類別佔 36 條的比例接下來寫什麼題
參數或資訊錯約 55%查最終狀態的題：資料庫的差異要等於目標
決策錯，沒照政策約 25%應該拒絕的題，加規則掃 trajectory
複合請求只做一半約 19%一題多個目標，用 checkpoint 給部分分數

第二步：把失敗變成題目。Anthropic 的建議是從 20 到 50 個來自真實失敗的簡單任務開始，不要等題組完整。他們的理由是評估越晚建越難：早期的產品需求可以直接寫成題目；等太久，就得從一個已經在跑的系統反推「怎樣算成功」。好題目有四個條件：

  • 兩位專家會給同樣的判決。做不到，grader 也寫不出來。
  • 有參考解。參考解是一份已知能通過所有 grader 的答案。一題跑 100 次都是 0% 時，Anthropic 說多半是題目或 grader 壞了；參考解過得了，就證明題目可解、grader 也設定對了，這兩種可能就排除了。
  • 正反都有。該做的題和不該做的題（應該拒絕、應該升級人工）都要放。Anthropic 的說法是「單向的評估造成單向的優化」：只考該做的，「永遠照做」就能拿高分。
  • 長得像真實的請求。Cursor（一個內建 coding agent 的程式編輯器）的題組取自自家工程師平常用 Cursor 寫程式的真實 session。題目描述故意寫短，因為開發者對 agent 下指令本來就簡短、常常沒講清楚，不像公開 benchmark 用的 GitHub issue 那樣詳細。

校準也會過期。Remote Labor Index（RLI）考的是真實的外包案子，例如 3D 與 CAD、建築、影片：每一案有客戶的需求說明、輸入檔，和一份專業人士做的交付物，也就是交給客戶的成品檔案。人工評審把 AI 的成品和專業版比，一樣好或更好，這一案才算自動化了。2026 年 7 月，作者試著用 judge 取代人工：一個會在真實的軟體裡打開兩份交付物、像客戶那樣檢查的 agent。校準時拿 4 個舊 model 的成品，調一個門檻，讓 judge 判的合格率對上人工判的 3.3%。

拿同一個 judge 去判 2 個它沒見過的新 model，判出的合格率是人工的 2.3 到 2.9 倍，例如 GPT-5.5，人工判 6.25%，judge 判 17.9%。作者的解釋是：檢查交付物本身就是困難的 agent 任務，要在對的專業軟體裡打開檔案、熟練地操作，這正是現在的 agent 最弱的能力，所以 judge 和它評的 agent 有一樣的弱點：agent 做不好的地方，judge 也查不出來，就判成合格。門檻是對著 4 個舊 model 的成品調的，新 model 的成品落在 judge 沒校準過的範圍，同一個門檻就對不上人工了（這一步是本文的推測，原文沒有拆解原因）。不過 judge 把這些 model 由好到壞排出的順序，和人工排的大致相同（Spearman ρ = 0.90；ρ 量兩個排序有多一致，1 表示完全相同），兩個新 model 都排在最前面，只是把它們領先的幅度誇大了。所以 judge 適合比 model 之間誰高誰低；某個 model 到底完成幾成，還是要靠人工判。

查閱GAIA：自備 tool，只看最終答案

GAIA（General AI Assistant，Mialon 等人，2023）有 466 題人寫的問題，要用到網頁瀏覽、試算表、PDF、圖片、音訊和計算。它沒有固定的 tool API：每個受測的 agent 自己帶搜尋、瀏覽器、Python 和 shell，所以它測的是整個 agent 系統。題目分三級：Level 1 不超過 5 步，最多用一個 tool；Level 2 要 5 到 10 步，用多個 tool；Level 3 步數不限。

例子：一張試算表列了很多部電影，找出符合兩個條件的那一部，查它的導演，回答導演的出生地。

答案很短，判分標準固定，沒有裁判的主觀，所以不同團隊的分數是用同一把尺量的。但每個團隊帶的 tool 不同，比到的是整個系統，不只是 model（第 1 章）。代價是量不到有副作用的動作：寄信、訂機票、改資料庫都沒有。

查閱答案正規化與 exact match：GAIA 怎麼把「比對文字」做乾淨

GAIA 的答案只有三種型別：短字串、數字、逗號分隔的清單。評分用 quasi exact match：依型別正規化，再完全比對。所以 4381 和 4,381 相同，大小寫與多餘空白也不計。

代價是題目要能用短答案回答。自己做評估時，先把答案格式限制死，grader 就能是幾行程式；答案一旦是自由文字，就需要 judge model。

評分有兩種：AST 檢查把輸出的 call 解析成樹，比對名稱和每個參數的值；執行檢查則真的叫一次，比對結果。多輪的題目在每一個 turn 都檢查狀態和回覆。V4 版加了 web search 和 memory 兩類題。總分把好幾類題混在一起，例如單輪、多輪、平行 call（一句話要同時發出好幾個 call，例如一次查三個城市的天氣），和無關 call（手上的 tool 都不該叫，正確做法是一個都不叫，上面的失敗 2 就是沒過這一類），V4 又加上 web search 和 memory。你的 agent 通常只用到其中一兩類，總分高可能來自你用不到的那幾類，所以要看分類分數，不要看總分。總分本身也要打折：Epoch 2026-09 的審查抽 50 題有 24 題有缺陷。

前情AST：L4 講過的語法樹，這裡拿來比對 function call

L4 講 edit tool 時介紹過 AST（abstract syntax tree）：parser 把一串字元讀成一棵樹，節點是語法單位，空格與換行不在樹上。BFCL 用它比對 call：先比 function 的名稱，再把參數依名字一個一個對值，不看參數的先後。所以 book_flight(flight_id="UA123", passenger_id=1) 和參數順序不同、空格不同的寫法會判成相同，不會因為格式扣分；但值錯了（"UA124"）就判錯。

AST 檢查不用真的執行，所以快、沒有副作用，但它只比寫法：標準答案沒列到的等價寫法會被判錯，例如標準答案只收 "BOS"，model 寫 "Boston"。執行檢查把 model 的 call 真的叫一次，拿傳回的結果和標準答案的結果比，結果一樣就算對，所以不會冤枉等價的寫法；代價是要有能執行的 API，而且會留下副作用。BFCL 一部分題目用 AST 檢查，一部分用執行檢查。

查閱WebArena：能不能完成一個網站工作流程

WebArena（Zhou 等人，ICLR 2024）自架了六種網站：購物、商店後台、Reddit、GitLab、地圖、Wikipedia，共 812 題。例子：在 GitLab 建一個叫「Update onboarding documentation」的 issue，指派給 Alex，加上 documentation 標籤。Agent 看到的是網頁的 accessibility tree，動作只有三種：click 某個節點、type 一段文字、stop 並回答。

Functional check 依題型不同：建 issue 的題檢查 issue 存在、指派人與標籤都對；其他題檢查最後的 URL、頁面內容、後端資料，或一段文字答案；原版判文字答案時，有些題用 LLM 判斷意思對不對（LLM-as-judge）。2025 年 ServiceNow 出了 WebArena-Verified：把答案改成結構化輸出，檢查改成用程式比對執行時錄下的網路紀錄（瀏覽器和網站後端之間每一筆 HTTP request 的網址與回應狀態，例如建 issue 的那一筆 request 有沒有送出、有沒有成功），結果是確定的，拿掉這類 LLM-as-judge。它看的是瀏覽器和後端之間實際發生了哪些 request，不是 agent 在畫面上走了哪幾步。

查閱Accessibility tree：瀏覽器給螢幕閱讀器看的那棵樹

瀏覽器把網頁畫成畫面之前，先建一棵 DOM 樹；為了讓視障者的螢幕閱讀器能用，它再從 DOM 整理出一棵只留「有意義的元素」的樹，叫 accessibility tree：每個節點有角色（button、link、textbox）、名稱（按鈕上的字）和狀態（勾選、展開）。裝飾用的 div、純排版的元素不在樹上。

WebArena 把這棵樹轉成文字給 agent，每個節點加一個編號，agent 用編號指定要點哪裡。好處是 token 少、不用看圖；代價是靠 canvas 畫的、沒有語意標記的頁面，樹上看不到。OSWorld 改用截圖，就是為了這些樹上看不到的東西。

查閱OSWorld：能不能操作一台真的電腦

OSWorld（Xie 等人，NeurIPS 2024）把動作空間再放大：agent 看到的是整個桌面的截圖，動作是滑鼠和鍵盤，369 題跨瀏覽器、辦公軟體、檔案與系統設定。例子：在試算表加一個計算欄、排序、存成 result.xlsx。每一步都是座標和按鍵。

評分分四步。環境先跑這題的設定腳本，把桌面準備成初始狀態（開好檔案、設好 app），這些步驟不是 agent 做的，不算分。Agent 做事時記錄 trajectory。結束後取最終狀態，交給這題專屬的 evaluator（OSWorld 對 grader 的叫法）算 reward，也就是這一題的分數；檢查的對象是檔案的儲存格與公式、app 的設定、系統的狀態。

OSWorld 2.0（2026）改成 108 個長流程，跨 31 個自架網站與專業軟體，每題 300 步以上，平均 27 個 checkpoint 給部分分數，因為原版已接近飽和。

Epoch 2025 年的分析提醒，原版量到的不全是「操作電腦」：約 15% 的題只要 terminal，再 30% 可以用 terminal 和 Python 代替大部分 GUI 操作，約 10% 的題有嚴重錯誤。

查閱SWE-bench 一家：能不能修好真實 repo 的 issue

SWE-bench（Jimenez 等人，2024）的題目來自 GitHub 上真的 issue：給 agent 一個 repo 和 issue 描述，要它交出一份 patch。例子：某個函式碰到空的索引會丟例外，改成回傳空結果，而且既有的行為不能壞。

Grader 只做一件事：套用 patch、跑測試。SWE-bench 有五個變體，各版的現況（飽和、壞題）在第 7 章：

  • Verified。OpenAI 人工篩出的 500 題。
  • Lite。300 題的子集。
  • Multilingual。300 題，涵蓋 9 種程式語言：C、C++、Go、Java、JavaScript、TypeScript、PHP、Ruby、Rust。
  • Multimodal。Issue 附圖片。
  • Pro。更難、要改多個檔案。
查閱τ-bench：和使用者對話、守政策、改後端

τ-bench（Yao 等人，2024）加了一個會說話的對手：一個 LLM 扮演客戶，agent 要和它對話，同時守一份航空公司的政策，並透過 API 改一個真的資料庫。政策的例子是「basic economy 的機票不能改」。

一題的典型流程：客戶說「我要把明天的航班改成晚班」，agent 先驗證身分、查訂位、搜航班、說明票價差、取得確認，再叫 change_booking，訂位更新。評分看最終的資料庫狀態，加上回覆內容：r = r_action × r_output。讀取的 call 怎麼叫都可以，多寫了一筆就是 0。

後續的 τ³-bench（Sierra，2026-03）修正了原本的題目，加上銀行領域的知識檢索（698 份文件）和語音。

查閱Terminal-Bench：透過 shell 做完一件事

Terminal-Bench（Merrill 等人，2.0 版 2026）的題目不限於修 bug：程式、系統管理與伺服器設定、資料處理、訓練模型、資安、科學計算流程，都是從頭到尾做完一件事。代表題目：在線上的 KV service 部署新協定，過程中不能掉連線、延遲要維持。

它卡在 SWE-bench 與 OSWorld 中間：比 SWE-bench 範圍大，因為還要裝東西、設服務；比 OSWorld 單純，因為所有動作都是文字指令，不用預測滑鼠座標。

查閱早期的指標：perplexity、accuracy、F1、win rate
  • Perplexity。量預測文字：對一段沒看過的文字，把每個字的負對數機率平均再取指數，數字越小表示 model 越不「驚訝」。
  • Accuracy。答對的比例。
  • F1。用在答案是一組東西時（例如抽出的關鍵字），同時看抓到的比例與抓錯的比例。
  • Preference 或 win rate。把兩個回答放在一起，問人或 judge model 偏好哪一個，Arena 的排行榜就是這樣算的。

這幾種指標有一個共同點：一題只跑一次。那時的題目是一問一答，model 只輸出一個答案或一段短文字，能變的地方少，大家假設跑第二次結果差不多，就不值得多跑。Agent 一題要走幾十步，每一步的選擇都會把後面帶到不同的路上，同一題重跑的結果常常不同，這個假設就打破了。

    壓縮後的重點

    1. 簡單 baseline 追得上複雜 agent，成本差 50 倍以上。HumanEval 164 題、每個 agent 跑 5 次。Warming（GPT-4）93.2%、總成本 2.45 美元；LATS（GPT-4）88.0%、134.50 美元；GPT-4 zero-shot 89.6%、1.93 美元。Warming 與最強架構的準確率沒有顯著差異。
    2. 成本與準確率可以一起最佳化。在 HotPotQA 用 DSPy 加 Optuna 搜尋 prompt 與 model 組合。GPT-3.5 的變動成本降 53%，Llama-3-70B 降 41%，準確率持平。搜尋本身的一次性成本約 1,300 次推論後回本。
    3. Model 開發者和 downstream 開發者要的 benchmark 不同。前者該用參數量或算力當代理指標，後者要真實美元成本。NovelQA 一次問完整本小說的所有問題，和使用者逐題問的情境不同，把 RAG 的相對成本高估約 10 倍。
    4. 小 benchmark 容易走捷徑。作者分四個通用性層級：distribution-specific、task-specific、domain-general、general-purpose。17 個 benchmark 裡 7 個沒有 held-out 集，也沒有計畫加。WebArena 上 35.8% 的 STeP 把 Reddit 的 user URL 寫死在 policy 裡，網站一改版就失效。

    2. 12 個指標都是 0 到 1 的分數。Consistency 4 個：結果、動作類型的分布、動作順序、資源用量。Robustness 3 個：注入 tool 錯誤、改 tool 介面、改寫 prompt，各算擾動後正確率除以原正確率。Predictability 3 個：calibration、AUROC、Brier score。Safety 2 個：無違規比例、違規嚴重度。
    3. 實驗規模。14 個 model 來自 OpenAI、Google、Anthropic。GAIA 165 題；τ-bench 用 airline 的 26 題乾淨子集，原本 50 題裡 24 題有錯。每題跑 5 次，temperature 0。

    5. 進步的是 calibration 與 safety，沒進步的是 consistency。Outcome consistency 在所有 model 都低。動作類型的分布穩定，動作順序不穩定。Fault 與 environment robustness 接近滿分，prompt robustness 差異最大。同一家族裡，小 model 的 consistency 有時比大 model 高。
    6. 三個真實事故各對應兩個指標。Replit 的 agent 刪掉 production 資料庫：harm severity 與 prompt robustness。Operator 未經授權花了 31.43 美元：compliance 與 trajectory consistency。NYC 聊天機器人給錯法律建議：calibration 與 consistency。
    7. Automation 的門檻比 augmentation 高。有人審核的輔助工具可以接受中等可靠性；agent 自己動手的自動化，可靠性是前提。Pilot 轉 production 前，先設 consistency 與 safety 的最低門檻。

  3. 必讀τ-bench: Tool-Agent-User Interaction in Real-World DomainsarXiv 2406.12045 · 論文 · 2024 · 挑段約 20 分

    評分看最終資料庫狀態與政策遵循。pass^k 把「每次都要對」量出來。

    導讀聚焦 pass@k 與 pass^k 的差別。問：客服型任務該報哪一個？

    摘要讀約 3 分；原文約 20 分

    一句話：τ-bench 用模擬客戶、真實 API 與一份政策文件測客服 agent，評分看最終資料庫狀態。它提出 pass^k 量「每次都要對」：gpt-4o 在 retail 單次成功 61.2%，連續 8 次都成功低於 25%。

    跟這堂課的關係

    Slides p.10–11 的 pass^k 定義與 p.12–23 裡的 τ-bench 介紹都來自這篇 §3。核心觀念〈指標〉與註〈pass@k 與 pass^k 的估計式〉（p.11）用的公式就是這篇的。第 8 章的 grader 相乘也來自這篇；〈目錄〉的表裡，τ-bench 是唯一同時檢查狀態與回覆內容的。註裡的 pass^4 例子是這篇 Figure 4 的簡化版。

    壓縮後的重點

    1. 環境有三樣東西：資料庫、API、政策。Retail 有 500 個使用者、50 項商品、1,000 筆訂單，7 個寫入 API、8 個讀取 API，115 題。Airline 有 500 個使用者、300 班航班、2,000 筆訂位，6 個寫入 API、7 個讀取 API，50 題。政策是一份 markdown，例如每筆已送達的訂單只能退換一次。
    2. 客戶由 LLM 模擬，agent 看不到他的指令。模擬客戶用 gpt-4-0613、temperature 1.0；agent 用 temperature 0。每題的客戶指令寫到只有一種正確的資料庫結果。客戶看得到對話，看不到 agent 的 tool call。
    3. Reward 是兩個 0/1 相乘。r_action：最終資料庫完全等於唯一的標準狀態。r_output：agent 的回覆含必要字串，例如價格。作者說這是必要條件，不是充分條件：agent 沒問客戶確認就退款，資料庫一樣對。
    4. pass^k 的定義。一題跑 n 次、成功 c 次，pass^k = C（c，k） / C（n，k），再對所有題目平均。pass@k = 1 − C（n−c，k） / C（n，k）。k = 1 時兩者相同，就是平均成功率。
    5. 最好的 model 也不到一半，而且不穩定。Function calling 下，gpt-4o 在 retail 61.2%、airline 35.2%；claude-3-opus 44.2% 與 34.7%；gpt-3.5-turbo 20.0% 與 10.8%。Retail 的 pass^k 隨 k 快速下降，gpt-4o 的 pass^8 低於 25%。Function calling 優於 ReAct，ReAct 優於 Act。
    6. 失敗原因有三類。抽 115 條 gpt-4o retail 軌跡，40 條失敗，其中 4 條是客戶指令寫壞。剩下的失敗：參數錯或資訊錯約 55%、決策錯（沒照政策）約 25%、複合請求只做一半約 19%。拿掉政策文件後，retail 從 61.2% 降到 56.8%，airline 從 33.2% 降到 10.8%。

    原文怎麼讀

    • 可以跳過：§2 Related Work；§4.1 兩個 domain 的建構過程；§5.1 Table 2 的全部 model，看 gpt-4o 與 claude-3-opus 兩列就夠；Appendix B。
    • 值得看原文：§3 的 reward 與 pass^k 定義（半頁）；Figure 4 的 pass^k 與 pass@k 曲線，兩條線的張開程度就是不穩定的量；Appendix C.2 的完整對話軌跡，看一次 agent 怎麼在政策與客戶之間失敗。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「pass^8 低於 25%，代表 gpt-4o 只做對四分之一的題目。」不對。它的平均成功率是 61.2%。pass^8 是「同一題連續 8 次都對」的比例，低於 25% 說的是穩定性，不是能力。兩個數字的差距就是 slides p.11 要你看的那一塊。

  2. 推薦Dapper: A Large-Scale Distributed Systems Tracing InfrastructureGoogle · 系統論文 · 2010 · 挑段約 20 分

    分散式 tracing 的奠基之作。把 agent 的步驟與 tool call 當 span，整套方法直接搬用。

    導讀適合系統背景的人導讀。重點：sampling rate 是主要的成本控制。

    摘要讀約 3 分；原文約 20 分

    一句話：Dapper 是 Google 的分散式 tracing 系統：把一個請求經過的所有 RPC 記成一棵 span 樹，只在幾個共用 library 裡埋點，靠抽樣把 overhead 壓到看不見。它是 OpenTelemetry 這類工具的原型。

    跟這堂課的關係

    這篇不談 agent，放在這一講的原因是 trajectory。Slides p.11 說 evaluator 看最終答案、環境狀態、trajectory；p.31 說只看結果會放過不安全的執行。要看 trajectory，就要先把每一步記下來，Dapper 的 span 樹就是記法。核心觀念〈指標〉要的成本與 latency（p.10），每個 span 都帶時間戳，可以逐步加總。第 2 章說公開分數回答不了「能不能上線」，第 9 章說線上要用真實流量評估；Dapper 就是從真實流量取樣的機制。

    壓縮後的重點

    1. 一個 trace 是一棵樹，節點是 span。每個 span 有名稱、span id、parent id，共用一個 64-bit 的 trace id。換成 agent：一次 session 是 trace，每次 LLM 呼叫與 tool call 是 span。
    2. 只在三個地方埋點，應用程式不用改。Thread：trace context 放在 thread-local storage。Control flow：callback 建立時存下 context，執行時還原。RPC：所有 RPC 自動包成 span。Google 的程式都走這幾個 library，覆蓋率接近全部。
    3. Annotation 讓應用程式加自己的資料。帶時間戳的文字或 key-value，每個 span 有容量上限。70% 的 span、90% 的 trace 至少有一個 annotation。換成 agent：prompt、tool 參數、token 數都是 annotation。
    4. Overhead 的數字。建一個 root span 204 ns，非 root 176 ns，沒抽中時加 annotation 約 9 ns。收集 daemon 最多用一個 core 的 0.3%；trace 流量低於 production 網路的 0.01%。全抽（1/1）時 latency 增加 16.3%、throughput 降 1.48%；1/16 時 latency 增 2.12%，已在實驗誤差 2.5% 內。
    5. 抽樣是主要的成本控制。第一版 production 統一抽 1/1024；高流量服務低到 0.01%；每秒幾十個請求的服務可以全記。後來改成 adaptive sampling，目標是每單位時間固定的 trace 數。收集端再抽一次：依 trace id 的 hash 決定整棵樹留或丟。
    6. 收集是 out-of-band。Span 先寫本機 log，daemon 拉走，collector 寫進 Bigtable，一列一個 trace、一欄一個 span。中位延遲 15 秒以內。抽樣後每天仍超過 1 TB，要留至少 2 週。
    7. 用途超出原本的設計。約 200 位工程師每個工作天用 UI。Ads Review 團隊靠它把 latency 改善兩個數量級。

    原文怎麼讀

    • 可以跳過：§2.6 安全與隱私；§3 部署狀況；§5.1 DAPI；§8 Related Work。
    • 值得看原文：§2.1 的三張圖（五個 server 的請求、它的 span 樹、一個 span 的內容）；§4.3 的 Table 2（6 種抽樣率對 latency 與 throughput 的影響）；§6.2 long tail latency 的案例。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「Dapper 抽 1/1024，所以 agent 的 trace 也該抽樣。」不對。1/1024 是給每秒數萬個請求的服務用的；論文說每秒幾十個請求的服務可以全部記錄。Agent 的請求少、每次又貴，評估又要逐筆看 trajectory，所以全記。要省的是儲存，用整棵保留或丟棄的二次抽樣。
