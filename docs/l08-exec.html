Execution 服務：誰替 agent 真正動手

L8 第 9 章的圖裡，microkernel 的 core 外面有三個服務：memory、tool、execution。前兩個還算好懂，execution 最抽象。這頁從最淺的一句話開始，一層一層往下：先看它在 loop 的哪一步，再按按鈕讓同一段程式在三種架構裡跑一次、故意讓它出事，最後看拆出去之後多出來的問題。每一層都可以動手玩，讀完大約 15 分鐘。

0一句話

Model 只會產生文字。文字要變成「真的跑了一段程式、真的改了一個檔案」，必須有一個程式替它執行。Execution 服務就是把這件事從 agent 的 process 拿出去，交給另一台機器上的一個隔離環境（sandbox）去做；agent 這邊只送出「請跑這段程式」，收回「跑完的結果」。

1它在 loop 的哪一步

L2 第 1 章的 agent loop 只有四步：harness 呼叫 model，model 回一段文字提議下一步，harness 照著做，把結果接回 context 再呼叫一次。Model 從頭到尾沒有碰過你的機器；「照著做」那一步才是真的動手。下面這張圖點每一步看看，execution 管的是第 ③ 步。

在最簡單的 agent 裡，第 ③ 步就是 harness 自己呼叫 subprocess.run() 或 exec()，在同一台機器、同一個 process 裡跑。問題是：這段程式是 model 剛剛寫的，沒有人審過。第 ③ 步要放在哪裡、隔多遠，就是這整頁在談的事。

2和 tool 服務差在哪

Tool 和 execution 都是「model 提議、程式執行」，差別在 model 給的是什麼。Tool 是事先寫好的函式，model 只填參數，行為和副作用在寫 tool 的時候就定了；execution 收的是 model 臨時寫的程式碼或 shell 指令，它能做什麼，要跑了才知道。所以 tool 的風險在寫 tool 時就能審，execution 的風險只能靠執行環境去擋，這也是 L4 第 7 章說「shell 最強，保護全在 harness」的原因。

下面六個 model 的提議，各是哪一種？點一下就會告訴你對不對。

3同一段程式，三條路

使用者說「幫我看一下這份 sales.csv 的統計」，model 寫了一段 Python。選一種架構，按「下一步」，看這段程式經過哪些元件、跨過哪一種邊界。深紅虛線是網路，也就是 L8 那張圖要你看的那條線。

架構

三條路跑出來的結果一模一樣，都是那張統計表。差別不在功能，而在出事的時候，誰會跟著倒。下一層就來試。

4故意讓它出事

Model 寫的程式不一定是好的：可能寫錯，也可能被 prompt injection（L2 第 5 章）帶著寫出壞東西。選一種狀況，三種架構並排看後果。Modular 那一欄假設 provider 是同一台機器上的 Docker container。

看完五種狀況會發現一個規律：monolithic 的問題是「壞掉的範圍太大」，modular 的答案是「看你怎麼設定」，microkernel 把前四種都關進一個用完就丟的盒子，但換來第五種：以前不存在的網路故障。拆出去不是免費的，第 6 層講這筆帳。

5Sandbox 的一生

Execution 服務不只是「跑一次程式」。資料分析通常要好幾步：先裝套件、再讀檔、再畫圖，後一步要看得到前一步留下的東西。所以服務會給你一個 sandbox_id，同一個 id 的呼叫都進同一個 sandbox，檔案和套件會留著。可是 sandbox 佔著機器，閒置太久服務就會回收。

你是 core。照順序按按鈕，看右邊的請求和回應；也試試在中途按「閒置 15 分鐘」。


      

      

    

    
被回收之後，舊的 id 會回 sandbox_not_found，套件和檔案都不見了。這時要不要重建、要重跑哪幾步，是 core 的決定，execution 服務不知道你的任務做到哪。所以「狀態放在哪裡」要先想好：只放在 sandbox 裡的東西，都要當作隨時會消失；要留下來的結果，寫到 sandbox 外面（物件儲存、session log）。這和 L8 第 9 章 Managed Agents 的設計是同一個道理：sandbox 掛了只回報成一個 tool error，由 model 決定要不要重試，重試時才配一個新的。

  


  
  

    
6拆出去的代價：送出去之後，不知道有沒有跑

    
在同一個 process 裡，函式要嘛回傳、要嘛丟 exception，你一定知道結果。跨過網路就不是了：請求送出去，等不到回應，可能是請求沒到、程式還在跑，也可能是程式跑完了、只是回應在路上丟了。從 core 這邊看，這三種情況長得一模一樣，都是 timeout。這就是 L5 講的 partial failure。

    
下面這段程式會在 orders.csv 加一筆訂單。回應在網路上丟了，core 照常重送。先關著 idempotency key 跑一次，再打開跑一次。

    

      
with open("/data/orders.csv", "a") as f:
    f.write("A1024, 3 台 GPU, NT$ 1,200,000\n")

沒有 key，同一筆訂單寫了兩次。有 key，execution 服務記得「這個 request_id 我跑過了」，直接回上次的結果，不再跑一次。L4 第 6 章說 tool 預設要做成 idempotent，在 execution 這裡更麻煩：程式是 model 寫的，你沒辦法保證它本身 idempotent，只能在協定這一層補。

    
這只是多出來的代價之一。把三種架構放在一起，帳是這樣算的：

    

      
同一個 process 執行Execution 服務

      
        
壞程式的影響範圍整個 agent，甚至整台機器一個用完就丟的 sandbox

        
Credential和程式在同一個環境，讀得到不放進 sandbox，需要時由外面的 proxy 代打

        
呼叫失敗時一定知道成功或失敗可能「不知道」：要 timeout、重試、idempotency key

        
狀態跟著 process，process 在就在跟著 sandbox，回收就沒了，要另外存

        
除錯一份 loglog 分在 core 和服務兩邊，要靠 trace id 串起來

        
多個 agent 共用各自在自己機器上跑共用一個 sandbox 池，按需配置

      
    

    
你熟悉的系統裡其實早就有這個形狀。Kubernetes 的 control plane 從不自己跑容器：它把 Pod spec 交給 node 上的 kubelet，kubelet 把容器跑起來，再回報 status；容器 OOM 了，kubelet 回報，control plane 決定要不要重開。對應過來，core 是 control plane，execution 服務是 kubelet，sandbox 是 Pod。作業系統的 microkernel 也是一樣：kernel 只做排程和訊息傳遞，driver 在 kernel 外面跑，driver 當掉，kernel 不會一起倒。

    
要不要拆，回到 L8 第 9 章最後那三個問題，套在 execution 上就是：model 寫的程式要和秘密隔開嗎？（幾乎一定要，除非是你自己筆電上的單人工具）sandbox 裡的狀態要活得比一次呼叫久嗎？（多步驟的資料分析要）很多 agent 要共用同一批執行機器嗎？（平台要）。市面上的 E2B、Modal、Daytona 這類 sandbox 服務，賣的就是這一層。
