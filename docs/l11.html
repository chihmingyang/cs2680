先看這裡

課程拿 58 位學生三份作業的 Claude Code 紀錄來看：用量漲了 4.5 到 7.2 倍，學生自己抓到的 agent 錯誤卻從六成掉到三成，平均每人踩到的陷阱從 1.3 個變成 5.0 個。十個陷阱裡最貴的，是最上游的那一個：沒先定義做完，又相信了沒檢查過的說法。其餘的依代價排：比較版本時的紀律、拿不回來的兩件事、每天的 session 與環境習慣。

  • 開工前寫做完，收工時看證據。終點、不變量、證據三樣寫進 prompt；agent 說「好了」，要看不經 pipe 的完整輸出、exit code 和 diff。
  • 一次改一件事，每版跑不只一次。同一份程式碼的分數會在 16 到 18 題之間跳，所以要比分布，不比一個分數。量的時候還有你控制不到的東西會變：你的程式呼叫的 model、跑評分的機器；如果你是讓 Claude Code 去跑同一組任務、比兩種做法，Claude Code 自己也在被比的東西裡，它可以不發新版就改變行為。所以baseline 要和新版同一段時間交錯跑。
  • 拿不回來的事，設定一次就擋。危險的一步之前先 commit，deny 規則擋住常見的寫法；key 不貼進 prompt，也不放進 agent 的環境，因為進過 context 的都留在 transcript 裡。

1根本的事實：agent 做得越多，人抓到的錯越少

這門課要每份作業都附上 Claude Code 的 session 封存，也就是 transcript：agent 每一則訊息、每一次 tool call 和它的結果，全部存成檔案。Tool call 是 agent 每一次動手：讀一個檔、改一段程式、跑一個指令，都是呼叫一個 tool。所以課程手上有同一批 58 位學生、三份作業的真實紀錄。三份作業一份比一份難。第一份用 Claude Code 做一個網頁，即時顯示 agent 在做什麼。第二份自己寫一個 agent loop：model 提議下一步，程式去執行，再把結果送回 model，一圈一圈轉到做完。第三份在成功率不變的前提下，壓低這個 agent 的成本和延遲。先看用量怎麼變：

使用的方式也變了。開過 subagent（主 agent 派出去、有自己 context 的子 agent）的學生從 36% 變成 74%。跑過 workflow（Claude 寫好、交給 runtime 在背景跑的腳本，L3〈Team 與 workflow〉）的從 2.9% 變成 35%。Agent 連續工作 30 分鐘以上才回來的長 turn，從全班 41 次變成 514 次。人交代的東西卻變少了：prompt 長度的中位數從 98 個字元縮到 65 個，寫明「怎樣算做完」的 prompt 從 39% 掉到 15%。也就是說，agent 做得越多，人交代得越少。

誰發現錯誤也跟著變了。課程把整理出的 agent 失敗紀錄，依「誰抓到的」分類，只算寫明了是誰抓到的那些：

學生自己抓到的比例從 61% 掉到 33%，評分的 run 抓到的從 4.5% 升到 22%（後者依本文的讀法，見圖說）。到了第三份作業，越來越多錯要等分數回來才知道。課程的總表也指向同一個方向：平均每位學生踩到的陷阱，從 1.3 個變成 3.4 個，再變成 5.0 個（同一班、三份作業的觀察，不是對照實驗；作業變難本身也會讓錯變多）。方向和業界的調查一致（第 3 章）。

花的時間不等於成績。課程把排行榜的名次分別對 Claude Code 的工作時數、學生自己花的時數畫成散佈圖。時數多，名次不一定高；第 1 名落在最省時間的那條邊界上，學生自己花的時間不到 1 小時。課程從這些資料得出兩句話：學生需要一個讓 agent 驗證自己工作的方法；人要掌握方向，決定 agent 做什麼。這也是 L1〈人的時間〉的結論：稀缺的是人的時間和注意力，不是 agent 的工作時數。

本文的判斷：照代價排，不照編號排。Slides 把十個陷阱編成 P1 到 P10。本文要先回答哪一種錯最貴，所以第 2 到 9 章依兩個問題排。先看忽略它要付多少，也就是多常碰到、碰到一次損失多大；這一項差不多時，再看付了能不能拿回來，拿不回來的排前面。排出來是這樣：

  • 每個任務都會碰到的驗證排最前面（第 2、3 章）。
  • 比較版本時才會碰到、一錯就白做好幾天的實驗紀律其次（第 4、5 章）。
  • 破壞性指令和 secret 拿不回來，但比較少碰到、設定一次就擋得住（第 6、7 章），所以排在每天都要做的 session 習慣（第 8、9 章）前面。

第 10 章是查閱，編號和每一項的數字收在那裡的表。

2開工前：把「做完」寫成檢查得了的條件

第 1 章最上游的一個數字是：寫明「怎樣算做完」的 prompt，從 39% 掉到 15%。沒有寫，agent 就自己決定什麼叫做完，而它會選最容易達成的那一種。課程舉了兩個例子：

兩個例子裡，agent 都照字面完成了要求。這叫 Goodhart's law：指標一旦變成目標，就不再是好指標。L3〈終點〉講 /goal 時碰過同一個陷阱：/goal 讓 Claude 一直做到你給的條件成立，條件若只寫「所有測試通過」，刪掉失敗的測試也算成立。第一份作業的回顧是同一個問題的另一面：沒寫清楚做完長什麼樣子，agent 不是做少，就是做多。需求寫得寬，agent 就多做了不需要的功能、過度的架構、錯的版面；給了截圖、明確的尺寸和量得出來的條件，結果就好得多。模糊的要求還讓 agent 跑得更久：第三份作業裡，30 分鐘以上的長 turn 有 69% 來自模糊的要求，第 8 章講怎麼把它切小。

一個檢查得了的「做完」有三部分。課程的建議是把需求寫成可以驗證的條件，配上畫面的例子。拆開來是：

  • 終點。一個能由輸出證明的條件：哪些測試要跑、exit code 是多少、截圖和設計稿對得上、數字要到多少。做不到時什麼時候停，也寫在這裡，例如同一個方法試了三次還不行，就停下來回報卡在哪裡。
  • 不變量。做完時不准動的東西：不准修改或刪除 tests/ 的測試；成本降了，解出的題數也不能比 baseline 少。上圖兩個例子缺的就是這一行。
  • 證據。要它交出什麼：跑了哪個指令、完整的輸出、exit code、截圖。第 3 章講怎麼看這些證據。

另外兩個習慣也來自課程的回顧：讓 agent 先把有歧義的地方問出來，不要自己猜；改動大的時候，先看它的設計再讓它動手。Claude Code 的 plan mode（按 Shift+Tab 切換，只讀不改）就是做後者的；官方文件的建議是，一句話講得完的 diff 就跳過 plan（best practices，2026-11）。照這三部分，再加上「歧義先問」一行，一個任務長這樣：

寫不出終點，就先別放手。有些任務一開始寫不出檢查，例如「把程式整理乾淨」。這時先讓 agent 提幾個方案，你挑一個，再把挑中的方案寫成檢查，然後才讓它長時間自己跑。L3 的 /goal（由另一個 model 判斷條件成立了沒）和 L6〈驗證〉的 Stop hook（agent 要結束時自動跑的檢查），都要先有這一行條件才用得上；有了條件之後，怎麼讓它擋住 agent 提早停下，在那兩章。

3收工時：agent 說「好了」是主張，要看證據

定義了做完，還要確認它真的做完。課程把這一條排在十個陷阱的第一個：agent 說改動有效、測試過了、發現成立，學生就往下走，沒有檢查。很多說法是錯的：測試根本沒跑，或 pipe 吃掉了失敗。三份作業裡，信了錯誤說法的學生是 20%、20%、33%，要求 agent 拿出測試或證據的 prompt 只有 15%、27%、17%。

錯的說法多半不是說謊。官方文件說得很直接：Claude 會在工作「看起來完成」時停下；沒有它自己能跑的檢查，「看起來完成」就是唯一的訊號，你就變成那個驗證迴圈。L6〈檢查要真的抓得到〉引用的研究裡，26% 的失敗 run 宣稱自己成功。所以第一份作業回顧的結論是：要改的不是叫 agent 寫程式的方式，是事先講好它的工作怎麼驗證、怎樣才能信。收工時要過四關：

4實驗：一次改一件事，每版跑不只一次

第三份作業要優化：同一組任務，花更少的錢和時間。這時出現兩種新的錯：把好幾個改動疊在一起，以及只憑一次 run 下結論。第一份作業是做網頁，不必比較版本，兩項都是 0%。第二份作業開始要比較，slides 後段的總表寫著 47% 的學生疊了改動、48% 只憑一次 run 下結論。到了第三份，升到 78% 的學生疊了改動，66% 只憑一次有雜訊的 run 下結論。Slides 分別介紹這兩個陷阱的那兩頁，另外給了一組標籤不同、數字也不同的比例，沒有說明和總表的差別；本文用總表，兩組都列在第 10 章的查閱。

疊改動的例子是：四個新功能一起疊進 v9（slides 叫它們 Expert 功能，沒有說明內容），成本上升，解題數沒動，四個裡哪個有用、哪個有害，已經分不出來。只跑一次的例子是：同一份程式碼，分數落在 16 到 18 題之間，所以單一次提交的分數很難解讀。

課程還拿第四份作業的排行榜量了雜訊。第四份作業講課時還沒截止，所以本文其他的數字都只來自前三份。這份作業把外部的 model API 拿掉，要學生在一張 GPU 上自己 serve model，再讓第三份作業的 agent 去用它；排行榜看解題數和端到端時間。課程把排行榜前 18 份提交（12 位學生）各重跑 10 次，共 180 次評分。同一份提交的 10 次會聚成一團；團的大小依 harness 而定，也就是學生交出去、包在 model 外面的那層程式：prompt、tool、loop 與重試（L2〈Loop〉）。但雜訊蓋不掉好的 harness。下面的示意圖（數字是本文編的）畫的是這件事的單一版本：一次 run 會騙人，真的變好時整團會往右移。

雜訊從哪裡來、要跑幾次、怎麼比，是 L7〈雜訊〉的主題：每一次 run 的路徑都不同，題目也只是抽樣，所以比兩版要比分布，最好逐題配對。L8〈淨節省〉也提醒，省下的錢只能在同一組任務上量。這一章只講習慣。

課程的 iteration loop。課程把習慣收成一個迴圈，一圈只回答一個問題：

第一步要一個簡單的 baseline。Slides 特別寫了不要一開始就從大型的現成 harness 改起（點名 pi 和 dsh），因為起點太複雜，之後每個改動的效果都看不清楚。第五步和第六步，就是擋住只跑一次和疊改動的兩道關。

對到 git 和一張結果表。課程的修法，每一條都有具體的做法：

  • 每個實驗一個 branch 或 worktree。Worktree 是同一個 repo 的另一個工作目錄（L3）。都從同一個 baseline 開出來；交出去的版本打 tag。
  • 動手之前寫下假設。寫進結果表：改什麼、預期哪個數字變多少。
  • 門檻在跑之前定。「差多少才算數」跑完才定，門檻就會跟著結果走。
  • 每版跑不只一次。同一組任務、同樣的設定，比的是分布，不是一個分數。
  • 沒有幫助的先丟掉。再加下一個想法，不要留在版本裡一起疊。

結果表每一列記：你的 agent 的版本（v8、v9）、跑之前寫的假設、commit、它呼叫的 model 的版本、每次 run 的分數與花費。Commit 固定得住你的程式，卻固定不住它呼叫的 model，因為 model 不在你的 repo 裡；不記下 model 的版本，baseline 就不是固定的。下一章看另一個不在你 repo 裡、而且會自己變的東西：你用來寫程式的 Claude Code。

5Claude Code：它也會在你腳下變

第 4 章比的是學生自己寫的 agent。這一章換一個對象：學生用來寫程式的 Claude Code。課程在第一份作業的 trace 裡發現，agent 常常用 Bash 的 cat、sed 讀檔改檔，不用 Claude Code 專用的檔案 tool：Read 讀檔，Edit 和 Write 改檔、寫檔。課程去看了作業期間 Claude Code 的 system prompt 和 feature flag（伺服器端可以開關的設定），slides 的結論是：這是 Anthropic 刻意做的實驗，作業剛好跑在實驗期間。那份作業要做的網頁，得從 trace 看出 agent 讀了、改了哪些檔，slides 說這個實驗讓作業碰上了壞時機。課程的分析有四點：

  • 一段提醒。在 auto（另一個 model 在背景審查每個動作）和 bypass（幾乎不再跳出權限提示）這兩種權限模式的 session，system prompt 加了一段提醒，要 agent 透過 Bash 做事，不用專用的 Read、Edit、Write。
  • Tool 的說明也改了。Bash tool 的說明拿掉了「不要用它做 cat、head、tail、sed、awk、echo」的警告；幾乎每個 session 都沒有 Grep 和 Glob，agent 試著用時，會收到改用 Bash 的 grep 的提示。
  • 幾乎全班都在實驗組。由一個 feature flag 控制，除了一位學生都在組內，只套用在部分 model，不含 Sonnet 和 Haiku。Flag 在 8 月 12 日加入，作業在 9 月 2 日到 22 日；一位學生自己找到並測試了它。
  • 效果明顯，而且不必發新版就能改。課程的圖顯示，加了提醒之後 Bash 的使用明顯增加；flag 快取在 ~/.claude.json，Anthropic 不必發新版就能改。

  1. 這個 session 在不在 Bash 優先的組。每個 session 判斷一次，subagent 跟著主 session。Opus 5.5 和 Fable 5.1 一律在組內；Opus 5 要看 flag；Sonnet 5 和 Haiku 不在。

公開的紀錄（本文補的）。上面是課程的分析。公開的資料裡，Claude Code 的 GitHub issue #87575 和 #87971 有使用者貼出同一段提醒的原文，也提到同一個 flag 名稱；到 2026-11-06 為止，兩串都沒有 Anthropic 的回覆，官方的 permission modes 文件也沒有提到 auto mode 會改變用哪個 tool。本文不推測原因，只看它對使用者的兩個後果。

後果一：經過 Claude Code 量的數字，會混進它自己的變化。先分清楚 Claude Code 的變化影響哪些數字。排行榜評分跑的是學生自己寫的 agent，它自己呼叫 model 的 API，不經過 Claude Code，所以這個 flag 不會直接改動 v8、v9 的分數。它改的是 Claude Code 替你寫程式的做法，寫出來的程式都在 commit 裡。

直接受影響的，是經過 Claude Code 量出來的數字。例如你想知道兩版 CLAUDE.md（專案根目錄的規則檔，Claude Code 每次開工都會讀）哪一版讓它少出錯，就要讓它照兩版各跑同一組任務。這種比較通常用 claude -p 跑：-p 是非互動模式，給它一個 prompt，它做完就印出結果、結束。這時包在 model 外面的那層程式就是 Claude Code。L7〈分數是整個 stack 的函數〉看過，同一個 model 換一個 harness，分數可以差幾十分；Claude Code 改了 system prompt 或 tool 的說明，就等於換了一部分 harness。

所以這類比較要在結果表記下 Claude Code 的版本，實驗期間關掉自動更新；官方文件寫明 native 安裝會在背景更新、下次啟動生效。但 flag 不發版也會變，所以baseline 和新版要在同一段時間交錯跑，不要拿上週的分數來比：

你自己的 agent 也有不在 repo 裡的部分：它呼叫的 model，和跑評分的機器（L7〈基礎設施也是雜訊〉）。所以比 v8、v9 時是同一個習慣：結果表記下 model 的版本（第 4 章），兩版交錯跑。

後果二：綁在專用 tool 上的安全網，會安靜地失效。Claude Code 有三個安全網只看專用的檔案 tool：

  • Checkpoint。你每送出一個 prompt，Claude Code 就存一份檔案的快照，打 /rewind 可以退回去。
  • Hook。Claude Code 在特定時機自動跑的指令。Matcher 決定哪些 tool 會觸發它，例如 matcher 寫 Edit|Write，就只有這兩個 tool 會觸發（L2〈Hook〉）。
  • CLAUDE.md 與 rule。寫給 Claude 看的規則檔。子目錄裡的 CLAUDE.md，和寫了 paths 的 rule（.claude/rules/ 裡的檔案），要等 Claude 讀到那些路徑的檔案才載入；沒載入，Claude 就看不到那些規則（L2〈記憶〉）。

Agent 改走 Bash，三個都看不到：

第一列是官方文件寫明的：checkpoint 只追蹤檔案編輯 tool 的改動，Bash 指令改的檔案 /rewind 退不回來，而且它不能取代 git。後兩列是上面兩串 issue 裡使用者的回報：matcher 寫 Edit|Write 的 hook，不會因 Bash 的寫入觸發；用 cat 讀檔，子目錄的 CLAUDE.md 和有 paths 的 rule 就不會載入。所以真正的 checkpoint 是 git commit（下一章），一定要跑的檢查掛在 Stop hook 或 git 的 pre-commit，不掛在 Edit|Write。

本文的判斷：教訓不限於這一個 flag。Claude Code 不在你的 repo 裡，卻是你工作流程的一部分，而且會在你沒動手時改變。所以任何依賴 agent「用哪個 tool」的保護，都要假設它會換 tool；任何經過它量的 before/after 數字，都要附上兩邊的 Claude Code 版本。

6破壞性指令：先 commit，危險指令讓權限規則擋

前面的錯多半能重來：重跑一次、重寫 prompt。這一章和下一章的錯拿不回來。第二份作業裡，一個 agent 覆寫了 prompts.py，跑出那個結果的 prompt 就此消失，那個分數再也對不回產生它的設定。同時，學生放手的程度一路升高：用 bypass 權限模式送出的 prompt，從 8.6% 升到 11%、16%。Agent 想做、卻要有人或規則攔下的動作也變多了：學生自己、deny 規則（設定裡寫明「這類指令一律不准跑」的規則）或 auto mode 擋下的 tool call，全班從 167 次升到 233 次、484 次。

7Secrets：進過 context 的，都留在 transcript 裡

第二份作業有 23% 的學生曝露過 key 或登入憑證，第三份有 19%（第一份是 3%）。課程的例子是一位學生把登入憑證打進 prompt，請 agent 在他離開時替他提交作業。課程依外洩的來源分成三類，每類各自計數（slides 沒有說同一件會不會同時算進兩類，所以三類的件數不能相加）。本文把三類排成一條路，說明 key 怎麼走到第三類的地方：

Log 為什麼會帶著 key。Claude Code 把每一則訊息、每一次 tool call 和它的結果，寫進 ~/.claude/projects/<專案>/<session>.jsonl。官方文件寫明這些檔案是純文字、沒有加密，tool 讀了 .env 或指令印出認證，值就寫進這個檔案（.claude 目錄，2026-11）。你打的每一個 prompt 還另外存在 ~/.claude/history.jsonl，它不在自動清理的範圍內，留到你自己刪。這門課要每份作業把 session 封存 commit 進 repo，所以前兩類的 key 只要還在封存裡，也會跟著進 git（slides 的統計沒有說這種情況算在哪一類）。你的團隊如果會分享 transcript、拿它除錯或寫事後檢討，是同一個風險。

課程的修法，對到設定。四條修法，每一條都有一個具體的做法：

  • Key 放環境變數或 .env。程式從環境變數或 .env 讀 key，不寫死在程式碼裡；.env 寫進 .gitignore，也排除在 session 封存之外。
  • 永遠不要貼進 prompt。要 agent 寫用到 key 的程式時，只告訴它環境變數的名字，例如 API_KEY，不給值。
  • 不讓 key 進 agent 的環境。Agent 跑的指令會繼承開 claude 那個 shell 的環境變數，它跑一次 env 或 printenv，值就印進 transcript。所以那個 shell 不 export key，權限規則擋住讀 .env。正式環境的 key 也不放在開發用的 .env；agent 碰得到的地方，只放範圍小、可以隨時作廢的測試 key（本文的建議）。
  • Commit 或封存之前掃一次。課程的說明建議封存前先 grep 常見的 key 格式，並提醒那只是 smoke test；本頁的動手試試有一個掃描的腳本。

下面三個檔案照這幾條寫。第三個是 MCP 的設定：MCP 是把外部系統接成 agent 的 tool 的協定（L2〈MCP〉），例如接上 Notion，agent 就能讀寫你的頁面。每個外部系統由一個 server 程式提供，它通常要一個 token 才能存取你的資料。

.mcp.json 的寫法讓 token 不進檔案，也就不會跟著進 git；但 token 還是要放在開 claude 的 shell 裡，所以照上面〈不讓 key 進 agent 的環境〉那一條，只用範圍小、可以隨時作廢的那一種。Read 的 deny 規則擋得住 Claude 的檔案 tool，也擋得住 Bash 裡它認得的 cat、head、sed；擋不住自己開檔的 Python 腳本，要完全擋住得開 sandbox。已經寫進 transcript 的，可以把保存期限 cleanupPeriodDays（預設 30 天）調短，或用 claude project purge 刪掉一個專案的紀錄。Key 一旦外洩，確定有效的處理只有一個：作廢，重發。

業界的數字（本文補的）。GitGuardian 的 State of Secrets Sprawl 2026 分析公開的 GitHub commit：署名有 Claude Code 的 commit，3.2% 外洩了 secret，全體 commit 是 1.5%，約 2 倍（廠商的相關分析，不是對照實驗；報告沒有說明怎麼辨識有 Claude Code 參與的 commit）。報告自己提醒，這個 2 倍不能讀成工具的失敗：接受、修改、push 都是人做的決定。SC Media 的報導也提到，兩者每千個 commit 的外洩數在 2025 年 9 月以後開始接近。同一份報告也查了公開的 MCP 設定檔，找到 24,008 個不重複的 secret，其中 2,117 個仍然有效。原因之一是熱門的設定教學直接叫你把 key 寫進設定檔，上面的 .mcp.json 就是反過來的寫法。方向和課程一致：agent 讓 key 多了幾條出口，出口要在設定裡關。

8Session：一個 session 一件事，狀態寫在檔案裡

這一章的錯都拿得回來，代價是時間，而且每天都會碰到。課程的三個陷阱是：看不懂 agent 做了什麼、session 太長讓 compaction（context 快滿時，由 LLM 把舊對話寫成摘要）丟了 context、發洩情緒而不是修正方向。三個的解法都是同一個形狀：讓每一步小到看得完，讓該記住的東西留在檔案裡，讓給 agent 的每一句話都帶著資訊。

看不懂 agent 做了什麼。三份作業裡 18%、37%、21% 的學生失去了對程式的掌握。第 1 章看過，長 turn 從 41 次變成 514 次，第 2 章看過其中 69% 來自模糊的要求：agent 一次跑半小時，回來時改了一大片，人已經跟不上。課程的修法是讓每一步都小到看得完：

  • 一個 turn 一件事。一個功能或一個實驗，做完讀 diff，再 commit。
  • 要短的回報。讀得懂的幾句話，不是一長串 log。
  • 一份 agent 會更新的筆記。NOTES.md 或 CLAUDE.md，記計畫、決定、狀態、測試結果。
  • 中途看進度、修方向。按 Esc 停下，已經做的保留；或直接打字，訊息會排隊，等這一批 tool call 做完就送進同一個 turn（依 2026-11 的官方文件）。

Session 太長，compaction 丟了 context。做過 compaction 的學生從 16% 變成 69%，全班的 compaction 次數從 20 次變成 201 次。課程的例子：一個開了 13 天、壓縮過兩次的 session，學生得一再提醒 agent 之前的測試結果；另一位學生在 compaction 之後，五小時前貼進去的回饋就不見了。原因是 compaction 有損：摘要之後，只有 CLAUDE.md、memory 這類從硬碟重載的東西完整回來，只在對話裡說過的事，摘要沒留就沒了（L4〈compaction〉）。所以：

  • 一個任務一個新 session。不相干的工作不要接在同一段對話後面。
  • 狀態寫進檔案。計畫、決定、狀態寫在 CLAUDE.md，或從它匯入的 NOTES.md，不留在對話裡。
  • 大範圍的搜尋和長 log 交給 subagent。主對話只收摘要。
  • 在自然的斷點自己壓縮。跑 /compact，並寫明要留什麼。

卡住時：給證據，不要給情緒。發洩的學生從 7%、5% 升到 21%。課程的例子：第一份作業裡，一句要它清乾淨、把 bug 修好的命令之後，agent 做了 93 次 tool call、61 分鐘；第二份作業裡，一串情緒化的全大寫要求之後，agent 做了 5 次 tool call、18 分鐘。

Slides 只記了 agent 接著做了多少事，沒有記做得好不好。兩個例子的共同點，是學生說的話都沒給 agent 新的資訊：哪裡錯、錯誤訊息是什麼、你預期看到什麼。課程的修法就是把情緒換成這些資訊：

  • 第二次修不好，先要它診斷。請 agent 拿出證據：log 的哪一行、確切的錯誤訊息。
  • 貼確切的錯誤或截圖。並說你預期看到什麼。
  • 分數一直低，先問時間花在哪。失敗的 run 把時間花在哪裡，問完再要新點子。
  • 退回上一個好的狀態。用 /rewind 或 git，不要在壞掉的狀態上疊修補。

官方文件說得更直接：同一個問題糾正超過兩次，context 裡就塞滿失敗的嘗試，/clear 之後用更好的 prompt 重來，通常勝過在長 session 裡繼續改。

9執行環境：平行要隔離，長跑要撐得住

Worktree 只隔離檔案，port、資料庫、CPU 都還是共用的，這是 L3〈worktree 只隔離檔案〉的結論。Worktree 隔離的只是 repo 裡的檔案：寫到 repo 外面的結果與 cache，以及同一個 worktree 裡先後跑的 run，還是會互相覆寫。所以 port 和每個 run 的輸出目錄要在開工時分開，做法是下面的指令；資料庫和 CPU 分不開，只能排時間。

派工也有成本。平行還有另一種形式：在一個 session 裡派 subagent。它不會搶 port，但有自己的成本。第一份作業的回顧裡，一個六個 agent、委派三層深的 run，花了 10 分鐘以上、將近 15 美元；之前一個相近的任務不到 2 分鐘、1 美元。Subagent 幫得上忙的是互不相干的 review 和各自獨立的實作；幫倒忙的是好幾個 agent 重讀同一個小 repo、重做主 agent 已經做過的事，或一邊改檔、一邊有人測同一批檔案。所以每個 agent 要有清楚的責任和互不重疊的改動範圍，沒把握的點子先用小的委派試。規格怎麼寫、深度和寬度怎麼設上限，在 L5〈派工〉。

長跑要撐得住。第三份作業的例子是 42 GB 的 task image 塞滿了一台筆電的磁碟，整個基礎設施跟著失敗。課程的修法有三條：

  • 先讀寫明的需求。第一次跑之前，確認平台、磁碟、Docker 的要求。
  • 筆電不夠就換機器。用 CloudLab 或 AWS 這類雲端機器。
  • 長的工作放在不會睡著的機器上。用 tmux 或 nohup 跑，斷線也不會停。
