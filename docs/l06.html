先看這裡

這堂課分兩半。前半把 agent memory 拆成一條生命週期：觀察、編碼、儲存、檢索、反思、遺忘，每一站都是一個 policy 決策。後半解釋 agent 為什麼不可靠：錯誤會相乘，失敗有 5 個來源。

  • Memory 有兩層，中間是 policy。Context window 是這一次的工作狀態，memory store 跨 session 保存。Store 的內容要先檢索進 context，model 才看得到。
  • 檢索不能只看語意。還要看 scope、重要性、有效時間、來源。遺忘和寫入一樣是正式操作。
  • 錯誤會相乘。每步成功率 95%，50 步全對只剩約 8%。失敗要先找來源層，再在那一層修。

2 · 核心觀念

讓 agent 記得對的事，再讓它把事做完

A · Memory：記什麼、怎麼找、怎麼忘

2.1Memory 的設計：兩層 store，中間是一串 policy 決策 p.5–10、p.17

Model 沒有狀態，記憶是 harness 搬進來的。Agent 看起來記得事情，是因為 harness 把 store（存在 context 外面的記憶，例如硬碟上的檔案或一個資料庫）裡的文字放進 context。所以 memory 是兩層：store 是長期的，context 是這一次 request 看得到的；memory 的每個設計問題都在問同一件事：什麼時候，把什麼，從哪一層搬到哪一層。Slide 把它拆成 7 個問題（p.6）：誰擁有這條記憶、值得記嗎、存成什麼形式、放在哪種 backend（存放的系統：檔案、SQL、vector database）、這個任務需要它嗎、能歸納出什麼教訓、還成立嗎。

前情Context 與它的代價（L4）：每一條記憶都要每圈重送

Context 是每一次送進 model 的全部文字：system prompt、tool 定義、對話歷史、tool 結果，上限叫 context window。Model 沒有記憶，request 結束 context 就消失，下一圈 harness 重新組一份再送。所以 memory 要先由 harness 讀進 context，model 才看得到；L4 2.1 的「三個零件」把 state 分成 context 和 memory 兩塊，就是這裡的兩層。

Context 有三種代價（L4 2.6）：錢，每一圈整份重送，一條 2,000 token 的記憶 50 圈就是 100,000 token；延遲，prompt 越長 prefill 越久；注意力，window 越滿，model 越難找回中間的資訊。所以記憶不是越多越好，L4 2.7 的四種策略（admission、offloading、transformation、compaction）在 memory 上一樣適用：常駐只放索引，細節要用再讀。

七個問題，每個都是取捨。寫入的時機：每次互動都寫，recall 最高，雜訊也最多；只在使用者要求時寫，precision 最高，但漏很多（p.7）。存成什麼形式（p.8）：原始事件最完整，但很大；摘要精簡，但丟掉「以前用 vLLM」（vLLM 和 SGLang 都是 LLM serving engine，Part II 會講）；結構化狀態好查，但存不進 schema（事先定好的欄位表）沒有的欄位；knowledge graph 能表達隨時間的變化。p.17 的 checklist 把六站排成一列，每一站都要有明確、可量測的規則。

名詞Precision 與 recall：用在 memory 的寫入與檢索

Recall：該記的事記下了多少；該取回的記憶取回了多少。Precision：記下的東西有多少真的有用；取回的有多少相關。兩者通常相反：寫得越多 recall 越高、precision 越低。寫入 policy 在兩者之間取捨 p.7。

評估時要分開量寫入和檢索：retrieval miss（該取回卻沒取回）可能是當初沒寫，也可能是寫了沒找到 p.19。兩種原因修法不同，一個改寫入 policy，一個改檢索。

名詞Knowledge graph 與結構化狀態：兩種「有形狀」的記憶

結構化狀態是一張固定欄位的表：serving_engine = vLLM、timezone = Asia/Taipei。查詢快、不會含糊，但欄位要事先定好，沒有欄位的事實存不進去。

Knowledge graph 把事實存成節點和邊：「專案 X」—使用—「vLLM」，每條邊可以帶時間（valid_from、valid_to）和來源。所以它能回答「4 月用什麼、6 月換成什麼」，也能順著邊找相關的事實；代價是寫入時要先抽出實體和關係，這一步通常靠 LLM，會出錯。Zep 的 Graphiti 是一個例子。

本文延伸｜Memory 和任務搶同一個 context不是 slide 的內容

每一條載入的記憶都佔 context，而且每圈 loop 都要重送（2.1 的註）。記憶越多，留給任務的空間越少；無關的記憶還會分散注意力（p.18 的 context pollution：無關的記憶把 model 的注意力帶偏）。

所以 memory 系統的第一個指標是 token overhead（p.19），不是記了多少。可行的預算：常駐記憶只放索引，細節按需讀取。Claude Code 每個 session 只載入 MEMORY.md 的前 200 行或 25KB，topic 檔按需讀。

2.2檢索：語意相似分不出現在的事實，還要四個訊號 p.11

語意相似分不出現在的事實。Store 裡的東西要經過檢索才回到 context，所以檢索的規則最重要。常見的檢索是 semantic search：把記憶和問題都轉成向量，取最相近的 k 筆。先看一個問題：使用者問「現在用哪個 serving engine？」，「用 vLLM」和「用 SGLang」兩筆的相似度幾乎一樣。語意分不出哪一筆是現在的事實。

前情Embedding 與 vector search（L4 2.2）：top-k 是怎麼算出來的

Embedding model 把一段文字轉成一串數字，也就是向量。意思相近的文字，向量也相近。建索引時每條記憶算一個向量存起來；查詢時把 query 也轉成向量，找出距離最近的 k 筆，這就是 top-k p.9。L4 2.2 用它找程式碼（semantic search），這裡用它找記憶，機制相同。

相似度量的是「意思像」，它不知道哪一筆是真的、哪一筆是現在的、哪一筆是別人的。所以這一章的四個訊號都是 embedding 給不了的東西，要另外存成欄位。

另外四個訊號。Slide 列出另外 4 個訊號。Scope：同一個使用者、專案或任務。Importance：漏掉它和放進來的代價。Validity：此刻仍然成立。Provenance：來源、信心、證據。

過濾還是排序。四個訊號的用法不同。Scope 和 validity 要寫成硬過濾條件；只當排序分數時，別人的記憶仍可能進入 top-k，這就是 p.18 的 isolation failure（A 使用者的記憶漏進 B 的查詢結果）。Importance 和 provenance 適合調整排序，或做成不看 query 的常駐規則。

2.3遺忘與有效時間：忘記、valid time、來源都是第一級操作 p.12–14、p.18–19

事實會變：valid time 與 provenance。專案 4 月用 vLLM，6 月換成 SGLang（p.14）。系統如果只會新增，舊的會蓋過新的，這是 p.18 的 staleness（過期的記憶還當成現在的事實）。解法是兩個欄位：valid time 記事實在哪段時間成立，新事實讓舊的 valid_to 關上，但不刪除，所以還能回答「以前是什麼」；provenance 記來源與信心，使用者親口說的和網頁讀到的，信任等級不同。

四種遺忘，加上歸納。遺忘有 4 種做法：標記失效、永久刪除、TTL 到期、分層移出（從常駐的一層搬到要查才讀的一層）（p.13）。歸納是另一種改寫：多筆觀察合成一條較高層的記憶，要附信心值並連回證據（p.12）。證據太少就歸納，一次事件會變成長期偏好。

名詞TTL 與 eviction：自動遺忘的兩種機制

TTL（time to live）是資料的存活時間，寫入時設定，時間到就自動刪除。Redis 的寫法：SET task:42:notes "..." EX 86400，86,400 秒後消失。Eviction 是空間不夠時挑東西丟，例如最久沒用的先丟（LRU）。

TTL 適合短期狀態，例如這個任務的暫存筆記；長期事實不要用 TTL，要用上一段的 valid time 標記失效 p.13，這樣還能回答「以前是什麼」。

B · 可靠性：為什麼跑不完，怎麼修

2.4錯誤相乘：每步 95%，50 步只剩 8% p.22

每步 95%，n 步只剩 0.95ⁿ。後半換題目：就算 model 看到了對的東西，任務還是常做不完。原因是一個 run（agent 從接到任務到停下來的一整趟執行）要每一步都對才算成功。每步成功率 95%，n 步全對的機率是 0.95ⁿ：5 步 77%，10 步 60%，20 步 36%，50 步 8%。約 13 次才有 1 次全對。

真實的 run 更差：錯誤會往後傳。這個算法假設每步獨立。真實的 run 更差：第 3 步讀錯檔案，第 4 步就改錯地方，第 5 步再為錯的修改補洞。反過來算，要讓 50 步有 90% 全對，每步要 99.79%。所以三件事要同時做：減少步數、讓每步更可靠、在中途驗證並存 checkpoint（驗證過的狀態存一份快照，失敗只重跑之後的步驟）。

名詞獨立假設：0.95ⁿ 背後的前提，以及 checkpoint 為什麼有用

把機率相乘，前提是每步的成敗互不影響。Agent 的步驟有相依性：前一步的輸出是下一步的輸入，錯誤往後傳時，後面步驟的成功率低於 95%，所以 0.95ⁿ 是上界，真實的全對機率更低 p.22。

驗證步驟能打斷這個傳遞：跑一次測試，錯的那一步就不會再往下帶。Checkpoint 再加一步：在驗證過的狀態存快照，失敗只重跑之後的步驟，而不是整趟重來 p.26。Claude Code 用 /rewind 回到之前的檔案狀態；Bash 指令改的檔案不在追蹤範圍。

本文延伸｜Memory 要像任何元件一樣做 eval不是 slide 的內容

p.20 的三個 benchmark（LoCoMo、LongMemEval、BEAM）測的都是聊天歷史的回想：給一段很長的使用者與助理對話，問它早先提過的事。Coding agent 的記憶，例如專案慣例，不在範圍內。

要知道自己的 memory 有沒有用，要自己做測試集：一組「應該記得」、一組「應該忘掉」、一組別人的事實，各自查一遍。沒有這組測試，policy 的改動只能靠感覺。L7 會講怎麼建 eval。

2.5失敗的五層：同一個症狀五個來源，每層一道防線 p.24–30

同一個症狀，五個來源。「agent 說測試過了，但測試沒過」：也許 model 沒跑測試，也許 tool 截掉了錯誤輸出，也許環境是舊的 build。Slide 把來源分成 5 層：任務規格、harness、model、tool、環境（p.24）。

前情Harness 與 tool（L4）：五層裡 model 以外的兩層是什麼

Harness 是包在 model 外面的那層程式，例如 Claude Code 這個 CLI：它組 context 送進 model、讀 model 的回覆、執行 model 要的 tool call、把結果放回 context，一圈一圈跑到任務結束。Tool 是 harness 給 model 的動作：讀檔、grep、edit、跑 shell；model 只輸出一段 JSON 說要呼叫哪個，執行的是 harness。L4 整堂講這兩層怎麼設計。

所以「harness 的 context 截斷」是 harness 為了省 context 把 tool 輸出砍短，砍掉了錯誤訊息；「tool 的靜默失敗」是 tool 失敗了卻回一個看起來正常的結果。L4 2.4 的五項保護（失敗訊號、輸出量、時間、預算、隔離）就是修這兩層的方法。

每層的失敗型態，與五個原則。每層有自己的失敗型態（p.25–29）：規格的代理目標（proxy goal：把「測試變綠」當成目標，agent 就去改測試）、harness 的 context 截斷、model 的沒驗證就宣布完成、tool 的靜默失敗、環境的版本不符。p.30 把修法濃縮成 5 個原則：把「完成」寫成測試；每個 run 都有上限；要求證據；tool 失敗要大聲；環境固定並隔離。除錯時先找第一個出錯的步驟，在那一層修。

本文延伸｜可靠性工程的習慣可以搬過來不是 slide 的內容

SRE 有 timeout、retry with backoff、circuit breaker、error budget。Agent 的對應物：步數和成本上限、tool 失敗先重試再下結論、沒進展就停、每種任務有可接受的失敗率。

名詞SRE 的四個習慣：timeout、retry with backoff、circuit breaker、error budget

Timeout：一個呼叫等多久就放棄，不讓一個卡住的下游拖住整個系統。Retry with backoff：失敗後重試，但每次等更久（1 秒、2 秒、4 秒），避免大家同時重試把下游壓垮。Circuit breaker：連續失敗到一個門檻就「斷路」，一段時間內直接回錯不再呼叫，讓下游有機會恢復。Error budget：先定可接受的失敗率（例如一個月 0.1%），沒用完就可以冒險發版，用完就只修不加。

這四個都是 SRE（site reliability engineering，Google 提出的服務維運方法）處理「下游會失敗」的標準手法。Agent 的 tool 和環境就是它的下游。

差別在失敗的型態。服務的失敗大多能偵測；agent 的失敗常常安靜，例如沒驗證就宣布成功（p.27）。所以「要求證據」排在所有習慣之前。

本文延伸｜「還沒有最佳實踐」對團隊的意思不是 slide 的內容

Slide 的結語是：我們對大規模的 agent 了解不多（p.30）。這堂的表格是起點，之後會改。對團隊的做法有三件：把每條規則寫成可量測的 policy；記錄每個 run 的 trajectory（一趟執行的完整紀錄：每一步的輸入、輸出、tool 結果）；定期看失敗來自哪一層。沒有記錄，就不知道該改什麼。

  1. p.5–7 · Memory 的兩層與寫入

    Store 的內容要經過什麼，model 才看得到？「每次都寫」和「只在使用者要求時寫」各有什麼代價？

    參考答案與重點複習

    答案：Store 的內容要先經過檢索，由 harness 放進 context window，model 才看得到（p.5、p.11）。Context window 是這一次的暫時工作狀態；memory store 在 context 之外，跨 session 保存（p.5）。每次互動都寫：recall 最高，雜訊也最多。只在使用者明確要求時寫：precision 最高，但會漏掉很多（p.7）。

    重點拆解

    Model 本身沒有狀態。每次呼叫，它只看得到這一次送進去的 context。所以 p.5 把 memory 分成兩層：context window 是工作狀態，session 結束就消失；memory store 在 context 之外，例如檔案或資料庫，跨 session 保存。兩層之間的搬運，全部由 harness 負責。

    讀的方向是檢索。Harness 用目前的 query 做 vector search，取回 top-k 筆，組進 prompt（p.11）。沒被取回的記憶，對 model 來說等於不存在。所以「store 裡有」和「model 知道」是兩件事，中間隔著一步檢索。p.18 的 retrieval miss 就發生在這一步：記憶存在，但沒被找到。誰觸發檢索也是設計選擇：每一輪自動查、由 harness 判斷，或由 model 呼叫 search_memory() 這類 tool（p.10）。

    寫的方向是寫入 policy。p.7 把寫入畫成一條光譜：一端是每次互動都寫（high recall），另一端是選擇性地寫（high precision）。光譜上有 4 種做法：使用者明確要求、deterministic rules、small classifier、periodic LLM review。每次都寫，該記的都記下了，但 store 裡大部分是雜訊。只在使用者說「記住這個」時寫，記下的幾乎都有用；但使用者沒想到要說的事，全部漏掉。

    背景補充

    這兩層對應 L1 的 OS 類比：context window 像 RAM，memory store 像 disk。CPU 只能直接讀 RAM，disk 上的資料要先載入。MemGPT（2023）把這個類比做成系統：model 自己用 function call 在兩層之間搬資料，像 OS 的 paging。RAG 也是同一個結構：知識放在外部索引，查詢時才取回、放進 prompt。

    寫入的雜訊有兩個成本。第一，取回的每一筆都佔 context，而且每一圈 loop 都要重送。第二，雜訊越多，真正相關的那一筆越難排進 top-k。所以寫入 policy 也決定了之後檢索的品質。

    常見誤解

    「Context window 夠大，就不需要 memory。」Context window 只活在這一個 session，session 結束就清空。而且 context 越長，越貴、越慢，model 也越難找到中間的資訊（L4 的 lost in the middle）。大 window 解決單次任務的容量，不解決跨 session 的保存。

    帶走這幾點
    1. Model 只看得到 context；store 的內容要經過檢索 → 放進 context，才會影響回答。
    2. 「Store 裡有」不等於「model 知道」；中間的檢索可能失敗，這就是 retrieval miss。
    3. 寫入 policy 是 recall 與 precision 的取捨：全寫 → 雜訊多；只照要求寫 → 漏很多。

    相關：核心觀念〈Memory 的設計：兩層 store，中間是一串 policy 決策〉；名詞註〈Embedding 與 vector search〉、〈Precision 與 recall〉；本文延伸〈Memory 和任務搶同一個 context〉；L1 Agent 是一台新的電腦、L2 記憶：就是每次 session 開始都會載入的檔案。進階題第 1 題會替 coding agent 設計寫入 policy。

  2. p.11–14 · 檢索訊號與有效時間

    除了語意相似，檢索還要看哪 4 個訊號？p.14 每條記憶帶的兩個欄位各記什麼？

    參考答案與重點複習

    答案：4 個訊號：scope（同一個使用者、專案、實體或任務）、importance（漏掉或放進來的代價）、validity（對這個任務、在此刻仍成立）、provenance（來源、信心、證據）（p.11）。Valid time 記這個事實在哪段時間成立；provenance 記它從哪裡來。p.14 的例子：4 月的 vLLM 標成 superseded，6 月的 SGLang 是 current，來源是 Episode 28。

    重點拆解

    Vector search 只回答一個問題：這筆記憶的意思和 query 像不像（p.11）。它不知道這筆屬於誰、現在還對不對、從哪裡來。使用者問「現在用哪個 serving engine？」，「用 vLLM」和「用 SGLang」都在講 serving engine，相似度幾乎一樣。語意分不出哪一筆是現在的事實。

    另外 4 個訊號，各補一個語意看不到的缺口。把它們和 p.18 的失敗模式對起來看，就知道缺了哪一個會出什麼事：

    訊號（p.11）它問什麼缺了它，容易出現（p.18）
    Scope是同一個使用者、專案、任務嗎？Isolation failure：別人的記憶跨界進來
    Importance漏掉或放進來，代價多大？Retrieval miss：關鍵規則沒取回；context pollution：無關記憶塞滿 context
    Validity此刻、對這個任務還成立嗎？Staleness：舊事實蓋過新的
    Provenance誰說的？信心多少？證據在哪？Memory hallucination：推論被當成事實

    p.14 用一條時間軸說明 valid time 與 provenance。Episode 28 這段互動提到，serving 從 vLLM 搬到了 SGLang。Store 把它存成一條三元組 Project → SERVES_WITH → SGLang，來源記 Episode 28。舊的 vLLM 那一筆沒有刪除，而是標成 superseded：它只在 4 月到 6 月之間成立。這樣系統能回答兩種問題。「現在用什麼」取 current 的那一筆；「5 月用什麼」取那段時間成立的那一筆。

    背景補充

    Valid time 是資料庫的老概念。Bitemporal 資料模型有兩條時間軸：valid time 是事實在真實世界成立的時間；transaction time 是系統記下它的時間。SQL:2011 標準把 temporal table 納入規格。p.16 的 Graphiti 是 temporal knowledge graph，把同一個想法用在 agent memory 上。

    Provenance 對應資料工程的 data lineage：每一筆資料都能追到來源。對 agent 來說，來源決定信任等級。使用者親口說的，和網頁上讀到的，不該同等對待。這一欄也是防 persistent prompt injection 的基礎（下一題）。

    常見誤解

    「新事實來了，把舊的刪掉就好。」刪掉之後，系統答不出「以前用什麼」，也查不到是誰、在什麼時候改的。新的一筆如果是錯的，也沒有舊值可以還原。所以 p.13 把「標記失效」和「永久刪除」列成兩種操作。永久刪除適合隱私這類資料必須真的消失的情況。

    帶走這幾點
    1. Vector search 只量「意思像不像」；它不知道是誰的、何時的、從哪來的。
    2. Scope、importance、validity、provenance 各補一個缺口；缺了哪一個，就對應 p.18 的一種失敗。
    3. 事實改變時，關掉舊事實的有效時間，不刪除 → 能回答現在，也能回答過去。

    相關：核心觀念〈檢索：語意相似分不出現在的事實，還要四個訊號〉、〈遺忘與有效時間：忘記、valid time、來源都是第一級操作〉；名詞註〈Embedding 與 vector search〉、〈TTL 與 eviction〉；L4 Embedding 與 semantic search。動手試試有一筆帶 valid time 的 JSON 記錄。

  3. p.15–18 · 擁有權與失敗模式

    Agent-owned 和 dedicated memory 差在哪裡？哪一種失敗模式讓惡意指令一直留著？

    參考答案與重點複習

    答案：Agent-owned：memory 是 harness 裡的檔案，例如 CLAUDE.md，harness 直接讀寫。Dedicated：memory 是 agent 呼叫的服務，例如 Mem0、Graphiti，可以跨 agent、跨 session 共用（p.15–16）。讓惡意指令一直留著的是 persistent prompt injection：惡意的文字寫進 memory，之後每個 session 讀回它，攻擊就再生效一次（p.18）。

    重點拆解

    兩種做法的差別，在「誰管理 memory」。p.21 把它畫成兩種 stack。一種是 runtime 自己管理 memory，storage 就是 Markdown 檔。另一種是在 runtime 和 storage 之間加一層獨立的 memory management，下面接 vector、SQL、graph 或 object store。

    Agent-ownedDedicated
    形式Harness 裡的檔案：CLAUDE.md、scratchpad、task notesAgent 呼叫的服務或 library
    誰讀寫Harness 直接讀寫，存到磁碟Agent 透過 memory layer 搜尋與更新
    共用範圍跟著這個 harness一個 API，跨 agent、跨 session
    例子CLAUDE.md、task notesMem0、Graphiti、supermemory（p.16）

    一般的 prompt injection 只活在一個 session 的 context 裡。Session 結束，惡意文字就跟著消失。Persistent 版本多了一步：agent 把讀到的惡意內容寫進 memory。之後每個 session，檢索或自動載入都把它帶回 context。它以「agent 自己的筆記」出現，看起來像可信的指令。所以它一直留著，直到有人發現並刪掉它。

    p.18 的 8 種失敗模式，可以照第 1 段的生命週期圖分組。寫入、整理與歸納時出錯：memory hallucination、overgeneralization、persistent prompt injection。檢索時出錯：retrieval miss、context pollution、isolation failure。沒有遺忘機制：staleness、unbounded growth。

    背景補充

    Persistent prompt injection 很像 web 安全的 stored XSS。Reflected XSS 只影響點了惡意連結的那一次請求。Stored XSS 把惡意腳本存進資料庫，之後每個讀到那一頁的人都會中招。OWASP 的 LLM 應用 Top 10 把 prompt injection 列為第一名（LLM01）。

    選擇 ownership 也是選擇怎麼稽核。Plain files 容易檢查、diff、搜尋（p.9），可以放進 git，每一次寫入都有紀錄。Dedicated 服務能跨 agent 共用、能做過濾查詢；代價是多一個要維運的服務。共用的 store 也必須做好 scope 隔離，不然就是 isolation failure。

    常見誤解

    「Memory 是 agent 自己寫的，所以可以信任。」Agent 寫下的，是它讀到的東西。它讀過網頁、README、tool 輸出，這些內容可能被寫進 memory。如果沒有記錄來源，下次讀回來時，已經分不出哪一句來自使用者、哪一句來自外部。

    帶走這幾點
    1. Agent-owned 是 harness 裡的檔案；dedicated 是一個跨 agent、跨 session 共用的服務。
    2. 一般 injection 隨 session 結束消失；寫進 memory → 每個 session 讀回 → 每次再生效。
    3. 8 種失敗模式分屬寫入、檢索、遺忘三段；除錯時先找是哪一段出錯。

    相關：核心觀念〈遺忘與有效時間：忘記、valid time、來源都是第一級操作〉；L2 記憶也是攻擊面、L2 Prompt injection。進階題第 3 題會畫出完整的攻擊路徑，並在每一站設計防線。

  4. p.22 · 錯誤會相乘

    每步成功率 95% 時，50 步全對的機率約多少？為什麼真實的 run 比這更差？

    參考答案與重點複習

    答案：約 8%（0.95⁵⁰ ≈ 7.7%），也就是約 13 次才有 1 次全對。一個 run 要每一步都對才算成功（p.22）。這個算法假設每步獨立。真實的 run 裡錯誤會往後傳：早期的一個錯誤，讓後面每一步更容易錯，所以實際更差（p.22）。

    重點拆解

    一個 run 是一條串起來的鏈。任何一步錯，整個 run 就失敗。每步成功的機率是 0.95，而且互不影響時，n 步全對的機率是 0.95 自乘 n 次。p.22 的數字：1 步 95%，5 步 77%，10 步 60%，20 步 36%，50 步 8%。每多 1 步，剩下的機率再乘一次 0.95。所以它是指數衰減，不是直線下降：約 13.5 步就只剩一半。

    真實的 run 更差，因為 agent 的步驟不獨立。前一步的輸出，是下一步的輸入。第 3 步讀錯檔案，第 4 步就在錯的檔案上修改，第 5 步再替錯的修改補洞。出錯之後，後面每一步的成功率都低於 95%。所以 0.95ⁿ 是樂觀的上界，p.22 也在註腳寫明這個假設。

    每步的可靠度槓桿很大。每步失敗率從 5% 降到 1%，50 步的成功率從 7.7% 升到 60.5%（0.99⁵⁰）。所以設計方向有三個：減少步數、讓每步更可靠、在中途驗證並存 checkpoint，讓錯誤不再往後傳（p.30）。

    例子

    不用計算機算 0.95⁵⁰：一直平方。0.95² = 0.9025；0.95⁴ = 0.9025² ≈ 0.8145；0.95⁸ ≈ 0.6634；0.95¹⁶ ≈ 0.4401；0.95³² ≈ 0.1937。50 = 32 + 16 + 2，所以 0.95⁵⁰ = 0.1937 × 0.4401 × 0.9025 ≈ 0.0769，約 7.7%。倒數 1 ÷ 0.0769 ≈ 13，就是「13 次才有 1 次全對」。

    背景補充

    這是可靠性工程的串聯系統：每個元件都要正常，系統才正常，整體可靠度等於各元件可靠度相乘（Lusser's law）。微服務也一樣：一個請求依序經過 10 個 99.9% 可用的服務，整體約 0.999¹⁰ ≈ 99.0%。

    心算捷徑：每步失敗率 ε 很小時，(1 − ε)ⁿ ≈ e^(−nε)。nε 是一個 run 平均出幾個錯。50 × 0.05 = 2.5 個錯，e^(−2.5) ≈ 0.082，和 7.7% 很接近。所以要控制的是「一個 run 平均出幾個錯」：步數加倍、失敗率減半，結果幾乎不變。

    常見誤解

    「Model 的 tool call 準確率 95%，所以 agent 的任務成功率大約 95%。」單步的準確率不能直接當成任務的成功率。任務要跑幾十步，成功率要用相乘來估；步驟之間還有相依，實際更低。

    帶走這幾點
    1. 每步都要對 → 成功率是 0.95ⁿ，指數衰減；50 步只剩 7.7%，約 13 次 1 次。
    2. 0.95ⁿ 假設各步獨立；錯誤會往後傳 → 真實的 run 更低，0.95ⁿ 是上界。
    3. 要壓低的是 n × 失敗率：減少步數、提高每步可靠度、中途驗證並存 checkpoint。

  5. p.24–30 · 五層失敗與對策

    失敗的來源分哪 5 層？Harness 這一層，p.30 給了什麼設計原則？

    參考答案與重點複習

    答案：5 層：使用者與任務規格、agent harness、LLM、tool 層、環境（p.24）。Harness 的原則是每個 run 都有邊界。具體做法是設定步數、成本、時間上限，並做 checkpoint 與回滾（p.26、p.30）。

    重點拆解

    分層的理由：同一個症狀，可能來自不同層。Agent 說「測試過了」，測試卻沒過。也許 model 沒跑測試，也許 tool 截掉了錯誤輸出，也許環境是舊的 build。p.24 由上往下排出 5 個來源：任務規格（目標模糊）、harness（context、loop、排程）、LLM（推理、規劃）、tool 層（shell、browser、API）、環境（repo、OS、web、服務）。p.25–29 每層一張表，例如規格的代理目標、model 沒驗證就宣布完成、tool 的靜默失敗、環境的版本不符。

    Harness 的失敗，p.26 列了 5 種。Context 截斷：harness 剪掉最舊的對話，「不能改 API」的規則跟著消失。Memory 錯誤：把過期的筆記當事實，去改一個已經搬走的檔案。狀態損壞：留下改到一半的檔案，後面每一步都建在壞掉的狀態上。Control loop 錯誤：沒有設步數或成本上限，跑了 200 步沒有進展。Blocking fan-out：等每一個 sub-agent，一個慢的就卡住整個 run。

    p.30 把 harness 的修法濃縮成一句：每個 run 都有邊界。上限把「跑不停」變成「有限的失敗」：花費有上限，停下來後人可以接手。Checkpoint 在驗證過的狀態存一份快照。後面的步驟失敗，就回滾到快照，只重跑之後的步驟。這正好切斷上一題說的錯誤傳遞。其他四層的原則：把「完成」寫成測試、要求證據、失敗要大聲、環境固定並隔離。

    背景補充

    這套原則和 SRE 的習慣對得上。步數與時間上限就是 timeout。「沒有進展就停」和 circuit breaker 的精神一樣：持續失敗時主動停下，不再浪費資源。Checkpoint 與回滾像資料庫的 transaction：失敗時回到上一個一致的狀態，不留下改到一半的資料。

    在 Claude Code 的非互動模式（-p），--max-turns 限制 turn 數，--max-budget-usd 限制花費，時間上限用外層的 timeout 指令。互動模式可以用 /rewind 回到之前的檔案狀態，但 Bash 指令改的檔案不在追蹤範圍。

    常見誤解

    「Agent 失敗了，換一個更強的 model 就好。」更強的 model 只處理 LLM 這一層。規則在 compaction 時被丟掉、tool 把錯誤包成空結果、環境版本不一樣，換 model 之後一樣會發生。p.30 把「用更強的 model」列在 model 層的修法裡，它只是 5 層中的一層。

    帶走這幾點
    1. 5 層：任務規格、harness、LLM、tool、環境；同一個症狀可能來自不同層 → 先找第一個出錯的步驟。
    2. Harness 的原則是每個 run 都有邊界：步數、成本、時間上限，加上 checkpoint 與回滾。
    3. 上限把「跑不停」變成「有限的失敗」；checkpoint 讓錯誤不再往後傳。

    一句話：MemGPT 把 OS 的虛擬記憶體搬到 LLM 上。Context window 是主記憶體，外部儲存是磁碟，model 自己用 function call 在兩層之間搬資料。固定 8k 的 GPT-4 因此能在跨 session 對話與多文件 QA 上表現得像有無限 context。

    跟這堂課的關係

    Slides p.5 的兩層就是這篇的主記憶體與外部儲存，見〈Memory 的設計：兩層 store，中間是一串 policy 決策〉。p.10 列的「由 model 呼叫 tool 觸發檢索」，MemGPT 是早期的完整實作。一處差異：slides 把搬運交給 harness 的 policy；MemGPT 把寫入、搜尋、摘要都交給 model 決定，harness 只在 token 到門檻時發警告。

    壓縮後的重點

    1. 主 context 分三塊。System instructions 唯讀，說明記憶階層與可用的 function。Working context 是固定大小的可讀寫文字塊，放關鍵事實，只能用 function call 修改。FIFO queue 是滾動的訊息歷史，第一則是驅逐訊息的遞迴摘要。
    2. 外部 context 分兩層。Recall storage 存完整的訊息歷史，可搜尋。Archival storage 存任意長度的文字物件，可讀寫。兩層的內容都要經由 function call 才會進入主 context。
    3. Queue manager 用兩個門檻管理溢出。Prompt token 超過警告門檻（例如 window 的 70%），插入一則 memory pressure 訊息，提醒 model 把重要內容存起來。到達 flush 門檻（例如 100%）時，驅逐一批訊息（例如 window 的 50%），更新遞迴摘要。驅逐的訊息仍在 recall storage。
    4. Heartbeat 讓 model 串接多步檢索。Function 帶 request_heartbeat=true 時，執行完立刻把控制權交回 model，它可以繼續呼叫下一個 function。沒有這個旗標，系統等待下一個外部事件。
    5. 跨 session 的記憶回想，準確度從 32.1% 升到 92.5%。Deep memory retrieval 任務上，GPT-4 基線 32.1%，加 MemGPT 92.5%；GPT-4 Turbo 從 35.3% 升到 93.4%。基線只看到歷史的有損摘要，MemGPT 能搜尋完整歷史。
    6. 多文件 QA 的準確度不隨文件數下降。檢索的文件數從 0 到 200，MemGPT 配 GPT-4 與 GPT-4 Turbo 都穩定。基線要截斷文件才塞得進 window，漏掉關鍵片段的機率隨之上升。配 GPT-3.5 的 MemGPT 變差，因為它的 function call 能力較弱。

    把失敗追到 root-cause 的那一步，再把修正餵回下一次嘗試。

    導讀重點是 step-level 標註：要歸因，先要有每一步的紀錄。連到 L7 的 tracing。

    摘要讀約 3 分；原文約 20 分

    一句話：這篇提出 AgentErrorTaxonomy（5 個模組、17 種錯誤）、AgentErrorBench（200 條逐步標註的失敗 trajectory）和 AgentDebug。AgentDebug 找出最早的關鍵錯誤，給回饋後從那一步重跑；ALFWorld 上成功率最高從 60% 升到 84%。

    跟這堂課的關係

    Slides p.30 說除錯要先找第一個出錯的步驟，見〈失敗的五層：同一個症狀五個來源，每層一道防線〉；這篇把它定義成 critical error，並做成 benchmark。分法不同：slides 依來源分 5 層，這篇依 agent 內部的模組分 5 個，規格層在這篇沒有對應。Memory 模組的 3 種錯誤對應 p.18 的 retrieval miss 與 memory hallucination，見〈遺忘與有效時間：忘記、valid time、來源都是第一級操作〉。它的 error propagation 分析是 p.22 錯誤相乘的實例，見〈錯誤相乘：每步 95%，50 步只剩 8%〉；這種分析要有每一步的紀錄，呼應〈「還沒有最佳實踐」〉。

    壓縮後的重點

    1. 錯誤依 agent 的模組分類：5 個模組、17 種。Memory 3 種：摘要過度簡化、假記憶、檢索失敗。Reflection 4 種：進度誤判、結果誤讀、歸因錯誤、幻覺。Planning 3 種：忽略限制、不可能的動作、低效計畫。Action 3 種：計畫與動作脫節、格式錯誤、參數錯誤。System 4 種：步數用盡、tool 錯誤、LLM 限制、環境錯誤。分類來自 3 個環境超過 500 條失敗 trajectory 的人工分析。
    2. Critical error 是最早的那一步：修好它，任務就會成功。標註員只找最小的 root-cause 集合，不標每個表面錯誤。Benchmark 有 200 條：ALFWorld 100、WebShop 50、GAIA 50。10 位研究生逐步標註，Cohen's κ = 0.55。
    3. 關鍵錯誤多在中段，planning 模組最多。第 6–10 步最多（48 條）。依模組看，planning 78、reflection 39、memory 38、action 22、system 22。作者的解讀：memory 與 reflection 的錯誤最會往後傳，記錯一件事，後面的計畫就整個歪掉。
    4. AgentDebug 分 3 階段。先用 taxonomy 逐步標錯誤；再用 counterfactual 推理找最早的關鍵錯誤；最後產生附錯誤類型與修正建議的回饋，從那一步重跑，最多 5 次。重跑不從頭開始，省下前段的計算。
    5. 找關鍵錯誤：step accuracy 45.0%，全對 24.3%。Debugger 用 GPT-4.1。最強的基線 Direct Prompting 是 28.0% 與 0.3%。全對要同時答對步數、模組、錯誤類型。GAIA 最高：58.0% 與 38.0%。
    6. 重跑後 ALFWorld 成功率大幅上升，弱 model 升最多。5 次嘗試後，GPT-4o-mini 從 21% 到 55%，Qwen3-8B 從 48% 到 74%，Qwen3-Next-80B 從 60% 到 84%。摘要的「最多 26% 相對提升」是和 Self-Refine、Best-of-N 比，嘗試預算按總 token 用量對齊。
    7. Debugger 要夠強。換 Llama-3.3-70B、GPT-4o-mini 或 Qwen3-Next-80B 當 debugger，step accuracy 都在 16% 以下；GPT-4.1 是 42%。

  2. 必讀Why Do Multi-Agent LLM Systems Fail?arXiv 2503.13657 · 論文 · 2025 · 挑段約 25 分

    14 種失敗模式、三大群：系統設計、agent 間不對齊、任務驗證。從 150 條精標加 1,600 多條 trace 歸納。

    導讀用三大群分流討論：一個修正該落在設計、agent 間的契約，還是 verifier？

    摘要讀約 3 分；原文約 25 分

    一句話：UC Berkeley 團隊分析 7 個 multi-agent 框架的 1,642 條 trace，歸納出 MAST：14 種失敗模式、3 大類。結論是多數失敗來自系統設計與 agent 間的協調，換更強的 model 修不好。

    跟這堂課的關係

    Slides p.24 把失敗來源分成 5 層，見〈失敗的五層：同一個症狀五個來源，每層一道防線〉；這篇分成 3 類。「系統設計」對應任務規格與 harness 兩層。「任務驗證」對應 p.27 與 p.30 的「要求證據」，也支持〈可靠性工程的習慣可以搬過來〉的排序。「agent 間不對齊」在 L6 沒有對應層，它屬於 L5 p.36 的 multi-agent 問題。

    壓縮後的重點

    1. Multi-agent 系統的失敗率很高。7 個框架在各自的 benchmark 上，失敗率從 41% 到 86.7%。Benchmark 不同，數字不能直接互比。
    2. 3 大類的比例：系統設計 44.2%、agent 間不對齊 32.3%、任務驗證 23.5%。分類來自 6 位專家對 150 多條 trace 的 grounded theory 分析。人工標註的 Cohen's κ 經三輪修訂後達 0.88。
    3. 最常見的單一模式是步驟重複（15.7%）。其次是推理與行動不一致（13.2%）、不知道終止條件（12.4%）、違反任務規格（11.8%）。驗證類裡，錯誤的驗證佔 9.1%，沒驗證或驗證不完整佔 8.2%。
    4. LLM 可以當標註員，規模化到 1,642 條。用 OpenAI o1 做 few-shot 標註，準確度 0.94，κ = 0.77。換到新的框架與 benchmark 上，κ = 0.79。
    5. 同一個 model，不同框架的失敗分布不同。MetaGPT 比 ChatDev 少 60–68% 的設計與協調失敗，但驗證失敗多 1.56 倍。AppWorld 以過早終止為主，OpenManus 與 HyperAgent 以步驟重複為主。
    6. 改 prompt 與拓撲有效，但不夠。ChatDev 在 ProgramDev-v0 上，基線 25.0%，改 prompt 後 34.4%，改拓撲後 40.6%；強制 CEO 有最終決定權提高約 9.4%，加高階驗證步驟提高約 15.6%。作者說這還不算實質改善，需要結構性的重新設計。
    7. Agent 間的不對齊，不只是溝通協定問題。作者認為它反映 agent 之間缺少 theory of mind。單靠更好的通訊協定，不太可能修好這一類。

    原文怎麼讀

    • 可以跳過：Section 2 Related Work；Section 3.3 LLM-as-judge pipeline 的建置細節；附錄的 prompt 與各框架描述。
    • 值得看原文：Figure 1 的 taxonomy 圖，一頁看完 14 種模式與比例；Section 4 每種模式的定義與例子；Section 5.2 的案例研究表（ChatDev 與 AG2 的介入前後數字）；Section 5.1 的逐框架失敗分布圖。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 25 分。
    別誤讀

    「系統設計佔 44.2%，所以改 prompt 和拓撲就能修好。」論文自己的介入只把 ChatDev 從 25.0% 拉到 40.6%，作者說這不算實質改善。而且 model 也有影響：同樣跑 MetaGPT，GPT-4o 的設計類失敗比 Claude 3.7 Sonnet 少 39%。修法要同時動架構、prompt、驗證與 model。

  3. 推薦Beyond the LeaderboardarXiv 2607.05775 · 論文 · 2026 · 挑段約 20 分

    27 篇研究的統合，整理成六類失敗。失敗隨任務長度複利；多加 scaffolding 不一定有救。

    導讀把「scaffolding 不一定有救」當警語帶進討論。它也批評排行榜（含 SWE-bench），接到 L7。

    摘要讀約 3 分；原文約 20 分

    一句話：Oxford 的 3 位作者統合 2023–2026 年的 27 篇研究（19 個 benchmark），歸納出 6 類失敗。結論：失敗隨任務長度非線性複利，子技能強不等於任務會成功，多加 scaffolding 不一定有幫助，排行榜分數有一部分來自測量錯誤。

    跟這堂課的關係

    Slides p.22 說真實的 run 比 0.95ⁿ 更差，見〈錯誤相乘：每步 95%，50 步只剩 8%〉與〈獨立假設〉；這篇 7.1 節同意：實測的下降比固定每步錯誤率更快，因為 agent 走錯後不會回頭。p.24 的 5 層依來源分，這篇的 6 類依症狀分，見〈失敗的五層：同一個症狀五個來源，每層一道防線〉；這篇的 tool 類是 agent 叫錯 tool 或給錯參數，依 slides 屬 p.27 的 model 層。長任務退化的瓶頸是 context 的管理，接到〈Memory 和任務搶同一個 context〉；測量效度接 L7，也呼應〈Memory 要像任何元件一樣做 eval〉。

    壓縮後的重點

    1. 這是文獻統合，不是實驗。入選條件：有量化的錯誤分析、有人工標註的 taxonomy，或檢驗過 benchmark 的效度；只報分數的不收。作者把 60 多個錯誤類別合併成 6 群。
    2. 6 類失敗。Tool 呼叫與參數錯誤；多限制同時滿足；長任務隨 context 累積退化；multi-agent 協調；安全與資安；測量效度。Table 2 把 16 組 benchmark 的數字排在一起。
    3. 規劃類：TravelPlanner 上 GPT-4 只有 0.6%。每個限制單獨都能滿足，一起就失敗。推理 model（o1-preview）約 10%；加形式化 verifier 與 critic 的最佳配置約 65%。
    4. 長任務類：下降不是線性的。METR 的資料：人類 4 分鐘內的任務，agent 接近 100%；4 小時以上的低於 10%。長 context 的 web agent 從 40–50% 掉到 10% 以下，而資訊仍在 context 裡；主因是忘了目標、陷入重複迴圈。
    5. 安全類：沒有專門防禦，就要假設會中 prompt injection。InjecAgent 上用 ReAct 的 GPT-4 約 24% 中招，強化攻擊約 47%，部分開源 model 超過 80%。
    6. 測量效度：修正 benchmark 後分數會掉。SWE-bench 上一個 SWE-agent 設定排除解答外洩與弱測試後，從約 12.5% 掉到約 4%。UTBoost 補強測試後，排名有 25–41% 改變。HAL 的 21,000 多次 rollout 顯示，提高 reasoning effort 多半降低準確度。
    7. 有進步的 3 處：單輪 tool 選擇、短 web 導航、範圍明確的 coding。WebArena 從約 14% 升到 61.7%（人類約 78%）；SWE-bench Verified 從 2024 年約 20% 升到 2026 年 50–60% 以上。
