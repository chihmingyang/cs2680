先看這裡

這堂講可靠性和 memory 兩半，講的是同一件事：agent 會出錯，錯誤會累積。一個 run（agent 從接到任務到停下來的一次執行）裡，錯誤逐步相乘；有了 memory，錯誤還能活過這個 run，在下個 session（下一次對話）再害你一次。所以要帶走的不是課程列的 26 種失敗、記憶從寫入到失效的 checklist，而是怎麼把錯攔下來，以及哪些事值得記。

  • 長任務靠攔錯，不靠每步都對。每步 95%，50 步全對只剩 8%；每步做完就檢查、錯了就重試一次，只要檢查都抓得到、重試和第一次一樣準，就升到 88%。實測也一樣：成功的 run 有七成途中修過錯。
  • 先找第一個出錯的步驟，在它的來源那一層修。同一個症狀有五個來源：規格、harness（跑 agent 的那層程式）、model、tool、環境。要找得到那一步，檢查就要真的抓得到，而且要早。
  • 壞的記憶比沒有記憶更糟。沒記，agent 再查一次；記錯，它照著做，下個 session 還會再犯。所以少記，記了就帶時間和來源：時間分得出哪一條過期了，來源決定兩條衝突時信誰。檢索時，過期的事實和別人的記憶看起來一樣相關，所以先依「屬於哪個使用者、專案」（scope）和「現在還成立嗎」（validity）過濾，再比 query 和記憶的語意相似度。

本文的判斷：這條算式有兩個前提，真實的 run 兩個都不成立。第一個前提是一步錯就整個 run 失敗，第二個是各步的成敗互相獨立。課程提醒真實的 run 比算式更差，因為錯誤會往後傳。2025–2026 年的量測顯示，真實的 run 有一處比算式好（第一個前提不成立），也有一處比算式差（第二個前提不成立）：

比算式好的是一步錯不等於整趟失敗。Failure as a Process（UCL 與南京大學，2026-07）逐步標註了 Terminal-Bench（在 shell 裡完成任務的 benchmark）上 21 個系統的 1,794 條 trajectory（一趟執行的完整紀錄）：成功的 run 有 71% 途中碰過至少一個錯，只有 29% 一路沒出錯。Snorkel（2026-02）的資料也類似：通過和失敗的任務，每題的錯誤數差不多（2.09 與 2.71 個），差別在修復率（95.0% 與 73.5%）。兩份都是觀察，不是對照實驗。

比算式差的是各步並不獨立：沒攔下來的錯會傳下去，越晚越難修。Recovery-Bench（Letta，2025-08）讓 agent 從之前失敗的 run 留下的環境接手，同一批 model 的平均成功率從 26.3% 掉到 11.2%。

所以算式不必丟，要換的是代入的 p：p 應該是「這一步沒有留下沒攔到的錯」的機率。換了定義，兩個前提就又站得住。第一個前提變成「留下一個沒攔到的錯，整趟就失敗」：當場攔下來重做的錯不算，這正是圖裡第二條和第三條路的差別。第二個前提：錯誤往後傳，只發生在已經留下一個沒攔到的錯之後，那時這個 run 已經算失敗了。算式要的只是「前面都沒留下錯時，這一步也沒留下錯」的機率，所以每步仍然可以乘起來。每步 5% 出錯，只要多數當場攔下來，p 就遠高於 95%，該壓低的是沒攔下來的錯。

本文延伸｜檢查會往兩個方向錯：漏抓與誤判不是 slide 的內容

本章的算式只算了檢查的一種錯。檢查拿這一步的結果做判斷：說「過」就放行，說「錯」就打回去重做。它可能往兩個方向判錯，所以一共有四種結果。下表的 p、detect 和本章開頭的意思一樣：p 是這一步第一次就做對的機率，detect 是這一步做錯時檢查抓到的機率。

英文常把這兩種錯叫 false positive 和 false negative，但哪一種叫哪個名字，要看把哪一種判定當成 positive（陽性），而兩種當法都有人用。把「檢查說錯」當 positive，就像驗出病叫陽性：漏抓是 false negative（偽陰性），誤判是 false positive（偽陽性）。評估 agent 的 grader（判斷 agent 有沒有做完任務的程式）通常反過來，把「判過」當 positive，名字就對調：沒做對卻判過，叫 false positive。L7〈Grader〉用的是後一種。為了不混淆，本文不用這兩個英文名字，直接說漏抓和誤判。

把誤判算進去。設 false_alarm 是檢查把做對的步驟判成錯的機率。打回去的步驟要重做。這裡的假設和本章的算式一樣：重做之後做對的機率是 retry_ok；重做的結果不再檢查，重做錯了就算這一步失敗。本章的算式也是這樣算的，它沒有「重試又錯、再檢查、再重試」那一項。

漏抓只會發生在做錯的步驟上，每一步只有 1 − p = 5% 的機率做錯。誤判發生在做對的步驟上，每一步有 p = 95% 的機率做對。所以誤判能碰到的步驟，是漏抓的 19 倍（95% ÷ 5%）。但兩種錯每發生一次的損失，要看 retry_ok。漏抓一次，損失的是一次修好的機會，這個機會本來有 retry_ok 的機率成功。誤判一次，那一步要在重做時改壞才算失敗，機率是 1 − retry_ok。兩邊乘起來：漏抓率每多 1 個百分點，一步的成功率就少 (1 − p) × retry_ok 個百分點；誤判率每多 1 個百分點，就少 p × (1 − retry_ok) 個百分點。重試和第一次一樣準的時候（retry_ok = p = 95%），兩個都是 5% × 95% = 0.0475：誤判碰到的步驟是 19 倍，每一次的損失卻只有漏抓的 19 分之一（5% 對 95%），剛好抵銷，傷害一樣大。重試常常還是錯的時候（retry_ok = 50%），兩種錯每一次的損失都是 50%，只剩碰到的步驟數不同，所以漏抓是 0.025、誤判是 0.475，誤判的傷害是漏抓的 19 倍。

所以檢查不是越嚴越好。把檢查調嚴，例如多跑幾種測試、或讓 reviewer 看到可疑的地方就打回去，漏抓會變少。但每多跑一個測試，就多一個可能本身寫錯、或時過時不過的測試；reviewer 打回去的「可疑」，也不一定真的錯。所以調嚴之後，誤判通常也會變多。下圖用本章的 p = 95%，比較四種檢查的 50 步全對率：

  • 本章的「檢查很準」：漏抓 0、誤判 0，理想的情況。
  • 寬鬆：漏抓 20%、誤判 0，就是本章表裡「檢查漏兩成」那一列。
  • 調嚴，少誤判：漏抓降到 1%，誤判 5%。
  • 調嚴，常誤判：漏抓降到 1%，誤判 20%。

用上一段的係數就算得出這張圖。從寬鬆調到「調嚴，少誤判」，漏抓少了 19 個百分點（20% 降到 1%），誤判多了 5 個百分點（0 升到 5%）。重試和第一次一樣準的時候，兩種錯每個百分點都讓一步的成功率少 0.0475 個百分點；漏抓少 19 個、誤判多 5 個，一步的成功率淨增約 0.67 個百分點，50 步全對率就從 55% 升到 76%。誤判多到 20% 時，多出來的誤判比少掉的漏抓還多 1 個百分點，一步的成功率反而微降，50 步全對率退回 53%，等於白調。重試常常還是錯的時候，漏抓每個百分點只值 0.025，誤判每個值 0.475：少掉 19 個百分點的漏抓，一步的成功率只多約 0.48 個百分點；多出 5 個百分點的誤判，卻少約 2.4 個百分點。一步淨少約 1.9 個百分點，50 步全對率從寬鬆的 22% 掉到 8%。所以評一個檢查要看兩個數字：漏抓多少、誤判多少，還要看重試修不修得好，因為它決定兩種錯各值多少。

實際的誤判比算式更傷。算式假設冤枉到的步驟只是重做一次，做對的機率還是 retry_ok。實際上 agent 收到的訊息是「你做錯了」，它會去修一個不存在的 bug，改壞的機率比重做一次更高。常見的來源是 flaky test：同一份程式碼有時過、有時不過的測試，例如一個依當天日期計算的測試，剛好碰到 2 月 29 日才失敗（第 10 章〈26 種 run 的失敗〉的環境那張表）。對策是先在沒改過的版本上，把同一個測試多跑幾次：沒改過的版本也會失敗，失敗就不是這一步造成的，該處理的是那個測試，不是叫 agent 改程式。更糟的是檢查本身寫錯，例如測試和規格矛盾，做對的實作永遠過不了，等於誤判率 100%。這正是本章前面 ImpossibleBench 的設定：GPT-5 在 Oneoff 有 76% 改用作弊讓測試變綠；給 agent 一個「回報給人」的出口，GPT-5 在 Conflicting 的作弊就從 54% 降到 9%。ImpossibleBench 量的是誤判率 100% 的極端情況，偶爾的誤判會不會也讓 agent 作弊，沒有量測。本文的推論是方向相同：agent 收到「錯了」卻找不到錯，能做的就只剩改程式去迎合檢查。所以誤判的代價可能不只是多一次重試。

漏抓的代價，sⁿ 也低估了。sⁿ 只回答 50 步全對的機率，不分失敗的 run 是哪一種。有的失敗至少有一次檢查說過「錯」，留下了紀錄，有人可以回頭看。漏抓的錯不一樣：那一步做錯了，檢查卻說過，當下沒有任何紀錄說它錯了。以寬鬆的檢查為例（漏抓 20%）：一步做錯的機率是 1 − p = 5%，做錯又漏抓的機率是 5% × 20% = 1%。50 步裡至少有一步漏抓的機率是 1 − 0.99⁵⁰，約 40%。重試和第一次一樣準的時候，寬鬆的檢查 50 步全對率是 55%，失敗的 run 約 45%。有漏抓的 run 一定不是全對的，所以這 40% 全部落在那 45% 裡。照這個算式推，失敗的 run 有近九成（40% ÷ 45%）至少帶著一個漏抓的錯。這些錯有的之後會露出症狀，有的不會；不會的，agent 就會當成成功交出去。本章前面引的 Failure as a Process 量到，26% 的失敗 run 宣稱自己成功，可見 agent 把失敗當成成功交出去，在實測裡並不少見。

3Checkpoint 與上限：決定失敗時退回多遠、最多花多少

驗證告訴你錯了。接下來要決定退回多遠，以及一直錯的時候什麼時候停。

退回多遠，決定要多跑多少步。第 2 章每一步都檢查，背後假設檢查不花成本。便宜的檢查（lint、型別檢查）確實可以每步跑；貴的檢查，例如跑整套測試、請另一個 agent 讀 diff，就不能每步都跑。做法是把 50 步切成幾段，每段結束時做一次貴的驗證：驗證過就存一個 checkpoint（可以退回的狀態），失敗就退回上一個 checkpoint，重跑這一段。

切成幾段最划算，要算兩筆帳。第一筆是步數。每段 k 步時，一段全對的機率是 0.95k。失敗就重跑，跑到過為止。平均要跑幾次，是全對機率的倒數：全對 60% 的段，跑 100 次約過 60 次，所以每過一次平均要跑 100 ÷ 60，約 1.7 次。一般式是 1 ÷ 0.95k 次。段越短，全對的機率越高，重跑的越少。第二筆是驗證。每跑完一次段就驗證一次，所以驗證次數是段數乘上每段平均跑幾次。這兩個數往相反方向變：段切短，段數變多，每段平均跑的次數卻變少。段很長時，每段平均跑的次數降得比段數漲得快：不分段是 1 段、平均跑 13 次，驗證 13 次；每段 25 步是 2 段、平均跑 3.6 次，驗證約 7.2 次，所以驗證次數先變少。段短到每段平均已經不到 2 次（每段 10 步時是 1.7 次），再降也有限，因為每段至少要跑 1 次，最多只能再少一半；段數卻還會翻好幾倍（每段 10 步是 5 段，每段 1 步是 50 段），驗證次數就跟著變多。這裡把一次驗證算成 5 步的成本（本文的假設：跑測試、讀輸出、存 checkpoint）。兩筆加起來是總成本，算出來的都是平均值：

同一個 run、同一個 model，只看灰色，從不分段切到每段 10 步，要跑的步數就從 650 步降到 84 步。再往下切，步數只剩每段 5 步 65、每段 2 步 55、每段 1 步 53，因為一步都不錯也要 50 步。黃色卻越來越長：每段 10 步共驗證約 8.4 次，成本 42；每段 1 步是 50 段，要驗證約 52.6 次，成本 263。兩筆加起來，每段 10 步的總成本 126（84 + 42）最省，每段 5 步是 130（65 + 65），只多 4 步。

最省的段長取決於兩個假設，圖下的兩個滑桿各管一個。第一個是驗證有多貴：一次驗證只算 1 步時，最省的從每段 10 步換成每段 5 步。驗證完全不花成本時，總成本只剩步數，最省的是每段 1 步，總成本 53 步，也就是第 2 章每一步都檢查的情況。第二個是每步多可靠：每步 95% 等於平均每 20 步錯一次。升到 99%，平均每 100 步才錯一次。切短是為了少重跑，重跑本來就少，切短省下的步數不多，驗證次數就成了主要的帳，所以少驗證幾次比較划算，最省的變成每段 25 步。降到 90%，最省的變成每段 5 步。合起來是一條規則：驗證越貴、每步越可靠，段就切得越長。這張圖還假設段尾才發現失敗。如果段中途就有便宜的檢查先抓到錯，灰色還會再短一些。

存什麼：驗證過的狀態，而且 context 也要退。Context 是這一次送進 model 的全部文字，包括對話歷史（第 5 章的註）。沒驗證就存，退回去也沒用。只退檔案也不夠：Recovery-Bench 比了三種接手方式：只給失敗後的環境、環境加一段動作摘要、環境加完整的動作歷史。帶著完整歷史的最差，因為錯的推理會繼續帶偏下一次。本文的做法是折衷：退回時不帶原本的對話，只留一句「這條路試過，為什麼失敗」。完整的對話已經量到會帶偏，什麼都不留，下一次又可能重走同一條路（本文的判斷）。

  • 只追蹤它自己的檔案編輯 tool 改的檔案。Agent 在 shell 裡跑指令改的檔案（rm、mv、會寫檔的 script）不在追蹤範圍。

上限：一直錯的時候什麼時候停。課程的例子是跑了 200 步沒有進展。Failure as a Process 也量到兩件事。第一，agent 很少自己停：失敗的 run 裡，只有 18% 在錯誤已經救不回來之後很快停下，其他的繼續做下去。第二，一次修復從出錯算到修好或放棄：修好的中位數 5 步，沒修好的中位數 12 步。修好通常很快，修了遠超過 5 步還沒好，就比典型的修好長很多，再修下去的價值變低，修太久就該停（本文的判斷；論文沒給兩組的比例）。Agent 自己不停，上限就要從外面加。上限有四種：

查閱SRE 的四個習慣：timeout、retry with backoff、circuit breaker、error budget

SRE（site reliability engineering）是 Google 提出的服務維運方法。四個習慣：

  • Timeout。一個呼叫等多久就放棄，不讓卡住的下游拖住整個系統。對應 agent 的步數與時間上限。
  • Retry with backoff。失敗後重試，每次等更久（1 秒、2 秒、4 秒），避免許多呼叫端同時重試，壓垮同一個下游。對應第 2 章的重試：檢查抓到錯就重做這一步。Backoff 在 agent 這邊少用：agent 的錯多半不是下游太忙，等久一點也不會變對（本文的判斷）。
  • Circuit breaker。連續失敗到門檻就斷路，一段時間內直接回錯，讓下游有機會恢復。對應「沒有進展就停」。
  • Error budget。先定可接受的失敗率（例如一個月 0.1%），沒用完就可以冒險發版，用完就只修不加。對應花費上限：先定一個 run 可以花多少，用完就停。

4失敗分層：同一個症狀有五個來源，在來源那一層修

知道會出錯之後，下一個問題是錯從哪裡來。同一句「agent 說測試過了，但測試沒過」，至少有五種解釋，來自五層（harness 與 tool 是 L2、L4 講過的兩層）：

前情Harness 與 tool：五層裡 model 以外的兩層是什麼

Harness 是包在 model 外面的那層程式，例如 Claude Code 這個 CLI：它組 context 送進 model、讀 model 的回覆、執行 model 要的 tool call、把結果放回 context。Tool 是 harness 給 model 的動作：讀檔、grep、edit、跑 shell。Model 只輸出一段 JSON 說要呼叫哪個，執行的是 harness。

所以「harness 的 context 截斷」是 harness 為了騰出 context，砍掉最舊的幾輪對話，或把太長的 tool 輸出砍短，錯誤訊息跟著不見；「tool 的靜默失敗」是 tool 失敗了卻回一個看起來正常的結果。看到輸出不完整，先問是誰砍的：harness 組 context 時砍的算 harness，tool 自己只回前 100 行算 tool（第 10 章的表）。L4〈Tool 設計〉講怎麼修這兩層。

前情Context 與它的代價（L4）：每一條記憶都要每圈重送

Context 是每一次送進 model 的全部文字：system prompt、tool 定義、對話歷史、tool 結果，上限叫 context window。L4〈Context 的成本〉講過三種代價：

  • 錢。每一圈整份重送，一條 2,000 token 的記憶 50 圈就是 100,000 token。
  • 延遲。Prompt 越長，prefill（model 開始回答前先讀完整個 prompt 的階段）越久。
  • 注意力。Window 越滿，model 越難找回中間的資訊。

L4〈Context 管理〉的四種策略，在 memory 上一樣適用：

  • Admission，在門口把關。不是每條記憶都讀進來，先過濾再取 top-k（第 7 章）。
  • Offloading，放在外面，要用再讀。常駐只放索引，細節要用再讀（第 8 章的 MEMORY.md）。
  • Transformation，用規則刪掉舊的。過期的記憶標成失效，不再讀進來（第 6 章）。
  • Compaction，讓 LLM 寫摘要。把好幾條合成一條，會丟資訊，也可能把推測寫成事實（第 6 章）。

7檢索：語意相似只是五個訊號之一

Store 裡的東西要經過檢索才回到 context，所以檢索決定 model 看到什麼。最常見的做法是 vector search：把問題和每條記憶都轉成向量，取最近的 k 條。先看它會怎麼錯：

前情Embedding 與 vector search（L4）：top-k 是怎麼算出來的

Embedding model 把一段文字轉成一串數字，也就是向量。意思相近的文字，向量也相近。建索引時每條記憶算一個向量存起來；查詢時把 query 也轉成向量，找出距離最近的 k 筆，這就是 top-k。L4〈Embedding 與 semantic search〉用它找程式碼，這裡用它找記憶，機制相同。

相似度量的是「意思像不像」。哪一條是現在的、是誰的、誰說的，都不在文字的意思裡，所以要在寫入時存成欄位（第 6 章）。

五個訊號，放在不同的位置。語意相似只是其中一個：

訊號問什麼放哪裡缺了會怎樣
Semantic match意思和 query 相近嗎排序找不到相關的（retrieval miss）
Scope同一個使用者、專案、任務嗎硬過濾別人的記憶跨界進來（isolation failure）
Validity此刻、對這個任務還成立嗎硬過濾舊事實和新事實並列（staleness）
Importance漏掉或放進來，代價多大調分數或常駐關鍵規則漏掉；無關的塞滿 context（context pollution）
Provenance誰說的、信心多少、證據在哪調分數把推測當成事實（memory hallucination）

    跟這堂課的關係

    Slides p.5 的兩層就是這篇的主記憶體與外部儲存，見〈要不要記：壞的記憶比沒有記憶更糟〉。p.10 列的「由 model 呼叫 tool 觸發檢索」，MemGPT 是早期的完整實作。一處差異：slides 把搬運交給 harness 的 policy；MemGPT 把寫入、搜尋、摘要都交給 model 決定，harness 只在 token 到門檻時發警告。

    壓縮後的重點

    1. 主 context 分三塊。System instructions 唯讀，說明記憶階層與可用的 function。Working context 是固定大小的可讀寫文字塊，放關鍵事實，只能用 function call 修改。FIFO queue 是滾動的訊息歷史，第一則是驅逐訊息的遞迴摘要。
    2. 外部 context 分兩層。Recall storage 存完整的訊息歷史，可搜尋。Archival storage 存任意長度的文字物件，可讀寫。兩層的內容都要經由 function call 才會進入主 context。
    3. Queue manager 用兩個門檻管理溢出。Prompt token 超過警告門檻（例如 window 的 70%），插入一則 memory pressure 訊息，提醒 model 把重要內容存起來。到達 flush 門檻（例如 100%）時，驅逐一批訊息（例如 window 的 50%），更新遞迴摘要。驅逐的訊息仍在 recall storage。
    4. Heartbeat 讓 model 串接多步檢索。Function 帶 request_heartbeat=true 時，執行完立刻把控制權交回 model，它可以繼續呼叫下一個 function。沒有這個旗標，系統等待下一個外部事件。
    5. 跨 session 的記憶回想，準確度從 32.1% 升到 92.5%。Deep memory retrieval 任務上，GPT-4 基線 32.1%，加 MemGPT 92.5%；GPT-4 Turbo 從 35.3% 升到 93.4%。基線只看到歷史的有損摘要，MemGPT 能搜尋完整歷史。
    6. 多文件 QA 的準確度不隨文件數下降。檢索的文件數從 0 到 200，MemGPT 配 GPT-4 與 GPT-4 Turbo 都穩定。基線要截斷文件才塞得進 window，漏掉關鍵片段的機率隨之上升。配 GPT-3.5 的 MemGPT 變差，因為它的 function call 能力較弱。
    7. 巢狀 key-value 檢索測多跳查詢。140 組 UUID（約 8k token），值可以是另一個 key。基線 GPT-4 在 3 層巢狀時掉到 0%；MemGPT 配 GPT-4 在各層都穩定。

    • 可以跳過：Section 1 Introduction 的長 context 動機（slides p.5 已講）；Section 4 Related Work；附錄的 prompt 全文。
    • 值得看原文：Section 2 的架構圖（Figure 1–3），看三塊主 context 與兩層外部儲存怎麼接；Section 2.2 Queue Manager 的兩個門檻；Table 2 的 DMR 數字；Section 3.2.2 的巢狀 KV 曲線。
