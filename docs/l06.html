先看這裡

這堂講可靠性和 memory 兩半，講的是同一件事：agent 會出錯，錯誤會累積。一個 run（agent 從接到任務到停下來的一次執行）裡，錯誤逐步相乘；有了 memory，錯誤還能活過這個 run，在下個 session（下一次對話）再害你一次。所以要帶走的不是課程列的 26 種失敗、記憶從寫入到失效的 checklist，而是怎麼把錯攔下來，以及哪些事值得記。

  • 長任務靠攔錯，不靠每步都對。每步 95%，50 步全對只剩 8%；每步做完就檢查、錯了就重試一次，只要檢查都抓得到、重試和第一次一樣準，就升到 88%。實測也一樣：成功的 run 有七成途中修過錯。
  • 先找第一個出錯的步驟，在它的來源那一層修。同一個症狀有五個來源：規格、harness（跑 agent 的那層程式）、model、tool、環境。要找得到那一步，檢查就要真的抓得到，而且要早。
  • 壞的記憶比沒有記憶更糟。沒記，agent 再查一次；記錯，它照著做，下個 session 還會再犯。所以少記，記了就帶時間和來源：時間分得出哪一條過期了，來源決定兩條衝突時信誰。檢索時，過期的事實和別人的記憶看起來一樣相關，所以先依「屬於哪個使用者、專案」（scope）和「現在還成立嗎」（validity）過濾，再比 query 和記憶的語意相似度。

1錯誤相乘：每步 95%，50 步只剩 8%

本文的判斷：這條算式有兩個前提，真實的 run 兩個都不成立。第一個前提是一步錯就整個 run 失敗，第二個是各步的成敗互相獨立。課程提醒真實的 run 比算式更差，因為錯誤會往後傳。2025–2026 年的量測顯示，真實的 run 有一處比算式好（第一個前提不成立），也有一處比算式差（第二個前提不成立）：

比算式好的是一步錯不等於整趟失敗。Failure as a Process（UCL 與南京大學，2026-07）逐步標註了 Terminal-Bench（在 shell 裡完成任務的 benchmark）上 21 個系統的 1,794 條 trajectory（一趟執行的完整紀錄）：成功的 run 有 71% 途中碰過至少一個錯，只有 29% 一路沒出錯。Snorkel（2026-02）的資料也類似：通過和失敗的任務，每題的錯誤數差不多（2.09 與 2.71 個），差別在修復率（95.0% 與 73.5%）。兩份都是觀察，不是對照實驗。

比算式差的是各步並不獨立：沒攔下來的錯會傳下去，越晚越難修。Recovery-Bench（Letta，2025-08）讓 agent 從之前失敗的 run 留下的環境接手，同一批 model 的平均成功率從 26.3% 掉到 11.2%。

所以算式不必丟，要換的是代入的 p：p 應該是「這一步沒有留下沒攔到的錯」的機率。換了定義，兩個前提就又站得住。第一個前提變成「留下一個沒攔到的錯，整趟就失敗」：當場攔下來重做的錯不算，這正是圖裡第二條和第三條路的差別。第二個前提：錯誤往後傳，只發生在已經留下一個沒攔到的錯之後，那時這個 run 已經算失敗了。算式要的只是「前面都沒留下錯時，這一步也沒留下錯」的機率，所以每步仍然可以乘起來。每步 5% 出錯，只要多數當場攔下來，p 就遠高於 95%，該壓低的是沒攔下來的錯。

存什麼：驗證過的狀態，而且 context 也要退。Context 是這一次送進 model 的全部文字，包括對話歷史（第 5 章的註）。沒驗證就存，退回去也沒用。只退檔案也不夠：Recovery-Bench 比了三種接手方式：只給失敗後的環境、環境加一段動作摘要、環境加完整的動作歷史。帶著完整歷史的最差，因為錯的推理會繼續帶偏下一次。本文的做法是折衷：退回時不帶原本的對話，只留一句「這條路試過，為什麼失敗」。完整的對話已經量到會帶偏，什麼都不留，下一次又可能重走同一條路（本文的判斷）。

工具能不能替你退？Claude Code 的 /rewind 能同時退 code 和對話，但有三個限制（2026-11 的官方文件）：

  • 你送出 prompt 時才存一個點。一個 prompt 讓 agent 自己跑幾十步的長任務，中間沒有點可以退，只能退回開頭。
  • 只追蹤它自己的檔案編輯 tool 改的檔案。Agent 在 shell 裡跑指令改的檔案（rm、mv、會寫檔的 script）不在追蹤範圍。
  • Subagent 改的檔案多半也不還原。Subagent 是主 agent 派出去做子任務的另一個 agent。

Git 沒有這三個限制。Commit 的時機由你決定，每段驗證過就存一個點；它記的是 repo 裡追蹤中的每個檔案，不管是 agent 的編輯 tool、shell 指令還是 subagent 改的，退回時一起退（.gitignore 排除的、還沒 add 過的新檔不在內）。但 git 只退檔案，context 要另外退：開一個新的 session 從退回的版本接著做，只帶上一句「這條路試過，為什麼失敗」，也就是上面的折衷。所以長任務的 checkpoint 用 git，每段驗證過就 commit 一次：

回不去的動作。Checkpoint 只退得了自己的檔案。付款、刪資料、對外發信，退不回來，也不能靠重試，要在發生之前把關。做法是由 harness 在執行前比對 allowlist（事先列好、可以自動執行的動作清單），不在清單上的就請人確認（L2〈權限〉）；或把環境切開，讓 agent 碰不到正式環境。Replit 2025 年的事故是例子：agent 在 code freeze 期間刪了 production 資料庫，Replit 事後推出 dev、prod 資料庫自動分離（單一案例，依當事人的說法）。

查閱SRE 的四個習慣：timeout、retry with backoff、circuit breaker、error budget

SRE（site reliability engineering）是 Google 提出的服務維運方法。四個習慣：

  • Timeout。一個呼叫等多久就放棄，不讓卡住的下游拖住整個系統。對應 agent 的步數與時間上限。
  • Retry with backoff。失敗後重試，每次等更久（1 秒、2 秒、4 秒），避免大家同時重試壓垮下游。對應 tool 失敗先重試再下結論。
  • Circuit breaker。連續失敗到門檻就斷路，一段時間內直接回錯，讓下游有機會恢復。對應「沒有進展就停」。
  • Error budget。先定可接受的失敗率（例如一個月 0.1%），沒用完就可以冒險發版，用完就只修不加。對應每種任務有可接受的失敗率。

4失敗分層：同一個症狀有五個來源，在來源那一層修

知道會出錯之後，下一個問題是錯從哪裡來。同一句「agent 說測試過了，但測試沒過」，至少有五種解釋，來自五層（harness 與 tool 是 L2、L4 講過的兩層）：

前情Harness 與 tool：五層裡 model 以外的兩層是什麼

Harness 是包在 model 外面的那層程式，例如 Claude Code 這個 CLI：它組 context 送進 model、讀 model 的回覆、執行 model 要的 tool call、把結果放回 context。Tool 是 harness 給 model 的動作：讀檔、grep、edit、跑 shell。Model 只輸出一段 JSON 說要呼叫哪個，執行的是 harness。

所以「harness 的 context 截斷」是 harness 為了騰出 context，砍掉最舊的幾輪對話，或把太長的 tool 輸出砍短，錯誤訊息跟著不見；「tool 的靜默失敗」是 tool 失敗了卻回一個看起來正常的結果。看到輸出不完整，先問是誰砍的：harness 組 context 時砍的算 harness，tool 自己只回前 100 行算 tool（第 10 章的表）。L4〈Tool 設計〉講怎麼修這兩層。

前情Context 與它的代價（L4）：每一條記憶都要每圈重送

Context 是每一次送進 model 的全部文字：system prompt、tool 定義、對話歷史、tool 結果，上限叫 context window。L4〈Context 的成本〉講過三種代價：

  • 錢。每一圈整份重送，一條 2,000 token 的記憶 50 圈就是 100,000 token。
  • 延遲。Prompt 越長，prefill（model 開始回答前先讀完整個 prompt 的階段）越久。
  • 注意力。Window 越滿，model 越難找回中間的資訊。

  • Admission，在門口把關。不是每條記憶都讀進來，先過濾再取 top-k（第 7 章）。
  • Offloading，放在外面，要用再讀。常駐只放索引，細節要用再讀（第 8 章的 MEMORY.md）。
  • Transformation，用規則刪掉舊的。過期的記憶標成失效，不再讀進來（第 6 章）。
  • Compaction，讓 LLM 寫摘要。把好幾條合成一條，會丟資訊，也可能把推測寫成事實（第 6 章）。

前情Embedding 與 vector search（L4）：top-k 是怎麼算出來的

Embedding model 把一段文字轉成一串數字，也就是向量。意思相近的文字，向量也相近。建索引時每條記憶算一個向量存起來；查詢時把 query 也轉成向量，找出距離最近的 k 筆，這就是 top-k。L4〈Embedding 與 semantic search〉用它找程式碼，這裡用它找記憶，機制相同。

相似度量的是「意思像不像」。哪一條是現在的、是誰的、誰說的，都不在文字的意思裡，所以要在寫入時存成欄位（第 6 章）。

五個訊號，放在不同的位置。語意相似只是其中一個：

訊號問什麼放哪裡缺了會怎樣
Semantic match意思和 query 相近嗎排序找不到相關的（retrieval miss）
Scope同一個使用者、專案、任務嗎硬過濾別人的記憶跨界進來（isolation failure）
Validity此刻、對這個任務還成立嗎硬過濾舊事實和新事實並列（staleness）

  • 版本免費。進 git 就有歷史，也能 diff，第 9 章的偵測要靠這個。
  • Policy 才是難的部分。換 backend 不會替你決定該記什麼。

值得離開檔案的情況有三種：多個 agent 要共用、要依使用者隔離、要查「什麼時候變的」或「連到誰」。第一種的原因是本機檔案只在一台機器上，另一台機器、另一個 container 裡的 agent 讀不到。第二種的原因是檔案的權限只認得作業系統的帳號，不認得你服務裡的使用者，要隔離就得自己另寫一層檢查。第三種要的是時間和關聯的查詢，這是 graph database 的長處（上面的 backend 圖）。

Anthropic 自己的兩個產品，剛好落在這條分界的兩邊。Claude Code 的每個 session 都在同一台開發者的電腦上跑，所以本機檔案就跨得了 session（查閱它的每個決定）。Managed Agents 的 session 跑在雲端，執行 code 的 sandbox 要用時才配一個（L8〈Harness 架構〉），寫在 sandbox 裡的檔案留不到下一個 session，也給不了同時在跑的其他 session。所以它換成託管的 store，但仍掛載成目錄，agent 用同一套檔案工具（這兩個產品的對照是本文的判斷）。

  1. 第 1、2 章 · 錯誤相乘與驗證

    每步 95%，50 步全對約多少？這條算式少算了什麼？多一次檢查與重試，數字怎麼變？

    參考答案與重點複習

    答案：約 8%（0.95⁵⁰ ≈ 7.7%），約 13 次才有 1 次全對（第 1 章）。

    算式假設一步錯就整個 run 失敗，少算了「錯了還能修」：實測裡成功的 run 有 71% 途中碰過錯。所以該算的是沒攔下來的錯。每步多一次檢查與重試，檢查很準時，一步的成功率變成 99.75%，50 步全對升到 88%（第 2 章）。

    重點拆解

    一個 run 是一條串起來的鏈。每步成功的機率是 p，互不影響時，n 步全對就是 p 自乘 n 次。它是指數衰減，不是直線下降：約 13.5 步就只剩一半。

    第 2 章的算式把「當場攔錯」放進來：s = p + (1 − p) × detect × retry_ok。第一次就對，或第一次錯、檢查抓到、重試成功，這一步都算過。所以 detect 和 retry_ok 都要高：檢查漏兩成，50 步就掉到 55%；重試常常還是錯，就掉到 28%。

    檢查還要真的抓得到。Model 說「應該會過了」不算檢查，要 tool 的輸出。Agent 評自己的成果會偏正面，測試可以改的話它會去改測試。檢查也要早：決定失敗的錯誤，中位數在第 7 步；第一個看得到的症狀，要到約第 16 步。

    背景補充

    這是可靠性工程的串聯系統：每個元件都要正常，系統才正常，整體可靠度等於各元件相乘（Lusser's law）。微服務也一樣：一個請求依序經過 10 個 99.9% 可用的服務，整體約 99.0%。

    心算捷徑：每步失敗率 ε 很小時，(1 − ε)ⁿ ≈ e^(−nε)。nε 是一個 run 平均出幾個錯。50 × 0.05 = 2.5 個錯，e^(−2.5) ≈ 0.082，和 7.7% 很接近。所以要控制的是一個 run 平均留下幾個沒攔到的錯。

    常見誤解

    「每步 95%，所以 50 步的任務只有 8% 會成功。」8% 是一步錯就整趟失敗時的算法。真實的 agent 會修錯，所以成功率可以遠高於它；但 model 的單步準確率也不能直接當成任務的成功率。要看錯誤有多少沒攔下來。

    帶走這幾點
    1. 每步都要對 → 0.95ⁿ 指數衰減 → 50 步只剩 7.7%。
    2. 真實的 run 會修錯，也會傳錯 → 該壓低的是沒攔下來的錯。
    3. 檢查加重試 → 8% 變 88%；檢查要真、要早，否則效果打對折。

    相關：核心觀念〈錯誤相乘：每步 95%，50 步只剩 8%〉、〈驗證：model 沒變強，8% 也能變 88%〉；L1〈長時間的 agent run 需要可靠性工程〉、L7〈pass^k〉。第 3 段動手試試的 compound.py 可以驗算。

  2. 第 3、4 章 · Checkpoint 與失敗分層

    為什麼每 10 步存 checkpoint，650 步會變 84 步？失敗分哪 5 層？為什麼要先找第一個出錯的步驟？

    參考答案與重點複習

    答案：不分段時，全對只有 7.7%，平均要跑 13 次，每次 50 步，約 650 步。每 10 步驗證並存 checkpoint，失敗只重跑一段：每段全對 60%，平均跑 1.7 次，五段合計約 84 步（第 3 章）。

    5 層是任務規格、harness、model、tool、環境（第 4 章）。同一個症狀可能來自任何一層，修法完全不同，所以要找第一個輸出和輸入對不上的步驟，在那一層修。

    重點拆解

    Checkpoint 決定失敗時退回多遠。要存驗證過的狀態，沒驗證就存，退回去也沒用。退回時 context 也要清，只留一句「這條路試過，為什麼失敗」，因為錯的推理會繼續帶偏下一次。

    Checkpoint 只退得了自己的檔案。付款、刪資料、對外發信退不回來，要在發生之前把關。一直錯的時候也要停：步數、花費、時間三個上限之外，再加一條「沒有進展就停」，因為失敗的修復中位數跑 12 步，成功的只要 5 步。

    分層的理由來自症狀。「agent 說測試過了，但測試沒過」可能是規格沒說要跑、harness 截掉了錯誤輸出、model 沒跑就宣布、tool 失敗卻回 exit 0，或環境是昨天的 build。每一種情況下 agent 都沒有報錯，它只是照著錯的輸入做下去。五層各一條原則：把「完成」寫成測試、每個 run 都有上限、要求證據、失敗要大聲、固定並隔離。

    背景補充

    這些原則和 SRE 的習慣對得上。步數與時間上限就是 timeout；「沒有進展就停」和 circuit breaker 的精神一樣；checkpoint 與回滾像資料庫的 transaction：失敗時回到上一個一致的狀態。

    Claude Code 的 -p 模式有 --max-turns 與 --max-budget-usd，時間上限用外層的 timeout 指令。/rewind 可以退回檔案和對話，但只有 Bash 改過的檔案不追蹤（依 2026-11 的官方文件），所以長任務用 git commit。

    常見誤解

    「Agent 失敗了，換一個更強的 model 就好。」更強的 model 只處理其中一層。規則在 compaction 時丟掉、tool 把錯誤包成空結果、環境版本不一樣，換 model 之後一樣會發生。

    帶走這幾點
    1. Checkpoint 存驗證過的狀態 → 失敗只重跑一段 → 650 步變 84 步。
    2. 回不去的動作要事前把關；一直錯就停，不要再診斷下去。
    3. 同一個症狀有 5 個來源 → 先找第一個出錯的步驟 → 在那一層修。

    相關：核心觀念〈Checkpoint 與上限〉、〈失敗分層：同一個症狀有五個來源，在來源那一層修〉；L3〈終點：自主程度由能不能驗證決定〉、L5〈Partial failure〉。第 3 段動手試試有一組 run 預算的設定。進階題第 2 題把 5 個事故歸層。

  3. 第 5 章 · 要不要記

    該記沒記和記錯，代價差在哪裡？哪些事不該記？記了的事，用之前要做什麼？

    參考答案與重點複習

    答案：該記沒記，agent 再查一次或問一次，多花幾步，而且看得到。記錯或過期，agent 當成事實照做，沒有人報錯，下個 session 還會再犯。所以壞的記憶比沒有記憶更糟。

    能重讀的事不要記，例如路徑、架構、程式碼和 git 讀得到的事。記了的事，用之前再確認一次。

    重點拆解

    Model 沒有狀態，agent 記得的事都是 harness 搬進 context 的。Memory 是一份跨 session 的副本：來源改了，沒有人通知它。這和 L5 講的「context 是會過期的副本」是同一件事，只是時間拉長了。

    SWE-ContextBench 量到了這個不對稱。沒有記憶解出 26.26%；給對的前例摘要解出 34.34%；讓 agent 自己挑摘要，只有 22.22%，因為它只有 36.36% 挑到對的前例。這是 99 題的結果，要當成方向。

    寫入 policy 是一條光譜：一端每次互動都寫，recall 最高，雜訊也最多；另一端只在使用者要求時寫，precision 最高，但漏最多。中間有定期 LLM 回顧、小 classifier、確定性的規則。因為記錯的代價比較高，本文建議預設往選擇性那一端靠，再用量測決定要不要往回移。

    背景補充

    Context window 和 memory store 的關係像 RAM 和 disk：CPU 只能直接讀 RAM，disk 上的資料要先載入。MemGPT（2023）把這個類比做成系統，讓 model 自己用 function call 在兩層之間搬資料。

    記憶也是一種 cache，而 cache 最難的是失效。一般的 cache 至少知道來源在哪裡，可以設 TTL 或監聽變更；記憶常常只有一句話，連來源都沒留，這是第 6 章要補的。

    常見誤解

    「Context window 夠大，就不需要 memory；記得越多，agent 越聰明。」Context window 只活在這一個 session，而且越長越貴、越慢。記憶多也不等於好：每一條都要每圈重送，無關或過期的還會把 agent 帶偏。

    帶走這幾點
    1. 記錯比沒記貴 → 沒記看得到、代價是幾步；記錯安靜、每個 session 重來。
    2. 能重讀的不記 → 副本會過期，重讀只要一個 tool call。
    3. 記憶當線索，不當事實 → 用之前先確認。

    相關：核心觀念〈要不要記：壞的記憶比沒有記憶更糟〉；L2〈記憶〉與〈Auto memory 與記憶的成本〉、L5〈狀態與時間〉。進階題第 1 題會替 coding agent 設計寫入 policy。

  4. 第 6、7 章 · 時間、來源與檢索

    問「現在用哪個 engine」，只靠 vector search 會怎樣？valid time 和 provenance 各記什麼？哪兩個訊號要硬過濾？

    參考答案與重點複習

    答案：「用 vLLM」和「用 SGLang」都在講 serving engine，相似度幾乎一樣，可能拿到舊的，或兩條都拿回來讓 model 猜（第 7 章）。

    Valid time 記這個事實在哪段時間成立，provenance 記它從哪裡來（第 6 章）。Scope 和 validity 要當硬過濾，在 vector search 之前就排除。

    重點拆解

    Vector search 只回答「意思像不像」。它不知道這筆屬於誰、現在還對不對、從哪裡來。這些資訊不在文字的意思裡，要在寫入時存成欄位，而且沒存就補不回來。

    訊號它問什麼放哪裡缺了它
    Scope是同一個使用者、專案、任務嗎？硬過濾Isolation failure：別人的記憶跨界進來
    Validity此刻、對這個任務還成立嗎？硬過濾Staleness：舊事實和新事實並列
    Importance漏掉或放進來，代價多大？調分數或常駐Retrieval miss：關鍵規則沒取回；context pollution
    Provenance誰說的？信心多少？證據在哪？調分數Memory hallucination：推測當成事實

    事實改變時，關上舊事實的 valid_to，紀錄留著。這樣「現在用什麼」和「5 月用什麼」都答得出來。來源決定信任等級：使用者親口說的，和網頁上讀到的，不該同等對待，衝突時依來源排序，不依新舊。歸納也要帶 evidence，才能查證、撤回，也才能在原始紀錄刪除時找到它。

    背景補充

    Valid time 是資料庫的老概念。Bitemporal 資料模型有兩條時間軸：valid time 是事實在真實世界成立的時間；transaction time 是系統記下它的時間。SQL:2011 標準把 temporal table 納入規格。Graphiti 把同一個想法用在 agent memory 上。

    Provenance 對應資料工程的 data lineage：每一筆資料都能追到來源。對 agent 來說，它也是防 persistent prompt injection 的基礎（下一題）。

    常見誤解

    「新事實來了，把舊的刪掉就好。」刪掉之後，系統答不出「以前用什麼」，也查不到是誰、在什麼時候改的。新的一筆如果是錯的，也沒有舊值可以還原。永久刪除留給隱私這類資料必須真的消失的情況，而且要連鎖刪掉推出來的東西。

    帶走這幾點
    1. Vector search 只量意思像不像 → 分不出現在的、誰的、誰說的。
    2. 時間和來源寫入時就要存 → 事後補不回來。
    3. Scope、validity 放 WHERE → 不合的記憶相似度再高也進不了 top-k。

    相關：核心觀念〈時間與來源：寫入時沒存，之後補不回來〉、〈檢索：語意相似只是五個訊號之一〉；名詞註〈Embedding 與 vector search〉、〈TTL 與 eviction〉；L4〈Embedding 與 semantic search〉。第 3 段動手試試有一筆帶 valid time 的 JSON 記錄。

  5. 第 8、9 章 · 放在哪裡與記憶中毒

    什麼情況才值得離開檔案，換成獨立的 memory layer？一般的 injection 和寫進記憶的 injection 差在哪裡？

    參考答案與重點複習

    答案：多個 agent 要共用、要依使用者隔離、要查「什麼時候變的」或「連到誰」時，才值得換（第 8 章）。其他情況先用檔案，因為人看得懂、改得動，記錯時才抓得到。

    一般的 injection 只活在一個 session；寫進記憶之後，它在之後每個 session 都回來一次，以「你的筆記」的身分（第 9 章）。

    重點拆解

    選型不要看分數。Letta 只用檔案和 grep，在 LoCoMo 拿到 74.0%，高於 Mem0 當時自報的 68.5%；Mem0 後來換演算法，自報 91.6。各家自報、設定不同，分數不能當依據，要自己做一組測試：該取回的、不該出現的、別人的。

    進去的路常常不像寫入。Unit 42 的概念驗證裡，網頁的隱藏指令進了 session 摘要，摘要自動進 memory。Microsoft 看到「Summarize with AI」按鈕的網址預填 prompt，叫助理記住某家公司是可信來源。Cisco 的案例裡，npm 套件直接覆寫 MEMORY.md。

    防線要每一站一道，至少一道不靠 model 判斷。寫入時，外部內容不自動進 store。儲存時，每條帶來源。讀回來時當資料，不放進 system prompt。動作時，危險動作由 hook 或 allowlist 擋，不看記憶寫什麼。

    背景補充

    Persistent prompt injection 很像 web 安全的 stored XSS。Reflected XSS 只影響點了惡意連結的那一次請求；stored XSS 把惡意腳本存進資料庫，之後每個讀到那一頁的人都會中招。OWASP 的 agentic 應用十大風險把 Memory & Context Poisoning 列為 ASI06。

    選擇 ownership 也是選擇怎麼稽核。純文字檔可以放進 git，每一次寫入都有紀錄。Dedicated 服務能跨 agent 共用、能做過濾查詢，代價是多一個要維運的服務，也要做好 scope 隔離。

    常見誤解

    「Memory 是 agent 自己寫的，所以可以信任。」Agent 寫下的，是它讀到的東西。它讀過網頁、README、tool 輸出，這些內容可能進了 memory。如果沒有記錄來源，下次讀回來時，已經分不出哪一句來自使用者、哪一句來自外部。

    帶走這幾點
    1. 先用檔案 → 共用、隔離、時間與關係查詢才值得換；分數不能當依據。
    2. 一般 injection 隨 session 結束消失；寫進 memory → 每個 session 再生效一次。
    3. 防線每站一道 → 動作這一站用確定性的 hook，不管記憶是否中毒都有效。

    相關：核心觀念〈放在哪裡：先用檔案，分數自己量〉、〈安全：記憶讓 injection 活過一個 session〉；L2〈記憶也是攻擊面〉、L2〈Prompt injection〉、L5〈安全〉。進階題第 3 題會畫出完整的攻擊路徑，並在每一站設計防線。

    跟這堂課的關係

    Slides p.5 的兩層就是這篇的主記憶體與外部儲存，見〈要不要記：壞的記憶比沒有記憶更糟〉。p.10 列的「由 model 呼叫 tool 觸發檢索」，MemGPT 是早期的完整實作。一處差異：slides 把搬運交給 harness 的 policy；MemGPT 把寫入、搜尋、摘要都交給 model 決定，harness 只在 token 到門檻時發警告。

    壓縮後的重點

    1. 主 context 分三塊。System instructions 唯讀，說明記憶階層與可用的 function。Working context 是固定大小的可讀寫文字塊，放關鍵事實，只能用 function call 修改。FIFO queue 是滾動的訊息歷史，第一則是驅逐訊息的遞迴摘要。
    2. 外部 context 分兩層。Recall storage 存完整的訊息歷史，可搜尋。Archival storage 存任意長度的文字物件，可讀寫。兩層的內容都要經由 function call 才會進入主 context。
    3. Queue manager 用兩個門檻管理溢出。Prompt token 超過警告門檻（例如 window 的 70%），插入一則 memory pressure 訊息，提醒 model 把重要內容存起來。到達 flush 門檻（例如 100%）時，驅逐一批訊息（例如 window 的 50%），更新遞迴摘要。驅逐的訊息仍在 recall storage。
    4. Heartbeat 讓 model 串接多步檢索。Function 帶 request_heartbeat=true 時，執行完立刻把控制權交回 model，它可以繼續呼叫下一個 function。沒有這個旗標，系統等待下一個外部事件。
    5. 跨 session 的記憶回想，準確度從 32.1% 升到 92.5%。Deep memory retrieval 任務上，GPT-4 基線 32.1%，加 MemGPT 92.5%；GPT-4 Turbo 從 35.3% 升到 93.4%。基線只看到歷史的有損摘要，MemGPT 能搜尋完整歷史。
    6. 多文件 QA 的準確度不隨文件數下降。檢索的文件數從 0 到 200，MemGPT 配 GPT-4 與 GPT-4 Turbo 都穩定。基線要截斷文件才塞得進 window，漏掉關鍵片段的機率隨之上升。配 GPT-3.5 的 MemGPT 變差，因為它的 function call 能力較弱。

    一句話：這篇提出 AgentErrorTaxonomy（5 個模組、17 種錯誤）、AgentErrorBench（200 條逐步標註的失敗 trajectory）和 AgentDebug。AgentDebug 找出最早的關鍵錯誤，給回饋後從那一步重跑；ALFWorld 上成功率最高從 60% 升到 84%。

    跟這堂課的關係

    Slides p.30 說除錯要先找第一個出錯的步驟，見〈失敗分層：同一個症狀有五個來源，在來源那一層修〉；這篇把它定義成 critical error，並做成 benchmark。分法不同：slides 依來源分 5 層，這篇依 agent 內部的模組分 5 個，規格層在這篇沒有對應。Memory 模組的 3 種錯誤對應 p.18 的 retrieval miss 與 memory hallucination，見〈時間與來源：寫入時沒存，之後補不回來〉。它的 error propagation 分析是 p.22 錯誤相乘的實例，見〈錯誤相乘：每步 95%，50 步只剩 8%〉；這種分析要有每一步的紀錄，呼應〈沒有紀錄，就不知道該改什麼〉。

    壓縮後的重點

    1. 錯誤依 agent 的模組分類：5 個模組、17 種。Memory 3 種：摘要過度簡化、假記憶、檢索失敗。Reflection 4 種：進度誤判、結果誤讀、歸因錯誤、幻覺。Planning 3 種：忽略限制、不可能的動作、低效計畫。Action 3 種：計畫與動作脫節、格式錯誤、參數錯誤。System 4 種：步數用盡、tool 錯誤、LLM 限制、環境錯誤。分類來自 3 個環境超過 500 條失敗 trajectory 的人工分析。
    2. Critical error 是最早的那一步：修好它，任務就會成功。標註員只找最小的 root-cause 集合，不標每個表面錯誤。Benchmark 有 200 條：ALFWorld 100、WebShop 50、GAIA 50。10 位研究生逐步標註，Cohen's κ = 0.55。
    3. 關鍵錯誤多在中段，planning 模組最多。第 6–10 步最多（48 條）。依模組看，planning 78、reflection 39、memory 38、action 22、system 22。作者的解讀：memory 與 reflection 的錯誤最會往後傳，記錯一件事，後面的計畫就整個歪掉。
    4. AgentDebug 分 3 階段。先用 taxonomy 逐步標錯誤；再用 counterfactual 推理找最早的關鍵錯誤；最後產生附錯誤類型與修正建議的回饋，從那一步重跑，最多 5 次。重跑不從頭開始，省下前段的計算。
    5. 找關鍵錯誤：step accuracy 45.0%，全對 24.3%。Debugger 用 GPT-4.1。最強的基線 Direct Prompting 是 28.0% 與 0.3%。全對要同時答對步數、模組、錯誤類型。GAIA 最高：58.0% 與 38.0%。
    6. 重跑後 ALFWorld 成功率大幅上升，弱 model 升最多。5 次嘗試後，GPT-4o-mini 從 21% 到 55%，Qwen3-8B 從 48% 到 74%，Qwen3-Next-80B 從 60% 到 84%。摘要的「最多 26% 相對提升」是和 Self-Refine、Best-of-N 比，嘗試預算按總 token 用量對齊。
    7. Debugger 要夠強。換 Llama-3.3-70B、GPT-4o-mini 或 Qwen3-Next-80B 當 debugger，step accuracy 都在 16% 以下；GPT-4.1 是 42%。

    原文怎麼讀

    • 可以跳過：Section 1 的 cascading failure 動機（slides p.22 已講）；Section 3.1；Section 6 Related Work；附錄 A.5 的 prompt 全文。
    • 值得看原文：附錄 Table 2 的 17 種錯誤定義；Figure 3 的錯誤分布；Figure 7a 的 5 次嘗試累積曲線；附錄 A.3 的 ALFWorld 案例，看回饋實際長什麼樣。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「AgentDebug 把準確度提高 24%，所以任務成功率也提高 24%。」摘要的 24% 與 17% 是偵測關鍵錯誤的百分點差（全對 24.3% 對 0.3%），和任務成功率無關。而且全對只有 24.3%，人工標註的 κ 也只有 0.55。這套方法的價值在從關鍵那一步重跑的流程；偵測本身還不可靠。

    摘要讀約 3 分；原文約 25 分

    一句話：UC Berkeley 團隊分析 7 個 multi-agent 框架的 1,642 條 trace，歸納出 MAST：14 種失敗模式、3 大類。結論是多數失敗來自系統設計與 agent 間的協調，換更強的 model 修不好。

    跟這堂課的關係

    Slides p.24 把失敗來源分成 5 層，見〈失敗分層：同一個症狀有五個來源，在來源那一層修〉；這篇分成 3 類。「系統設計」對應任務規格與 harness 兩層。「任務驗證」對應 p.27 與 p.30 的「要求證據」，也支持〈驗證〉把檢查排在前面。「agent 間不對齊」在 L6 沒有對應層，它屬於 L5 p.36 的 multi-agent 問題。

    壓縮後的重點

    1. Multi-agent 系統的失敗率很高。7 個框架在各自的 benchmark 上，失敗率從 41% 到 86.7%。Benchmark 不同，數字不能直接互比。
    2. 3 大類的比例：系統設計 44.2%、agent 間不對齊 32.3%、任務驗證 23.5%。分類來自 6 位專家對 150 多條 trace 的 grounded theory 分析。人工標註的 Cohen's κ 經三輪修訂後達 0.88。
    3. 最常見的單一模式是步驟重複（15.7%）。其次是推理與行動不一致（13.2%）、不知道終止條件（12.4%）、違反任務規格（11.8%）。驗證類裡，錯誤的驗證佔 9.1%，沒驗證或驗證不完整佔 8.2%。
    4. LLM 可以當標註員，規模化到 1,642 條。用 OpenAI o1 做 few-shot 標註，準確度 0.94，κ = 0.77。換到新的框架與 benchmark 上，κ = 0.79。

    6. 改 prompt 與拓撲有效，但不夠。ChatDev 在 ProgramDev-v0 上，基線 25.0%，改 prompt 後 34.4%，改拓撲後 40.6%；強制 CEO 有最終決定權提高約 9.4%，加高階驗證步驟提高約 15.6%。作者說這還不算實質改善，需要結構性的重新設計。
    7. Agent 間的不對齊，不只是溝通協定問題。作者認為它反映 agent 之間缺少 theory of mind。單靠更好的通訊協定，不太可能修好這一類。

    • 可以跳過：Section 2 Related Work；Section 3.3 LLM-as-judge pipeline 的建置細節；附錄的 prompt 與各框架描述。

    27 篇研究的統合，整理成六類失敗。失敗隨任務長度複利；多加 scaffolding 不一定有救。

    導讀把「scaffolding 不一定有救」當警語帶進討論。它也批評排行榜（含 SWE-bench），接到 L7。

    摘要讀約 3 分；原文約 20 分

    一句話：Oxford 的 3 位作者統合 2023–2026 年的 27 篇研究（19 個 benchmark），歸納出 6 類失敗。結論：失敗隨任務長度非線性複利，子技能強不等於任務會成功，多加 scaffolding 不一定有幫助，排行榜分數有一部分來自測量錯誤。

    跟這堂課的關係

    Slides p.22 說真實的 run 比 0.95ⁿ 更差，見〈錯誤相乘：每步 95%，50 步只剩 8%〉與〈獨立假設〉；這篇 7.1 節同意：實測的下降比固定每步錯誤率更快，因為 agent 走錯後不會回頭。p.24 的 5 層依來源分，這篇的 6 類依症狀分，見〈失敗分層：同一個症狀有五個來源，在來源那一層修〉；這篇的 tool 類是 agent 叫錯 tool 或給錯參數，依 slides 屬 p.27 的 model 層。長任務退化的瓶頸是 context 的管理，接到〈要不要記〉；測量效度接 L7，也呼應〈分數要自己量〉。

    壓縮後的重點

    1. 這是文獻統合，不是實驗。入選條件：有量化的錯誤分析、有人工標註的 taxonomy，或檢驗過 benchmark 的效度；只報分數的不收。作者把 60 多個錯誤類別合併成 6 群。
    2. 6 類失敗。Tool 呼叫與參數錯誤；多限制同時滿足；長任務隨 context 累積退化；multi-agent 協調；安全與資安；測量效度。Table 2 把 16 組 benchmark 的數字排在一起。
    3. 規劃類：TravelPlanner 上 GPT-4 只有 0.6%。每個限制單獨都能滿足，一起就失敗。推理 model（o1-preview）約 10%；加形式化 verifier 與 critic 的最佳配置約 65%。

    5. 安全類：沒有專門防禦，就要假設會中 prompt injection。InjecAgent 上用 ReAct 的 GPT-4 約 24% 中招，強化攻擊約 47%，部分開源 model 超過 80%。
