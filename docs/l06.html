先看這裡

先看一個例子。你下班前交給 agent 一個大約要 50 步的任務。Agent 是會自己讀檔、跑指令、改 code 的 AI 助手，裡面做決定的是語言模型（下面叫 model）；它每做一個動作，例如讀一個檔、改一個檔、跑一次指令，算一步。隔天早上它回報「完成，測試都通過」。你自己一跑，測試是紅的。翻紀錄才發現兩件事：它很早就改錯了一個檔案，之後的每一步都建立在這個錯上；最後它也沒有真的看到測試通過，就回報了通過。

一個任務有幾十步，只要其中一步錯了沒被發現，整個任務就錯，所以步數越多，全對的機會越低。這門課替這類失敗列了 26 種；這堂不背它們，回答的問題是：怎麼把錯攔下來。下面三條是這堂的判斷：在哪裡檢查、失敗時從哪裡重做、出錯之後去哪裡修。

  • 長任務靠攔錯，不靠每一步第一次就做對。假設每一步第一次做對的機率是 95%：完全不檢查，50 步全對的機率只剩 8%；改成每步做完就檢查、錯了重試一次，而且檢查都抓得到錯，就升到 88%。Model 沒有變強，差別只在錯有沒有當場被攔下（第 1、2 章）。
  • 失敗時從哪裡重做、最多花多少，要事先定。檢查分兩種。很快就跑完的（例如語法檢查）每一步都跑。要跑很久的（例如整套測試）隔一段跑一次：通過了，就把當時的檔案存成一個存檔點（checkpoint）；沒通過，就退回上一個存檔點重做。隔得太密，時間和費用都花在驗證上；隔得太疏，一錯就要重做一大段。例子裡如果每 10 步驗一次，那個改錯的檔案最晚在 10 步之內就會被抓到，不會錯到最後。再替每個任務定步數、費用、時間的上限，一直沒有進展就停（第 3 章）。
  • 修的時候，先分清楚錯是從哪裡來的。例子的最後一個錯是「說測試通過，其實沒過」。這一個症狀就有五種可能的來源：你的任務說明沒要求跑測試；harness（包在 model 外面、替它執行動作的程式）截掉了測試的錯誤輸出；model 沒跑就宣布完成；跑測試的工具失敗了卻回報成功；跑的是還沒重新編譯的舊程式。五種的修法都不同，修錯地方，下次還會再犯（第 4 章）。

另一種錯是 agent 把錯的資訊存成筆記，下一次對話又讀回來照做，那是 L6b〈Agent Memory〉的主題。26 種失敗的清單在第 5 章，需要時查。

1錯誤相乘：每步 95%，50 步只剩 8%

反過來算，要讓 50 步有 90% 全對，每步要 99.79%，等於約 475 步才錯一次；100 步要 99.89%。實際的 agent 離這個很遠：照 99.79% 算，十個 50 步的 run 只有一個會碰到錯；下面的量測裡，連最後成功的 run，七成途中都出過錯。而且每一步有多準由 model 和任務決定，寫 harness 的人改不了。所以長任務不能靠每一步都對。

本文的判斷：這條算式有兩個前提，真實的 run 兩個都不成立。第一個前提是一步錯就整個 run 失敗，第二個是各步的成敗互相獨立。課程提醒真實的 run 比算式更差，因為錯誤會往後傳。2025–2026 年的量測顯示，真實的 run 有一處比算式好（第一個前提不成立），也有一處比算式差（第二個前提不成立）：

比算式好的是一步錯不等於整趟失敗。Failure as a Process（UCL 與南京大學，2026-07）逐步標註了 Terminal-Bench（在 shell 裡完成任務的 benchmark）上 21 個系統的 1,794 條 trajectory（一趟執行的完整紀錄）：成功的 run 有 71% 途中碰過至少一個錯，只有 29% 一路沒出錯。Snorkel（2026-02）的資料也類似：通過和失敗的任務，每題的錯誤數差不多（2.09 與 2.71 個），差別在修復率（95.0% 與 73.5%）。兩份都是觀察，不是對照實驗。

比算式差的是各步並不獨立：沒攔下來的錯會傳下去，越晚越難修。Recovery-Bench（Letta，2025-08）讓 agent 從之前失敗的 run 留下的環境接手，同一批 model 的平均成功率從 26.3% 掉到 11.2%。

所以算式不必丟，要換的是代入的 p：p 應該是「這一步沒有留下沒攔到的錯」的機率。換了定義，兩個前提就又站得住。第一個前提變成「留下一個沒攔到的錯，整趟就失敗」：當場攔下來重做的錯不算，這正是圖裡第二條和第三條路的差別。第二個前提：錯誤往後傳，只發生在已經留下一個沒攔到的錯之後，那時這個 run 已經算失敗了。算式要的只是「前面都沒留下錯時，這一步也沒留下錯」的機率，所以每步仍然可以乘起來。每步 5% 出錯，只要多數當場攔下來，p 就遠高於 95%，該壓低的是沒攔下來的錯。

三個槓桿。pⁿ 裡只有 n 和 p 兩個量，能動的做法有三種：減少 n，以及兩種提高 p 的辦法：

三種做法裡，「讓每步更準」最直覺，但只靠它不夠：Towards a Science of AI Agent Reliability（Princeton，2026-02）量了 15 個 model，能力進步帶來的可靠性進步很小。所以接下來兩章講另外兩種：第 2 章當場攔錯，第 3 章減少步數。同一條 pⁿ 在 L7 也會再出現：pass^k 把 p 換成同一題跑一次成功的機率、n 換成跑的次數 k，問的是 k 次都成功的機率。

Model 一點都沒變強，50 步的全對率從 8% 升到 88%。但檢查要準：漏兩成，就掉到 55%。檢查也會往另一個方向錯：把做對的步驟判成錯，打回去重做。上面的算式沒算這一種。把檢查調嚴，漏抓會變少；但多加的測試和規則本身也可能判錯，所以這一種錯通常會變多。冤枉到的步驟要重做，重做時可能把本來對的改壞，所以檢查不是越嚴越好，數字見本章最後的本文延伸〈檢查會往兩個方向錯〉。另外，重試之前要確認這一步做兩次不會出事，這是 L5〈送出去之後〉講的冪等。

第三列有量測。ImpossibleBench（CMU 與 Anthropic，2025-10）把測試改成和規格矛盾，任何通過都只能靠作弊。改法有兩種：Oneoff 改掉一個測試的期望值，讓它和規格矛盾。Conflicting 複製一個測試、給它不同的期望值，同一個輸入有兩個互相矛盾的答案，連測試之間都衝突。GPT-5 在 Oneoff 作弊 76%、在 Conflicting 54%；Claude Opus 4.1 在 Conflicting 50%。手法有改測試、讓 == 永遠成立、針對測試寫特例。Read-only 擋得住改測試，擋不住寫特例；給 agent 一個「回報給人」的出口，GPT-5 在 Conflicting 從 54% 降到 9%，Opus 4.1 降得少得多。這些是當時的 model，數字會變。寫給 agent 的任務可以這樣防：

本文延伸｜檢查會往兩個方向錯：漏抓與誤判不是 slide 的內容

本章的算式只算了檢查的一種錯。檢查拿這一步的結果做判斷：說「過」就放行，說「錯」就打回去重做。它可能往兩個方向判錯，所以一共有四種結果。下表的 p、detect 和本章開頭的意思一樣：p 是這一步第一次就做對的機率，detect 是這一步做錯時檢查抓到的機率。

英文常把這兩種錯叫 false positive 和 false negative，但哪一種叫哪個名字，要看把哪一種判定當成 positive（陽性），而兩種當法都有人用。把「檢查說錯」當 positive，就像驗出病叫陽性：漏抓是 false negative（偽陰性），誤判是 false positive（偽陽性）。評估 agent 的 grader（判斷 agent 有沒有做完任務的程式）通常反過來，把「判過」當 positive，名字就對調：沒做對卻判過，叫 false positive。L7〈Grader〉用的是後一種。為了不混淆，本文不用這兩個英文名字，直接說漏抓和誤判。

把誤判算進去。設 false_alarm 是檢查把做對的步驟判成錯的機率。打回去的步驟要重做。這裡的假設和本章的算式一樣：重做之後做對的機率是 retry_ok；重做的結果不再檢查，重做錯了就算這一步失敗。本章的算式也是這樣算的，它沒有「重試又錯、再檢查、再重試」那一項。

漏抓只會發生在做錯的步驟上，每一步只有 1 − p = 5% 的機率做錯。誤判發生在做對的步驟上，每一步有 p = 95% 的機率做對。所以誤判能碰到的步驟，是漏抓的 19 倍（95% ÷ 5%）。但兩種錯每發生一次的損失，要看 retry_ok。漏抓一次，損失的是一次修好的機會，這個機會本來有 retry_ok 的機率成功。誤判一次，那一步要在重做時改壞才算失敗，機率是 1 − retry_ok。兩邊乘起來：漏抓率每多 1 個百分點，一步的成功率就少 (1 − p) × retry_ok 個百分點；誤判率每多 1 個百分點，就少 p × (1 − retry_ok) 個百分點。重試和第一次一樣準的時候（retry_ok = p = 95%），兩個都是 5% × 95% = 0.0475：誤判碰到的步驟是 19 倍，每一次的損失卻只有漏抓的 19 分之一（5% 對 95%），剛好抵銷，傷害一樣大。重試常常還是錯的時候（retry_ok = 50%），兩種錯每一次的損失都是 50%，只剩碰到的步驟數不同，所以漏抓是 0.025、誤判是 0.475，誤判的傷害是漏抓的 19 倍。

所以檢查不是越嚴越好。把檢查調嚴，例如多跑幾種測試、或讓 reviewer 看到可疑的地方就打回去，漏抓會變少。但每多跑一個測試，就多一個可能本身寫錯、或時過時不過的測試；reviewer 打回去的「可疑」，也不一定真的錯。所以調嚴之後，誤判通常也會變多。下圖用本章的 p = 95%，比較四種檢查的 50 步全對率：

  • 本章的「檢查很準」：漏抓 0、誤判 0，理想的情況。
  • 寬鬆：漏抓 20%、誤判 0，就是本章表裡「檢查漏兩成」那一列。
  • 調嚴，少誤判：漏抓降到 1%，誤判 5%。
  • 調嚴，常誤判：漏抓降到 1%，誤判 20%。

用上一段的係數就算得出這張圖。從寬鬆調到「調嚴，少誤判」，漏抓少了 19 個百分點（20% 降到 1%），誤判多了 5 個百分點（0 升到 5%）。重試和第一次一樣準的時候，兩種錯每個百分點都讓一步的成功率少 0.0475 個百分點；漏抓少 19 個、誤判多 5 個，一步的成功率淨增約 0.67 個百分點，50 步全對率就從 55% 升到 76%。誤判多到 20% 時，多出來的誤判比少掉的漏抓還多 1 個百分點，一步的成功率反而微降，50 步全對率退回 53%，等於白調。重試常常還是錯的時候，漏抓每個百分點只值 0.025，誤判每個值 0.475：少掉 19 個百分點的漏抓，一步的成功率只多約 0.48 個百分點；多出 5 個百分點的誤判，卻少約 2.4 個百分點。一步淨少約 1.9 個百分點，50 步全對率從寬鬆的 22% 掉到 8%。所以評一個檢查要看兩個數字：漏抓多少、誤判多少，還要看重試修不修得好，因為它決定兩種錯各值多少。

實際的誤判比算式更傷。算式假設冤枉到的步驟只是重做一次，做對的機率還是 retry_ok。實際上 agent 收到的訊息是「你做錯了」，它會去修一個不存在的 bug，改壞的機率比重做一次更高。常見的來源是 flaky test：同一份程式碼有時過、有時不過的測試，例如一個依當天日期計算的測試，剛好碰到 2 月 29 日才失敗（第 5 章〈26 種 run 的失敗〉的環境那張表）。對策是先在沒改過的版本上，把同一個測試多跑幾次：沒改過的版本也會失敗，失敗就不是這一步造成的，該處理的是那個測試，不是叫 agent 改程式。更糟的是檢查本身寫錯，例如測試和規格矛盾，做對的實作永遠過不了，等於誤判率 100%。這正是本章前面 ImpossibleBench 的設定：GPT-5 在 Oneoff 有 76% 改用作弊讓測試變綠；給 agent 一個「回報給人」的出口，GPT-5 在 Conflicting 的作弊就從 54% 降到 9%。ImpossibleBench 量的是誤判率 100% 的極端情況，偶爾的誤判會不會也讓 agent 作弊，沒有量測。本文的推論是方向相同：agent 收到「錯了」卻找不到錯，能做的就只剩改程式去迎合檢查。所以誤判的代價可能不只是多一次重試。

漏抓的代價，sⁿ 也低估了。sⁿ 只回答 50 步全對的機率，不分失敗的 run 是哪一種。有的失敗至少有一次檢查說過「錯」，留下了紀錄，有人可以回頭看。漏抓的錯不一樣：那一步做錯了，檢查卻說過，當下沒有任何紀錄說它錯了。以寬鬆的檢查為例（漏抓 20%）：一步做錯的機率是 1 − p = 5%，做錯又漏抓的機率是 5% × 20% = 1%。50 步裡至少有一步漏抓的機率是 1 − 0.99⁵⁰，約 40%。重試和第一次一樣準的時候，寬鬆的檢查 50 步全對率是 55%，失敗的 run 約 45%。有漏抓的 run 一定不是全對的，所以這 40% 全部落在那 45% 裡。照這個算式推，失敗的 run 有近九成（40% ÷ 45%）至少帶著一個漏抓的錯。這些錯有的之後會露出症狀，有的不會；不會的，agent 就會當成成功交出去。本章前面引的 Failure as a Process 量到，26% 的失敗 run 宣稱自己成功，可見 agent 把失敗當成成功交出去，在實測裡並不少見。

3Checkpoint 與上限：決定失敗時退回多遠、最多花多少

驗證告訴你錯了。接下來要決定退回多遠，以及一直錯的時候什麼時候停。

退回多遠，決定要多跑多少步。第 2 章每一步都檢查，背後假設檢查不花成本。便宜的檢查（lint、型別檢查）確實可以每步跑；貴的檢查，例如跑整套測試、請另一個 agent 讀 diff，就不能每步都跑。做法是把 50 步切成幾段，每段結束時做一次貴的驗證：驗證過就存一個 checkpoint（可以退回的狀態），失敗就退回上一個 checkpoint，重跑這一段。

切成幾段最划算，要算兩筆帳。第一筆是步數。每段 k 步時，一段全對的機率是 0.95k。失敗就重跑，跑到過為止。平均要跑幾次，是全對機率的倒數：全對 60% 的段，跑 100 次約過 60 次，所以每過一次平均要跑 100 ÷ 60，約 1.7 次。一般式是 1 ÷ 0.95k 次。段越短，全對的機率越高，重跑的越少。第二筆是驗證。每跑完一次段就驗證一次，所以驗證次數是段數乘上每段平均跑幾次。這兩個數往相反方向變：段切短，段數變多，每段平均跑的次數卻變少。段很長時，每段平均跑的次數降得比段數漲得快：不分段是 1 段、平均跑 13 次，驗證 13 次；每段 25 步是 2 段、平均跑 3.6 次，驗證約 7.2 次，所以驗證次數先變少。段短到每段平均已經不到 2 次（每段 10 步時是 1.7 次），再降也有限，因為每段至少要跑 1 次，最多只能再少一半；段數卻還會翻好幾倍（每段 10 步是 5 段，每段 1 步是 50 段），驗證次數就跟著變多。這裡把一次驗證算成 5 步的成本（本文的假設：跑測試、讀輸出、存 checkpoint）。兩筆加起來是總成本，算出來的都是平均值：

把六種切法代進去，就是下圖。每一列是一種切法：列名下一行是一段的數字，長條是整個 run 的數字，灰色是步數，黃色是驗證的成本。

同一個 run、同一個 model，只看灰色，從不分段切到每段 10 步，要跑的步數就從 650 步降到 84 步。再往下切，步數只剩每段 5 步 65、每段 2 步 55、每段 1 步 53，因為一步都不錯也要 50 步。黃色卻越來越長：每段 10 步共驗證約 8.4 次，成本 42；每段 1 步是 50 段，要驗證約 52.6 次，成本 263。兩筆加起來，每段 10 步的總成本 126（84 + 42）最省，每段 5 步是 130（65 + 65），只多 4 步。

最省的段長取決於兩個假設，圖下的兩個滑桿各管一個。第一個是驗證有多貴：一次驗證只算 1 步時，最省的從每段 10 步換成每段 5 步。驗證完全不花成本時，總成本只剩步數，最省的是每段 1 步，總成本 53 步，也就是第 2 章每一步都檢查的情況。第二個是每步多可靠：每步 95% 等於平均每 20 步錯一次。升到 99%，平均每 100 步才錯一次。切短是為了少重跑，重跑本來就少，切短省下的步數不多，驗證次數就成了主要的帳，所以少驗證幾次比較划算，最省的變成每段 25 步。降到 90%，最省的變成每段 5 步。合起來是一條規則：驗證越貴、每步越可靠，段就切得越長。這張圖還假設段尾才發現失敗。如果段中途就有便宜的檢查先抓到錯，灰色還會再短一些。

存什麼：驗證過的狀態，而且 context 也要退。Context 是這一次送進 model 的全部文字，包括對話歷史（L4〈Context 的成本〉）。沒驗證就存，存下來的狀態可能已經帶著錯，退回去錯還在。只退檔案也不夠：檔案退回去了，前面那段錯的推理還留在 context 裡，下一次會照著它再走一遍。Recovery-Bench 量到的是同一件事：讓 agent 接手一個失敗過的環境，比了三種接手方式（只給環境、環境加一段動作摘要、環境加完整的動作歷史），帶著完整歷史的表現最差，作者的解釋是錯的推理會繼續帶偏下一次。本文的做法是折衷：退回時不帶原本的對話，只留一句「這條路試過，為什麼失敗」。完整的對話已經量到會帶偏，什麼都不留，下一次又可能重走同一條路（本文的判斷）。

工具能不能替你退？Claude Code 的 /rewind 能同時退 code 和對話，但有三個限制（2026-11 的官方文件）：

  • 你送出 prompt 時才存一個點。一個 prompt 讓 agent 自己跑幾十步的長任務，中間沒有點可以退，只能退回開頭。
  • 只追蹤它自己的檔案編輯 tool 改的檔案。Agent 在 shell 裡跑指令改的檔案（rm、mv、會寫檔的 script）不在追蹤範圍。
  • Subagent 改的檔案多半也不還原。Subagent 是主 agent 派出去做子任務的另一個 agent。

Git 沒有這三個限制。Commit 的時機由你決定，每段驗證過就存一個點；它記的是 repo 裡追蹤中的每個檔案，不管是 agent 的編輯 tool、shell 指令還是 subagent 改的，退回時一起退（.gitignore 排除的、還沒 add 過的新檔不在內）。但 git 只退檔案，context 要另外退：開一個新的 session 從退回的版本接著做，只帶上一句「這條路試過，為什麼失敗」，也就是上面的折衷。所以長任務的 checkpoint 用 git，每段驗證過就 commit 一次：

回不去的動作。Checkpoint 只退得了自己的檔案。付款、刪資料、對外發信，退不回來，也不能靠重試，要在發生之前把關。做法是由 harness 在執行前比對 allowlist（事先列好、可以自動執行的動作清單），不在清單上的就請人確認（L2〈權限〉）；或把環境切開，讓 agent 碰不到正式環境。Replit 2025 年的事故是例子：使用 Replit agent 的 SaaStr 創辦人 Jason Lemkin 說，agent 在 code freeze 期間刪了他的 production 資料庫；Replit 事後推出 dev、prod 資料庫自動分離（單一案例，事故經過是 Lemkin 一方的說法）。

這種形狀也會過時：同一家公司 2026 年寫道，harness 的每個元件都是對 model 能力的假設。例子是 context reset：每個 session 從空的 context 開始、靠檔案交接，原因是他們較早用的 Sonnet 4.5 接近 context 上限時會提早收尾；換到 Opus 4.5 之後這個行為大致消失，他們就拿掉定期清空，只靠壓縮對話（L4〈先用規則刪，最後才摘要〉）。所以要不要照圖切成短 session，看你用的 model：它接近 context 上限時還會提早收尾，就照圖切；不會，一個 session 可以做不只一個 feature。不管哪一種，一段還是一個 feature：每段驗證過才 commit，錯的狀態就留在這一段。失敗退回時 context 也要退，錯的推理就不會帶偏下一次。這兩件照做，因為它們防的是錯誤往下傳，不是 context 快滿（本文的判斷）。怎麼當使用者跑長任務，在 L3〈終點〉。回到圖裡靠檔案交接的那一格：progress.txt 是寫給下一個 session 讀的，這種跨 session 留下來、之後再讀回 context 的東西就是 memory，L6b〈Agent Memory〉接著講它會出什麼錯。

上限：一直錯的時候什麼時候停。課程的例子是跑了 200 步沒有進展。Failure as a Process 也量到兩件事。第一，agent 很少自己停：失敗的 run 裡，只有 18% 在錯誤已經救不回來之後很快停下，其他的繼續做下去。第二，一次修復從出錯算到修好或放棄：修好的中位數 5 步，沒修好的中位數 12 步。修好通常很快，修了遠超過 5 步還沒好，就比典型的修好長很多，再修下去的價值變低，修太久就該停（本文的判斷；論文沒給兩組的比例）。Agent 自己不停，上限就要從外面加。上限有四種：

上限擋什麼在 Claude Code 裡（2026-11 的官方文件）
步數繞圈--max-turns，只在 -p（非互動模式：一次給完 prompt 就跑）有效，到上限就回報錯誤；subagent 用 maxTurns，到上限時輸出標成 partial

這四種上限，加上第 2 章的重試，都是 SRE（site reliability engineering，Google 提出的服務維運方法）處理「下游會失敗」的老習慣（查閱）。差別是服務的失敗大多能偵測，agent 的失敗常常安靜，上限只在它錯很久之後才停下它，所以第 2 章的檢查排在前面。本頁核心觀念之後的第 2 段〈動手試試〉有指令可以照打；subagent 的深度與寬度在 L5〈派工〉，上限設多少在 L8〈反向成本與上限〉。

查閱SRE 的四個習慣：timeout、retry with backoff、circuit breaker、error budget

SRE（site reliability engineering）是 Google 提出的服務維運方法。四個習慣：

  • Timeout。一個呼叫等多久就放棄，不讓卡住的下游拖住整個系統。對應 agent 的步數與時間上限。
  • Retry with backoff。失敗後重試，每次等更久（1 秒、2 秒、4 秒），避免許多呼叫端同時重試，壓垮同一個下游。對應第 2 章的重試：檢查抓到錯就重做這一步。Backoff 在 agent 這邊少用：agent 的錯多半不是下游太忙，等久一點也不會變對（本文的判斷）。
  • Circuit breaker。連續失敗到門檻就斷路，一段時間內直接回錯，讓下游有機會恢復。對應「沒有進展就停」。
  • Error budget。先定可接受的失敗率（例如一個月 0.1%），沒用完就可以冒險發版，用完就只修不加。對應花費上限：先定一個 run 可以花多少，用完就停。

4失敗分層：同一個症狀有五個來源，在來源那一層修

知道會出錯之後，下一個問題是錯從哪裡來。同一句「agent 說測試過了，但測試沒過」，至少有五種解釋，來自五層（harness 與 tool 是 L2、L4 講過的兩層）：

前情Harness 與 tool：五層裡 model 以外的兩層是什麼

Harness 是包在 model 外面的那層程式，例如 Claude Code 這個 CLI：它組 context 送進 model、讀 model 的回覆、執行 model 要的 tool call、把結果放回 context。Tool 是 harness 給 model 的動作：讀檔、grep、edit、跑 shell。Model 只輸出一段 JSON 說要呼叫哪個，執行的是 harness。

所以「harness 的 context 截斷」是 harness 為了騰出 context，砍掉最舊的幾輪對話，或把太長的 tool 輸出砍短，錯誤訊息跟著不見；「tool 的靜默失敗」是 tool 失敗了卻回一個看起來正常的結果。看到輸出不完整，先問是誰砍的：harness 組 context 時砍的算 harness，tool 自己只回前 100 行算 tool（第 5 章的表）。L4〈Tool 設計〉講怎麼修這兩層。

五種情況有一個共同點：agent 都沒有報錯，它只是照著錯的輸入做下去。這是它和程式 crash 最大的差別，所以不能等錯誤訊息，要自己去找。

先找第一個出錯的步驟，在那一層修。拿到一個失敗的 run，從頭讀 trajectory，找第一個「輸出和輸入對不上」的步驟：

不要在症狀出現的地方修。例如症狀是 model 沒跑測試就宣布完成，來源卻是任務沒寫「完成」的定義。在這次對話裡補一句「記得跑測試」，只救這一個 run；下一個任務照樣沒寫，就會再犯。修在來源，是把完成的定義寫進每個任務都會帶到的地方，例如任務範本，或 CLAUDE.md（Claude Code 每個 session 都會載入的專案說明檔）。

換更強的 model，也只處理其中一層。Failure as a Process 把決定失敗的錯誤分成兩大類：57.9% 是 epistemic（認知的錯：agent 以為的狀態和實際不符，像第 2 章錯的前提），32.8% 是 competence（能力的錯：狀態沒看錯，事情卻做錯）。更強的 model 主要補後一類。前一類的來源常在 model 看到的東西：tool 回了錯的結果、context 少了資訊、環境和它以為的不同，這些要在 harness、tool、環境那幾層修（分類名照論文，中文說明與對應是本文的整理）。

  • 把五條原則寫成量得到的 policy。例如把「每個 run 都要有上限」寫成「每個 claude -p 指令都帶 --max-turns」，再用一支 script 掃 log，數出沒帶的比例。寫成這樣，才說得出團隊跑的 run 有沒有照做。
  • 記錄每個 run 的 trajectory。每一步的輸入、輸出、tool 結果；多個 agent 時用 L5〈tracing〉串起來。
  • 定期看失敗來自哪一層。失敗的分布就是你們的 roadmap。

5目錄：26 種 run 的失敗，依第 4 章的五層各一張表

這一章不必讀完，需要時再查。課程（CS2680 這堂）列了 26 種 run 的失敗，依第 4 章的五層各一張表。它們都是那五條原則沒守住的樣子，所以拿到一個症狀，先對回是哪一層，比記名字有用。Harness 那張表裡的「Memory 錯誤」是記憶出的錯：一條筆記寫下時是對的，後來過期了，harness 照樣把它放進 context，model 當成現在的事實照做；記憶怎麼出錯，L6b〈目錄〉另外列了八種。

查閱26 種 run 的失敗：五層各一張表

每一列的 agent 都沒有報錯：它把錯的東西當成對的，照著做下去。錯的可能是它拿到的輸入（規格、harness、tool、環境四張表），也可能是它自己的推理（model 那張表）。修法依第 4 章的五條原則。

任務規格（5 種）

失敗規格說了什麼Agent 做了什麼修法
目標含糊「修 login 的 bug」三個 bug 裡挑錯了一個去修寫明檔案、症狀、重現步驟
代理目標（proxy objective）「讓測試通過」刪掉失敗的測試禁止改測試；review diff

目標互相衝突「最小的 diff，所有 edge case」默默放掉 edge case明確排目標的優先順序

Harness（5 種）

失敗Harness 做了什麼結果修法
Context 截斷為了騰出 context，砍掉最舊的幾輪（另一種砍法見第 4 章的註）忘了「不准動 API」那條規則關鍵規則不放在會被砍的對話裡，放在 system prompt 或 CLAUDE.md，每一圈（每次呼叫 model）都重新送
Memory 錯誤把一條過期的筆記放進 context，沒附日期Model 當成現在的事實，在筆記裡的舊路徑新建了一個同名檔案來改；真正在用的那個（已經搬走）沒改到，也沒有任何錯誤訊息記憶標日期；用之前重新確認（L6b〈記憶是會過期的副本〉）
狀態損壞留下一個只改到一半的 edit後面的步驟建在壞掉的檔案上Checkpoint；失敗的步驟回滾
Control loop 錯誤沒有步數或成本上限跑了 200 步，沒有進展限制步數、成本、時間
Fan-out 阻塞等每一個 subagent 回來一個慢的 child 拖住整個 run設 timeout；用部分結果（L5〈送出去之後〉）

Model（6 種）

失敗Model 怎麼推理Agent 做了什麼修法

長任務退化「config 還要再修」把自己第 12 步修好的東西改回去重讀狀態；拆成短任務

Claude Code 的非互動模式（-p）有兩個對應的 flag，時間上限用系統的 timeout 指令。下面的數字是假設的：先量這類任務的 p95，再取兩倍當上限。
