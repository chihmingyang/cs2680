先看這裡

LLM 一次只算出下一個 token（model 讀寫文字的單位，大約一個中文字），所以一個 request 分成兩段：prefill 一次算完整段 prompt，decode 每一步只產生一個 token。兩段的成本都由 model 的形狀決定，歸結成三個數字：權重（訓練好的參數）的 byte 數、每個 token 的運算量、每個 token 的 KV cache（留在 GPU 記憶體裡的中間結果）。這堂要帶走的是：用這三個數字，算出一個 model 在你的 GPU 上能同時服務幾人、每人的對話能多長，第一個字又要等多久。

  • 三個數字各卡一件事。運算量卡 prefill，權重卡 decode 的每一步，KV cache 卡「同時的人數 × 每人的對話長度」。以 Llama 3 70B（Meta 的 700 億參數 model）跑在 2 張 H200（NVIDIA 的 GPU）上為例：GPU 記憶體扣掉權重，只放得下約 43 萬個 token 的 KV cache，由同時在跑的對話一起分。
  • Agent 的長對話省得下算力，省不下記憶體。Agent 每呼叫一次 model，都把到目前為止的整段輸入（context）重送一次；prefix cache 讓重送的部分不用重算，但它的 KV cache 照樣佔著 GPU，所以能同時服務幾個 agent，多半先卡在 KV cache。
  • 選 model 要看每個 token 的 KV，和它怎麼切字。現在的 model 用不同方法縮小每個 token 的 KV：每一層裡的幾組計算共用一份 KV、壓縮後再存、只存最近一段，或換成固定大小的狀態，每個 token 的 KV 因此差到 13 倍。切字的規則（tokenizer）也不同：繁體中文一個字約 0.7 到 0.9 個 token，課程的「3 到 4 個字元一個 token」只適用英文。

1一個 request 的一生：prefill 決定第一個字多快，decode 決定之後每個字多快

從送出一段 prompt，到畫面上一個字一個字冒出回答，serving 系統（把 model 放在 GPU 上、替很多使用者回答 request 的程式）做了六件事：

圖上灰色的四段不用 GPU。Tokenize（①）把文字切成 token，每個 token 換成一個整數 ID，例如 Llama 3 的 tokenizer 把「 is」換成 374；detokenize（⑤）反過來，把 ID 換回文字。Model 只看得到這串整數，怎麼切、中文為什麼特別，留到第 8 章。Schedule（②）決定這一步要算哪幾個 request，stream（⑥）把字送給使用者。只有 ③ 和 ④ 是 GPU 上的 model 在算。

Model 一次只算出下一個 token。Model 的輸出是一張表：詞彙裡的每個 token 一個機率，代表它接在後面的可能性。挑一個 token 接上去，再把加長的序列送回 model，才能算下一個。所以生成一段回答是一個 loop，回答有幾個 token，loop 就跑幾圈。

Prompt 和 output 在這個 loop 裡的待遇不同。Prompt 的 token 一開始就全部知道，可以一起算，這一段叫 prefill；output 的 token 要等上一個算完才知道，只能一個一個算，這一段叫 decode：

兩段各決定使用者感受到的一個數字，L1〈Prefill 與 decode〉已經替它們命名：

  • TTFT（time to first token）。按下送出到第一個字出現，主要是排隊加 prefill。Prompt 越長，prefill 越久。
  • 每個字的間隔。之後每個字都要等一步 decode，常用每秒幾個 token（tokens/s）表示。回答越長，總時間越長。

兩段的瓶頸也不同。課程的說法是 prefill 吃算力、decode 吃記憶體頻寬：prefill 一次算幾千個 token，GPU 的運算單元是忙的；decode 每一步只替每個 request 算 1 個 token，卻要把整個 model 的權重從記憶體讀一遍，運算單元多半在等資料。第 4 章用數字算這件事，GPU 為什麼算得快、讀得慢，見 L10〈Roofline〉。所以prefill 決定第一個字多快，decode 決定之後每個字多快，優化前要先知道使用者在等哪一段。

Prefill 的副產品：KV cache。Prefill 除了產生第一個 token，還會把 prompt 每個 token 在每一層算出的兩組中間結果存起來，這兩組叫 key 和 value，合稱 KV cache。之後每一步 decode 都要讀它，也在後面加一格。它為什麼存在、有多大，是第 3、4 章的主題；這裡先記住兩件事：它跟著 context 的長度變大，而且一直佔著 GPU 記憶體，直到 request 結束。Context 指到目前為止的整段輸入：prompt，加上已經產生的 token。

Schedule：每一步重新決定誰上車。Request 一個一個獨立地來，GPU 卻要一次算一批才有效率，理由在第 4 章。所以 scheduler 每一步都重新組一次 batch：做完的 request 立刻離開，新的 request 不用等整批結束就能加入，這叫 continuous batching：

能不能再收一個 request，看的是記憶體：每個 request 的 KV cache 各佔一份，KV cache 放不下時，新的 request 只能排隊，或由 scheduler 先暫停一個正在跑的（preempt）。Batching 與記憶體分頁的做法，後面的講次會講。

什麼時候停。Decode 停在三種情況：model 產生 stop token（代表「說完了」的特殊 token）、長度到了上限（API 的 max_tokens）、使用者斷線。早一點停，KV cache 的記憶體就早一點釋放，可以收下一個 request。

Agent 的每一圈，都是一次完整的 request。L4〈根本的限制〉說過，model 沒有記憶，agent 每一圈都把整段 context 重送。對 serving 系統來說，重送的每個 token 都是一份 prefill 的工作，也佔一份 KV cache。L8〈Prompt cache〉講的 prefix cache 讓開頭相同的部分不用重算，但那一段的 KV 仍然要放在 GPU 記憶體裡，decode 的每一步也照樣要讀：

所以 prefix cache 省下的是算力和 TTFT，省不下記憶體。第 4 章會算出兩邊各差多少。

2Model 的骨架：一疊相同的 block，參數就是矩陣裡的數字

上一章把 model 當成黑盒子：輸入一串 token ID，輸出下一個 token 的機率。這一章打開它，看裡面有哪些零件、參數放在哪裡。後面的帳都從這裡算起，例子一律用課程選的 Llama 3 70B。

Vector：一個 token 變成一串數字。Model 不能直接拿整數 ID 做運算，所以第一步是查表。Embedding table 是一張 128,256 列、8,192 欄的表，每個 token ID 對應一列；查到的那一列有 8,192 個數字，叫這個 token 的 vector，可以想成一個長度 8,192 的 list[float]。這些數字是訓練出來的，意思相近的 token，vector 也相近。查表的過程如下：

整段 prompt 有 n 個 token，就疊成一個 n 列、8,192 欄的矩陣，寫成 X（n × d）。d = 8,192 是 model 的寬度，之後每一層都在這個形狀的矩陣上運算。

矩陣乘法：model 幾乎所有的計算。一個 n × d 的矩陣乘上一個 d × k 的矩陣，得到 n × k 的矩陣。結果的每一格，是一列和一欄的對應位置相乘再加總，要做 d 次乘法和 d 次加法。所以整個乘法要 2 × n × d × k 次浮點運算，單位叫 FLOP（floating-point operation）：

W 裡的每一個數字就是一個參數（parameter）：訓練時調整，推論時固定不變。Model 的大小說的就是參數的總數，Llama 3 70B 有 70.6B（706 億）個。上面最後一行是後面會用到的關鍵：一個 token 乘過一個矩陣，運算次數是那個矩陣參數數量的 2 倍。

每個 block 有兩個子層，分工不同：

  • Attention。讓 token 之間交換資訊，例如處理「它」這個字時，去前文找「它」指的是誰。這是 token 唯一看得到其他 token 的地方，下一章專門講。
  • FFN（feed-forward network）。對每個 token 各自運算，不看其他 token。Llama 3 用的 SwiGLU 有三個矩陣：兩個 d × dff 把 vector 從 8,192 撐到 28,672 維，再用一個 dff × d 壓回來。

每個子層的輸出不取代輸入，而是加回去：h = x + Attention(RMSNorm(x))。所以有一條 vector 從第一層流到最後一層，叫 residual stream，每個子層只在上面加一筆修正。最後一層的 vector 乘上 LM head（一個 d × V 的矩陣，V = 128,256 是詞彙表的大小），得到 128,256 個分數，每個候選 token 一個，叫 logits；softmax 再把分數變成加總為 1 的機率。

名詞RMSNorm、pre-norm、residual：讓 80 層疊得起來的三個設計

RMSNorm 把 vector 除以它的均方根（root mean square），再乘上每一維一個學到的係數，讓數值的大小維持穩定。

Pre-norm 是先 normalize 再進子層，課程說這讓很深的 stack 訓練得穩。Residual 讓每個子層只學一筆修正，加回原本的 vector。

這三樣對 serving 的帳幾乎沒有影響：norm 每層只有 2 × 8,192 個參數，80 層合計不到總數的萬分之一。

3Attention：每個新 token 都要讀前面全部的 K 和 V

FFN 對每個 token 各自運算，看不到別的 token。要知道「它」指的是誰，「它」必須能讀前文，這就是 attention 的工作。這一章先講 attention 怎麼讀，再講為什麼要存 KV cache，最後講 GQA 怎麼把 cache 變小。

每個 token 產生三個 vector。每一層的 attention 先把每個 token 的 vector 乘上三個 weight 矩陣，得到三個 vector：query（q）、key（k）、value（v）。Llama 3 70B 把這件事拆成 64 份平行做，每一份叫一個 head，每個 head 的 q、k、v 各長 dk = 128；64 × 128 = 8,192，剛好是 d（head 的細節在本章後面）。可以把它想成一次搜尋：q 是搜尋的字串，每份文件有自己的關鍵字 k 和內文 v；先拿 q 和每個 k 比對出分數，再依分數把各份內文 v 混在一起。整段 prompt 一起算時，就是三次矩陣乘法：

分數、mask、softmax。Token i 讀 token j 的分數，是 qi 和 kj 的內積：對應位置相乘再加總，越大代表越相關。一次算全部，就是 S = QKᵀ ÷ √dk，S 是 n × n 的矩陣，第 i 列是 token i 對每個 token 的分數。接著有兩步：

  1. Causal mask。生成時看不到未來，所以 token i 只能讀 j ≤ i 的 token，對角線右上方的分數設成 −∞。
  2. Softmax。把每一列的分數變成加總為 1 的權重，得到 A。

除以 √dk（√128 ≈ 11.3）把分數拉回穩定的範圍。這是 2017 年 Attention Is All You Need 的設計，見延伸閱讀。

成本：n 個 token，n² 個分數。每一層、每個 head 都要替每一對 token 算一個分數，n 個 token 就是 n × n 個，所以 context 加倍，分數變 4 倍。課程估每一層約 4n²d 次運算，QKᵀ 和 AV 各佔一半：一個 head 的一個分數是 128 個乘積的和，約 2 × 128 次運算，64 個 head 合起來是 2 × 8,192 = 2d，n² 對 token 就是 2n²d；AV 依權重加總 v，也是 2n²d。Causal mask 讓實際要算的約少一半。如果把 S 整個存下來，n = 8,192 時是 8,192² × 64 個 head × 80 層 × 2 byte，約 690 GB，比 model 本身還大。所以實作上用 FlashAttention 一塊一塊算 softmax，從不存下完整的 S；它怎麼做到，見 L10〈FlashAttention〉。

為什麼要存 KV cache。回到第 1 章的 decode。新的 token 要讀前面全部的 token，需要它自己的 q，加上前面每個 token 的 k 和 v。前面 token 的 k、v 不會變，因為 causal mask 讓 token j 只受 j 之前的 token 影響，後來的 token 改變不了它。所以算過一次就存起來：

有了 cache，每一步 decode 只替 1 個新的 token 算 q、k、v，再讀整份 cache。沒有 cache，每一步都要把前面所有 token 重算一遍，生成 n 個 token 的總工作量隨 n² 成長。KV cache 是用記憶體換掉重算：每個 token 在每一層都留下一組 k 和 v，直到 request 結束。第 2 段動手試試有一段 numpy，驗證兩種算法的輸出相同。

Multi-head：64 個小 attention 一起跑。回到本章開頭的 head：Llama 3 70B 把 d = 8,192 切成 H = 64 個 head，每個 head 有自己的 128 維 q、k、v，各自做一次上面的 attention；64 個輸出接起來，再乘上 WO 混回 8,192 維。64 × 128 = 8,192，所以切成 head 不增加運算量，只改變 model 學到什麼。課程的例子裡，有的 head 專看前一個 token，有的看第一個 token，有的看整段 context。

Agent 的帳：算力省得下，記憶體省不下。回到第 1 章的 agent。假設 context 已經有 100K token 命中 prefix cache，這一圈再加進 3K 個新 token：agent 上一圈呼叫工具（tool，例如讀檔、跑測試）得到的輸出，加上新的指令。這一圈的帳：

  • Prefill。只算新的 3K：每個新 token 走過所有參數，還要讀前面 100K 個 token 的 K、V，合計約 1.22 PFLOP，0.62 秒。沒有 cache 時整段 103K 重算，是 28.4 PFLOP、14.4 秒，差 23 倍。
  • 記憶體。Decode 時 103K 個 token 的 KV cache 都要在 GPU 上，33.8 GB，有沒有命中都一樣，約是權重的四分之一。

Router 是一個小矩陣，替每個 token 給每個 expert 一個分數，挑分數最高的 2 個（top-2），兩個 expert 的輸出再依分數加權相加。同一個 token 在不同層、不同 token 在同一層，都可能挑到不同的 expert。

6改 KV cache 的架構：縮小、封頂，或換成固定大小的 state

第 4 章的帳裡，最難擴充的是 KV cache：它跟著 context 長度和人數一起長。所以近年的架構多半在改它的長法。課程列了五類做法：sliding window（只存最近一段）、MLA（壓縮之後再存）、linear attention 和 SSM（state-space model；兩者都改存一個固定大小的 state），以及 sparse attention（照樣全存，每一步只讀挑中的一部分）。下圖把它們和完整的 attention 並排，linear attention 和 SSM 併成一格：

做法 1：Sliding window，讓大多數層只看最近 w 個 token。一般的 attention 讓最後一個 token 讀前面全部 n 個；sliding window 只讓它讀最近 w 個，所以這一層的 KV cache 最多存 w 個 token，不再隨 n 成長：

代價是這一層看不到更遠的內容，所以通常留幾層 global（讀全部）負責長距離的記憶。課程舉了三種配法：Gemma 3 每 5 層 local（w = 1,024）配 1 層 global；Mistral 7B 每一層都是 local，w = 4,096；Gemma 2 是 local（w = 4,096）和 global 一層一層交替。以 Gemma 3 的比例算，128K context 時只有 1/6 的層存滿 128K，其餘只存 1,024，總量約是全部 global 的 1/5.8，和 slides 說的「約 6 倍」一致。

做法 2：MLA，每個 token 只存一個壓縮過的 vector。MLA（multi-head latent attention）不存每個 head 的 k 和 v，改存一個短的 latent vector c，要做 attention 時再從 c 還原出 K、V：

Decode 時，還原用的矩陣可以事先併進 query 和輸出的矩陣，所以不必真的把 K、V 算出來；代價是每一步 decode 都直接拿 latent 算分數，比讀現成的 K、V 多算一些。DeepSeek-V3 每層每 token 存 512 + 64 = 576 個數，那 64 個是位置資訊用的 key（RoPE，把 token 的位置編進 q、k 的方法）；對照 Llama 3 70B 每層每 token 的 K 加 V 是 2,048 個數。課程引用的結果：DeepSeek-V2 比 DeepSeek 67B 的 KV cache 少 93%，生成的 throughput 是 5.8 倍。

做法 3：Linear attention，用固定大小的 state 取代越長越大的 cache。Softmax attention 每多一個 token，cache 就多一筆，一直到 request 結束。Linear attention 改成維護一個固定大小的 state，寫成矩陣 S（和第 3 章 n × n 的分數矩陣 S 是兩回事），大小是 dk × dv：key 的長度乘 value 的長度，例如 128 × 128。每個新 token 把它的 k 和 v 做外積（k 的每一格乘 v 的每一格，得到一個 dk × dv 的矩陣），加進 S；要輸出時，用 q 乘 S，得到一個長度 dv 的 vector。所以不論讀過多少 token，S 都一樣大：

Gated DeltaNet 是其中一種，它把「加進 S」改成兩步，就是圖中的 ① 和 ②。第一步，用 decay gate αt（0 到 1 之間的一個數）把整個 S 乘小一點，讓舊的內容淡掉。第二步，先用新 token 的 k 從 S 讀出它原本記的 value，再依 write gate βt 決定換掉多少，換成新的 v；所以同一個 key 再寫一次，會更新它記的值，不會再疊一份上去。固定大小的代價是記不住全部細節，所以實際的 model 混著用：Qwen3-Next 的 48 層裡，36 層是 Gated DeltaNet、12 層是一般的 attention（3:1），只有那 12 層存 KV cache。課程說 Kimi Linear、Qwen3.5 也是同一種配方。

做法 4：State-space model，每個 channel 一個小 state。SSM（例如 Mamba）也維護固定大小的 state，差別在形狀：gated linear attention 的 state 是一個 dk × dv 的矩陣；Mamba 替 vector 的每一維各留一個很短的 vector h，每一維叫一個 channel，所以 d 維的 vector 有 d 個 channel。Mamba 屬於 selective SSM：決定「舊的 h 留多少、新的輸入寫多少」的兩個係數 Ā、B̄，由每個 token 的內容算出來，所以這一層能自己決定記住什麼。這兩個係數和第 2 章的參數不同：參數是訓練完就固定的權重，Ā、B̄ 是每個 token 用那些權重算出來的值。課程引用 Mamba 的結果：生成的 throughput 最高是 Transformer 的 5 倍。

  • Qwen3-Next-80B-A3B。36 層 Gated DeltaNet 各有一個固定的 state（32 個 value head × 128 × 128），每個 request 約 36 MiB（BF16），等於它的 attention 層 1,536 個 token 的 KV。所以 context 很短時，它的優勢不明顯。
  • DeepSeek-V3.2。表中每個數字以 BF16（2 byte）計。開源的 serving engine vLLM（把 model 跑成服務的軟體）可以改用 FP8 存；依 vLLM 2025-09 的說明，每層每 token 是 656 byte：512 個 latent 數各 1 byte，共 512 byte；每 128 個數共用一個 4 byte 的縮放係數（scale），共 16 byte；64 個位置用的數維持 BF16，共 128 byte。61 層合計約 39 KiB。DSA 的 indexer 另有一份 FP8 的 key cache，表中沒算。

本文的判斷：選 model 時，每個 token 的 KV 和參數一樣重要。每 100 GB 的空閒記憶體，Llama 3 70B 放得下 31 萬個 token，Qwen3-Next 放得下 407 萬個，差 13 倍。這會改變選擇：Qwen3-32B 的權重 65.6 GB（BF16），比 Qwen3-Next-80B-A3B 的約 160 GB 小得多，但一個 128K 的 request 要 34.4 GB 對 3.2 GB（Qwen3-Next 另加固定的 36 MiB）。要同時跑很多長 context 的 agent，比較大的 model 反而放得下比較多人。

這張表只算記憶體，不是對照實驗：品質、serving engine 對新架構的支援、固定 state 的開銷，都要另外驗證。表格會過時，公式不會。第 2 段動手試試有一段 python，貼上任何 model 的 config.json 數字就能算。

9Sampling：設定改的是答案，也改輸出有多長

第 1 章說 model 每一步輸出一張機率表，sampling 決定從表裡挑哪一個。同一個 model、同一段 prompt，sampling 的設定不同，答案和長度都會不同。

從分數到機率：temperature。LM head 給每個 token 一個分數 z（logit）。Softmax 把分數變成機率：先算 e 的 z 次方，再除以全部的總和。Temperature T 在這之前把每個分數除以 T：T 小於 1，高分和低分的差距拉大，機率集中到最高分；T = 0 等於每次都挑最高分，叫 greedy decoding；T 大於 1，分布變平，冷門的 token 也有機會。

只從前幾名裡抽：top-k 與 top-p。Top-k 只從機率最高的 k 個 token 裡抽，例如 top_k = 50，k 是固定的。Top-p（也叫 nucleus sampling）從高到低累加機率，取最少的幾個 token 讓總和達到 p，例如 top_p = 0.9，所以留幾個看 model 有多少把握：

設定也改變輸出有多長。每一步都可能抽到 stop token，也可能抽到別的，所以設定會改變回答在第幾步結束，也就改變 decode 的步數、時間和成本。Greedy 有一個已知的陷阱。Qwen3 有兩種模式：thinking mode 先寫出一段推理再回答，non-thinking mode 直接回答；它的官方 model card 說 thinking mode 不要用 greedy decoding，會讓表現變差，還可能無止境地重複。它建議 thinking mode 用 Temperature 0.6、TopP 0.95、TopK 20，non-thinking mode 用 0.7、0.8、20。所以不論設定是什麼，都要設 max_tokens，讓第 1 章的長度上限替你停下來。

Temperature 0 也不保證每次相同。同一個 prompt 在 serving 系統裡，每一步和不同的 request 排在同一個 batch；batch 的大小一變，GPU 的加總順序可能跟著變，浮點數的結果差一點點。碰到兩個 token 分數很接近時，就會挑到不同的 token，之後整段都不一樣。原因與量測見 L1〈浮點數沒有結合律〉。

託管的 model 開始不讓你調。2026-11 查 Claude Opus 5.5 的 migration guide：request 要拿掉 temperature、top_p、top_k，改用 prompt 引導行為；文件也提醒，舊 model 上設 temperature = 0 也從來不保證相同的輸出。所以這一章的設定，主要用在自己架的 open-weight model：先照 model card 的建議值，再用自己的 eval 驗證（L7〈建立評估〉）。

結構是 prelude P、block R 重複 K 次、coda C。多跑幾圈不增加參數，K 圈的運算是 R 的 K 倍。

Geiping 等人（2025）訓練了 3.5B 參數、800B token 的 recurrent-depth model。他們把 K 一路加大，直到每個 token 的運算量和一個 50B 參數的 model 一樣多；在這段範圍裡，推理題的表現隨 K 變大而提升，有時提升很多（摘要比的是運算量，沒有說表現追上 50B 的 model）。

    第 2 章〈Model 的骨架〉與第 3 章〈Attention〉的 Q、K、V、√dk、softmax、multi-head，在這篇都有逐步的圖。差別在規模與結構：它的 vector 是 512 維、8 個 head，Llama 3 70B 是 8,192 維、64 個 head；它有 encoder，今天的 LLM 只用 decoder 那一半。

    壓縮後的重點

    1. 每個字先變成 512 維的 vector。只有最底層吃 embedding，上面每一層吃下面一層的輸出。
    2. Self-attention 分六步。乘三個矩陣得到 64 維的 q、k、v；q 和每個 k 內積打分；除以 8（√64）；softmax；用分數加權 v；加總得到輸出。
    3. 整段一起算就是矩陣乘法。把 vector 疊成 X，乘 WQ、WK、WV 得到 Q、K、V，六步變成一條式子。
    4. Multi-head 是 8 組獨立的 q、k、v。8 個輸出接起來，再乘 WO 混回一個矩陣；不同的 head 會注意不同的字。
    5. 位置要另外加。Attention 不知道順序，所以每個 embedding 加上一個位置編碼；每個子層也都有 residual 和 layer normalization。
    6. Decoder 一次產生一個字。產生的字送回輸入；它的 self-attention 把未來的位置設成 −∞。最後的 linear 加 softmax 輸出整個詞彙表的機率。

    原文怎麼讀

    • 可以跳過：開頭的 black box 比喻；「Recap of Training」與「The Loss Function」兩節，講的是訓練。
    • 值得看原文：「Self-Attention in Detail」的六步圖，和第 3 章的式子逐一對照；「The Beast With Many Heads」把 8 個 head 接起來的大圖；「The Decoder Side」的動畫。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。

    「LLM 就長這張圖的樣子。」圖上是 2017 年翻譯用的 encoder-decoder，有 encoder 和 encoder-decoder attention，位置用 sinusoidal。今天的 LLM 只留 decoder 並加上 causal mask，常改用 RMSNorm、RoPE、GQA。作者在頁首也說，新的內容寫在他的書裡。

權重、運算與 KV cache Weights, FLOPs, and the KV cache

  1. 必讀Transformer Inference Arithmetickipply · 部落格 · 2022 · 約 40 分

    從第一原理算權重的 byte、每個 token 的運算、KV cache，再和 GPU 的算力與頻寬比較。第 4 章的原型。

    導讀用 Llama 3 70B 重算它的 capacity 一節：扣掉權重，2 張 H200 放得下多少 token？和第 4 章的 43 萬對一下。

    摘要讀約 3 分；原文約 40 分

    一句話：用第一原理估 Transformer 推論的成本：每個 token 的 KV cache 幾 byte、一張卡放得下多少 token、每個 token 要多少運算、什麼時候卡在頻寬、什麼時候卡在算力。最後拿實測對照，看估算差在哪裡。

    跟這堂課的關係

    這篇是第 4 章〈三個數字〉的原型：KV cache 的公式、每個 token 約 2 × 參數次運算、扣掉權重剩多少 token，都是這篇的算法。它寫於 2022 年，KV cache 用 MHA 的 head 數算，今天要換成第 3 章〈Attention〉的 KV head 數。頻寬與算力的部分見 L10。

    壓縮後的重點

    1. KV cache 每個 token 是 2 · 2 · n_layers · n_heads · d_head byte。第一個 2 是 k 和 v，第二個 2 是 16 bit。沒有 cache，取樣的時間隨長度的平方成長。
    2. 容量的算法。52B 的 model 權重約 104 GB，至少要 3 張 40 GB 的 A100；剩約 16 GB，每個 token 約 0.002 GB，放得下約 8,000 個 token。
    3. 每個 token 約 2 × 參數次運算。每個參數在矩陣乘 vector 裡做一次乘加；每層的權重約 12 · d_model²。
    4. 小 batch 卡頻寬，大 batch 卡算力。A100 是 312 TFLOPS、1.5 TB/s，比值約 208；batch 小於它時，時間由讀權重決定。
    5. Softmax、layernorm 看的是 byte，不是 FLOPs。這類運算在 52B 的 model 約佔 5% 的時間。
    6. 和實測對照。13B 的 model 單卡估 16.8 ms，實測 22.0 ms；修正頻寬效率與中間運算後約 20.7 ms。

    原文怎麼讀

    • 可以跳過：「model parallelism」的通訊量細節，多 GPU 是後面講次的主題；結尾的練習題。
    • 值得看原文：「kv cache」與「capacity」兩節，和第 4 章的 token 預算一起讀；「flops counting」逐項數出 12 · d_model²；「comparing against real benchmarks」看估算差在哪裡。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 25 分。
    別誤讀

    「KV cache 要用 head 數算。」文章寫在 GQA 普及之前。Llama 3 70B 有 64 個 query head，但只有 8 個 KV head；用 64 算會高估 8 倍。

    跟這堂課的關係

    第 5 章〈MoE〉的「記憶體跟著總參數，運算跟著 active 參數」，這篇寫得最直接：active 參數決定推論的運算，總參數決定記憶體。第 5 章的表裡 Mixtral 是 46.7B 與 12.9B，來自 slides；論文寫成 47B 與 13B。

    壓縮後的重點

    1. 架構。32 層、4,096 維、32 個 query head、8 個 KV head、32K context、32,000 個 token 的詞彙；每層 8 個 expert，每個 token 用 2 個。
