導讀

公司買了 2 張 H200（NVIDIA 的 GPU），要在上面架 Llama 3 70B 給內部用；它是 Meta 的語言模型（下面叫 model）。Model 的本體是一大堆訓練出來的數字，叫參數；這個 model 有 700 億個，要整份放進 GPU 的記憶體才能跑。老闆問你三個問題：能同時給幾個人用？每個人的對話能多長？送出問題之後，第一個字要等多久？

這三個問題不必實際架起來才知道。這堂回答的問題是：用哪幾個數字，算出一個 model 在你的 GPU 上撐得住多少。

  • 一個請求分成兩段，各決定一種等待。第一段叫 prefill：model 把你送進去的整段文字一次讀完，它決定第一個字要等多久。第二段叫 decode：model 一步只產生一個 token（它讀寫文字的單位，大約一個中文字），它決定之後每個字出來的速度（第 1 章）。
  • 三個數字，各卡住一件事。每個 token 要做多少運算，卡住 prefill，也就是老闆的第三個問題。參數總共佔多少記憶體，卡住 decode 每一步的速度，因為 decode 每產生一個 token，都要把全部參數從記憶體讀一遍。第三個數字是每個 token 的 KV cache 有多大：model 讀過的每個 token，都會留一份中間結果在 GPU 記憶體裡，叫 KV cache，對話還在就不能丟。它卡住記憶體能分給多少對話，也就是老闆的前兩個問題。GPU 的記憶體先放參數，剩下的才放 KV cache；例子裡剩下的空間只放得下約 43 萬個 token 的 KV cache，由所有同時在跑的對話一起分（第 4 章）。
  • 老闆的前兩個問題是同一個。人數和對話長度分的是同一塊記憶體：43 萬個 token，可以是很多人各聊一小段，也可以是少數人各聊很長。多輪對話的每一輪都把整段對話重送一次；前面讀過的部分留著 KV cache 就不用重算，所以省得下運算，省不下記憶體（第 3、4 章）。

選 model 時要看它每個 token 的 KV cache 多大，不同的 model 之間最多差到 13 倍（第 6、7 章）。估 token 數時，繁體中文一個字約 0.7 到 0.9 個 token（第 8 章）。

核心觀念

一個 request 的帳，由 model 的形狀決定

前四章一章建在前一章上：先看一個 request 怎麼跑，再打開 model 看參數放在哪裡，接著看 attention 為什麼要存 KV cache，最後把三個數字算成一本帳。後面幾章都接在這本帳上：第 5 到 8 章看換一個 model 時帳怎麼變，以及中文一個字算幾個 token；第 9 章是自己架 model 時才調的 sampling。符號、公式，以及這堂沒展開的其他 model 架構方向，收在最後的〈查閱〉，需要時再查。

1Request lifecycle：Prefill 決定 TTFT，Decode 決定每個 token 的間隔

從送出一段 prompt，到畫面上一個字一個字冒出回答，serving 系統（把 model 放在 GPU 上、替很多使用者回答 request 的程式）做了六件事：

圖上灰色的四段不用 GPU。Tokenize（①）把文字切成 token，每個 token 換成一個整數 ID，例如 Llama 3 的 tokenizer 把「 is」換成 374；detokenize（⑤）反過來，把 ID 換回文字。Model 只看得到這串整數，怎麼切、中文為什麼特別，留到第 8 章。Schedule（②）決定 GPU 接下來要一起算哪幾個 request，一起算的那一批叫 batch，stream（⑥）把字送給使用者。只有 ③ 和 ④ 是 GPU 上的 model 在算。

Next-token generation：分成 Prefill 與 Decode 兩段。Model 的輸出是一張表：詞彙裡的每個 token 一個機率，代表它接在後面的可能性。挑一個 token 接上去，再把加長的序列送回 model，才能算下一個。所以生成一段回答是一個 loop，回答有幾個 token，loop 就跑幾圈。

Prompt 和 output 在這個 loop 裡的待遇不同。Prompt 的 token 一開始就全部知道，可以一起算，這一段叫 prefill；output 的 token 要等上一個算完才知道，只能一個一個算，這一段叫 decode：

兩段各決定使用者感受到的一個數字，

  • TTFT（time to first token）。按下送出到第一個字出現，主要是排隊（②）加 prefill。Prompt 越長，prefill 越久。
  • 每個字的間隔。之後每個字都要等一步 decode，常用每秒幾個 token（tokens/s）表示。回答越長，總時間越長。

兩段的瓶頸也不同。Prefill 吃算力，decode 吃記憶體頻寬（每秒能從記憶體讀出多少資料）：prefill 一次算幾千個 token，讀一遍參數的時間由這幾千個 token 分攤，GPU 的運算單元是忙的；decode 每一步只替每個 request 算 1 個 token，卻要把整個 model 的參數（也叫權重，weights）從記憶體讀一遍，運算單元多半在等資料。第 4 章用數字算這件事，GPU 為什麼算得快、讀得慢，見 L10〈Roofline〉。優化前要先知道使用者在等哪一段。

KV cache 在 request 裡的角色：Prefill 留下、Decode 每一步都要讀，跟著 context 變大。Prefill 除了產生第一個 token，還會把 prompt 每個 token 在 model 的每一層（第 2 章）算出的兩組中間結果存起來，這兩組叫 key 和 value，合稱 KV cache。之後每一步 decode 都要讀它，也在後面加一格。它為什麼存在、有多大，是第 3、4 章的主題；這裡先記住兩件事：它跟著 context 的長度變大，而且 request 還在跑的時候，一直佔著 GPU 記憶體。Context 指到目前為止的整段輸入：prompt，加上已經產生的 token。

Continuous batching：scheduler 每一步重組 batch，KV cache 記憶體不夠時新 request 要排隊。Request 一個一個獨立地來，GPU 卻要一次算一批才有效率，理由在第 4 章。所以 scheduler 每算完一步，就重新組一次 batch：做完的 request 立刻離開，新的 request 不用等整批結束就能加入（先做它自己的 prefill，再和其他 request 一起一步一步 decode），這叫 continuous batching：

能不能再收一個 request，看的是記憶體：每個 request 的 KV cache 各佔一份，KV cache 放不下時，新的 request 只能排隊，或由 scheduler 先暫停一個正在跑的（preempt）。Batching 與記憶體分頁的做法，後面的講次會講。

Decode 的停止條件：stop token、max_tokens、使用者斷線。Decode 停在三種情況：model 產生 stop token（代表「說完了」的特殊 token）、長度到了上限（API 的 max_tokens）、使用者斷線。早一點停，KV cache 的記憶體就早一點釋放，可以收下一個 request。

Agent 的 request：每一圈重送整段 context。L4〈根本的限制〉說過，model 沒有記憶，所以 agent（自己呼叫工具、一圈一圈做事的程式，每一圈呼叫一次 model）每一圈都把整段 context 重送。對 serving 系統來說，重送的每個 token 都是一份 prefill 的工作，也佔一份 KV cache。L8〈Prefix cache〉講的 prefix cache，是 serving 系統把上一圈的 KV cache 留著，下一圈開頭相同的部分直接拿來用、不用重算；但那一段的 KV 仍然要放在 GPU 記憶體裡，decode 的每一步也照樣要讀：

所以 prefix cache 省下的是算力和 TTFT，省不下記憶體。

2Transformer 的結構、參數與運算量

上一章把 model 當成黑盒子：輸入一串 token ID，輸出下一個 token 的機率。這一章打開它：現在的語言模型幾乎都是同一種架構，叫 Transformer。下面看它裡面有哪些零件、參數放在哪裡。後面的帳都從這裡算起，例子一律用 Llama 3 70B。

Embedding：token ID 查表變成 vector。Model 不能直接拿整數 ID 做運算，所以第一步是查表。Embedding table 是一張 128,256 列、8,192 欄的表，每個 token ID 對應一列；查到的那一列有 8,192 個數字，叫這個 token 的 vector，可以想成一個長度 8,192 的 list[float]。這些數字是訓練出來的，意思相近的 token，vector 也相近。

整段 prompt 有 n 個 token，就疊成一個 n 列、8,192 欄的矩陣，寫成 X（n × d）。d = 8,192 是 model 的寬度，之後每一層都在這個形狀的矩陣上運算。

矩陣乘法的 FLOPs：一個 token 乘過一個矩陣，運算次數是參數數的 2 倍。一個 n × d 的矩陣乘上一個 d × k 的矩陣，得到 n × k 的矩陣。結果的每一格，是一列和一欄的對應位置相乘再加總，要做 d 次乘法和 d 次加法。所以整個乘法要 2 × n × d × k 次浮點運算，單位叫 FLOP（floating-point operation）：

W 裡的每一個數字就是一個參數（parameter）：訓練時調整，推論時固定不變。Model 的大小說的就是參數的總數，Llama 3 70B 有 70.6B（706 億）個。上面最後一行是後面會用到的關鍵：一個 token 乘過一個矩陣，運算次數是那個矩陣參數數量的 2 倍。

Transformer block：Attention 與 FFN 兩個子層，重複 80 次。

每個 block 有兩個子層，分工不同：

  • Attention。讓 token 之間交換資訊，例如處理「它」這個字時，去前文找「它」指的是誰。這是 token 唯一看得到其他 token 的地方，下一章專門講。
  • FFN（feed-forward network）。對每個 token 各自運算，不看其他 token。Llama 3 的 FFN 有三個矩陣（這種設計叫 SwiGLU）：兩個 d × dff 的矩陣把 vector 從 8,192 維撐到 dff = 28,672 維，再用一個 dff × d 的矩陣壓回來。

每個子層的輸出不取代輸入，而是加回去：h = x + Attention(RMSNorm(x))。所以有一條 vector 從第一層流到最後一層，叫 residual stream，每個子層只在上面加一筆修正。最後一層的 vector 乘上 LM head（一個 d × V 的矩陣，V = 128,256 是詞彙表的大小），得到 128,256 個分數，每個候選 token 一個，叫 logits；softmax 再把分數變成加總為 1 的機率。

名詞RMSNorm、pre-norm、residual：讓 80 層疊得起來的三個設計

RMSNorm 把 vector 除以它的均方根（root mean square），再乘上每一維一個學到的係數，讓數值的大小維持穩定。

Pre-norm 是先 normalize 再進子層，這讓很深的 stack 訓練得穩。Residual 讓每個子層只學一筆修正，加回原本的 vector。

這三樣對 serving 的帳幾乎沒有影響：norm 每層只有 2 × 8,192 個參數，80 層合計不到總數的萬分之一。

參數的分布：FFN 佔八成，Attention 不到兩成。把每個矩陣的形狀乘起來，就是參數的數量。下表的數字用 python 驗算過；norm 的參數太少，表上略去。公式裡的 d、dff、V 上面都出現過；attention 那一列的 H、Hkv、dk 和 head 有關，下一章才講，這裡先看結果。全部符號的定義見〈查閱〉：

零件公式參數
Attention，每層2·d·H·dk + 2·d·Hkv·dk151M

這釐清兩件常混在一起的事：attention 的計算量會隨 context 變長而增加（下一章），但 model 的大小主要在 FFN。

Weights 的大小與每個 token 的 FLOPs：由參數總數 N 直接算出。參數總數 N 確定之後，有兩本帳可以直接算，而且都和 prompt 多長無關：

  • 權重有多大：N × 每個數字的 byte 數。BF16（一種 16 bit 的浮點格式）每個數字 2 byte，70.6B 個參數就是 141 GB。改存 FP8（1 byte）是 71 GB，4 bit 是 35 GB；怎麼壓而不掉品質，後面的講次會講。
  • 每個 token 要算多少：約 2 × N 次運算。上面的 numpy 例子已經看到，一個 token 乘過一個矩陣，運算次數是參數數量的 2 倍。一個 token 走過整個 model，每個參數都參與一次乘和一次加，所以約 141 GFLOP（1,410 億次）。Embedding table 是查表、不用算，但它只佔參數的 1.5%，可以忽略。

和長度有關的運算，只有 attention 裡 token 互相讀取的那一段，下一章講。第三個數字（KV cache）也在那裡。

3Attention 與 KV cache

FFN 對每個 token 各自運算，看不到別的 token。要知道「它」指的是誰，「它」必須能讀前文，這就是 attention 的工作。

Query、Key、Value：每個 token 在每一層產生的三個 vector。每一層的 attention 先把每個 token 的 vector 乘上三個 weight 矩陣，得到三個 vector：query（q）、key（k）、value（v）。Llama 3 70B 把這件事拆成 64 份平行做，每一份叫一個 head，每個 head 的 q、k、v 各長 dk = 128；64 × 128 = 8,192，剛好是 d（head 的細節在本章後面）。可以把它想成一次搜尋：正在讀的 token 拿 q 當搜尋的字串，前面每個 token 是一份文件，有自己的關鍵字 k 和內文 v；先拿 q 和每個 k 比對出分數，再依分數把各份內文 v 混在一起。整段 prompt 一起算時，就是三次矩陣乘法：

Attention 的算法：內積分數、Causal mask、Softmax。Token i 讀 token j 的分數，是 qi 和 kj 的內積：對應位置相乘再加總，越大代表越相關。一次算全部，就是 S = QKᵀ ÷ √dk，S 是 n × n 的矩陣，第 i 列是 token i 對每個 token 的分數。接著有兩步：

  1. Causal mask。Model 訓練時就是只看前文猜下一個 token，所以不論 prompt 還是 output，token i 都只能讀 j ≤ i 的 token，對角線右上方的分數設成 −∞。
  2. Softmax。把每一列的分數變成加總為 1 的權重，得到 A。

最後 O = A × V：每個 token 的輸出，是前面各個 token 的 v 依權重加起來。

名詞為什麼要除以 √dk

q 和 k 的內積是 128 個乘積的和，維度越大，數值通常越大。

太大的分數進 softmax，權重會幾乎全部集中在一個 token，訓練會學不動。

除以 √dk（√128 ≈ 11.3）把分數拉回穩定的範圍。這是 2017 年 Attention Is All You Need 的設計，見原文出處。

Attention 的成本：n 個 token 要算 n² 個分數。每一層、每個 head 都要替每一對 token 算一個分數，n 個 token 就是 n × n 個，所以 context 加倍，分數變 4 倍。每一層約 4n²d 次運算：照第 2 章矩陣乘法的算法，64 個 head 合起來，算分數的 QKᵀ 是 2n²d 次，依權重加總 v 的 AV 也是 2n²d 次。Causal mask 讓實際要算的約少一半。S 本身有 n² 格，context 一長就存不下，所以實作上用 FlashAttention 一塊一塊算 softmax，從不存下完整的 S（L10b〈FlashAttention〉）。

KV cache 的原理：前面 token 的 K、V 不會變，存起來不重算。回到第 1 章的 decode。新的 token 要讀前面全部的 token，需要它自己的 q，加上前面每個 token 的 k 和 v。前面 token 的 k、v 不會變，因為 causal mask 讓 token j 只受 j 之前的 token 影響，後來的 token 改變不了它。所以算過一次就存起來：

有了 cache，每一步 decode 只替 1 個新的 token 算 q、k、v，再讀整份 cache。沒有 cache，每一步都要把前面所有 token 重算一遍，生成 n 個 token 的總工作量隨 n² 成長。KV cache 是用記憶體換掉重算：每個 token 在每一層都留下一組 k 和 v，直到 request 結束。

Multi-head attention（MHA）：切成 64 個 head，運算量不變。回到本章開頭的 head：Llama 3 70B 把 d = 8,192 切成 H = 64 個 head。Multi-head attention 原本的做法是每個 head 有自己的 128 維 q、k、v，各自做一次上面的 attention（Llama 3 的 k、v 是幾個 head 共用一份，下一節講）；64 個輸出接起來，再乘上 WO 混回 8,192 維。64 × 128 = 8,192，所以切成 head 不增加運算量，只改變 model 學到什麼。例如有的 head 專看前一個 token，有的看第一個 token，有的看整段 context。

GQA：query head 共用 K、V，每個 token 的 KV cache 縮成 320 KiB。KV cache 的大小和 KV head 的數量成正比。GQA（grouped-query attention）讓一組 query head 共用一份 k 和 v：query head 的數量不變，存的 k、v 變少。MQA（multi-query attention）更極端，所有 query head 共用一份：

名詞FLOP/s、TB/s、GB：本章用到的三個 GPU 規格

算力是每秒做幾次浮點運算。2 張 H200 合計 1,978 TFLOP/s（BF16），也就是每秒 1.978 × 10¹⁵ 次。

頻寬是每秒能從 GPU 記憶體（HBM）讀幾 byte，合計 9.6 TB/s。容量是 GPU 記憶體多大，合計 282 GB。

Weights 的大小決定 Decode 一步的時間：所以 Decode 要 batch。Decode 每一步都要把 141 GB 的權重從記憶體讀一遍，才能替每個 request 算出 1 個 token。2 張 H200 每秒讀 9.6 TB，讀一遍要 14.7 毫秒，所以 batch 只有 1 個 request 時，一個 request 每秒最多約 68 個 token，算力再強也一樣。這就是 decode 必須 batch 的原因：同一份權重讀一次，batch 裡每個 request 都能用；但每個 request 的 KV cache 各是一份，要各讀各的，分攤不掉。為什麼 GPU 算得快、讀得慢，見 L10〈Decode〉。

  • 讓每個數字變小。KV 改存 FP8，預算加倍成約 86 萬個 token。
  • 加 GPU。容量變大，但權重也可能要切到多張卡。

  • Prefill。只算新的 3K：每個新 token 走過所有參數，還要讀前面 100K 個 token 的 K、V，合計約 1.22 PFLOP，0.62 秒。沒有 cache 時整段 103K 重算，是 28.4 PFLOP、14.4 秒，差 23 倍。
  • 記憶體。Decode 時 103K 個 token 的 KV cache 都要在 GPU 上，33.8 GB，有沒有命中都一樣，約是權重的四分之一。

5MoE（Mixture of Experts）：每個 token 只用幾個 expert

第 2 章說 FFN 佔了八成的參數，而且每個 token 都要走過整個 FFN。MoE（mixture of experts）改掉這一點：把一個大 FFN 換成好幾個小 FFN，每個叫一個 expert，每個 token 只用其中幾個：

Router 是一個小矩陣，替每個 token 給每個 expert 一個分數，挑分數最高的 2 個（top-2），兩個 expert 的輸出再依分數加權相加。同一個 token 在不同層、不同 token 在同一層，都可能挑到不同的 expert。

Total 與 Active 參數：各管記憶體與運算。第 4 章的三個數字，在 MoE 上分開看：權重的記憶體看總參數（total）；每個 token 的運算看 active 參數，也就是這個 token 實際用到的幾個 expert，加上每個 token 都要走的 attention 等部分；KV cache 不受影響，因為 MoE 只換掉 FFN，attention 照舊，第 3 章的公式照用。

MoE 的適用條件：記憶體夠、要每個 token 算得快。MoE 常被說成拿記憶體換運算，那是和每個 token 運算量相同的 dense model 比：同樣的運算，MoE 要放的參數是它的 3.6 倍（Mixtral）到 18 倍（DeepSeek-V3）。和品質相近的 dense model 比，運算少很多，記憶體則有多有少，就是上一段的 Mixtral 和 DeepSeek-V3。所以記憶體夠、要的是每個 token 算得快，例如 prefill 很重、要高 throughput 時，它划算；GPU 記憶體有限、必須放進固定幾張卡時，總參數就是門檻，active 再小也幫不上。

MoE 的 Decode：batch 越大，要讀的 expert 越多。第 4 章說 decode 每一步都要讀權重。Batch 裡只有 1 個 request 時，這一步只有 1 個 token，每一層只讀它挑中的 expert；但 batch 裡的 token 各挑各的，挑中的 expert 加起來會變多。假設 router 平均分配，每一層至少有一個 token 挑中的 expert 比例如下（本文的推算）：

6改 KV cache 的架構：Sliding window、MLA、Linear attention、SSM、Sparse attention

第 4 章的帳裡，最難擴充的是 KV cache：它跟著 context 長度和人數一起長。所以近年的架構多半在改它。做法有五類：前四類讓存的量變少，第五類存的量不變，只讓每一步讀的量變少。下圖把它們和完整的 attention 並排，linear attention 和 SSM 併成一格：

Sliding window attention：大多數層只存最近 w 個 token。一般的 attention 讓最後一個 token 讀前面全部 n 個；sliding window 只讓它讀最近 w 個，所以這一層的 KV cache 最多存 w 個 token，不再隨 n 成長：

代價是這一層看不到更遠的內容，所以通常留幾層 global（讀全部）負責長距離的記憶。例如 Gemma 3 每 5 層 local（w = 1,024）配 1 層 global。照這個比例，128K context 時只有 1/6 的層存滿 128K，其餘只存 1,024，總量約是全部 global 的 1/5.8。

MLA：每個 token 每層只存一個壓縮過的 latent。MLA（multi-head latent attention）不存每個 head 的 k 和 v，改存一個短的 latent vector c，要做 attention 時再從 c 還原出 K、V：

實作上，decode 時不必真的把每個 token 的 K、V 還原出來：還原用的矩陣可以事先併到 query 那一邊，直接拿 latent 算分數。代價是 latent 比一個 head 的 k 長，每個 head 都要對它算一次，比讀現成的 K、V 多算一些。圖上另外存的那 64 個數是記位置用的（RoPE，把 token 的位置編進 q、k 的方法），不跟著壓縮。

Linear attention：用固定大小的 state 取代 KV cache。一般的 attention 每多一個 token，cache 就多一筆，一直到 request 結束。Linear attention 改成維護一個固定大小的 state，寫成矩陣 S（和第 3 章 n × n 的分數矩陣 S 是兩回事），大小是 dk × dv：key 的長度乘 value 的長度，例如 128 × 128。每個新 token 把它的 k 和 v 做外積（k 的每一格乘 v 的每一格，得到一個 dk × dv 的矩陣），加進 S；要輸出時，用 q 乘 S，得到一個長度 dv 的 vector。所以不論讀過多少 token，S 都一樣大：

Gated DeltaNet 是其中一種，它把「加進 S」改成兩步，就是圖中的 ① 和 ②。第一步，用 decay gate αt（0 到 1 之間的一個數）把整個 S 乘小一點，讓舊的內容淡掉。第二步，先用新 token 的 k 從 S 讀出它原本記的 value，再依 write gate βt 決定換掉多少，換成新的 v；所以同一個 key 再寫一次，會更新它記的值，不會再疊一份上去。

固定大小的代價是記不住全部細節，所以實際的 model 混著用：Qwen3-Next 的 48 層裡，36 層是 Gated DeltaNet、12 層是一般的 attention（3:1），只有那 12 層存 KV cache。Kimi Linear、Qwen3.5 也是同一種配方。

State-space model（Mamba）：也是固定大小的 state，vector 的每一維各留一個。SSM（例如 Mamba）也維護固定大小的 state，差別在形狀：linear attention 的 state 是一個 dk × dv 的矩陣；Mamba 替 token 的 vector 的每一維各留一個很短的 vector h，每一維叫一個 channel，所以 d 維的 vector 有 d 個 channel。Mamba 屬於 selective SSM：決定「舊的 h 留多少、新的輸入寫多少」的兩個係數 Ā、B̄，由每個 token 的內容算出來，所以這一層能自己決定記住什麼。

Sparse attention：KV 全部照存，每一步只讀 top-k 個 token。DeepSeek-V3.2 的 sparse attention（DSA）先用一個便宜的 indexer 替前面每個 token 打分數，挑出分數最高的 2,048 個，attention 只讀這些：

選 model：每個 token 的 KV cache 和參數量一樣重要。本文的判斷是，這個差距會改變選擇：Qwen3-32B 的權重 65.6 GB（BF16），比 Qwen3-Next-80B-A3B 的約 160 GB 小得多，但一個 128K 的 request，Qwen3-32B 的 KV cache 要 34.4 GB，Qwen3-Next 只要 3.2 GB；同樣 2 張 H200，前者放得下 6 個這樣的 request，後者約 37 個。要同時跑很多長 context 的 agent，比較大的 model 反而放得下比較多人。

8Tokenizer 與中文的 token 數

第 4 章的帳都以 token 計，所以要先知道一段文字是幾個 token。常見的經驗值是 3 到 4 個字元一個 token，那是英文；我們讀寫的是繁體中文，數字差很多。

BPE：從 byte 開始，合併最常相鄰的兩塊。現在的 model 多半用 byte-level BPE（byte pair encoding）建詞彙表：先把文字轉成 UTF-8 的 byte，256 種 byte 各是一個基本單位；接著在大量文字裡找最常相鄰出現的一對，合併成一個新單位，重複幾十萬次。因為最底層是 byte，任何文字都切得出來，不會有不認得的字：

Vocabulary size：詞彙越大 token 越少，embedding 越大。詞彙表大，常見的字串更可能是一個完整的 token，同一段文字就切得比較少。Llama 3 把詞彙從 Llama 2 的 32K 擴到 128K，論文說英文從每個 token 3.17 個字元進步到 3.94 個。代價在第 2 章的表：embedding 和 LM head 的大小是 2 × V × d，Llama 3 70B 的 2.1B 個參數就在這裡，LM head 每一步也要替 128,256 個 token 各算一個分數。

中文的切法：一個字是 3 個 byte，切成幾個 token 看詞彙表。一個中文字在 UTF-8 裡是 3 個 byte。詞彙表收了這個字，它就是 1 個 token；收了常見的詞，幾個字合成 1 個 token；兩樣都沒收，就拆成 byte 片段：

Token 數的影響：估 context 用量、選 model、prompt 用哪種語言。

  • 估算。繁體中文在現在的 tokenizer 上，1,000 個 token 約 1,100 到 1,400 個字；一個 128K 的 context window 約放 14 萬到 18 萬字。
  • 選 model。Tokenizer 的效率乘在每一本帳上：prefill 的運算、KV cache、decode 的步數、API 的帳單都和 token 數成正比。同一段繁體中文，Llama 3 比 DeepSeek-V3 多 25% 的 token。專門擴充繁體詞彙的 model 差得更多：聯發科的 Breeze-7B（2024）在 Mistral 7B 的詞彙上加了約 3 萬個繁體中文 token，報告說同一段中文切出的 token 約是 Mistral 7B 的一半，推論也快約 2 倍。
  • 同一件事用中文寫，不會比較省。中文字的資訊密度高，但一個字的 token 也多。2026-04 一篇初步研究（樣本小，只看方向）把同一批程式題的敘述寫成中文和英文：中文的 token 數是英文的 0.92 到 1.15 倍，看 tokenizer 而定，解題率反而比較低。

三件事之外，估帳時還要記得一個前提：token 數是 tokenizer 的性質，不是文字的性質，換一代 model 就可能變。Claude 的官方文件說，Claude 4.7 之後的 model 換了新的 tokenizer，同一段文字約多 30% 的 token。所以要估自己的帳，用你要用的那個 model 實際數一次：open-weight model 用它 repo 裡的 tokenizer.json，Claude 用 API 的 count_tokens 端點（2026-11 查官方文件）。

Streaming 的 detokenize：不完整的 UTF-8 byte 先暫存。Tokenizer 把一個字拆成 byte 片段時，detokenize 會遇到一個問題。Llama 3 把「帳」切成兩個 token，第一個只帶來 E5 B8 兩個 byte，還不是一個完整的字，印不出來：

所以 serving 系統把不完整的 byte 先留著，等下一個 token 補上，才把整個字送出去。英文很少碰到，中文常常碰到，自己寫串流的程式時要處理。

9Sampling：Temperature、Top-k、Top-p

第 1 章說 model 每一步輸出一張機率表，sampling 決定從表裡挑哪一個。同一個 model、同一段 prompt，sampling 的設定不同，答案和長度都會不同。

Temperature：把 logits 除以 T，控制機率集中或攤平。LM head 給每個 token 一個分數 z（logit）。Softmax 把分數變成機率：先算 e 的 z 次方，再除以全部的總和。Temperature T 在這之前把每個分數除以 T：T 小於 1，高分和低分的差距拉大，機率集中到最高分；T = 0 等於每次都挑最高分，叫 greedy decoding；T 大於 1，分布變平，冷門的 token 也有機會。

Top-k 與 Top-p：只從機率最高的幾個 token 裡抽。Top-k 只從機率最高的 k 個 token 裡抽，例如 top_k = 50，k 是固定的。Top-p（也叫 nucleus sampling）從高到低累加機率，取最少的幾個 token 讓總和達到 p，例如 top_p = 0.9，所以留幾個看 model 有多少把握：

Sampling 對輸出長度的影響：greedy 可能重複不停，要設 max_tokens。每一步都可能抽到 stop token，也可能抽到別的，所以設定會改變回答在第幾步結束，也就改變 decode 的步數、時間和成本。Greedy 有一個已知的陷阱。Qwen3 有兩種模式：thinking mode 先寫出一段推理再回答，non-thinking mode 直接回答；它的官方 model card 說 thinking mode 不要用 greedy decoding，會讓表現變差，還可能無止境地重複。它建議的值是 Temperature 0.6、TopP 0.95、TopK 20。所以不論設定是什麼，都要設 max_tokens，讓第 1 章的長度上限替你停下來。

Temperature 0 的 nondeterminism：batch 一變，輸出可能不同。同一個 prompt 在 serving 系統裡，每一步和不同的 request 排在同一個 batch；batch 的大小一變，GPU 的加總順序可能跟著變，浮點數的結果差一點點。碰到兩個 token 分數很接近時，就會挑到不同的 token，之後整段都不一樣。原因與量測見 L1〈浮點數沒有結合律〉。

託管 model 的 sampling 參數：Claude Opus 5.5 不接受，設定主要用在自架。2026-11 查 Claude Opus 5.5 的 migration guide：request 帶 temperature、top_p、top_k 會被拒絕（回 400），要改用 prompt 引導行為；文件也提醒，舊 model 上設 temperature = 0 也從來不保證相同的輸出。所以這一章的設定，主要用在自己架的 open-weight model：先照 model card 的建議值，再用自己的 eval 驗證（L7b〈建立評估〉）。

進階架構裡，第 6 章講了五類改 KV cache 的做法。另外三個方向改的是深度或生成的方式，還沒有成為主流，serving 的帳一樣用三個數字算：

查閱Looped transformer：深度用運算換，不用參數換

結構是三段：開頭的 prelude P、重複 K 次的 block R、收尾的 coda C。多跑幾圈不增加參數，K 圈的運算是 R 的 K 倍。

Geiping 等人（2025）用 800B token 訓練了一個 3.5B 參數的 looped model。他們把 K 一路加大，直到每個 token 的運算量和一個 50B 參數的 model 一樣多；在這段範圍裡，推理題的表現隨 K 變大而提升，有時提升很多（摘要比的是運算量，沒有說表現追上 50B 的 model）。

用三個數字看：weights 不變；每個 token 的 FLOPs 乘上 K；KV cache 看實作，每一圈的 attention 如果各存一份，也跟著乘上 K。每一圈要等上一圈算完，所以延遲也跟著 K 增加。

查閱Diffusion LM：一次填好幾個 token，每一步都重讀權重

LLaDA（2025）是從頭訓練的 8B masked diffusion model，用了 2.3T token，表現和 Llama 3 8B 接近。

每一步整段的 token 都可能改，前面 token 的 K、V 跟著變，所以 KV cache 用不上。生成 n 個 token 不再需要 n 步，步數變成延遲與品質的取捨。

查閱Multi-token prediction：一次多預測幾個 token

另一個方向是 multi-token prediction：訓練時讓 model 除了下一個 token，也預測再後面的 token。

DeepSeek-V3 用它當訓練目標：在主 model 後面多接預測用的小模組，每個模組多預測後面一個 token。技術報告說，推論時可以直接丟掉這些模組，也可以拿它們來做 speculative decoding（先猜幾個 token，再讓 model 一次驗證），加速生成；speculative decoding 是後面講次的主題。
