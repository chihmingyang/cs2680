先看這裡

L2 到 L4 看的都是一個 agent。這堂從一個 agent 走到多個 agent，回答三個問題：要不要拆、怎麼拆、拆開之後怎麼溝通。三個答案背後是同一條限制：多一個 agent 只是多一個 loop，兩個 loop 的 context 互不相通，agent 之間只能靠文字傳話。所以每個答案都碰到分散式系統的老問題，而且每一則訊息都是某個 context 裡的 token。

  • 先問要不要拆。拆開只換到四樣東西：specialization、isolation、parallelism、context management；代價是每一次交接都遺失資訊、多一份 context、多一個會失敗的點。一個 agent 常常就夠了。
  • 架構 = 三張圖。Control graph 決定誰協調，communication graph 決定誰和誰說話，task graph 決定工作怎麼拆。八種架構是這三張圖的不同組合，弱點從線就讀得出來；子任務要寫成八個欄位的規格，而且拆得越細不一定越快。
  • 溝通是分散式系統問題。訊息的外層欄位給 runtime、內容給 LLM。Timeout 之後你不知道對方做了沒，重試時用 task_id 當 idempotency key，才不會做兩次。A2A 和 MCP 只標準化溝通，不管 orchestration。

這篇可以不看 slides 從頭讀到尾：每個名詞在第一次出現的地方就有解釋，由淺入深，頁碼只是出處。少見的名詞和別堂講過的東西收在正文裡的「名詞」「前情」註，碰到不懂的再點開。想對照 slides，就在讀到頁碼時打開那幾頁；想先帶著問題讀，就先看第 3 段的基礎題。讀書會前用第 3 段的進階題。

1 · 架構

Multi-agent 系統的零件怎麼接在一起

先把兩個名詞定下來。Agent 是 L4 講的那個 loop：一個 model 加 harness，harness 替它執行 tool、組 context。Multi-agent 系統就是好幾個這樣的 loop，每個有自己的 context window，彼此只能靠訊息傳話。上方的三個框是這堂描述任何架構的語言：誰協調、誰和誰說話、工作怎麼拆。下方四格是四種常見的接法，每格最後一行是它在三張圖上的答案。

讀圖的重點是看線。Supervisor–worker 的線全部匯到中心，所以中心的 context 長得最快；pipeline 只往下一站送，所以要補一條回頭的 retry edge；blackboard 的線都經過工作區，問題變成一致性；swarm 的線隨 n² 成長。線越多，context 和 token 的成本越高，所以 slide 的原則是「照相依關係連線」。第 2 段從 2.1 的三張圖開始，依序把八種架構、子任務的規格與粒度、訊息的格式、分散式系統的難題和兩個協定講清楚。

A · 要不要拆

2.1多一個 agent：只換到四樣東西，每一樣都有價格 p.5–7

L2 到 L4 看的都是一個 agent：一個 loop、一組 tool、一個 context window。這一章先把「第二個 agent」是什麼講清楚，再看多一個 agent 能換到的四樣東西、各自的價格，最後用三張圖建立之後每一章共用的語言。

第二個 agent 是什麼。L4 的 2.1 說，一個 agent 是 model 加 loop：model 每一圈決定下一步，harness 執行 tool、把結果放回 context。第二個 agent 就是第二個 loop，它有自己的 system prompt、自己的 tool 清單、自己的 context window。兩個 loop 之間沒有共用的記憶，所以 agent 之間只能靠文字傳話：一個 agent 把一段文字送出去，另一個 agent 把它放進自己的 context。Slide p.5 說 multi-agent 系統有幾十年的研究史，這堂不講歷史，只講今天用 LLM 做時會碰到的事。

四樣換得到的東西。既然多一個 agent 只是多一個 loop，它能換到的東西也只有四種（p.6）：

  • Specialization。每個 agent 用不同的 model、prompt、tool。Review 程式碼的 agent 可以配較強的 model 和一份只講安全的 prompt；改程式碼的 agent 配較快的 model 和 edit tool。一個 agent 做兩件事，prompt 就要同時講兩件事，兩件都講得淺。
  • Isolation。每個 agent 拿不同的權限。讀網頁的 agent 只有 WebFetch，沒有 shell；網頁裡夾帶的指令（L4 2.1 講過的 prompt injection）就算騙過了 model，也碰不到會刪檔案的 tool。這是資安的最小權限原則：每個元件只拿完成工作所需的權限。
  • Parallelism。互不相依的子任務同時跑。查四篇論文的摘要，四個 agent 同時查，時間接近一個 agent 查一篇。
  • Context management。不必把整條 trajectory（從接到任務到現在的全部對話與 tool 結果）交給每個 agent。Worker 只拿到自己的子任務，supervisor 只收回摘要。L4 2.6 講過 context 越長越貴、越慢、越不準，所以這一項換到的是乾淨的 context。

四樣裡只有 parallelism 和速度有關，其他三樣改善的是品質、安全與 context。這個區分之後會一直用到：拆開之前要先問，我要換的是哪一樣。

每一樣都有價格。價格從同一個地方來：兩個 context 互不相通，所以每多一次交接，就多三件事。第一，資訊遺失。Worker 看不到 supervisor 的 context，supervisor 沒寫進規格的事，worker 都不知道；worker 回報時也只回摘要，supervisor 不知道它丟掉了什麼。第二，多一份 context。每個 agent 都有自己的 system prompt 和 tool 定義，這些是每一圈都要重送的固定成本（L4 2.6），n 個 agent 就付 n 份。第三，多一個會失敗的點。訊息會遺失、agent 會 timeout、兩個 agent 會對同一件事有不同的認知；2.7 會把這些失敗逐一講清楚。

換到的東西它改善什麼付出的價格
Specialization品質：prompt 短而專一、model 對得上任務每個角色一份 prompt 與 tool 定義，每圈重送
Isolation安全：注入的指令碰不到危險的 tool需要結果時要跨 agent 傳，不能直接讀
Parallelism時間：獨立的子任務同時做派工與合併的時間，以及拆錯的風險（2.5）
Context management注意力：每個 agent 只看自己需要的交接時遺失細節，而且下游不知道丟了什麼

所以 slide p.44 的第一條設計原則排在所有架構之前：先問真的需要 multi-agent 嗎。一個 agent 夠用的任務，多加 agent 只會加成本和複雜度。本文延伸〈一個 agent 常常就夠了〉有量化的證據。

三張圖描述任何架構。決定要拆之後，slide p.7 用三個問題描述任何一種架構，每個問題是一張圖：

  • Control graph：誰協調？誰能派工、誰能停工。答案可以是一個 supervisor、一層層的 hierarchy，或是沒有人。執行中也可以換人，叫 handoff（把控制權交給另一個 agent）。
  • Communication graph：誰和誰說話？訊息走哪條線。答案可以是直接傳訊、broadcast（一則訊息送給所有人），或是一個共享的工作區，大家讀寫同一個地方。
  • Task graph：工作怎麼拆？誰相依誰。答案可以是 planner 事先拆好、agent 對任務出價認領，或是從局部規則浮現，沒有人事先規劃。

三張圖是三個獨立的軸。同樣拆成三個子任務（task graph 相同），可以由 supervisor 派工，也可以讓 agent 從一份共享的 task list 自己認領（control graph 不同）；同樣由 supervisor 協調，worker 之間可以沒有線，也可以互相傳訊（communication graph 不同）。所以 架構的名字只是三張圖的一種組合，拿到任何系統，先把三個問題各答一句，比記名字有用。2.2 和 2.3 會用這個方法看八種架構。

本文延伸｜一個 agent 常常就夠了不是 slide 的內容

第 5 段延伸閱讀的數字支持 p.44 的第一條原則。Towards a Science of Scaling Agent Systems 測了 260 種設定：和單一 agent 相比，表現從 +80.8%（可分解的財務推理）到 −70.0%（循序規劃）。單一 agent 已超過約 45% 準確度的任務，多加 agent 反而變差。Anthropic 說 multi-agent 系統的 token 約是聊天的 15 倍。

Cognition（Devin 的開發公司）的立場更強：actions carry implicit decisions。兩個 agent 各做一半，隱含的決定會互相衝突，例如一個選了某種視覺風格，另一個選了另一種。他們建議從單線程的 agent 開始，長任務靠 context 壓縮撐住。

把這些證據收成一個設計 review 的問題：拿掉一個 agent，品質掉多少？掉得不多，就先不要加。四樣換得到的東西裡，只有 parallelism 和 isolation 是一個 agent 做不到的；specialization 和 context management 常常可以用 L2 的 skill 與 subagent，或 L4 的 context 管理做到一部分。

B · 怎麼拆

2.2中心化的四種架構：線都經過一個點，弱點也在那一點 p.8–11、p.14

有了三張圖，就可以逐一看架構。Slide p.8 列了八種，之後每一頁講一種，頁底寫它在三張圖上的答案：

  1. Supervisor–worker。一個 agent 規劃、派工、整合。
  2. Hierarchical。Supervisor 再管 supervisor。
  3. Pipeline / DAG。固定的階段，一站傳一站。
  4. Blackboard。透過共享狀態協調。
  5. Committee / debate。各自回答，再裁決。
  6. Market / auction。Agent 對任務出價。
  7. Swarm。同儕直接協商。
  8. Dynamic topology。執行中增減、改接 agent。

p.18 的總表把它們分成三類：中心化（1、2、3、6）、去中心化（4、5、7）、混合（8）。「中心化」的意思是 control graph 有一個點決定誰做什麼，所以這一類好預測、好 debug，弱點也都在那一個點附近。這一章講中心化的四種，每一種依「機制、適合什麼、弱點、三張圖的答案」的順序走；2.3 講另外四種，再把八種排成一張表。

Supervisor–worker：一個規劃，多個執行。一個 supervisor 把任務拆成子任務，派給 worker，收回結果後整合（p.9）。Worker 只看到自己的子任務，看不到整個任務，也看不到其他 worker 在做什麼。Slide 的例子是 supervisor 帶三個 worker：researcher、coder、reviewer。Claude Code 的 subagent 就是這個架構：主對話是 supervisor，每個 subagent 在新的 context 裡做一件事，做完回一份結果（L3 的 2.3）。寫成程式，supervisor 的 loop 長這樣：

Pipeline / DAG：固定的階段，一站傳一站。Pipeline 是一串固定的階段，每個階段一個 agent，前一站的輸出是後一站的輸入（p.11）。每道邊界有一份 typed contract：兩站事先約好傳什麼欄位、什麼型別，例如用一份 JSON Schema（L4 2.2 講過，用 JSON 描述另一份 JSON 該長什麼樣）。Slide 的例子是發票處理，五站：OCR、擷取欄位、比對採購單、核准、入帳。OCR 和擷取之間的 contract 可以長這樣：

DAG 是 pipeline 的一般形式：directed acyclic graph，有方向、沒有環的圖。Pipeline 是一條鏈；DAG 允許一站分給兩站、兩站匯到一站，但仍然不能回頭。因為每站的輸入輸出都有 contract，錯誤會停在出錯的那一站，slide 說這是最便宜的除錯方式：入帳的數字錯了，從後往前看哪一站的輸出先不對。弱點是沒有回頭的路，第四站不能要求第一站重做，例如核准那站發現 OCR 讀錯金額，也只能照錯的往下走。所以 p.11 的經驗法則是：加一條 retry edge，勝過多加一個 agent。Retry edge 是一條讓結果退回上一站重做的線，第 1 段架構圖裡的虛線就是它。三張圖的答案：task 在設計時固定，control 就是順序本身，comms 站到站。

這樣工作會自動流向最便宜又做得到的 agent，中心不必知道每個 agent 的細節。弱點是出價由 agent 自己報：誇大能力的 agent 會得標，T4 node 若謊報 4 秒，就搶到自己做不完的工作。2.8 的 A2A agent card 也有同樣的問題，card 上寫的 skill 是自己宣稱的。三張圖的答案：task 公告後由出價認領，control 由拍賣者裁定，comms 是公告出去、出價回來。

四種放在一起看，中心的角色不同：supervisor–worker 的中心做規劃，hierarchical 的中心有好幾層，pipeline 的中心是順序本身，market 的中心只裁定。但弱點都在控制的路徑上，問題沿著它集中（瓶頸）或擴散（放大、下傳、不實出價）。這個規律在 2.3 會和去中心化的三種對照。

2.3去中心化與混合：沒有中心，弱點變成一致性 p.12–13、p.15–18

中心化的四種，問題都在控制的路徑上。這一章看拿掉中心之後會怎樣：三種去中心化的架構、一種混合的架構，再看真實系統怎麼把幾種混在一起，最後用 p.18 的總表把八種收攏。「去中心化」的意思是 control graph 沒有一個固定的點決定誰做什麼，協調靠共享的狀態，或靠 agent 之間直接協商。

Blackboard：透過共享狀態協調。Agent 之間不直接傳訊息，而是讀寫同一個工作區（p.12）。工作區可以是一個資料庫、一個 vector store、一個檔案系統、一個 git repo，或一張 task graph。Slide 的例子是三個 agent 共用一個 git repo：feature agent、refactor agent、test agent，各自讀 task list、各自 commit，彼此之間沒有線。協調全靠共享狀態，例如一份 task list：

好處有兩個。Agent 可以隨時加入、離開，不必改接任何線：多開一個 docs agent，它讀同一份 task list 就能工作。共享狀態也是持久、可檢查的：任何時候打開 repo，就看得到誰做了什麼，這點 supervisor 的 context 做不到。代價是 slide 列的五個難題，每一個在 git 上都看得到：

  • 一致性（consistency）。Agent B 讀的 task list 是五分鐘前的版本，T1 已經完成，它還當成沒做。
  • 並行控制（concurrency control）。兩個 agent 同時改同一個檔案，commit 時衝突；或兩個 agent 同時認領 T4。
  • 來源（provenance）。這段程式碼是誰、依什麼理由寫的？Commit message 不夠時，沒有人知道。
  • 版本（versioning）。Refactor agent 改了 class 名稱，feature agent 手上的分支還用舊名。
  • 垃圾回收（garbage collection）。做完的 task、過期的筆記沒有人刪，工作區越來越大，每個 agent 讀進 context 的也越來越多。

p.18 把這五個難題濃縮成一個弱點：狀態過期（stale state）。每個 agent 看到的不是同一份狀態，而且系統不會報錯，只是各做各的。三張圖的答案：task 從共享狀態浮現，control 沒有中心，comms 間接，經過工作區。

Committee / debate：各自回答，再裁決。幾個 agent 對同一個問題各自提出答案，互相討論，最後由一個 judge 裁決，或用投票決定（p.13）。例子是作文評分：grader A 和 grader B 各給一個分數，judge 看兩份評語後定案。它適合需要判斷的任務，多一個獨立的意見能抓到單一 agent 的盲點。但 slide 點出一種失敗：agreement without independence，同意了但彼此不獨立。兩個 grader 用同一個 model、讀同一份 context，盲點也相同，兩票同意帶來的新資訊很少。這是 ensemble（把多個判斷合起來）的基本條件：多數決只在錯誤彼此獨立時有效。獨立性要刻意製造：

做法製造什麼獨立性代價
換不同的 model訓練資料不同，盲點不同要維護兩套 prompt，分數的尺度可能不一致

三張圖的答案：task 是同一件事平行做幾次，control 由 judge 決定，comms 是同儕之間先說，再送到 judge。

Swarm：同儕直接協商，沒有協調者。沒有固定的協調者，agent 直接交換發現、互相協商（p.15）。例子是倉庫機器人協商誰去撿哪一張訂單。好處是沒有協調者會卡住或掛掉，同儕來來去去，工作照常進行。但它需要一整套協定，slide 列了五件事：discovery（怎麼找到彼此）、addressing（怎麼指名對方）、synchronization（怎麼對齊狀態）、termination（怎麼知道做完了）、trust（怎麼信任對方的說法）。2.8 的 A2A 就是在標準化前兩件。代價是訊息量：n 個 agent 兩兩都要說話，線數是 n(n−1)/2。4 個 agent 6 條線，10 個 45 條，50 個 1,225 條；每一條線上的每一則訊息都進入某個 context。衝突也難解，兩個 picker 都想撿同一張訂單時，沒有人裁決。所以 slide 說它在產品裡很少用。三張圖的答案：task 在局部協商，control 沒有固定的協調者，comms 全對全。

Dynamic topology：執行中改接。唯一一種混合的架構：agent 在任務進行中加入、移除或改接（p.16）。例子是客服 bot：一般工單只有一個 support bot；工單升級時，才接上 billing agent 和 log agent。好處是容量跟著難度走，簡單的工單維持便宜。弱點是每次執行的形狀都不同，失敗很難重現；本文延伸〈Dynamic topology 難重現，也難除錯〉講原因與對策。三張圖的答案：task 在工作變難時重拆，control 隨 agent 加入而移動，comms 在執行時決定。

真實系統是混合體。Slide p.17 畫了一個生產系統的樣子：一個 supervisor 底下有一個 planner agent，planner 產生一張 dynamic task DAG，分給 coder、researcher、tester、reviewer 四個 agent，四個 agent 都接到一個共享的 git。它同時用了 hierarchy（supervisor 管 planner）、pipeline（DAG）、shared memory（git），還能在需要時重新規劃。Claude Code 的 agent teams 也是混合體：lead 派工是 supervisor–worker，共享的 task list 是 blackboard，teammate 之間直接傳訊是 swarm 的線。

2.4子任務：沿六個軸拆，寫成八個欄位的規格 p.19–21

架構決定誰協調、誰和誰說話；這一章看第三張圖，工作怎麼拆。Task decomposition 的形狀很簡單（p.19）：一個複雜任務拆成幾個子任務，各自做完，再合併成一份結果。難的是兩件事：沿哪個軸拆，以及一個子任務要寫到多清楚。2.5 再講拆多細、以及拆錯會怎樣。

六個軸。Slide p.20 列了六種拆法，每一種沿一個軸切：

  • Data。每個 agent 處理一部分資料：一批文件、一批紀錄、一批檔案。子任務彼此最獨立，合併最容易。
  • Expertise。依專業切：安全、效能、正確性、法律。每個 agent 看同一份東西，但從不同角度看，合併時要去重。
  • Stage。依階段切：規劃、實作、測試、review。這就是 2.2 的 pipeline，子任務有順序。
  • Hypothesis。每個 agent 驗證一個互斥的解釋。Debug 時最常用：一個查 cache、一個查資料庫、一個查最近的 deploy。
  • Tool。依 tool 切：一個查網頁、一個查資料庫、一個跑程式碼、一個讀內部文件。配合 2.1 的 isolation，每個 agent 只拿它那一種 tool。
  • Authority。依管轄範圍切：不同的 agent 在不同的行政範圍裡行動，例如各自只能動自己團隊的 repo。

軸可以疊。Slide 的例子是 review 一個改了 200 個檔案的 PR：先沿 data 軸拆成幾組檔案，再沿 expertise 軸拆成安全與效能，兩個軸疊起來就是一張格子：

為什麼規格要寫到那麼清楚。2.1 的圖說過，worker 的 context 是新的，它看不到 supervisor 的對話、讀過的檔案、做過的決定。對 worker 來說，規格沒寫的事就不存在。所以 slide p.21 要求一份子任務規格要有八個欄位：

  1. 目標（objective）。要做出什麼。少了它，worker 自己猜任務。
  2. 輸入與相關 context（inputs）。Worker 需要知道的事實、檔案、前面的結論。少了它，worker 重做 supervisor 做過的事。
  3. 邊界與排除（boundaries）。哪些不要碰、不要查。少了它，兩個 worker 做重疊的事，或跑出範圍。
  4. 可用的 tool 與權限（tools）。能用什麼、不能用什麼。少了它，worker 用錯 tool，或做了危險的事。
  5. 輸出的 schema（output）。回傳什麼欄位、什麼格式。少了它，結果合併不起來。
  6. 完成的測試（completion test）。什麼情況算做完。少了它，worker 不知道何時停。
  7. 預算與期限（budget）。最多幾次 tool call、幾分鐘、多少錢。少了它，一個 worker 跑很久，拖住全部。
  8. 相依關係（dependencies）。要等誰、誰在等它。少了它，worker 用到還沒產生的輸入。

兩頭都不好。子任務太大，平行度太低，工作還是一件接一件做；太小，排程和溝通的開銷反而吃掉省下的時間（p.22）。Slide 給了一條估算式：

T_multi ≈ T_planning ＋ T_critical_path ＋ T_communication ＋ T_merge

四項各是什麼：

  • T_planning：supervisor 讀任務、寫規格的時間。

2.6溝通的設計空間：四個維度分開選，欄位給 runtime、內容給 LLM p.26–32

拆好了，agent 之間要傳話。Slide p.26 的例子是一個 research agent 收到使用者的問題，分給 web agent、coding agent、data agent，再把三份結果整合成最終答案。這一章把「傳話」拆成四個可以分開選的維度，逐一看每個維度的選項與代價，再看一則訊息該長什麼樣，最後用 p.32 的表把整個設計空間收攏。

四個維度。Slide p.27 把 agent 之間的溝通拆成四個問題：

  • Topology：誰能和誰說話？Supervisor–worker 或 peer-to-peer。這由 2.2、2.3 選的架構決定，就是 2.1 的 communication graph。
  • Medium：資訊怎麼交換？訊息、共享記憶體、檔案、資料庫。
  • Format 與 semantics：一則訊息怎麼組成、表達什麼？自然語言或結構化；它是委派、回報、詢問、交接，還是取消。
  • Channel：資訊怎麼傳？點對點、broadcast、pub/sub、共享狀態、request/response。

四個維度可以分開選，因為它們各管一件事：topology 管線存不存在，medium 管線上搬的是什麼，channel 管搬的方式，format 管搬的東西長什麼樣。同一個 supervisor–worker 的 topology，可以用訊息傳規格、用檔案傳產出；也可以 worker 回報走 request/response，狀態更新走 broadcast。

本文延伸｜溝通的價格是 token 和 context不是 slide 的內容

LLM agent 的通訊成本多一項：每則訊息都進入某個 context，之後每一圈 loop 都重送。一則 2k token 的 broadcast 發給 10 個 agent，每個再跑 20 圈，就是 2k × 10 × 20 ＝ 400k token 的 input。這是 p.44 說「密集的 mesh 很少是好的預設」的原因：線越多，每則訊息重送的次數越多。

所以 multi-agent 系統裡，L4 2.7 的四種 context 管理策略要用在訊息上：admission（這則訊息該不該進這個 context）、offloading（大型產出寫檔案，訊息只帶路徑）、transformation（舊的 UPDATE 讀過就刪）、compaction（最後才摘要歷史）。L8 會算 agent 系統的成本結構。

2.7溝通是分散式系統問題：timeout 之後，你不知道對方做了沒 p.33–36

Envelope 解決了「訊息長什麼樣」，沒有解決「訊息送不送得到」。只要兩個 agent 跑在不同的 process 或機器上，它們之間就是一個分散式系統，而分散式系統有一組幾十年沒變的難題。這一章從 slide 的一個購買例子開始，再列出繼承的六個老問題、多個 agent 同時跑時 runtime 要管的事，最後是 LLM 當黑盒子帶來的新問題。

Timeout 之後，三種情況看起來一樣。Slide p.33 的例子：Agent A 送一則訊息給 Agent B，「購買 8 台 GPU instance」，然後網路 timeout，沒有回覆。B 到底買了沒？從 A 這一側，三種情況長得一模一樣：

實際發生的事A 看到什麼A 不重試A 重試
請求沒送到 B沒有回覆一台都沒買，任務失敗買到 8 台，正確
B 買了，回覆在路上遺失沒有回覆買到 8 台，但 A 不知道買到 16 台
B 還在處理，只是慢沒有回覆可能買到 8 台可能買到 16 台

A 分不出三列，所以不管選哪一欄，都有一列是錯的：不重試可能一台都沒買，重試可能買 16 台。Slide 接著問三個問題：要重試還是放棄？要 at-most-once 還是 at-least-once？exactly-once 做得到嗎？這三個名詞是 delivery semantics，傳遞層能保證什麼。答案是傳遞層只能二選一，exactly-once 要靠應用層補。

名詞Delivery semantics：at-most-once、at-least-once、exactly-once

網路會遺失、延遲、重複訊息。傳遞層只能保證兩種事：不重試，每則訊息最多送達一次（at-most-once，可能丟）；重試到收到確認為止，至少送達一次（at-least-once，可能重複）。Exactly-once 無法由傳遞層單獨保證，因為「確認」本身也可能遺失：B 做完回 ACK，ACK 丟了，A 只能再送一次。

所以設計分兩層：傳遞層做 at-least-once，應用層用冪等處理去除重複，合起來的效果等於 exactly-once。這就是下面「at-least-once 加冪等」的意思。

對策：at-least-once 加冪等，再加 compensation。Slide 列了三個對策，合在一起才完整：

  1. Idempotency key，用 task_id 當 key。A 重試時帶同一個 task_id；B 收到請求先查這個 key 做過沒，做過就回傳上次的結果，不再買一次。這讓「重試」變安全，三種情況都買到 8 台。
  2. Compensation 或 rollback 路徑。真的買了兩次時，要有一個反向操作把多出的 8 台釋放掉。Compensation 是用一個反向操作抵銷已經做掉的事，因為購買這種動作沒有辦法「取消送出」，只能事後補。
  3. 事先決定誰付錢。Compensation 也可能失敗。多付的錢算誰的，要在設計時就寫下規則，不能等事故發生再吵。
名詞Idempotency key：重送的請求為什麼不會做兩次

一個操作做一次和做很多次，結果相同，就叫冪等（idempotent）。「設 x = 5」冪等，「x 加 1」不冪等。「購買 8 台 instance」不冪等，所以要靠一把 key：呼叫端每次重試帶同一個 key（上面的例子用 task_id），服務端用 key 查做過沒，做過就回傳上次的結果，不再執行（p.33）。Key 由呼叫端產生，服務端的紀錄要持久保存，否則重啟後又會做一次。

紀錄要在真的去買之前先寫「處理中」。否則 B 買完、還沒寫紀錄就 crash，重啟後查不到紀錄，又買一次。第 4 段的 runtime.py 有這個順序。L4 的 2.4 從 tool 設計的角度講過同一件事（tool 預設冪等）；這裡是 agent 與 agent 之間的版本。

這裡有一個 LLM 特有的陷阱：重試如果由 LLM 自己決定，它可能重新產生一個新的 task_id，key 就對不上了。所以 重試要由 runtime 做，用同一個 envelope 重送，這是 2.6 把 task_id 放在外層欄位的理由之一。第 3 段進階題第 3 題把這條路徑完整設計一次。

多個 agent 同時跑，runtime 要管四件事。Slide p.35 說，系統裡同時跑很多 agent 時，runtime 還要處理四件單一 agent 沒有的事：

  • Scheduling。誰下一個跑、跑多久。十個 agent 都要呼叫 model，誰先？
  • State management。Checkpoint、memory、provenance、版本。每個 agent 的狀態要存在哪裡，掛了怎麼接回去。
  • Resource allocation。Model、CPU 和其他共用資源怎麼分。
  • 沒有事先決定的 request flow。系統事先不知道誰會需要跑、跑多久、每個 agent 會用多少資源，因為這些都由 LLM 在執行時決定。

第四點是 agent 系統和傳統服務最大的差別：一個 web 服務的請求路徑是設計時寫死的，agent 系統的路徑每次都不同（2.3 的 dynamic topology 是極端的例子）。所以 排程和資源分配不能靠事先規劃，要在執行時做。Part II 的 serving system 講的就是怎麼在這種不確定的負載下排程。

2.8兩個協定與四條原則：A2A 連 agent，MCP 連服務，都不管 orchestration p.37–44

前兩章講的 envelope 和重試，每個團隊都可以自己定格式。協定（protocol）是把這些格式標準化，讓不同團隊、不同公司做的 agent 互相說得上話。這一章看兩個協定：A2A 連接 agent 與 agent，MCP 連接 agent 與服務；再看兩者的分工，最後用 slide p.44 的四條設計原則把這一堂收起來。

呼叫者從 card 學到五件事：identity、skills、endpoints、capabilities、auth。注意 skills 是對方自己宣稱的，和 2.2 market 的出價一樣：card 說會訂機票，不保證訂得好。信不信，要靠 2.3 swarm 講的 trust 那一層，A2A 本身不管。

三個抽象：message、task、artifact。A2A 只有三個核心概念（p.39）。Message 是 client 和 agent 之間的一個回合，例如「訂一張到波士頓的機票」。Task 是一個有狀態的工作單位，有 ID、有生命週期，例如 task-42 從 working 走到 completed。Artifact 是 task 產出的東西，例如一份行程 PDF 或訂位資料。三者的關係：一則 message 開啟一個 task，task 回傳 artifact；後續的追問加入同一個 task，例如 agent 反問「哪一天？」，client 回「10 月 3 日」，仍然是 task-42。

追蹤一個長任務：三種方式。Task 可能跑幾秒，也可能跑幾小時，呼叫端自己選怎麼追蹤（p.41）：

  • Polling。Client 一直重查，直到做完。適合短的工作。
  • Streaming。即時收到更新。適合要互動的輸出，例如邊產生邊顯示。
  • Push notification。做完時由一個 webhook 通知你。適合跑幾小時的工作，不用一直開著連線。

Slide 在這一頁下了一個重要的註腳：A2A 標準化的是溝通，不是 orchestration。要不要委派、怎麼拆、什麼時候停，仍然由 harness（包在 model 外面、負責跑 loop 與 tool 的那層程式，L4 的 2.1）決定。協定只保證兩個 agent 說同一種語言，不替你做 2.2 到 2.5 的決定。

MCP：agent 與服務之間。MCP（Model Context Protocol）是另一道邊界：agent 與服務之間，一次 tool call、一個結果（p.42）。它標準化三種東西：tools（可呼叫、有型別的能力）、resources（host 可以附上的可讀資料）、prompts（可重用的互動範本）。一個 client 可以同時接很多 server，slide 畫了四個：filesystem、database、GitHub、browser。而且是 host（跑 agent 的程式）決定要讓 model 看到哪些 tool，不是 model 自己決定。

前情MCP（L2、L4）：agent 與服務之間的協定

MCP（Model Context Protocol）是 2024 年底 Anthropic 提出的標準：每個外部系統（GitHub、Jira、資料庫）包成一個 server，用固定的訊息回答「你有哪些 tool」「替我呼叫這一個」；harness 只要會說 MCP，就能接上所有 server，N 個 harness 乘 M 種系統變成 N 加 M。L2 第 2 段講 Claude Code 的擴充機制時完整講過，L4 的 2.2 拿它和 LSP 對照。

  1. p.6–7 · 為什麼拆、三張圖

    把工作拆給多個 agent 有哪四個理由？描述架構用的三張圖，各回答什麼問題？

    參考答案與重點複習

    答案：四個理由（p.6）：

    • Specialization。每個 agent 用不同的 model、prompt、tool。
    • Isolation。每個 agent 給不同的權限。
    • Parallelism。互不相依的子任務同時跑。
    • Context management。不必把整條 trajectory 交給每個 agent。

    三張圖（p.7）：control graph 回答誰協調，communication graph 回答 agent 怎麼溝通，task graph 回答工作怎麼拆。

    重點拆解

    四個理由換到的東西不同。Specialization 讓每個角色有短而專一的 prompt，也能配不同的 model。Isolation 切割權限：讀網頁的 agent 沒有 shell，網頁裡夾帶的指令就碰不到危險的 tool。Context management 換到乾淨的 context：worker 只看到自己的子任務，supervisor 只收摘要。Parallelism 換到的是時間。

    只有 parallelism 和速度有關，其他三個改善品質、安全與 context。每一項都有價格：多一次交接，就多一次資訊遺失、多一份 context、多一個會失敗的點。所以 p.44 的第一條原則是先問：真的需要 multi-agent 嗎？

    圖回答的問題常見的答案（p.7）
    Control graph誰協調？誰能派工、停工一個 supervisor、一層層的 hierarchy、沒有協調者；執行中可用 handoff 換人
    Communication graphAgent 之間怎麼傳話直接傳訊、broadcast、共享的工作區
    Task graph工作怎麼拆、誰相依誰Planner 事先拆、用出價認領、從局部規則浮現

    三張圖是三個獨立的軸。同樣拆成三個子任務（task graph 相同），可以由 supervisor 派工，也可以讓 agent 從共享的 task list 自己認領（control graph 不同）。p.9–16 每頁底部那一行，就是該架構在三張圖上的答案。

    背景補充

    把「誰決定」和「訊息走哪條線」分開看，網路設計早就這樣做：路由器的 control plane 決定路徑，data plane 搬封包。Multi-agent 也一樣：agent team 的 lead 負責派工，teammate 之間卻能直接傳訊，訊息不經過 lead。

    Isolation 是資安的最小權限原則（least privilege）：每個元件只拿完成工作所需的權限。L2 講過 prompt injection：外部內容可能夾帶指令。讀不可信內容的 agent 和執行危險動作的 agent 分開，注入的指令就到不了危險的 tool。Context management 延伸自 L3 的 subagent：子任務在新的 context 跑，只交回摘要。

    常見誤解

    「拆成多個 agent，答案一定比較好。」四個理由都不會讓 model 變聰明。Parallelism 只換到時間，交接還會遺失資訊。本文延伸〈一個 agent 常常就夠了〉整理了反例：循序規劃的任務，拆開後大幅變差。

    帶走這幾點
    1. 四個理由：specialization、isolation、parallelism、context management；只有 parallelism 換到速度。
    2. 多一個 agent → 多一次交接 → 多一個資訊遺失點與失敗點，所以先問要不要拆。
    3. 任何架構都能用三張圖描述：誰協調（control）、怎麼傳話（communication）、怎麼拆（task）。

    相關：第 1 段的架構圖；核心觀念〈多一個 agent：只換到四樣東西，每一樣都有價格〉、〈中心化的四種架構：線都經過一個點，弱點也在那一點〉、〈去中心化與混合：沒有中心，弱點變成一致性〉；本文延伸〈一個 agent 常常就夠了〉；L2〈Prompt injection〉、L3〈Context 隔離與摘要〉。

  2. p.9–18 · 八種架構的弱點

    八種架構分成哪三類？中心化和去中心化的弱點差在哪裡？

    參考答案與重點複習

    答案：p.18 的總表分成三類：centralized（supervisor–worker、hierarchical、pipeline/DAG、market）、decentralized（blackboard、committee、swarm）、hybrid（dynamic topology）。中心化的弱點是 planner 瓶頸、錯誤放大、錯誤往下傳、不實的出價：問題沿著控制的路徑集中或擴散。去中心化沒有控制者，弱點變成一致性與訊息量：狀態過期、groupthink、O(n²) 的訊息。

    重點拆解

    中心化的四種都有一個點決定誰做什麼，所以好預測、好 debug。弱點也從這個點出發。Supervisor 要重讀每份結果，context 長得最快（p.9）。Hierarchical 每一層都摘要一次，下層的錯被往上放大。Pipeline 沒有回頭的路，後段不能要求前段重做，所以 p.11 說加一條 retry edge 勝過多加一個 agent。Market 的出價是 agent 自己報的，誇大能力的 agent 會得標（p.14）。

    去中心化拿掉協調者，沒有單點會卡住或掛掉，agent 也能隨時加入、離開（p.15）。代價是每個 agent 看到的狀態可能不同。Blackboard 要處理一致性、並行控制、來源、版本（p.12）。Committee 的失敗是沒有獨立性的同意：同一個 model、同一份 context，盲點也相同（p.13）。Swarm 的訊息量是 O(n²)，產品裡很少用（p.15）。

    Hybrid 只有 dynamic topology：工單升級時才加入 billing 和 log agent（p.16）。簡單工單維持便宜，代價是每次執行的形狀不同，失敗很難重現。

    背景補充

    分散式系統把中心化的弱點叫 single point of failure（SPOF）。常見的補法是備援加 leader election：協調者掛了，選一個新的接手，Raft 這類共識演算法就在做這件事。前提是協調者的狀態能從 log 或 checkpoint 重建。Agent 系統的 supervisor 也一樣，狀態只在它的 context 裡，它一掛，整個任務就停。

    Groupthink 對應 ensemble 的基本條件：多數決只有在錯誤彼此獨立時才有效。兩個同 model 的 grader 錯誤高度相關，兩票同意帶來的新資訊很少。補法是換不同的 model 或評分角度，先各自作答再看彼此。

    常見誤解

    「去中心化沒有單點，所以比較可靠。」它只是把失敗換了形狀：從一個點卡住，變成每個 agent 看到不同的狀態。延伸閱讀的 Scaling 論文量到：independent 系統把錯誤放大 17.2 倍，centralized 是 4.4 倍。有人彙整，錯誤才有機會停下來。

    帶走這幾點
    1. 三類：中心化 4 種、去中心化 3 種、hybrid 1 種（dynamic topology）。
    2. 中心化：問題沿控制路徑集中（瓶頸）或擴散（放大、下傳）→ 減輕中心的負擔，加一條回頭的線。
    3. 去中心化：沒有單點，改付一致性與訊息量 → 狀態過期、groupthink、O(n²)。

    相關：第 1 段的架構圖；核心觀念〈中心化的四種架構：線都經過一個點，弱點也在那一點〉、〈去中心化與混合：沒有中心，弱點變成一致性〉；本文延伸〈彙整節點是細節流失的地方〉、〈Dynamic topology 難重現，也難除錯〉。進階題第 1 題練習選架構。

  3. p.22–23 · 粒度與拆解上限

    拆得太細，為什麼反而變慢？動態拆解為什麼一定要設上限？

    參考答案與重點複習

    答案：平行只縮短 T_critical_path；planning、communication、merge 都是額外成本，子任務越多，communication 越大。省下的循序時間小於這些成本，拆開就變慢，所以 p.22 把 20 個一行的 lookup 打包成 4 個子任務。動態拆解會在執行中生出新任務，worker 還能自己再委派，沒有上限就會遞迴爆炸。p.23 要求四種上限：spawn 數量、預算、深度、終止條件。

    重點拆解

    p.22 的估算式是 T_multi ≈ T_planning ＋ T_critical_path ＋ T_communication ＋ T_merge。四項裡只有 T_critical_path 會因為平行而變短：它是最長那條相依鏈的時間。T_communication 是每個子任務的派工加讀回報，子任務越多，這一項越大。所以 p.22 說兩頭都不好：子任務太大，平行度太低；太小，overhead 吃掉省下的時間。

    下圖用本頁「動手試試」的假設數字：每個 lookup 5 秒，每個子任務的溝通 8 秒，planning 和 merge 各 10 秒。拆 4 份最低，77 秒。拆 20 份要 185 秒，比不拆的 100 秒還慢。

    p.23 把拆解分成四種：

    • Static。任務在執行前就知道。
    • Dynamic。依發現生出新任務。
    • Recursive。讓 worker 再委派。
    • Opportunistic。讓閒著的 agent 認領新任務。

    後三種的任務數在執行前未知，所以需要四種上限：spawn 數量、預算、深度、終止條件。

    背景補充

    最低點可以算。總時間裡會隨 n 變的部分是 100 ÷ n ＋ 8n。前項遞減，後項遞增，最低點在 n = √(100 ÷ 8) ≈ 3.5。整數裡 4 最好，和圖一致。L3 的 Amdahl's law 說不能平行的部分限制加速上限；這裡更糟，overhead 隨 n 成長，所以拆過頭會變慢。

    拆得越細，fan-out 越大，也越容易遇到 straggler。Critical path 取最慢的那一份。假設每份有 1% 機率變慢，fan-out 100 時，至少一份變慢的機率是 1 − 0.99100 ≈ 63%。Google 的〈The Tail at Scale〉用這個算式說明 fan-out 讓尾端延遲變重要。這是 p.25 失敗 06 的機率面。

    例子

    沒有深度上限時，假設每個 worker 再開 3 個 subagent。第 1 層 3 個，第 2 層 9 個，第 3 層 27 個，第 4 層 81 個，合計 120 個 agent。每個都有自己的 context 和 token 帳單。Spawn 數量限制每層的寬度，深度上限限制層數，預算限制總花費，終止條件決定何時停。

    帶走這幾點
    1. 平行只縮短 critical path；planning、communication、merge 是額外成本，communication 隨子任務數成長。
    2. 總時間對子任務數有一個最低點 → 拆之前先算，太細比不拆還慢。
    3. 動態、遞迴拆解的任務數事先未知 → 要設 spawn 數量、預算、深度、終止條件四種上限。

  4. p.31–33 · Envelope 與 idempotency

    Runtime 為什麼不用問 LLM 就能路由和停止？購買請求 timeout 後，靠哪個欄位避免買兩次？

    參考答案與重點複習

    答案：p.31 的 envelope 把控制和內容分開：外層的 id、task_id、from、to、type 給 runtime 讀，payload 才放給 LLM 讀的自然語言。Type 只有 9 種（DELEGATE、QUERY、REPORT、HANDOFF、UPDATE、CANCEL、ACK、ERROR、COMPLETE），runtime 看欄位就能路由、重試、停止。購買請求靠 task_id（p.33）：重試時沿用同一個 task_id 當 idempotency key，B 認出這是同一個請求，就不會再買一次。

    重點拆解

    Type 是封閉的 9 個值，runtime 可以直接照值分派。例如 CANCEL 就停掉該 task，ERROR 就重試或升級給人。這些判斷不經過 LLM，所以快、便宜、每次結果相同。p.32 把它寫成法則：依欄位路由，不依內文路由。反過來讓 LLM 讀內文決定路由，要多付一次 model 呼叫；同一句話也可能被讀成不同意思。p.30 的建議是兩者並用：claim、confidence、evidence 給 LLM 判斷，task_id、type、requires_response 給 runtime。

    p.33 的難處在 timeout。A 請 B「購買 8 台 GPU instance」，然後沒有回覆。從 A 這一側，三種情況看起來一樣：請求沒送到、B 買了但回覆遺失、B 還在處理。不重試，可能一台都沒買；重試，可能買 16 台。Slide 列的對策是 task_id 當 idempotency key，加上一條 compensation（rollback）路徑。

    紀錄要持久保存，而且要在呼叫雲端 API 之前寫入。否則 B 在購買後、寫入前 crash，重啟後查不到紀錄，就會再買一次。重複請求來時，B 照紀錄的狀態回覆：working 回「處理中」，done 回傳原本的 order_id。

    背景補充

    網路只能保證兩種傳遞語意。At-most-once：不重試，最多送達一次，可能遺失。At-least-once：重試到收到確認，至少送達一次，可能重複。傳遞層做不到 exactly-once。實務上傳遞層做 at-least-once，接收端用冪等處理去除重複，合起來效果等於 exactly-once。

    付款與雲端 API 普遍這樣做。Stripe 的 API 讓呼叫端在 header 帶 Idempotency-Key；AWS EC2 的 RunInstances 有 ClientToken 參數，同一個 token 重送不會多開機器。共通點：key 由呼叫端產生，每個操作一把，重試時不換。

    常見誤解

    「Timeout 代表 B 沒做，重送就好。」Timeout 只代表 A 沒收到回覆。B 可能已經做完，也可能還在做。重送要由 runtime 用原本的 envelope 送，不要讓 LLM 重寫一次請求：重寫的請求可能帶新的 task_id，B 就會當成新的購買。

    帶走這幾點
    1. Envelope 分兩層：欄位給 runtime（路由、重試、停止），payload 給 LLM → 依欄位路由，不依內文。
    2. Timeout ≠ 沒做：沒送到、回覆遺失、還在做，從呼叫端看起來都一樣。
    3. At-least-once 重試 ＋ 同一個 task_id 當 idempotency key ＋ 先寫紀錄再動手 → 重試也只買一次。

    相關：核心觀念〈溝通的設計空間：四個維度分開選，欄位給 runtime、內容給 LLM〉、〈溝通是分散式系統問題：timeout 之後，你不知道對方做了沒〉；名詞註〈Idempotency key〉、〈Delivery semantics〉、〈Partial failure〉；第 4 段動手試試的 runtime.py。進階題第 3 題會設計完整的重試與 compensation。

  5. p.41–43 · A2A 與 MCP

    A2A 只標準化溝通，哪些事仍留給 harness？MCP 和 A2A 的工作單位差在哪裡？

    參考答案與重點複習

    答案：A2A 不負責 orchestration（p.41）。要不要委派、怎麼拆、何時停止，仍由 harness 決定。MCP 連接 agent 與服務，工作單位是一次 tool call：一次呼叫，一個結果（p.42）。A2A 連接 agent 與 agent，工作單位是一個長時間的 task（p.43）。

    重點拆解

    A2A 標準化的是「和另一個 agent 合作」這一段。對方在 /.well-known/agent-card.json 公開 agent card，呼叫者從中得知對方的身分、skills、endpoint、能力和認證方式（p.38）。互動有三個抽象（p.39）：message 是一輪對話，task 是有 ID、有生命週期的工作，artifact 是 task 的產出。一則 message 開啟 task，後續的回覆加入同一個 task。

    Task 有狀態，所以能暫停（p.40）。缺資料時進入 Input required，缺授權時進入 Auth required，補齊後回到 Working。Task 可能跑很久，p.41 給三種追進度的方法：polling 適合短工作，streaming 適合互動式輸出，push notification（webhook）適合跑幾小時的工作。

    MCP 是 agent 的服務邊界（p.42）。它標準化 tools、resources、prompts 三種東西；一個 client 可以接多個 server，開放哪些 tool 由 host 決定。p.43 再補兩點。A2A 的遠端 agent 最好不公開內部狀態，它內部可能再呼叫多個 MCP server。類比上，MCP 像裝置或 API 介面，A2A 像 service 之間的 RPC。

    背景補充

    兩個協定都在解 L2 的 N×M 整合問題，只是層次不同。MCP 由 Anthropic 在 2024 年 11 月發表，解 agent 對工具的整合；A2A 由 Google 在 2025 年 4 月發表，解 agent 對 agent 的整合，之後交給 Linux Foundation 管理。

    A2A 的 task 是分散式系統常見的 long-running operation 模式：送出請求，先拿到一個 ID，之後用 ID 查狀態或等通知。HTTP 的 202 Accepted 加上狀態查詢 URL 是同一個想法。這也連回 B4：task 有 ID 和狀態，timeout 之後可以先查狀態，不必盲目重送。

    常見誤解

    「用了 A2A，multi-agent 系統就設計好了。」A2A 只管傳話：找到對方、開 task、追狀態、拿回產出。要不要委派、拆多細、誰協調、何時停，仍是本堂前半段的設計問題（p.41）。協定換不掉 B1 到 B3 的判斷。

    帶走這幾點
    1. A2A 標準化溝通：發現（agent card）、task、狀態、artifact；orchestration 留給 harness。
    2. MCP：agent 對服務，一次 tool call，一個結果。A2A：agent 對 agent，一個有 ID、有狀態、能暫停的 task。
    3. 兩者互補，不互相取代：遠端的 A2A agent 內部可能再呼叫多個 MCP server。

    相關：核心觀念〈兩個協定與四條原則：A2A 連 agent，MCP 連服務，都不管 orchestration〉；名詞註〈狀態機〉；第 4 段動手試試的 agent card；L2〈N×M 整合問題〉。第 3 段「自我檢查」的第 3 題可以用來自測 MCP 和 A2A 的選擇。

自我檢查

兩個 grader 都給這篇作文 A，judge 就採用。這個設計有什麼問題？

兩個 grader 用同一個 model、讀同一份 context，錯誤高度相關，兩票同意帶來的新資訊很少。改用不同的 model 或評分角度，並讓它們先各自作答（p.13）。

20 個 lookup，每個 5 秒；每個子任務的派工與回報要 8 秒。為什麼拆成 20 個子任務，比不拆還慢？

平行只把 critical path 從 100 秒縮到 5 秒，溝通卻要 20 × 8 = 160 秒。打包成 4 個子任務，總時間約 77 秒。

情境一用 MCP：一次明確的動作，一個結果。情境二用 A2A：對方要自己推理，可能反問日期或要求授權，也可能跑很久。

  3. 必讀How we built our multi-agent research systemAnthropic · 工程文章 · 2025 · 約 20 分

    Lead agent 把平行搜尋委派給 worker，worker 只回摘要。Agent 約為 chat 的 4 倍 token，multi-agent 約 15 倍。

    導讀聚焦兩個數字（4×、15×）與「什麼時候平行划算」：獨立、唯讀的子任務。

    摘要讀約 3 分；原文約 20 分

    一句話：Anthropic 用 orchestrator–worker 架構做 Research 功能：lead agent 規劃並派工，subagent 平行搜尋後只回報摘要。平行帶來大幅加速，代價是 token 用量約為 chat 的 15 倍，所以只適合高價值、可平行的任務。

    跟這堂課的關係

    這篇是 slides p.9 supervisor–worker 的生產案例。它換到〈多一個 agent：只換到四樣東西，每一樣都有價格〉裡的 parallelism 與 context management。文中 subagent 的指令要有目標、輸出格式、tool 指引與邊界，和 p.21 的子任務規格一致。它建議 subagent 把產出存進檔案、只回傳參照，對應本文延伸〈彙整節點是細節流失的地方〉的對策。

    壓縮後的重點

    1. 平行 subagent 帶來加速，也帶來高成本。內部研究 eval 上，Opus 4 當 lead、Sonnet 4 當 subagent，勝過單一 Opus 4 達 90.2%。Lead 同時開 3–5 個 subagent，每個再平行呼叫 3 個以上 tool，複雜查詢的時間最多縮短 90%。Agent 的 token 約是 chat 的 4 倍，multi-agent 約 15 倍。
    2. Token 用量解釋了大部分的表現差異。BrowseComp 上，三個因素解釋 95% 的差異，token 用量一項就佔 80%。另外兩項是 tool call 次數與 model 選擇。換成 Sonnet 4 的增益，大於把 Sonnet 3.7 的 token 預算加倍。
    3. Prompt 是主要的修法。早期的 lead 會為簡單問題開 50 個 subagent。修法是教它依複雜度配置：簡單查證 1 個 agent 加 3–10 次 tool call，比較題 2–4 個 subagent，複雜研究 10 個以上。
    4. 派工指令要寫成規格。指令太模糊時，subagent 會重複做同一件事。每個 subagent 需要目標、輸出格式、tool 指引與任務邊界。
    5. Agent 可以改進自己的 tool。一個測試 tool 的 agent 跑了數十次後，重寫了一個 MCP tool 的描述。之後的 agent 完成任務的時間縮短 40%。
    6. 評估先看結果，再看過程是否合理。一開始只用約 20 個真實查詢就能看出效果。LLM-as-judge 用一個 prompt 評 0.0–1.0 分加 pass/fail，最接近人類判斷。人工測試抓到自動評估漏掉的問題，例如偏好 SEO 內容農場。
    7. 生產環境的問題來自狀態與長時間執行。Agent 需要 durable execution 與 checkpoint，失敗時從斷點繼續。更新用 rainbow deployment，新舊版本並行。Lead 同步等待每批 subagent，是目前的瓶頸。

    原文怎麼讀

    • 可以跳過：「Benefits of a multi-agent system」前半的動機（slides p.5–7 已講）；「Architecture overview」的 orchestrator–worker 描述（p.9）；「Usage data」與致謝。
    • 值得看原文：「Prompt engineering and evaluations」的 8 條原則，特別是依複雜度配置 agent 數量那段；「Production reliability」裡的 rainbow deployment 與同步瓶頸；附錄三條：end-state evaluation、長對話管理、subagent 輸出寫進檔案系統。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 20 分。
    別誤讀

    「multi-agent 贏單一 agent 90.2%，所以研究類任務都該拆。」這個數字來自內部 eval，而且 token 用量解釋了 80% 的差異。文章自己說：coding 這種可平行部分少的任務，較不適合 multi-agent。用之前先問：任務能不能拆成獨立、唯讀的子任務？

  4. 必讀Towards a Science of Scaling Agent SystemsarXiv 2512.08296 · 論文 · 2025 · 挑段約 25 分

    260 種配置、六個 benchmark 的對照比較：可分解任務加分、序列任務扣分，錯誤放大依協調方式而異。

    導讀結論依任務結構而定。問：slides 的八種架構，各對應哪一種任務結構？

    摘要讀約 3 分；原文約 25 分

    一句話：用 260 種配置、6 個 benchmark、3 個 model 家族做對照實驗，結論是 multi-agent 沒有通用的好處。可分解的任務加分，循序任務扣分，而且 multi-agent 的平均變化只有 −0.3%。

    跟這堂課的關係

    論文的四種 multi-agent 架構，對應 slides p.18 的 centralized、decentralized、hybrid 分類，見〈中心化的四種架構：線都經過一個點，弱點也在那一點〉、〈去中心化與混合：沒有中心，弱點變成一致性〉。本文延伸〈一個 agent 常常就夠了〉與〈彙整節點是細節流失的地方〉引用的 +80.8%、−70.0%、45%、17.2 倍與 4.4 倍，都來自這篇。一處分歧：p.18 把 O(n²) 訊息量列為去中心化的弱點。論文裡 decentralized 的 overhead（263%）略低於 centralized（285%），因為它最多只測到 9 個 agent。

    壓縮後的重點

    1. 效果依任務結構而定。Finance-Agent 可分解，centralized 比單一 agent 高 80.8%。PlanCraft 是循序規劃，四種 multi-agent 全部變差，independent 掉 70.0%，centralized 掉 50.3%。SWE-bench Verified 掉 2.1% 到 14.9%。
    2. 單一 agent 夠強時，加 agent 的收益遞減。回歸模型裡，baseline × agent 數量的交互項是 β = −0.236（p = 0.004）。換算的門檻約是 45% 的原始準確度。
    3. Tool 越多，協調的代價越大。效率 × tool 數量的交互項是 β = −0.096（p = 0.002）。Tool 數 ≤ 4 時效果可忽略；WorkBench 有 16 個 tool，代價明顯。
    4. 協調的 overhead 隨 agent 數量超線性成長。平均對話輪數：單一 agent 7.2，centralized 27.7，hybrid 44.3。Overhead 分別是 independent 58%、decentralized 263%、centralized 285%、hybrid 515%。每 1,000 token 的成功次數，單一 agent 67.7，hybrid 只有 13.6。
    5. 有中心彙整的架構能吸收錯誤。Trace 層級的錯誤放大倍數：independent 17.2 倍、decentralized 7.8 倍、hybrid 5.1 倍、centralized 4.4 倍。Context omission 這類錯誤，centralized 佔 8.3%，independent 佔 24.1%。
    6. 模型能用來選架構。依任務結構與 baseline 選架構，在 held-out 配置上選對 87%；隨機選 20%，只看模型能力 54%。作者的建議：循序規劃用單一 agent，可分解的分析用 centralized，平行探索可試 decentralized。

    原文怎麼讀

    • 可以跳過：Section 2 Related Work；Section 3.1 System Definition 的架構定義（slides p.8–18 已講）；Section 4.5 Robustness 的穩健性檢驗。
    • 值得看原文：Section 4.2 的逐 benchmark 結果表，看每種架構在六個 benchmark 的正負號；Section 4.4 的 Table 5（輪數、overhead、效率）與錯誤類型分解；Section 5 Limitations：SWE-bench 與 Terminal-Bench 各只取 20 題，agent 數最多測到 9。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 25 分。
    別誤讀

    「真實系統都是 hybrid（slides p.17），所以 hybrid 最好。」論文裡的 hybrid 是 orchestrator 加上有限的 peer 溝通，它的 overhead 最高（515%）、token 效率最差，協調失敗的錯誤佔 12.4%。p.17 只說真實系統混用多種機制，沒有說混得越多越好。

  5. 必讀Don't Build Multi-AgentsCognition · 工程文章 · 2025 · 約 15 分

    業界反方：平行 agent 會做出互相衝突的隱含決策，單一 context thread 更可靠。

    導讀把它的每一個主張，拿去問上一篇的實驗：哪些被檢驗過、結果如何？

    摘要讀約 3 分；原文約 15 分

    一句話：Cognition（Devin 的團隊）主張 2025 年不要做平行的 multi-agent。Subagent 看不到彼此的 context，各自的動作帶著隱含決策，合併時會衝突。他們建議用單一線程的 agent，長任務靠 context 壓縮撐住。

    跟這堂課的關係

    這篇是 slides p.44 第一條原則「先問要不要拆」的業界反方。本文延伸〈一個 agent 常常就夠了〉直接引用它的立場。它的 Flappy Bird 例子，就是 p.24–25 的失敗 05「失去全局 context」與 04「無法合併的輸出」。分歧在結論：slides 教怎麼拆、怎麼溝通；它說 2025 年的 agent 還不會協商，所以先不要拆。

    壓縮後的重點

    1. 長時間 agent 的可靠性，靠的是 context engineering。作者把它定義為：在動態系統裡自動替 model 組好 context。這是 prompt engineering 的下一層。
    2. 典型的拆法會失敗。任務「做一個 Flappy Bird clone」拆成兩份：背景與水管、會上下動的鳥。Subagent 1 做出 Super Mario 風格的背景，subagent 2 做的鳥和遊戲不搭。最後的合併者要同時收拾兩個誤解。
    3. 原則 1：分享完整的 agent trace，不只分享單則訊息。把原始任務複製給每個 subagent 不夠，因為真實對話是多輪的，前面的 tool call 會改變對任務的理解。
    4. 原則 2：動作帶著隱含決策，衝突的決策帶來壞結果。就算 subagent 都看得到前面的 context，兩個 subagent 仍看不到彼此的工作。鳥和背景會各自選一種視覺風格。
    5. 符合兩條原則的架構：單一線程，加 context 壓縮。單線程 agent 的 context 連續，但大任務會塞滿 context window。做法是加一個專門壓縮歷史的 model，留下關鍵事件與決策。Cognition 為此 fine-tune 了一個較小的 model，但任意長的 context 仍是未解問題。
    6. Claude Code 的 subagent 是刻意的保守設計。2025 年 6 月時，subagent 從不和主 agent 平行跑，通常只回答明確的問題、不寫 code。好處是調查工作不進主 agent 的歷史，trace 可以更長。
    7. 多 agent 協商要等 agent 更成熟。人類工程師靠討論解決 merge conflict；現在的 agent 撐不住那種長 context 的協商。作者認為跨 agent 的 context 傳遞會隨單線程 agent 進步而出現。

    原文怎麼讀

    • 可以跳過：開頭的 HTML 與 React 類比；結尾的 Devin 宣傳。
    • 值得看原文：「The Typical Multi-Agent Architecture」到「Revised Architecture」之間的三張架構圖與 Flappy Bird 例子；「Real-World Examples」裡的 edit apply model 段落，說明 2024 年大 model 寫 markdown、小 model 改檔的做法為何失敗。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 15 分。
    別誤讀

    「Cognition 反對所有 multi-agent。」作者反對的是平行的、各自帶決策的 subagent。他自己舉 Claude Code 的 subagent 當正面例子：只做調查、不寫 code、不平行，所以不違反兩條原則。他對長期的多 agent 協作是樂觀的。
