先看這裡

先看一個例子。你想省時間，讓一個 agent（會自己讀檔、跑指令、改 code 的 AI 助手）寫前端，另一個同時寫後端。兩邊各自做完，各自的測試都通過，接起來卻不能跑：前端送的欄位叫 userId，後端等的是 user_id。兩個 agent 都沒有做錯，只是沒有人把這個決定告訴對方。

每個 agent 只看得到自己讀過的東西：你給它的任務說明，和它自己讀的檔案、跑的指令的結果。它看不到另一個 agent 讀過什麼；要讓對方知道一件事，只能寫成文字傳過去。拆開的好處和代價都從這裡來。好處是每個 agent 一次能讀的文字有上限，分開做，各自只需要裝自己那一半的資料。代價是該讓對方知道的事，沒寫出來，對方就不知道。這堂回答的問題是：什麼時候值得拆成幾個 agent，拆了之後風險在哪裡。下面三條是這堂的判斷。

  • 多數任務不該拆。拆開只在幾件子任務互不相干的時候有好處。有一篇實驗拿同樣的題目，比較單一 agent 和幾個 agent 分工的得分：子任務互不相干的題目，分工的得分高約八成；每一步都要用上一步結果的題目，分工的得分反而低四到七成。例子裡前端和後端要用同一套欄位名，並不是互不相干；硬拆，就得把這類決定一條一條寫給對方（第 2 章）。
  • 要拆的話：讀可以同時做，寫盡量留給一個 agent。只查資料、讀 code 的 agent 可以同時跑，各自的發現只會累積。改檔案不一樣：每次改動都帶著命名、風格這類沒說出口的決定，例子裡的 userId 和 user_id 就是。兩個 agent 各寫一半，就會各選一套（第 3 章）。
  • 真的拆了，風險都在交接。有三個地方會出事。派出去的時候：寫任務說明的人沒寫到的事，接手的 agent 就不知道。交回來的時候：它做完只交回一段摘要，細節會掉。等的時候：等不到它回報，分不出它是沒做，還是做了沒回（第 4 到 6 章）。

還有兩個風險各有一章。幾個 agent 讀了同一份資料，其中一個把它改掉之後，其他 agent 手上的就是舊的（第 7 章）。Agent 交回來的文字裡，可能夾著它從網頁上讀來、別人故意寫給 agent 照做的話（第 8 章）。常見架構的名字收在第 9 章，需要時查。

1 · 核心觀念

什麼時候值得拆，拆了怎麼不壞

九章依重要性排：前三章決定要不要拆，接著兩章是派工與回報，再兩章是 agent 系統繼承的分散式系統問題，然後是安全，最後一章是需要時再查的目錄。

1根本的限制：agent 之間只能傳文字

L4 說過，一個 agent 是 model 加 loop：model 決定下一步，harness 執行 tool，再把結果放回 context。第二個 agent 就是第二個 loop，有自己的 system prompt、tool 清單和 context window。兩個 loop 沒有共用的記憶，一方知道的事，必須寫成文字送過去，另一方才知道。

隔離能換到四樣東西，但不是每一樣都非拆不可：

換到什麼例子一個 agent 做得到嗎
平行四個方向同時查做不到
權限隔離讀網頁的 agent 沒有 shell做不到
乾淨的 context查資料的過程不進主對話部分可以：context 快滿時把舊內容壓成摘要（compaction）；但查資料的過程已經先進過 context 一次
專一的 prompt 與 model搜尋交給便宜的 model部分可以：skill（需要時才載入的一份指令檔）讓同一個 agent 換上專門的指令，也能指定 model；但指令是加進同一份 context

代價也從隔離來。每交接一次，就多三件事：資訊遺失、多一份 context、多一個會失敗的點。其中 context 的帳最容易低估。Model 不記得上一圈，所以 harness 每一圈都把整份 context 當 input 重新送給 model；訊息一旦進了 context，之後每一圈都要再付一次它的 token（token 是 model 計量和計價文字的單位，一個英文詞約 1 個 token，一個中文字約 1 到 2 個）。一則 2k token 的 broadcast（同一則訊息送給所有 agent）發給 10 個 agent，每個 agent 再跑 20 圈，就是 2k × 10 × 20 ＝ 400k token 的 input。

所以拆開不是免費的組織方式。後面每一章都在處理同一個問題：怎麼讓該過去的資訊過去，不該進 context 的不要進去。

2最重要的判斷：多數任務不該拆

很多人把 multi-agent 當成「更強的 agent」，實測卻是有好有壞，差距很大。下表的數字都是 multi-agent 的分數相對單一 agent 的變化（相對值，不是百分點）：

任務和單一 agent 比來源與量法
財務分析（Finance-Agent），子任務可以分開做 中央協調（一個 orchestrator 分派子任務、彙整結果）的分數高 約 81% Towards a Science of Scaling Agent Systems（Google 等，2025-12）：5 種架構（單一 agent 加 4 種 multi-agent）、6 個 benchmark、3 家公司各幾個不同能力的 model，組合起來共 260 種設定，tool 與 token 預算相同
Minecraft 的合成規劃（PlanCraft），每一步要用上一步的結果試過的 4 種 multi-agent 架構全部退步，依架構低 39% 到 70%
研究類，平行查很多方向一個 Opus 4 當主 agent，規劃後把搜尋分給幾個 Sonnet 4 subagent 平行做（Opus 4、Sonnet 4 都是 Anthropic 的 model；subagent 是主 agent 派出去做一部分工作的 agent）。這個系統的分數比單一 Opus 4 高 90.2%；代價是 token：這個系統的用量約是一般聊天的 15 倍，單一 agent 的用量約是聊天的 4 倍，所以這個系統的 token 約是單一 agent 的 15 ÷ 4 ≈ 4 倍Anthropic 的 multi-agent research system（2025-06）：自家的 research 評估（Anthropic 一家的內部數字，不是對照實驗）

差別不在架構，在任務的形狀，也就是子任務能不能各自進行。證據在前兩列，它們出自同一篇實驗：在財務分析上進步最多的中央協調，換到 PlanCraft 也一樣退步，4 種架構無一例外。循序任務一拆就退步，因為每一步都要知道上一步的細節，而細節正是交接時會掉的東西。架構仍有影響，只是要先看任務才選得對：同一篇用任務的特徵預測該選哪種架構，在沒看過的設定上有 87% 選對。

這條路的第一格最重要。第一條設計原則就是先問「真的需要 multi-agent 嗎」：多數情況單一 agent 就夠，多加的 agent 常常只帶來 overhead 和複雜度。如果任務不需要平行，也不需要把權限隔開（第 1 章表 1 那兩件一個 agent 做不到的事），一個 agent 又做得完，拆開只會付第 1 章的三種代價，換不到東西；Anthropic 也提醒，多數 coding 任務能真正平行的部分比研究少。實務上可以問一句：少了這個 agent，品質掉多少？第一次決定要不要拆時，就是拿 multi-agent 和單一 agent 比；掉得不多，就先不要加。要回答這句話，就得先有單一 agent 的基準線，所以評估要先於架構，這是 L7 的主題。

3最實用的分界：讀可以平行，寫留在單線

常見的架構分類看的是誰管誰。實務上更有用的問題是：這個 agent 會不會改東西。Cognition（開發 coding agent Devin 的公司）2025 年的 Don't Build Multi-Agents 指出，動作帶著隱含的決定。寫程式時要選命名、風格、邊界條件的處理方式，這些決定多半沒有說出口。兩個 agent 各寫一半，就會各選一套。

讀就沒有這個問題。三個 agent 分別查安全、效能和錯誤，發現只會累積，不會互相矛盾到無法合併。這也解釋了上一章的數字：研究和分析多半是讀，所以吃得到平行的好處；coding 要寫，所以能平行的部分少。

十個月後，Cognition 在 Multi-Agents: What's Actually Working 修正了自己的立場，不再一概反對，但結論更清楚：寫保持單線，其他 agent 貢獻判斷，不貢獻動作。他們列出幾種行得通的形狀：

Writer 加 reviewer 最值得學。Cognition 說，他們的 review agent 平均在每個 Devin 寫的 PR 抓到約 2 個 bug，其中約 58% 屬於嚴重問題。反直覺的是，兩邊事前不共用 context 時效果最好：reviewer 只看 diff，不知道作者的理由，理由就說服不了它。這和人類的 committee 同一個道理：多一票只在錯誤彼此獨立時才有意義。同一個 model、讀同一份 context，兩票同意帶來的新資訊很少。

平行寫什麼時候可以。範圍切得開，而且有能自動驗證的標準。Cognition 認為，一些大型展示（用很多 agent 寫瀏覽器、C compiler）能成功，部分原因是成功標準簡單又可驗證，多數真實軟體沒有這種條件。L3 講的 git worktree（同一個 repo 在不同目錄各 checkout 一份，每個 agent 改自己那一份，最後再合併）能解決兩個 agent 改同一個檔案的衝突，但解決不了隱含決定的衝突：兩份各自都合法，合起來卻是兩套風格。

本文的判斷：驗證能力比架構重要。沒有測試或 reviewer，多個 agent 只是更快產生沒人檢查的東西，瓶頸會移到人身上。Cognition 也觀察到，使用者開始卡在管理、規劃和 review 大量 agent。這些是單一公司的經驗，不是對照實驗，所以當成假設來驗證，不要當成定律。

4派工：worker 的全部世界就是那段 prompt

派工的那個 agent，這一章叫 supervisor（就是第 2 章的主 agent、orchestrator）；接工作的叫 worker。Worker 的 context 是新的，看不到 supervisor 的對話、讀過的檔案和做過的決定。所以規格沒寫的事就不存在。一句「Research storage systems」會讓 worker 自己猜年份、格式和範圍。好的規格長這樣：

怎麼知道規格寫夠了？把它交給一個完全不懂這個專案的人。他要問的每個問題，都是規格缺的一個欄位。

前四種在派工時就能擋住；後兩種要到執行時才看得到，所以除了欄位，還要靠合併時的通讀和 timeout。六種的樣子畫在下圖：

拆多細。拆成越多份，不一定越快。把工作拆成 n 份交給 n 個 worker，總時間由四段組成，其中只有一段會隨 n 變短：

  • 規劃（planning）。Supervisor 讀任務、寫規格。這段和 n 關係不大，這裡算固定 10 秒。
  • 最慢那一份要跑多久（critical path）。n 份同時開工，要等最後一份做完才能往下走。工作平均分成 n 份，這段就縮成原來的 1/n。四段裡只有它會變短。
  • 派工和回報（communication）。每多一份，supervisor 就要多送一次規格、多讀一份回報。假設它一份一份處理，這段時間會隨 n 一直累加。
  • 合併（merge）。把結果合起來、去重、通讀，這裡算固定 10 秒。

用一個例子算：20 個 lookup，每個 5 秒，一個 agent 依序做完是 100 秒。拆成 n 份後，最慢那份是 100 ÷ n 秒；每份的派工加回報算 8 秒，n 份就是 8 × n 秒。四段加起來：

這張圖要這樣讀。拆成 1 份沒有好處：只是把整份工作交給一個 worker，工作沒有變快，卻多付了規劃、派工和合併，比不拆多 28 秒。再往下拆，每多拆一份，最慢那份省下的秒數越來越少：1 份拆成 2 份省 50 秒，2 份拆成 3 份省約 17 秒，3 份拆成 4 份省約 8.3 秒，4 份拆成 5 份只省 5 秒。派工卻固定每份多 8 秒。省下的比 8 秒多，總時間就變短；省下的比 8 秒少，就變長。所以拆到 4 份最快，77 秒，而且只比 3 份快一點，因為 3 份拆成 4 份省的 8.3 秒只比 8 秒多一點。拆到 9 份以上，總時間就超過 100 秒，比一個 agent 自己做還慢，20 份要 185 秒。派工越貴，省下的秒數越早追不上它，該拆的份數就越少；拆之前，先用自己的數字算一次。

沿什麼切。依資料切最獨立，例如一批檔案一個 worker：每個 worker 只碰自己那批，結果不會互相指涉，合併就是把各批接起來，所以也最簡單。依專業角度切（安全、效能）時，不同角度常會看到同一個問題（一段把整個檔案一次讀進記憶體的 code，安全 worker 報它會被超大的檔案打掛，效能 worker 報它吃記憶體，兩份報告指著同一行），所以要在合併時去重。依階段切有先後順序，回到第 2 章要小心的循序問題。Debug 時可以依假設切，每個 agent 驗證一個互斥的解釋。

一定要設上限。Worker 可以再開 worker 時，每層開 3 個，四層加起來就是 3 ＋ 9 ＋ 27 ＋ 81 ＝ 120 個 agent，每個都有自己的帳單。要限制寬度、深度、預算和終止條件：

5回報：訊息只帶主張和證據，原文放檔案

把多份輸入變成一份輸出的節點，都會丟細節，而且下游不知道丟了什麼。Supervisor 讀 8 份報告寫一份摘要。系統分成好幾層時（supervisor 底下再有各管一組 worker 的 lead，第 9 章的 Hierarchical），每多一層就再摘要一次。底層 agent 誤讀了一個欄位，到上面只剩「API 完成」。

但彙整節點不該拿掉，反而要讓它能檢查。第 2 章那篇實驗量了錯誤放大，也就是 multi-agent 的失敗率是單一 agent 的幾倍。各 agent 分開做、結果只合成一份、中間沒有人檢查的架構是 17.2 倍，中央協調只有 4.4 倍，因為 orchestrator 讀得到每一份回報，錯誤才有機會在它那裡停下來。所以該做的是讓彙整者看得到證據：

這則訊息的欄位分給兩種讀者。task_id、type、status 給 runtime，也就是在 agent 之間轉送訊息、排程、重試的那段程式；它不是 model，只看這幾個欄位。claim、evidence 給收訊息的 LLM（large language model，就是前面一直說的 model），它讀的是主張和證據：

給 runtime 的三個欄位（task_id、type、status）像信封上的收件人和郵戳，常叫做 envelope；claim 和 evidence 是信的內容。Envelope 讓程式直接判斷：路由、重試、停止都看欄位，不要問 LLM 這段話是什麼意思，這樣更快、更便宜；而且 model 讀同一段話，每次的判斷可能不同，程式比對欄位每次都一樣。自然語言只留給真正需要判斷的內容。

欄位決定訊息裡放什麼；另一個選擇是傳法，也就是訊息傳給誰：點對點只給一個 agent，broadcast 給所有 agent（第 9 章的查閱列了六種）。選的時候先問一個問題：這則訊息會進幾個 context？點對點進一個，broadcast 進全部。第 1 章的 400k token 就是這樣來的，所以只有所有人都要知道時才 broadcast。

6送出去之後：timeout、冪等與 partial failure

只要 agent 不在同一個 process，它們之間就是分散式系統。最典型的情況是 A 叫 B 買 8 台 GPU，然後 timeout：

A 分不出來，所以兩邊都有風險：不重試可能一台都沒買，重試可能買到 16 台。傳遞層也幫不了你：它只能保證最多送達一次（可能丟），或至少送達一次（可能重複），因為「收到了」這個確認本身也會遺失。

解法分兩層：傳遞層一直重送，接收端負責認出重複的請求，不做第二次。後者叫冪等（idempotent）：做一次和做很多次，結果相同。做法是用 task_id 當 key，收到請求先查紀錄：

LLM 還多一個陷阱：讓它自己決定重試，它會重新寫一整則訊息，task_id 這個欄位也是它填的，可能填成一個新的號碼，接收端用 task_id 查紀錄就查不到，key 就對不上了。所以重試由 runtime 用同一個訊息重送，不交給 model。

Partial failure：分不出對方是慢，還是掛了。上面的購買例子，根源是分散式系統最基本的難題。單機程式要嘛整個在跑，要嘛整個停了；分散式系統裡，一部分正常、另一部分壞掉，而且從外面看不出來。沒有回覆，可能是對方 crash、網路斷了，或只是慢。在沒有時間上限保證的網路裡，只靠等待區分不了這三種：你永遠不知道回覆會不會在下一秒到。

LLM agent 讓這件事更難判斷，因為慢是常態。一圈 loop 可能跑幾分鐘，跑測試的 worker 可能十分鐘不出聲。Timeout 設短，會把正常的 worker 當成死掉；設長，真的死掉時又要等很久。所以 timeout 只代表「我不知道了」，不代表失敗。Timeout 之後要有明確的下一步：

  • 先問狀態，不要盲目重送。用 task_id 查對方的紀錄，查得到就照狀態處理。A2A（Agent2Agent，Google 2025 年 4 月提出、現在由 Linux Foundation 管理的 agent 之間的通訊協定，第 9 章有細節）把委派出去的工作做成有 ID、有狀態的 task，並提供 GetTask 讓呼叫端用 ID 查狀態，就是為了這一步。
  • 用心跳和租約判斷存活。前面是 A 直接把工作交給 B；worker 一多，常改成由一個協調者發工作，例如下圖存放任務和結果的 result store。Worker 認領任務時，從協調者拿到一份有期限的租約（lease），工作中定期向它送心跳（heartbeat）續約。租約過期，協調者才把任務交給別的 worker。這樣「要等多久」就從猜測變成規則。
  • 換人之後，舊的 worker 可能還活著。它只是卡住，回來後仍會寫結果，兩個 worker 都以為任務是自己的。解法是每次換手時發一個遞增的編號，叫 fencing token。寫入時要帶上編號，存放結果的地方只接受最新的編號。
  • 等不到時，先用部分結果。七個 worker 回了六個，就先合併六份，並標明缺了哪一份。這是讓一個 worker 卡不住整個系統的邊界。

合起來看，前三點把「對方可能死了」變成可以處理的步驟：查得到狀態就照狀態做；查不到就等租約過期，過期就換人；換人之後用編號擋住舊 worker 的寫入。第四點讓系統在等的時候不必停下來。冪等處理重複的請求，fencing token 處理重複的執行者，兩個都要有。Agent 系統容易漏掉後者，因為大家常把 subagent 當成一次函式呼叫，很少有人設想它卡住之後又回來（本文的判斷）。

其他常見的失敗，對策也都在 runtime：

失敗長什麼樣對策
繞圈A 問 B，B 問 C，C 問 A訊息帶一個跳數上限，每轉給下一個 agent 就減 1；減到 0 時，runtime 不再轉送，改回報錯誤

LLM 不會自己發現它在繞圈，也不會發現手上的事實過期了，要靠訊息的欄位和 runtime 的規則替它擋。

7狀態與時間：每個 agent 的 context 都是一份會過期的副本

第 6 章談的是一則訊息送出去之後的事。這一章談多個 agent 共用狀態時的事。先換一個角度看 context：agent 讀進 context 的每一個事實，都是外面那份狀態的一份副本（replica）。讀完的那一刻，它就開始過期。分散式系統花了幾十年處理副本，那些結論在這裡都用得上。

Consistency：兩個 agent 同時改同一份東西。共享的 task list 上，Agent A 和 Agent B 同時讀到 T4 沒人認領，各自寫上自己的名字，兩個人都去做 T4。這叫 lost update：後寫的蓋掉先寫的，雙方都不知道。解法是 conditional write，也叫 compare-and-swap：寫入時附上「我讀到的版本」，版本已經變了就拒絕，要求重讀。你天天在用的 git 就是這樣：

所以用 git 當 blackboard（多個 agent 共用、各自讀寫的工作區，第 9 章的一種架構）不只是方便：git 天生就擋住了 lost update。用一般檔案或資料庫時，認領任務這種寫入要自己加版本檢查。

CAP：網路斷開時，只能保住一個。CAP 說的是：當網路分成兩半（partition），系統只能在 consistency（簡寫 C：每個人看到同一份最新狀態）和 availability（簡寫 A：每個人都能繼續做事）之間選一個。對 agent 來說，就是連不上共享狀態時，手上那份舊副本要不要用：

沒有分區的時候也有取捨：每次行動前都重讀共享狀態，資料最新，但每次多一個 tool call 和一份 token；直接用 context 裡的副本，快，但可能過期。這是 latency 和 consistency 的取捨，有人把它和 CAP 合稱 PACELC。實務上可以接回第 3 章的讀寫分界：寫之前一定重讀（選 C），讀和探索可以用副本（選 A）。不可逆的動作，例如付款、刪除、對外發信，一律選 C。

沒有全域時鐘：時間戳排不出先後。每台機器的時鐘都會漂移，即使有 NTP 同步也有毫秒級誤差，機器暫停或沒同步時更大。所以兩個 agent 的時間戳不能拿來比先後，最危險的用法是 last-write-wins：

要排先後，有兩種做法。第一種是讓同一個地方發號碼：store 替每次寫入發遞增的版本號，第 6 章的 fencing token 也是這個做法。第二種是 logical clock，例如 Lamport clock：每個 agent 帶一個計數器，每做一件事加 1，送訊息時附上計數器；收到訊息的一方把自己的計數器設成兩者較大值再加 1。這樣有因果關係的事件，順序一定排得對，不靠任何人的時鐘。有因果關係指的是：同一個 agent 先後做的兩件事，或一則訊息的送出和收到，以及由這兩種關係一路串起來的事（收到訊息才做的事，一定排在送訊息那一方之後，因為收方的計數器被調成比送方大）。彼此沒有訊息往來的兩次寫入，像圖 3 的 A 和 B（兩個 agent 各自寫 store，誰也沒通知誰），Lamport clock 仍會各給一個數字，比大小也比得出來，但這個大小不代表誰先誰後，因為兩邊各自累加、互不知道對方；這種事件在這套方法裡叫 concurrent（並行）。要排它們的先後，還是要靠第一種做法，由 store 發號。

Observability：用 trace 把散落的 log 串起來。時鐘不可靠，除錯時就不能靠時間戳把八個 agent 的 log 排在一起。做法是 distributed tracing：每個 agent 的每次工作是一個 span，帶著共同的 trace id 和自己的 parent id，事後用 parent 關係重建一棵樹，而不是用時間排一條線。Claude Code 也提供了這種資訊：stream-json 輸出裡，subagent 的每則訊息都帶 parent_tool_use_id，指向開啟它的那次呼叫：

不確定性：同一個任務跑兩次，結果不同。傳統分散式系統的不確定性來自排程和網路；LLM agent 多了一層，model 每次的輸出都可能不同。所以「重現 bug」不能靠重跑，要靠記錄：每則訊息的 envelope（第 5 章給 runtime 看的欄位）和內文、每次 tool 的結果都存下來，用 trace 的順序重播。第 9 章的 dynamic topology（執行中依難度加減 agent、改變誰接誰的架構）更需要這樣做，因為它每次跑出來的形狀都不同，這也是它難除錯的原因。

8安全：傳回來的文字也不可信

第 1 章說，拆開可以隔離權限：讀網頁的 agent 沒有 shell，網頁裡的指令就算騙過它，也碰不到危險的 tool。網頁、檔案這類外部內容裡夾著指令、被 model 當成自己該做的事，這種攻擊叫 prompt injection。權限隔離只擋了一半，因為它的輸出還是會回到另一個 agent 的 context：

對 model 來說，worker 的報告和使用者的話都只是文字。Prompt Infection（2024）更進一步展示，惡意 prompt 可以像病毒一樣在 agent 之間自我複製。即使每個 agent 只看得到上游傳給它的部分訊息、看不到整段對話，感染仍然傳得下去。這是 multi-agent 特有的風險：線越多，感染的路徑越多。

這個問題目前沒有根治的方法。該論文提出 LLM Tagging：每個 agent 的回覆傳給下一個 agent 之前，開頭加上 [AGENT NAME]:（填這個 agent 的名稱），讓下游分得出哪些是使用者的話、哪些是別的 agent 產生的。單獨用它幾乎沒有效果：和不設防比，攻擊成功率只少約 5%（原文就這樣寫，沒說是百分點還是相對值，也沒給不設防的成功率），也說它試過的每一種防護單獨用都不太有效。搭配既有的防護（例如用特殊符號區分使用者和 agent 的 prompt，或在 prompt 裡要求不得改動使用者的指令），在論文的測試裡攻擊成功率降到 0% 到 3%，也就是幾乎全擋下來（作者自己設計的攻擊，換一種攻擊不一定擋得住）。所以實務上是多層防線：

  • 把回報當資料，不當指令。Worker 的內文放進固定欄位，supervisor 的 prompt 明寫裡面的內容不能當指令執行。
  • 危險動作不由文字決定。刪除、付款、對外傳送這類動作，由 runtime 檢查 allowlist，或要人確認。這是第 5 章「看欄位，不看內文」的延伸。
  • 拆開三種能力。一個 agent 同時能讀私密資料、會接觸不可信內容、又能對外傳送時最危險：不可信內容裡的指令可以叫它把私密資料送出去，三步都在它自己手上完成。Simon Willison（長期追蹤 prompt injection 的開發者，Django 的共同作者）稱這個組合為 lethal trifecta。把三種能力切給不同 agent 時，讀不可信內容的 agent 寫的文字還是會流到另外兩種 agent 手上，所以它們之間還是要有前兩點的關卡：把流過來的文字當資料，危險動作由 runtime 檢查。
  • 別把對方的自述當認證。A2A 的每個 agent 會公開一張 agent card：一份 JSON，寫它是誰、會做哪些事、怎麼呼叫。裡面的 skills 是對方自己宣稱的能力清單，和第 1 章說的 skill（載入的指令檔）不是同一個東西。認證只告訴你對方是誰，不代表它宣稱的能力或它傳回的內容可信。

把安全排在第 8 章、放在「要不要拆」和交接之後，是本文的判斷：多數讀者先碰到的是要不要拆。兩種環境不同。受管制的環境（金融、醫療），資料外洩有法規責任，一次注入的代價不是重做而是罰則；多租戶的環境，別人的資料和你的 agent 在同一套系統裡，一次注入就能把一個租戶的資料送到另一個租戶手上。這兩種地方，這一章的份量應該和第 2 章一樣重。

9目錄：八種架構、通訊選項、兩個協定

這一章不必讀完，需要時再查。架構的名字只是三個問題的答案組合：誰協調、誰和誰說話、工作怎麼拆。拿到任何系統，先把這三題各答一句，比記名字有用。

查閱通訊的選項：資料放在哪裡（三種 medium）、怎麼流（六種 channel）

通訊分成兩層，兩層分的是不同的事。Medium 分的是資料放在什麼載體上：一則訊息、一個共用的物件，或一個檔案。Channel 分的是資料怎麼流：給一個還是給全部、要不要訂閱、發問的一方要不要停下來等。

一種 channel 可以放在不同的 medium 上：共享 blackboard 這種 channel 可以放在 shared memory，也可以放在檔案或 git；artifact passing 這種 channel（一個 agent 把結果寫成檔案，另一個 agent 讀那個檔案，下圖第六格）用的是 files 這種 medium。另外兩個名字在這一頁有兩種用法，要分開：blackboard 在這裡是一種 channel（大家讀寫同一塊），在上面的架構表裡也是一種架構的名字，兩處說的是同一個做法，一個從資料怎麼流看、一個從誰協調看；shared memory 在這裡嚴格只指同一個 process 裡的物件（git repo 和一般檔案都算 files），上面混合系統圖說裡的 shared memory 則是泛稱，共享的 git 也這樣叫。

兩個協定。看對面是什麼：對面是明確的動作、一次一個結果，用 MCP（Model Context Protocol，Anthropic 2024-11 提出、讓 model 呼叫外部 tool 的協定）；對面會自己推理、可能反問、可能跑很久，用 A2A。兩者都不替你決定要不要委派、怎麼拆、何時停，那些仍由 harness 決定。
