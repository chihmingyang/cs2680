閱讀 01 · A first operating loop

How I use LLMsAndrej Karpathy

影片 · YouTube2025-02-27長度 2 小時以上選讀（新手必讀）
看原影片 ↗

用具體任務，按使用者遇到的順序，走一遍 LLM 產品的每個功能：選模型、thinking、搜尋、檔案、寫程式、記憶。

核心主張

消費型 LLM 產品把很多能力放在同一個輸入框後面：模型選擇、推理控制、tools、檔案上傳、寫程式功能、持久指令。新使用者可以一直只用輸入框，不知道其他選項改變了什麼。介面不會告訴你一個任務需要哪個能力，也不會告訴你每個選擇的代價。選錯模型、少給 context、多叫一次 tool，品質會下降、延遲會增加，但畫面上不會出現任何錯誤。

Karpathy 用具體任務逐一示範這些選擇怎麼改變結果。課程要你從示範中看到另一件事：一個使用者任務，背後會產生多次 model call、多次 tool call，以及越來越長的 prompt。這三個量，就是整門課要量測的東西。

重點

  • 對話在底層是一串 token。開新對話，就是清空 context window。
  • 要知道自己在用哪個模型、哪個價格層級。不同層級的模型能力不同。
  • Thinking model 適合需要推理的難題（數學、程式）。簡單問題用一般模型，比較快。
  • 網路搜尋、deep research、Python interpreter 都是 tool：它們把外部結果放進 context。
  • 上傳檔案，就是把文件內容放進 context window。
  • Cursor 段落示範了 coding agent 的雛形：模型直接改你的專案檔案。
  • Memory 與 custom instructions 是每次都帶進 prompt 的持久設定。這和後面 CLAUDE.md 是同一個概念。

背景概念

Token 與 tokenizer
模型處理的單位是 token，不是字也不是詞。中文一個字常常是一到兩個 token，依 tokenizer 而定。成本與 context 上限都用 token 計算。
Context window = 工作記憶
模型沒有跨請求的記憶。它只看得到這一次請求裡的 token。所以「記憶」功能，本質上就是自動把一段文字塞回 prompt。
一次請求 ≠ 一次 model call
產品啟用搜尋或程式執行時，背後是一個 loop：模型要求 tool → 系統執行 → 結果附加回對話 → 模型再被呼叫一次。每一次都重送整段歷史。

閱讀 02 · A first operating loop

Best practices for Claude CodeAnthropic 官方文件

官方文件持續更新約 25 分必讀
打開原文 ↗

Claude Code 的使用手冊，同時也是一份 workload 說明書：每一個好習慣，都改變了 prompt 長度或 model call 的數量。

核心主張

Terminal coding agent 可以檢查 repo、改檔案、跑指令，一直做到它判斷任務完成。它的 context 裡累積了對話、讀過的檔案、指令輸出。大部分建議都來自一個限制：context window 很快就滿，而模型表現會隨之下降。

所以有兩個資源要明確管理。第一是 verification。給 agent 一個它能自己跑的檢查，例如測試、build 的 exit code、截圖比對。沒有檢查，「看起來完成」是它唯一的停止訊號，而你變成人工驗證迴圈。第二是 context。先 explore、再 plan、再 implement、最後 commit。給具體的 context，早點糾正方向，不相關的工作用 /clear 切開。需要大量讀檔的調查交給 subagent，只有在輸出能被檢查與合併時才平行。

課程要你把這份指南也當成 workload 描述。Verification 改變 run 何時停止。Context 管理改變 prompt 長度。Subagent 與平行 session 改變 model call 的數量與依賴結構。Assignment 1 會記錄這些效果。

重點

  • Verification 有四級強度：在 prompt 裡要求跑測試 → /goal 條件（另一個 evaluator 每輪檢查）→ Stop hook（script 不過就不准結束）→ 獨立 subagent 嘗試反駁結果。要求 agent 貼出證據：執行的指令與輸出。
  • Explore → Plan → Implement → Commit：按 Shift+Tab 進 plan mode（唯讀），或用 claude --permission-mode plan 啟動。Ctrl+G 在編輯器裡改計畫。能用一句話描述的 diff，跳過 plan。
  • 具體 context：指定檔案、情境、限制、可參考的既有程式。用 @檔名 引用檔案，或用 pipe 餵資料。
  • CLAUDE.md：用 /init 產生初稿。每一行都問：刪掉會不會讓 Claude 出錯？不會就刪。檔案太長，重要規則會被淹沒。每次都必須發生的事，改用 hook。
  • Session 管理：Esc 中斷；Esc Esc 或 /rewind 回到 checkpoint；同一個問題糾正超過兩次，就 /clear 並重寫更好的 prompt；/compact 保留 API 變更 可指定壓縮重點。
  • Scale：claude -p 非互動模式可放進 CI；git worktree 讓多個 session 平行；Writer / Reviewer 兩個 session 互相檢查。
  • 五種失敗模式：什麼都塞的 session、反覆糾正、過胖的 CLAUDE.md、先信任後驗證、沒有邊界的探索。

具體範例

注意「範圍」三行都是「不要」型的限制。09 的實驗發現，這類規則最有幫助。「不要改 migrations/」如果必須保證，改用 07 的 hook。

背景概念

長 context 讓品質下降
Context 越長，模型越容易忽略中間的指令。長 context 研究常稱這個現象為 lost in the middle。所以 /clear 不只省錢，也提升品質。
Prompt caching
每一輪都重送整段歷史。Provider 會快取相同的前綴，計價便宜很多。前綴一改（例如改了 CLAUDE.md、增減 MCP server），快取就失效。穩定的常駐內容，比常變的內容便宜。
Subagent ≈ 函式呼叫
Subagent 有自己的 context。它讀很多檔案，最後只回傳摘要。主 session 只付摘要的 token，像呼叫函式只拿回傳值。
Permission mode
Plan mode 是唯讀模式。Auto mode 由另一個 classifier 模型審查動作，只擋看起來有風險的操作。

Agentic Engineering PatternsSimon Willison

實務指南 · 持續更新2026挑 6 章約 25 分；全部約 1.5 小時推薦
打開原文 ↗

一份持續更新的 coding agent 實務手冊。它把散落各處的技巧，整理成一套共同的詞彙。

核心主張

Coding agent 的實務知識散在產品文件、部落格和個人的 prompt 裡。同一招常常有不同名字，所以經驗很難在工具之間轉移。沒有共同詞彙，建議就很難比較，也很難對應到一次失敗：這個任務需要更小的 prompt、測試迴圈、checkpoint、subagent，還是換個介面？

Willison 把這些做法整理成可重用的 pattern：Git 是復原機制，subagent 處理有邊界的工作，red/green TDD，agent 執行的手動測試，code walkthrough，以及附註解的真實 prompt。他對 agent 的定義很短：在 loop 裡跑 tools 來達成目標。Coding agent 的關鍵能力，是能執行它寫的程式。

課程建議讀完 01、02 之後，把它當參考書，不必從頭讀到尾。它把每個使用習慣連到一個 harness 可以提供的控制機制。這是從本講「使用 agent」走到第 4 講「設計 agent」的橋樑。

重點

  • 寫 code 變便宜了，好的 code 沒有。好的 code 要能跑、你要確定它能跑、解對問題、處理錯誤、簡單、有測試、文件跟得上。
  • 新習慣：直覺說「不值得花時間做」的事，還是開一個 async agent session 試試。最壞的結果只是浪費一些 token。
  • Red/green TDD：先寫測試，確認它失敗（red），再實作到通過（green）。「確認失敗」這一步，防止 agent 寫出本來就會通過的假測試。
  • First run the tests：新 session 第一句就叫 agent 跑測試。它因此知道有測試、怎麼跑、專案多大，並進入測試的心態。
  • Agentic manual testing：測試全過，不代表真的能用。叫 agent 用 python -c、curl、Playwright 實際操作。發現的問題，再用 red/green TDD 寫成永久測試。
  • Git：commit、整理歷史、git bisect 找出引入 bug 的 commit、從 reflog 找回遺失的程式碼，都可以交給 agent。
  • Anti-pattern：不要把自己沒 review 過的 agent code 丟給同事 review。PR 要小，要附證據：怎麼測的、截圖或錄影。

具體範例

背景概念

Red → green → refactor
TDD 的迴圈來自 Kent Beck 與 Extreme Programming。對 agent 來說，red 階段的價值是證明測試真的在檢查新行為。
Test oracle problem
誰來判斷輸出是對的？Agent 同時寫測試和實作時，兩邊可能一起錯。所以要有人看測試，或讓一個沒看過實作過程的 reviewer 檢查。
git bisect
在 commit 歷史上做二分搜尋。1,000 個 commit 只要測約 10 次。過去難用的原因是要把 bug 寫成可執行的判斷，這一步現在可以交給 agent。

Skill 是一個資料夾。它用三層 progressive disclosure，只在需要時把內容載入 context。

核心主張

CLAUDE.md 這類持久指令檔，會把整本操作手冊放進每一次 prompt，即使目前任務只需要其中一個程序。裝越多程序，使用者還沒開口，context 就被佔掉越多。Agent 需要足夠的資訊來發現相關能力，但不能每次呼叫都把所有能力全文載入。載入策略也要能打包 scripts 和參考資料，它們只在選中某個程序後才有用。

解法是三層載入。第一層：啟動時只載入每個 skill 的 name 和 description。第二層：模型判斷相關時，才讀整份 SKILL.md。第三層：SKILL.md 引用的其他檔案和 scripts，只在後續步驟需要時才打開或執行。

課程把它看成一個具體的 context admission policy。Description 是常駐成本；body 和 resources 用到才付。對照第 2 講的 context rent，逐條問：這條指令配得上哪一層？

重點

  • 最小結構：一個資料夾加一份 SKILL.md。YAML frontmatter 必填 name 和 description。
  • Description 決定 skill 會不會被觸發。要寫清楚「什麼情況該用」。
  • 確定性的工作交給 code。例如抽出 PDF 的表單欄位：直接跑 script，script 和 PDF 都不必進 context。
  • 撰寫流程：先在代表性任務上觀察 agent 卡在哪裡，再針對缺口寫 skill。SKILL.md 太大就拆檔。觀察 Claude 實際怎麼用，再修改。
  • 讓 Claude 自己把成功做法和常見錯誤寫回 skill。
  • 安全：skill 包含指令和程式碼。惡意 skill 可以叫 agent 外洩資料。只裝可信來源，安裝前讀過每一個檔案。

具體範例

在 Claude Code 裡，Claude 會依 description 自動載入；你也可以打 /release-notes 直接呼叫。

背景概念

Progressive disclosure
原本是 UI 設計原則：先給最少的資訊，使用者需要時再展開。
系統課的類比：demand paging
Description 像 page table 的一筆 entry，常駐但很小。Body 像實際的 page，用到才載入。附檔像更外層的儲存。Context window 就是有限的實體記憶體。
常駐成本 × 輪數
每個常駐 token，每一次 model call 都要付。一個 50 輪的 session，100 token 的 description 就是 5,000 token。Prompt caching 會大幅打折，但它仍然佔用模型的注意力。

Code execution with MCPAnthropic Engineering · Adam Jones、Conor Kelly

打開原文 ↗

把 MCP tools 當成 code API，讓 agent 寫程式呼叫。Tool 定義按需讀取，中間資料留在執行環境。

核心主張

很多 MCP host 把每一個啟用的 tool 定義都放進 prompt，並把每一個中間結果經過對話傳回模型。於是 tool 清單和資料，與使用者的任務搶同一個 context。直接呼叫 tool 會在每次 model call 重送 schema。大型結果也被序列化、經過模型，即使一段普通程式就能過濾或合併它們。成本隨 tool 數量與 workflow 長度一起成長。

解法：把 MCP server 呈現成檔案系統裡的程式模組。Agent 用列目錄、讀檔的方式找到需要的 tool，再寫程式，在 sandbox 裡完成 loop、join、過濾和錯誤處理。只有被選中的定義和精簡後的結果進入 context。

文中範例把 tool 定義從 150,000 token 降到 2,000 token，減少 98.7%。課程提醒：這是一個示範機制的例子，不是在代表性任務分布上跑出來的 benchmark。它的意義是讓 context admission 變得可操作：選 tool 變成檢索，中間資料留在 prompt 外，幾個相依的 tool 操作之間不必再插入一次 model call。

重點

  • 問題一：tool 定義塞爆 context。連上千個 tool 時，模型讀到請求之前要先處理數十萬 token。
  • 問題二：中間結果經過模型。把會議逐字稿從 Google Drive 搬到 Salesforce，全文會經過模型兩次。2 小時的會議約多花 50,000 token，模型抄寫時也可能出錯。
  • 好處 1：按需載入。列目錄找 tool，或提供 search_tools，並可選擇只回傳名稱、加描述、或完整 schema。
  • 好處 2：先過濾再回傳。10,000 列的試算表，在程式裡過濾後只把 5 列印給模型看。
  • 好處 3：控制流程在程式裡。Loop、條件、重試由程式執行，不必每一步都等模型決定。
  • 好處 4：隱私。MCP client 可以把 PII 換成代號（例如 [EMAIL_1]），模型只看到代號，真值直接在系統之間流動。
  • 好處 5：狀態與 skill。中間結果可存檔，之後接著做。寫好的函式可以存下來重用，加上 SKILL.md 就是 skill。
  • 代價：執行 agent 寫的程式，需要安全的 sandbox、資源限制和監控。這是直接呼叫 tool 不需要的維運成本。Cloudflare 把同類做法稱為 “Code Mode”。

具體範例

直接呼叫 tool 的版本：全部 issue 先進 context，模型讀完再自己挑，最後把文字再寫一次進 Slack 的參數。

背景概念

MCP 的基本結構
Host 裡的 MCP client 連到 MCP server。Server 宣告它的 tools（也可以有 resources 和 prompts），傳輸格式是 JSON-RPC。模型不執行 tool；它只輸出「請呼叫 X，參數是 Y」，由 harness 執行。
為什麼結果一定經過模型
在直接呼叫模式下，tool 結果必須附加成一則訊息，模型才看得到並決定下一步。Code execution 打破這個限制：結果先落在程式的變數裡。
Tokenization vault
PII 代號化和支付業的 tokenization 相同：系統之間流動的是代號，真值只在受信任的邊界內還原。對政府、醫療、金融這類受監管環境，這是一個可以寫進架構的控制點。
減少輪數 = 減少等待
每多一輪 model call，就多一次 time-to-first-token 的等待。把 if 和 loop 交給程式，省下的是輪數。

  • 10實測：唯一按需載入 schema 的 scaffold（7 個 vs 44 個），成本低 3.1 倍，但有 confound。

How skills and MCPs actually workLawrence Jones（incident.io）

打開原文 ↗

模型只看到一串訊息。MCP 往裡面加 tools，skill 往裡面加指令，plugin 把兩者打包。

核心主張

Skills 和 MCP server 裝進同一個 context window，模型都是以文字讀到它們，然後才做決定。所以設定 agent 時，一條指導有三個地方可以放：system prompt、skill，或 tool 本身。

這三個位置不能互換，差別也不只是措辭。System prompt 的優先權高於使用者訊息，寫在那裡的規則會被「服從」，而不是「權衡」。Tool description 每一輪都常駐，不論這一輪需不需要。用文字寫的要求，模型可以推理繞過。

作者的規則是：把 capability（能力）和 know-how（做法）分開，再各自放到讓模型正確對待它的位置。MCP 提供能力：一份合併進 prompt 的 tool 清單，和一般 HTTP API 差不多，OpenAPI 規格也能做到一樣的事。Skill 提供做法：以一般 thread 訊息的形式出現在 system prompt 下方，所以模型會把它和任務放在一起權衡。真正不能妥協的規則，兩邊都不放，而是做成 tool 的必填參數。模型必須提供的參數，它無法爭論。

重點

  • LLM 101：訊息有 system、user、assistant 三種角色。模型是 stateless，所有狀態都在 thread 裡。Tool call 由 harness 執行，結果附加回 thread，再整段送回模型。
  • Agent 就是這個流程跑 loop。Claude Code 給模型的 tools 很普通：Bash、Read、Write、Edit、Grep、WebFetch。
  • Bash tool 不一定真的跑 bash。只要回傳的結果看起來像 bash 就夠了。incident.io 在 Go 裡實作了一個虛擬 shell。
  • 成本：一個 skill 的 description 約 100 token 常駐；body 有幾千 token，只在匹配時載入。這和 04 的三層，是從不同團隊的實務獨立得出的同一結論。
  • 放錯位置的代價：「長時間範圍的查詢要拆小」寫在 system prompt 時，agent 拒絕使用者明確要求、而且安全的一週查詢。同一條規則改成 skill 後，請求正常完成。
  • 幻覺的一個來源：「為文件產生 3 到 5 個 tag」這種規則，遇到空文件時沒有合規的答案，模型只好捏造。作者認為他看到的前沿模型幻覺，多數來自這種「沒有出路」的 prompt。
  • 不可妥協的保證放在 tool 層：他們的 purge tool 沒有 dry run 或 confirm 參數就拒絕執行。
  • 架構轉變：他們把多個專用 agent（各自有 system prompt）合併成一個 agent 加多個 skills。一個 agent 看到全部 context，規劃更好。

具體範例

三個問題，決定一行設定該放哪裡

問題答案 → 位置
它必須每一輪都在嗎？否 → skill（按需載入）
它應該被權衡，還是被服從？權衡 → skill；服從 → system prompt
模型應該完全無法拒絕它嗎？是 → tool 的必填參數，或 07 的 hook

Server 端再檢查：同一個 subscription 沒有先跑過 dry_run，就拒絕 confirm。規則落在程式裡，模型無法說服它。

背景概念

Instruction hierarchy
模型被訓練成依 system、user、tool 結果的順序決定優先權。這是抵抗 prompt injection 的安全機制，也是本文說的「過度服從」的來源。
OpenAPI
HTTP API 的機器可讀描述。任何 OpenAPI 規格都能轉成一組 tool schema。所以 MCP 的新意在協定與生態，不在能力本身。
Plugin
一個資料夾加 .claude-plugin/plugin.json，裡面放 skills，也可以放 hooks、subagents、MCP 設定。概念類似 npm package。

Claude Code hooks referenceAnthropic 官方文件

Hooks 在 Claude Code 生命週期的固定時間點執行你的程式。PreToolUse 可以在動作發生之前擋下它。

核心主張

Instruction file 和 skill，只有在模型注意到並遵守時才有效。有些要求不能依賴模型合作，例如禁止寫入受保護的目錄。在 prompt 裡重複「絕對不要」只會花 token，不會強制執行。Host 需要一個確定性的攔截點，在動作之前；也需要動作與 session 事件之後的可觀測訊號。

Hooks 讓你在 SessionStart、PreToolUse、PostToolUse、Stop 等事件註冊 handler。PreToolUse 的 command hook 可以檢查一個即將發生的 tool call，在 permission check 或執行之前擋下它。

課程說 hooks 劃出 guidance 與 enforcement 的界線。建議只讀 event table，不必讀每個 schema。目標是分類：哪些要求屬於 context，哪些屬於自動修復，哪些必須在執行前就被拒絕。

重點

  • 三層結構：event（何時）→ matcher（過濾，例如只看 Bash 或 Edit|Write）→ handler（做什麼）。
  • Handler 類型：command（shell 指令）、http（POST 到 URL）、mcp_tool、prompt（請模型判斷）、agent（實驗中）。
  • 設定位置：~/.claude/settings.json（個人，所有專案）、.claude/settings.json（專案，可 commit）、.claude/settings.local.json（專案，不 commit）、managed policy（組織管理員）、plugin、skill 與 subagent 的 frontmatter。
  • Exit code：0 成功；2 阻擋（PreToolUse 擋下 tool call，Stop 讓 Claude 繼續工作）；其他值（包括 1）只是非阻擋錯誤，動作照樣執行。
  • Fail-closed：預設 hook 壞掉或逾時，動作照做。政策型 hook 要設 "onFailure": "block"。
  • if 欄位是 best-effort 過濾。需要硬性 allow / deny 時，用 permission 系統，不要只靠 hook。
  • 用 /hooks 查看目前載入了哪些 hook、來自哪個設定檔。

常用事件

Event何時觸發能阻擋嗎典型用途
SessionStartSession 開始或 resume否注入目前 branch、未完成 issue 等 context
UserPromptSubmit使用者送出 prompt，Claude 處理前是擋下含 secret 的 prompt；附加 context
PreToolUseTool 執行前是擋 rm -rf；擋寫入受保護目錄；改寫參數
PermissionRequest需要權限決定時用 JSON decision自動允許安全指令
PostToolUseTool 成功之後否（stderr 回饋給 Claude）每次編輯後自動跑 formatter 或 lint
StopClaude 回應結束是（讓它繼續）測試沒過就不准結束
PreCompactContext 壓縮之前是壓縮前備份 transcript
SessionEndSession 結束否清理、記錄

背景概念

類比：Kubernetes admission controller
PreToolUse 像 validating / mutating admission webhook：可以拒絕，也可以用 updatedInput 改寫參數。PostToolUse 像 audit log。
Fail-open vs fail-closed
預設是 fail-open：hook 壞了，動作照做。安全政策通常要 fail-closed。路徑打錯的政策 hook 會一直沒跑，而且表面上看不出來。
Guidance vs enforcement
CLAUDE.md 裡的「不要」是 guidance。Hook 是 enforcement。09 發現「不要」型規則有幫助，但有幫助不等於有保證。

The Harness Is the ThingScott Fryxell

部落格2026-08-25約 10 分選讀
打開原文 ↗

模型正在變成可替換的零件。真正要設計的是 harness：角色、模型路由、scripts，以及跨 session 留下來的檔案。

核心主張

作者同時用幾個 terminal coding agent（Cursor、Claude，需要時再加 Pi）。他把形塑它們的設定放在任何單一產品之外：一份指令檔、skills、extensions、scripts、一個工作目錄，全部在一個 repo 裡，每個 agent 都載入同一份。本文把這一整圈結構，而不是 terminal 背後的模型，稱為 harness。換工具時，不必重寫設定。

他把一件工作拆成隔離的角色。Exploration 產出計畫；計畫變成明確的 DAG 任務清單；worker 一次實作一個節點；critic 精簡並質疑結果；promoter 對外溝通完成的工作。一個同時規劃、實作、自我批評的 prompt，會混淆自己的目標。每個角色配一個合適的模型：前沿模型留給規劃、第一個任務和 promotion，維護工作交給便宜模型。

他自述在最密集的情境下，前沿模型用量降低 75%，兩個每月 20 美元的訂閱就夠應付客戶與個人專案。課程提醒：這是一個開發者對自己專案的自述，不是受控量測；作者也承認，要確認哪些 harness 改動真的有效，還需要他尚未採用的實證方法。

重點

  • 三個工具共用同一份 AGENTS.md 和 skills，體驗一致，因此不依賴任何一家。
  • 角色流程：explore → planner（DAG）→ worker → critic → promoter。Critic 常常把工作推回給 worker。
  • 「Prewalk」：用前沿模型做規劃與第一個任務，pattern 確定後交給便宜模型。
  • 可重複的工作寫成 script 放進 harness。之後執行多少次都不花 token。
  • 所有產出放在 artifacts/ 目錄，保持可稽核。
  • 他發現 skill 寫得太細反而浪費 token，正在學著放鬆指示的細節。

具體範例

階段做什麼用哪種模型
Explore / planner探索，產出 DAG 計畫前沿模型
Worker 的第一個節點定下實作的 pattern前沿模型
其餘 worker、critic、日常維護照 pattern 實作、精簡、質疑便宜模型為主
Promoter對外溝通完成的工作部分用前沿模型

背景概念

Model routing / cascade
先用便宜模型，遇到難題才升級。這是降低推論成本的常見架構，和儲存系統的冷熱分層是同一個思路。
Planner–executor–critic
Agent 設計中常見的角色分離。好處是每個 prompt 只有一個目標。壞處是角色交接時會遺失 context，需要明確的交接物（計畫檔、DAG）。
AGENTS.md
跨工具的指令檔慣例。Claude Code 讀 CLAUDE.md，但可以在 CLAUDE.md 裡 import AGENTS.md，讓不同工具共用。

Guardrails Beat GuidanceA Large-Scale Study of Rules, Skills, and Persistent Configuration for Coding Agents · Zhang et al.

論文 · arXiv 2604.110882026-04（v2 2026-05）挑段落約 25 分必讀

5,000 多次 Claude Code 實驗：隨機規則和專家規則一樣有效。單獨有益的規則都是「不要」，有害的都是「要」。

核心主張

Coding agent 會把 repo 規則、skills、持久設定當成 context 載入。團隊憑經驗寫這些檔案，但一條看起來合理的規則，並不能證明它造成了更好的結果。規則的內容、正負語氣、位置，以及「多了一段 context」這件事本身，全部混在一起。除非每一項都和無規則的對照組比較，否則觀察到的例子無法指出是哪條指令有幫助。

作者從 GitHub 收集 679 個規則檔，抽出 25,532 條規則。接著在 SWE-bench Verified 上跑超過 5,000 次 Claude Code（Claude Opus 4.6），變化 curated、random、shuffled、mismatched，以及逐條 ablation 等條件。

結果一：在 58 題的子集上，curated 和 random 規則都比無規則基準高 13.8 個百分點（50.0% → 63.8%）。結果二：逐條 ablation 中，有益的規則都是負面限制，有害的規則都是正面指令。課程提醒兩件事：random 對照組說明了為什麼沒做 ablation，就不該把功勞歸給某條規則；polarity 結果應視為強假說，不是普遍定律，因為實驗只用一個 harness、一個模型、一個 benchmark 子集。

重點

  • 挑題方法：500 題各跑 3 次基準。47% 永遠成功、27% 永遠失敗，沒有訊號。只保留成功 1 或 2 次的 58 題（discriminative tasks）。
  • Exp 1 有沒有用：七種規則條件都比基準高 6.9–13.8 pp，但彼此之間沒有顯著差異。錯領域規則（React 規則用在 Python 題）58.6%，同領域 56.9%；打亂句子也差不多。作者解讀為 context priming：有結構、相關的指令，讓模型進入比較謹慎的模式。
  • Exp 2 數量：規則從 0 到 50 條，通過率都在 59–67%，沒有「太多就崩潰」的臨界點。
  • Exp 3 類型：tool / process 規則 63.8% 最高，architecture 規則 53.4% 最低。方向符合預測，但不顯著。
  • Exp 4a 逐條拿掉（18 條、35 題）：3 條有益，全是「不要」；4 條有害，全是「要」（讀測試檔、照 code style、處理 edge case、保持相容）；其餘 11 條影響不大。
  • 最強的一條：「不要重構無關的程式碼」，拿掉後掉 20 pp（p = 0.016）。但它是唯一單獨顯著的，而且通不過嚴格的多重比較校正。
  • 門檻敏感度：以 3 或 5 pp 判定時，正負分界成立；7 pp 變弱；10 pp 消失。
  • 整體韌性：單獨看起來有害的規則，放進整組後傷害不會累積。作者稱之為 distortion averaging。

具體範例

論文的作者建議（Box 1，限 Claude Code 類 agent 與 SWE-bench 類任務）

做不要做
寫負面限制（「不要 X」）沒有檢驗就寫正面指令（「照 code style」「處理 edge case」）
放規則；隨機或錯領域的規則也有幫助花大量時間雕琢措辭；有沒有放比怎麼寫更重要
最多 50 條規則都沒觀察到退化只靠逐條單獨評估來挑規則；整組效應才是主角

背景概念

SWE-bench Verified
從真實 GitHub issue 中，經人工確認可解的 500 題。Agent 要產生 patch，讓 repo 的測試通過。題目都是 Python bug fix，天生偏好「最小修改」。
Ablation
一次拿掉一個元件，看結果變多少。這是歸因的基本方法。
McNemar test
同一題在兩個條件下的成敗是成對資料。McNemar 只看「一邊過、一邊沒過」的題目。論文自己說明：58 題大約只能偵測 15 pp 左右的差異。
多重比較
測 18 條規則、門檻 p < 0.05，純靠運氣也預期約 0.9 條「顯著」。Bonferroni 校正會把門檻降到約 0.0028。
PBRS（potential-based reward shaping）
Ng 等人 1999 年的 RL 結果：依狀態而定的輔助獎勵不改變最佳策略，與狀態無關的偏差可能扭曲它。作者只把它當比喻，並指出比喻在哪裡失效。
外部效度
SWE-bench 獎勵小 patch，所以「不要重構」自然有利。換成需要大幅修改的任務，結論可能不同。

The Scaffolding Matters More Than the InterfaceA Controlled Comparison of MCP and CLI Tool Use · Alier Forment, Casañ, García-Peñalvo, Pereira

論文 · arXiv 2608.086542026-08挑段落約 30 分；全文 1 小時以上推薦（在乎自架小模型則必讀）
打開原文 ↗

同一個 GitHub 任務、7 個 scaffold、5 個模型：成本主要由 scaffold 決定，不是 MCP 或 CLI。

核心主張

Agent 可以透過 MCP tools 操作 repo，也可以直接寫一般的命令列指令。很多比較把成本差異歸給介面，但同時也換了外圍的 harness。System prompt、tool 描述、重試行為、agent 有沒有真的走被指定的路徑，每一次都可能不同。所以沒有配對的比較，其實同時量了好幾個變數。

作者固定一個 6 步驟的軟體任務，在 7 個 agent scaffold、5 個模型上執行。在同時支援兩種介面的 scaffold 上，做 MCP 與 CLI 的配對。完成度用 repo 的實際狀態驗證，不相信 agent 的自我回報。

結果：scaffold 主導成本。13 組配對的 MCP / CLI 成本比，從 0.43× 到 29×；agent 也常常不用被指定的介面。課程要你留下的是方法要求：比較介面時，要驗證實際走的路徑，並固定 harness。證據只來自一個小任務，所以要記住的是「比例不穩定」，不是任何一個比例。

重點

  • 任務：找 issue → 開 branch → 套 patch → commit → 開 PR → 回報某目錄有幾個檔案。事後用 GitHub API 檢查 4 個條件。
  • Scaffold：Claude Code、Codex、qwen-code、Hermes、opencode 支援 MCP；pi 和 Tau 沒有 MCP client，作為對照。
  • CLI arm（完全沒掛 MCP）：pi 和 Claude Code 差 28 倍。Claude Code 的 27 個內建 tool schema，讓任務還沒開始就約 22,000 token。
  • 小模型：27B 本地模型在 Tau 下花 17,416 token，在 Codex 加 MCP 下花 2,418,828 token（108 次 tool call）。差 139 倍，兩者都完成任務。
  • MCP vs CLI：13 組配對比 0.43×–29.06×，中位數 0.93，無法下結論。同一設定重跑的變異中位數 1.51×、最大 5.41×，所以小於約 2 倍的差異都分不出來。
  • 失敗的成本：兩邊失敗次數相同（各 19 次中 3 次）。但 MCP arm 有 12.9% 的錢花在沒完成的 run，CLI arm 只有 2.2%。失敗的 run 花的 token 約是成功 run 的 2 倍。
  • Schema 傳送方式：Hermes 每次只送 7 個 schema（含一對 gateway tool，其餘定義按需取得），其他 scaffold 每次送 44 個。成本差 3.1 倍，但只有一個樣本，有 confound。
  • Agent 不照指定介面：在沒有隔離的預實驗中，21 次 run 只有 6 次只用 MCP。改 prompt 沒用；把替代路徑的 credential 拿掉才有用。

背景概念

Scaffold = harness
把使用者請求送進模型、執行模型要求的動作、把結果送回去的那一層軟體。本文用 scaffold，其他篇用 harness，指的是同一件事。
Schema 成本乘上輪數
模型在請求之間不記得任何事，每次請求都要重送整個 tool 清單。成本約等於「輪數 × schema 數 × 每個 schema 的 token」。Prompt caching 會打折，但不會讓它消失。
配對設計與 confound
同一個 scaffold、同一個模型，只換介面，才是配對比較。跨 scaffold 比較時，其他所有差異都混在結果裡。
驗證環境狀態
就像測試要 assert 結果，而不是看 log 寫了 success。論文中一個 credential 設錯的 run，從成本、完成度、tool call 看起來都很正常，只有 agent 最後一句話透露了問題。
Resolution limit
同一設定重跑的變異，決定了實驗能分辨的最小效果。小於這個範圍的差異，不能當成結論。

對自架、地端部署的意義

27B 模型在每一個 scaffold 下都能完成任務。限制它的是 scaffold 替它花了多少 token，不是模型能力。對 air-gapped、自架模型的團隊，選一個精簡、可控的 scaffold，可能比等待更大的模型更有效。作者的建議：開放式探索用通用 assistant；邊界清楚、會重複執行的任務，用團隊自己能改的小 scaffold。
