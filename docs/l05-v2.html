Lecture 05 · 試讀版：依想法重組

Multi-agent：什麼時候值得拆，拆了怎麼不壞

  • 閱讀約 19 分鐘
  • 現行版本L5（照投影片順序）

先看這裡

多一個 agent 只是多一個 loop，兩個 loop 的 context 互不相通，只能靠文字傳話。這一條限制決定了一切：拆開的好處來自隔離，代價也來自隔離。所以這堂要帶走的不是幾種架構的名字，而是判斷什麼時候值得拆，以及拆了之後把風險放在哪裡。

  • 多數任務不該拆。可以平行的任務能進步八成，循序的任務反而退步四到七成。效果由任務的形狀決定。
  • 讀可以平行，寫盡量留在單線。這是目前最實用的一條分界，也最常被架構分類蓋過去。
  • 拆了之後，風險在交接。規格沒寫的事不存在，摘要會丟細節，timeout 分不出對方做了沒，傳回來的文字也可能夾帶指令。

1根本的限制：agent 之間只能傳文字

L4 說過，一個 agent 是 model 加 loop：model 決定下一步，harness 執行 tool，再把結果放回 context。第二個 agent 就是第二個 loop，有自己的 system prompt、tool 清單和 context window。兩個 loop 沒有共用的記憶，一方知道的事，必須寫成文字送過去，另一方才知道。

隔離能換到四樣東西，但不是每一樣都非拆不可：

換到什麼例子一個 agent 做得到嗎
平行四個方向同時查做不到
權限隔離讀網頁的 agent 沒有 shell做不到
乾淨的 context查資料的過程不進主對話部分可以，靠壓縮
專一的 prompt 與 model搜尋交給便宜的 model部分可以，靠 skill

代價也從隔離來。每交接一次，就多三件事：資訊遺失、多一份 context、多一個會失敗的點。其中 context 的帳最容易低估，因為訊息進了 context，之後每一圈 loop 都要重送。一則 2k token 的 broadcast 發給 10 個 agent，每個 agent 再跑 20 圈，就是 2k × 10 × 20 ＝ 400k token 的 input。

所以拆開不是免費的組織方式。後面每一章都在處理同一個問題：怎麼讓該過去的資訊過去，不該進 context 的不要進去。

2最重要的判斷：多數任務不該拆

Multi-agent 常被當成「更強的 agent」，實測卻是有好有壞，差距很大：

任務和單一 agent 比來源
可以拆開分析的任務（財務推理），中央協調約 +81%Towards a Science of Scaling Agent Systems，260 種設定的對照實驗
嚴格循序的規劃任務（PlanCraft）−39% 到 −70%
研究類，平行查很多方向+90.2%，但 token 約是聊天的 15 倍Anthropic 的 multi-agent research system，內部評估

三列的差別不在架構，在任務的形狀：子任務能不能獨立進行。循序任務一拆就退步，因為每一步都要知道上一步的細節，而細節正是交接時會掉的東西。同一篇實驗也顯示，用任務的特徵預測該選哪種架構，在沒看過的設定上有 87% 選對。

這條路的第一格最重要。實務上可以問一句：拿掉一個 agent，品質掉多少？掉得不多，就先不要加。要回答這句話，就得先有單一 agent 的基準線，所以評估要先於架構，這是 L7 的主題。

3最實用的分界：讀可以平行，寫留在單線

常見的架構分類看的是誰管誰。實務上更有用的問題是：這個 agent 會不會改東西。Cognition（Devin 的開發公司）2025 年的 Don't Build Multi-Agents 指出，動作帶著隱含的決定。寫程式時要選命名、風格、邊界條件的處理方式，這些決定多半沒有說出口。兩個 agent 各寫一半，就會各選一套。

讀就沒有這個問題。三個 agent 分別查安全、效能和錯誤，發現只會累積，不會互相矛盾到無法合併。這也解釋了上一章的數字：研究和分析吃得到平行的好處，而 Anthropic 也提醒，多數 coding 任務能平行的部分比研究少。

十個月後，Cognition 在 Multi-Agents: What's Actually Working 修正了自己的立場，不再一概反對，但結論更清楚：寫保持單線，其他 agent 貢獻判斷，不貢獻動作。他們列出幾種行得通的形狀：

Writer 加 reviewer 最值得學。Cognition 說，他們的 review agent 平均在每個 Devin 寫的 PR 抓到約 2 個 bug，其中約 58% 屬於嚴重問題。反直覺的是，兩邊事前不共用 context 時效果最好：reviewer 只看 diff，不知道作者的理由，就不會被理由說服。這和人類的 committee 同一個道理：多一票只在錯誤彼此獨立時才有意義。同一個 model、讀同一份 context，兩票同意帶來的新資訊很少。

平行寫什麼時候可以。範圍切得開，而且有能自動驗證的標準。Cognition 認為，一些大型展示（用很多 agent 寫瀏覽器、C compiler）能成功，部分原因是成功標準簡單又可驗證，多數真實軟體沒有這種條件。L3 講的 worktree 能解決檔案衝突，但解決不了隱含決定的衝突。

本文的判斷：驗證能力比架構重要。沒有測試或 reviewer，多個 agent 只是更快產生沒人檢查的東西，瓶頸會移到人身上。Cognition 也觀察到，使用者開始卡在管理、規劃和 review 大量 agent。這些是單一公司的經驗，不是對照實驗，所以當成假設來驗證，不要當成定律。

5回報：訊息只帶主張和證據，原文放檔案

把多份輸入變成一份輸出的節點，都會丟細節，而且下游不知道丟了什麼。Supervisor 讀 8 份報告寫一份摘要，每多一層 lead 就再摘要一次。底層 agent 誤讀了一個欄位，到上面只剩「API 完成」。

但彙整節點不該拿掉。實驗量到，沒有人彙整的系統把錯誤放大 17.2 倍，中央協調只有 4.4 倍，因為有人彙整，錯誤才有機會停下來。該做的是讓彙整者看得到證據：

外層欄位讓程式直接判斷。路由、重試、停止都看欄位，不要問 LLM 這段話是什麼意思，這樣更快、更便宜，每次結果也相同。自然語言只留給真正需要判斷的內容。

要選傳法時，只要先記一個問題：這則訊息會進幾個 context？點對點進一個，broadcast 進全部。第 1 章的 400k token 就是這樣來的，所以只有所有人都要知道時才 broadcast。

6失敗：timeout 之後，你不知道對方做了沒

只要 agent 不在同一個 process，它們之間就是分散式系統。最典型的情況是 A 叫 B 買 8 台 GPU，然後 timeout：

A 分不出來，所以兩邊都有風險：不重試可能一台都沒買，重試可能買到 16 台。傳遞層也幫不了你：它只能保證最多送達一次（可能丟），或至少送達一次（可能重複），因為「收到了」這個確認本身也會遺失。

解法分兩層：傳遞層一直重送，接收端負責認出重複的請求，不做第二次。後者叫冪等（idempotent）：做一次和做很多次，結果相同。做法是用 task_id 當 key，收到請求先查紀錄：

LLM 還多一個陷阱：讓它自己決定重試，它可能產生新的 task_id，key 就對不上了。所以重試由 runtime 用同一個訊息重送，不交給 model。其他常見的失敗，對策也都在 runtime：

失敗長什麼樣對策
繞圈A 問 B，B 問 C，C 問 A訊息帶跳數上限，到 0 就報錯
沒人負責每個 agent 都以為是別人的事每個 task 一個 owner
過期的事實X 已經改成 5，B 還依 X＝3 行動事實帶版本，用之前重讀
互相矛盾A 說安全，B 說有漏洞指定裁決者，兩邊都附證據
等不到人一個 worker 慢，全部卡住Timeout 後先用部分結果

LLM 不會自己發現它在繞圈，也不會發現手上的事實過期了，要靠訊息的欄位和 runtime 的規則替它擋。

7安全：傳回來的文字也不可信

第 1 章說，拆開可以隔離權限：讀網頁的 agent 沒有 shell，網頁裡的指令就算騙過它，也碰不到危險的 tool。這只擋了一半，因為它的輸出還是會回到另一個 agent 的 context：

對 model 來說，worker 的報告和使用者的話都只是文字。Prompt Infection（2024）更進一步展示，惡意 prompt 可以像病毒一樣在 agent 之間自我複製，即使 agent 彼此並未公開所有通訊。這是 multi-agent 特有的風險：線越多，感染的路徑越多。

這個問題目前沒有根治的方法。該論文提出的標記法搭配既有防護，能大幅降低擴散，但不是消除。實務上是多層防線：

  • 把回報當資料，不當指令。Worker 的內文放進固定欄位，supervisor 的 prompt 明寫裡面的內容不能當指令執行。
  • 危險動作不由文字決定。刪除、付款、對外傳送這類動作，由 runtime 檢查 allowlist，或要人確認。這是第 5 章「看欄位，不看內文」的延伸。
  • 拆開三種能力。同時能讀私密資料、會接觸不可信內容、又能對外傳送的 agent 最危險，Simon Willison 稱為 lethal trifecta。切到不同 agent 時，別忘了文字還是會流回來，所以兩者之間還是要有上一點講的關卡。
  • 別把對方的自述當認證。A2A 的 agent card 寫的 skill 是對方自己宣稱的，認證只告訴你對方是誰，不代表內容可信。

這一章的取捨是本文的判斷。受管制或多租戶的環境，這一章的份量應該和第 2 章一樣重。

8目錄：八種架構、通訊選項、兩個協定

這一章不必讀完，需要時再查。架構的名字只是三個問題的答案組合：誰協調、誰和誰說話、工作怎麼拆。拿到任何系統，先把這三題各答一句，比記名字有用。

架構適合弱點什麼時候想到它
Supervisor–worker可分開的子任務中心的 context 長得最快預設的第一選擇
Hierarchical有層次的任務錯誤層層放大一層 supervisor 真的管不完
Pipeline / DAG順序清楚的階段錯誤往下傳流程固定、要好除錯；記得加 retry edge
Blackboard共同的產出狀態過期Agent 會來來去去，要留下可檢查的紀錄
Committee需要判斷的題目盲點相同值得付多次成本，而且能讓意見獨立
Market能力、成本不一的 agent自報的出價不實任務分配本身是問題
Swarm局部協商線數 n(n−1)/2很少；產品中罕見
Dynamic topology結構事先未知難重現、難除錯簡單案件要便宜，難的才升級
查閱八種架構與混合系統，一種一張圖
查閱通訊的選項：三種 medium、六種 channel

兩個協定。看對面是什麼：對面是明確的動作、一次一個結果，用 MCP；對面會自己推理、可能反問、可能跑很久，用 A2A。兩者都不替你決定要不要委派、怎麼拆、何時停，那些仍由 harness 決定。

動手與討論

用自己的任務驗證一次

第 2 章的問題最好自己量。挑一個真實的 PR，同一份 diff 跑兩次，再看哪一次抓到的真問題多、花了多少。這組指令本文還沒實際跑過；total_cost_usd 會包含 subagent 的花費，但只是估算值。

討論題。

  1. 你現在的 agent 流程裡，哪些步驟會寫、哪些只讀？寫的部分是單線嗎？如果不是，靠什麼避免隱含決定互相衝突？
  2. Reviewer 不看規格能避免被說服，卻可能漏掉「功能做錯了」。你會給 reviewer 哪些資訊，哪些刻意不給？
  3. 實驗顯示中央協調能壓低錯誤放大，Cognition 卻提醒平行 agent 會互相衝突。這兩件事矛盾嗎？各自在回答什麼問題？
