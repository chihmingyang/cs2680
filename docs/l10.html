導讀

你在一張 H200（NVIDIA 的 GPU）上跑語言模型（下面叫 model），一次只服務一個請求。監控工具 nvidia-smi 顯示使用率 100%，字卻出得很慢。你的第一個念頭是 GPU 不夠快，要再買一張。其實這張 GPU 的運算能力只用到大約 0.5%（第 3 章用規格算出這個數字）。它的時間幾乎都花在搬資料：把 model 的參數（訓練出來的一大堆數字，就是 model 的本體）從 GPU 自己的記憶體讀到做運算的電路上。那個 100% 只代表「有程式在跑」。

Model 的每一步運算，在 GPU 上是一段一段的小程式在跑，每一段叫一個 kernel。一個 kernel 要花多久，看兩件事：要從記憶體搬多少資料，和要做多少次運算。資料是邊搬邊算的，所以時間不是兩者相加，是比較慢的那一件；這個估法叫 roofline。這堂回答的問題是：怎麼先算出瓶頸在哪一邊，再用對的數字確認。

  • 先算每搬 1 byte 做了幾次運算。這個比值叫 arithmetic intensity，是 kernel 的性質。GPU 這邊有一個單位相同的數字，叫 ridge point：它每秒能做的運算次數，除以它每秒能從記憶體搬的 byte 數，也就是搬來的每 1 byte 要配幾次運算，運算電路才不會停下來等資料。H200 的 ridge point 大約是每 byte 206 次。Kernel 的比值低於 ridge point，慢的是搬資料（叫 memory-bound），這時加運算能力沒有用，要想辦法少搬；高於它，才是運算能力不夠（第 2 章）。
  • Model 逐字輸出時，慢的是搬資料。Model 一次輸出一個 token（文字的一小段，中文大約一個字）。每產生一個 token，都要把全部的參數從 GPU 的記憶體讀一遍：參數有十幾到上百 GB，做運算的電路旁邊留不住，只能每次重讀。每個參數讀進來只算一次，搬得多、算得少，比值大約是每 byte 1 次，遠低於 206，所以例子裡運算能力只用到約 0.5%（第 3 章）。
  • 把請求併成一批，分攤得了參數，分攤不了每個請求自己的資料。改法是把很多請求併成一批一起算，一批叫一個 batch：參數讀一遍，整批請求一起用，batch 越大，每個請求分攤到的搬運越少。分攤不了的是 KV cache：每個請求到目前為止的對話算出來的中間結果。新的 token 要參考前面的每一個字，所以每產生一個 token，這個請求的 KV cache 也要整份讀一遍，別的請求用不到。對話越長，這個請求每一步要讀的就越多，每個字也就出得越慢（第 3 章）。
  • 量對了再改。Model 逐字輸出的階段，要看的是記憶體每秒能搬的量（叫記憶體頻寬）用了幾成；nvidia-smi 的 100% 沒有告訴你這個（第 5 章）。

第 4 章打開晶片內部，需要時再查。瓶頸找到之後怎麼改，在 L10b〈Kernel Optimization〉：要不要自己寫 GPU 程式、一個 kernel 之內怎麼少搬資料、kernel 和 kernel 之間怎麼少空等（GPU 跑完一個 kernel，閒著等下一個），AI 寫的 kernel 怎麼驗收，以及一張 GPU 以外的限制（網路、故障、電力）。

核心觀念

先算瓶頸在記憶體還是算力，再量

五章照「後一章用到前一章」排。前三章先把 GPU 當成規格表上的幾個數字來估算：GPU 為什麼這樣設計、roofline 怎麼判斷卡在算力還是頻寬、decode 為什麼卡在頻寬。第 4 章打開晶片，看這些上限在什麼條件下才拿得到；第 5 章的量測，看的就是晶片裡這些單元忙不忙。

1GPU 的設計：用上萬個簡單的核心換 throughput

L1 說過，LLM 的 decode（一次產生一個 token、逐字輸出的那一段）卡在記憶體頻寬，GPU 做運算的電路（下面叫運算單元）大多在等資料（L1〈時間〉）。這一堂解釋為什麼，以及怎麼量；怎麼改在 L10b〈Kernel Optimization〉。這一章先看 GPU 為什麼做成上萬個簡單的 core。

Latency 與 throughput：CPU 為前者設計，GPU 為後者設計。Latency（延遲）是一件工作從開始到結束要多久，throughput（吞吐量）是單位時間做完多少件。打個比方：跑車一次載 2 個人，到得最快；一隊巴士每台都比較慢，一次卻能載幾千人。CPU 是跑車，為 latency 設計；GPU 是巴士車隊，為整顆晶片的 throughput 設計。

Core（核心）是執行指令的電路；thread 是一串依序執行的指令，帶著自己的 register（暫存器，core 裡最快、最小的儲存位置）。

CPU 的每個 core 把大部分面積給了讓一個 thread 跑最快的東西：大的 cache（core 旁邊的小記憶體，放最近用過的資料，下次不必回到慢的主記憶體去拿），和兩種控制邏輯，out-of-order execution（不照順序執行，先做資料已經到的指令）與 branch prediction（先猜 if 會走哪一邊，照著做下去）。GPU 反過來，把面積給了運算單元：

H200 有 132 個 SM（streaming multiprocessor，GPU 的基本運算單位，可以想成一個小處理器），共 16,896 個 FP32 core（做 32 位元浮點運算的電路）。這種 core 很簡單，自己不取指令（下面 SIMT 一段會講，32 個 core 共用一次取指令），所以同樣大小的晶片放得下上萬個。拿來和 CPU 的 core 比的是 SM：一個 SM 才像一個有自己排程的小處理器。兩者的差距如下（TFLOP/s 是每秒做幾兆次浮點運算，第 2 章細講）：

Warp（32 個 thread 一組）的切換：GPU 藏住記憶體延遲的方法。從 HBM（high bandwidth memory，GPU 的主記憶體）讀一筆資料約要 500 個 cycle（時脈的一拍；H200 每秒約 20 億拍，所以約 250 ns）。CPU 靠 cache 和 out-of-order 撐過這段等待，GPU 則是換一批工作來做。GPU 的 thread 以 32 個為一組，叫 warp。每個 SM 有 4 個 warp scheduler，每個最多管 16 個 warp，所以一個 SM 上同時有 64 個 warp。一個 warp 在等記憶體時，scheduler 下一個 cycle 就改發另一個 warp 的指令：

切換不花時間，因為每個 warp 的 register 一直留在 SM 上，不必像 CPU 換 thread 時把狀態存回記憶體。代價是要有足夠多的 warp 可以換：工作太少時，所有 warp 都在等，運算單元就空轉。所以 GPU 要有幾十萬個 thread 的工作才填得滿。

SIMT：程式為一個 thread 寫，同一個 warp 的 thread 共用一條指令流。CPU 有 SIMD（single instruction, multiple data）：一條指令同時處理 8 或 16 個數字，但程式要明確寫成一次處理一排數字。GPU 的 SIMT（single instruction, multiple threads）把這件事藏起來：你寫的是一個 thread 一次處理一個數字的程式，硬體把 32 個 thread 綁成一個 warp，共用一次取指令、一次解碼和一次排程，也就是共用同一串指令（指令流）。Warp 裡的 32 個位置各叫一個 lane：一個 lane 跑一個 thread、用一個 FP32 core 和自己的 register，每個 thread 拿到的編號不同，所以 同一行程式在 32 個 lane 上算到 32 個不同的元素：

Divergence：同一個 warp 走不同分支，兩邊都要走一次。32 個 lane 共用一條指令流。碰到 if/else 而 lane 之間的答案不同時，warp 只能輪流執行兩邊：先跑 if 那一邊，用 active mask（標記哪些 lane 要寫結果的位元遮罩）關掉不該寫的 lane，再跑 else，最後再合流。例如 if (i % 4 == 0)：

這段花的時間是 f 加 g，不是二選一，關掉的 lane 只是閒著。所以寫 GPU 程式時，同一個 warp 的 thread 最好走同一條路；控制流程很不規則的工作，例如排序或圖演算法，在 GPU 上比較難寫快。

GPU 放棄的四樣：單一 thread 的速度、自動的平行、各自的控制流程、每個 thread 的大記憶體。把上面合起來，GPU 放棄了四樣東西，各換到一樣：

  • 放棄單一 thread 的速度。不先猜分支、不重排指令，循序的程式慢很多。換到的是面積和電力都給了上萬個 FP32 core。
  • 放棄自動的平行。CPU 會在一個 thread 裡自己找出能同時做的指令（instruction-level parallelism，靠 out-of-order execution）；GPU 要你自己給它夠多的 thread，約 27 萬個才填得滿 132 個 SM，工作小的時候晶片大半閒著。換到的是不必把面積花在大 cache 和 out-of-order 上，等待改用切換 warp 藏住。
  • 放棄各自的控制流程。32 個 thread 共用一條指令流，分支不同就要輪流跑（上一段的 divergence）。換到的是取一次指令、解碼一次，就能驅動 32 個 core。
  • 放棄每個 thread 的大記憶體。滿載時 registers 加 shared memory（SM 上給同一個 thread block 共用的晶片內記憶體；thread block 是程式一次交給一個 SM 的一批 thread，L10b〈CUDA kernel〉講；這塊記憶體第 4 章細講），平均每個 thread 只有約 240 bytes。換到的是所有 thread 的狀態都留在晶片上，切換 warp 才不花時間。

本文的判斷：讀者最常撞到的是第二個取捨的後果：工作小的時候晶片大半閒著。LLM 適合 GPU，因為 model 處理的每個 token（文字切成的小段）都用同一組 weights（model 的參數）做同樣的矩陣乘法，可以大量平行。但 decode 一次只產生一個 token，每一步的工作量太小，問題有兩層，都是工作不夠多。第一層和 thread 的數量無關，缺的是每個 byte 上的運算：讀進來的每個 weight 只做一次乘加，而 HBM 每秒送得來的資料有上限，warp 再多，送來的資料也只夠運算單元忙一小段時間（下一章把它算成數字）。第二層缺的才是 thread：有些運算本身能拆開平行的部分不多，切不出上百個 thread block；一個 block 交給一個 SM，多出來的 SM 沒有工作。怎麼把這類運算切得更細，在 L10b〈SM 之間的空等〉。

2Roofline：GPU kernel 的時間由搬資料與運算較慢的一邊決定

上一章說 GPU 要大量平行才填得滿。但填滿了也不一定快：資料供不上時，運算單元一樣在等。這一章給一個判斷工具，叫 roofline（屋頂線，畫成圖時形狀像屋頂）：先算一個 kernel（在 GPU 上跑的一個函式，CPU 每發一次 launch 它就跑一次）要搬多少 byte、要算多少 FLOP，就能估出它最快能多快，以及卡在哪一邊。之後每一種最佳化，都在移動這兩個數字的其中一個。

FLOP、byte、bandwidth：roofline 用的三個單位。

  • FLOP。Floating-point operation，一次浮點加法或乘法。矩陣乘法裡最常見的是 multiply-add（先乘再加），算 2 個 FLOP。FLOP/s 是每秒做幾個，1 TFLOP/s 是每秒一兆個。
  • Byte。資料量。BF16（一種 16 位元的浮點格式，LLM 推論最常用）每個數字 2 bytes，FP32 每個 4 bytes。下面用 b 代表每個數字幾個 bytes。
  • Bandwidth。頻寬，每秒能從記憶體搬多少 bytes，例如 4.8 TB/s。它和 latency 是兩回事：latency 是一筆資料要等多久才到，頻寬是持續搬的時候每秒到多少。

GPU 的三個規格：算力、記憶體頻寬、記憶體容量。用汽車比喻：算力是引擎，頻寬是油管，容量是油箱。算力限制算得多快；容量限制放得下多少 weights 和 KV cache（每個請求存下的前文中間結果，下面的前情細講）；頻寬限制讀 weights 和 KV cache 讀得多快：

Decode 和 prefill 要的改法完全相反：prefill 要更快的算力或更少的 FLOP，decode 要更少的 bytes。

Arithmetic intensity 與 ridge point：判斷 memory-bound 還是 compute-bound。比較公式的兩項誰大，移項之後是比兩個數字，一個屬於 kernel，一個屬於硬體：

  • Arithmetic intensity。運算強度，等於 FLOPs ÷ 搬的 bytes：每從 HBM 搬 1 byte，做幾個 FLOP。它由 kernel 的寫法和輸入的大小（矩陣幾乘幾、batch 多大）決定。
  • Ridge point。等於 peak 算力 ÷ 頻寬：每搬 1 byte 要配幾個 FLOP，運算單元才不會閒著。H200 是 989 ÷ 4.8 ≈ 206 FLOP/B。

Intensity 低於 ridge，kernel 受頻寬限制（memory-bound），每秒做到的 FLOP 等於頻寬 × intensity；高於 ridge，受算力限制（compute-bound），每秒做到的 FLOP 等於 peak。把這條規則畫在 log-log 圖上，形狀像屋頂，所以叫 roofline（Williams、Waterman、Patterson，2009）：

圖上最左的 vector add 只到 0.4 TFLOP/s，batch 1 的 GEMV（矩陣乘向量）到 4.8 TFLOP/s，約 peak 的 0.5%。這張圖的結論是：memory-bound 的 kernel，換更快的算力沒有用，只能少搬 bytes，或讓每個 byte 多用幾次。

前情Attention、head 與 KV cache（L9）

LLM 由很多層疊起來，每一層都有一步 attention：讓每個 token 參考前面的 token。每個 token 先算出三個向量：query（Q，代表要找什麼）、key（K，代表自己有什麼）和 value（V，要交出去的內容）。新 token 的 query 和前文每個 token 的 key 逐項相乘再加總，得到分數；分數經過 softmax（取指數再除以總和）變成加起來是 1 的比例，再照比例把各個 value 加起來。

一層裡有好幾組這樣的計算同時做，每一組叫一個 head，每個 head 的向量長度是 d（Llama 3 是 128）。前文每個 token 的 K、V 之後每一步都還要用，所以存起來不重算，這份存檔就是 KV cache，存了幾個 token 就是它的長度 n。

原本每個 head 各存一份 K、V（叫 MHA，multi-head attention）。GQA（grouped-query attention）讓 g 個 head 的 query 共用一份 K、V，KV cache 小 g 倍：Llama 3 8B 有 32 個 head、存 8 份 K、V（g = 4），70B 有 64 個 head、存 8 份（g = 8）。見 L9〈GQA〉。

四種運算的 intensity：vector add、GEMV、decode attention、GEMM。Intensity 不必跑就能從輸入的大小算出來。表裡 b 是每個數字的 bytes，n 是 KV cache 存了幾個 token，d 是每個 head 的向量長度（attention、head 和 KV cache 見上面的前情）：

Ridge 的趨勢：精度越低 ridge 越大，kernel 越容易 memory-bound。精度指每個數字用幾個位元存：FP32 是 32 位元，BF16 是 16，FP8、FP4 是 8 和 4。同一顆 GPU 的 Tensor Core（專做矩陣乘法的電路，第 4 章），從 BF16 往下，精度每減半，peak 算力約加倍，頻寬不變，ridge 就加倍（FP32 不在 Tensor Core 上算，不照這個比例）。常見的說法是：新的 GPU 上，kernel 越來越容易 memory-bound。本文的判斷是，這 主要來自新一代才支援的低精度（FP8、FP4），不是來自換代本身：只看 BF16，各代的 ridge 有大有小，沒有一路變大（下面的查閱）。

低精度會不會讓 kernel 變成 memory-bound，要看哪些資料跟著變小。如果每個數字都變小，b 減半，kernel 的 intensity（上表的公式分母都有 b）和 ridge 一起加倍，相對位置不變。實際上常只有 weights 改成 FP8、FP4，每一層算出來的中間結果、KV cache 和輸出還是 BF16，bytes 沒有跟著減半，ridge 卻照低精度的算力加倍，原本 compute-bound 的 kernel 才會變成 memory-bound。

3Decode（逐 token 輸出）的瓶頸：batch 1 只用到 0.5% 的算力

現在把第 2 章的 roofline 用在 LLM 上。這一章只用到三個 model 數字：weights 多大、每個 token 多少 FLOP、每個 token 的 KV cache 多大，它們的推導是 L9 的主場：

前情Prefill、decode 與 model 的三個數字（L1、L9）

L1 講過，一個請求在 GPU 上分兩段。Prefill 一次讀完整段 prompt，決定第一個 token 多快出來（TTFT）。Decode 一次產生一個 token，重複到輸出結束，決定之後每個 token 的間隔（TPOT）。見 L1〈Prefill 與 decode〉。

Batch 1 的 decode：每個 weight 讀一次只用一次，intensity 約 1。Decode 一步要把全部 weights 從 HBM 讀一遍，每個 weight（2 bytes）只做一次 multiply-add（2 FLOPs），intensity 約 1 FLOP/B。H200 的 ridge 是 206，所以它只能跑到 4.8 TB/s × 1 ≈ 5 TFLOP/s，而 peak 是 989：batch 1 的 decode 只用到約 0.5% 的算力。

Decode 的三個槓桿：batch、降低精度、減少 KV cache 的讀取。Decode 卡在 bytes，所以能動的都是 bytes：

  • Batch。一步同時算 B 個請求，一份 weights 讀一次給 B 個 token 用，weights 的 intensity 變成約 B。怎麼排 batch 是後面的講次（batching、paging、parallelism）的主題。
  • 降低精度。Weights 從 2 bytes 變成 1 byte 或半個 byte，同樣的 FLOP 少搬一半以上的 bytes。這是 quantization，後面的講次會講。
  • 減少 KV cache 的讀取。GQA 這類架構讓每個 token 的 KV cache 變小（L9〈改 KV cache 的架構〉），KV cache 的最佳化也是後面的講次。

Batching 的效果：分攤得了 weights，分攤不了 KV cache。Weights 是所有請求共用的，KV cache 是每個請求自己的，所以 batch 對兩者的效果不同：

所以 batch 只能分攤 weights，分攤不了 KV cache：batch 加大之後，一步 decode 的時間會越來越由 KV cache 的讀取決定。

L1〈Batching〉的例子是 Llama 3 8B、每個請求的前文有 4K 個 token，batch 從 1 加到 32：weights 還是只讀一份，KV cache 卻從可以忽略變成和 weights 差不多大，一步要讀的量和時間都變成 2 倍。所以整張 GPU 每秒產出的 token 只多 16 倍，不是 32 倍。

Context 長度對 decode 的影響：KV cache 越大，每一步越慢。Context 長度是前文有幾個 token，也就是 KV cache 存的 token 數 n。例子是 Llama 3 8B、batch 16、BF16。Weights 16.1 GB 每一步讀一次，和長度無關；KV cache 每個 token 128 KiB，隨 batch × 長度成長。一步的時間約等於讀的總量 ÷ 4.8 TB/s：

換成每個請求的速度上限（本文用同一組數字算的，實際會更慢）：1K 時每秒 263 個 token，32K 時只剩 57 個，這時一步要讀的 bytes 有八成是 KV cache。所以 長 context 的 decode，速度由要讀多少 KV cache 決定：時間花在讀記憶體，不在運算。同一張 GPU 上，batch 和 context 搶的是同一個東西：每一步能讀的 bytes。

MoE 的 batching：batch 被分給各個 expert。上面的分析假設每個 token 都用同一組 weights，一般的 model 是這樣（相對於 MoE，叫 dense model）。MoE（mixture of experts，L9〈MoE〉）改的是 FFN（feed-forward network）：每一層在 attention 之後的那幾個大矩陣乘法，每個 token 各自算，占了 model 大部分的 weights。MoE 把每一層的 FFN 換成很多組，每一組叫一個 expert，每個 token 只送到其中幾組。DeepSeek-V3 每層有 256 個 expert，每個 token 用 8 個。所以一步 batch B 個 token，每個 expert 平均只分到 B × 8 ÷ 256 = B ÷ 32 個：

反過來看讀取：假設 routing 平均分配，batch 64 時每一層絕大多數的 expert 都至少分到一個 token，weights 幾乎都要讀進來，每個 expert 平均卻只算 2 個 token。要讓每個 expert 也分到約 206 個 token（碰到 ridge），一步要約 6,600 個 token。

DeepSeek 2025-02 公開的推論系統說明寫了同一個理由：每個 token 只用到很少的 expert，所以需要很大的總 batch（所有 GPU 上的請求加起來），每個 expert 才分得到足夠的 token。他們 decode 時把 expert 分到 144 張 GPU 上：每個 token 送到放著它所選 expert 的 GPU，所以一個 expert 收到的是 144 張 GPU 合起來的 token。Wang 等 2025-12 在 A100 上的量測也看得到同一個方向：decode 時把 batch 加大，dense model 的 FFN intensity 隨 batch 一路往上，MoE model 的幾乎不動。

本文的判斷：MoE 每個 token 只算幾個 expert，省下的是 FLOP；decode 的瓶頸卻在 bytes，所以 MoE 要很大的總 batch 才吃得到 batching 的好處。同時請求不多時，總 batch 小，每個 expert 分到的 token 更少，intensity 停在很低的地方。GPU 少也一樣：每張 GPU 的 batch 有上限（KV cache 要放得下，每個請求的延遲也不能太長），一個 expert 收到的是所有送 token 給它的 GPU 合起來的量，GPU 越少，湊得到的總 batch 越小。這也是 expert parallelism（把 expert 分到很多張 GPU 上，上面 DeepSeek 的做法就是一例）的動機，parallelism 是後面的講次。

4GPU 晶片的內部：SM、Tensor Core、記憶體階層

前三章只拿規格表上的數字看 GPU，主要是第 2 章三個規格裡的算力（peak）和頻寬。這一章打開晶片，看這兩個上限在什麼條件下才拿得到：peak 只屬於矩陣乘法，頻寬只屬於同時有夠多資料在路上的程式。「在路上」指已經發出讀取、還沒送到的資料，本章最後一節的 Little's law 會算要多少。

H200 的組成：132 個 SM、L2、HBM。H200 屬於 Hopper 這一代（和 H100 同一代）。132 個 SM 共用一個 L2 和六個 HBM stack，每個 SM 有自己的 registers 和 256 KB 的 SRAM（晶片上的靜態記憶體，比 HBM 快得多，也小得多）；這 256 KB 在後面放大一個 SM 的圖裡叫 L1／shared memory：

SM 的結構：四個 partition，各有一個 warp scheduler 與一個 Tensor Core。第 1 章說每個 SM 有 4 個 warp scheduler，它們各自帶著一份 register 和一組運算單元，就是四個 partition：

Tensor Core：一條指令做一小塊矩陣乘法，peak 只有矩陣乘法拿得到。LLM 的 FLOP 超過 99% 是矩陣乘法，softmax 和 normalization（把每個 token 的那串數字縮放到同一個尺度的運算）只占很小一部分。Tensor Core 是專門做 D = A × B + C 的電路，一條指令處理一整塊：

它快的原因有四個：

  • 專用的電路。乘法器和加法器直接排成整塊 tile（矩陣切出來的一小塊，例如上圖 16 × 16 的 A）的形狀。一塊的資料流過整片電路就算完，累加到一半的值不必寫回 register 再讀出來。
  • 每個 FLOP 的指令少。一條指令分攤了取指令、解碼和排程。
  • Operand 重用。A、B 的每個值在單元裡重複用了好幾次。
  • 低精度。FP16、BF16、FP8 讓 operand 變小、吞吐變大，累加時再用較高的精度。

Little's law：頻寬 = 在路上的 bytes ÷ latency，要夠多讀取同時在路上才拿得滿。HBM 的頻寬不是自動拿到的。Little's law 是排隊理論的一條定律：系統裡平均有多少東西，等於到達率乘以每件停留的時間。套到記憶體上，系統是 HBM 到 SM 的這條路，東西是 bytes：到達率是頻寬，停留時間是一次讀取的 latency，系統裡的東西就是路上的 bytes。所以路上的 bytes = 頻寬 × latency，移項就是：

管子的長度是硬體定的，能動的只有路上的 bytes。做法有三種：每個 thread 改用 16-byte 的 vector load（一次搬 4 倍）、讓每個 thread 同時發好幾個彼此獨立的 load，或用 Hopper 的 TMA 一條指令搬一整塊。每一代 GPU 的頻寬變大，要在路上的 bytes 也跟著變多，單靠 thread 一個一個發 load 越來越難做到：每個還在路上的 load，都要先在 register 裡留好放資料的位置，而每個 thread 的 register 有限。所以每一代都加了新的資料搬運硬體，讓一條指令搬更多、少占 register（下面的查閱）。這也解釋了第 1 章的規則：要有夠多的 warp，不只是為了藏延遲，也是為了讓夠多的 bytes 同時在路上。

下面每一項都在回答同一個問題：一條指令能讓多少 bytes 上路，又少占多少 register 或 shared memory。這兩件事是同一個目標：正文說過，在路上的 load 要在 register 留位置，晶片上的空間少占一點，就能多發幾個 load、放更大的 tile。

  • Coalescing。一個 warp 的 32 個 thread 讀連續的 32 個 4-byte 字，硬體合併成一個 128 B 的請求。thread i 讀 x[i] 會合併，讀 x[32·i] 不會：32 個 thread 各發一個請求，每個請求從 HBM 搬一小段卻只用到其中 4 bytes，同樣的頻寬送到的有用資料少很多。
  • 16-byte vector load。每個 thread 一次讀 16 bytes，一條 warp 指令搬 512 B，是 4-byte load 的 4 倍。
  • cp.async。Ampere 起，資料從 HBM 直接進 shared memory，不經過 register，register 留給計算。
  • TMA。Hopper 的 Tensor Memory Accelerator。一個 thread 發一條指令，硬體自己產生位址，把一整塊 tile 從 HBM 搬進 shared memory。128 × 64 個 BF16（每個 2 bytes）就是 16 KB，一條指令就有 16 KB 在路上。
  • TMA multicast。Cluster 是最多 8 個 thread block 綁成一組，各在一個 SM 上跑。它們要用同一塊 tile 時（例如矩陣乘法裡共用的那個矩陣），一條指令、一次 L2 讀取就送到這 8 個 SM，L2 的流量也變少。
  • TMEM。Blackwell 的 tensor memory，每個 SM 256 KB。矩陣乘法的結果寫進 TMEM，不占 register，register 又能多發幾個 load。
  • 2-SM MMA。Blackwell 讓兩個 SM 合算一個兩倍大的 tile。算 C = A × B 時，兩個 SM 各算 C 的一半，各自需要自己那一塊 A，卻都要用同一塊 B；合算時 B 由兩個 SM 各載入一半、互相共用，B 只搬一次，每個 SM 存 B 的空間也只要一半，省下的 shared memory 可以放更大的 tile，一次讓更多 bytes 上路。
  • Inline TMA descriptor。Rubin。TMA 搬一塊 tile 之前，要先讀一份 descriptor，記下這塊資料的位址、大小和每一列的間距。Blackwell 的 descriptor 放在記憶體裡，MoE 的每個 expert 位置不同，就要各存一份；Rubin 把 descriptor 直接放進 TMA 指令，執行時更新，省下讀 descriptor 和算位址的工作（依 Tom's Hardware 對 NVIDIA 說明的整理）。

5GPU 使用率的量測：nvidia-smi、MFU、MBU、DCGM counter、profiler

前三章估算 GPU 最快能多快，上一章再看這些上限由晶片裡的哪個單元決定。實際跑起來，GPU 用得好不好要量。最常見的錯是看 nvidia-smi 的 GPU-Util：batch 1 的 decode 只用到 0.5% 的算力，它照樣顯示 100%。這一章講該看哪些數字，以及看到之後怎麼判斷下一步。

nvidia-smi 的 GPU-Util：量的是有沒有 kernel 在跑，不是算力用了幾成。NVML（nvidia-smi 背後的函式庫）的文件把 GPU utilization 定義成：過去一段取樣時間裡，有一個以上 kernel 在執行的時間比例。只要 kernel 一個接一個，數字就是 100%，不管 kernel 用了幾個 SM、Tensor Core（上一章那個專做矩陣乘法的電路）忙不忙：

所以 拿 nvidia-smi 做容量規劃會買錯 GPU：一台算力只用到 0.5% 的 GPU，和一台用到 70% 的 GPU，都顯示 100%。它只適合回答一件事：GPU 有沒有在等 CPU。Horace He 的〈Making Deep Learning Go Brrrr〉也這樣用它：數字低，表示 kernel 之間有空檔。

MFU（model FLOPs utilization）：prefill 和訓練看算力用了幾成。MFU 是實際的 model FLOP/s ÷ peak FLOP/s。分子只算 model 本身需要的 FLOP：推論時每處理一個 token 約 2N 個（N 是參數量），prefill 讀進的和 decode 產生的 token 都算。2N 是只跑 forward（從輸入算到輸出的那一趟）的量；訓練還要反方向再算一趟（backward，約 4N），合計約 6N。分母是 Tensor Core 的 dense peak，也就是不算 sparsity 的峰值。例子是 8 張 H100 跑 Llama 2 70B，每張每秒 3,040 個 token（只示範算法）：

算法結果
每個 token 的 FLOP2 × 70B約 140 GFLOP
實際的 model FLOP/s每張 3,040 tok/s × 140 GFLOP約 426 TFLOP/s
MFU，分母用 FP8 dense peak426 ÷ 1,979約 22%
MFU，分母換成 BF16 dense peak
H100 和 H200 的 BF16 都是 989		426 ÷ 989約 43%

同一個速度，分母從 FP8 的 peak 換成 BF16 的，MFU 就從 22% 變成 43%，所以 報 MFU 要寫明分母是哪一個精度。MFU 偏低通常有四個原因：

  • 多張 GPU 之間的通訊沒有藏在計算後面。
  • 把 model 的層切給幾張 GPU 接力算（pipeline parallelism）時，一批資料剛進來和快做完時，有幾段 GPU 沒事做，這段空檔叫 bubble。
  • Memory-bound 的 kernel，例如 normalization（把每個 token 的那串數字縮放到同一個尺度的運算）、softmax。
  • 訓練時為了省記憶體重算的 FLOP（activation checkpointing），不算進分子。

MFU 把「硬體能做多少」和「軟體用了多少」分開：它量的是軟體把手上的 GPU 用到幾成，和這張 GPU 本身多快無關。所以兩套軟體跑在不同的 GPU 上時，MFU 比 tokens/s 公平：tokens/s 高，可能只是那張 GPU 比較快。在同一張 GPU 上比，兩者是同一件事。要挑哪張 GPU，還是看 tokens/s 和成本。

MBU（model bandwidth utilization）：decode 看頻寬用了幾成。MBU 是實際的 bytes/s ÷ peak 頻寬。Decode 一步要讀的 bytes 是全部 weights 加上讀到的 KV cache。例子：Llama 3 8B、BF16、batch 1、H200，每個 token 要讀 16 GB 的 weights（對話短時 KV cache 不到 weights 的 1%，先忽略）。跑到 200 tok/s 時是 16 GB × 200 = 3.2 TB/s，MBU = 3.2 ÷ 4.8 ≈ 67%。

規則是 prefill 和訓練報 MFU，decode 報 MBU：batch 小的 decode，就算 kernel 已經把頻寬用滿，MFU 還是只有幾個百分點以下，看不出還有多少進步空間。MBU 量的是真正的瓶頸，67% 表示離頻寬的上限還差三成多，這才是能改進的空間。

Serving 另外常報三個數字：延遲達標時每張 GPU 的 tokens/s（只報 tokens/s 不報延遲，數字可以靠加大 batch 灌高）、每個 token 的能耗（平均功率 ÷ tokens/s），以及每百萬 token 的成本：（每 GPU 小時的價格 ÷（tokens/s × 3,600））× 10⁶。假設每小時 3 美元、每秒 1,000 個 token，約 0.83 美元。

Counter 的讀法：依序問 GPU 忙嗎、SM 忙嗎、哪個單元在忙。nvidia-smi 的數字加上其中三個 counter（SM activity、Tensor activity、DRAM activity），可以排成三個問題。圖裡的 Nsight Systems 和 Nsight Compute 是 NVIDIA 的兩個 profiler：前者畫出整段執行的時間軸（timeline），後者分析單一 kernel，下一節再講怎麼用：

流程是：nsys 找出慢的區段，ncu 解釋其中一個 kernel，一次只改一件事，再量一次。還有一個不用工具的檢查來自 Horace He：把 batch 加倍，時間只多 10% 左右，就可能是 overhead-bound：時間花在 CPU 準備和送出 kernel（kernel launch）上，這部分每一步差不多是固定的，不隨 batch 變大，所以 batch 加倍時間也幾乎不變。這條檢查分不出另一種情況：小 batch 的 decode 卡在讀 weights，batch 加倍時要讀的 bytes 幾乎不變（第 3 章），時間也只多一點。兩者要用 nsys 的 timeline 分開：kernel 之間有大段空檔是 overhead-bound；kernel 一個接一個、DRAM activity 高，是 memory-bound。

瓶頸找到之後怎麼改，在 L10b〈Kernel Optimization〉：要不要自己寫 GPU 程式、一個 kernel 之內怎麼少搬資料、kernel 之外怎麼少空等、AI 寫的 kernel 怎麼驗收。
