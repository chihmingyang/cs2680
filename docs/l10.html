先看這裡

GPU 用幾千個簡單的核心換 throughput。GPU 上的一個函式（kernel）要跑多久，看兩件事裡較慢的一件：從記憶體搬多少 byte，要做多少次浮點運算（FLOP）。LLM 一次產生一個 token（文字的一小段），叫 decode；每一步都把 model 的參數（weights）整份讀一遍、每個只用一次，所以一次只算一個請求（batch 1）時，只用到 H200 這張 GPU 約 0.5% 的算力。這堂要帶走一個判斷順序：先算瓶頸在哪一邊，再選改法，最後用對的數字量。

  • 先算 arithmetic intensity。每搬 1 byte 做幾個 FLOP，和 GPU 的門檻 ridge（H200 約每 byte 206 個 FLOP）比。低於門檻，要少搬資料，不是加算力：加大 batch、用更少位元的數字、縮小每個請求存著的前文（KV cache）、把幾個 kernel 合成一個（fusion）。
  • Decode 的帳在 bytes。一批請求共用一份 weights，batch 越大越分攤得開；KV cache 是每個請求自己的，分攤不了，所以前文（context）越長，每產生一個 token 越慢。MoE 把每層的 weights 分成很多組（expert），每個 token 只用幾組，要更大的總 batch 才分攤得開。
  • 量對再改，也別信假的加速。監控工具 nvidia-smi 的 100% 只代表有 kernel 在跑；decode 要看頻寬用了幾成，一次讀完 prompt 的 prefill 要看算力用了幾成。AI 寫的 kernel，先確認它報的時間不低於物理下限，再用多組輸入驗證，才能相信它快。

1GPU 的設計：用幾千個簡單的核心換 throughput

L1 說過，LLM 的 decode 卡在記憶體頻寬，GPU 的運算單元大多在等資料（L1〈時間〉）。這一堂解釋為什麼，以及能怎麼辦。後面講 batching、paging、quantization（把 weights 改用更少的位元存）的幾堂，都在回答同一個硬體事實，所以先從 GPU 怎麼運作講起。讀者不需要寫過 GPU 程式，這一章從 CPU 的幾個名詞出發。

Latency 和 throughput 是兩個目標。Latency（延遲）是一件工作從開始到結束要多久，throughput（吞吐量）是單位時間做完多少件。Slides 的比喻是：跑車一次載 2 個人，到得最快；一隊巴士每台都比較慢，一次卻能載幾千人。CPU 是跑車，為 latency 設計；GPU 是巴士車隊，為整顆晶片的 throughput 設計。

先定義三個名詞。Core（核心）是執行指令的電路。Thread 是一串依序執行的指令，帶著自己的 register（暫存器，core 裡最快、最小的儲存位置）。Cache 是 core 旁邊的小記憶體，放最近用過的資料，下次就不必回到慢的主記憶體去拿。CPU 的每個 core 把大部分面積給了控制邏輯：out-of-order execution（不照順序執行，先做資料已經到的指令）和 branch prediction（先猜 if 會走哪一邊，照著做下去），再加上大的 cache，目標是讓一個 thread 跑最快。GPU 反過來，把面積給了運算單元：

怎麼藏住記憶體延遲cache 和 out-of-order execution換一組資料已經到的 thread 來跑（一組 32 個，叫 warp，下一段細講）

GPU 怎麼藏住等待：切換 warp。從 HBM（high bandwidth memory，GPU 的主記憶體）讀一筆資料約要 500 個 cycle（時脈的一拍；H200 每秒約 20 億拍，所以約 250 ns）。CPU 靠 cache 和 out-of-order 撐過這段等待，GPU 則是換一批工作來做。GPU 的 thread 以 32 個為一組，叫 warp。每個 SM 有 4 個 warp scheduler，每個最多管 16 個 warp，所以一個 SM 上同時有 64 個 warp。一個 warp 在等記憶體時，scheduler 下一個 cycle 就改發另一個 warp 的指令：

切換不花時間，因為每個 warp 的 register 一直留在 SM 上，不必像 CPU 換 thread 時把狀態存回記憶體。代價是要有足夠多的 warp 可以換：工作太少時，所有 warp 都在等，運算單元就空轉。所以 GPU 要有幾十萬個 thread 的工作才填得滿，這一條會在第 3 章的 decode 反覆出現。

SIMT：程式為一個 thread 寫，硬體一次跑 32 個。CPU 有 SIMD（single instruction, multiple data）：一條向量指令同時處理 8 或 16 個數字，但程式要明確寫成向量。GPU 的 SIMT（single instruction, multiple threads）把這件事藏起來：你寫的是一個 thread 的純量程式，硬體把 32 個 thread 綁成一個 warp，共用一次取指令、一次解碼和一次排程。每個 lane（warp 裡的一個位置）用自己的 register，所以 同一行程式在 32 個 lane 上算到 32 個不同的元素：

四個取捨。把上面合起來，GPU 放棄了四樣東西，各換到一樣（依 slides 的整理）：

  • 放棄單一 thread 的速度。時脈不高，也不先猜分支往下做，循序的程式慢很多。換到的是面積和電力都給了幾千個運算單元。
  • 放棄自動的平行。CPU 會在一個 thread 裡自己找出能同時做的指令；GPU 要你自己給它夠多的 thread，約 27 萬個才填得滿 132 個 SM，工作小的時候晶片大半閒著。換到的是延遲靠切換 warp 藏住，不靠 cache 和猜測。
  • 放棄各自的控制流程。32 個 thread 共用一條指令流，分支不同就要輪流跑（上一段的 divergence）。換到的是取一次指令、解碼一次，就能驅動 32 個 core。
  • 放棄每個 thread 的大記憶體。滿載時 registers 加 shared memory（SM 上給同一個 thread block 共用的晶片內記憶體；thread block 是程式一次交給一個 SM 的一批 thread，第 6 章講，這塊記憶體第 5 章細講），平均每個 thread 只有約 240 bytes。換到的是所有 thread 的狀態都留在晶片上，切換 warp 才不花時間。

本文的判斷：讀者最常撞到的是第二個取捨。LLM 適合 GPU，因為 model 處理的每個 token（文字切成的小段）都用同一組 weights（model 的參數）做同樣的矩陣乘法，可以大量平行。但 decode 一次只產生一個 token，每一步的工作量太小，問題有兩層：讀進來的每個 weight 只做一次乘加，運算單元多半在等 HBM 送資料；有些步驟能平行的工作也不多，填不滿 132 個 SM（第 8 章）。下一章先把前一層算成數字：每搬 1 byte 做幾個 FLOP。

2Roofline：kernel 的時間由較慢的那一邊決定

上一章說 GPU 要大量平行才填得滿。但填滿了也不一定快：資料供不上時，運算單元一樣在等。這一章給一個判斷工具，叫 roofline（屋頂線，畫成圖時形狀像屋頂）：先算一個 kernel 要搬多少 byte、要算多少 FLOP，就能估出它最快能多快，以及卡在哪一邊。之後每一種最佳化，都在移動這兩個數字的其中一個。

三個單位。估算之前，先把單位定下來：

  • FLOP。Floating-point operation，一次浮點加法或乘法。矩陣乘法裡最常見的是 multiply-add（先乘再加），算 2 個 FLOP。FLOP/s 是每秒做幾個，1 TFLOP/s 是每秒一兆個。
  • Byte。資料量。BF16（一種 16 位元的浮點格式，LLM 推論最常用）每個數字 2 bytes，FP32 每個 4 bytes。下面用 b 代表每個數字幾個 bytes。
  • Bandwidth。頻寬，每秒能從記憶體搬多少 bytes，例如 4.8 TB/s。它和 latency 是兩回事：latency 是一筆資料要等多久才到，頻寬是持續搬的時候每秒到多少。

三個規格決定每顆 GPU 的上限。Slides 用汽車比喻：算力是引擎，頻寬是油管，容量是油箱。算力限制算得多快；容量限制放得下多少 weights 和 KV cache；頻寬限制讀 weights 和 KV cache 讀得多快。HBM 是疊在 GPU 旁邊的 DRAM，就是 GPU 的主記憶體：

Arithmetic intensity 和 ridge。把公式的兩項相除，就得到判斷瓶頸的兩個數字，一個屬於 kernel，一個屬於硬體：

  • Arithmetic intensity。運算強度，等於 FLOPs ÷ 搬的 bytes：每從 HBM 搬 1 byte，做幾個 FLOP。它由 kernel 的寫法和形狀決定。
  • Ridge point。等於 peak 算力 ÷ 頻寬：每搬 1 byte 要配幾個 FLOP，運算單元才不會閒著。H200 是 989 ÷ 4.8 ≈ 206 FLOP/B。

前情Attention、head 與 KV cache（L9）

LLM 的每一層都有一步 attention：讓每個 token 參考前面的 token。每個 token 先算出三個向量：query（Q，代表要找什麼）、key（K，代表自己有什麼）和 value（V，要交出去的內容）。新 token 的 query 和前文每個 token 的 key 做內積得到分數，分數經過 softmax（取指數再除以總和，權重加起來是 1）變成權重，再用權重把各個 value 加權平均。

一層裡有好幾組這樣的計算同時做，每一組叫一個 head；d 是每個 head 的向量長度，Llama 3 是 128。前文每個 token 的 K、V 之後每一步都還要用，所以存起來不重算，這份存檔就是 KV cache，長度 n 是存了幾個 token。傳統的 MHA（multi-head attention）每個 query head 有自己的一份 K、V；GQA（grouped-query attention）讓 g 個 query head 共用一份，KV cache 小 g 倍。Llama 3 8B 是 32 個 query head 共用 8 份 K、V（g = 4），70B 是 64 個共用 8 份（g = 8）。見 L9〈改 KV cache 的架構〉。

四列的差別在 reuse：GEMM 讀進來的每個數字會用上 N 次，GEMV 的每個 weight 只用 1 次。Decode attention 也一樣：每個請求的 KV cache 只有自己的那一個 query 會讀，而且只讀一次。GQA 讓一份 K、V 給 g 個 query head 用，intensity 變成 2g ÷ b，Llama 3 70B 的 g 是 8，所以約 8（8B 是 4）。但 batch 1 時，一步要讀的 bytes 幾乎全是 weights：Llama 3 8B 的 weights 是 16 GB，1K 個 token 的 KV cache 只有約 0.13 GB。整步的 intensity 是全部的 FLOP 除以全部的 bytes，由占了 99% bytes 的 GEMV 決定，所以 decode 的 intensity 約 1，離 206 很遠。

趨勢：精度越低，ridge 越往右。同一顆 GPU，精度每減半，peak 算力約加倍，頻寬不變，ridge 就右移一倍。H200 的 FP8 ridge 是 412；B200 的 FP4 要每 byte 配 1,125 個 FLOP 才吃得滿算力，Rubin 的 FP4 要 1,591（各 GPU 各精度的 ridge 見下面的查閱）。Slides 由此下的結論是：新的 GPU 上，kernel 越來越容易 memory-bound。本文的判斷：只看 BF16，ridge 並沒有一直右移，A100 是 153、B200 是 281、Rubin 又回到 182。B200 到 Rubin，BF16 算力約 1.8 倍（2,250 → 約 4,000 TFLOP/s），頻寬約 2.75 倍（8 → 約 22 TB/s），頻寬加得比算力多，ridge 才往左回。從 A100 到 Rubin，算力 12.8 倍、頻寬 10.8 倍，兩者差不多（slides 寫頻寬約 9 倍，和同一張表的 2.04、22 TB/s 對不起來）。所以 memory-bound 變多 主要來自低精度：改用 FP8、FP4 之後，原本貼在屋頂上的 kernel 會掉到斜坡上。

3Decode：batch 1 只用到 0.5% 的算力

現在把 roofline 用在 LLM 上。這一章只用到三個 model 數字：weights 多大、每個 token 多少 FLOP、每個 token 的 KV cache 多大，它們的推導是 L9 的主場：

前情Prefill、decode 與 model 的三個數字（L1、L9）

L1 講過，一個請求在 GPU 上分兩段。Prefill 一次讀完整段 prompt，決定第一個 token 多快出來（TTFT）。Decode 一次產生一個 token，重複到輸出結束，決定之後每個 token 的間隔（TPOT）。見 L1〈Prefill 與 decode〉。

L9 從 model 的形狀算出三個數字。Weights：參數量 × 2 bytes（BF16）。計算：每個 token 約 2 × 參數量個 FLOP。KV cache：每個 token 在每一層存 K 和 V，大小是 2 × 層數 × KV head 數 × head 維度 × 2 bytes。Llama 3 8B 是 16 GB、16 GFLOP、每個 token 128 KiB；Llama 3 70B 是 141 GB、141 GFLOP、每個 token 320 KB。推導見 L9〈三個數字〉。

Batch 1：每個 weight 只用一次。Decode 一步要把全部 weights 從 HBM 讀一遍，每個 weight（2 bytes）只做一次 multiply-add（2 FLOPs），intensity 約 1 FLOP/B。H200 的 ridge 是 206，所以它只能跑到 4.8 TB/s × 1 ≈ 5 TFLOP/s。Slides 把這題當小考，選項是約 50%、約 10%、約 2%、不到 1%：答案是最後一個，batch 1 的 decode 只用到約 0.5% 的算力。Prefill 剛好相反：2,048 個 token 共用同一次讀取，intensity 約 2,048，貼在屋頂上，只有更快的算力或更少的 FLOP 才有用。

三個槓桿。Decode 卡在 bytes，所以能動的都是 bytes：

  • Batch。一步同時算 B 個請求，一份 weights 讀一次給 B 個 token 用，weights 的 intensity 變成約 B。怎麼排 batch 是下一堂（batching、paging、parallelism）的主題。
  • 降低精度。Weights 從 2 bytes 變成 1 byte 或半個 byte，同樣的 FLOP 少搬一半以上的 bytes。這是 quantization，後面的講次會講。
  • 減少 KV cache 的讀取。GQA、MLA 這類架構讓每個 token 的 KV cache 變小（L9〈改 KV cache 的架構〉），KV cache 的最佳化也是後面的講次。

Batch 拉高 weights 的 intensity，拉不動 attention。Weights 是所有請求共用的，KV cache 是每個請求自己的，所以 batch 對兩者的效果不同：

Weights 的線在 batch 約 206 時碰到 ridge，attention 的線不管 batch 多大都是平的。所以 batch 只能分攤 weights，分攤不了 KV cache：batch 加大之後，一步 decode 的時間會越來越由 KV cache 的讀取決定。L1〈Batching〉那張表裡，batch 32 時整張 GPU 只快 16 倍、不是 32 倍，原因就在這裡。

Context 越長，每一步越慢。Slides 的例子是 Llama 3 8B、batch 16、BF16。Weights 16.1 GB 每一步讀一次，和長度無關；KV cache 每個 token 128 KiB，隨 batch × 長度成長。一步的時間約等於讀的總量 ÷ 4.8 TB/s：

本文補的：MoE 會把 batch 分給各個 expert。上面的分析假設每個 token 都用同一組 weights，dense model 是這樣。MoE（mixture of experts，L9〈MoE〉）把每一層的 FFN 換成很多組，每一組叫一個 expert，每個 token 只送到其中幾組。FFN（feed-forward network）是每一層在 attention 之後的那幾個大矩陣乘法，每個 token 各自算，占了 model 大部分的 weights。DeepSeek-V3 每層有 256 個 routed expert，每個 token 用 8 個（L9 的表寫成 257 個裡用 9 個，多的那 1 個是所有 token 都用的 shared expert）。所以一步 batch B 個 token，每個 routed expert 平均只分到 B × 8 ÷ 256 = B ÷ 32 個：

反過來看讀取：假設 routing 平均分配，batch 64 時每層約 87% 的 expert 至少分到一個 token，weights 幾乎都要讀進來，每個卻只算 2 個 token。要讓每個 expert 也分到約 206 個 token，一步要約 6,600 個 token。DeepSeek 2025-02 公開的推論系統說明寫了同一個理由：model 很稀疏（每個 token 只用到 256 個 expert 裡的 8 個），需要很大的總 batch，每個 expert 才分得到足夠的 batch。他們 decode 時把 expert 分到 144 張 GPU 上（EP144），每張 GPU 放 2 個 routed expert：256 個各一份，再加 32 份負載高的 expert 的備份，共 288 個。每個 token 送到放著它所選 expert 的 GPU，所以一個 expert 收到的是 144 張 GPU 合起來的 token。Wang 等 2025-12 在 A100 上的量測也看得到同一個方向：decode 時把 batch 加大，dense 的 Qwen2.5-32B，FFN 的 intensity 一路升到 15.74 FLOP/B；MoE 的 Qwen3-30B-A3B 在他們試的幾個 batch 裡都停在約 8，因為每個 expert 只分到 batch 的一小部分（論文沒寫 15.74 是在多大的 batch 量到的）。論文的解釋也是 routing 把 batch 分散到各個 expert。

本文的判斷：MoE 省下的是 FLOP，decode 的瓶頸卻在 bytes，所以 MoE 要很大的總 batch 才吃得到 batching 的好處。同時請求不多、GPU 又少時，它的每個 expert 都停在斜坡的最底端；這也是 expert parallelism 的動機，parallelism 是後面的講次。

4量測：nvidia-smi 的 100% 只代表有 kernel 在跑

前三章是估算。實際跑起來，GPU 用得好不好要量。最常見的錯是看 nvidia-smi 的 GPU-Util：batch 1 的 decode 只用到 0.5% 的算力，它照樣顯示 100%。這一章講該看哪些數字，以及看到之後怎麼判斷下一步。

nvidia-smi 量的是「有沒有 kernel 在跑」。NVML（nvidia-smi 背後的函式庫）的文件把 GPU utilization 定義成：過去一段取樣時間裡，有一個以上 kernel 在執行的時間比例。只要 kernel 一個接一個，數字就是 100%，不管 kernel 用了幾個 SM、Tensor Core（GPU 上專做矩陣乘法的電路，第 5 章）忙不忙：

所以 拿 nvidia-smi 做容量規劃會買錯 GPU：一台 0.5% 的 GPU 和一台 70% 的 GPU 都顯示 100%。它只適合回答一件事：GPU 有沒有在等 CPU。Horace He 的〈Making Deep Learning Go Brrrr〉也這樣用它：數字低，表示 kernel 之間有空檔。

MFU：prefill 和訓練看算力用了多少。MFU（model FLOPs utilization）是實際的 model FLOP/s ÷ peak FLOP/s。分子只算 model 本身需要的 FLOP：推論時每處理一個 token 約 2N 個（N 是參數量），prefill 讀進的和 decode 產生的 token 都算。2N 是只跑 forward（從輸入算到輸出的那一趟）的量；訓練還要算 backward 求梯度，約 6N。分母是 Tensor Core 的 dense peak，也就是不算 sparsity 的峰值。Slides 的例子是 8 張 H100 跑 Llama 2 70B，每張每秒 3,040 個 token；slides 沒有說是 prefill 還是 decode、用哪種精度跑，所以這個例子只用來示範算法，不對照下面的經驗值：

  • 多張 GPU 之間的通訊沒有藏在計算後面。
  • 把 model 的層切給幾張 GPU 接力算（pipeline parallelism）時，一批資料剛進來和快做完時，有幾段 GPU 沒事做，這段空檔叫 bubble。
  • Memory-bound 的 kernel，例如 normalization（把每個 token 的那串數字縮放到同一個尺度的運算）、softmax。
  • 訓練時為了省記憶體重算的 FLOP（activation checkpointing），不算進分子。

MFU 把「硬體能做多少」和「軟體用了多少」分開：它量的是軟體把手上的 GPU 用到幾成，和這張 GPU 本身多快無關。所以比較兩套軟體、兩種設定時，MFU 比 tokens/s 公平；要挑哪張 GPU，還是看 tokens/s 和成本。

MBU：decode 看頻寬用了多少。MBU（model bandwidth utilization）是實際的 bytes/s ÷ peak 頻寬。Decode 一步要讀的 bytes 是全部 weights 加上讀到的 KV cache。例子：Llama 3 8B、BF16、batch 1、H200，每個 token 要讀 16 GB；跑到 200 tok/s 時是 16 GB × 200 = 3.2 TB/s，MBU = 3.2 ÷ 4.8 ≈ 67%。規則是 prefill 和訓練報 MFU，decode 報 MBU：batch 小的 decode，MFU 本來就低，拿它比較只會看到雜訊。

Serving 另外常報三個數字：延遲達標時每張 GPU 的 tokens/s（只報 tokens/s 不報延遲，數字可以靠加大 batch 灌高）、每個 token 的能耗（平均功率 ÷ tokens/s），以及每百萬 token 的成本：（每 GPU 小時的價格 ÷（tokens/s × 3,600））× 10⁶。假設每小時 3 美元、每秒 1,000 個 token，約 0.83 美元，這是 L8〈成本公式〉裡單價的來源。

7Kernel 之內：少搬資料，FlashAttention 是範例

GPU 最佳化的手法名字很多，slides 把它們收成四個目標，一個快的 kernel 常常四個一起用：

  1. 少搬資料。Coalescing 把一個 warp 的讀取合併成少數幾個大請求，搬進來的 bytes 都用得到；tiling 把一塊資料搬進 shared memory，給很多 thread 重複用；fusion 讓中間值留在晶片上，不寫回 HBM。三者合起來，同一份資料盡量只從 HBM 讀一次。
  2. 藏住等待。Async copy、double buffering（算這一塊時先載下一塊）、warp specialization（一些 warp 專門搬資料，另一些專門算）。
  3. 露出更多平行。Split-K 把一個長的加總切給好幾個 block 同時算，最後再加起來。在一個 thread 裡也能這樣做：用好幾個獨立的累加器輪流加，下一個加法不必等上一個的結果。
  4. 用更快的指令。改用 Tensor Core、改用低精度。

例如一個快的 GEMM 會合併 load、用兩份 buffer 輪流載 tile、交給 Tensor Core 算。四個目標裡，第一個和第 2 章的 roofline 直接相關：memory-bound 的 kernel 只能靠少搬資料變快。這一章講它最重要的兩個做法，fusion 和 FlashAttention。

這是 Flash-Decoding（2023）的做法。FlashInfer（MLSys 2025）再加上兩件事。第一，KV cache 一頁一頁散在 HBM 裡，它把「每個請求用到哪幾頁」寫成一個 block-sparse 矩陣：一列是一個請求，只有用到的頁才有值，同一個 kernel 就能處理各種存法。第二，它的排程把工作平均切給固定數量的 block，不管請求多長，每次 launch 的 grid 大小都一樣。下一節的 CUDA Graph 只能重播形狀固定的 launch，所以是第二件事讓它能放進 CUDA Graph。vLLM 和 SGLang 都用 FlashInfer。Paging 本身是下一堂的主題。

Launch 之間：CUDA Graphs、PDL 與 megakernel。Decode 一個 token 要跑幾十個小 kernel，每次 launch 都要幾微秒的 CPU 與 driver 時間，GPU 在這段時間沒事做。Kernel 越小，這段空檔占的比例越大。三種做法一步比一步徹底：

  • CUDA Graphs。把一步 decode 的所有 launch 錄一次，之後每個 token 只送一次。vLLM 和 SGLang 都這樣做，torch.compile 的 reduce-overhead 也是用它。限制是形狀和記憶體位址要固定。
  • PDL。Programmatic Dependent Launch。同一個 stream 裡，下一個 kernel 原本要等上一個完全結束才開始。PDL 讓上一個 kernel 提早通知「可以開始了」，下一個 kernel 先做自己的準備，到真正需要資料時才等待（兩個 API 是 cudaTriggerProgrammaticLaunchCompletion 和 cudaGridDependencySynchronize）。要 Hopper 以上，可以放在 CUDA Graph 裡。
  • Megakernel。整個 model 的一步只 launch 一次。Slides 引用 Hazy Research 2025 年的量測：Llama-3.2-1B 的 batch 1 decode 每一層約 7 個 kernel、共 16 層，vLLM 和 SGLang 約用到 H100 頻寬的 50%；他們的 megakernel 用到 78%，每個使用者的速度約是 SGLang 的 1.5 倍。Mirage 的 MPK（2025-12）讓 compiler 自動把整個 model 編成一個 megakernel；論文報告，端到端的推論延遲比一個 op 一個 kernel 的 serving 系統最多快 1.7 倍。

GPU 之間：把通訊藏在計算後面。Model 大到一張 GPU 放不下時，要切到多張（parallelism，後面的講次）。最常見的 tensor parallelism 把每個矩陣乘法切給 8 張 GPU，前面要一次 AllGather（每張 GPU 收齊別人的那一份），後面要一次 ReduceScatter（把結果加總再分回去）。寫成分開的 kernel 時，GEMM 要等整個通訊做完：

FLUX（2024）把通訊 fuse 進 GEMM 的 tile：一列資料到了就開始算，每個 tile 的結尾直接寫給它的擁有者那張 GPU，不另外起 kernel。論文報告 最多能藏住 96% 的通訊，8 張 GPU 上 prefill 比 vLLM 快最多 1.66 倍、decode 快 1.30 倍。MoE 有另一種通訊：每個 token 要送到別張 GPU 上的 8 個 expert，算完再收回來（all-to-all）。DeepSeek 的 DeepEP 把一個 batch 拆成兩個 micro-batch，一個在算時，另一個在傳。它有兩種 kernel：decode 用的 low-latency kernel 只走 RDMA（讓網卡直接讀寫另一台機器上 GPU 記憶體的網路傳輸），傳輸在背景由網卡完成、不占 SM；prefill 和訓練用的 normal kernel，機內走 NVLink、跨機走 RDMA。DeepEP 的 README 量的是 normal kernel，用的 GPU 是 H800：H100 為了出口限制調低 NVLink 頻寬的版本，README 寫它的 NVLink 實際上限約 160 GB/s，比第 5 章 H200 每個方向的 450 GB/s 低。量到的結果是：機內 8 張 GPU 之間，把 token 送去 expert 的 dispatch 約 153 GB/s，接近這個上限；跨機的 dispatch 約 43 GB/s，走 400 Gb/s 的 RDMA 網卡，接近上限約 50 GB/s。

本文的判斷：多數團隊選 engine，不寫這些。這一章的手法幾乎都已經在 serving engine 裡：vLLM 和 SGLang 用 FlashInfer、CUDA Graphs，DeepEP 和 DeepGEMM 也是開源的。讀者要做的決定通常是兩件：選一個做了這些的 engine，再用 Nsight Systems 的 timeline 確認 kernel 之間沒有大空檔、通訊有藏在計算後面。看到空檔，回到第 4 章的決策樹。

漏洞集中在四個地方。把五個案例的原因分類（本文的整理）：

  • 計時。停在工作做完之前，或題目小到只量到 launch。
  • 正確性。只測一組形狀、一種分布，輸出幾乎是常數。
  • Harness 的狀態。重複使用的記憶體、改掉的計時函式或參考實作。
  • Baseline。太弱，或精度不對等。

本文的判斷：驗收一個 AI 寫的 kernel，五個檢查。依上面的案例，一個 kernel 要合進 serving 的程式碼之前，至少要過這五關：

  1. 先算 speed of light。比下限還快就停，先查計時和測試。
  2. 正確性用很多組輸入。多種形狀、多種分布，每次用新的輸出 buffer；先確認輸出會隨輸入明顯變化。
  3. 計時在全部工作結束之後。同步整個 device，不只主 stream；先暖機，跑很多次；問題要大到 launch 的 overhead 不主導（KernelBench v0.1 用 1–15 ms）。
  4. 和同精度的強 baseline 比。和 torch.compile、cuBLAS 比，不只和 eager PyTorch 比。
  5. 讀 code。CUDA 真的有執行、沒有偷偷改回 torch、沒有碰 harness 的狀態。分數最高的那幾個一律人看。

第一條最便宜，卻擋得住最誇張的那一類：十倍、百倍的假加速都先違反了物理下限。後四條擋的是比較小、比較像真的假加速，所以 能自動驗證的部分越多，agent 寫的 kernel 才越能信。「動手試試」第 3 題的 harness.py 用 numpy 寫了兩個假 kernel，重現快取結果和另開 stream 計時兩種作弊，可以自己跑一次。

Llama 3 70B 的 KV cache 每個 token 320 KB（第 3 章的前情），32K 個 token 是 320 KB × 32,768 ≈ 10.7 GB。搬的時候只用一個方向，所以 NVLink 要用每個方向的 450 GB/s 算：10.7 GB ÷ 450 GB/s ≈ 24 ms。400 Gb/s 的網卡是每秒 50 GB，10.7 ÷ 50 ≈ 215 ms，差 9 倍，和 slides 標的「跨機器慢 9 倍」一致。所以需要頻繁交換資料的工作，例如 tensor parallelism，通常放在同一個 NVLink 網域裡；要跨機器的搬運，就要像第 8 章那樣藏在計算後面。怎麼切是後面 parallelism 的講次。

同一台機器，矩陣乘法每秒做的 FLOP 是 vector add 的約 180 倍，差別只在 intensity。下面四列是 batching：batch 從 1 變成 128，每秒的 FLOP 從 7.5 G 變成 132 G，每個 token 分到的時間從 18 ms 降到約 1 ms。這台 CPU 的 ridge 約是 161 GFLOP/s ÷ 13 GB/s ≈ 12 FLOP/B，所以 batch 32（16 FLOP/B）之後就接近算力的上限，增加的幅度變小。和 GPU 不同的是，b = 8 的時間就比 b = 1 多一倍：小矩陣在 OpenBLAS 裡沒有完全吃到頻寬。這是 CPU 函式庫的細節，結論不變。

harness.py：兩個看起來很快的假 kernel第 6、9 章

第 9 章的兩種作弊，用 numpy 重現。cheat_cache 依輸入的記憶體位址記住答案，同一個輸入重複計時就幾乎不花時間；cheat_async 把工作丟給背景的 worker 就返回，像把 kernel 丟到另一個 CUDA stream。兩個 harness 量同樣三個函式：naive 重複用同一個輸入、呼叫一返回就停表；strict 每次用新的輸入、等全部工作做完才停表，並且檢查每一個結果。

效能模型 The performance model

  1. 必讀Roofline: An Insightful Visual Performance Model for Multicore ArchitecturesWilliams、Waterman、Patterson · CACM 論文 · 2009 · 挑段約 25 分

    Roofline 的原始論文：效能由頻寬的斜線和算力的平頂決定，ridge 點說明一台機器多難吃滿。

    導讀論文裡 2009 年機器的 ridge 只有 0.33 到 6.7 FLOP/B。開場問：H200 的 206、Rubin FP4 的 1,591，代表今天哪些 kernel 會掉到斜坡上？

    摘要讀約 3 分；原文約 25 分

    一句話：一個 kernel 能跑多快，由兩個屋頂中較低的那個決定：頻寬乘以 operational intensity 的斜線，和峰值算力的平頂。兩者的交點叫 ridge point，說明一台機器要多高的 intensity 才吃得滿。

    跟這堂課的關係

    本頁〈Roofline：kernel 的時間由較慢的那一邊決定〉直接用這個模型；論文的 operational intensity 就是本頁的 arithmetic intensity。差別在年代：論文的四台機器 ridge 只有 0.33 到 6.7 FLOP/B，H200 的 BF16 是 206，所以今天落在斜坡上的 kernel 比 2009 年多得多。

    壓縮後的重點

    1. Intensity 量的是 DRAM 的流量。定義是每 byte DRAM 流量做幾個運算，量在 cache 和主記憶體之間，所以 cache 的效果已經算進去。
    2. 兩個屋頂取較低者。平頂是峰值算力，斜線是頻寬乘以 intensity；log-log 圖上斜線的斜率是 1。
    3. Ridge 越右，peak 越難拿到。作者把 ridge 當成「這台機器多難用滿」的指標，並提醒設計晶片的人要注意它。
    4. Ceiling 告訴你先做哪個最佳化。算力那邊是 ILP、SIMD、乘加平衡；頻寬那邊是 unit-stride 存取、memory affinity、software prefetch，由易到難排。
    5. 四台機器、四個 kernel。Xeon 6.7、Opteron X4 4.4、Cell 0.65、UltraSPARC T2+ 0.33 FLOP/B；SpMV、LBMHD、Stencil、3D FFT 的 intensity 在 0.25 到 1.64，中位數 0.60，都低於兩台 x86 的 ridge。
    6. 幾個常見的誤解。把 cache 加大，四個 kernel 裡有三個的 intensity 不會變；模型不限於浮點運算；一台機器的 roofline 只要算一次。

    原文怎麼讀

    • 可以跳過：四台機器逐一的架構說明，以及各 kernel 的實作細節。
    • 值得看原文：開頭那張基本的 roofline 圖，和加上 ceiling 之後的圖；四台機器的 ridge 對照；最後的 fallacies 一節。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 25 分。
    別誤讀

    「Roofline 告訴你 kernel 會跑多快。」它給的是上限。實際速度可能遠低於屋頂，例如本頁第 4 章那種兩個單元都不忙的 latency-bound。Intensity 也不是演算法固定的性質：同一個運算，tiling 和 fusion 會改變搬的 bytes。

  2. 必讀Making Deep Learning Go Brrrr From First PrinciplesHorace He · 部落格 · 2022 · 約 30 分

    把深度學習的時間分成 compute、memory bandwidth、overhead 三種瓶頸，各有各的解法。這一講最好讀的入門。

    導讀開場問：你最近跑的一個模型落在哪一種？用文中「batch 加倍」的測試判斷一次。

    摘要讀約 3 分；原文約 30 分

    一句話：深度學習程式的時間花在三個地方：compute、memory bandwidth、overhead。先判斷是哪一種，再選對應的改法，否則改了也沒用。

    跟這堂課的關係

    本頁〈Roofline〉的 compute-bound 和 memory-bound，這篇再加上第三種 overhead-bound。〈量測〉的 batch 加倍測試與 nvidia-smi 的讀法、〈晶片裡面〉非矩陣乘法慢很多的例子都出自這篇；它對 memory-bound 開的藥方 fusion，在〈Kernel 之內〉。

    壓縮後的重點

    1. 三種瓶頸、三種解法。Compute-bound 用 Tensor Core 或更多硬體；bandwidth-bound 用 operator fusion，加算力沒用；overhead-bound 用 tracing、fusion、避開 Python 或 JIT。
    2. 工廠的比喻。算力是工廠，頻寬是倉庫到工廠的運輸，overhead 是發指令。算力長得比頻寬快，工廠就在等材料。
    3. 非矩陣乘法占的時間遠多於 FLOP。A100 的矩陣乘法 312 TFLOPS，其他運算 19.5。BERT 裡非矩陣乘法只占 0.2% 的 FLOP，normalization 和 pointwise 的 FLOP/s 卻比矩陣乘法低 250 倍和 700 倍。
    4. Elementwise 運算幾乎都卡在頻寬。A100 每秒 1.5 TB 只搬得動約 4,000 億個 FP32 數字，同時間能做約 20 兆次運算；每個元素要上百個運算才會換成 compute-bound。
    5. Fusion 省的是記憶體來回。x.cos().cos() 分開做要 4 次全域記憶體讀寫，fuse 之後 2 次，約快 2 倍。
    6. Overhead 很大，但能藏。Python 每秒約 3,200 萬次加法；eager PyTorch 對小 tensor 每秒約 28 萬個 op。Kernel 夠大時，非同步的排隊會把它藏起來。
    7. 怎麼判斷。Batch 加倍、時間只多約 10%，是 overhead-bound；profiler 的 GPU 時間軸有空檔；達到 peak 的 80%，至少有 80% 是 compute-bound。

    原文怎麼讀

    • 可以跳過：開頭的動機和結尾的總結表，本頁第 2、4 章已經講過。
    • 值得看原文：Bandwidth 一節重複乘法的 microbenchmark 圖（到約 64 次才轉成 compute-bound）；Overhead 一節的 profiler 截圖。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 30 分。
    別誤讀

    「nvidia-smi 的 GPU-Util 很高，所以是 compute-bound。」作者只拿 GPU-Util 檢查 overhead：它量的是有 kernel 在跑的時間比例，不是算力用了多少。要判斷是不是 compute-bound，看達到的 FLOP/s 占 peak 多少。

FlashAttention FlashAttention needs your attention

  1. 必讀FlashAttention: Fast and Memory-Efficient Exact Attention with IO-AwarenessarXiv 2205.14135 · 論文 · 2022 · 挑段約 30 分

    用 tiling 和 online softmax 讓 n × n 的分數矩陣不寫回 HBM，結果精確，記憶體隨長度線性成長。

    導讀從 IO 的角度看 attention：它的 FLOP 沒變，為什麼會快好幾倍？請認領的人用本頁第 7 章的兩張圖開場。

    摘要讀約 3 分；原文約 30 分

    一句話：Attention 慢在 HBM 的讀寫，不在 FLOP。FlashAttention 用 tiling 和 online softmax 一塊一塊算，n × n 的中間矩陣不寫回 HBM；結果是精確的，記憶體隨長度線性成長。

    跟這堂課的關係

    本頁〈Kernel 之內：少搬資料，FlashAttention 是範例〉的資料流圖和 online softmax 都來自這篇；它是〈Roofline〉判斷出 memory-bound 之後「少搬 bytes」最好的例子。同一章的表接著講 FA2 到 FA4。

    壓縮後的重點

    1. 先看記憶體，再看 FLOP。A100 的 HBM 有 40–80 GB、1.5–2.0 TB/s；每個 SM 的 SRAM 只有 192 KB，108 個 SM 合計約 19 TB/s，快一個數量級，小很多。
    2. 標準 attention 把 S、P 寫進 HBM。存取次數是 Ω(Nd + N²)；FlashAttention 是 O(N²d²M⁻¹)，M 是 SRAM 的大小，在常見的 d 和 M 下最多少 9 倍。
    3. Tiling 加上 running max 與 sum。Q 切塊、K 和 V 一塊一塊讀進 SRAM，維護每列的 m 和 ℓ；合併兩塊時乘上 e^(mᵢ − m) 換算，結果是精確的 softmax。
    4. Backward 用重算換記憶體。只存輸出 O 和 (m, ℓ)，backward 時在 SRAM 重算 S 和 P；FLOP 變多，仍比從 HBM 讀快。
    5. 結果。GPT-2 的 attention 快 7.6 倍；BERT-large（長度 512）端到端快 15%；GPT-2（1K）快 3 倍；long-range arena（1K–4K）快 2.4 倍；第一個在 Path-X 與 Path-256（64K，63.1%）超過隨機猜的 Transformer。
    6. 有下限。作者證明沒有任何精確的 attention 演算法，能在所有 SRAM 大小下都漸近地更少存取 HBM。

    原文怎麼讀

    • 可以跳過：Related work；block-sparse 的變體（除非要的是近似 attention）。
    • 值得看原文：Section 3.1 的 tiling 推導和 Algorithm 1；IO complexity 的定理；Figure 1 的示意圖。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 30 分。
    別誤讀

    「FlashAttention 是一種近似的 attention，用品質換速度。」主體演算法是精確的，和標準 attention 算出相同的結果；論文裡的 block-sparse 版本才是近似。它也沒有減少 FLOP，省下的是 HBM 的讀寫。

    B200 的 Tensor Core 加倍、exp 單元沒有，瓶頸移到 softmax；這篇示範怎麼依硬體的不對稱重新設計 kernel。

    導讀從硬體不對稱的那張表開場：下一代 GPU 如果 exp 單元也加倍，瓶頸會移到哪裡？

    摘要讀約 3 分；原文約 30 分

    一句話：B200 的 Tensor Core 吞吐加倍，算 exp 的單元和 shared memory 的頻寬卻沒變，瓶頸從矩陣乘法移到 softmax。FA4 重新設計 pipeline、用 FMA 單元分擔一部分 exp、跳過不必要的 rescale，最高到 1,613 TFLOP/s，約 peak 的 71%。

    跟這堂課的關係

    本頁〈Kernel 之內〉那張 Hopper 對 Blackwell 的 cycle 圖用的就是這篇的數字，它是「晶片裡每個單元都有自己的屋頂」的例子。TMEM 和 2-CTA MMA 的背景在〈晶片裡面〉的查閱註。

    壓縮後的重點

    1. 不對稱的成長。BF16 MMA 每個 SM 每個 clock 8,192 個 FLOP，Hopper 是 4,096；MUFU 的 exp 一樣是 16 個（B300 才加倍）；shared memory 一樣每個 clock 128 bytes。
    2. 算出瓶頸。一塊 128 × 128、head 維度 128 的 forward：MMA 1,024 cycle、exp 1,024、shared memory 768，MMA 和 exp 並列最慢。
    3. 用軟體算 exp。Cody-Waite 的範圍縮減加上多項式，在 FMA 單元上和 MUFU 平行；每列只模擬 10–25%，三次多項式在 BF16 下 99% 的輸入和硬體差不到 1 ULP。
    4. 條件式 rescale。Running max 增加不到 256 倍時跳過 rescale，最後的正規化會補回；整個 warp 一起決定，避免 divergence。
    5. Pipeline 與分工。每個 CTA 輪流算兩塊 Q tile；兩組 warp 做 softmax、一組做 correction、一組驅動 Tensor Core 和 TMA；結果放在 TMEM。
    6. Backward。用 2-CTA MMA、TMEM，dQ 的 atomic 減半；deterministic 模式最高約為非 deterministic 的 75% 速度。
    7. 結果。B200、BF16、head 維度 128：最高 1,613 TFLOP/s，比 cuDNN 9.13 快 1.1–1.3 倍、比 Triton 快 2.1–2.7 倍。全部用 CuTe-DSL（Python）寫，編譯比 C++ 樣板快 20–30 倍。

    原文怎麼讀

    • 可以跳過：attention 與前幾代 FlashAttention 的背景，本頁第 7 章已經講過。
    • 值得看原文：硬體不對稱的表與 roofline 式的 cycle 分析；exp 模擬的精度表；forward pipeline 的分工圖。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 30 分。
    別誤讀

    「FA4 比 cuDNN 快，所以 B200 上一定要用 FA4。」論文自己說，新版的 cuDNN 已經吸收了許多做法，效能相近。要帶走的是瓶頸怎麼隨硬體移動，以及怎麼先算出瓶頸再設計 kernel，不是哪一個函式庫比較快。
