先看這裡

這門課前半講 agent 怎麼設計，後半講 LLM 怎麼 serve，主體是後半。把兩半接起來的是一個觀察：agent 把一次 inference 拉成一條跨過 GPU、tool 和人的鏈，所以傳統 serving 在意的數字，不再代表任務變好。這堂要帶走的是目標要從 tokens/sec 換成每個成功任務的成本，以及問題出在哪一層時怎麼看。

  • Agent 是另一種 workload。GitHub Copilot 的 production trace 裡，一個 session 中位數 15 次 LLM call，每次輸入 68K token、輸出 247 token；聊天是 1 次、750 token、105 token。延遲、狀態和失敗沿著整條鏈累積。
  • 目標要換，而且要把人算進去。Tokens/sec 高，agent 仍可能又慢又貴。要看成功率和每個成功任務的成本；同一個 batching，有人等和沒人等，答案相反。
  • 問題會跨層，底下的假設也不一樣了。Harness 怎麼組 context，決定 serving 層的 cache 能不能命中；LLM 的 workload 打破傳統系統的五個假設，Part II 就從這裡開始。

1根本的差別：一次 inference 變成一條鏈

先看一次聊天。你送出一句話，model 先一次讀完這段文字（這一步叫 prefill），接著一個 token 一個 token 地生成回答（這一步叫 decode，第 7 章細講）。Token 是 model 處理文字的最小單位，英文約 4 個字母 1 個，中文一個字常是 1 到 2 個。Model 讀進一段文字、生成下一段文字的這一次計算叫 inference。傳統的 LLM serving 處理的就是很多個這樣的請求：一個 request，一次 inference，一段 response，請求之間互不相關。

再看 coding agent 修一個 bug。Model 還是只會生成文字，但這次它生成的是一個 tool call，也就是「請執行 pytest」這樣一段請求。Model 自己碰不到檔案和 shell，真正去執行的是 model 外面那層程式，叫 harness。Harness 把執行結果接在對話後面，再整段送回 model；送進去的這一整段文字叫 context，所以 context 每一圈都變長。Model 看完結果再決定下一步，一直跑到它認為做完為止（這個 loop 的細節在 L2）。於是一次 inference 變成一條鏈：

因為每一步都等上一步，整條鏈都在 critical path 上。Critical path 是決定總時間的那條最長的相依鏈；這裡任何一段慢，整個任務就慢，而這條鏈同時跨過 GPU、CPU、storage、網路和外部服務，沒有一個元件單獨負責。

這和聊天差多少？課程只有定性的描述，2026 年才有大規模的實測。Microsoft Azure Research 分析了 GitHub Copilot 的 production trace，也就是線上真實流量的紀錄，樣本是 2026 年 6 月第一週的美國區，320 萬名使用者、1,350 萬個 session（一段對話從開始到結束）：

一個 session 有很多 turn，turn 是你打一句話、agent 跑完再回來的那一段。同一份 trace 裡，87% 的 LLM call 由 agent 自己發起，中間沒有人看著。課程列了這條鏈帶來的六個挑戰，下表把每一個對上實測的樣子；數字來自這份 trace 和 TraceLab（華盛頓大學團隊收集的 43 位開發者、4,265 個 Claude Code 與 Codex session，是他們自己的研究工作，不代表所有人）：

對照傳統的 serving，這條鏈讓每個老問題都更難：時間更不可預測，因為連步數也未知；狀態更大、活得更久，因為 context 跨過幾十步一直在；失敗點更多，因為每一步都可能碰外界。所以 agent 把 serving 的問題乘上步數，傳統 serving 在意的那些數字，也不再代表任務變好了。

2最重要的判斷：throughput 是錯的目標，要算每個成功任務的成本

Serving 系統的儀表板上通常是這幾個數字。TTFT（time to first token）是送出請求到第一個 token 出現的時間，TPOT（time per output token）是之後每個 token 的間隔，tool-call latency 是一次 tool 來回的時間，GPU utilization 是 GPU 忙的比例，throughput 是整張 GPU 每秒生成幾個 token（tokens/sec）。它們都有用，但每一個只量到鏈上的一小段，沒有一個能告訴你任務有沒有變好：

所以課程的關鍵句是 throughput 對 agent 來說是錯的目標。正確的寫法是一個帶限制的最佳化：在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。限制的意思是不能超過上限；成功率再高，等太久的設計還是不合格。

每個成功任務的成本。目標要算得出來。一個任務可能試好幾次才成功，失敗的那幾次也要付錢，所以成本要除以成功率。式子裡有三項：

  • 每次嘗試的 token 數。由 agent 繞不繞路決定。
  • 每個 token 的單價。由 model 和 serving 決定。
  • 成功率。同一種任務 100 次裡成功幾次。

把兩個版本的 agent 代進去，這裡直接用 token 數乘單價之後的花費：

版本100 次的花費成功次數每次嘗試每個成功任務
A$4050$0.40$0.80
B：更貴的設定$6090$0.60$0.67

B 每次較貴，每個成功任務反而便宜，使用者拿到結果的次數還幾乎是兩倍。只看每次請求的成本或 tokens/sec，你會選 A。要把這個數字算準，成功率得量得對，這是 L7 的主題；token 數和單價再怎麼拆，是 L8 的主題。

本文的判斷：tokens/sec 會把優化帶錯方向。它有三個盲點，每一個都會讓數字變好、agent 變差：

  • 大 batch 讓鏈上的每一步變慢。Batching 把多個請求併成一步算，整張 GPU 的 tokens/sec 升高，每個請求卻變慢（下圖）。一步生成 500 個 token、跑 40 步的 agent，batch 從 1 加到 32，生成時間從約 3.4 分鐘變成約 6.9 分鐘。
  • 繞遠路的 agent 生成更多 token。每秒 200 個、共 20,000 個 token 要 100 秒；每秒 100 個、共 5,000 個只要 50 秒。數字好看的那個慢一倍。
  • Tool 的時間和大部分的錢不在裡面。TraceLab 的 session 裡，tool 執行花的時間比 LLM 生成還多（21.2% 對 14.5%，第 3 章有圖）；依 API 定價，output token 只佔成本 11.2%，59.5% 是每一步重讀前文的 input token。

這不表示 throughput 沒有用。GPU 每秒生成的 token 多 16 倍，每個 token 的單價就低 16 倍，所以它動的是目標式裡「單價」這一項，拿來做容量規劃（要買幾張 GPU）也很合適。錯的是把它當成目標。指標一旦變成目標，團隊就會去優化它，不管它還代不代表原本的目的，這叫 Goodhart's law。所以儀表板最上面放任務層級的指標，tokens/sec 留在 serving 的分頁。第 2 段進階題第 2 題請你替一個團隊設計這組指標。

3目標少算的一項：人的時間

第 2 章的算式只算機器的錢。可是 coding agent 跑完之後，還有人要讀 diff、跑起來看、決定要不要合併。課程自己的 AI 規則就這樣寫：可以用 AI，但要揭露它幫了什麼、什麼沒成功，每份作業附 session log（agent 的完整對話紀錄），而且你要對交出去的每一行負責。責任既然還在人身上，人的時間就是成本的一部分，而課程列的限制條件（latency、cost、resources、reliability、security）裡沒有這一項。

4Stack：每一層動目標的一項，問題會跨層

目標定了，下一個問題是要動哪裡。整個系統可以畫成六層，課程從最上面的 agent 一路往下講到硬體。每一層都有人在優化，但它們動的是目標式裡不同的項：

這張圖也是這門課的範圍。Part I 的 L2–L8 講上面兩層，之後大多數的課都在 serving 這一側，從 batching、scheduling、KV cache 一路講到 GPU kernel，所以這門課的主體是 serving，agent 是它的 workload。傳統的 LLM serving 只看 model 以下三層；agent 把上面兩層接進來，問題就開始跨層，課程把這塊叫 agent serving。

這張圖的用法是：agent 太貴時，先分清是哪一項。例如一個任務用 200K token、每百萬 token $3、成功率 40%，每個成功任務 $1.50。Token 數減半、單價減半、成功率提高到 80%，三條路都能降到 $0.75，但它們在不同的層，歸不同的人管，而 throughput 只碰得到單價那一條。

問題會跨層：prefix cache。Prefix cache 把算過的中間結果存起來，下一個請求的開頭和上一個完全相同時，那一段就不必重算。Agent 每一圈都重送前面的全部，所以最依賴它。它住在 serving 層，能不能命中卻由上面的 harness 決定：

差距有多大？Claude Code 每一步的中位數是重讀 126K token、新增 857 token，沒有命中就要多算約 148 倍。Manus 2025 年的經驗文章把這個命中率稱為 production agent 最重要的單一指標：他們用的 model，命中的 input 每百萬 token $0.30，沒命中 $3，同樣的 token 差 10 倍（這是一家公司的經驗，不是對照實驗）。Copilot 的 trace 也看得到上層的行為怎麼改變命中率：一個 turn 內平均 90%，跨 turn 掉到 55%，換 model 之後只剩 8%。這筆錢怎麼算，見 L8〈Prefix cache 與單價〉。

反過來，serving 也要知道上面在做什麼。傳統的 scheduler 看到的是一堆互不相關的請求，它不知道這些請求屬於同一條鏈。Autellix（2025）讓 serving engine 認得哪些請求屬於同一個 agent，依整個 agent 已經用掉的時間排程；作者的實驗裡，同樣的 latency 下，throughput 是 vLLM（常見的開源 serving engine）的 4 到 15 倍。Copilot 那篇得到同樣的結論：優化和排程的單位，要從單一請求移到整個 session。

6五個假設：零件和傳統系統相同，workload 不同

Stack 的下半部變的是什麼？一個 AI 系統有七種會動的零件：scheduling 與 orchestration、state management、communication、caching、fault tolerance、security、observability。這張清單和一本作業系統或分散式系統教科書的目錄幾乎一樣，所以 AI 系統沒有新零件，新的是 workload。同一個 model，ML 研究者問該用哪個、怎麼設計，優化 accuracy；系統工程師問怎麼在大規模下 serve 它，優化 GPU 使用率、資源浪費、停機時間和碳排。課程說這裡是能力變成產品的地方，而且比 AI 本身更難。

7時間：prefill 和 decode 瓶頸不同，長度事先不知道

第一條假設是「一個請求花多久大致可以預測」。LLM 的請求做不到，原因要從它在 GPU 上怎麼跑講起。一個請求分兩段，瓶頸不同：

Prefill 是 model 一次讀完整段 prompt：所有 token 同時算，權重（weights，model 訓練出來的參數）每讀一次就用在幾千個 token 上，所以瓶頸在算力，GPU 的運算單元是忙的。接著是 decode：一次生成一個 token，每生成一個都要把全部權重和前面所有 token 的中間結果再讀一遍，卻只算一個 token，所以瓶頸在記憶體頻寬，運算單元大多在等資料。Decode 一直重複到 model 輸出結束 token。同樣 2,000 token 的 prompt，回答可能只有 50 token，也可能有 5,000 token，所以執行時間要等生成完才知道，scheduler 不能像排傳統的 job 那樣先估時間再排。

名詞Prefill 與 decode：怎麼判斷瓶頸在算力還是頻寬（arithmetic intensity）

判斷方法：比較每讀 1 byte 做幾次運算（arithmetic intensity），和 GPU 的算力 ÷ 頻寬。H100 的比值約 295（989 TFLOPS ÷ 3.35 TB/s）。Decode 在 batch 1 時只有約 1，遠低於 295，所以受頻寬限制；2,000 token 的 prefill 約 2,000，高於 295，所以受算力限制。Batching 就是把 decode 的比值往上推。

運算也是異質的。CPU 負責 tokenization（把文字切成 token）、發起 kernel（GPU 上跑的小程式）、搬資料和跑 tool，GPU 只負責矩陣乘法；叢集裡還常混著不同世代的 GPU，所以 routing 也要知道每張卡的差別。

Batching：整張 GPU 變快，每個請求變慢。既然 decode 卡在讀記憶體，把多個請求併成一步算，同一份權重讀一次就能分給所有請求，這是 serving 系統一定要做 batching 的原因。但每個請求的 KV cache（前面所有 token 的中間結果，下一章細講）各是一份，不能分攤。算一次，只算讀記憶體的時間，所以是速度的上限。式子裡有四項：

  • B：記憶體頻寬。假設 1.6 TB/s。

8狀態：KV cache 放哪裡，變成首要決定

傳統的 web 服務每個 session 只有幾 KB 的狀態。LLM 有兩塊大得多的狀態。第一塊是權重，從幾 GB 到幾 TB。第二塊是 KV cache：attention 要用到前面每個 token 在每一層算出的 key 與 value，model 把它們存起來，下一步直接用，不重算。第 4 章的 prefix cache，就是把這塊存起來跨請求重用。

KV cache 有多大。大小可以算。每個 token 在每一層存 key 和 value 兩份，每份有幾個 KV head，每個 head 有固定的維度，每個數字佔幾個 byte。以 32 層、8 個 KV head、head 維度 128、BF16（每個數字 2 byte）的 8B model 為例：

查閱一張 GPU 放不下時：平行化的切法與通訊零件

平行化有五種切法：

  • Data parallelism。複製整個 model，各處理不同請求。
  • Tensor parallelism。把每一層的矩陣切給多張 GPU。
  • Pipeline parallelism。把 model 按層切給多張 GPU。
  • Expert parallelism。把 MoE（mixture of experts，model 由多個專家子網路組成）的 expert 分到不同 GPU。
  • Context parallelism。把一段很長的輸入切給多張 GPU 一起算。

切得越細，GPU 之間交換的資料越多，所以 tensor parallelism 通常留在同一台機器內走 NVLink。通訊的零件有三樣：collective 函式庫（NCCL、UCCL，負責 all-reduce 這類所有 GPU 一起交換再加總的操作）；拓樸（同一台機器內走 NVLink，跨機器走 Ethernet 或 InfiniBand）；RDMA（網卡直接讀寫對方機器的記憶體，繞過 CPU 和 OS kernel）。

9不確定與故障：測試和長任務都要換寫法

傳統系統的另外兩個假設是「同樣的輸入給同樣的輸出」和「機器很少壞」。這兩條打破之後，直接改變團隊怎麼寫測試、怎麼設計長任務。

同一個 prompt，輸出為什麼不同。浮點數每做一次運算就捨入一次，所以加總的順序會改變結果。GPU 把一個矩陣乘法切成很多小塊平行算，再把部分和加起來，切法由 kernel（GPU 上跑的小程式）決定，kernel 又依 batch size 選：

差距只在第 7 位小數，但前兩名很接近時，這就夠讓最高分換人；一個 token 換了，後面的句子就全部不同。課程叫它蝴蝶效應。Temperature 是控制隨機取樣的參數，0 表示每一步都選最高分，所以 temperature 0 只固定了選法，不保證可重現。課程的結論看另一面：近似計算可以接受，FP8（8 位元浮點數）與 quantization（用較少的 bit 存權重）都是用精度換速度。延伸閱讀裡的 Thinking Machines 則示範它修得掉：改用不隨 batch size 變的 kernel 後，1,000 次輸出完全相同，代價是時間變成 1.6 到 2.1 倍，而且只在你控制 serving stack 時才做得到。

背景浮點數沒有結合律：同一個 prompt 為什麼有不同輸出

浮點數每做一次運算就捨入一次，所以 (a + b) + c 和 a + (b + c) 可能不相等。GPU 把 matmul 切成小塊平行加總，切法由 kernel 決定。Batch size 一變，kernel 可能換，加總順序跟著改變。

課程把不確定性的來源分三層：

  • Runtime。Warp 與 block 的排程、記憶體順序、非同步的 stream、batch size。
  • 軟體。Fused multiply-add 一次算完 a × b + c，只捨入一次，和分兩步算的結果不同；autotuning 依輸入形狀換 kernel；subnormal 的處理方式。
  • 硬體。CUDA core 與 tensor core 的累加方式不同；Hopper 的 FP8 和 Blackwell 的 micro-scaling tile 捨入的位置也不同。

本文的判斷：測試要分兩層。傳統的測試假設同樣的輸入得到同樣的輸出，所以可以直接比對字串。LLM 功能沒有這個保證，於是字串比對的測試時好時壞，團隊習慣「失敗就重跑」之後，真正的退步也跟著漏掉。做法是把會變和不會變的分開：

  1. p.30 · Prefill 與 decode

    Prefill 和 decode 各受什麼限制？為什麼一個請求的執行時間，事先無法預測？

    參考答案與重點複習

    答案：Prefill 受算力限制（compute-bound），decode 受記憶體頻寬限制（memory-bandwidth-bound）。執行時間取決於 model 輸出幾個 token。這個數字要等生成結束才知道，所以事先無法預測（p.30）。

    重點拆解

    一個請求分兩個階段。Prefill 一次讀進整段 prompt。每個權重從記憶體讀出來一次，就套用在 prompt 的全部 token 上。讀一次、算幾千次，所以 GPU 的運算單元很忙。

    Decode 一次只生成 1 個 token。每生成 1 個 token，就要把全部權重和這個請求的 KV cache 從記憶體再讀一遍。讀一次只算 1 個 token，運算單元大多在等資料。所以 decode 的上限是「每秒能搬多少 byte」，不是「每秒能算多少次」。

    執行時間難預測，因為 decode 要跑幾步由 model 決定：model 輸出結束 token 才停。同樣 2,000 token 的 prompt，回答可能只有 50 token，也可能有 5,000 token。所以 scheduler 很難決定先跑誰，也很難事先預留 KV cache 要用的記憶體。

    背景補充

    判斷 compute-bound 還是 memory-bound，看 arithmetic intensity：每從記憶體讀 1 byte，做幾次運算。GPU 也有自己的比值：算力 ÷ 頻寬。H100 約 989 TFLOPS ÷ 3.35 TB/s ≈ 295。Workload 的比值高於 295，瓶頸在算力；低於 295，瓶頸在頻寬。

    粗算一次。BF16 一個參數 2 byte；每個 token 對每個參數約做 2 次運算（一次乘、一次加）。Decode batch 1：讀 2 byte、做 2 次運算，比值約 1，遠低於 295。Prefill 2,000 token：同樣讀 2 byte，做 4,000 次運算，比值約 2,000，高於 295。

    Batching 把多個請求的 decode 併成一步。同一份權重讀一次，給 32 個請求用，比值就從 1 變成約 32。這是 serving 系統一定要做 batching 的原因。但每個請求的 KV cache 各是一份，不能分攤，所以 batch 不能無限加大。

    兩個階段也對應兩個使用者感受得到的指標。TTFT（time to first token）主要由 prefill 決定；TPOT（time per output token）由 decode 決定。Prompt 很長時 TTFT 變長；回答很長時總時間變長。

    常見誤解

    「GPU 使用率 100%，代表算力用滿了。」不一定。nvidia-smi 的 utilization 只代表這段時間有 kernel 在跑，不代表運算單元在忙。Decode 時 GPU 看起來很忙，運算單元大多在等記憶體。

    帶走這幾點
    1. Prefill：讀一次權重，算很多 token → 算力是瓶頸 → 影響 TTFT。
    2. Decode：每個 token 都重讀權重與 KV cache → 頻寬是瓶頸 → 影響 TPOT。
    3. 輸出長度事先未知，所以執行時間和記憶體用量都無法預估，scheduling 因此變難。

    相關：第 7 章〈時間〉和註〈Prefill 與 decode〉、第 8 章〈KV cache 有多大〉。進階題第 1 題用數字再算一次。Part II 的 serving 基礎（10/19–10/21）會正式展開。

  2. p.31 · 不確定的運算

    同一個 prompt，為什麼可能得到不同的輸出？Batch size 在這裡扮演什麼角色？

    參考答案與重點複習

    答案：浮點數加法沒有結合律，加總順序一變，結果就差一點點。Matmul 第 7 位小數的變動，就可能換掉下一個 token，後面的文字全部跟著改變；slide 稱為蝴蝶效應（p.31）。Batch size 是 slide 列出的 runtime 誤差來源：batch size 改變時，GPU 可能換 kernel 或換切法，加總順序跟著改變（p.31）。

    重點拆解

    浮點數只有固定的位數，每做一次加法就捨入一次。所以 (a + b) + c 和 a + (b + c) 可能差在最後一位。Matmul 的每個輸出都是幾千個乘積的總和。GPU 把這個總和切成小塊平行加總，再把各塊合併。切法不同，捨入的時機就不同，總和的最後幾位也不同。

    誤差本身很小，p.31 也說近似計算可以接受。麻煩在 decode 會放大它。Model 每一步替每個候選 token 打分數（logit），temperature 0 時選最高分。前兩名很接近時，最後幾位的差異就能讓它們互換。換掉一個 token 之後，後面每一步讀到的 context 都不同，整段文字就此分岔。

    Slide 把誤差來源分成三類（p.31）。Runtime：warp 與 block 的排程、記憶體順序、async stream、batch size。Software：乘加合成一個指令（FMA）或分開算、autotuning、subnormal 數。Hardware：用 CUDA core 還是 tensor core、Hopper 的 FP8 與 Blackwell 的 micro-scaling 格式。

    背景補充

    為什麼是第 7 位？FP32 的有效位數約等於 7 位十進位數字。GPU 通常用 FP32 累加 BF16 的乘積，所以第 7 位附近的差異，正好是捨入誤差的大小。

    四類來源裡，batch size 對使用者影響最大。Thinking Machines 2025 年的文章指出：同樣的輸入、同樣的 batch 重跑，GPU 的結果通常逐 bit 相同。真正的變數是伺服器負載：別人的請求多寡決定 batch size，kernel 再依矩陣形狀選切法。例如 batch 小時，kernel 把加總的維度切開，讓更多核心分工（split-K）。他們用 Qwen3-235B 在 temperature 0 跑 1,000 次，得到 80 種輸出；前 102 個 token 全部相同，第 103 個開始分岔。改用不受 batch size 影響（batch-invariant）的 kernel 後，1,000 次完全相同，代價是變慢。

    常見誤解

    「Temperature 0，輸出就固定。」Temperature 0 只固定選法：每一步選最高分。它不固定分數本身。分數由 GPU 算出，會隨 batch size 改變。要可重現，伺服器要用 batch-invariant 的 kernel；做不到時，測試的寫法就要改（進階題第 3 題）。

    帶走這幾點
    1. 浮點數每次運算都捨入 → 加總順序一變，總和的最後幾位就變。
    2. Batch size 一變 → kernel 換切法 → 加總順序改變。Batch size 由伺服器負載決定，使用者控制不了。
    3. 前兩名 logit 很接近時，一點誤差就換掉 token → 之後的 context 全部不同 → 整段輸出分岔。

    相關：第 9 章〈同一個 prompt，輸出為什麼不同〉、註〈浮點數沒有結合律〉、〈本文的判斷：測試要分兩層〉、動手試試的 fp_order.py、延伸閱讀的 Thinking Machines 文章。進階題第 3 題把這一點帶到 CI 測試上。

  3. p.32–34 · 狀態與故障

    Slide 說 AI 系統的瓶頸常在哪裡？16K 張 GPU 的叢集，多久壞一張？

    參考答案與重點複習

    答案：瓶頸常在搬資料（data movement），不在計算。原因是狀態很大：權重從幾 GB 到幾 TB，KV cache 每個 token 要幾十到幾百 KB（p.32）。16K 張 GPU 的叢集約每 3 小時壞一張（p.34）。Slide 列出每張 GPU 的年故障率（AFR）9%、MTBF 50,000 小時；叢集的故障間隔約等於 MTBF ÷ GPU 數。

    重點拆解

    先看狀態有多大。權重從幾 GB 到幾 TB；KV cache 每個 token 要幾十到幾百 KB，context 越長越大（p.32）。B1 講過，decode 每一步都要讀完權重和 KV cache。所以 GPU 的時間常花在等資料，不是在計算。

    一張 GPU 放不下時，model 要切到多張 GPU：pipeline、tensor、expert、context parallelism（p.32）。切開之後，GPU 之間每一層或每一步都要交換資料。交換靠 NCCL、UCCL 這類 collective 函式庫，走機器內的 NVLink，或機器之間的 Ethernet、InfiniBand。RDMA 讓資料直接寫進另一台機器的記憶體，不經過對方的 CPU 和 OS kernel（p.32）。Prefix cache 在請求之間重用 KV cache，省下重算；代價是這些 KV cache 要有地方放、也要搬得過去。

    故障的算法不同。一張 GPU 的 MTBF 是 50,000 小時，約 5.7 年。假設每張 GPU 獨立故障，N 張裡「任何一張」壞掉的頻率是單張的 N 倍。所以 50,000 ÷ 16,384 ≈ 3.05 小時壞一張，一天約 8 次（p.34）。改用 AFR 9% 算：8,760 小時 ÷（0.09 × 16,384）≈ 5.9 小時。兩種算法差約 2 倍，量級相同。同一頁也提到耗電：一台 server 從 800 W 升到 6,000 W。

    背景補充

    搬資料為什麼慢？離 GPU 的運算單元越遠，頻寬越小。以 H100 為例：HBM 約 3.35 TB/s，NVLink 合計約 900 GB/s，PCIe 5.0 x16 單向約 64 GB/s。用第 8 章〈KV cache 有多大〉算過的例子：100K token 的 session 約有 13 GB 的 KV cache。在 HBM 裡讀一遍約 4 ms；從 CPU 記憶體經 PCIe 搬回 GPU 約 0.2 秒。所以 KV cache 放在哪一層（p.44 第 3 題），直接變成 latency。

    每 3 小時壞一張，和 Meta 公開的 Llama 3 訓練紀錄一致：16K 張 H100，54 天內有 419 次非預期中斷，平均約 3 小時一次；約 78% 確認或疑似是硬體問題，GPU 與 HBM 記憶體佔最多。大型訓練是同步的，每一步所有 GPU 互相等，所以一張壞掉就可能要重啟整個 job。他們靠縮短 checkpoint 與重啟的時間，讓有效訓練時間維持在 90% 以上。

    常見誤解

    「MTBF 50,000 小時，代表每張 GPU 可以用 5.7 年才壞。」MTBF 是平均值，描述一大群 GPU 的故障頻率，不是每一張的壽命；單張可能第一個月就壞。叢集只看總數：16,384 張一起跑，平均每 3 小時就有一張壞。

    帶走這幾點
    1. 狀態大（權重 GB 到 TB，KV cache 每個 token 幾十到幾百 KB）→ 瓶頸在搬資料，不在計算。
    2. 叢集故障間隔 ≈ MTBF ÷ GPU 數：50,000 ÷ 16,384 ≈ 3 小時。
    3. 單張 GPU 很少壞，大叢集卻一直在壞 → 系統要把故障當常態設計：checkpoint、快速重啟。

    相關：第 8 章〈KV cache 有多大〉與〈搬資料才是瓶頸〉、註〈平行化的切法〉；第 9 章〈故障是常態〉與〈本文的判斷：單一個 run，先怕 tool，不是 GPU〉；動手試試的 fleet.py。「每張獨立故障」這個假設，見 L6 獨立假設。

  4. p.38–39 · Agent 是系統問題

    把 agent 比成電腦，harness 是什麼？Agent 的流程和傳統 serving 差在哪裡？

    參考答案與重點複習

    答案：Harness 對應 OS。其他對應：LLM 是 CPU，context window 是 RAM，tool 是周邊裝置，agent 是 application（p.38）。傳統 serving 是 request → inference → response，一個請求只跑一次 inference。Agent 是 infer → tool → infer → tool → retrieval → infer → … 的長鏈，跨過 GPU、CPU、storage、network 與外部服務；下一步要等上一步的結果，所以每一步的延遲都加進整個任務的時間（p.39）。

    重點拆解

    LLM 本身只做一件事：讀進一段文字，產生下一段文字。它不能自己讀檔或跑指令，也不記得上一步。Harness 補上其餘的工作：決定每一步的 context 放什麼，解析 model 輸出的 tool call，執行 tool，再把結果寫回 context。這就是 OS 的角色：程式透過 system call 使用硬體。

    Slide 強調這是一種新的電腦，有自己的 programming model 與 failure model（p.38）。程式用自然語言寫，同一個任務每次可能走不同路徑。LLM 出錯是常態，所以 harness 要像 OS 一樣做隔離與權限控制：先檢查 tool call，再決定要不要執行。

    第二個子問題看 p.39。傳統 serving 的請求彼此獨立，一次 inference 就結束。Agent 的每一步都依賴上一步的結果，所以整條鏈都在 critical path 上。Slide 列出這帶來的難題：步驟之間有相依、每步的延遲變化很大、等 tool 時卡住、狀態快速變大、平行與預先執行（concurrency、speculation）、軌跡上任何一步都可能失敗（p.39）。

    背景補充

    OS 類比可以再往下推。RAM 有限，OS 把不常用的 page 換到 disk。Context window 也有限，harness 要決定留什麼、壓縮什麼、存到外部檔案。L4 的 compaction 與 L6 的 memory 就在做這件事。MemGPT（2023）把這個類比做成系統：仿照 virtual memory 搬資料。

    從 serving 系統看，傳統 serving 收到的是互不相關的請求。Agent 的請求卻屬於同一個任務：開頭相同，而且一個接一個。Serving 系統不知道這層關係時，可能在 agent 等 tool 時清掉它的 KV cache，下一步只好重做 prefill。p.42 的 prefix caching 與 dependency-aware scheduling 從這裡來；p.44 第 4 題「同一個 agent 的請求怎麼排程」也是。

    常見誤解

    「Harness 只是 API 外面的一層薄 wrapper，agent 好不好全看 model。」Harness 決定 model 每一步看到什麼、能用哪些 tool、出錯時怎麼處理。同一個 model 換一個 harness，任務成功率可能差很多。所以比較 model 時要固定 harness。

    帶走這幾點
    1. LLM ≈ CPU，context window ≈ RAM，tool ≈ 周邊裝置，harness ≈ OS，agent ≈ application。
    2. Harness 像 OS：管 context、執行 tool call、做權限與隔離，因為 LLM 出錯是常態。
    3. 傳統 serving 一個請求一次 inference；agent 是一條相依的鏈 → 延遲、狀態、失敗都沿著鏈累積。

    相關：第 5 章〈Agent 這一層：一台會出錯的新電腦，harness 是它的 OS〉、第 1 章〈根本的差別：一次 inference 變成一條鏈〉；L2 一個 prompt，很多圈 loop、L2 產品差異在 harness、L4 評估時要固定 harness、L8 Critical path。進階題第 1 題會算 batching 讓一條長鏈多花多少時間。

  5. p.41 · 要優化什麼

    Slide 說哪個目標不適合 agent？要改看哪些指標？

    參考答案與重點複習

    答案：Throughput（tokens/sec）不適合當 agent 的目標：tokens/sec 高，agent 仍可能更慢、更貴（p.41）。目標是在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。TTFT、TPOT、tool-call latency、GPU 使用率「有用，但不夠」；要改看任務成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能（p.41）。

    重點拆解

    p.41 把目標寫成一個有限制的最佳化問題：要最大化的是任務成功率；latency、cost、resources、reliability、security 是限制。限制的意思是「不能超過上限」，不是「越低越好」。成功率再高，延遲超過使用者願意等的時間，這個設計仍然不合格。

    四個元件指標各量一層。下表列出每個指標漏掉什麼。

    元件指標量的是看不到
    TTFT一次請求多久出現第一個 token一個任務有幾十次請求，還有 tool 與排隊的時間
    TPOTDecode 每生成一個 token 要多久生成了幾個 token，那些 token 是否必要
    Tool-call latency一次 tool 執行多久這個 tool 該不該呼叫，總共呼叫幾次
    GPU 使用率GPU 有沒有在跑 kernel這些運算有沒有讓任務成功

    任務指標的單位是「一個任務」，不是一個請求或一個 token。所以量測時要知道哪些請求屬於同一個任務。p.43 說 agent 的 trace 是巢狀的：session → turn → agent step → model request、tool call、tool result。沒有這層結構，只看得到一堆互不相關的請求。p.43 的結論是：看不到，就無法優化。

    背景補充

    Serving 領域也走過同一條路。DistServe（OSDI 2024）提出 goodput：只計算 TTFT 與 TPOT 都達到目標（SLO）的請求。Agent 的任務指標再往上一層：看整個任務有沒有成功。

    每個成功任務的花費可以拆成三個因子（見下面的例子）。Serving 的 throughput 只動得到其中一個：每個 token 的成本。另外兩個由 agent 的行為決定：繞路越多，token 越多；失敗越多，成功率越低。

    例子

    每個成功任務的花費 =（每個任務的 token 數 × 每個 token 的成本）÷ 成功率。假設一個任務用 200K token，每百萬 token $3，成功率 40%：200K × $3 ÷ 1M = $0.60，÷ 0.4 = $1.50。三種改法都能降到 $0.75：每個 token 的成本減半；token 數減半；成功率提高到 80%。Throughput 只負責第一種。

    常見誤解

    「Tokens/sec 變高，agent 就變快。」Tokens/sec 通常指整張 GPU 的總量。看動手試試的 decode_bound.py：batch 從 1 加到 32，整張 GPU 從 97 升到 1,543 tok/s，每個請求卻從 97 降到 48 tok/s。Agent 的每一步都在 critical path 上，所以它反而變慢。

    帶走這幾點
    1. Agent 的目標：在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。Throughput 不是目標。
    2. TTFT、TPOT、tool-call latency、GPU 使用率各量一個元件 → 有用，但看不到整個任務。
    3. 改看任務指標：成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能。要算得出來，trace 要能把請求歸到同一個任務（p.43）。

    相關：第 2 章〈最重要的判斷：throughput 是錯的目標，要算每個成功任務的成本〉與〈本文的判斷：tokens/sec 會把優化帶錯方向〉、第 3 章〈目標少算的一項：人的時間〉、第 4 章〈看不到就不能優化：trace〉；L7 一個成功率不夠、L8 成本是一串乘數。進階題第 2 題請你替 coding agent 設計這組指標。

自我檢查

Prefill 和 decode，哪一個受算力限制？為什麼 decode 不能把很多 token 併成一次運算？

Prefill。Prompt 的 token 全部已知，可以平行計算，權重讀一次就用在幾千個 token 上。Decode 的第 n 個 token 要等第 n−1 個生成後才能算。

Agent A 每次嘗試花 $0.30，成功率 40%。Agent B 每次花 $0.50，成功率 80%。哪一個的每個成功任務成本較低？

B。A：$0.30 ÷ 0.4 = $0.75。B：$0.50 ÷ 0.8 = $0.625。只看每次呼叫的價格，會選錯。

為什麼 agent 比單輪的聊天更需要 prefix cache?

Agent 每一步都重送整段 context，開頭完全相同。Prefix cache 保留開頭的 KV cache，下一步只要 prefill 新增的部分。Context 越長，省得越多。

3 · 動手試試

自己算一次

三個小練習，只用 Python 標準函式庫。解答在每個練習的最後。

用 Python 看加總順序怎麼改變結果p.31

GPU 的 kernel 把加總切成小塊。下面用 float32 模擬：同一組 4,096 個數字，只改分組大小。

練習：（1）4 種分組的總和最多差多少？（2）rival 是另一個候選 token 的 logit，winner 為什麼換來換去？（3）這和 temperature 0 有什麼關係？

解答：（1）最大差約 0.000023，約是總和的 5 × 10⁻⁷。（2）兩個 logit 的差距比加總誤差還小，分組一變，大小關係就變。（3）Kernel 依 batch size 選切法，切法就是這裡的 chunk。差距小於誤差時，換一個 batch size 就可能換掉 argmax。

估算 decode 的速度上限p.30、p.32

只算讀記憶體的時間。數字和第 2 段進階題第 1 題相同。

練習：（1）ctx 4K 時，batch 從 1 加到 32，每個請求和整張 GPU 的速度各變幾倍？（2）ctx 32K、batch 32 這一列，在 96 GB 的 GPU 上跑得起來嗎？（3）把 bw 改成 3.35e12，速度怎麼變？

解答：（1）每個請求約剩一半；整張 GPU 約 16 倍。KV 讀取不能分攤，所以不是 32 倍。（2）不行：16 + 32 × 4.3 ≈ 153 GB，超過容量。（3）每一列約快 2.1 倍。只要還受頻寬限制，速度就和頻寬成正比。

算叢集多久壞一張 GPUp.34

用 slide 的數字：MTBF 50,000 小時、16,384 張 GPU。假設每張 GPU 獨立故障，間隔服從指數分布。

練習：（1）叢集多久壞一張？一天幾次？（2）MTBF 換算成 AFR 是多少？和 slide 的 9% 一致嗎？（3）一個 run 遇到 GPU 故障的風險，和每步 1% 出錯、共 60 步的風險，哪個大？

解答：（1）約 3.05 小時一次，一天約 8 次。（2）約 16%，和 9% 不一致；用 9% 算是約 5.9 小時一次，量級相同。（3）GPU 故障約 0.008%；每步 1% 出錯時，60 步全部順利只有約 55%。對單一個 run，tool 與 API 的失敗才是主要風險。

延伸閱讀

這一講沒有官方 readings 清單。slides 直接引了兩篇；課程網站（cs2680.com）另列四本背景教材，基礎不足時當查閱來源。「推薦」的 1 篇各附一段摘要：3 分鐘讀完它的主張與數字、它和 slides 重疊的部分，以及原文哪幾節值得看。

必讀推薦選讀或查閱時間是專注閱讀的估計；等級是本站的建議，不是課程要求

  1. 選讀Software Is Changing (Again)Andrej Karpathy · 演講影片 · 2025 · 約 40 分

    L1 p.37 引用的影片。把 Software 1.0／2.0／3.0 的分類接到 agent 時代。

    導讀L3 會正式指定這支影片，可以留到那時候讀。先看也可以：只看 autonomy slider 那一段。

  2. 推薦Defeating Nondeterminism in LLM InferenceThinking Machines · 部落格 · 2025 · 約 15 分

    p.31 的延伸：同一個 prompt 跑兩次，結果為什麼不同。原因在 batch size 與浮點運算順序。

    導讀對照第 9 章的註〈浮點數沒有結合律〉。問大家：這對「可重現的 eval」意味著什麼？

    摘要讀約 3 分；原文約 15 分

    一句話：temperature 0 仍得到不同輸出，主因是 kernel 缺少 batch invariance：你的請求和多少別人的請求一起算，reduction 順序就跟著變。作者改寫三個 kernel，1000 次 completion 從 80 種變成 1 種，代價是時間變成 1.6 到 2.1 倍。

    跟這堂課的關係

    第 9 章〈同一個 prompt，輸出為什麼不同〉說同一個 prompt 可能得到不同輸出，這篇是那一段的全文版。Slides p.31 把 batch size 與 warp scheduling 並列為 runtime 層的來源；這篇說 concurrency 無關，batch size 才是主因，這點和 p.31 的 takeaway「approximate computing 可以接受」方向不同：作者認為可重現做得到，也值得做。〈浮點數沒有結合律〉寫了機制，〈本文的判斷：測試要分兩層〉講團隊怎麼應對；這篇補上修法與數字。

    壓縮後的重點

    1. 常見的「concurrency + 浮點數」解釋不成立。這個說法把加總順序的變化歸給 GPU thread 的完成順序與 atomic add。作者指出 LLM 的 forward pass 通常一個 atomic add 都沒有。同一個 matmul 用同樣資料重跑，結果 bitwise 相同。
    2. 真正的原因是 kernel 不具 batch invariance。同一個請求在 batch 1 和 batch 32 裡算，kernel 換切法，reduction 順序跟著變。Batch size 由伺服器當下的負載決定，使用者看不到。所以系統整體是確定的，從單一使用者看卻是隨機的。
    3. 三個有 reduction 的 kernel 要改，原則是切法不隨 batch size 變。RMSNorm：每個 batch element 固定交給一個 core，小 batch 時寧可讓 core 閒置。Matmul：所有形狀用同一組 kernel 設定，不用 Split-K，約比 cuBLAS 慢 20%。Attention：先更新 KV cache 與 page table 再進 kernel；沿 KV 切塊時固定每塊大小（例如 256），塊數隨 KV 長度變。
    4. 數字：80 種變 1 種。Qwen3-235B-A22B-Instruct-2507，prompt 是「Tell me about Richard Feynman」，temperature 0，1000 次各 1000 token，原本有 80 種不同的 completion，最常見的出現 78 次。前 102 個 token 全部相同，第 103 個開始分歧：992 次寫 Queens, New York，8 次寫 New York City。改用 batch-invariant kernel 後，1000 次完全相同。
    5. 效能代價：時間 1.6 到 2.1 倍。單張 GPU 跑 Qwen-3-8B，1000 條序列，每條輸出 90 到 110 token。vLLM 預設 26 秒；未優化的 deterministic 版 55 秒；改良 attention kernel 後 42 秒。
    6. 副產品：真正的 on-policy RL。Sampler 與 trainer 數值不一致時，on-policy RL 會悄悄變成 off-policy。Bigmath 上的實驗：不做 importance weighting，reward 中途崩潰；做了之後 KL 約 0.001。兩端 bitwise 一致時，KL 一直是 0。

    原文怎麼讀

    • 可以跳過：「The original sin: floating-point non-associativity」一節，slides p.31 與本頁第 9 章的註已經講過。「Implementation」只說用 vLLM 的 FlexAttention backend 加 torch.Library 換 kernel。
    • 值得看原文：「Batch invariance and determinism」一節，解釋每個 kernel 都確定、endpoint 仍不確定的原因。「Batch-invariant attention」的 fixed split size 圖：KV 長度 1000 切成 256、256、256、232。「True on-policy RL」的三條 KL 曲線。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 15 分。
    別誤讀

    「浮點數不可結合，所以 GPU 上的 LLM 本來就不可能可重現。」作者反對這種放棄。單一 kernel 重跑的結果 bitwise 相同；會變的只有 batch size 帶來的 reduction 順序，固定它就可重現。但這只在你控制 serving stack 時成立；第三方 API 的 batch 你管不到。
