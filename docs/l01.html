先看這裡

這堂前半講課務，後半畫出整門課的地圖。它回答兩個問題：AI 系統和傳統系統差在哪裡，以及 agent 為什麼是一個系統問題。結論是：agent 的目標是任務成功，tokens/sec 只是手段。

  • AI workload 打破傳統系統的假設。Decode 受記憶體頻寬限制；同一個 prompt 可能得到不同輸出；大叢集每幾小時壞一張 GPU。
  • Agent 把一次 inference 拉成一條鏈。infer → tool → infer …，每一步都等上一步。延遲、狀態和失敗沿著整條鏈累積。
  • 優化目標要換。Tokens/sec 高，agent 仍可能又慢又貴。要看任務成功率，和每個成功任務的成本。

建議順序：先讀第 5 段的基礎題，帶著問題自己一頁一頁看完 slides；再回來讀這篇。讀書會前用第 5 段的進階題。

1 · 架構

整門課的零件怎麼接在一起

兩張圖一起看。第一張是空間：系統分 6 層，課程從上往下講。第二張是時間：agent 把一次 inference 拉成一條鏈，每一步都在 critical path 上。這堂的主張落在交點：下層為 throughput 做的優化，放到上層的鏈上不一定划算。

2 · 核心觀念

四個觀念串起整堂課

AI 系統優化的東西，和 AI/ML 不同 p.28–29

同一個 model，兩種人問不同的問題。ML 研究者問：該用哪個 model，它答對幾題？系統工程師問：怎麼在上千張 GPU 上穩定地訓練與 serve？前者優化 accuracy，後者優化 GPU 使用率、資源浪費、停機時間與碳排。

系統這一側的零件和傳統系統一樣：scheduling、狀態管理、通訊、caching、fault tolerance。差別在 workload 的性質。p.29：把 model 的能力變成產品，比 AI 本身更難。

AI workload 打破傳統系統的五個假設 p.30–34

傳統服務隱含幾個假設：處理時間可以預測、同樣的輸入得到同樣的輸出、狀態小、故障少見。LLM 的 workload 打破每一條。一個請求分兩個階段：prefill 受算力限制，decode 受記憶體頻寬限制。執行時間取決於輸出多少 token，事先無法得知。

浮點數的加總順序會改變結果，所以同一個 prompt 可能得到不同輸出。狀態很大：權重從幾 GB 到幾 TB，KV cache 每個 token 要幾十到幾百 KB，瓶頸常在搬資料。Model 與 workload 變化快。故障是常態：16K 張 GPU 約每 3 小時壞一張；一台 server 從 800 W 升到 6,000 W。

Agent 是一種新的電腦，也是一個系統問題 p.36–43

Slide 把 agent 看成一台新的電腦：LLM 是 CPU，context window 是 RAM，tool 是周邊裝置，harness 是 OS，agent 是 application。兩個不同點：程式用自然語言寫，每次可能走不同路徑；LLM 出錯是常態，所以 harness 要像 OS 一樣做隔離與權限控制。

傳統 serving 是 request → inference → response。Agent 把它拉成 infer → tool → infer → retrieval → … 的鏈，跨過 GPU、CPU、storage、network 與外部服務。每一步都等上一步，所以整條鏈都在 critical path 上。Tool 執行時 agent 用不到 GPU，它的 KV cache 卻還佔著記憶體。這帶出 p.42 的新問題：狀態管理、prefix caching、checkpoint。要優化先要看得到，所以 observability 是一等問題（p.43）。

目標：在限制下讓任務成功 p.41–44

Throughput 不適合當 agent 的目標。目標是在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。TTFT、TPOT、GPU 使用率都有用，但各自只量一個元件。要看任務層級：成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能。

例：A 跑 100 次花 $40，成功 50 次，每個成功任務 $0.80。B 花 $60，成功 90 次，約 $0.67。B 每次較貴，換算後反而便宜。p.44 用 9 個問題收尾，要求你能用數字回答。第 5 段的討論題從這裡出發。

3 · 觀念補充

Slide 預設你已經懂的背景

Prefill 與 decode同一個請求的兩種瓶頸

Prefill 一次處理整段 prompt，每個權重讀一次就用在幾千個 token 上，瓶頸在算力。Decode 一次只生成 1 個 token，每一步都要讀完全部權重和 KV cache，瓶頸在記憶體頻寬。

判斷方法：比較每讀 1 byte 做幾次運算（arithmetic intensity），和 GPU 的算力 ÷ 頻寬。H100 的比值約 295（989 TFLOPS ÷ 3.35 TB/s）。Decode 在 batch 1 時只有約 1；batching 就是把它往上推 p.30。

浮點數沒有結合律同一個 prompt 為什麼有不同輸出

浮點數每做一次運算就捨入一次，所以 (a + b) + c 和 a + (b + c) 可能不相等。GPU 把 matmul 切成小塊平行加總，切法由 kernel 決定。Batch size 一變，kernel 可能換，加總順序跟著改變。

Model 每一步替每個候選 token 打分數（logit），greedy decoding 選最高分。前兩名很接近時，捨入誤差就能讓它們互換。所以 temperature 0 只固定了選法，不保證輸出可重現 p.31。

KV cacheagent 的狀態為什麼這麼大

Attention 讓每個新 token 參考前面所有的 token。Model 把每個 token 在每一層的 key 和 value 存起來重用，這就是 KV cache。每個 token 的大小 = 2 × 層數 × KV head 數 × head 維度 × byte 數。

以 32 層、8 個 KV head、head 維度 128、BF16 的 8B model 為例，每個 token 要 128 KiB。100K token 的 session 約 13 GB，接近權重的 16 GB。Prefix cache 保留共同開頭的 KV cache 給下一個請求重用 p.32。

MTBF 與叢集故障大叢集為什麼一直在壞

MTBF 是單一元件平均多久故障一次。假設每張 GPU 獨立故障，N 張的叢集平均每 MTBF ÷ N 就壞一張：50,000 小時 ÷ 16,384 張 ≈ 3 小時 p.34。年故障率 9% 換算是約每 6 小時一張，量級相同。

平行化的切法一張 GPU 放不下時

Data parallelism 複製整個 model，各處理不同請求。Tensor parallelism 把每一層的矩陣切給多張 GPU；pipeline parallelism 按層切；expert parallelism 把 MoE 的 expert 分到不同 GPU。切得越細，GPU 之間交換的資料越多，所以 tensor parallelism 通常留在同一台機器內走 NVLink p.32。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

Tokens/sec 會把 agent 的優化帶錯方向

Tokens/sec 是 serving 層的指標，適合做容量規劃。拿來評估 agent 有三個盲點：大 batch 讓 critical path 上的每一步變慢；繞遠路的 agent 生成更多 token，數字反而好看；tool 的時間不在裡面。

指標一旦變成目標，團隊就會去優化它，不管它還代不代表原本的目的（Goodhart's law）。所以儀表板最上面放任務層級的指標，tokens/sec 留在 serving 的分頁。第 5 段第 3 題請你設計這組指標。

不確定性改變團隊測試 LLM 功能的方式

傳統測試假設同樣的輸入得到同樣的輸出，所以可以比對字串。LLM 功能沒有這個保證，temperature 0 也沒有。字串比對的測試會時好時壞；團隊習慣直接重跑之後，真正的退步也跟著漏掉。

做法分兩層。Harness 的程式碼是確定性的：錄下 model 的回覆（record / replay），用一般的 unit test 測。Model 的行為用 eval 測：同一題跑多次，檢查性質，看通過率。L7 的 pass^k 是同一個想法。

長時間的 agent run 需要可靠性工程

對單一個 run，GPU 故障很少見：30 分鐘的 run 跑在 8 張 GPU 上，遇到故障的機率約 0.008%。但一天跑 10 萬個這種 run，就有約 8 個會遇到。Tool 逾時、API 錯誤更常見：每步 1% 出錯時，60 步全部順利的機率只有約 55%。

所以長的 run 要用分散式系統的老方法：每一步存 checkpoint，有副作用的 tool 要冪等（idempotent），重試要有上限。L4 的「tool 預設冪等」和 L6 的「checkpoint 與回滾」處理同一個問題。第 5 段第 5 題請你設計一套復原機制。

9 個問題裡，Part II 負責 stack 的下半部

p.44 的 9 個問題，Part I 已經碰到幾個：L3 與 L5 談什麼時候開 subagent；L8 談每個成功任務的成本。剩下的多半在 stack 的下半部。依課表推測：batching 的取捨在 10/19–10/21；KV 狀態與排程在 11/02；routing 在 11/23。讀 Part II 時，拿 p.44 當檢查表，每堂回答一題。

  1. p.30 · Prefill 與 decode

    Prefill 和 decode 各受什麼限制？為什麼一個請求的執行時間，事先無法預測？

    參考答案與重點複習

    答案：Prefill 受算力限制（compute-bound），decode 受記憶體頻寬限制（memory-bandwidth-bound）。執行時間取決於 model 輸出幾個 token。這個數字要等生成結束才知道，所以事先無法預測（p.30）。

    重點拆解

    一個請求分兩個階段。Prefill 一次讀進整段 prompt。每個權重從記憶體讀出來一次，就套用在 prompt 的全部 token 上。讀一次、算幾千次，所以 GPU 的運算單元很忙。

    Decode 一次只生成 1 個 token。每生成 1 個 token，就要把全部權重和這個請求的 KV cache 從記憶體再讀一遍。讀一次只算 1 個 token，運算單元大多在等資料。所以 decode 的上限是「每秒能搬多少 byte」，不是「每秒能算多少次」。

    執行時間難預測，因為 decode 要跑幾步由 model 決定：model 輸出結束 token 才停。同樣 2,000 token 的 prompt，回答可能只有 50 token，也可能有 5,000 token。所以 scheduler 很難決定先跑誰，也很難事先預留 KV cache 要用的記憶體。

    背景補充

    判斷 compute-bound 還是 memory-bound，看 arithmetic intensity：每從記憶體讀 1 byte，做幾次運算。GPU 也有自己的比值：算力 ÷ 頻寬。H100 約 989 TFLOPS ÷ 3.35 TB/s ≈ 295。Workload 的比值高於 295，瓶頸在算力；低於 295，瓶頸在頻寬。

    粗算一次。BF16 一個參數 2 byte；每個 token 對每個參數約做 2 次運算（一次乘、一次加）。Decode batch 1：讀 2 byte、做 2 次運算，比值約 1，遠低於 295。Prefill 2,000 token：同樣讀 2 byte，做 4,000 次運算，比值約 2,000，高於 295。

    Batching 把多個請求的 decode 併成一步。同一份權重讀一次，給 32 個請求用，比值就從 1 變成約 32。這是 serving 系統一定要做 batching 的原因。但每個請求的 KV cache 各是一份，不能分攤，所以 batch 不能無限加大。

    兩個階段也對應兩個使用者感受得到的指標。TTFT（time to first token）主要由 prefill 決定；TPOT（time per output token）由 decode 決定。Prompt 很長時 TTFT 變長；回答很長時總時間變長。

    常見誤解

    「GPU 使用率 100%，代表算力用滿了。」不一定。nvidia-smi 的 utilization 只代表這段時間有 kernel 在跑，不代表運算單元在忙。Decode 時 GPU 看起來很忙，運算單元其實大多在等記憶體。

    帶走這幾點
    1. Prefill：讀一次權重，算很多 token → 算力是瓶頸 → 影響 TTFT。
    2. Decode：每個 token 都重讀權重與 KV cache → 頻寬是瓶頸 → 影響 TPOT。
    3. 輸出長度事先未知，所以執行時間和記憶體用量都無法預估，scheduling 因此變難。

    相關：觀念補充〈Prefill 與 decode〉、〈KV cache〉。進階題第 1、2 題用數字再算一次。Part II 的 serving 基礎（10/19–10/21）會正式展開。

  2. p.31 · 不確定的運算

    同一個 prompt，為什麼可能得到不同的輸出？Batch size 在這裡扮演什麼角色？

    參考答案與重點複習

    答案：浮點數加法沒有結合律，加總順序一變，結果就差一點點。Matmul 第 7 位小數的變動，就可能換掉下一個 token，後面的文字全部跟著改變；slide 稱為蝴蝶效應（p.31）。Batch size 是 slide 列出的 runtime 誤差來源：batch size 改變時，GPU 可能換 kernel 或換切法，加總順序跟著改變（p.31）。

    重點拆解

    浮點數只有固定的位數，每做一次加法就捨入一次。所以 (a + b) + c 和 a + (b + c) 可能差在最後一位。Matmul 的每個輸出都是幾千個乘積的總和。GPU 把這個總和切成小塊平行加總，再把各塊合併。切法不同，捨入的時機就不同，總和的最後幾位也不同。

    誤差本身很小，p.31 也說近似計算可以接受。麻煩在 decode 會放大它。Model 每一步替每個候選 token 打分數（logit），temperature 0 時選最高分。前兩名很接近時，最後幾位的差異就能讓它們互換。換掉一個 token 之後，後面每一步讀到的 context 都不同，整段文字就此分岔。

    Slide 把誤差來源分成三類（p.31）。Runtime：warp 與 block 的排程、記憶體順序、async stream、batch size。Software：乘加合成一個指令（FMA）或分開算、autotuning、subnormal 數。Hardware：用 CUDA core 還是 tensor core、Hopper 的 FP8 與 Blackwell 的 micro-scaling 格式。

    背景補充

    為什麼是第 7 位？FP32 的有效位數約等於 7 位十進位數字。GPU 通常用 FP32 累加 BF16 的乘積，所以第 7 位附近的差異，正好是捨入誤差的大小。

    四類來源裡，batch size 對使用者影響最大。Thinking Machines 2025 年的文章指出：同樣的輸入、同樣的 batch 重跑，GPU 的結果通常逐 bit 相同。真正的變數是伺服器負載：別人的請求多寡決定 batch size，kernel 再依矩陣形狀選切法。例如 batch 小時，kernel 把加總的維度切開，讓更多核心分工（split-K）。他們用 Qwen3-235B 在 temperature 0 跑 1,000 次，得到 80 種輸出；前 102 個 token 全部相同，第 103 個開始分岔。改用不受 batch size 影響（batch-invariant）的 kernel 後，1,000 次完全相同，代價是變慢。

    常見誤解

    「Temperature 0，輸出就固定。」Temperature 0 只固定選法：每一步選最高分。它不固定分數本身。分數由 GPU 算出，會隨 batch size 改變。要可重現，伺服器要用 batch-invariant 的 kernel；做不到時，測試的寫法就要改（進階題第 4 題）。

    帶走這幾點
    1. 浮點數每次運算都捨入 → 加總順序一變，總和的最後幾位就變。
    2. Batch size 一變 → kernel 換切法 → 加總順序改變。Batch size 由伺服器負載決定，使用者控制不了。
    3. 前兩名 logit 很接近時，一點誤差就換掉 token → 之後的 context 全部不同 → 整段輸出分岔。

    相關：觀念補充〈浮點數沒有結合律〉、延伸思考〈不確定性改變團隊測試 LLM 功能的方式〉、動手試試的 fp_order.py、延伸閱讀的 Thinking Machines 文章。進階題第 4 題把這一點帶到 CI 測試上。

  3. p.32–34 · 狀態與故障

    Slide 說 AI 系統的瓶頸常在哪裡？16K 張 GPU 的叢集，多久壞一張？

    參考答案與重點複習

    答案：瓶頸常在搬資料（data movement），不在計算。原因是狀態很大：權重從幾 GB 到幾 TB，KV cache 每個 token 要幾十到幾百 KB（p.32）。16K 張 GPU 的叢集約每 3 小時壞一張（p.34）。Slide 列出每張 GPU 的年故障率（AFR）9%、MTBF 50,000 小時；叢集的故障間隔約等於 MTBF ÷ GPU 數。

    重點拆解

    先看狀態有多大。權重從幾 GB 到幾 TB；KV cache 每個 token 要幾十到幾百 KB，context 越長越大（p.32）。B1 講過，decode 每一步都要讀完權重和 KV cache。所以 GPU 的時間常花在等資料，不是在計算。

    一張 GPU 放不下時，model 要切到多張 GPU：pipeline、tensor、expert、context parallelism（p.32）。切開之後，GPU 之間每一層或每一步都要交換資料。交換靠 NCCL、UCCL 這類 collective 函式庫，走機器內的 NVLink，或機器之間的 Ethernet、InfiniBand。RDMA 讓資料直接寫進另一台機器的記憶體，不經過對方的 CPU 和 OS kernel（p.32）。Prefix cache 在請求之間重用 KV cache，省下重算；代價是這些 KV cache 要有地方放、也要搬得過去。

    故障的算法不同。一張 GPU 的 MTBF 是 50,000 小時，約 5.7 年。假設每張 GPU 獨立故障，N 張裡「任何一張」壞掉的頻率是單張的 N 倍。所以 50,000 ÷ 16,384 ≈ 3.05 小時壞一張，一天約 8 次（p.34）。改用 AFR 9% 算：8,760 小時 ÷（0.09 × 16,384）≈ 5.9 小時。兩種算法差約 2 倍，量級相同。同一頁也提到耗電：一台 server 從 800 W 升到 6,000 W。

    背景補充

    搬資料為什麼慢？離 GPU 的運算單元越遠，頻寬越小。以 H100 為例：HBM 約 3.35 TB/s，NVLink 合計約 900 GB/s，PCIe 5.0 x16 單向約 64 GB/s。用〈KV cache〉的例子：100K token 的 session 約有 13 GB 的 KV cache。在 HBM 裡讀一遍約 4 ms；從 CPU 記憶體經 PCIe 搬回 GPU 約 0.2 秒。所以 KV cache 放在哪一層（p.44 第 3 題），直接變成 latency。

    每 3 小時壞一張，和 Meta 公開的 Llama 3 訓練紀錄一致：16K 張 H100，54 天內有 419 次非預期中斷，平均約 3 小時一次；約 78% 確認或疑似是硬體問題，GPU 與 HBM 記憶體佔最多。大型訓練是同步的，每一步所有 GPU 互相等，所以一張壞掉就可能要重啟整個 job。他們靠縮短 checkpoint 與重啟的時間，讓有效訓練時間維持在 90% 以上。

    常見誤解

    「MTBF 50,000 小時，代表每張 GPU 可以用 5.7 年才壞。」MTBF 是平均值，描述一大群 GPU 的故障頻率，不是每一張的壽命；單張可能第一個月就壞。叢集只看總數：16,384 張一起跑，平均每 3 小時就有一張壞。

    帶走這幾點
    1. 狀態大（權重 GB 到 TB，KV cache 每個 token 幾十到幾百 KB）→ 瓶頸在搬資料，不在計算。
    2. 叢集故障間隔 ≈ MTBF ÷ GPU 數：50,000 ÷ 16,384 ≈ 3 小時。
    3. 單張 GPU 很少壞，大叢集卻一直在壞 → 系統要把故障當常態設計：checkpoint、快速重啟。

    相關：觀念補充〈KV cache〉、〈MTBF 與叢集故障〉、〈平行化的切法〉；延伸思考〈長時間的 agent run 需要可靠性工程〉；動手試試的 fleet.py。「每張獨立故障」這個假設，見 L6 獨立假設。進階題第 5 題把故障帶到 agent run 的復原設計。

  4. p.38–39 · Agent 是系統問題

    把 agent 比成電腦，harness 是什麼？Agent 的流程和傳統 serving 差在哪裡？

    參考答案與重點複習

    答案：Harness 對應 OS。其他對應：LLM 是 CPU，context window 是 RAM，tool 是周邊裝置，agent 是 application（p.38）。傳統 serving 是 request → inference → response，一個請求只跑一次 inference。Agent 是 infer → tool → infer → tool → retrieval → infer → … 的長鏈，跨過 GPU、CPU、storage、network 與外部服務；下一步要等上一步的結果，所以每一步的延遲都加進整個任務的時間（p.39）。

    重點拆解

    LLM 本身只做一件事：讀進一段文字，產生下一段文字。它不能自己讀檔或跑指令，也不記得上一步。Harness 補上其餘的工作：決定每一步的 context 放什麼，解析 model 輸出的 tool call，執行 tool，再把結果寫回 context。這就是 OS 的角色：程式透過 system call 使用硬體。

    Slide 強調這是一種新的電腦，有自己的 programming model 與 failure model（p.38）。程式用自然語言寫，同一個任務每次可能走不同路徑。LLM 出錯是常態，所以 harness 要像 OS 一樣做隔離與權限控制：先檢查 tool call，再決定要不要執行。

    第二個子問題看 p.39。傳統 serving 的請求彼此獨立，一次 inference 就結束。Agent 的每一步都依賴上一步的結果，所以整條鏈都在 critical path 上。Slide 列出這帶來的難題：步驟之間有相依、每步的延遲變化很大、等 tool 時卡住、狀態快速變大、平行與預先執行（concurrency、speculation）、軌跡上任何一步都可能失敗（p.39）。

    背景補充

    OS 類比可以再往下推。RAM 有限，OS 把不常用的 page 換到 disk。Context window 也有限，harness 要決定留什麼、壓縮什麼、存到外部檔案。L4 的 compaction 與 L6 的 memory 就在做這件事。MemGPT（2023）把這個類比做成系統：仿照 virtual memory 搬資料。

    從 serving 系統看，傳統 serving 收到的是互不相關的請求。Agent 的請求其實屬於同一個任務：開頭相同，而且一個接一個。Serving 系統不知道這層關係時，可能在 agent 等 tool 時清掉它的 KV cache，下一步只好重做 prefill。p.42 的 prefix caching 與 dependency-aware scheduling 從這裡來；p.44 第 4 題「同一個 agent 的請求怎麼排程」也是。

    常見誤解

    「Harness 只是 API 外面的一層薄 wrapper，agent 好不好全看 model。」Harness 決定 model 每一步看到什麼、能用哪些 tool、出錯時怎麼處理。同一個 model 換一個 harness，任務成功率可能差很多。所以比較 model 時要固定 harness。

    帶走這幾點
    1. LLM ≈ CPU，context window ≈ RAM，tool ≈ 周邊裝置，harness ≈ OS，agent ≈ application。
    2. Harness 像 OS：管 context、執行 tool call、做權限與隔離，因為 LLM 出錯是常態。
    3. 傳統 serving 一個請求一次 inference；agent 是一條相依的鏈 → 延遲、狀態、失敗都沿著鏈累積。

    相關：核心觀念〈Agent 是一種新的電腦，也是一個系統問題〉、第 1 段的第二張圖；L2 一個 prompt，很多圈 loop、L2 產品差異在 harness、L4 評估時要固定 harness、L8 Critical path。進階題第 2 題會算 batching 讓一條長鏈多花多少時間。

  5. p.41 · 要優化什麼

    Slide 說哪個目標不適合 agent？要改看哪些指標？

    參考答案與重點複習

    答案：Throughput（tokens/sec）不適合當 agent 的目標：tokens/sec 高，agent 仍可能更慢、更貴（p.41）。目標是在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。TTFT、TPOT、tool-call latency、GPU 使用率「有用，但不夠」；要改看任務成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能（p.41）。

    重點拆解

    p.41 把目標寫成一個有限制的最佳化問題：要最大化的是任務成功率；latency、cost、resources、reliability、security 是限制。限制的意思是「不能超過上限」，不是「越低越好」。成功率再高，延遲超過使用者願意等的時間，這個設計仍然不合格。

    四個元件指標各量一層。下表列出每個指標漏掉什麼。

    元件指標量的是看不到
    TTFT一次請求多久出現第一個 token一個任務有幾十次請求，還有 tool 與排隊的時間
    TPOTDecode 每生成一個 token 要多久生成了幾個 token，那些 token 是否必要
    Tool-call latency一次 tool 執行多久這個 tool 該不該呼叫，總共呼叫幾次
    GPU 使用率GPU 有沒有在跑 kernel這些運算有沒有讓任務成功

    任務指標的單位是「一個任務」，不是一個請求或一個 token。所以量測時要知道哪些請求屬於同一個任務。p.43 說 agent 的 trace 是巢狀的：session → turn → agent step → model request、tool call、tool result。沒有這層結構，只看得到一堆互不相關的請求。p.43 的結論是：看不到，就無法優化。

    背景補充

    Serving 領域也走過同一條路。DistServe（OSDI 2024）提出 goodput：只計算 TTFT 與 TPOT 都達到目標（SLO）的請求。Agent 的任務指標再往上一層：看整個任務有沒有成功。

    每個成功任務的花費可以拆成三個因子（見下面的例子）。Serving 的 throughput 只動得到其中一個：每個 token 的成本。另外兩個由 agent 的行為決定：繞路越多，token 越多；失敗越多，成功率越低。

    例子

    每個成功任務的花費 =（每個任務的 token 數 × 每個 token 的成本）÷ 成功率。假設一個任務用 200K token，每百萬 token $3，成功率 40%：200K × $3 ÷ 1M = $0.60，÷ 0.4 = $1.50。三種改法都能降到 $0.75：每個 token 的成本減半；token 數減半；成功率提高到 80%。Throughput 只負責第一種。

    常見誤解

    「Tokens/sec 變高，agent 就變快。」Tokens/sec 通常指整張 GPU 的總量。看動手試試的 decode_bound.py：batch 從 1 加到 32，整張 GPU 從 97 升到 1,543 tok/s，每個請求卻從 97 降到 48 tok/s。Agent 的每一步都在 critical path 上，所以它反而變慢。

    帶走這幾點
    1. Agent 的目標：在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。Throughput 不是目標。
    2. TTFT、TPOT、tool-call latency、GPU 使用率各量一個元件 → 有用，但看不到整個任務。
    3. 改看任務指標：成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能。要算得出來，trace 要能把請求歸到同一個任務（p.43）。

    相關：核心觀念〈目標：在限制下讓任務成功〉、延伸思考〈Tokens/sec 會把 agent 的優化帶錯方向〉；L7 一個成功率不夠、L8 成本是一串乘數。進階題第 3 題請你替 coding agent 設計這組指標；第 6 題用 p.44 第 9 題練習量測。

  1. 概念 · Decode 與 batching · p.30

    為什麼 decode 受記憶體頻寬限制，prefill 卻受算力限制？Batching 改變了哪一部分，哪一部分沒變？

    情境：一個 8B 參數的 model 用 BF16 存，權重 16 GB。一個請求的 prompt 有 2,000 個 token，要生成 500 個 token。Serving 系統可以一次跑 1 個請求，或把 32 個請求併成一個 batch。

    回答時請涵蓋
    • 分別估算 prefill 與 decode 每讀 1 byte 的權重，大約做幾次運算。提示：1 個參數 2 byte，每個 token 做 2 次運算。Prefill 讀 1 次給 2,000 個 token，decode 給 1 個。
    • 說明 batch 從 1 變成 32 時，哪些記憶體讀取可以分攤，哪些不行。提示：把讀取分成兩種：權重（所有請求共用）和 KV cache（每個請求一份）。
    • 指出 batch 一直加大時，會先撞到哪兩種限制。提示：一種是「放不下」，一種是「算不完」。各對應 GPU 的哪個規格？
    作答範本

    Prefill 每讀 1 byte 約做 ＿＿ 次運算，decode（batch 1）約 ＿＿ 次；decode 受（算力／頻寬）限制。

    Batch 變成 32 後，＿＿ 只讀一次、大家共用；＿＿ 每個請求還是要各讀一次。

    Batch 一直加大，會先撞到 ＿＿，再來是 ＿＿。

    參考觀點與追問
    • Prefill：每個權重讀 1 次，用在 2,000 個 token 上，約 2,000 FLOPs/byte。這遠高於 GPU 的算力 ÷ 頻寬（H100 約 295），所以受算力限制。
    • Decode（batch 1）：每一步讀完 16 GB，只算 1 個 token，約 1 FLOP/byte。GPU 大部分時間在等資料。
    • Batch 32：權重讀一次，32 個請求共用，強度約變成 32 FLOPs/byte。只看權重，throughput 接近 32 倍。
    • 不能分攤的：每個請求的 KV cache 要各自讀。Context 越長，KV 的讀取越佔比重，batching 的好處越小。
    • 兩種限制：KV cache 先塞滿記憶體容量；或強度超過 GPU 的比值，變成受算力限制。在那之前，每一步也因為 KV 的讀取變慢（p.44 第 1 題）。

    追問：Decode 為什麼不能像 prefill 一樣一次算很多個 token？哪一種技術試著突破這一點？（提示：課表 10/28 的 speculative decoding。）

  2. 估算 · Decode 的速度上限 · p.30、p.32

    估算單一請求 decode 的速度上限。Batch 變成 32 時，每個請求和整張 GPU 的速度各變成多少？

    情境：8B model，BF16，權重 16 GB。GPU 記憶體頻寬 1.6 TB/s，容量 96 GB。每個 token 的 KV cache 是 128 KiB（32 層、8 個 KV head、head 維度 128）。每個請求的 context 是 4,096 個 token。只算讀記憶體的時間。

    回答時請涵蓋
    • 寫出 batch 1 的算式：每個 token 要幾 ms，每秒最多幾個 token。提示：時間 ≈ 讀的 byte ÷ 頻寬。每一步讀 16 GB 權重，加上 4,096 × 128 KiB 的 KV cache。
    • 算出 batch 32 每一步要讀幾 GB，以及每個請求與整張 GPU 每秒各幾個 token。提示：每一步讀 16 GB + 32 × 一個請求的 KV。整張 GPU 的速度 = 32 × 每個請求的速度。
    • 估算每個請求的 context 變成 32K token 時，96 GB 最多放得下幾個請求。提示：先扣掉權重，再除以一個請求的 KV：（96 − 16）GB ÷（32K × 128 KiB）。
    作答範本

    Batch 1 每一步讀約 ＿＿ GB，要 ＿＿ ms，每秒最多約 ＿＿ 個 token。

    Batch 32 每一步讀約 ＿＿ GB，要 ＿＿ ms；每個請求每秒 ＿＿ 個，整張 GPU 每秒 ＿＿ 個。

    32K token 的請求，每個要 ＿＿ GB 的 KV cache；扣掉權重，最多放 ＿＿ 個。

    參考觀點與追問
    • Batch 1，不計 KV：16 GB ÷ 1.6 TB/s = 10 ms，每秒最多 100 個 token。加上 4,096 個 token 的 KV（≈ 0.54 GB），約 10.3 ms，每秒約 97 個。
    • Batch 32：每一步讀 16 + 32 × 0.54 ≈ 33.2 GB，約 20.7 ms。每個請求每秒約 48 個 token，整張 GPU 約 1,540 個。忽略 KV 會算出 3,200 個，KV 讓數字少一半以上。
    • 容量：96 − 16 = 80 GB 給 KV。32K token 的請求每個要 4.3 GB，最多放 18 個，batch 32 放不下。
    • 對 agent 的意義：一步生成 500 個 token，batch 1 約 5.2 秒，batch 32 約 10.4 秒。40 步的 run，critical path 上多出約 3.5 分鐘。

    追問：32 個請求共用同一段 2,000 token 的 system prompt 時，哪些成本可以省下來？Agent 的 context 每一步都變長，這組算式要怎麼改？

    • 反例：batch 加大，tokens/sec 上升，但 critical path 上每一步變慢。或換一個話多的 model：每秒 200 個、共 20,000 個 token 要 100 秒；每秒 100 個、共 5,000 個只要 50 秒。
    • 成功的判定：先用自動訊號（測試通過、CI 綠燈），再每週抽樣人工 review。只看「使用者沒抱怨」會高估成功率：失敗的人常常就不再用了。

    追問：成功率上升 5%，每個成功任務的成本也上升 20%，這週算變好還是變差？你會怎麼事先訂出換算規則？

  4. 團隊實務 · 不確定性與測試 · p.31

    Temperature 0 也不保證輸出可重現。團隊要怎麼替 LLM 功能寫測試，才能在 CI 裡穩定地抓到退步？

    情境：一個功能把使用者的 bug 描述轉成 JSON，欄位是 component、severity、steps。CI 有 50 個測試案例，每個都比對完整的 JSON 字串。最近一週，每次 CI 都有 2–5 個案例隨機失敗，大家開始直接按 rerun。

    回答時請涵蓋
    • 指出這些隨機失敗至少兩個可能的來源。提示：一個來源在伺服器端：p.31 說 batch size 改變時，什麼跟著變？另一個想：prompt 每次都一模一樣嗎？
    • 把測試分成確定性的部分與 model 行為的部分，各提出一種寫法。提示：Prompt 組裝與 JSON parse 怎麼測，才不必呼叫 model？Model 的輸出：不比字串，改查哪些性質？
    • 訂出判定退步的規則：每個案例跑幾次、通過率低於多少算退步，並說明理由。提示：先想：每個案例只跑 1 次，看得出通過率嗎？再想：跑 20 次時，通過率的誤差大約多大？
    作答範本

    隨機失敗可能來自 ＿＿，也可能來自 ＿＿。

    ＿＿ 這類確定性的部分用 ＿＿ 測；model 的輸出改成檢查 ＿＿。

    每個案例跑 ＿＿ 次，通過率低於 ＿＿ 才算退步，因為 ＿＿。

    參考觀點與追問
    • 來源：伺服器每次的 batch 不同，加總順序跟著變（p.31）；provider 更新了 model 或 serving 設定；prompt 裡有日期這類每次不同的內容。
    • 確定性的部分：錄下 model 的回覆，用 record / replay 跑一般的 unit test。這一層必須 100% 穩定，失敗就是程式的錯。
    • Model 的部分：不比對字串，改檢查性質。JSON 能 parse、欄位齊全、severity 是允許的值、component 和標準答案一致。
    • 判定規則：每個案例跑 10–20 次，看整體通過率。注意誤差：20 次過 18 次，95% 信賴區間約 70%–97%。兩個版本 18/20 對 16/20，Fisher exact test 的 p 值約 0.66，不能說退步。
    • 上線前改看 pass^k（L7）：k 次都成功才算過。對 agent 更重要：一個 token 不同，可能換掉整個 tool call。

    追問：每個案例跑 20 次，CI 的成本和時間都變成 20 倍。哪些檢查放在每個 PR，哪些放到每晚？Provider 換了 model 版本，你怎麼第一時間知道？

  5. 風險 · 長 run 的復原 · p.34、p.42、p.44

    一個 30 分鐘的 agent run 在第 25 分鐘失敗。設計一套 checkpoint 與復原機制，並說明它的代價。

    情境：Agent 在做一次資料庫 migration：讀 schema、改程式、跑測試、在 staging 資料庫執行 SQL、開 PR。全程約 60 步，每步平均 30 秒。第 25 分鐘時，serving 的一張 GPU 故障，進行中的 inference 中斷。當時 context 約 120K token；SQL 已經執行，PR 還沒開。

    回答時請涵蓋
    • 列出 checkpoint 要存哪些狀態，以及在哪些時間點存。提示：分三種狀態：trajectory、工作目錄、外部系統的副作用。時間點想：哪一種動作做完後，最怕丟掉紀錄？
    • 分別寫出三種失敗的復原方式：inference 中斷、tool 失敗、model 走錯方向。提示：每一種都問兩件事：從哪一步重做？重做會不會重複副作用？例如 SQL 執行兩次會怎樣？
    • 估算有、沒有 checkpoint 時各要重做多少工作，並指出 checkpoint 本身的代價。提示：沒存，損失已跑的時間；每步都存，損失 ≤ 1 步 + 一次 120K 的 prefill。代價想：存哪、多等多久？
    作答範本

    Checkpoint 存 ＿＿、＿＿ 和 ＿＿，在每次 ＿＿ 之後存。

    Inference 中斷時 ＿＿；tool 失敗時 ＿＿；model 走錯方向時 ＿＿。

    沒有 checkpoint 要重做約 ＿＿；每步都存，最多重做 ＿＿。代價是 ＿＿。

    參考觀點與追問
    • 存什麼：完整的 trajectory；工作目錄的狀態，例如每步一個 git commit；副作用的紀錄，例如 migration 版本、PR 編號。
    • 什麼時候存：每個 tool 結果回來之後。有副作用的動作，執行前先記「打算做」，執行後再記「做完了」，像資料庫的 write-ahead log。
    • Inference 中斷：換一台 replica，用 trajectory 重建 context，重做那一步。代價是重新 prefill 120K token；KV cache 若存在 CPU 記憶體或 SSD，可以直接載回（p.44 第 3 題）。
    • Tool 失敗：有上限的重試，加上 backoff。SQL 要冪等：先查 migration 版本，執行過就跳過（L4）。Model 走錯方向：回到上一個驗證過的 checkpoint 重新規劃（L6），只重做最後一步不夠。
    • 估算：沒有 checkpoint 就從頭重來，損失 25 分鐘，token 也要重付。每步存 checkpoint，最多損失 1 步（約 30 秒）加一次 120K token 的 prefill。代價是儲存空間、每步多一點延遲，以及復原程式本身的 bug。

    追問：如果 migration 跑在正式環境的資料庫，你的設計要改哪裡？Trajectory 裡有 secret 時，checkpoint 要怎麼存？

  6. 應用 · 課程的 9 個問題 · p.44

    從 p.44 的 9 個問題挑一題，套到你們團隊的系統或流程上。你會怎麼量它？

    情境：例如你們用 agent 處理 bug 單、寫測試、產生報告，或你們在 serve 一個內部的 model。選一個你熟悉的情境。

    回答時請涵蓋
    • 把問題改寫成你們團隊的版本，並寫出要量的 1–2 個數字。提示：套用句型：在什麼限制下，比較哪兩種做法，看哪個數字。不知道選哪題，就選第 9 題。
    • 說明資料從哪裡來：log、trace、帳單，還是要新增量測點。提示：先列手上已有的資料，例如 API 帳單的 usage、CI log。算你的數字還缺哪個欄位？那就是新的量測點。
    • 設計一個最小的實驗：比較哪兩種做法、跑多少次、怎麼判定結果。提示：用 20–50 個過去的真實案例當題目，兩種做法各跑幾次。差距要大過誤差才算數，見第 4 題。
    作答範本

    我選第 ＿＿ 題，在我們團隊是：＿＿。要量的數字是 ＿＿。

    資料來自 ＿＿；還缺 ＿＿，要在 ＿＿ 加一個量測點。

    用 ＿＿ 個過去的案例，比較 ＿＿ 和 ＿＿，各跑 ＿＿ 次；差距大於 ＿＿ 才下結論。

    參考觀點與追問

    以第 9 題「怎麼優化每個成功任務的成本」為例：

    • 改寫：我們的 bug 修復 agent，每修好一個 bug 花多少錢？換較小的 model 會更省嗎？
    • 數字：每個成功任務的成本，等於一週的 API 花費 ÷ 合併的修復 PR 數。另外看成功率與每個任務的 step 數。
    • 資料來源：API 回傳的 usage 欄位，依任務 ID 加總；成功與否看 PR 的狀態。沒有任務 ID 就先補上。
    • 實驗：取 50 個過去的 bug，兩種設定各跑 3 次，比較成功率與每個成功任務的成本。差距小於誤差時不下結論（見第 4 題）。
    • 同一個實驗也回答第 2 題：大 model 每次較貴，但少繞路、成功率高時，每個成功任務反而便宜（p.41）。

    追問：你挑的這一題，答案會不會隨著 model 更新而改變？多久要重新量一次？

自我檢查

Prefill 和 decode，哪一個受算力限制？為什麼 decode 不能把很多 token 併成一次運算？

Prefill。Prompt 的 token 全部已知，可以平行計算，權重讀一次就用在幾千個 token 上。Decode 的第 n 個 token 要等第 n−1 個生成後才能算。

Agent A 每次嘗試花 $0.30，成功率 40%。Agent B 每次花 $0.50，成功率 80%。哪一個的每個成功任務成本較低？

B。A：$0.30 ÷ 0.4 = $0.75。B：$0.50 ÷ 0.8 = $0.625。只看每次呼叫的價格，會選錯。

為什麼 agent 比單輪的聊天更需要 prefix cache?

Agent 每一步都重送整段 context，開頭完全相同。Prefix cache 保留開頭的 KV cache，下一步只要 prefill 新增的部分。Context 越長，省得越多。

6 · 動手試試

自己算一次

三個小練習，只用 Python 標準函式庫。解答在每個練習的最後。

用 Python 看加總順序怎麼改變結果p.31

GPU 的 kernel 把加總切成小塊。下面用 float32 模擬：同一組 4,096 個數字，只改分組大小。

$ python3 fp_order.py
chunk=4096 sum=45.4947853 winner=B
chunk= 512 sum=45.4947968 winner=A
chunk=  64 sum=45.4947891 winner=B
chunk=   8 sum=45.4948082 winner=A

練習：（1）4 種分組的總和最多差多少？（2）rival 是另一個候選 token 的 logit，winner 為什麼換來換去？（3）這和 temperature 0 有什麼關係？

解答：（1）最大差約 0.000023，約是總和的 5 × 10⁻⁷。（2）兩個 logit 的差距比加總誤差還小，分組一變，大小關係就變。（3）Kernel 依 batch size 選切法，切法就是這裡的 chunk。差距小於誤差時，換一個 batch size 就可能換掉 argmax。

估算 decode 的速度上限p.30、p.32

只算讀記憶體的時間。數字和第 5 段第 2 題相同。

$ python3 decode_bound.py
ctx= 4096 batch= 1  step= 10.3 ms  per-request= 96.8 tok/s  total=   97 tok/s
ctx= 4096 batch= 8  step= 12.7 ms  per-request= 78.8 tok/s  total=  631 tok/s
ctx= 4096 batch=32  step= 20.7 ms  per-request= 48.2 tok/s  total= 1543 tok/s
ctx=32768 batch= 1  step= 12.7 ms  per-request= 78.8 tok/s  total=   79 tok/s
ctx=32768 batch= 8  step= 31.5 ms  per-request= 31.8 tok/s  total=  254 tok/s
ctx=32768 batch=32  step= 95.9 ms  per-request= 10.4 tok/s  total=  334 tok/s

練習：（1）ctx 4K 時，batch 從 1 加到 32，每個請求和整張 GPU 的速度各變幾倍？（2）ctx 32K、batch 32 這一列，在 96 GB 的 GPU 上跑得起來嗎？（3）把 bw 改成 3.35e12，速度怎麼變？

解答：（1）每個請求約剩一半；整張 GPU 約 16 倍。KV 讀取不能分攤，所以不是 32 倍。（2）不行：16 + 32 × 4.3 ≈ 153 GB，超過容量。（3）每一列約快 2.1 倍。只要還受頻寬限制，速度就和頻寬成正比。

算叢集多久壞一張 GPUp.34

用 slide 的數字：MTBF 50,000 小時、16,384 張 GPU。假設每張 GPU 獨立故障，間隔服從指數分布。

$ python3 fleet.py

with AFR 9%: one failure every 5.94 h

runs hit per day at 100,000 runs/day: 8.0

練習：（1）叢集多久壞一張？一天幾次？（2）MTBF 換算成 AFR 是多少？和 slide 的 9% 一致嗎？（3）一個 run 遇到 GPU 故障的風險，和每步 1% 出錯、共 60 步的風險，哪個大？

解答：（1）約 3.05 小時一次，一天約 8 次。（2）約 16%，和 9% 不一致；用 9% 算是約 5.9 小時一次，量級相同。（3）GPU 故障約 0.008%；每步 1% 出錯時，60 步全部順利只有約 55%。對單一個 run，tool 與 API 的失敗才是主要風險。
