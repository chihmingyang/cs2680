先看這裡

這門課前半講 agent（會自己呼叫工具、連跑很多步的 AI 程式）怎麼設計，後半講 LLM 怎麼在 GPU 上 serve 給很多人用，主體是後半。把兩半接起來的觀察是：聊天跑一次 model 就回答，agent 卻要跑很多次，中間還要執行工具、等人，連成一條鏈。Serving 常看的數字，例如 GPU 每秒生成幾個 token（tokens/sec；token 是 model 處理文字的單位），只量到鏈上 model 那一段，所以它們變好，任務不一定更快、更便宜，甚至不一定做成。這堂是課程總覽，要帶走的是目標要從 tokens/sec 換成每個成功任務的成本，也就是連失敗的嘗試一起付的錢，攤到每個做成的任務上，以及怎麼判斷問題出在哪一層，從 agent 程式到 GPU 硬體。

  • Agent 是另一種 workload。Microsoft 分析 GitHub Copilot 線上流量的論文裡，agent 一段對話中位數呼叫 model 15 次，每次都把前面的對話和工具輸出整段再送一次。所以每次送進的前文中位數是 68K token，約是聊天一次送進 750 token 的 90 倍（750 是這篇論文引用的更早研究）。延遲、狀態和失敗沿著整條鏈累積：每一步等上一步；前文的中間結果留在 GPU 記憶體裡省得重算，等工具時也佔著；每一步都可能出錯重試。
  • 目標要換，而且要把人等結果、驗結果的時間算進成本。Tokens/sec 高，agent 仍可能又慢又貴：把很多請求併成一批算（batching），GPU 總產量變高，每個請求卻變慢；繞遠路多生成的 token 也照樣算進產量。失敗的嘗試也要付錢，成功率越低，每個成功任務越貴；大 batch 拖慢的時間，有人坐著等就是人的成本，所以有人等用小 batch，沒人等用大 batch。
  • 問題會跨層，底下的假設也不一樣了。例如 serving 層把算過的前文存起來，下一次開頭完全相同才能重用（prefix cache），所以 agent 的外層程式（harness）怎麼排送給 model 的文字，決定 cache 能不能命中。寫 web 服務時默認的五件事，跑 LLM 時都反過來了：算多久無法預測，狀態不小（一個請求可達好幾 GB），同樣輸入可能給不同輸出，機器常壞，model 架構一年換好幾輪。課程的後半就從這五條講起，第 6 章逐條對照。

1根本的差別：一次 inference 變成一條鏈

先看一次聊天。你送出一句話，model 先一次讀完這段文字（這一步叫 prefill），接著一個 token 一個 token 地生成回答（這一步叫 decode，第 7 章細講）。Token 是 model 處理文字的最小單位，英文約 4 個字母 1 個，中文一個字常是 1 到 2 個。Model 讀進一段文字、生成下一段文字的這一次計算叫 inference。傳統的 LLM serving 處理的就是很多個這樣的請求：一個 request，一次 inference，一段 response，請求之間互不相關。

再看 coding agent 修一個 bug。Model 還是只會生成文字，但這次它生成的是一個 tool call，也就是「請執行 pytest」這樣一段請求。Model 自己碰不到檔案和 shell，真正去執行的是 model 外面那層程式，叫 harness。Harness 把執行結果接在對話後面，再整段送回 model；送進去的這一整段文字叫 context，所以 context 每一圈都變長。Model 看完結果再決定下一步，一直跑到它認為做完為止（這個 loop 的細節在 L2）。於是一次 inference 變成一條鏈：

因為每一步都等上一步，整條鏈都在 critical path 上：這裡任何一段慢，整個任務就慢，而這條鏈同時跨過 GPU、CPU、storage、網路和外部服務，沒有一個元件單獨負責。

這和聊天差多少？課程只有定性的描述，2026 年才有大規模的實測。Microsoft Azure Research 分析了 GitHub Copilot 的 production trace，也就是線上真實流量的紀錄，樣本是 2026 年 6 月第一週的美國區，320 萬名使用者、1,350 萬個 session（一段對話從開始到結束）：

一個 session 有很多 turn，turn 是你打一句話、agent 跑完再回來的那一段。同一份 trace 裡，87% 的 LLM call 由 agent 自己發起，中間沒有人看著。課程列了這條鏈帶來的六個挑戰，下表把每一個對上實測的樣子（有一項沒有實測）。數字來自這份 trace 和 TraceLab：華盛頓大學團隊收集了 43 位開發者的 4,265 個 Claude Code 與 Codex session（這些 session 是團隊成員做自己的研究時留下的，不代表所有開發者）：

任何一步都可能失敗9% 的 turn 有 tool 失敗。Agent 會自動重試，每次重試都帶著更長的 context，所以和沒失敗相比，這些 turn 的運算量最多放大 4 倍。

對照傳統的 serving，這條鏈讓每個老問題都更難：時間更不可預測，因為連步數也未知；狀態更大、活得更久，因為 context 跨過幾十步一直在；失敗點更多，因為每一步都可能碰外界。所以 agent 把 serving 的問題乘上步數。傳統 serving 在意的數字，例如第一個 token 多快出現、GPU 每秒生成幾個 token，都只量鏈上 inference 那幾段，不含 tool、重試和等待，所以它們變好，也不代表任務變好了。

2最重要的判斷：throughput 是錯的目標，要算每個成功任務的成本

Serving 系統的儀表板上通常是這幾個數字。TTFT（time to first token）是送出請求到第一個 token 出現的時間，TPOT（time per output token）是之後每個 token 的間隔，tool-call latency 是一次 tool 來回的時間，GPU utilization 是 GPU 忙的比例，throughput 是整張 GPU 每秒生成幾個 token（tokens/sec）。它們都有用，但每一個只量到鏈上的一小段，沒有一個能告訴你任務有沒有變好：

所以課程的關鍵句是 throughput 對 agent 來說是錯的目標。正確的寫法是一個帶限制的最佳化：在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。限制的意思是不能超過上限；成功率再高，等太久的設計還是不合格。

每個成功任務的成本。目標要算得出來。一個任務可能試好幾次才成功：成功率 50% 時，平均要試 2 次才成功 1 次，也就是 1 ÷ 成功率 次。失敗的那幾次也要付錢，所以成本要除以成功率。式子裡有三項：

  • 每次嘗試的 token 數。由 agent 繞不繞路決定。
  • 每個 token 的單價。由 model 和 serving 決定。
  • 成功率。同一種任務 100 次裡成功幾次。

把兩個版本的 agent 代進去，這裡直接用 token 數乘單價之後的花費：

B 每次較貴，每個成功任務反而便宜，使用者拿到結果的次數還幾乎是兩倍。只看每次嘗試的花費，你會選 A。要把這個數字算準，成功率得量得對，這是 L7 的主題；token 數和單價再怎麼拆，是 L8 的主題。

本文的判斷：tokens/sec 會把優化帶錯方向。它有三個盲點，每一個都讓 tokens/sec 變好或不動，agent 卻變差：

  • 大 batch 讓鏈上的每一步變慢。Batching 把多個請求放進同一次 GPU 運算一起算。整張 GPU 每秒產出的 token 變多，但每次運算要讀的資料也變多，因為每個請求各有自己的中間結果，所以每個請求等下一個 token 的時間變長（第 7 章算給你看）。一個跑 40 圈、每圈生成 500 個 token 的 agent，batch 從 1 加到 32，生成時間從約 3.4 分鐘變成約 6.9 分鐘（下圖）。
  • 繞遠路的 agent 生成更多 token。Tokens/sec 只算每秒生成幾個 token，不管這些 token 該不該生成，多繞的路照樣算進產量，所以它看不出 agent 在繞路。拿它來挑設定，就可能挑錯。假設同一個任務有兩種設定：甲用比較小、比較快的 model，每秒生成 200 個 token，但它繞路，總共生成 20,000 個，要 100 秒；乙用比較大的 model，每秒只生成 100 個，但它直接做，生成 5,000 個，只要 50 秒。照 tokens/sec 會選好看一倍的甲，任務卻慢一倍。
  • Tool 的時間和大部分的錢不在裡面。Tokens/sec 只量 GPU 生成 token 的速度，tool 跑多久、每一步重讀前文花多少錢，它都看不到，所以這兩項變差時數字不會動。這兩項還很大：TraceLab 的 session 裡，tool 執行花的時間比 LLM 生成還多（21.2% 對 14.5%，第 3 章有圖）；依 API 定價，output token 只佔成本 11.2%，59.5% 是每一步重讀前文的 input token。

這不表示 throughput 沒有用。GPU 按時間計費，一小時的費用固定；同樣一小時裡生成的 token 多 16 倍，每個 token 分到的費用就低 16 倍。所以它動的是目標式裡「單價」這一項，拿來做容量規劃（要買幾張 GPU）也很合適。錯的是把它當成目標。指標一旦變成目標，團隊就會去優化它，不管它還代不代表原本的目的，這叫 Goodhart's law。所以儀表板最上面放任務層級的指標，tokens/sec 留在 serving 的分頁。

3目標少算的一項：人的時間

6五個假設：零件和傳統系統相同，workload 不同

Stack 的下半部變的是什麼？一個 AI 系統有七種會動的零件：scheduling 與 orchestration、state management、communication、caching、fault tolerance、security、observability。這張清單和一本作業系統或分散式系統教科書的目錄幾乎一樣，所以 AI 系統沒有新零件，新的是 workload。零件既然相同，系統這一側在做什麼？課程拿同一個 model 對比兩種人：ML 研究者問該用哪個、怎麼設計，優化 accuracy；系統工程師問怎麼在大規模下 serve 它，優化 GPU 使用率、資源浪費、停機時間和碳排。課程說系統工程這一側是能力變成產品的地方，而且比 AI 本身更難。

查閱MHA、GQA、MLA、NSA、linear attention：五個名字差在 KV cache

先看 attention 怎麼做。新 token 算出一個 query，表示它要找什麼。前文每個 token 各有一個 key 和一個 value：key 用來和 query 比對打分，value 是參考它時取出的內容。新 token 依分數把前文的 value 加權取出來。

KV cache 存的就是前文每個 token 的 key 與 value。Model 會把 attention 平行做好幾份，每一份叫一個 head，各看不同的關係。下面五個名字，差在要存幾份 key 與 value、存多大。

MHA（multi-head attention）每個 head 各有自己的 key 與 value，KV cache 最大。GQA（grouped-query attention）讓幾個 query head（只算 query 的 head）共用一組 key 與 value。要存的組數變少，KV cache 縮小好幾倍，Llama 3 用它。MLA（multi-head latent attention）把 key 與 value 壓成一個低維向量存，DeepSeek-V2 起用它。

NSA（native sparse attention）讓每個 token 只挑前文的一部分來比對，DeepSeek 2025 年提出。一般的 attention 用 softmax 把分數換成權重，要先拿 query 和前文每個 key 都算完分數，所以前文的 key 與 value 一個都不能丟。Linear attention 換掉 softmax，改成可以把前文先累加成一個固定大小的矩陣，用這個狀態取代 KV cache，所以不隨長度成長。對 serving 的意義：各種架構要存的東西大小與讀法不同，記憶體管理要各自適配。

7時間：prefill 和 decode 瓶頸不同，長度事先不知道

第一條假設是「一個請求花多久大致可以預測」。LLM 的請求做不到，原因要從它在 GPU 上怎麼跑講起。一個請求分兩段，瓶頸不同：

Prefill 是 model 一次讀完整段 prompt：所有 token 同時算，權重（weights，model 訓練出來的參數）每讀一次就用在幾千個 token 上，所以瓶頸在算力，GPU 的運算單元是忙的。接著是 decode：一次生成一個 token，每生成一個都要把全部權重和前面所有 token 的中間結果再讀一遍，卻只算一個 token，所以瓶頸在記憶體頻寬，運算單元大多在等資料。Decode 一直重複到 model 輸出結束 token。同樣 2,000 token 的 prompt，回答可能只有 50 token，也可能有 5,000 token，所以執行時間要等生成完才知道，scheduler 不能像排傳統的 job 那樣先估時間再排。

名詞Prefill 與 decode：怎麼判斷瓶頸在算力還是頻寬（arithmetic intensity）

判斷方法：比較每讀 1 byte 做幾次運算（arithmetic intensity），和 GPU 的算力 ÷ 頻寬。H100 的比值約 295（989 TFLOPS ÷ 3.35 TB/s）。比值低於 295，GPU 算得比讀得快，瓶頸在頻寬；高於 295，瓶頸在算力。

Model 的比值這樣估：每個參數佔 2 byte，每個 token 用到一個參數約做 2 次運算（一次乘、一次加）。Decode 在 batch 1 時，讀一個參數只替 1 個 token 算，比值約 2 ÷ 2 = 1，所以受頻寬限制。2,000 token 的 prefill 讀一次參數就替 2,000 個 token 算，比值約 2,000，所以受算力限制。Batch 有 n 個請求時，讀一次參數替 n 個 token 算，比值約 n，所以 batching 就是把 decode 的比值往上推。

瓶頸也不只在 GPU 裡，因為運算是異質的。CPU 負責 tokenization（把文字切成 token）、發起 kernel（GPU 上跑的小程式）、搬資料和跑 tool，GPU 只負責矩陣乘法；叢集裡還常混著不同世代的 GPU，所以 routing 也要知道每張卡的差別。

拆開不是免費的。Dynamo 的文件寫得很直接：輸入很長、輸出很短的 workload 才划算，輸入輸出比在 2:1 到 10:1 之間時，不拆常常比較好；KV cache 的傳輸要靠 RDMA，沒有 RDMA 時 TTFT 從 355 ms 變成 10 秒以上。本文的判斷：agent 的 prompt 雖然長，命中 cache 時真的要 prefill 的只有新增的部分。Claude Code 的中位數是新增 857 token、輸出 252 token，約 3.4:1，落在 Dynamo 說不拆常常比較好的 2:1 到 10:1 之間。改用整段 prompt 算，重讀的 126K 加新增的 857，對輸出 252，約 504:1，看起來是最該拆的那種。兩種算法的結論相反，所以要不要拆，先看 cache 命中後的長度，不是 prompt 的長度。

8狀態：KV cache 放哪裡，變成首要決定

傳統的 web 服務每個 session 只有幾 KB 的狀態。LLM 有兩塊大得多的狀態。第一塊是權重，從幾 GB 到幾 TB。第二塊是 KV cache：attention 要用到前面每個 token 在每一層算出的 key 與 value，model 把它們存起來，下一步直接用，不重算。第 4 章的 prefix cache，就是把這塊存起來跨請求重用。

KV cache 有多大。大小可以算。每個 token 在每一層存 key 和 value 兩份，每份有幾個 KV head，每個 head 有固定的維度，每個數字佔幾個 byte。以 32 層、8 個 KV head、head 維度 128、BF16（每個數字 2 byte）的 8B model 為例：

Model 大到要切到多張 GPU 時，GPU 之間也要通訊，切法和通訊零件收在下面的註。

查閱一張 GPU 放不下時：平行化的切法與通訊零件

平行化有五種切法：

  • Data parallelism。複製整個 model，各處理不同請求。
  • Tensor parallelism。把每一層的矩陣切給多張 GPU。
  • Pipeline parallelism。把 model 按層切給多張 GPU。
  • Expert parallelism。把 MoE（mixture of experts，model 由多個專家子網路組成）的 expert 分到不同 GPU。
  • Context parallelism。把一段很長的輸入切給多張 GPU 一起算。

切得越細，GPU 之間交換的資料越多，所以 tensor parallelism 通常留在同一台機器內走 NVLink。通訊的零件有三樣：collective 函式庫（NCCL、UCCL，負責 all-reduce 這類所有 GPU 一起交換再加總的操作）；拓樸（同一台機器內走 NVLink，跨機器走 Ethernet 或 InfiniBand）；RDMA（網卡直接讀寫對方機器的記憶體，繞過 CPU 和 OS kernel）。

本文補的：agent 的 KV cache 什麼時候閒著。課程問 KV 與 prefix 的狀態該放哪裡，直覺的答案是等 tool 時就搬走。GitHub Copilot 的 trace 改了這個問題的重點：閒置分成兩種，長度差兩個量級。

Tool 造成的閒置多半很短，中位數 1.2 秒，下一次 call 馬上就來。100K token 的 KV cache 經 PCIe 搬到 CPU memory 再搬回來，來回約 0.4 秒（見〈搬資料才是瓶頸〉那張圖），已經是這段閒置的三分之一，空出來的位置又很快要還回去，不划算。真正長的閒置來自人，中位數 172 秒。所以該搬的時機是 turn 的邊界，不是每次等 tool。這是第 3 章的人的時間在 serving 層留下的影子。

9不確定與故障：測試和長任務都要換寫法

傳統系統的另外兩個假設是「同樣的輸入給同樣的輸出」和「機器很少壞」。這兩條打破之後，直接改變團隊怎麼寫測試、怎麼設計長任務。

同一個 prompt，輸出為什麼不同。浮點數每做一次運算就捨入一次，所以加總的順序會改變結果。GPU 把一個矩陣乘法切成很多小塊平行算，再把部分和加起來，切法由 kernel（GPU 上跑的小程式）決定，kernel 又依 batch size 選：

兩次的 logit 從第 7 位有效數字才開始不同（45.49479… 對 45.49478…，差約 0.00001），但前兩名很接近時，這就夠讓最高分換人；一個 token 換了，後面的句子就全部不同。課程叫它蝴蝶效應。Temperature 是控制隨機取樣的參數，0 表示每一步都選最高分，所以 temperature 0 只固定了選法，不保證可重現。既然捨入誤差免不了，課程的結論是近似計算可以接受：FP8（8 位元浮點數）與 quantization（用較少的 bit 存權重）都是刻意用精度換速度。要可重現也做得到，延伸閱讀裡的 Thinking Machines 示範了修法：改用不隨 batch size 變的 kernel 後，1,000 次輸出完全相同，代價是時間變成 1.6 到 2.1 倍，而且只在你控制 serving stack 時才做得到。

背景浮點數沒有結合律：同一個 prompt 為什麼有不同輸出

浮點數每做一次運算就捨入一次，所以 (a + b) + c 和 a + (b + c) 可能不相等。GPU 把 matmul 切成小塊平行加總，切法由 kernel 決定。Batch size 一變，kernel 可能換，加總順序跟著改變。

課程把不確定性的來源分三層：

  • Runtime。GPU 把執行緒 32 個編成一組（warp），好幾組再編成一個 block 來排程；哪一組先算完、先把部分和加回去，每次可能不同。多個執行緒加到同一個記憶體位置時，誰先加也不固定（記憶體順序）。Stream 是 GPU 上可以同時執行的工作佇列，非同步的 stream 也會改變運算的先後。最後是 batch size。
  • 軟體。Fused multiply-add 一次算完 a × b + c，只捨入一次，和分兩步算的結果不同。Autotuning 依輸入形狀換 kernel。Subnormal 是比最小的一般浮點數還接近 0、精度較低的數；有的設定直接把它當成 0，有的照算，結果就不同。
  • 硬體。NVIDIA GPU 有兩種運算單元：一般的 CUDA core 和專做矩陣乘法的 tensor core，兩者累加的方式不同。Hopper 是 H100 那一代，Blackwell 是下一代（B200）。Blackwell 的 micro-scaling 格式讓每一小塊數字（tile）共用一個縮放係數，Hopper 的 FP8 沒有這種硬體的區塊縮放，所以捨入的位置也不同。

2 · 動手試試

自己算一次

三個小練習，只用 Python 標準函式庫。解答在每個練習的最後。

用 Python 看加總順序怎麼改變結果p.31

GPU 的 kernel 把加總切成小塊。下面用 float32 模擬：同一組 4,096 個數字，只改分組大小。

練習：（1）4 種分組的總和最多差多少？（2）rival 是另一個候選 token 的 logit，winner 為什麼換來換去？（3）這和 temperature 0 有什麼關係？

解答：（1）最大差約 0.000023，約是總和的 5 × 10⁻⁷。（2）兩個 logit 的差距比加總誤差還小，分組一變，大小關係就變。（3）Kernel 依 batch size 選切法，切法就是這裡的 chunk。差距小於誤差時，換一個 batch size 就可能換掉 argmax。

估算 decode 的速度上限p.30、p.32

只算讀記憶體的時間。

練習：（1）ctx 4K 時，batch 從 1 加到 32，每個請求和整張 GPU 的速度各變幾倍？（2）ctx 32K、batch 32 這一列，在 96 GB 的 GPU 上跑得起來嗎？（3）把 bw 改成 3.35e12，速度怎麼變？

解答：（1）每個請求約剩一半；整張 GPU 約 16 倍。KV 讀取不能分攤，所以不是 32 倍。（2）不行：16 + 32 × 4.3 ≈ 153 GB，超過容量。（3）每一列約快 2.1 倍。只要還受頻寬限制，速度就和頻寬成正比。

算叢集多久壞一張 GPUp.34

用 slide 的數字：MTBF 50,000 小時、16,384 張 GPU。假設每張 GPU 獨立故障，間隔服從指數分布。

練習：（1）叢集多久壞一張？一天幾次？（2）MTBF 換算成 AFR 是多少？和 slide 的 9% 一致嗎？（3）一個 run 遇到 GPU 故障的風險，和每步 1% 出錯、共 60 步的風險，哪個大？

解答：（1）約 3.05 小時一次，一天約 8 次。（2）約 16%，和 9% 不一致；用 9% 算是約 5.9 小時一次，量級相同。（3）GPU 故障約 0.008%；每步 1% 出錯時，60 步全部順利只有約 55%。對單一個 run，tool 與 API 的失敗才是主要風險。

必讀推薦選讀或查閱時間是專注閱讀的估計；等級是本站的建議，不是課程要求

  1. 選讀Software Is Changing (Again)Andrej Karpathy · 演講影片 · 2025 · 約 40 分

    L1 p.37 引用的影片。把 Software 1.0／2.0／3.0 的分類接到 agent 時代。

    導讀L3 會正式指定這支影片，可以留到那時候讀。先看也可以：只看 autonomy slider 那一段。

  2. 推薦Defeating Nondeterminism in LLM InferenceThinking Machines · 部落格 · 2025 · 約 15 分

    p.31 的延伸：同一個 prompt 跑兩次，結果為什麼不同。原因在 batch size 與浮點運算順序。

    導讀對照第 9 章的註〈浮點數沒有結合律〉。問大家：這對「可重現的 eval」意味著什麼？

    摘要讀約 3 分；原文約 15 分

    一句話：temperature 0 仍得到不同輸出，主因是 kernel 缺少 batch invariance：你的請求和多少別人的請求一起算，reduction 順序就跟著變。作者改寫三個 kernel，1000 次 completion 從 80 種變成 1 種，代價是時間變成 1.6 到 2.1 倍。

    跟這堂課的關係

    第 9 章〈同一個 prompt，輸出為什麼不同〉說同一個 prompt 可能得到不同輸出，這篇是那一段的全文版。Slides p.31 把 batch size 與 warp scheduling 並列為 runtime 層的來源；這篇說 concurrency 無關，batch size 才是主因，這點和 p.31 的 takeaway「approximate computing 可以接受」方向不同：作者認為可重現做得到，也值得做。〈浮點數沒有結合律〉寫了機制，〈本文的判斷：測試要分兩層〉講團隊怎麼應對；這篇補上修法與數字。

    壓縮後的重點

    1. 常見的「concurrency + 浮點數」解釋不成立。這個說法把加總順序的變化歸給 GPU thread 的完成順序與 atomic add。作者指出 LLM 的 forward pass 通常一個 atomic add 都沒有。同一個 matmul 用同樣資料重跑，結果 bitwise 相同。
    2. 真正的原因是 kernel 不具 batch invariance。同一個請求在 batch 1 和 batch 32 裡算，kernel 換切法，reduction 順序跟著變。Batch size 由伺服器當下的負載決定，使用者看不到。所以系統整體是確定的，從單一使用者看卻是隨機的。
    3. 三個有 reduction 的 kernel 要改，原則是切法不隨 batch size 變。RMSNorm：每個 batch element 固定交給一個 core，小 batch 時寧可讓 core 閒置。Matmul：所有形狀用同一組 kernel 設定，不用 Split-K，約比 cuBLAS 慢 20%。Attention：先更新 KV cache 與 page table 再進 kernel；沿 KV 切塊時固定每塊大小（例如 256），塊數隨 KV 長度變。
    4. 數字：80 種變 1 種。Qwen3-235B-A22B-Instruct-2507，prompt 是「Tell me about Richard Feynman」，temperature 0，1000 次各 1000 token，原本有 80 種不同的 completion，最常見的出現 78 次。前 102 個 token 全部相同，第 103 個開始分歧：992 次寫 Queens, New York，8 次寫 New York City。改用 batch-invariant kernel 後，1000 次完全相同。
    5. 效能代價：時間 1.6 到 2.1 倍。單張 GPU 跑 Qwen-3-8B，1000 條序列，每條輸出 90 到 110 token。vLLM 預設 26 秒；未優化的 deterministic 版 55 秒；改良 attention kernel 後 42 秒。
    6. 副產品：真正的 on-policy RL。Sampler 與 trainer 數值不一致時，on-policy RL 會悄悄變成 off-policy。Bigmath 上的實驗：不做 importance weighting，reward 中途崩潰；做了之後 KL 約 0.001。兩端 bitwise 一致時，KL 一直是 0。

    原文怎麼讀

    • 可以跳過：「The original sin: floating-point non-associativity」一節，slides p.31 與本頁第 9 章的註已經講過。「Implementation」只說用 vLLM 的 FlexAttention backend 加 torch.Library 換 kernel。
    • 值得看原文：「Batch invariance and determinism」一節，解釋每個 kernel 都確定、endpoint 仍不確定的原因。「Batch-invariant attention」的 fixed split size 圖：KV 長度 1000 切成 256、256、256、232。「True on-policy RL」的三條 KL 曲線。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 15 分。
    別誤讀

    「浮點數不可結合，所以 GPU 上的 LLM 本來就不可能可重現。」作者反對這種放棄。單一 kernel 重跑的結果 bitwise 相同；會變的只有 batch size 帶來的 reduction 順序，固定它就可重現。但這只在你控制 serving stack 時成立；第三方 API 的 batch 你管不到。
