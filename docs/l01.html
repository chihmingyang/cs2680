先看這裡

這堂前半講課務：兩個主題、五個作業、用 AI 的規則，以及這門課的主體是 serving，agent 是它的 workload。後半畫出整門課的地圖，回答兩個問題：AI 系統和傳統系統差在哪裡，答案是零件相同、workload 打破五個假設；agent 為什麼是一個系統問題，答案是它把一次 inference 拉成一條跨層的鏈。結論是：agent 的目標是任務成功，tokens/sec 只是手段。

  • AI workload 打破傳統系統的假設。Decode 受記憶體頻寬限制；同一個 prompt 可能得到不同輸出；大叢集每幾小時壞一張 GPU。
  • Agent 把一次 inference 拉成一條鏈。infer → tool → infer …，每一步都等上一步。延遲、狀態和失敗沿著整條鏈累積。
  • 優化目標要換。Tokens/sec 高，agent 仍可能又慢又貴。要看任務成功率，和每個成功任務的成本。

A · 這門課：範圍、作業與規則

2.1課程：兩個主題、五個作業，目標是能用數字回答 agent 系統的問題 p.9–26

這一章先講這門課在教什麼，再看五個作業怎麼串成一條線、成績怎麼算、用 AI 的規則是什麼，最後看 slide 怎麼替「用 AI 寫程式」分級；2.2 起進入內容。課務的細節（辦公時間、信箱、投票）不在這裡，要查就開 p.5–7、p.22–25。

這門課教什麼。CS2680 的正式名稱是 Agentic AI Systems，一門研究所等級的計算機系統課。它預設你修過一門研究所的系統課（作業系統、網路、資料庫或計算機結構），而且碰過真實的系統（p.9）。內容分兩塊：agent 怎麼設計，以及 LLM 與 agent 怎麼 serve。前幾堂是基礎：LLM 與 agent 是什麼、怎麼用 Claude Code（Anthropic 的 coding agent，在終端機裡跑，L2 專門講它）、怎麼自己寫一個 coding agent、怎麼把它調好（p.10）。之後大多數的課在 serving 這一側：GPU programming 與 kernel、batching 與 scheduling 與記憶體管理、load balancing 與 routing、KV cache 與 prefix cache、agent serving 系統。本站的 L2–L8 對應前一塊，Part II 從 10/19 起對應後一塊，所以這門課的主體是 serving，agent 是它的 workload。

用 AI 的規則（p.18）值得照抄到自己的團隊：可以用，甚至鼓勵用，但要揭露 AI 幫了什麼、什麼沒成功；每份作業附上 session log；你要能解釋 AI 產生的程式碼，而且對交出去的每一行負責。其他政策：要到場，課不錄影；筆電開著就坐後排（p.19）。計算資源有四種（p.20）：Claude Code 的 API 額度、GitHub 的 private repo（和課程人員共用）、課程的 HPC（SLURM 排程，RTX 6000 PRO Blackwell GPU，只能做課程作業）、AWS（要先填表，不用時關機）。Slide 提醒資源不會隨人數增加：原本預算 40 人，開課當天 80 人，截止日當天可能拿不到 GPU（p.17）。

名詞SLURM：HPC 叢集的工作排程器

SLURM 是學術叢集常用的排程器。你用 sbatch 送一份 job 描述：要幾張 GPU、跑多久、跑哪個 script。它排隊、分配節點，時間到就收回資源。

它和 Kubernetes 的差別：以「跑完就結束的 job」為單位，不是長駐的 service。GPU 都在用時，job 在 queue 裡等。這就是 p.17 說的「截止日當天可能拿不到 GPU」。

用 AI 寫程式的六個等級。p.26 給一把尺，量你現在怎麼用 AI 寫程式，從 0 到 5：

  1. 0 · No AI。全部手寫。
  2. 1 · Assist。AI 做 autocompletion，一次補一行。
  3. 2 · Supervised。AI 寫整個 function，你逐段 review。
  4. 3 · Scoped。你交出一個任務，AI 做完，你 review 程式碼。
  5. 4 · Goal-driven。AI 寫全部的程式，由測試驗證，你看結果。
  6. 5 · Parallel agents。多個 subagent 分工，同時做。

這把尺有兩個用途。第一，它是 p.25 投票的延伸：聊天、用 coding agent（MCP、skill、plugin、subagent、平行 agent）、客製自己的 agent，三個層次對到尺上不同的位置。第二，它是這門課要帶你走的路：A1 在等級 3 附近，A3 的 subagent 與 routing 已經是等級 5。等級越高，你 review 的對象從程式碼變成測試與目標，L3 會專門談這個轉變。

背景MCP、skill、plugin、subagent：p.25 的四個名詞，L2–L3 會講

MCP（Model Context Protocol）是 agent 接外部工具與資料的標準協定，一個 MCP server 提供一組 tool。Skill 是一份寫給 agent 讀的做事說明，agent 覺得用得上就載入。Plugin 把 skill、指令與設定打包，方便分享。Subagent 是主 agent 另外開的一個 agent，有自己的 context，做完回報結果。

L2 講 Claude Code 怎麼用這四樣東西；L3 講 subagent 與平行 agent 怎麼放大產能。

不講什麼。p.45 列出這門課不碰的部分：訓練（資料管線、checkpoint、pre-training、fine-tuning、post-training、RL rollout），理由是 inference 已經是算力需求的大宗；叢集管理；model 架構設計；其他和 inference 有關但不講的題目：通訊、電力與能源、新硬體設計。所以範圍是 inference 這一側的軟體，從 agent 往下講到 kernel。p.44 用 9 個問題收尾，要求學期末能用數字回答它們，2.6 會逐題列出。

B · AI 系統：零件一樣，workload 不一樣

2.2AI 系統：零件和傳統系統相同，問的問題不同 p.28–29

這一章先定義 AI 系統是什麼，再看它和 ML 研究問的問題差在哪裡，最後講為什麼值得學；2.3 看 LLM 的 workload 把傳統系統的哪些假設打破。

AI 系統是什麼。Slide 的定義從零件開始（p.28）。一個 AI 系統有七種會動的部分：

  • Scheduling 與 orchestration。哪個請求先跑、在哪張 GPU 跑。
  • State management。權重、對話歷史、算過的中間結果放哪裡。
  • Communication。GPU 之間、機器之間怎麼傳資料。
  • Caching。算過的東西怎麼重用。
  • Fault tolerance。壞了怎麼辦。
  • Security。系統能碰什麼、不能碰什麼。
  • Observability。看得到系統在做什麼。

這張清單和一本作業系統或分散式系統教科書的目錄幾乎一樣，所以AI 系統沒有新零件，新的是 workload。Slide 的註腳說「AI 系統」是一個寬的詞，這門課只看 LLM 系統。

兩種人，兩組問題。同一個 model，ML 研究者和系統工程師問不同的問題（p.28）：

AI / MLAI 系統
問的問題該用哪個 model？model 該怎麼設計？怎麼在大規模下訓練與 serve 它？
做的事挑一個 model，寫一支 Python script 解一個任務把 model 放進上千張 GPU 的叢集，讓它穩定地跑
優化什麼accuracy、能力GPU 使用率（performance）、資源浪費（efficiency）、停機時間（reliability）、碳排（sustainability）
怎麼量（本文補的）一個 benchmark 的分數throughput、latency、每個請求的成本、每瓦做多少事

右欄的四個目標就是 p.4 研究群組的四個目標。Performance 和 efficiency 常混用，差別是：performance 問跑多快，efficiency 問同樣的結果用了多少資源。一個 model 答對幾題是 ML 的事；同一個 model 在一張 GPU 上一秒能服務多少人，是系統的事。兩邊互相影響：model 的架構決定 KV cache 多大（2.3 會算），serving 的 batch size 又會改變 model 的輸出（2.3 的不確定性）。所以這門課雖然站在系統這一側，仍然要懂 model 在做什麼。

為什麼要在乎。p.29 給三個理由。第一，這裡是能力變成產品的地方，而且把 model 的能力變成產品，比 AI 本身更難：訓練出一個好 model 是一次性的，讓它每天服務上百萬人、不當機、不虧錢，是持續的工程。第二，AI 系統已經是關鍵的數位基礎設施，像電網與網路。第三，對你的好處：懂系統才懂 model 為什麼這樣設計，例如新的 attention 架構多半是為了縮小 KV cache（2.3 的註）；能設計更好的產品，因為 latency 與成本決定一個功能做不做得起來；工作機會也更多。

本文補一句：這門課的 agent 視角讓這個論點更強。Agent 每一圈都把前面的全部對話重送給 model，這些送進去的文字叫 context；L8 會算，一個 coding agent 的成本大宗是重讀的 context，而這筆錢能不能省，取決於 serving 層的 prefix cache 有沒有命中。這件事 ML 研究者看不到，只做 serving 的人也常看不到，因為它跨了 agent 和 serving 兩層。

2.3AI workload：打破傳統系統的五個假設 p.30–34

這一章先列出傳統系統默認的五個假設，再逐一看 slide 講的五項差異：算力、不確定性、記憶體與通訊、變化速度、可靠性與電力。每一項先講機制，再給 slide 的數字；第 4 段有三支小程式可以自己算。

傳統系統的五個假設。寫一個 web 服務時，你多半默認幾件事：一個請求花多久大致可以預測；同樣的輸入給同樣的輸出；每個請求的狀態很小，一個 session 幾 KB；機器很少壞；一台 server 幾百瓦。Scheduler、cache、測試、容量規劃都建在這些假設上。LLM 的 workload 把五條都打破（p.30–34）。下表是本文的整理，後面逐條講：

差異 1：算力，一個請求分兩個階段。先看一個請求在 GPU 上怎麼跑。你送進一段 prompt，model 處理文字的最小單位是 token，英文約 4 個字母 1 個，中文一個字常是 1 到 2 個。Model 先一次讀完整段 prompt，這一步叫 prefill：所有 token 同時算，權重每讀一次就用在幾千個 token 上，所以瓶頸在算力（compute-bound），運算單元是忙的。接著 model 一次產生一個 token，每產生一個都要把全部權重和前面所有 token 的中間結果讀一遍，卻只算一個 token，所以瓶頸在記憶體頻寬（memory-bandwidth-bound），運算單元大部分時間在等資料；這一步叫 decode，重複到結束為止。同一套部署可能在三種瓶頸之間切換：算力、頻寬，以及記憶體容量（放不下更多請求的中間結果）。怎麼判斷當下是哪一種，見註。

Batching 怎麼幫 decode：32 個請求一起 decode，權重只讀一次就分給 32 個 token 用，所以整張 GPU 快很多，每個請求卻慢一點，因為每一步要多讀 32 份中間結果。第 4 段的 decode_bound.py 用數字算：batch 從 1 到 32，整張 GPU 從 97 升到 1,543 tok/s，每個請求從 97 掉到 48 tok/s。這就是 p.44 第 1 題「batching 提高 throughput 卻傷 agent 的 latency」的來源，2.6 會回到它。

p.30 還講兩件事。運算是異質的：CPU 負責 tokenization（把文字切成 token）、發起 kernel（GPU 上跑的一支小程式）、搬資料、跑 tool call，GPU 只負責矩陣乘法；叢集裡常混著不同世代的 GPU 和其他加速器。執行時間取決於輸出長度，而輸出長度在開始前沒有人知道，所以 scheduler 不能像排傳統的 job 那樣先估時間再排。

名詞Prefill 與 decode：怎麼判斷瓶頸在算力還是頻寬（arithmetic intensity）

Prefill 一次處理整段 prompt，每個權重讀一次就用在幾千個 token 上，瓶頸在算力。Decode 一次只生成 1 個 token，每一步都要讀完全部權重和 KV cache，瓶頸在記憶體頻寬。

判斷方法：比較每讀 1 byte 做幾次運算（arithmetic intensity），和 GPU 的算力 ÷ 頻寬。H100 的比值約 295（989 TFLOPS ÷ 3.35 TB/s）。Decode 在 batch 1 時只有約 1；batching 就是把它往上推 p.30。

差異 2：運算不確定。數學上 a × (b + c) = a × b + a × c，而且 a = b、b = c 就有 a = c。浮點數兩條都可能不成立（p.31），因為每做一次運算就捨入一次，所以加總的順序會改變結果。GPU 把一個矩陣乘法切成很多小塊平行算，再把部分和加起來；切法由 kernel 決定，kernel 又依 batch size 與硬體選。Slide 把不確定性的來源分三層：

  • Runtime。Warp 與 block 的排程（GPU 上執行緒分組的先後）、記憶體順序、非同步的 stream、batch size。其中 batch size 最常見：同一個請求和不同數量的請求一起算，走的 kernel 就不同。
  • 軟體。Fused multiply-add 一次算完 a × b + c，只捨入一次，和分兩步算的結果不同；autotuning 依當下的輸入形狀換 kernel；subnormal（很接近 0 的浮點數）的處理方式。
  • 硬體。CUDA core 與 tensor core 的累加方式不同；Hopper 的 FP8 和 Blackwell 的 micro-scaling tile 捨入的位置也不同。

後果是蝴蝶效應：矩陣乘法第 7 位小數的差，就能換掉下一個 token。原因是 model 每一步替每個候選 token 打分數（叫 logit），然後取最大；前兩名很接近時，捨入誤差就能讓它們互換，而一個 token 換了，後面的句子就全部不同。所以 temperature 0 只固定了「選最高分」這個規則，不保證可重現；第 4 段的 fp_order.py 用 4,096 個數字示範這件事。Slide 的結論看另一面：近似計算是可以接受的，系統可以用精度換速度，FP8 與 quantization（A5 的題目之一）都是這個交換。本文延伸 x1 講這件事怎麼改變團隊寫測試的方式。

背景浮點數沒有結合律：同一個 prompt 為什麼有不同輸出

浮點數每做一次運算就捨入一次，所以 (a + b) + c 和 a + (b + c) 可能不相等。GPU 把 matmul 切成小塊平行加總，切法由 kernel 決定。Batch size 一變，kernel 可能換，加總順序跟著改變。

Model 每一步替每個候選 token 打分數（logit），greedy decoding 選最高分。前兩名很接近時，捨入誤差就能讓它們互換。所以 temperature 0 只固定了選法，不保證輸出可重現 p.31。

本文延伸｜不確定性改變團隊測試 LLM 功能的方式不是 slide 的內容

傳統測試假設同樣的輸入得到同樣的輸出，所以可以比對字串。LLM 功能沒有這個保證，temperature 0 也沒有。字串比對的測試會時好時壞；團隊習慣直接重跑之後，真正的退步也跟著漏掉。

做法分兩層。Harness 的程式碼是確定性的：錄下 model 的回覆（record / replay），用一般的 unit test 測。Model 的行為用 eval 測：同一題跑多次，檢查性質，看通過率。L7 的 pass^k 是同一個想法。第 3 段進階題第 3 題請你替一個 JSON 功能設計這套測試。

差異 3：記憶體、儲存與通訊。狀態大得多（p.32）。權重從幾 GB 到幾 TB：一個 8B 的 model 用 BF16（每個數 2 byte）存是 16 GB，最大的 model 上 TB。第二塊是 KV cache：attention 讓每個新 token 參考前面所有的 token，model 把每個 token 在每一層算出的 key 與 value 存起來，下一步直接用，不重算；代價是每個 token 要幾十到幾百 KB，100K token 的對話就是十幾 GB，和權重同一個量級。Prefix cache 是把這塊存起來跨請求重用：兩個請求的開頭一樣（同一份 system prompt、同一段對話），第二個請求就不必重新 prefill 那一段。Agent 每一圈都重送前面的全部，所以它最依賴這件事。Slide 的結論：搬資料是瓶頸，不是算。

名詞KV cache：agent 的狀態為什麼這麼大

Attention 讓每個新 token 參考前面所有的 token。Model 把每個 token 在每一層的 key 和 value 存起來重用，這就是 KV cache。每個 token 的大小 = 2 × 層數 × KV head 數 × head 維度 × byte 數。

以 32 層、8 個 KV head、head 維度 128、BF16 的 8B model 為例，每個 token 要 128 KiB。100K token 的 session 約 13 GB，接近權重的 16 GB。Prefix cache 保留共同開頭的 KV cache 給下一個請求重用 p.32。

一張 GPU 放不下時要切到多張，GPU 之間就要通訊。Slide 列了四樣東西：平行化的種類（pipeline、tensor、expert、context，見註）；collective 函式庫，例如 NCCL 與 UCCL，負責 all-reduce 這類「所有 GPU 一起交換再加總」的操作；拓樸，同一台機器內走 NVLink，跨機器走 Ethernet 或 InfiniBand；RDMA，讓網卡直接讀寫對方機器的記憶體，繞過 CPU 和作業系統的 kernel。一張 H100 的數字給你量級：HBM（GPU 自己的記憶體）約 3.35 TB/s，NVLink 合計約 900 GB/s，PCIe 5.0 x16 單向約 64 GB/s，離運算單元越遠越窄。所以把 13 GB 的 KV cache 從 HBM 讀一遍約 4 ms，搬到另一張 GPU 要幾十 ms，搬到 CPU 記憶體要幾百 ms；第 3 段第 3 題的參考答案有完整的算式。

背景平行化的切法：一張 GPU 放不下時

Data parallelism 複製整個 model，各處理不同請求。Tensor parallelism 把每一層的矩陣切給多張 GPU；pipeline parallelism 按層切；expert parallelism 把 MoE 的 expert 分到不同 GPU；context parallelism 把一段很長的輸入切給多張 GPU 一起算。切得越細，GPU 之間交換的資料越多，所以 tensor parallelism 通常留在同一台機器內走 NVLink p.32。

差異 4：model 與 workload 變化快。Model 架構一年換好幾輪（p.33）：MHA、GQA、MLA、NSA、linear attention，每一種改的都是 attention 這一層，而 attention 決定 KV cache 的大小與形狀，所以 serving 系統的記憶體管理要跟著改。Workload 也在變，slide 列四種：多輪聊天（互動式，對延遲敏感）、解題（reasoning，輸出很長）、RAG（先檢索文件再回答，context 很長）、agent（context 長、prefix cache 關鍵、需要 routing 與 load balancing）。四種對系統的要求不同：聊天要第一個 token 快，解題要 decode 快，RAG 要 prefill 快，agent 要 cache 命中。Slide 底下的原則是雙向的：model 要配合硬體，硬體也要為 model 架構設計；A5 的「engine 與 agent 一起設計」是同一個精神。

背景MHA、GQA、MLA、NSA、linear attention：p.33 的五個名字差在 KV cache

MHA（multi-head attention）每個 head 各有自己的 key 與 value。GQA（grouped-query attention）讓幾個 query head 共用一組 key 與 value，KV cache 縮小好幾倍，Llama 3 用它。MLA（multi-head latent attention）把 key 與 value 壓成一個低維向量存，DeepSeek-V2 起用它。

NSA（native sparse attention）讓每個 token 只看前文的一部分，DeepSeek 2025 年提出。Linear attention 換掉 softmax，狀態大小固定，不隨長度成長。對 serving 的意義：KV cache 的大小與讀法各不相同，記憶體管理要各自適配。

差異 5：可靠性、電力與能源。GPU 的年故障率（AFR）約 9%，MTBF 約 50,000 小時（p.34）。單張看很可靠，但 16K 張一起用，平均每 3 小時就壞一張（50,000 ÷ 16,384 ≈ 3.05），所以故障是常態，不是例外：訓練要靠 checkpoint，serving 要能把請求搬走。電力：CPU 100–300 W，GPU 700–1,000 W，一台 server 裝 4–8 張，整台從 800 W 升到 6,000 W，約 8 倍。挑戰是電力波動：上千台 server 同時從閒置跳到滿載，機房的供電和電網都要承受得住。第 4 段的 fleet.py 用這些數字算一個 run 的風險；2.5 的本文延伸 x2 接著講長時間的 agent run 要怎麼活過這些故障。

名詞MTBF 與叢集故障：大叢集為什麼一直在壞

MTBF 是單一元件平均多久故障一次。假設每張 GPU 獨立故障，N 張的叢集平均每 MTBF ÷ N 就壞一張：50,000 小時 ÷ 16,384 張 ≈ 3 小時 p.34。年故障率 9% 換算是約每 6 小時一張，量級相同。

C · Agent：一台新的電腦，一個系統問題

2.4Agent：一台用自然語言編程、常常出錯的新電腦 p.36–38、p.49–50

這一章先給 agent 的定義和它的五步 loop，再問為什麼需要 agent（LLM 哪裡強、哪裡弱），然後把 agent 對到一台電腦的五個零件，最後用 slide 的補充表分清 agent、assistant 和 bot；2.5 看把它 serve 起來為什麼是系統問題。

定義與五步 loop。Slide 的定義（p.36）：agent 是一個自主的軟體系統，用一個 AI model 推理一個目標、使用外部 tool、執行多步動作，直到任務完成。拆開看有四個要素：有目標，不是一問一答；會用 tool，例如 API、資料庫、shell；多步；自己決定什麼時候算完成。Slide 把一圈拆成五步：

  1. Plan。把任務拆成子步驟。
  2. Act。呼叫外部 tool，例如打一個 API、查資料庫、跑一個指令。
  3. Observe。解讀 tool 回來的結果。
  4. Adapt。依新資訊修正計畫。
  5. Deliver。回傳最終結果。

p.36 的圖只有兩個箱子：agent（裡面是 LLM 的 reasoning 與 planning，加上 memory）送 action 給 environment，environment 回 observation。這和 L4 要寫成程式的 ReAct loop 是同一件事：model 每一圈只決定下一個 action，執行它、把 observation 放回去的是 model 外面的程式，這一章下面會叫它 harness。

為什麼需要 agent：LLM 是一台奇怪的電腦。p.37 引 Andrej Karpathy 2025 年的演講：LLM 是奇怪的電腦，同時超人又無能。超人的地方：記得大量事實、語言、pattern matching、寫程式碼、跨很多領域都能用。弱的地方：沒有持久記憶，每次對話從零開始；不能可靠地理解 context；會 hallucinate，也就是編出不存在的事實；不知道自己不知道什麼；對 security 與對抗性輸入沒有抵抗力。把兩張清單對起來看，agent 的周邊就是在補弱項：memory 補持久記憶（L6）；tool 與 observation 補「不知道」，讓它查而不是猜；測試補 hallucination，因為 tool 的結果會回到它眼前（L4）；權限與 sandbox 補 security（L2）。所以 agent 不是把 LLM 變聰明，是替它記、替它查、替它擋。

把 agent 對到一台電腦的五個零件。p.38 的主張：LLM 不只是一顆更聰明的 CPU，它是一種新的可編程電腦，programming model 和 failure model 都不同。Slide 把傳統電腦的五個零件逐一對到 agent：

逐層看。CPU 對 LLM：都在執行指令，但 LLM 的指令是自然語言，而且同一段指令每次可能走不同的路（2.3 的不確定性再加上 model 本身的隨機取樣）。RAM 對 context window：context 是這一次送給 model 的全部文字，context window 是它的容量上限，常見的大小是 200K token；滿了就要把東西換出去，L4 專講這件事。周邊對 tool：LLM 自己碰不到檔案與網路，要透過 tool，而 tool 的輸出又會回到 context 裡。OS 對 harness：harness 是 model 外面那層程式，決定什麼進 context、哪個 tool 可以自動跑、出錯了怎麼辦，L2 用 Claude Code 當例子拆它。Application 對 agent：一個特定任務的 agent 就是一支應用程式。兩個不同點裡，failure model 對系統設計的影響最大：OS 隔離 process 是因為 process 會壞，harness 隔離 LLM 的 action 也是因為它會錯，所以權限、sandbox、人工核准都跟著 tool 走。

2.5Agent serving：一次 inference 變成一條鏈，問題跨過整個 stack p.39–40、p.42–43

這一章先看 serve 一個 agent 和 serve 一個聊天請求差在哪裡，再把這條鏈放到六層的 stack 上，看 slide 列的十個新問題各落在哪一層，最後講為什麼 observability 是一等問題；2.6 定優化的目標。

從一次往返變成一條鏈。傳統的 LLM serving 是 request → inference → response：一個請求在 GPU 上跑一次 inference，回一段文字就結束，scheduler 只要把很多這樣的請求批次好。Agent serving 變成 infer → tool → infer → tool → retrieval → infer → …（p.39），第 1 段的第二張圖畫了這條鏈。每一步都等上一步，所以 critical path 跨過 GPU、CPU、storage、網路和外部服務；critical path 是決定總時間的那條最長的鏈。Slide 列了六個挑戰：

  • 步驟之間有依賴。下一次 infer 要等 tool 的結果回來才能開始。
  • 每一步的 latency 差很多。一次 infer 幾百毫秒，一次 grep 幾十毫秒，跑一輪測試可能幾分鐘。
  • 等 tool 時在 blocking。這段時間 agent 用不到 GPU，它的 KV cache 卻還佔著 GPU 記憶體。
  • 狀態快速成長。每一步都把 tool 的輸出加進 context，context 只會變長。
  • Concurrency 與 speculation。哪些步驟可以同時跑？能不能在結果回來前先猜下一步？
  • 失敗可能在軌跡的任何一點。GPU、tool、網路、外部 API，任何一個都可能出錯。

對照 2.3 的五個假設，這條鏈讓每一條更糟：時間更不可預測，因為步數也未知；狀態更大、活得更久，因為 context 跨幾十步一直在；失敗點更多，因為每一步都可能碰外界。Agent 把 serving 的問題乘上步數。

六層 stack，每一層有人在優化。p.40 把整個系統畫成六層，第 1 段的第一張圖照它重畫：最上面是 application 與使用者；接著是 agent 與 harness，負責 planning、context、memory、tools、subagents；再來是 model；model 下面是 serving system，做 batching、scheduling、routing、caching；再下面是 runtime 與 kernel，CUDA、Triton、collectives；最底是硬體，GPU、CPU、記憶體、網路、儲存。Harness 旁邊有一個「外部環境」：web、檔案、API、人，tool 就是通往它的路。Slide 另外標了三個跨層的箭頭：agent serving 橫跨 serving 以下幾層；systems 標在 scheduling 與 caching；hardware co-design 把 agent serving 連到硬體。傳統的 LLM serving 只看 model 以下三層；agent 把上面兩層接進來，問題就變成跨層：harness 怎麼組 context，決定 serving 層的 prefix cache 能不能命中，這是第 1 段圖右下角的例子。這門課的 Part I 講上面兩層，Part II 往下講。

看不到就不能優化：observability。p.43 說，對 agent 來說，分散式追蹤（distributed trace）變成一棵巢狀的軌跡。先講分散式追蹤：一個請求穿過好幾個微服務時，每個服務記下自己處理它的起訖時間和上一層是誰，這一段叫 span；把同一個請求的所有 span 串起來就是一條 trace，你可以看到時間花在哪個服務。Agent 的 trace 多了巢狀：一個 session 裡有很多 turn，一個 turn 裡有很多 agent step，一個 step 裡有一次 model request、一次 tool call、一個 tool result，有的 step 還會開一個 subagent，subagent 裡面又是一整棵。

Slide 的口號是「你無法優化你看不到的東西」。它是一等問題的原因很具體：p.44 的九個問題，每一題都要先量：batching 傷了 latency 多少，要有每一步的 model request 時間；一個 subagent 值不值得開，要有它那一棵子樹的 token 數與耗時；錢花在哪，要把 2.6 的每個成功任務成本拆回每一層。沒有 trace，這些數字都拿不到，優化就只能猜。L7 講評估、L8 講成本時，用的資料就是這棵樹。

本文延伸｜長時間的 agent run 需要可靠性工程不是 slide 的內容

對單一個 run，GPU 故障很少見：30 分鐘的 run 跑在 8 張 GPU 上，遇到故障的機率約 0.008%。但一天跑 10 萬個這種 run，就有約 8 個會遇到。Tool 逾時、API 錯誤更常見：每步 1% 出錯時，60 步全部順利的機率只有約 55%。

所以長的 run 要用分散式系統的老方法：每一步存 checkpoint，有副作用的 tool 要冪等（idempotent，重做一次結果不變），重試要有上限。L4 的「tool 預設冪等」和 L6 的「checkpoint 與回滾」處理同一個問題。第 4 段的 fleet.py 算這些數字。

2.6優化目標：throughput 是錯的目標，要算每個成功任務的成本 p.41、p.44

這一章先講元件層的指標為什麼不夠，再給 slide 的任務層指標和一個成本的例子，最後列出 p.44 的九個問題，當作整學期的檢查表。

元件指標各量一層。Serving 系統慣用的指標有四個（p.41）。TTFT（time to first token）是送出請求到第一個 token 出現的時間，大致就是 prefill 加排隊。TPOT（time per output token）是之後每個 token 的間隔，就是一步 decode 的時間。Tool-call latency 是一次 tool 來回的時間。GPU utilization 是 GPU 忙的比例。四個都有用，但各自只量一個元件或一層：TTFT 與 TPOT 量 model 與 serving，tool latency 量外部環境，使用率量硬體。Agent 的一個任務跨過所有層，所以沒有一個元件指標能告訴你任務有沒有變好。Slide 的用詞是「有用但不足」。

要優化的是任務成功。Slide 的關鍵句：throughput 對 agent 來說是錯的目標。正確的寫法是一個帶限制的最佳化：在 latency、cost、資源、reliability、security 的限制下，讓任務成功率最高。對應的指標也換成任務層級：

有用但不足（量一個元件）真正要優化的（量一個任務）
TTFT、TPOT任務成功率、accuracy
tool-call latency端到端的 latency
GPU utilization每個任務的 token 數
每個成功任務的花費（$）
每個成功任務的能耗

Slide 加了一句警告：tokens/sec 更高，agent 仍可能更慢、更貴。2.3 已經給了一半的原因：大 batch 讓整張 GPU 的 tokens/sec 升高，每個請求的每一步卻變慢，而 agent 有幾十步，每步慢一點加起來就慢很多。另一半是：一個繞遠路的 agent 生成更多 token，tokens/sec 的數字反而好看。本文延伸 x3 把這兩點展開，也講為什麼儀表板不該把它放最上面。

  1. p.30 · Prefill 與 decode

    Prefill 和 decode 各受什麼限制？為什麼一個請求的執行時間，事先無法預測？

    參考答案與重點複習

    答案：Prefill 受算力限制（compute-bound），decode 受記憶體頻寬限制（memory-bandwidth-bound）。執行時間取決於 model 輸出幾個 token。這個數字要等生成結束才知道，所以事先無法預測（p.30）。

    重點拆解

    一個請求分兩個階段。Prefill 一次讀進整段 prompt。每個權重從記憶體讀出來一次，就套用在 prompt 的全部 token 上。讀一次、算幾千次，所以 GPU 的運算單元很忙。

    Decode 一次只生成 1 個 token。每生成 1 個 token，就要把全部權重和這個請求的 KV cache 從記憶體再讀一遍。讀一次只算 1 個 token，運算單元大多在等資料。所以 decode 的上限是「每秒能搬多少 byte」，不是「每秒能算多少次」。

    執行時間難預測，因為 decode 要跑幾步由 model 決定：model 輸出結束 token 才停。同樣 2,000 token 的 prompt，回答可能只有 50 token，也可能有 5,000 token。所以 scheduler 很難決定先跑誰，也很難事先預留 KV cache 要用的記憶體。

    背景補充

    判斷 compute-bound 還是 memory-bound，看 arithmetic intensity：每從記憶體讀 1 byte，做幾次運算。GPU 也有自己的比值：算力 ÷ 頻寬。H100 約 989 TFLOPS ÷ 3.35 TB/s ≈ 295。Workload 的比值高於 295，瓶頸在算力；低於 295，瓶頸在頻寬。

    粗算一次。BF16 一個參數 2 byte；每個 token 對每個參數約做 2 次運算（一次乘、一次加）。Decode batch 1：讀 2 byte、做 2 次運算，比值約 1，遠低於 295。Prefill 2,000 token：同樣讀 2 byte，做 4,000 次運算，比值約 2,000，高於 295。

    Batching 把多個請求的 decode 併成一步。同一份權重讀一次，給 32 個請求用，比值就從 1 變成約 32。這是 serving 系統一定要做 batching 的原因。但每個請求的 KV cache 各是一份，不能分攤，所以 batch 不能無限加大。

    兩個階段也對應兩個使用者感受得到的指標。TTFT（time to first token）主要由 prefill 決定；TPOT（time per output token）由 decode 決定。Prompt 很長時 TTFT 變長；回答很長時總時間變長。

    常見誤解

    「GPU 使用率 100%，代表算力用滿了。」不一定。nvidia-smi 的 utilization 只代表這段時間有 kernel 在跑，不代表運算單元在忙。Decode 時 GPU 看起來很忙，運算單元其實大多在等記憶體。

    帶走這幾點
    1. Prefill：讀一次權重，算很多 token → 算力是瓶頸 → 影響 TTFT。
    2. Decode：每個 token 都重讀權重與 KV cache → 頻寬是瓶頸 → 影響 TPOT。
    3. 輸出長度事先未知，所以執行時間和記憶體用量都無法預估，scheduling 因此變難。

    相關：註〈Prefill 與 decode〉、〈KV cache〉。進階題第 1 題用數字再算一次。Part II 的 serving 基礎（10/19–10/21）會正式展開。

  2. p.31 · 不確定的運算

    同一個 prompt，為什麼可能得到不同的輸出？Batch size 在這裡扮演什麼角色？

    參考答案與重點複習

    答案：浮點數加法沒有結合律，加總順序一變，結果就差一點點。Matmul 第 7 位小數的變動，就可能換掉下一個 token，後面的文字全部跟著改變；slide 稱為蝴蝶效應（p.31）。Batch size 是 slide 列出的 runtime 誤差來源：batch size 改變時，GPU 可能換 kernel 或換切法，加總順序跟著改變（p.31）。

    重點拆解

    浮點數只有固定的位數，每做一次加法就捨入一次。所以 (a + b) + c 和 a + (b + c) 可能差在最後一位。Matmul 的每個輸出都是幾千個乘積的總和。GPU 把這個總和切成小塊平行加總，再把各塊合併。切法不同，捨入的時機就不同，總和的最後幾位也不同。

    誤差本身很小，p.31 也說近似計算可以接受。麻煩在 decode 會放大它。Model 每一步替每個候選 token 打分數（logit），temperature 0 時選最高分。前兩名很接近時，最後幾位的差異就能讓它們互換。換掉一個 token 之後，後面每一步讀到的 context 都不同，整段文字就此分岔。

    Slide 把誤差來源分成三類（p.31）。Runtime：warp 與 block 的排程、記憶體順序、async stream、batch size。Software：乘加合成一個指令（FMA）或分開算、autotuning、subnormal 數。Hardware：用 CUDA core 還是 tensor core、Hopper 的 FP8 與 Blackwell 的 micro-scaling 格式。

    背景補充

    為什麼是第 7 位？FP32 的有效位數約等於 7 位十進位數字。GPU 通常用 FP32 累加 BF16 的乘積，所以第 7 位附近的差異，正好是捨入誤差的大小。

    四類來源裡，batch size 對使用者影響最大。Thinking Machines 2025 年的文章指出：同樣的輸入、同樣的 batch 重跑，GPU 的結果通常逐 bit 相同。真正的變數是伺服器負載：別人的請求多寡決定 batch size，kernel 再依矩陣形狀選切法。例如 batch 小時，kernel 把加總的維度切開，讓更多核心分工（split-K）。他們用 Qwen3-235B 在 temperature 0 跑 1,000 次，得到 80 種輸出；前 102 個 token 全部相同，第 103 個開始分岔。改用不受 batch size 影響（batch-invariant）的 kernel 後，1,000 次完全相同，代價是變慢。

    常見誤解

    「Temperature 0，輸出就固定。」Temperature 0 只固定選法：每一步選最高分。它不固定分數本身。分數由 GPU 算出，會隨 batch size 改變。要可重現，伺服器要用 batch-invariant 的 kernel；做不到時，測試的寫法就要改（進階題第 3 題）。

    帶走這幾點
    1. 浮點數每次運算都捨入 → 加總順序一變，總和的最後幾位就變。
    2. Batch size 一變 → kernel 換切法 → 加總順序改變。Batch size 由伺服器負載決定，使用者控制不了。
    3. 前兩名 logit 很接近時，一點誤差就換掉 token → 之後的 context 全部不同 → 整段輸出分岔。

    相關：註〈浮點數沒有結合律〉、本文延伸〈不確定性改變團隊測試 LLM 功能的方式〉、動手試試的 fp_order.py、延伸閱讀的 Thinking Machines 文章。進階題第 3 題把這一點帶到 CI 測試上。

  3. p.32–34 · 狀態與故障

    Slide 說 AI 系統的瓶頸常在哪裡？16K 張 GPU 的叢集，多久壞一張？

    參考答案與重點複習

    答案：瓶頸常在搬資料（data movement），不在計算。原因是狀態很大：權重從幾 GB 到幾 TB，KV cache 每個 token 要幾十到幾百 KB（p.32）。16K 張 GPU 的叢集約每 3 小時壞一張（p.34）。Slide 列出每張 GPU 的年故障率（AFR）9%、MTBF 50,000 小時；叢集的故障間隔約等於 MTBF ÷ GPU 數。

    重點拆解

    先看狀態有多大。權重從幾 GB 到幾 TB；KV cache 每個 token 要幾十到幾百 KB，context 越長越大（p.32）。B1 講過，decode 每一步都要讀完權重和 KV cache。所以 GPU 的時間常花在等資料，不是在計算。

    一張 GPU 放不下時，model 要切到多張 GPU：pipeline、tensor、expert、context parallelism（p.32）。切開之後，GPU 之間每一層或每一步都要交換資料。交換靠 NCCL、UCCL 這類 collective 函式庫，走機器內的 NVLink，或機器之間的 Ethernet、InfiniBand。RDMA 讓資料直接寫進另一台機器的記憶體，不經過對方的 CPU 和 OS kernel（p.32）。Prefix cache 在請求之間重用 KV cache，省下重算；代價是這些 KV cache 要有地方放、也要搬得過去。

    故障的算法不同。一張 GPU 的 MTBF 是 50,000 小時，約 5.7 年。假設每張 GPU 獨立故障，N 張裡「任何一張」壞掉的頻率是單張的 N 倍。所以 50,000 ÷ 16,384 ≈ 3.05 小時壞一張，一天約 8 次（p.34）。改用 AFR 9% 算：8,760 小時 ÷（0.09 × 16,384）≈ 5.9 小時。兩種算法差約 2 倍，量級相同。同一頁也提到耗電：一台 server 從 800 W 升到 6,000 W。

    背景補充

    搬資料為什麼慢？離 GPU 的運算單元越遠，頻寬越小。以 H100 為例：HBM 約 3.35 TB/s，NVLink 合計約 900 GB/s，PCIe 5.0 x16 單向約 64 GB/s。用〈KV cache〉的例子：100K token 的 session 約有 13 GB 的 KV cache。在 HBM 裡讀一遍約 4 ms；從 CPU 記憶體經 PCIe 搬回 GPU 約 0.2 秒。所以 KV cache 放在哪一層（p.44 第 3 題），直接變成 latency。

    每 3 小時壞一張，和 Meta 公開的 Llama 3 訓練紀錄一致：16K 張 H100，54 天內有 419 次非預期中斷，平均約 3 小時一次；約 78% 確認或疑似是硬體問題，GPU 與 HBM 記憶體佔最多。大型訓練是同步的，每一步所有 GPU 互相等，所以一張壞掉就可能要重啟整個 job。他們靠縮短 checkpoint 與重啟的時間，讓有效訓練時間維持在 90% 以上。

    常見誤解

    「MTBF 50,000 小時，代表每張 GPU 可以用 5.7 年才壞。」MTBF 是平均值，描述一大群 GPU 的故障頻率，不是每一張的壽命；單張可能第一個月就壞。叢集只看總數：16,384 張一起跑，平均每 3 小時就有一張壞。

    帶走這幾點
    1. 狀態大（權重 GB 到 TB，KV cache 每個 token 幾十到幾百 KB）→ 瓶頸在搬資料，不在計算。
    2. 叢集故障間隔 ≈ MTBF ÷ GPU 數：50,000 ÷ 16,384 ≈ 3 小時。
    3. 單張 GPU 很少壞，大叢集卻一直在壞 → 系統要把故障當常態設計：checkpoint、快速重啟。

  4. p.38–39 · Agent 是系統問題

    把 agent 比成電腦，harness 是什麼？Agent 的流程和傳統 serving 差在哪裡？

    參考答案與重點複習

    答案：Harness 對應 OS。其他對應：LLM 是 CPU，context window 是 RAM，tool 是周邊裝置，agent 是 application（p.38）。傳統 serving 是 request → inference → response，一個請求只跑一次 inference。Agent 是 infer → tool → infer → tool → retrieval → infer → … 的長鏈，跨過 GPU、CPU、storage、network 與外部服務；下一步要等上一步的結果，所以每一步的延遲都加進整個任務的時間（p.39）。

    重點拆解

    LLM 本身只做一件事：讀進一段文字，產生下一段文字。它不能自己讀檔或跑指令，也不記得上一步。Harness 補上其餘的工作：決定每一步的 context 放什麼，解析 model 輸出的 tool call，執行 tool，再把結果寫回 context。這就是 OS 的角色：程式透過 system call 使用硬體。

    Slide 強調這是一種新的電腦，有自己的 programming model 與 failure model（p.38）。程式用自然語言寫，同一個任務每次可能走不同路徑。LLM 出錯是常態，所以 harness 要像 OS 一樣做隔離與權限控制：先檢查 tool call，再決定要不要執行。

    第二個子問題看 p.39。傳統 serving 的請求彼此獨立，一次 inference 就結束。Agent 的每一步都依賴上一步的結果，所以整條鏈都在 critical path 上。Slide 列出這帶來的難題：步驟之間有相依、每步的延遲變化很大、等 tool 時卡住、狀態快速變大、平行與預先執行（concurrency、speculation）、軌跡上任何一步都可能失敗（p.39）。

    背景補充

    OS 類比可以再往下推。RAM 有限，OS 把不常用的 page 換到 disk。Context window 也有限，harness 要決定留什麼、壓縮什麼、存到外部檔案。L4 的 compaction 與 L6 的 memory 就在做這件事。MemGPT（2023）把這個類比做成系統：仿照 virtual memory 搬資料。

    從 serving 系統看，傳統 serving 收到的是互不相關的請求。Agent 的請求其實屬於同一個任務：開頭相同，而且一個接一個。Serving 系統不知道這層關係時，可能在 agent 等 tool 時清掉它的 KV cache，下一步只好重做 prefill。p.42 的 prefix caching 與 dependency-aware scheduling 從這裡來；p.44 第 4 題「同一個 agent 的請求怎麼排程」也是。

    常見誤解

    「Harness 只是 API 外面的一層薄 wrapper，agent 好不好全看 model。」Harness 決定 model 每一步看到什麼、能用哪些 tool、出錯時怎麼處理。同一個 model 換一個 harness，任務成功率可能差很多。所以比較 model 時要固定 harness。

    帶走這幾點
    1. LLM ≈ CPU，context window ≈ RAM，tool ≈ 周邊裝置，harness ≈ OS，agent ≈ application。
    2. Harness 像 OS：管 context、執行 tool call、做權限與隔離，因為 LLM 出錯是常態。
    3. 傳統 serving 一個請求一次 inference；agent 是一條相依的鏈 → 延遲、狀態、失敗都沿著鏈累積。

    相關：核心觀念〈Agent：一台用自然語言編程、常常出錯的新電腦〉、〈Agent serving：一次 inference 變成一條鏈，問題跨過整個 stack〉、第 1 段的第二張圖；L2 一個 prompt，很多圈 loop、L2 產品差異在 harness、L4 評估時要固定 harness、L8 Critical path。進階題第 1 題會算 batching 讓一條長鏈多花多少時間。

  5. p.41 · 要優化什麼

    Slide 說哪個目標不適合 agent？要改看哪些指標？

    參考答案與重點複習

    答案：Throughput（tokens/sec）不適合當 agent 的目標：tokens/sec 高，agent 仍可能更慢、更貴（p.41）。目標是在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。TTFT、TPOT、tool-call latency、GPU 使用率「有用，但不夠」；要改看任務成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能（p.41）。

    重點拆解

    p.41 把目標寫成一個有限制的最佳化問題：要最大化的是任務成功率；latency、cost、resources、reliability、security 是限制。限制的意思是「不能超過上限」，不是「越低越好」。成功率再高，延遲超過使用者願意等的時間，這個設計仍然不合格。

    四個元件指標各量一層。下表列出每個指標漏掉什麼。

    元件指標量的是看不到
    TTFT一次請求多久出現第一個 token一個任務有幾十次請求，還有 tool 與排隊的時間
    TPOTDecode 每生成一個 token 要多久生成了幾個 token，那些 token 是否必要
    Tool-call latency一次 tool 執行多久這個 tool 該不該呼叫，總共呼叫幾次
    GPU 使用率GPU 有沒有在跑 kernel這些運算有沒有讓任務成功

    任務指標的單位是「一個任務」，不是一個請求或一個 token。所以量測時要知道哪些請求屬於同一個任務。p.43 說 agent 的 trace 是巢狀的：session → turn → agent step → model request、tool call、tool result。沒有這層結構，只看得到一堆互不相關的請求。p.43 的結論是：看不到，就無法優化。

    背景補充

    Serving 領域也走過同一條路。DistServe（OSDI 2024）提出 goodput：只計算 TTFT 與 TPOT 都達到目標（SLO）的請求。Agent 的任務指標再往上一層：看整個任務有沒有成功。

    每個成功任務的花費可以拆成三個因子（見下面的例子）。Serving 的 throughput 只動得到其中一個：每個 token 的成本。另外兩個由 agent 的行為決定：繞路越多，token 越多；失敗越多，成功率越低。

    例子

    每個成功任務的花費 =（每個任務的 token 數 × 每個 token 的成本）÷ 成功率。假設一個任務用 200K token，每百萬 token $3，成功率 40%：200K × $3 ÷ 1M = $0.60，÷ 0.4 = $1.50。三種改法都能降到 $0.75：每個 token 的成本減半；token 數減半；成功率提高到 80%。Throughput 只負責第一種。

    常見誤解

    「Tokens/sec 變高，agent 就變快。」Tokens/sec 通常指整張 GPU 的總量。看動手試試的 decode_bound.py：batch 從 1 加到 32，整張 GPU 從 97 升到 1,543 tok/s，每個請求卻從 97 降到 48 tok/s。Agent 的每一步都在 critical path 上，所以它反而變慢。

    帶走這幾點
    1. Agent 的目標：在 latency、cost、resources、reliability、security 的限制下，讓任務成功率最高。Throughput 不是目標。
    2. TTFT、TPOT、tool-call latency、GPU 使用率各量一個元件 → 有用，但看不到整個任務。
    3. 改看任務指標：成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能。要算得出來，trace 要能把請求歸到同一個任務（p.43）。

    相關：核心觀念〈優化目標：throughput 是錯的目標，要算每個成功任務的成本〉、本文延伸〈Tokens/sec 會把 agent 的優化帶錯方向〉；L7 一個成功率不夠、L8 成本是一串乘數。進階題第 2 題請你替 coding agent 設計這組指標。

自我檢查

Prefill 和 decode，哪一個受算力限制？為什麼 decode 不能把很多 token 併成一次運算？

Prefill。Prompt 的 token 全部已知，可以平行計算，權重讀一次就用在幾千個 token 上。Decode 的第 n 個 token 要等第 n−1 個生成後才能算。

Agent A 每次嘗試花 $0.30，成功率 40%。Agent B 每次花 $0.50，成功率 80%。哪一個的每個成功任務成本較低？

B。A：$0.30 ÷ 0.4 = $0.75。B：$0.50 ÷ 0.8 = $0.625。只看每次呼叫的價格，會選錯。

為什麼 agent 比單輪的聊天更需要 prefix cache?

Agent 每一步都重送整段 context，開頭完全相同。Prefix cache 保留開頭的 KV cache，下一步只要 prefill 新增的部分。Context 越長，省得越多。

解答：（1）每個請求約剩一半；整張 GPU 約 16 倍。KV 讀取不能分攤，所以不是 32 倍。（2）不行：16 + 32 × 4.3 ≈ 153 GB，超過容量。（3）每一列約快 2.1 倍。只要還受頻寬限制，速度就和頻寬成正比。

算叢集多久壞一張 GPUp.34

用 slide 的數字：MTBF 50,000 小時、16,384 張 GPU。假設每張 GPU 獨立故障，間隔服從指數分布。

練習：（1）叢集多久壞一張？一天幾次？（2）MTBF 換算成 AFR 是多少？和 slide 的 9% 一致嗎？（3）一個 run 遇到 GPU 故障的風險，和每步 1% 出錯、共 60 步的風險，哪個大？

解答：（1）約 3.05 小時一次，一天約 8 次。（2）約 16%，和 9% 不一致；用 9% 算是約 5.9 小時一次，量級相同。（3）GPU 故障約 0.008%；每步 1% 出錯時，60 步全部順利只有約 55%。對單一個 run，tool 與 API 的失敗才是主要風險。

  1. 選讀Software Is Changing (Again)Andrej Karpathy · 演講影片 · 2025 · 約 40 分

    L1 p.37 引用的影片。把 Software 1.0／2.0／3.0 的分類接到 agent 時代。

    導讀L3 會正式指定這支影片，可以留到那時候讀。先看也可以：只看 autonomy slider 那一段。

  2. 推薦Defeating Nondeterminism in LLM InferenceThinking Machines · 部落格 · 2025 · 約 15 分

    p.31 的延伸：同一個 prompt 跑兩次，結果為什麼不同。原因在 batch size 與浮點運算順序。

    導讀對照 2.3 的註〈浮點數沒有結合律〉。問大家：這對「可重現的 eval」意味著什麼？

    摘要讀約 3 分；原文約 15 分

    一句話：temperature 0 仍得到不同輸出，主因是 kernel 缺少 batch invariance：你的請求和多少別人的請求一起算，reduction 順序就跟著變。作者改寫三個 kernel，1000 次 completion 從 80 種變成 1 種，代價是時間變成 1.6 到 2.1 倍。

    跟這堂課的關係

    〈AI workload：打破傳統系統的五個假設〉（p.30–34）說同一個 prompt 可能得到不同輸出，這篇是那一條的全文版。Slides p.31 把 batch size 與 warp scheduling 並列為 runtime 層的來源；這篇說 concurrency 無關，batch size 才是主因，這點和 p.31 的 takeaway「approximate computing 可以接受」方向不同：作者認為可重現做得到，也值得做。〈浮點數沒有結合律〉寫了機制，〈不確定性改變團隊測試〉說 temperature 0 不保證可重現；這篇補上修法與數字。

    壓縮後的重點

    1. 常見的「concurrency + 浮點數」解釋不成立。這個說法把加總順序的變化歸給 GPU thread 的完成順序與 atomic add。作者指出 LLM 的 forward pass 通常一個 atomic add 都沒有。同一個 matmul 用同樣資料重跑，結果 bitwise 相同。
    2. 真正的原因是 kernel 不具 batch invariance。同一個請求在 batch 1 和 batch 32 裡算，kernel 換切法，reduction 順序跟著變。Batch size 由伺服器當下的負載決定，使用者看不到。所以系統整體是確定的，從單一使用者看卻是隨機的。
    3. 三個有 reduction 的 kernel 要改，原則是切法不隨 batch size 變。RMSNorm：每個 batch element 固定交給一個 core，小 batch 時寧可讓 core 閒置。Matmul：所有形狀用同一組 kernel 設定，不用 Split-K，約比 cuBLAS 慢 20%。Attention：先更新 KV cache 與 page table 再進 kernel；沿 KV 切塊時固定每塊大小（例如 256），塊數隨 KV 長度變。
    4. 數字：80 種變 1 種。Qwen3-235B-A22B-Instruct-2507，prompt 是「Tell me about Richard Feynman」，temperature 0，1000 次各 1000 token，原本有 80 種不同的 completion，最常見的出現 78 次。前 102 個 token 全部相同，第 103 個開始分歧：992 次寫 Queens, New York，8 次寫 New York City。改用 batch-invariant kernel 後，1000 次完全相同。
    5. 效能代價：時間 1.6 到 2.1 倍。單張 GPU 跑 Qwen-3-8B，1000 條序列，每條輸出 90 到 110 token。vLLM 預設 26 秒；未優化的 deterministic 版 55 秒；改良 attention kernel 後 42 秒。
    6. 副產品：真正的 on-policy RL。Sampler 與 trainer 數值不一致時，on-policy RL 會悄悄變成 off-policy。Bigmath 上的實驗：不做 importance weighting，reward 中途崩潰；做了之後 KL 約 0.001。兩端 bitwise 一致時，KL 一直是 0。

    原文怎麼讀

    • 可以跳過：「The original sin: floating-point non-associativity」一節，slides p.31 與本頁 2.3 的註已經講過。「Implementation」只說用 vLLM 的 FlexAttention backend 加 torch.Library 換 kernel。
    • 值得看原文：「Batch invariance and determinism」一節，解釋每個 kernel 都確定、endpoint 仍不確定的原因。「Batch-invariant attention」的 fixed split size 圖：KV 長度 1000 切成 256、256、256、232。「True on-policy RL」的三條 KL 曲線。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 15 分。
    別誤讀

    「浮點數不可結合，所以 GPU 上的 LLM 本來就不可能可重現。」作者反對這種放棄。單一 kernel 重跑的結果 bitwise 相同；會變的只有 batch size 帶來的 reduction 順序，固定它就可重現。但這只在你控制 serving stack 時成立；第三方 API 的 batch 你管不到。
