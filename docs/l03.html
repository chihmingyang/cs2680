先看這裡

放大產能只有三個方向：同時開更多 agent、把工作交給另一個 context、讓一個 agent 跑更久。每個方向只買到一樣東西，而且都有上限。所以這堂要帶走的是一個判斷：該不該加、能加多少、上限卡在哪裡。

  • 加 agent 有上限。不能平行的部分佔兩成時，16 個 agent 只快 4 倍，過了某個點還會變慢；能管幾個，最後由你 review 的速度決定。先縮短不能平行的部分，比加 agent 有效。
  • 驗證決定你能放手多久。Agent 不確定，周圍的系統要可靠：終點要能檢查，判斷做完的不能是做事的 model，自主程度要配合風險。
  • 選法看計畫在誰手上，改行為看誰保證。只要結果用 subagent，要討論才用 team，對話協調不了才用 workflow。要保證的事交給 hook，要判斷的留給 model；省 token 先看帳單，輸入方向才是大宗。

建議先讀 L2 和 L4：後面兩個案例章接 L2 講的擴充機制，全篇一直用到 L4 講的 context 代價；沒時間讀，第 6 章開頭的「前情」註有 L4 的摘要。

1放大的三個軸：每一種只買到一樣東西

L2 和 L4 講一個 agent 怎麼運作。這堂問下一個問題：手上的事比一個 agent 做得完的多，要怎麼放大？先定兩個名詞。Session 是你打開 Claude Code 之後的一段對話，有自己的 context window。Agent 在這堂裡就是一個在跑的 session，或是 session 派出去的小 agent。兩個 agent 的 context 互不相通，L5〈根本的限制〉會講這件事帶來的後果。放大有三個方向，每個方向只買到一樣東西：

名詞Throughput、latency、critical path：量「快」的三個字

Throughput 是單位時間做完多少事，例如一天 merge 幾個 PR。Latency 是一件事從開始到做完要等多久。平行提高 throughput，不會降低單一任務的 latency：10 個 session 一天做完 10 件事，每一件還是要花原本的時間。

Critical path 是一串必須依序做、不能平行的步驟裡最長的那一條。規劃要先做完才能派工，所有子任務做完才能整合。整件事的最短時間由它決定，再多 agent 也壓不下去；第 2 章用 Amdahl's law 算這件事。

同時用更多 agent 的做法看起來很多，分法只有一條：計畫在誰手上。它決定誰負責派工、誰負責整合，也決定這個做法撐得到幾個 agent。官方文件比較這幾種做法時，用的也是這一條軸：

2上限：16 個 agent 不會快 16 倍

多派幾個 agent，工作會快多少？直覺是 16 個快 16 倍，實際上不會。一件工作裡總有些步驟只能一件一件做：規劃要先寫完才能派工，16 份結果交回來要有人合併，合併完還要 review。這些步驟花的時間，派再多 agent 也不會變短。IBM 的電腦架構師 Gene Amdahl 在 1967 年提出這個論證，當時大家在爭論多處理器的電腦值不值得做。原本講 CPU，把處理器換成 agent，道理相同。

算一次。假設一個 agent 從頭做到尾要 100 分鐘。其中 20 分鐘只能一個 agent 做：規劃 5 分鐘、合併 10 分鐘、review 5 分鐘。剩下 80 分鐘是改 300 個彼此無關的檔案，可以拆開。把總時間 100 換成 1，就是這條式子：

三個推論。下圖把兩種 s 畫在一起：

  1. 加速有上限，等於 1 ÷ s。n 很大時，p ÷ n 趨近 0，總時間只剩 s。所以 s 是 20% 時上限 5 倍，10% 時 10 倍。
  2. 每多一個 agent，省下的時間越來越少。從 1 個加到 4 個省 60 分鐘，4 個加到 16 個省 15 分鐘，16 個加到 64 個省 3.75 分鐘。費用卻大約跟 agent 數成正比，所以 16 個 agent 只快 4 倍時，平均每個只發揮 25%。
  3. 要更快，先縮短不能平行的部分。同樣 16 個 agent，s 從 20% 降到 10%，加速從 4 倍變成 6.4 倍；s 不動、agent 加到 64 個，只到 4.7 倍。

縮短循序的部分比加 agent 有效。在 agent 的工作裡，就是讓那些只能一個人做的步驟變小：

  • 規劃。計畫先寫成 script 或 ticket，不在對話裡邊聊邊規劃（第 7、8 章）。
  • 合併。拆給每個 agent 自己做：各自 pull、解 conflict、push，不留到最後一次合併全部（第 7 章）。
  • Review。盡量交給自動測試，不等一個人從頭讀到尾（第 3、4 章）。

真實情況更差：協調也要時間。Amdahl 假設不能平行的 20 分鐘是固定的。但 agent 一多，merge conflict 變多，互傳的訊息也變多，循序的部分會隨 n 變大，過了某個 n 總時間還會回頭變長：

L5〈拆多細〉把這件事寫成四項相加的估算式，也算出拆成幾份最快。反過來，工作量不固定時結果會好一些：John Gustafson 在 1988 年指出，機器變多時人通常拿它去做更大的工作，規劃和合併沒有變多少，能平行的部分卻大了好幾倍，s 就變小。所以放大最划算的是又大又整齊的工作，例如掃整個 codebase、500 個檔案的搬遷。

任務切不開，加 agent 也沒用。這是 Amdahl 的極端情況：能平行的部分變成 0。Anthropic 的 Nicholas Carlini 讓 16 個 agent 平行寫一個 C compiler（第 7 章），他的報告寫到，編譯 Linux kernel 時，每個 agent 都修同一個 bug，再互相覆蓋彼此的修改：

一般原則是：平行需要獨立的子任務，也需要獨立的進度訊號。只有一個大測試失敗時，先把它拆成很多小訊號，再考慮加 agent。上面的算式還漏了一段 s：人 review 的速度，下一章算它。

3人：能管幾個 agent，由你 review 的速度決定

上一章的算式漏了一段：agent 交出來的東西，最後要有人看。講者引用的田野報告都指向同一個變化：人從動手的人，變成規劃、委派、監看、review、整合的人。這一章問這個角色的上限，你能同時管幾個 agent。課程沒有算這件事，下面的算式是本文補的。

  • 讓機器先篩。測試和可檢查的終點攔下壞的，人只看通過的（第 4 章）。
  • 把機械的規範變成檢查。Lint、型別、pre-commit 能抓的，不佔人的眼睛（第 8 章的 retro）。
  • 只讓必須看的東西到人面前。訊息短到能決定下一步就好（第 10 章）。

4終點：自主程度由能不能驗證決定

上一章的結論是：要多開 agent，就要讓機器先替你篩一遍。這一章講這件事的原理與做法。講者把這種寫程式的方式叫 Programming 3.0，用「人寫什麼」分三代：

新的不確定性有四個來源：自然語言的語意、檢索的漂移（索引更新、context 截斷）、model 的取樣、agent 和 tool 的迴圈。它們都集中在產生程式的階段；程式產生之後通常是確定的，除非執行時又呼叫 model 或 tool。所以講者的結論是兩句，這也是整堂最重要的原則：

  • 不要期待 agent 是確定的，讓它周圍的系統可靠。Hook、可檢查的終點、lock file、測試，都是周圍系統的零件。
  • 自主程度要配合風險。自主越高，不確定性和風險越高。
查閱Karpathy 的 Software 3.0，和不確定性早就存在的那張表

Karpathy 用「程式是什麼」分三代：1.0 程式是原始碼，人用 Python 或 C++ 寫；2.0 程式是神經網路的權重，人收集資料再訓練；3.0 程式是 prompt，人用自然語言寫，LLM 執行。講者用「人寫什麼」分，名字像，分法不同。兩種分法導向同一個工程問題：哪一塊用確定的程式，哪一塊交給 model。

周圍的系統怎麼做。講者的做法分三組，順序就是一件工作的前、中、後：

  1. Define。先把假設寫出來；有歧義的地方讓 model 先確認再動手。
  2. Control。提案和執行分開，驗證過才 commit。寫結果，不寫 prompt：需求、不變量、限制和驗收測試。
  3. Verify。把產生和驗證的迴圈收緊，便宜而頻繁的檢查勝過最後一次昂貴的 review。

5手動平行：worktree 只隔離檔案

最簡單的放大是自己開好幾個 session，一個 session 做一件事。問題是它們在同一個 repo 裡會互相踩：一個 session 改到一半的檔案，另一個 session 會看到。Git worktree 解決這件事。一般的 repo 只有一個工作目錄，一次只能站在一個 branch 上；worktree 讓一個 .git 同時掛好幾個工作目錄：

它只隔離檔案。同一個 branch 不能同時在兩個 worktree 裡 checkout。新目錄裡沒有 .env、node_modules 這類不在 git 裡的檔案，要重新裝，或在 .worktreeinclude 列出要複製的檔。Port、資料庫、外部服務還是共用的，兩個 session 都跑測試資料庫時一樣會撞。

撐到哪裡。3 個 session 你還記得住計畫，20 個 session 你需要一個分身。原因有四個，接下來兩章的做法就是把它們交給別人：

  • 計畫在你腦中。每一次交接都靠你。
  • Session 之間看不到彼此。發現要靠你搬過去；現在有 cross-session messaging 可以讓 Claude 代傳，但什麼時候該傳仍是你決定。
  • Branch 要你來 merge。順序和衝突都是你的。
  • 沒有人把整件事記下來。下次不能重跑。

Slide 之後多了 claude agents，它解決的是「看不過來」：一個畫面列出誰在等你。計畫和 merge 還是你的，所以第 3 章的上限不變。

主幹也在動。Worktree 把別人的 commit 擋在目錄外面，但你做事的時候它們還是進了 main。SWE-Shift 量過做到一半 repo 變了會怎樣：最好的系統，成功率從 67.35% 掉到 24.79%。這是挑過的場景，不是日常的故障率；但 teammate 的 code 被順手刪掉是會發生的事。本文查證之後的建議有三條：

  • 別人改了檔案。執行期用 worktree，合併期換一個新 context，並把原因寫進 commit message 或計畫檔。
  • 需求、tool、環境變了。Worktree 擋不住，要在流程裡排固定的重讀節點。
  • Merge 之後多查一件事。不只跑原本的測試，還要查 main 新加的東西還在不在。

6Subagent：換到乾淨的主對話，代價是摘要有損

Subagent 是一個專門的小助手，有自己的 context window、tool 清單和權限。主 agent 把一個有邊界的任務交給它，它在自己的 context 裡做完，只交回一段摘要。這很像函式呼叫：函式有自己的區域變數，return 之後就釋放，呼叫者只拿到回傳值。

它買到的第一件事是乾淨的主對話，因為主對話每一圈都重送整個 context，少放 30 份檔案，之後每一圈都省。另外四個理由：

  • 限制。只給它讀的 tool，它就改不了檔案。
  • 重用。同一份定義跨專案、跨團隊用。
  • 平行。互相獨立的子任務同時跑，總時間等於最慢的那一個。
  • 省錢。簡單的任務指定便宜快的 model。
前情Context 的代價與四種管理策略（L4）：這堂一直用到的四個名詞

Context 是每一圈送進 model 的全部文字：system prompt、tool 定義、對話歷史、每一筆 tool 結果；上限叫 context window。L4 說它有三種代價。錢：model 沒有記憶，每一圈都要把整個 window 重送一次，一份 786 行的 log 進了 context，之後每圈都再付一次。延遲：prompt 越長，model 讀得越久。注意力：window 越滿，model 越難找回中間的資訊。

L4 給了四種管理策略，由無損排到有損：

  1. Admission。在內容進 window 之前把關，只放需要的部分（截斷、整形、交給 subagent）。
  2. Offloading。把內容放在 window 外面，只留一個 handle，要用再讀回。
  3. Transformation。把舊的或重複的 tool 結果換成一行占位文字。
  4. Compaction。用 LLM 把舊歷史寫成一段摘要換掉原文，有損又不可逆，所以排在最後。Claude Code 的 /compact 就是這一種。

這堂用到的地方：subagent 和第 9 章的 proxy 是 admission，caveman_compress 回 handle 是 offloading，第 8 章的 hook 在 compaction 之後重新注入規則，是在補 compaction 丟掉的東西。細節見 L4〈Context 的成本〉與〈Context 管理〉。

代價：兩個方向都會掉東西。往回的方向，摘要是有損壓縮：30 份文件換成一頁結論，所以委派時要指定回報格式，例如「每個問題附 file:line」。往去的方向，subagent 會讀 CLAUDE.md，但看不到你的對話歷史，你在對話裡講好的規則要寫進任務訊息；它也要從零收集 context，多一段延遲。例外是 fork（/subtask）：它繼承整段對話，適合側面的問題，拿不到乾淨 context 的好處。

查閱Plugin 的結構、manifest、三個 scope 與指令

Plugin 是整個 repo 資料夾，不是最上面那個 .claude-plugin/。.claude-plugin/ 只放一個叫 manifest 的檔。Manifest 是「說明檔」的通稱：一份給工具讀的 JSON 或 XML，告訴工具這個資料夾是什麼、叫什麼、哪一版，npm 的 package.json、Chrome extension 的 manifest.json 都是。Skill、hook、command 放在 repo 根目錄的 skills/、hooks/hooks.json、commands/，Claude Code 認得這些固定的位置，所以 manifest 不必列出檔案清單；放在別的位置才要在 plugin.json 指過去。Caveman 就把 hook 直接寫在 plugin.json 裡，mattpocock 則在裡面列 27 個 skill 的路徑。

  • Ubiquitous language。它來自 Eric Evans 的 Domain-Driven Design：開發者和領域專家共用同一套詞，程式碼裡的名字也用它。這套 skill 把它寫成 GLOSSARY.md。

9Caveman：省 token 先看帳單，輸入方向只有 proxy 管得到

前一章改的是 agent 做事的順序，這一章改的是 token 的進出。Caveman 是一個專門省 token 的 plugin，把第 8 章那張表的機制全用上，還多一個本機 proxy（站在 agent 和 provider 中間的程式）。它要解決的問題來自 L4：log、diff、tool 輸出塞滿 context，而每一圈 loop 都重送整個 context，所以一份長 log 進了 context，之後每一圈都要再付一次：

Token 有兩個方向：model 讀進去的叫 input，model 寫出來的叫 output。Agent 每跑一圈，就把整段 context 打包成一個 request 送給 model。Caveman 兩邊都壓，一句話記：skill 改 model 怎麼寫，proxy 改 model 讀什麼。

輸出方向容易做：一份 skill。它規定保留技術名詞、指令、路徑、程式碼、錯誤、數字、否定詞，刪掉客套、重複和 hedging（含糊的保留語）。省下的大半來自一句話：和一句 Answer concisely. 比，/caveman 的中位數只再少 3%，/ultracave 少 35%。所以先在 CLAUDE.md 加一句，還要更短再裝 skill。查證見下面的本文延伸〈回答寫短真的好嗎〉。

輸入方向難做：要改寫每一個 request。你把 Claude Code 的 API 位址指到本機的 proxy，Claude Code 以為自己在跟 provider 講話，每一個 request 都先經過 proxy，改完再轉送。Caveman 依內容類型壓縮，原文存在本機，caveman_retrieve 取得回來。值得記的是：用別人的 agent 才需要 proxy，自己寫 harness 的話，這件事在 harness 裡直接做就好，也就是 L4 的 admission。

Proxy 用的是程式規則，不是 model。讀到這裡容易以為壓縮都是 model 在做。Caveman 有三處在壓縮，量最大的輸入方向不用 model：

原因都來自同一件事：每個 request 都要經過它。用 model 壓，每一圈要多一次 model call，多花的可能比省下的還多；同一段若每次壓得不一樣，prefix cache 就失效，所以 engine 要讓同一段永遠壓成同一串 bytes；解析不了或壓完沒變小，就原樣送出。記憶檔反過來用 model，因為一個 CLAUDE.md 只壓一次，結果也能先檢查再存。這是第 4 章問題的具體版本：哪一塊用確定的程式，哪一塊交給 model。

10dsh-superagent：把人的注意力當第一個要省的資源

第 3 章留下的問題是 review 跟不上。dsh-superagent 從這個問題反過來設計，也把前面幾章全部用上，所以放在最後當完整案例。它是 DeepSeek Harness 團隊 2026 年 10 月底公開的研究原型，一個替整個團隊工作的 coding agent。它掛在一個 GitHub repo 上，有人點名它做事，它就開一張工單（repo 裡叫 Ticket），在自己的 session 和目錄裡做完，回到原來那個對話交出 PR。README 寫明它不是產品。事實依 2026-11-03 的 repo，仍只有一個 commit。

它的全部設計只服從一句話：向人要最少的注意力，給最多的價值。訊息、通知、提問、設定、面板上的元素，每一樣都用「花掉多少注意力」來評。原因是：一個能替整個團隊做事的 agent，也能浪費整個團隊的注意力。

五條規則，每一條都在省注意力。這句原則落到 agent 身上，是 docs/000-philosophy.md 裡的五條：

  1. 只在有人點名、或團隊寫下的規則允許時才動。沒人要求的工作，例如看到 CI 紅了自己去修，要從「只記錄、不動手」開始跑。
  2. 只在人必須做決定、或能用結果時才說話。接到請求回一句，做的時候不出聲，訊息上限 100 個詞。
  3. 一次只問一個具體的問題。問題放在報告的專門欄位，問在那個人原本寫字的地方。
  4. 停在影響，不是停在努力。一個 module 內部的改動做到可以 review；要改 interface，就停下來留一個 draft PR 和一個問題。
  5. 誠實回報。草稿標成未完成，失敗報成失敗。

Prompt 給 worker 的檢查只有一句：刪掉這一句，人會不會看不懂結果、或少做一個動作？不會，就刪。重寫了哪個函式、比較過哪兩個套件，都是真的工作，但不會改變人接下來要做的事，所以留在 PR 裡。

分工：主 Session 只路由，worker 只做事。放回第 1 章的表，它是 subagent 加 worktree，沒有 team。主 Session 的 14 個工具全是路由用的，prompt 明文禁止它讀程式碼、看 log、寫實作計畫。有人問「可以加 dark mode 嗎？」，worker 收到的必須是這句原話和出處，不能是主 Session 替它挑好的配色，因為它一改寫，原本的需求就丟了。主 Session 也不等：sleep、超過 30 秒的 shell、超過 5 秒的 job 等待都會被擋，因為它一卡住，下一個請求就要排隊。

Worker 開工前跑一次團隊設定的 prepare 指令，文件的範例就是 git worktree add，所以第 5 章的做法在這裡是系統做的。Worker 彼此不講話，靠訂閱協調：一張 Ticket 訂閱了它的 issue 和 PR，之後那條討論串的留言和 CI 都自動送給它。同時跑幾個是一個設定 maxWorkers，預設 3、上限 16；上限之外多留一個位子給人的訊息，所以新工作再多，也擋不住人繼續一張既有的 Ticket。第 3 章算的上限，在這裡寫進了 code。

授權：誰能叫它做事，是 host 的程式碼在管。第 4 章說「讓周圍的系統可靠」，這裡畫得最清楚。文件把「誰說了算」排成五層：

沒人要求的工作有三段開關：off 完全不理，observe（預設）記下「本來會接」但不動手，auto 評估通過就接。文件要求從 observe 開始，看過它記下的判斷都對了再切。這就是第 4 章的自主程度配合風險，做成一個開關加一份紀錄。Merge 也一樣：預設不 merge 自己的 PR，要 merge 得另外給一個人的帳號的 CLI，而且只對 200 行以下、approval 都齊的 PR 開。

人的工作。這個系統裡人不寫程式，也不派工，只設邊界、看面板、負責。面板只回答三個問題：現在有沒有東西在等我？系統健不健康、做的事對不對？某一份工作的來龍去脈是什麼？docs/000-philosophy.md 的責任一節寫給操作者四條：

  • 從窄的開始。短名單，沒人要求的工作只記錄；看它本來會做的事都對了，再放寬。
  • 調低噪音。它太吵就把 prompt 改短，不要再多發訊息去解釋噪音。
  • 不拿它衝量。大量 PR 和廣播訊息，花掉的注意力比給的多。
  • 為它說的話負責。讀它用你的名義發出的每一句話，錯了就改 prompt。

它還沒回答的。這個案例回答了第 3 章的一半：agent 的目標從做更多，換成讓人每次只看必須看的東西。沒有回答的是它有沒有用：

  • 沒有量測。repo 裡沒有任何數字，一張 Ticket 花人幾分鐘、observe 記下的判斷有多少是對的，都沒有。
  • 它自己的注意力成本。仍需要一份詞彙表，操作者要依序讀七份文件（約 1.4 萬個英文詞）。
  • 範圍。只支援一個 repo；授權那一層看起來比它要解決的問題還重。

本文的判斷（2026 年 11 月）：五條規則和主 Session／worker 的分工值得照抄；授權那一層，等你真的要讓 agent 替整個團隊做事、而且會叫它的不只一個人時再學。

    Superpowers 的流程和預設流程差在哪裡？SessionStart hook 在哪三個時機執行？

    參考答案與重點複習

    答案：預設流程是收到需求就寫 code，出錯再改。Superpowers 走六個階段：釐清問題、核准設計、寫詳細的計畫、測試驅動實作、review 與驗證、收尾或整合 branch，分成 PLAN、BUILD、SHIP 三組。兩邊的 model 和 tool 完全相同，只有指示不同（p.6）。Hook 的 matcher 是 startup|clear|compact：新 session、/clear 之後、compaction 之後各執行一次（p.11）。

    重點拆解

    流程寫在 skill 裡。Slide 列了 Superpowers 的 9 個 skill（p.7）；repo 現在有 15 個，見第 8 章。每個 SKILL.md 的 frontmatter 是 metadata，例如 name 和 description；body 是 agent 照著做的步驟（p.9）。以 brainstorming 為例，最後兩步是「等使用者核准」和「載入 writing-plans」。流程型的 skill 還寫明進入條件、禁止的動作、人工核准的關卡和下一個 skill（p.10）。每個 skill 指向下一個，流程就自己接下去。

    只有 skill 還不夠。Skill 放在那裡，不代表 agent 會去查（p.11）。Model 依 description 決定要不要載入；任務看起來簡單時，它可能直接寫 code。所以 Superpowers 加了 SessionStart hook。Hook 讀出 using-superpowers 這個 bootstrap skill，用 additionalContext 加進 context（p.12）。這份內容是「怎麼選 skill」的規則。Hook 設 async: false，所以它在 agent 動作之前跑完（p.11）。

    三個時機，都是 context 可能沒有規則的時候。Startup 是全新的 context。/clear 清掉整段對話，先前注入的規則也一起消失。Compaction 把舊對話壓成摘要，規則可能被省略。所以 hook 在這三個時機都重新放一次。

    背景補充

    這是 L2 講的分工。寫在 skill 或 CLAUDE.md 的規則，是對 model 的要求：model 大多會照做，但沒有保證。Hook 是程式，時機到了就一定執行。Superpowers 用 hook 保證規則在 context 裡；要載入哪個 skill，仍由 model 判斷。

    Skill 會被跳過，根源是漸進載入：一開始 context 裡只有每個 skill 的名稱和描述，全文要等 model 決定載入才讀進來。這樣省 context，但 model 也可能沒查就動手。Plugin 是打包的單位，skill、hook、command 一次安裝、一起更新（p.8、p.25）。

    1. Model 和 tool 都沒換，只換了 context 裡的流程指示 → agent 的行為就不同。
    2. 要不要載入 skill 由 model 判斷；hook 是程式，保證規則一定在 context 裡。

  2. p.16–24 · Caveman 的雙向壓縮

    Caveman 從哪兩個方向壓縮 token？輸入方向為什麼要用 proxy，不用 hook？

    參考答案與重點複習

    答案：輸出方向靠 response skill，讓 model 寫得短；slide 的數字是 output token 少 65%（p.17）。輸入方向靠本機 proxy，壓縮 model 讀到的 log、diff、tool 結果；p.16 的例子把 786 行的 npm test 輸出壓成 1 行。壓縮輸入要改寫送給 model 的每一個 request。Hook 不能透明地改寫 LLM request；proxy 位在 coding agent 和 model provider 之間，每個 request 都經過它（p.24）。

    重點拆解

    Log、diff、tool 輸出會塞滿 context（p.16）。Agent 每一圈 loop 都重送整個 context，所以一份長 log 進來以後，之後每一圈都要再付一次。等 context 快滿才修剪，重要的資訊可能已經被剪掉（p.16）。所以 Caveman 在資料進 context 時就壓，兩個方向都壓，而且保留原文。

    輸出方向用 skill，改的是 model 怎麼寫（p.17）。它保留技術名詞、指令、路徑、程式碼、錯誤、數字、單位和否定詞；刪掉贅字、重複、客套和含糊的保留語（p.20）。結果是 output 少 65%（p.17）。

    輸入方向用 proxy，改的是 model 讀到什麼。這個方向的量更大：C compiler 案例用了 2B input、140M output token（p.47），2B ÷ 140M ≈ 14 倍。Proxy 依內容類型壓縮：log 留錯誤、stack trace、開頭和結尾；diff 留檔案與 hunk 標頭、改動的行（p.24）。Agent 需要細節時，用 MCP tool caveman_retrieve 取回逐 byte 相同的原文（p.23）。

    為什麼一定要 proxy？Hook 綁在事件上。改 tool 的 hook 在單一 tool call 前後執行，只能改那一個 tool 的輸入或輸出，碰不到整個 request。所以一筆 tool 輸出，PostToolUse hook 換得掉（第 9 章）；system prompt 和之前的對話，它換不掉。MCP 只在 agent 呼叫時執行，也改不了 context。只有夾在中間的 proxy，每個 request 都經過（p.24）。自己寫 harness 的話，也能在 harness 裡改。

    背景補充

    Proxy 是網路系統的老做法：在兩端之間插一層，兩端都不用改。公司常用的 LLM gateway 也是這種 proxy，用來集中管 API key、用量和紀錄。Claude Code 可以用環境變數 ANTHROPIC_BASE_URL 把 request 送到 gateway 或 proxy。

    這也是 L2 的分工：壓縮 log 是確定的程式，交給 engine；回答的風格需要判斷，寫進 skill 交給 model。

    常見誤解

    「Output 少 65%，整個 session 就省 65%。」Output 只占 token 的一小部分；skill 本身還多佔 input token，所以整個 session 省得更少（p.17）。要大幅省 token，重點在輸入方向。進階題第 2 題會用數字比較兩個方向。

    例子

    在終端機輸入 claude plugin marketplace add JuliusBrussee/caveman，再輸入 claude plugin install caveman@caveman 安裝（p.15）。然後開一個 session，輸入 /caveman ultra，再打「Run the tests and explain the failure.」（p.17）。等級有 lite、full、ultra、off，預設 full（p.21）。

    帶走這幾點
    1. 輸出方向：skill 改 model 怎麼寫。輸入方向：proxy 改 model 讀到什麼。
    2. Input 約是 output 的 14 倍 → 大宗在輸入方向，而只有 proxy 管得到每一個 request。
    3. 壓縮要能還原：原文保留，agent 需要細節時用 caveman_retrieve 取回。

    相關：核心觀念〈Caveman：省 token 先看帳單，輸入方向只有 proxy 管得到〉、L4〈Context 的成本〉、L8〈Input token：留在 context 裡的 token，之後每一步都再付一次〉。進階題第 2 題算省多少，也討論壓縮的風險。

  3. p.27–31 · 三個擴展軸

    擴展的三個軸各買到什麼？Subagent 怎麼保護主對話的 context？

    參考答案與重點複習

    答案：平行的 session（廣度）買到 throughput，縮短牆上時間，答案不會更好；subagent（廣度＋深度）買到 throughput 與專注；長時間執行（時間）買到更大的範圍、更少人工介入（p.27）。Subagent 在自己的 context window 做事，log、搜尋結果、整份檔案都留在那裡。主對話只收到摘要（p.27、p.31）。

    重點拆解

    三個軸回答三個問題：同時跑幾個、交出去多少、一個 agent 跑多久。Agent team 和 workflow 是這三個軸的組合（p.27）。

    平行 session 最直接：一個任務一個 session，各在自己的 git worktree，改動互不影響（p.28）。它只買到時間，每個任務仍是一個 agent 的水準。開幾個 session 是生產力；開到 20 個，你需要一個自己的分身（p.30）。原因有四個：計畫只在你腦中、session 互相看不到、branch 要你自己整合，而且整個過程無法重跑。

    Subagent 靠 context 隔離保護主對話。每個 subagent 有自己的 context window、tool 和權限（p.31）。它讀的檔案、跑的 log 留在自己的 context；做完只交回摘要，主對話看不到中間過程（p.27）。主對話每一圈都重送整個 context，所以少放 30 份檔案，之後每一圈都省。代價是摘要會丟細節；subagent 也看不到對話歷史，要花時間從零收集 context（p.37）。

    背景補充

    Context 隔離很像函式呼叫。被呼叫的函式有自己的 local 變數；return 之後變數就釋放，呼叫者只拿到回傳值。Subagent 的摘要就是回傳值，格式由你定。委派時寫明「每個問題附 file：line」，損失就小。

    主對話乾淨，不只是省錢。Context 越長，model 越容易漏看中間的內容（L4 的 lost in the middle）。內建的 Explore 和 Plan 甚至不讀 CLAUDE.md 和 git status，以求快又便宜（p.32），所以相關規則要寫進任務訊息。

    常見誤解

    「平行的 agent 越多，答案越好。」平行只縮短牆上時間，每個任務仍是一個 agent 的水準（p.27）。協調和 merge 的工作還會隨 session 數增加。要更好的答案，靠的是更專注的 context 和更好的驗證。

    例子

    平行：開兩個 terminal，分別輸入 claude -w feature-payments 和 claude -w bugfix-auth，每個 session 各有一個 worktree（p.28）。Subagent：在 session 裡打「Use the Explore subagent to find every caller of parseConfig. Report file:line only.」。搜尋結果留在 Explore 的 context，你只看到一份清單。

    帶走這幾點
    1. 平行 session 只買到牆上時間；計畫和 merge 仍在你身上，超過幾個就管不動。
    2. Subagent ＝ 新的 context ＋ 只交回摘要 → 中間產物不進主對話，之後每一圈都省。
    3. 摘要是有損壓縮 → 委派時指定回報格式；要頻繁來回討論的工作留在主對話（p.37）。

    相關：核心觀念〈放大的三個軸：每一種只買到一樣東西〉、〈手動平行：worktree 只隔離檔案〉、〈Subagent：換到乾淨的主對話，代價是摘要有損〉、〈上限：16 個 agent 不會快 16 倍〉、L4〈Lost in the middle〉。進階題第 1 題替任務選擴展方式。

  4. p.39–45 · Team 與長時間執行

    只要結果時，為什麼用 subagent，不用 agent team？/goal 和 /loop 什麼時候停？

    參考答案與重點複習

    答案：每個 teammate 都是獨立的 Claude Code instance，各有 context window，所以 team 的 token 成本較高（p.39、p.41）。Slide 的規則：只要結果，用 subagent；工作需要討論，才用 team（p.41）。/goal 在可驗證的條件成立時停：每次嘗試後，evaluator 重新檢查條件，沒成立就讓 Claude 繼續；--max-tries 用完也會停（p.44）。/loop 依固定間隔重跑同一個 prompt，直到你叫它停（p.45）。

    重點拆解

    兩者的差別在結果流向哪裡。Subagent 做完，把結果交回呼叫它的 agent；subagent 之間不溝通。Teammate 共用一份任務清單，自己認領工作，還能直接互傳訊息；每個 agent 有一個 JSON 格式的 mailbox（p.39–40）。

    SubagentAgent team
    Context自己的 window，結果交回呼叫者自己的 window，完全獨立
    溝通只回報給呼叫者Teammate 之間直接傳訊
    協調主 agent 管理工作共用任務清單

    Token 成本較低較高

    Team 貴，因為每個 teammate 都是完整的 session。它自己載入 CLAUDE.md 和 skill，再從零讀任務需要的檔案。它也不繼承你的對話，任務細節要寫進 spawn prompt（p.39）。所以 token 用量隨人數線性成長。只要三份獨立的報告，這筆錢換不到東西；要互相挑戰、要整合跨層的改動，才值得付。依序做的任務、改同一個檔案、相依很重的工作，slide 建議用一個 session 或 subagent（p.38）。

    /goal 和 /loop 的差別在停止的依據。/goal 看條件：每一輪結束，另一個小而快的 model 讀對話，判斷條件是否成立。做事的 model 不能自己宣布完成。/loop 看時間：它是觸發器，不是測試（p.45）。Slide 的說法是你叫它停才停（p.45）；〈動手試試〉依官方文件補充：固定間隔的 loop 要請 Claude 取消，或 7 天後自動過期。

    背景補充

    Evaluator 只讀對話，不跑指令，也不讀檔案。所以條件要寫成 Claude 的輸出能證明的形式。「npm run lint exits with zero errors」可以，因為 lint 的結果會印在對話裡；「refactor the code」不行（p.44）。Slide 用 --max-tries 限制次數；〈動手試試〉照官方文件，把「or stop after 15 turns」寫進條件。目的相同：限制花費。

    常見誤解

    「/loop 發現工作做完，就會自己停。」固定間隔的 loop 不判斷完成；CI 早就綠了，它還是照時間再跑一次。要「做到成立就停」，用 /goal。

    例子

    Agent team 預設關閉（p.38）。先在 .claude/settings.json 的 env 加上 "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"。再在 session 裡打：「Spawn three teammates to review PR #142: one on security, one on performance, one on test coverage. Have them challenge each other's findings.」。/goal 和 /loop 的寫法，見〈動手試試〉最後一個範例。

    帶走這幾點
    1. Subagent 把結果交回主 agent；teammate 互相傳訊 → 只要結果用 subagent，需要討論才用 team。
    2. 每個 teammate 是完整的 session，不繼承你的對話 → token 隨人數線性成長。
    3. /goal 由另一個 model 檢查條件才停；/loop 照時間觸發，要你取消。

    相關：核心觀念〈Subagent〉、〈Team 與 workflow：要討論才用 team，對話協調不了才用 script〉、〈終點：自主程度由能不能驗證決定〉（含〈/goal〉與〈/loop〉兩段）、L5〈根本的限制：agent 之間只能傳文字〉。進階題第 1 題替四個任務選做法，並寫出完整的 /goal 條件。

  5. p.52–59 · Programming 3.0

    Programming 3.0 比 2.0 多了哪一層，代價是什麼？結論原則怎麼面對不確定性？

    參考答案與重點複習

    答案：3.0 在人和程式語言之間多了 agent 這一層：人用自然語言說目標，agent 寫程式碼（p.52）。它換來更高的產能，代價是更多的不確定性。結論原則：不要期待 agent 是確定的，要讓 agent 周圍的系統可靠。自主程度要配合風險：自主越多，不確定性與風險越高（p.59）。

    重點拆解

    每一代都在人和硬體之間多一層（p.52）。1.0 是人直接寫機器指令。2.0 是人寫程式語言，compiler 轉成機器指令。3.0 是人用自然語言說目標，agent 產生程式語言。每多一層，人寫的東西更接近目的，所以產能變高。但 compiler 是確定的：同一份原始碼，得到同樣的指令。Agent 不是：同一個目標，兩次可能寫出不同的程式。

    不確定性本身不是新的（p.55）。2.0 就有 32 位元與 64 位元、endianness、並行、不可靠的網路、compiler 版本、相依套件漂移。2.0 的對策是固定寬度的型別、虛擬化、idempotent API、升級前跑完整測試。3.0 在硬體、環境、軟體三列各加一項：GPU 的 nondeterministic kernel、寫 code 時就和環境互動、model 的取樣。

    新的不確定性集中在產生程式的階段（p.57）：自然語言的語意、檢索的漂移、model 的取樣、agent 與 tool 的迴圈。程式寫好以後，除非執行時還呼叫 model 或 tool，通常是確定的。所以 p.58 把對策放在生成的前後：先寫明假設和驗收測試，生成後用頻繁又便宜的檢查驗證。

    背景補充

    Karpathy 的 Software 3.0 是另一種分法，看「程式是什麼」：1.0 是原始碼，2.0 是權重，3.0 是 prompt（p.53）。講者的分法看「人寫什麼」。兩者導向同一個工程能力：決定哪一塊用確定的程式，哪一塊交給 model。

    「自主程度配合風險」對應 Karpathy 講的 autonomy slider：自主程度是一個可以調的滑桿，不是全有或全無。本堂的工具都是這個可靠系統的零件：hook 保證規則在 context 裡，/goal 要求可驗證的終點，測試判斷進度。

    常見誤解

    「把 temperature 設成 0，agent 就確定了。」取樣只是一個來源。p.57 另外列了軟硬體的不確定性：GPU 的加總順序會隨 batch 改變，浮點數沒有結合律，結果就差一點（L1）。Tool 的輸出和環境也會變。所以對策是讓周邊系統可靠，不是追求 agent 確定。

    例子

    在 Claude Code 裡，依風險調整自主程度。修 lint 錯誤：低風險、可驗證，切到 auto mode，再輸入 /goal npm run lint exits 0; no file under tests/ is modified。Security review：只給讀的權限，用〈動手試試〉的唯讀 subagent（tools: Read, Glob, Grep）。Merge 到 main：留給人。

    帶走這幾點
    1. 3.0 多了 agent 這一層：人說目標，agent 寫程式 → 產能變高，不確定性也變高。
    2. 不確定性早就存在；新的部分集中在產生程式的階段，程式寫好後通常是確定的。
    3. 不追求 agent 確定 → 讓周邊系統可靠（可驗證的終點、測試、hook），自主程度配合風險。

    相關：核心觀念〈終點：自主程度由能不能驗證決定〉（含〈Karpathy 的 Software 3.0〉那則查閱）、〈人：能管幾個 agent，由你 review 的速度決定〉、L1〈浮點數沒有結合律〉、L2〈自主程度要配合風險〉。

  2. 風險與取捨 · 壓縮 model 讀到的內容 · p.16–25

    Caveman 用 proxy 壓縮 model 讀到的每一個 request。這能省多少，會冒什麼風險？什麼情況下值得，什麼情況下不值得？

3 · 動手試試

照著做一次

每個範例都依 2026 年 10 月的 Claude Code 官方文件。點開才會展開。

用 SessionStart hook 保證規則一定在 context 裡p.11–12

這是 Superpowers 的做法，縮小成一個專案能用的版本。Hook 在 session 開始、/clear 之後、compaction 之後各執行一次，把一份規則檔的內容加進 context。

驗證：開新 session，輸入「你現在的規則是什麼？」。Claude 應該能複述 WORKFLOW.md 的內容。再輸入 /clear，問一次，規則應該還在。

兩個任務，兩個 worktree，兩個 sessionp.28–29

最短的做法是 -w。Claude Code 會在 .claude/worktrees/<name>/ 建 worktree，branch 叫 worktree-<name>。離開 session 時，有改動它會問你要保留或刪除。

想自己控制目錄和 branch 名稱，用 git 指令。三個目錄共用一個 .git，在一個 worktree 的 commit，其他 worktree 立刻看得到。

新 worktree 沒有 .env 和 node_modules。先裝相依套件，或在 .worktreeinclude 列出要複製的檔案。同一個 branch 不能在兩個 worktree 同時 checkout。

定義一個唯讀的 reviewer subagent，再明確委派p.33–36

一個 subagent 就是一個 Markdown 檔。Frontmatter 是設定，body 是它的 system prompt。只給三個唯讀 tool，它就改不了檔案。

委派時寫清楚範圍和回報格式。自訂的 subagent 會讀 CLAUDE.md，內建的 Explore、Plan 不讀；但不管哪一種，都沒有你的對話歷史，所以在對話裡講好的規則要寫進任務訊息。

一定要它執行時，用 @agent-code-reviewer 開頭。要限制巢狀層數，在 .claude/settings.json 的 env 設 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH；設 1 就關閉巢狀。

寫一個 /goal 檢查得到的條件，和一個 /loop 的 promptp.44–45

好的 goal 條件有三部分：可量測的終點、檢查方法、限制條件。再加一個停止條款，限制花費。條件不必加引號。

/goal 不改權限模式。要讓它無人看管地跑，先切到 auto mode；否則每個沒放行的指令都會停下來問你。輸入 /goal 看狀態，/goal clear 提早結束。

/loop 是觸發器，不判斷完成。固定間隔的 loop 要請 Claude 取消，或 7 天後過期。省略 prompt 時，它跑 .claude/loop.md。

Software 3.0 的脈絡 From Software 2.0 to 3.0

  1. 推薦Software 2.0Andrej Karpathy · 部落格 · 2017 · 約 10 分

    2017 年的起點：神經網路的權重取代手寫程式，成為「軟體」本身。

    導讀問：從 2.0（權重）到 3.0（prompt），「寫軟體」的單位各是什麼？改變的是誰的工作？

    摘要讀約 3 分；原文約 10 分

    一句話：Karpathy 在 2017 年提出：神經網路的權重是一種新的軟體。人不再逐行寫程式，改成給目標與資料，由 optimizer 在程式空間裡搜出程式。

    跟這堂課的關係

    Slides p.53 的 1.0／2.0／3.0 表格，2.0 那一列（程式是權重、用資料加優化產生）就是這篇。本頁第 4 章的〈Karpathy 的 Software 3.0〉那則查閱說明它和講者 p.52 的分法不同：這篇分「程式是什麼」，講者分「人寫什麼」。〈終點〉談的不確定性，這篇在 2017 年已經寫到。第 3 章〈人〉問人做什麼；這篇的答案是：多數人整理資料集，少數人維護訓練基礎設施。

    壓縮後的重點

    1. 2.0 的「原始碼」是資料集加網路架構，訓練就是 compile。1.0 由人寫 Python 或 C++，每一行把程式釘在程式空間的一個點。2.0 由人給目標與架構骨架，backprop 與 SGD 在這個子空間裡搜尋。
    2. 2017 年已有多個領域換成 2.0。視覺辨識從手工特徵加 SVM 換成 ConvNet；語音辨識丟掉 GMM 與 HMM；AlphaGo Zero 讀原始棋盤直接出手。資料庫索引也開始學：learned index 比 cache 最佳化的 B-Tree 快最多 70%，記憶體省一個數量級。
    3. 好處來自計算同質。網路只有矩陣乘法與 ReLU 兩種操作，所以容易燒進 ASIC。每次 forward pass 的 FLOPS 固定，執行時間與記憶體都是常數。砍掉一半 channel 再訓練，速度剛好快一倍，效果略差。獨立訓練的模組可以接起來一起 backprop。
    4. 最大的好處：它比人寫的程式好。影像、影片、聲音、語音的程式，神經網路寫得比任何人都好。原文把這點標為最重要。
    5. 壞處是不可解釋，而且失敗得奇怪。你可能要在 90% 準確但看得懂、99% 準確但看不懂之間選。網路會吸收資料裡的偏見、默默失敗；adversarial example 顯示這個 stack 還有很多沒搞懂的性質。
    6. 2.0 的程式設計是整理資料，工具鏈還沒出現。修 bug 的方法是補那類案例的標註資料。他問誰來做 2.0 的 IDE：用 loss 找出可能標錯的樣本、依不確定性挑該標的樣本。2.0 的 GitHub 是資料集的版本控制，commit 是標籤的增修。

    原文怎麼讀

    • 可以跳過：開頭 Software 2.0 一節的定義，slides p.53 的表已經夠；Ongoing transition 的六個領域是 2017 年的例子，現在都成了常識。
    • 值得看原文：The benefits of Software 2.0 的八點清單，看他怎麼從「只有兩種操作」推出硬體與執行時間的好處；Programming in the 2.0 stack 最後的三個開放問題（IDE、GitHub、conda），對照 2026 年的工具鏈。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 5 分。
    別誤讀

    「Software 2.0 就是用 LLM 寫程式。」這篇的 2.0 是權重取代程式碼：人交出資料與標籤，程式碼本身消失。用自然語言讓 agent 產生程式碼，是講者 p.52 的 Programming 3.0；Karpathy 自己到 2025 年的演講才把 prompt 叫做 3.0。

  2. 選讀Software 3.0 — the era of intelligent software developmentItamar Friedman · 部落格 · 2022 · 約 10 分

    2022 年對「Software 3.0」一詞的早期用法，作者自己標明是推測。重點放在自動測試與 review。

    把 1.0／2.0／3.0 的分類接到 agent 時代。核心是 autonomy slider。（L1 p.37 也引用了這支影片）

    導讀聚焦 autonomy slider：自主程度拉高，人的角色怎麼從寫程式變成「定義結果 + 驗證結果」？

    摘要讀約 3 分；原文約 40 分

    一句話：Software 3.0 用英文 prompt 寫程式。LLM 會犯錯，所以現在該蓋帶 autonomy slider 的部分自主產品，不是全自主 agent。人的工作變成讓「生成、驗證」迴圈轉得快。

    跟這堂課的關係

    Slides p.53 直接引用這支影片的 1.0／2.0／3.0 分法；本頁第 4 章的〈Karpathy 的 Software 3.0〉那則查閱說明它和講者 p.52 的分法不同。〈終點：自主程度由能不能驗證決定〉的結論「自主程度配合風險」（p.59），就是 Karpathy 的 autonomy slider。第 3 章〈人〉接的是他的生成與驗證迴圈。

    壓縮後的重點

    1. 軟體 70 年沒大變，最近幾年變了兩次。1.0 是手寫程式碼，2.0 是神經網路權重，3.0 是給 LLM 的 prompt。Tesla Autopilot 裡的 C++ 逐步刪除，功能移進神經網路；他預期 prompt 會再吃掉一部分。
    2. LLM 同時像公用事業、晶圓廠和作業系統。Model 像 CPU，context window 像記憶體。算力貴又集中在雲端，像 1960 年代的分時系統。
    3. LLM 是「people spirits」，有固定的認知缺陷。它會幻覺、能力參差（jagged intelligence）、沒有長期記憶（anterograde amnesia），而且容易受 prompt injection 欺騙。Context window 只是工作記憶。
    4. 部分自主的 app 有四個特徵。Cursor 與 Perplexity 都做到：管理 context、協調多次 LLM call、專用 GUI 加快審查、autonomy slider。Cursor 的 slider 從 Tab 補全到 Cmd+K、Cmd+L、Cmd+I。
    5. 人負責驗證，AI 負責生成，迴圈要快。GUI 讓驗證更快，因為視覺檢查比讀文字快。把 AI 拴緊：避免一次 1,000 行的 diff，prompt 寫具體，小步前進。
    6. 自駕的教訓：demo 到產品要很久。他 2013 年坐過一次 30 分鐘零接管的 Waymo；12 年後，Waymo 仍有大量遠端操作。所以「2025 是 agent 之年」太樂觀，他說是 agent 的十年。Iron Man 的比喻：先造增強人的裝甲，slider 隨時間往右推。
    7. Vibe coding 容易，部署難。MenuGen 的 demo 幾小時就在筆電上跑起來；認證、付款、網域、部署又花了一週，大部分時間在瀏覽器裡點選。所以要為 agent 蓋基礎設施：llms.txt、Markdown 文件、用 curl 指令取代「點這裡」、gitingest 與 DeepWiki 把 repo 變成一份文字。

    原文怎麼讀

    • 可以跳過：01:25–06:10 的 1.0／2.0／3.0 定義，slides p.53 已經講過；06:10–14:39 的三個比喻只是背景。
    • 值得看原文：18:22–23:40 的 Cursor 與 Perplexity 拆解，看 slider 怎麼落在 UI 上；26:00–29:06 的 Tesla、Waymo 與 Iron Man 段；33:39–38:14 的 build for agents，看 llms.txt 與文件範例的畫面。
    • 時間：只讀摘要約 3 分；照上面挑著看影片約 20 分。

  1. 推薦Claude Code subagentsAnthropic · 官方文件 · 查表約 10 分

    Subagent 是 context 隔離與委派的基本單位，用 Markdown 檔設定。

    導讀看限制：nesting 深度、並行上限、token 警告、權限怎麼繼承。這些就是 slides 範例的邊界。

    摘要讀約 3 分；原文約 10 分

    一句話：Subagent 是一個有自己 context window、自己 system prompt 與 tool 清單的助手。用一個 Markdown 檔定義，主對話只收到它最後的報告。

    跟這堂課的關係

    Slides p.31–37 幾乎逐節取自這份文件：p.31 的五個理由、p.33 的 frontmatter 範例、p.36 的三種叫法、p.37 的「留在主對話還是委派」。本頁第 6 章〈Subagent〉講的機制，文件寫得更細：subagent 開始時載入什麼、報告回來前經過什麼。一處分歧：p.34 說巢狀最多 5 層；現行文件預設是主對話下 3 層，早期版本才固定 5 層。

    壓縮後的重點

    1. 定義檔就是一個 Markdown。YAML frontmatter 放設定，內文是 system prompt。只有 name 和 description 必填。Claude 依 description 決定要不要委派，所以它要寫清楚什麼時候用；所有自訂 description 合計超過 15,000 token 時，啟動會警告。
    2. 常用欄位：tools、disallowedTools、model、permissionMode、maxTurns。model 可填 sonnet、opus、haiku、完整 model ID 或 inherit。isolation: worktree 讓它在獨立的 git worktree 裡改檔；memory 給它跨 session 的記憶目錄；hooks 與 skills 也能寫在 frontmatter。
    3. 放哪裡決定誰能用。.claude/agents/ 是專案層，進版控全隊共用；~/.claude/agents/ 是個人層，所有專案可用。同名時優先序是：管理設定、--agents 旗標、專案、個人、plugin。
    4. 內建三個：Explore、Plan、general-purpose。Explore 與 Plan 只能讀，不載入 CLAUDE.md 與 git status，所以快又便宜。要關掉某一個，在 permissions.deny 寫 Agent(Explore)。
    5. Subagent 從零開始，主對話只拿到摘要。它收到的是 system prompt、委派訊息、CLAUDE.md、git status 快照與預載的 skill；沒有對話歷史。報告回到主對話前會經過掃描，裡面的指令不具使用者的權限。例外是 fork：它繼承整段對話，並共用 prompt cache。
    6. 上限與叫法。預設同時最多 20 個，巢狀 3 層，兩者都能用環境變數改。叫法三種：自然語言點名、@ 指定（保證執行）、claude --agent code-reviewer（整個 session 用它）。互動模式下 subagent 預設在背景跑，權限提示回到主 session。

    原文怎麼讀

    • 可以跳過：Quickstart 與 Example subagents 的四個範例，p.33 已經給了最小範例；Choose a model 的解析順序與 Fork 一節，第一次讀用不到。
    • 值得看原文：Frontmatter reference 的完整表格，查欄位名時回來看；Choose between subagents and main conversation 的對照清單，比 p.37 多了 skill 與 /btw 兩個選項；What loads at startup，看一個 subagent 開始時到底拿到什麼。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 8 分。
    別誤讀

    「Subagent 看得到主對話，只是分開跑。」錯。一般的 subagent 沒有任何對話歷史，只有你寫進委派訊息的內容。它查過的檔案和跑出的 log，主對話也看不到，只拿到最後的報告。要帶著完整對話，得用 fork；要互相傳訊、共用任務清單，得用 agent team。

    對等 agent 協作的官方機制。文件自己標明：experimental、昂貴、有限制。

    導讀聚焦失敗模式：成本、檔案衝突、卡住的任務。問：什麼任務值得開一個 team，而不是一個 subagent？

    摘要讀約 3 分；原文約 10 分

    一句話：Agent team 是好幾個完整的 Claude Code session 一起做事：一個 lead 派工，teammate 認領共用任務清單上的工作，彼此直接傳訊。文件自己標明 experimental、預設關閉、token 隨人數線性增加。

    跟這堂課的關係

    Slides p.38–42 取自這份文件：p.38 的四種適用情境與警語、p.39 的四個組件、p.41 的 subagent 對照表。本頁第 7 章〈Agent team〉的選擇規則「需要討論才用 team」，就是文件的結論。第 2 章〈上限〉講的 token 線性成長，文件寫成建議：先開 3 到 5 個。第 7 章〈16 個 agent〉的 lock file 做法這裡也用：teammate 認領任務時靠 file locking 防止搶同一題。

    壓縮後的重點

    1. 和 subagent 差在三件事。Subagent 只把結果交回呼叫者，主 agent 管所有工作。Teammate 是獨立的 session，彼此直接傳訊，靠共用任務清單自我協調。所以 subagent 適合只要結果的任務，team 適合需要討論的工作，代價是每個 teammate 都是一個完整的 Claude 實例。
    2. 開啟要設環境變數。在 settings.json 的 env 或 shell 裡設 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1。開了之後，Claude 替 subagent 取名時會直接開成 teammate，所以沒要求也可能形成 team；設回 0 就關掉。-p 的非互動模式不會開 teammate。
    3. 四個組件：lead、teammate、task list、mailbox。Lead 是主 session，負責開人、派工、整合。每個 agent 的 mailbox 是一個 JSON 檔，放在 ~/.claude/teams/ 底下。Teammate 載入 CLAUDE.md 與 skill，但不繼承 lead 的對話，所以任務細節要寫進 spawn prompt。
    4. 任務清單有三種狀態與相依。pending、in progress、completed；有相依的任務要等前置完成才能認領。Teammate 做完會自己認領下一題。三個 hook 當品質關卡：TeammateIdle、TaskCreated、TaskCompleted，exit code 2 就退回並附回饋。
    5. Lead 怎麼帶，權限也集中在 lead。用自然語言跟 lead 說要幾個 teammate、用哪個 model、各自的角色；也可以引用 .claude/agents/ 裡的 subagent 定義當角色。Teammate 繼承 lead 的 permission mode，它的權限提示都回到 lead 的 session 由你核准；teammate 不能替你核准任何事。
    6. 限制清單要先看。文件列了好幾條，常碰到的是這五條：
      • /resume 不會把 in-process 的 teammate 找回來。
      • 任務狀態可能卡住沒更新。
      • 一個 session 只有一個 team。
      • Teammate 不能再開 team。
      • Lead 不能換人。
      建議：3 到 5 個 teammate、每人 5 到 6 個任務、不要讓兩人改同一個檔案。

    原文怎麼讀

    • 可以跳過：When to use agent teams 與 Compare with subagents，slides p.38 與 p.41 已經講完；Choose a display mode 的 tmux 設定，要用分割視窗時再查。
    • 值得看原文：Use case examples 裡「5 個 teammate 互相推翻假設」的 prompt，看 debate 怎麼對抗 anchoring；Limitations 整節，決定要不要開 team 之前先讀。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 8 分。
    別誤讀

    「Teammate 比 subagent 強，所以平行工作都該開 team。」文件說的相反。Team 的 token 隨人數線性增加，協調成本也跟著漲；順序性的工作、改同一個檔案、相依很多的工作，一個 session 或 subagent 做得更好。文件建議先從 review 與研究這類不寫 code 的任務試起。

  1. 必讀Building a C compiler with a team of parallel ClaudesNicholas Carlini（Anthropic）· 工程報告 · 2026 · 約 25 分

    16 個並行 agent 蓋出一個 C compiler 的實戰紀錄。slides p.47–50 直接取材於此。

    導讀主線是「verifier 品質決定自主工作的上限」。也看成本數字與作者自列的限制。問：你的領域裡，等價的 verifier 是什麼？

    摘要讀約 3 分；原文約 25 分

    一句話：16 個 Claude agent 平行跑兩週，沒有人介入，用 Rust 從零寫出能編譯 Linux kernel 的 C compiler。成立的條件有兩個：測試接近完美，失敗訊號能切成很多小塊。

    跟這堂課的關係

    Slides p.47–50 直接取材於這篇，見第 7 章〈16 個 agent〉；verifier 的主張接第 4 章〈終點〉。Kernel 卡關的故事是第 2 章〈任務切不開，加 agent 也沒用〉的來源（p.50）。Slides 沒有講的是成本數字、agent 的分工角色，以及作者對「測試通過」的保留態度。

    壓縮後的重點

    1. 規模與成本。16 個 agent、將近 2,000 個 Claude Code session、兩週，model 是 Opus 4.6。API 成本略低於 20,000 美元；input 20 億 token，output 1.4 億 token。Compiler 約 100,000 行 Rust，過程中沒有網路。
    2. 成果與限制。它能編譯 Linux 6.9（x86、ARM、RISC-V）、SQLite、FFmpeg、QEMU 等專案，跑得動 Doom；大多數測試集通過率 99%。但全部最佳化打開，產出仍比 GCC 關掉最佳化還慢。自己的 assembler 與 linker 還有 bug，展示時借用 GCC 的。
    3. 長時間執行靠檔案，不靠記憶。每個 session 在全新的 container 開始，沒有任何 context。所以 prompt 要求 agent 維護 README 與進度檔；卡住時，記錄失敗過的做法與剩下的任務。
    4. 協調只靠 git。每個 agent 在自己的 container 裡 clone 共用的 bare repo。認領任務就是在 current_tasks/ 寫一個 lock file 並 push；兩個 agent 搶同一題，git 會逼其中一個換題。沒有 orchestrator；merge conflict 很常見，agent 自己解。
    5. Verifier 要接近完美。測試有錯，agent 就會解錯的問題。測試來自 compiler 測試集、開源專案的 build script，以及針對新失敗寫的測試。輸出也為 model 設計：只印幾行，細節進 log 檔，錯誤行標 ERROR；預設 --fast 只抽 1% 或 10% 的測試。
    6. 平行要靠獨立的失敗訊號。測試集有很多獨立失敗時，每個 agent 各拿一個。到了 kernel，所有 agent 卡在同一個 bug，互相覆蓋修改，16 個 agent 沒有加速。解法是用 GCC 當 oracle：大部分檔案用 GCC 編譯，少數用自己的 compiler，失敗就縮小範圍。

    原文怎麼讀

    • 可以跳過：開頭的 compiler 功能展示，slides p.47 已經講過；Acknowledgements。
    • 值得看原文：Enabling long-running Claudes 裡的 harness 與 lock file 說明；Lessons 底下的 Put yourself in Claude's shoes 與 Multiple agent roles（去重複、效能、Rust 品質、文件各一個 agent）；Stress testing the limits 裡的 kernel 故事。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 15 分。
    別誤讀

    「測試通過率 99%，所以 agent 可以無人監督交付軟體。」作者自己不這麼說。他寫道，看到測試通過就以為工作完成很容易，但這很少成立；他對部署沒有人親自驗證過的軟體感到不安。這個 compiler 也不是生產用的替代品。
