先看這裡

這堂從一個 agent 走到很多個 agent。前半承接 L2 的擴充機制，用三個 plugin 案例說明：model 不變，改 workflow 和 token 的進出，結果就不同；其中 mattpocock/skills（2.2）是本文補的，slide 沒有，拿來和 Superpowers 並排看「skill 之外要不要 hook」。後半比較擴大規模的幾種做法：誰協調、context 在哪裡隔離、各要付什麼代價。最後退一步問：用自然語言叫 agent 寫程式，和以前的寫法差在哪裡，不確定性要怎麼管。這篇文章會把 plugin、skill、hook、MCP、proxy、git worktree、subagent 這些名詞，在第一次出現的地方講清楚。

  • Model 不變，改 workflow 就改結果。Superpowers 用 skill 定義開發流程，再用 SessionStart hook 保證 agent 每次都讀到規則；mattpocock/skills 只用 skill，把「要不要走流程」交回給人；Caveman 用 skill 讓 model 寫得短，用一個本機 proxy 讓 model 讀得少。三個 plugin 都沒有換 model，也沒有加新能力。
  • 每種擴展方式都有代價。平行要你 merge，subagent 的摘要會丟細節，agent team 的 token 隨人數成長，workflow 每個任務用更多 token。只要結果，用 subagent；需要討論，才用 team；agent 多到對話協調不了，才用 workflow。而且加 agent 有上限：不能平行的那段工作決定了最快能多快。
  • Agent 不確定，周邊系統要可靠。寫可驗證的終點、跑測試、讓自主程度配合風險。/goal 能自己停下來，靠的是一個可以檢查的終點；16 個 agent 能寫出一個 C compiler，靠的是 git、lock file 和測試，不是 agent 之間的聊天。

這篇可以不看 slides 從頭讀到尾：每個名詞在第一次出現的地方就有解釋，由淺入深，頁碼只是出處。少見的名詞和 L2、L4 講過的東西收在正文裡的「名詞」「前情」註，碰到不懂的再點開。想對照 slides，就在讀到頁碼時打開那幾頁；想先帶著問題讀，就先看第 3 段的基礎題。讀書會前用第 3 段的進階題。建議先讀 L2 和 L4：前半的三個 plugin 用的是 L2 2.4 講的擴充機制，後半一直用到 L4 講的 context 代價和 subagent；沒時間讀，2.3 開頭的「前情」註有 L4 的摘要。

1 · 架構

多個 agent 怎麼分工：誰協調，context 隔離在哪裡

這張圖是整堂課後半的地圖，前半的三個 plugin 案例都還是一個 agent，所以圖上沒有它們。先定兩個名詞。Session 是你打開 Claude Code 之後的一段對話，它有自己的 context window（一次送給 model 的全部文字，L4 有完整說明）。Agent 在這堂課裡就是一個在跑的 session，或是一個由 session 派出去的小 agent。圖上每一個方框都有自己的 context，方框之間看不到彼此的 context，這是所有擴展方式的共同前提。

看圖時先找藍框：誰持有計畫。從 A 到 D，計畫依序在你腦中（A 手動平行）、主 agent（B subagent）、lead 與共用清單（C agent team）、script 裡（D workflow）。計畫在哪裡，決定了誰負責派工、誰負責整合，也決定了這個做法能撐到幾個 agent。每個 worker 都有自己的 context；差別在結果怎麼交回，以及交回給誰。E 是 slide 的第三個軸：時間，由停止條件決定一個 agent 什麼時候結束。第 2 段會先講三個案例，再依 A 到 E 的順序把每一種做法講清楚；2.5 末尾的 /implement-spec 是一個同時用到 A、B、D 的真實例子。

沒有 hook，拿什麼保證 skill 會用到。2.1 的教訓是：skill 裝了，model 不一定用，Superpowers 用 hook 補這個洞。這套沒有 hook，它靠三件事。入口是 user-invoked，你打了就一定載入，不靠 model 判斷；這等於把「要不要走流程」這個決定交回給人。紀律是 model-invoked，靠 description 裡的觸發詞讓 model 自己挑，這一層沒有保證，和 2.1 裝了 skill 的狀況一樣。流程裡的 skill 用「Call the Skill tool with "tdd"」這種句子點名下一個，作者說寫成 tool 呼叫比寫 /tdd 命中率高。

名詞ADR、ubiquitous language、tracer bullet、seam：這套 skill 從四本書借的名詞

這套 skill 借了四個名詞：

  • ADR。ADR 是 Architecture Decision Record：一頁的決策紀錄，寫背景、決定、後果，放在 docs/adr/，一個決定一個檔案。
  • Ubiquitous language。它來自 Eric Evans 的 Domain-Driven Design：開發者和領域專家共用同一套詞，程式碼裡的名字也用它。這套 skill 把它寫成 GLOSSARY.md。
  • Tracer bullet。它來自 The Pragmatic Programmer：先打一條穿過每一層（schema、API、UI、測試）的細路徑，能動了再加寬。to-tickets 要求每張 ticket 都是這種垂直切片。
  • Seam。Seam 是測試落點：模組對外的邊界，從外面觀察行為、不碰內部。tdd 規定只在事先講好的 seam 寫測試。

逐步看。grilling 把一個計畫畫成 design tree：每個決定底下掛著它引出的決定。它一輪問完整個 frontier，也就是前提已定、現在就能問的題；每題附建議答案，題目寫成「你答 yes 就是接受建議」。答案改變了樹，它再算一次 frontier，問下一輪。兩條規則值得記：查事實是 agent 的工作，要查檔案就派 subagent，不問你；決定才是你的。Frontier 空了才算完，而且要你確認想法一致，它才能動手。

to-spec 不再問你，它把對話整理成 spec，用專案的 glossary 詞彙寫，先和你確認在哪幾個 seam 測（越高、越少越好，理想是一個），再發到 issue tracker 並貼 ready-for-agent 標籤。Spec 的欄位固定：問題、解法、一長串 user story、實作決定、測試決定、範圍外。它禁止寫檔案路徑和程式碼片段，因為那些過期最快。to-tickets 把 spec 拆成 ticket，每張是一條穿過每一層的 tracer bullet，大小以一個新的 context window 裝得下為準，各寫明 blocked by 哪幾張。它把拆法列給你看，問粗細和邊對不對，你核准才發。發到 GitHub 用原生的 blocking 關係；本機 tracker 就一張 ticket 一個檔案：

implement 做一張：抓 ticket、在講好的 seam 上跑 tdd、常跑 typecheck 和單檔測試、最後跑一次整套，然後叫 code-review，再 commit。code-review 比對 HEAD 和一個固定點的 diff，分兩軸：Standards 看有沒有照 repo 的規範（加一組 Fowler 的 code smell 當底線），Spec 看有沒有做到 issue 要的。兩軸各派一個 subagent 平行跑，SKILL.md 寫明理由：不讓兩邊污染彼此的 context。報告並排，不合併、不排名，因為兩軸會互相遮掩：照規範但做錯東西，或做對東西但壞了慣例。

一張一張 /implement 是手動模式。/implement-spec 一次做整份 spec：把 ticket 當 task graph，沒有 blocker 的 ticket 各派一個 subagent 在自己的 worktree 做，做完再派一個 subagent 合併。它要先懂 worktree 和 subagent 才看得懂，所以放在 2.5 的末尾當案例。

可靠性的零件：tdd、diagnosing-bugs、retro。2.7 的結論是「不期待 agent 確定，讓周邊系統可靠」。這套 skill 裡負責周邊系統的是三個 model-invoked skill。tdd 有四條規則：

  • 先和你講好 seam，不在沒講好的 seam 寫測試。
  • 紅在綠之前，只寫剛好讓測試過的程式。
  • 一次一個 slice。
  • Refactor 不在迴圈裡，留給 review。

它列了三種壞測試：綁住實作細節的、assert 用和程式一樣的算法算出來的（永遠過）、先寫完所有測試再寫實作的（測的是想像的行為）。

diagnosing-bugs 把 2.6 的「可以檢查的終點」寫成 bug 版。它的 Phase 1 只做一件事：建一個會因為這個 bug 變紅的 feedback loop。完成條件寫得很硬：你要能說出一個指令（測試、curl、script），已經至少跑過一次，而且它會抓到使用者講的那個症狀、每次結果一樣、幾秒跑完、不用人介入。沒有這個指令，不准進下一階段提假設。/goal 的檢查 model 只讀對話，所以證據要出現在輸出裡；diagnosing-bugs 要求一個已經跑過、會變紅的指令。兩個作者從不同方向走到同一條規則。它對 flaky bug 的做法也和 2.6 一致：不追求乾淨的重現，而是把重現率拉高到能 debug，例如跑 100 次、加壓力、縮時間窗。

retro 在做完之後跑，改的是 agent 的環境，不是程式：哪裡找檔案花太久（加一個導航指標）、哪個錯誤自動檢查能抓（加 lint、型別、測試）、哪條規範該給 reviewer。它把規範分兩類：機械的（固定的語法樣式、禁用的 API、檔案位置）一律變成確定的檢查，lint 規則、pre-commit hook 或 CI；只有判斷題才留在 CODING_STANDARDS.md。這是 2.7 說的 VERIFY：便宜而頻繁的檢查，勝過最後一次昂貴的 review。它還有一條對 CLAUDE.md 的看法：這個檔案每個 agent 都載入，所以只放導航指標；規範放在 review 階段讀的檔案，因為 reviewer 的 context 壓力最小，只拿到一份 diff。

GLOSSARY.md：用共用語言省 token。README 的第二個失敗模式是囉嗦，作者的例子是他自己的 repo：改之前要說「一門課程裡某一節底下的 lesson 變成『真的』，也就是在檔案系統上有了位置」；有了 glossary 之後只說「materialization cascade 有問題」。domain-modeling 負責建這份語言，做四件事：

  • 指出衝突。你用的詞和 glossary 衝突，就當場指出。
  • 換成精確的詞。詞太模糊，就提一個精確的（你說 account，是 Customer 還是 User？）。
  • 測邊界。用具體情境測詞的邊界。
  • 對程式碼。你說程式怎麼運作，它去對程式碼，不一致就問。

2.3Caveman：token 要雙向壓縮，輸入方向只有 proxy 管得到 p.15–25

前兩章改的是 agent 做事的順序，這一章的 Caveman 改的是 token 的進出，而且把 2.1 那張表的五種機制全用上，還多一個 proxy。這章先講它要解的問題，再依輸出、輸入兩個方向看每一種機制站在哪裡，最後把三個 plugin 並排。

為什麼要壓縮 token。Caveman 是一個專門省 token 的 plugin。它要解決的問題來自 L4 講的 context 代價：log、diff、tool 輸出會塞滿 context；每一圈 loop 都重送整個 context，所以一份長 log 進了 context，之後每一圈都要再付一次錢和時間；等到 context 快滿才做 compaction，又會把重要的細節摘掉。Slide p.16 的例子：

前情Context 的代價與四種管理策略（L4）：這堂一直用到的四個名詞

Context 是每一圈送進 model 的全部文字：system prompt、tool 定義、對話歷史、每一筆 tool 結果；上限叫 context window。L4 說它有三種代價。錢：model 沒有記憶，每一圈都要把整個 window 重送一次，一份 786 行的 log 進了 context，之後每圈都再付一次。延遲：prompt 越長，model 讀得越久。注意力：window 越滿，model 越難找回中間的資訊。

L4 給了四種管理策略，由無損排到有損：

  1. Admission。在內容進 window 之前把關，只放需要的部分（截斷、整形、交給 subagent）。
  2. Offloading。把內容放在 window 外面，只留一個 handle，要用再讀回。
  3. Transformation。把舊的或重複的 tool 結果換成一行占位文字。
  4. Compaction。用 LLM 把舊歷史寫成一段摘要換掉原文，有損又不可逆，所以排在最後。

Claude Code 的 /compact 和自動 compaction 就是最後一種。

Caveman 的 proxy 做的是 admission，caveman_compress 回 handle 是 offloading，Superpowers 的 hook 在 compaction 之後重新注入規則，就是在補 compaction 丟掉的東西。細節見 L4 的 2.6 與 2.7。

Caveman 的目標就是讓 model 只讀到那一行，原文留著，要的時候再取。Token 有兩個方向：model 讀進去的叫 input，model 寫出來的叫 output。Caveman 兩邊都壓（slide p.17）。輸出方向用一個 skill：它規定回答的風格，model 載入後就寫得短。Agent 每跑一圈，就把整段 context（system prompt、之前的對話、這次的 tool 輸出）打包成一個 request 送給 model；model 讀完，寫一個回答送回來。輸入方向用一個本機 proxy：每個 request 都先經過它，它把 log、diff 壓短再送出去。一句話記：skill 改 model 怎麼寫，proxy 改 model 讀什麼。

B · 多個 agent：三個擴展軸

2.4平行與 subagent：各買到一樣東西，也各有代價 p.26–37

三個擴展軸。三個案例都是一個 agent 在做事。要做更多事，slide p.27 把擴展分成三個軸，每個軸買到一樣東西：

  • 平行。很多個獨立的任務同時做，每個在自己的工作目錄裡。買到 throughput，也就是單位時間做完的事變多；答案不會更好。
  • Subagent。把一個有邊界的任務交給一個新的 context 去做，只拿一段摘要回來。買到 throughput 和專注；主對話永遠看不到中間的雜訊。
  • 長時間執行。讓一個 agent 跨很多步做一件大事。買到範圍，也就是用更少的介入做更多事。

前兩個軸同時用更多 agent，第三個軸讓一個 agent 做更久，留到 2.6。這一章講前兩個軸的基本做法：A 手動平行，靠 git worktree 隔離檔案；B subagent，把任務交給另一個 context。Agent team 和 dynamic workflow 是這些軸的組合，2.5 再講。

名詞Throughput、latency、critical path：量「快」的三個字

Throughput 是單位時間做完多少事，例如一天 merge 幾個 PR；latency 是一件事從開始到做完要等多久。平行提高 throughput，不會降低單一任務的 latency：10 個 session 一天做完 10 件事，每一件還是要花原本的時間。

Critical path 是一串必須依序做、不能平行的步驟裡最長的那一條：規劃要先做完才能派工，所有子任務做完才能整合。整件事的最短時間由它決定，再多 agent 也壓不下去；2.6 用 Amdahl's law 算這件事，L5 把它寫成估算式。

A 手動平行：一個任務一個 worktree。最簡單的擴展是自己開好幾個 session，一個 session 做一件事。問題是它們在同一個 repo 裡會互相踩：一個 session 改到一半的檔案，另一個 session 會看到。Git worktree 解決這件事。先回想 git 的結構：一個 repo 有一個 .git 目錄，裡面存全部的歷史、branch 和檔案內容；你平常看到的那些檔案叫工作目錄，它是某一個 branch 的一份 checkout。一般的 repo 只有一個工作目錄，所以一次只能站在一個 branch 上，要換 branch 得先 stash 或 commit。Worktree 讓一個 .git 同時掛好幾個工作目錄：

Worktree 有兩個限制要知道。同一個 branch 不能同時在兩個 worktree 裡 checkout；新目錄裡也沒有 .env、node_modules 這類不在 git 裡的檔案，要重新裝。更重要的是它只隔離檔案：port、資料庫、外部服務還是共用的，最後的 merge 也還是你的事。主幹在你做事的時候也會動：執行期用 worktree 把別人的 commit 擋在目錄外面，合併期換一個沒有執行期歷史的新 context 做 merge，並把「為什麼這樣改」寫進 commit message。這個建議的根據是一個 2026-10 的 benchmark，本章末尾的本文延伸說明。Slide p.30 說明這個做法撐到哪裡：3 個 session 你還記得住計畫，20 個 session 你需要一個分身。四個原因：

  • 計畫在你腦中。每一次交接都靠你。
  • Session 之間看不到彼此。發現要靠你搬過去。
  • Branch 要你來 merge。順序和衝突都是你的。
  • 沒有人把整件事記下來。下次不能重跑。

接下來的三種做法，分別把這四件事交給別人。

B Subagent：結果回到主 agent。Subagent 是一個專門的小助手，有自己的 context window、自己的 tool 清單和權限（slide p.31）。主 agent 把一個任務交給它，它在自己的 context 裡做完，只交回一段摘要。Slide 列了五個理由：

  • 保護 context。log、搜尋結果、整個檔案的內容都留在 subagent 裡，主對話只多一段摘要。
  • 限制。可以規定 subagent 只能用哪些 tool，例如只能讀不能寫。
  • 重用。一份寫好的 subagent 定義可以跨專案、跨團隊用。
  • 平行。互相獨立的子任務可以同時跑，例如 style-checker、security-scanner、test-coverage 三個一起，總時間等於最慢的那一個。
  • 省錢。簡單的任務可以指定用便宜快的 model，例如在定義裡寫 model: haiku。

上圖把第一個理由畫出來。同一個搜尋任務，主對話自己做，檔案、log、搜尋結果全進了主對話的 context，之後每一圈都重送，快滿時 compaction 還可能把細節摘掉。交給 subagent，這些中間產物留在 subagent 的 context 裡，做完就丟掉，主對話只多一段摘要。這是有損壓縮：30 份文件換成一頁結論，所以委派時要指定回報格式，例如「每個問題附 file:line」，不然細節就沒了。代價還有一個：subagent 看不到主對話的歷史，它要從零開始收集 context，所以多一段延遲。

上面說 worktree 只隔離檔案，最後的 merge 還是你的事。讀書會成員轉來一段評論（2026-10-29），把這件事往前推了一步：它引用一個 benchmark，說 agent 做到一半時主幹一變，成功率跌到兩成；接著建議執行期用 git worktree 隔離，合併期清空對話歷史，兩件事一起做才有用。本文先查證這個 benchmark，再判斷這個建議成不成立。Benchmark 是 SWE-Shift（Huang 等，arXiv 2026-10-23）；數字依它的摘要與 repo 公布的結果檔（2026-10-30 比對）。

SWE-Shift 量什麼。SWE-bench 這類 benchmark 給 agent 一個 issue，改到測試通過就算解出，而且假設任務開始後 repo 不會動。SWE-Shift 問的是：做到一半 repo 變了，agent 還做得完嗎。它有 120 個場景，分成 12 類變動，每類 10 個；每個場景在參考軌跡上取 9 個節點 T10 到 T90（進度的一成到九成），到了節點就把 agent 的 workspace 和對話存下來，分成兩條繼續：Clean 照舊做完，Shifted 先注入變動再做完。注入是腳本做的：改 workspace 的檔案、送一則訊息，或換掉 tool 的回應。

Subagent 只向主 agent 回報，而且計畫還在主對話裡。這一章講另外兩種做法：agent team 讓成員互相傳訊，dynamic workflow 把計畫交給一支 script；接著把 A 到 D 放在一起，給一條選擇規則；最後用 2.2 的 /implement-spec 看一個真實的 skill 怎麼組合 A、B、D。

C Agent team：成員互相傳訊。Subagent 只會向主 agent 回報，彼此不講話。Agent team 把這一點改掉（slide p.38）：好幾個 Claude Code session 一起工作，一個 lead 加幾個 teammate，teammate 之間可以直接傳訊息。Slide p.39 列了四個零件：

  • Team lead。你的主 session，負責生出 teammate、協調、整合結果。
  • Teammate。獨立的 Claude Code 實例，各有自己的 context window。
  • Task list。一份共用的任務清單，teammate 從裡面認領任務、做完標記完成。
  • Mailbox。每個 agent 一個 JSON 收件匣，teammate 把訊息放進對方的收件匣。

要注意 teammate 不會繼承你的對話，它們只自動載入 CLAUDE.md 和 skill，所以任務的細節要寫在生出它們的那段 prompt 裡。Team 適合需要討論的工作，slide p.38 舉了四種：

  • Review。幾個 teammate 從不同角度看，再互相挑戰對方的發現。
  • 獨立模組。幾個獨立模組各由一個 teammate 負責。
  • 除錯。幾個假設平行驗證，收斂得快。
  • 跨層的工作。前端、後端、測試各一個。

代價是協調開銷和 token 都隨人數成長，因為每個 teammate 都是完整的 session。所以順序相依的任務、改同一個檔案的任務、彼此依賴很重的任務，交給一個 session 或 subagent 比較好。

D Dynamic workflow：script 持有計畫。當一個任務需要的 agent 多到一個對話協調不了，例如掃整個 codebase 找 bug、500 個檔案的搬遷、從好幾個角度交叉查證一份研究，就用 dynamic workflow（slide p.43）。它是一支 JavaScript script，在背景調度很多 subagent，有三個性質：

  • 計畫在 script 裡。不在對話裡。
  • 中間結果存在 script 的變數裡。不進主 context。
  • Script 可以重跑。這正好補上手動平行做不到的「記下來」。

在 Claude Code 裡有兩種啟動方式：在 prompt 裡打「ultracode」，或是用 /effort ultracode 讓 Claude 自己決定；兩種都會生出很多 subagent 去規劃、設計、實作、review。代價是每個任務用的 token 更多。

A 到 D 怎麼選。把四種放在一起，選擇規則是三句：只要結果，用 subagent；需要討論，才用 team；agent 多到對話協調不了，就用 workflow。第 1 段的架構圖就是這四種做法並排，藍框標出計畫在誰手上。

案例：implement-spec 怎麼組合 A、B、D。2.2 的 mattpocock/skills 有一個 user-invoked skill /implement-spec，一次做整份 spec。它的 SKILL.md 只有 40 行，卻把第 1 段架構圖的 A、B、D 各用了一次：

  1. 讀 spec 和 ticket，把它們當 task graph：有 blocking 關係，所以隨時有一個 frontier，也就是可以直接開工的 ticket。
  2. 可選：先派一個 exploration subagent 探路，把筆記存在 repo 外面的目錄，之後所有 subagent 都讀得到，implementer 就不用各自再探一次。
  3. 開一條 integration branch。
  4. Frontier 上的每張 ticket 派一個 implementer subagent，各在自己的 worktree、自己的 branch 上做（2.4 的 A）。它先確認 worktree 基於 integration branch，用 tdd 做，回報前先把 integration branch 的最新版 merge 進來。
  5. 做完一個，派一個 merger subagent 把它合進 integration branch（2.4 的 B：只交回結果）。
  6. Frontier 變了，就再派新的 implementer。這一步讓平行度最大。
  7. 全部做完，對 integration branch 跑一次 code-review，問題交給一個 implementer 修。
  8. 把 draft PR 標成可 review，或依 tracker 的方式結案；清掉所有 worktree。

SKILL.md 另外規定：和 subagent 的溝通要少，主要用 context pointer，也就是指向 spec、ticket、研究筆記、commit 的連結，不複製內容。這和 2.4 說的「委派時只交任務訊息」是同一件事。放回第 1 段的架構圖，它用了其中三種：

  • D 的性質。計畫在 ticket 裡，不在對話裡，所以可以重跑。
  • B。派工的是主對話。
  • A。每個 worker 一個 worktree。

它沒有 C，implementer 之間不講話。和 2.6 的 C compiler 比，這裡不需要 lock file，因為派工的只有一個主對話；C compiler 有 16 個對等的 agent，才要用 git 裁決。Frontier 就是 2.4 註講的 critical path 的另一面：有 blocker 的 ticket 要等，沒有的才能平行。代價也有：主對話持有派工狀態，ticket 多了 context 會滿；merge conflict 和 p.50 一樣常見，只是交給 merger subagent 解。巢狀 subagent 的上限（2.4 說最多 5 層），作者明文不在 skill 裡擋，交給 harness：Claude Code 用環境變數 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH 設。

2.6長時間執行與 16 個 agent：終點要能檢查，加 agent 有上限 p.44–50

/goal：給一個可以驗證的終點。2.4 的第三個軸是時間：讓一個 agent 做更久。/goal 給 Claude 一個條件，它一直做到條件成立為止（slide p.44）。它的運作方式是：Claude 做一輪，每一輪結束後，另一個小而快的 model 讀對話，判斷條件是否成立；沒成立就把 Claude 送回去再做一輪；成立就停，或是 --max-tries 用完也停。關鍵在於做事的 model 不能自己宣布完成，判斷的是另一個 model。

所以條件要能從對話裡證明。「npm run lint exits with zero errors」可以檢查，因為 lint 的輸出就在對話裡。「refactor the code」無法檢查，因為沒有一個輸出能證明重構完成。檢查的 model 不跑指令、不讀檔案，只讀對話，所以證據必須出現在 Claude 的輸出裡。還有一個陷阱：「所有測試通過」可以靠刪掉失敗的測試達成。所以條件旁邊要加不變量，例如「不修改 tests/」。這是 Goodhart's law：指標一旦變成目標，就不再是好指標。

/loop：用時間觸發。/loop 是另一種長時間執行（slide p.45）。它是一個觸發器，不是一個測試：你設定間隔，它每次都跑同一段話，不判斷做完了沒；做完了也照跑，直到你在它等待時按 Esc 取消。兩者的差別一句話：/goal 在條件成立時停，/loop 在你叫它停時停。Slide p.46 把整個後半收成兩組：讓一個 agent 做更久（/goal、/loop）；同時用更多 agent（手動平行、subagent、agent team、workflow）。

16 個 agent 寫一個 C compiler。Anthropic 的 C compiler 案例是長時間執行放大到極限的版本（slide p.47）：16 個 agent 平行，約兩週、約 2,000 個 session，用了 20 億 input token 和 1.4 億 output token，API 費用略低於 20,000 美元。結果是一個約 100,000 行 Rust 寫的 C compiler，能編譯 Linux 6.9 kernel，在 x86、ARM、RISC-V 上都能跑，也能編譯並執行 QEMU（模擬器）、FFmpeg、Postgres、Redis 和 Doom，主要測試套件的通過率約 99%。注意 input 是 output 的 14 倍，這就是 2.3 說輸入方向更值得壓縮的原因。

為什麼 16 個 agent 不會快 16 倍：Amdahl's law。2.5 的四種做法都在回答同一件事：多派幾個 agent，工作會快多少？直覺的答案是 16 個 agent 快 16 倍，但實際上不會。一件工作裡總有些步驟只能一件一件做：規劃要先寫完，才能把子任務派出去；16 份結果交回來，要有人合併；合併完，還要有人 review。這些步驟花的時間，派再多 agent 也不會變短。

這是 IBM 的電腦架構師 Gene Amdahl 在 1967 年提出的論證。當時大家在爭論多處理器的電腦值不值得做，他指出：處理器加再多，程式裡只能循序執行的那一段還是一樣慢，所以加速有上限。原本講的是 CPU，把「處理器」換成「agent」，道理完全一樣。它的做法很簡單：把一件工作的時間切成兩塊，一塊能平行、一塊不能平行，然後問：能平行的那一塊交給 n 個 agent 分著做之後，總時間還剩多少？

假設一個 agent 從頭做到尾要 100 分鐘。其中 20 分鐘只能一個 agent 做：規劃 5 分鐘、合併 10 分鐘、review 5 分鐘。剩下 80 分鐘是改 300 個彼此無關的檔案，可以拆開。改成 16 個 agent 時，不能平行的 20 分鐘不變；能平行的 80 分鐘由 16 個 agent 分，每個做 5 分鐘。總時間是 20 ＋ 5 ＝ 25 分鐘，所以加速是 100 ÷ 25 ＝ 4 倍。把總時間 100 換成 1，就是原本那條式子：

三個推論。第一，加速有上限，等於 1 ÷ s：n 變得很大時，p ÷ n 趨近 0，總時間只剩不能平行的 s，所以 s 是 20% 時上限 5 倍，10% 時 10 倍。第二，每多一個 agent，省下的時間越來越少：從 1 個加到 4 個省了 60 分鐘，4 個加到 16 個只再省 15 分鐘，16 個加到 64 個只再省 3.75 分鐘；但 token 費用不會跟著遞減，2.5 說過每個 agent 都是完整的 session，費用大約跟 agent 數成正比，所以 16 個 agent 只快 4 倍，平均每個只發揮 25% 的效用。第三，要更快，先縮短不能平行的部分：同樣 16 個 agent，把 s 從 20% 降到 10%，加速從 4 倍變成 1 ÷（0.1 ＋ 0.9 ÷ 16）≈ 6.4 倍；s 不動、agent 加到 64 個，只到 4.7 倍。縮短循序的部分比加 agent 有效。在 agent 的工作裡，就是讓那些「只能一個人做」的步驟變小：

  • 規劃。計畫先寫成 dynamic workflow 的 script，不在對話裡邊聊邊規劃（2.5 的 D）。
  • 合併。拆給每個 agent 自己做。像上面的 C compiler 案例，每個 agent 自己 pull、解 conflict、push，沒有一個總負責人在最後一次合併全部。
  • Review。盡量交給自動測試，而不是等一個人從頭讀到尾。

真實情況比 Amdahl's law 算的還差。它假設不能平行的 20 分鐘是固定的，但 agent 一多，要協調的事也變多：16 個 agent 改同一個 repo，merge conflict 很常見，這就是 p.50 的第一項；agent team 的 teammate 互傳訊息，量隨人數成長。所以循序的部分會隨 n 變大，過了某個 n 總時間還會回頭變長。L5 把這件事寫成估算式：總時間約等於規劃、critical path（2.4 的註）、溝通、合併四項相加，平行只能縮短 critical path，它也算出拆成幾份最快（L5 的 2.5）。反過來，工作量不固定時結果會好一些：1988 年 John Gustafson 指出，機器變多時人通常拿它去做更大的工作（Gustafson's law），規劃和合併沒有變多少，能平行的部分卻大了好幾倍，s 就變小。這也是 2.5 說 dynamic workflow 適合「掃整個 codebase、500 個檔案的搬遷」這種大工作的原因。

任務切不開，加 agent 也沒用。p.50 的第二項是 Amdahl's law 的極端情況：平行的部分變成 0。編譯 Linux kernel 時，所有 agent 都卡在同一個錯誤。原文寫道：每個 agent 都修同一個 bug，再互相覆蓋彼此的修改。

原文的解法，是把一個大的失敗訊號切成很多小訊號。作者用 GCC 當已知正確的 oracle（測試裡用來判斷對錯的標準答案來源）：隨機挑大部分檔案用 GCC 編譯，其餘檔案才用 agent 寫的 compiler。Kernel 能跑，問題就不在那些檔案；壞了，就再縮小範圍。每個 agent 因此拿到不同的失敗檔案，可以平行修不同的 bug。

一般原則：平行需要獨立的子任務，也需要獨立的進度訊號。只有一個大測試失敗時，先把它拆成很多小訊號，再考慮加 agent。

C · 退一步看：不確定性與人的角色

2.7Programming 3.0：接受不確定性，讓周邊系統可靠 p.51–59

三代程式設計。前面都在講怎麼改一個 agent、怎麼用更多 agent。最後兩章退一步問：這種寫程式的方式，和以前差在哪裡；人的角色又變成什麼。講者把它叫 Programming 3.0（slide p.52），用「人寫什麼」分三代。1.0 是人直接寫機器指令或組合語言，交給硬體。2.0 是人寫程式語言，compiler 翻成機器指令。3.0 是人用自然語言說目標，agent 寫程式語言，再由 compiler 翻成機器指令。每一代都在人和硬體之間多加一層；產能變高，不確定性也變高，因為 compiler 是確定的，agent 不是。

Karpathy 的 Software 3.0 是另一種分法。Slide p.53 放了它，兩者名字像，分法不同，不要混。Karpathy 用「程式是什麼」分成三代：

  • 1.0。程式是原始碼，人用 Python 或 C++ 寫。
  • 2.0。程式是神經網路的權重，人收集資料再用 optimizer 訓練出來。
  • 3.0。程式是 prompt，人用自然語言寫，LLM 執行。

他的結論是：知道在哪裡劃 1.0、2.0、3.0 的界線，是一項重要的工程技能。兩種分法導向同一個工程問題：哪一塊用確定的程式，哪一塊交給 model。拿 2.3 的 Caveman 當例子，壓縮 engine 是 1.0 的程式，回答風格寫在 skill 裡，屬於 3.0；2.2 的 retro 把機械的規範變成 lint，也是把 3.0 的事搬回 1.0。

不確定性是新的嗎。Slide p.54 只有一句話：不確定性變成核心主題，你要學著和它共處。但 p.55 接著指出，不確定性早就存在：

硬體環境軟體
2.0 早就有32 位元 vs 64 位元、endianness並行、不可靠的網路compiler 版本、相依套件漂移
2.0 的解法固定寬度的型別、cross-compilation、虛擬化memory consistency model、冪等的 API升級前跑完整的測試
3.0 新加的GPU 的 nondeterministic kernel、浮點數差異agent 在寫程式的過程中就會碰環境compiler 和 model 都有多種 kernel 與取樣

依 p.55 整理。結論是：同一份原始碼產生不同結果，很久以前就發生了，2.0 的對策可以沿用。那 3.0 新增的不確定性在哪裡？Slide p.57 列了四個來源：

  • 自然語言。語意本身不確定。
  • 檢索的漂移。索引更新、切 chunk、context 截斷都會改變 model 看到的東西。
  • Model 生成的機率性。取樣加上軟硬體的 nondeterminism（同一個輸入，因為浮點運算順序或執行緒排程不同而算出不同結果，L1 講過）。
  • Agent 和 tool 的迴圈。軌跡、環境、tool 失敗、環境改變。

重點是 slide 的最後一行：程式產生之後通常是確定的，除非它在執行時又呼叫 model 或 tool。所以不確定性集中在產生程式的階段；程式碼經過 commit、review、測試之後，可以用 2.0 的老方法管。

怎麼和不確定性共處。Slide p.58 給的做法分三組：

  • DEFINE。先把假設寫出來；有歧義的地方讓 model 先確認再動手。
  • CONTROL。把提案和執行分開，agent 先提計畫，驗證過才 commit。明確管理 context：自己管 memory、來源和檢索，讓過時的資訊過期。寫結果而不是寫 prompt：需求、不變量、限制和驗收測試。
  • VERIFY & GOVERN。把產生和驗證的迴圈收緊，便宜而頻繁的檢查勝過最後一次昂貴的 review。量深一層：自己寫測試、看多個指標、用自己能推理的合成負載。

兩句原則。最後是 p.59 的兩句原則：不要期待 agent 是確定的，讓它周圍的系統可靠；自主程度要配合風險，自主越高，不確定性和風險越高。回頭看這堂課，前面的 hook、可驗證的終點、lock file、測試，都是「周圍的系統」的零件。

    重點拆解

    流程寫在 skill 裡。Slide 列了 Superpowers 的 9 個 skill（p.7）；repo 現在有 15 個，見 2.1 最後一段。每個 SKILL.md 的 frontmatter 是 metadata，例如 name 和 description；body 是 agent 照著做的步驟（p.9）。以 brainstorming 為例，最後兩步是「等使用者核准」和「載入 writing-plans」。流程型的 skill 還寫明進入條件、禁止的動作、人工核准的關卡和下一個 skill（p.10）。每個 skill 指向下一個，流程就自己接下去。

    只有 skill 還不夠。Skill 放在那裡，不代表 agent 會去查（p.11）。Model 依 description 決定要不要載入；任務看起來簡單時，它可能直接寫 code。所以 Superpowers 加了 SessionStart hook。Hook 讀出 using-superpowers 這個 bootstrap skill，用 additionalContext 加進 context（p.12）。這份內容是「怎麼選 skill」的規則。Hook 設 async: false，所以它在 agent 動作之前跑完（p.11）。

    三個時機，都是 context 可能沒有規則的時候。Startup 是全新的 context。/clear 清掉整段對話，先前注入的規則也一起消失。Compaction 把舊對話壓成摘要，規則可能被省略。所以 hook 在這三個時機都重新放一次。

    背景補充

    這是 L2 講的分工。寫在 skill 或 CLAUDE.md 的規則，是對 model 的要求：model 大多會照做，但沒有保證。Hook 是程式，時機到了就一定執行。Superpowers 用 hook 保證規則在 context 裡；要載入哪個 skill，仍由 model 判斷。

    Skill 會被跳過，根源是漸進載入：一開始 context 裡只有每個 skill 的名稱和描述，全文要等 model 決定載入才讀進來。這樣省 context，但 model 也可能沒查就動手。Plugin 是打包的單位，skill、hook、command 一次安裝、一起更新（p.8、p.25）。

    例子

    在 Claude Code 的 session 裡輸入 /plugin install superpowers@claude-plugins-official 安裝（p.5）。開一個新 session，打「Add authentication」。Agent 會先載入 brainstorming，問你需求、提出設計，等你核准才載入 writing-plans（p.13）。想在自己的專案做同樣的事，照〈動手試試〉第一個範例寫 .claude/settings.json。

    帶走這幾點
    1. Model 和 tool 都沒換，只換了 context 裡的流程指示 → agent 的行為就不同。
    2. 要不要載入 skill 由 model 判斷；hook 是程式，保證規則一定在 context 裡。
    3. Matcher 要含 clear 與 compact：這兩個時機會清掉或摘要掉先前注入的規則。

    相關：核心觀念〈Superpowers：skill 寫流程，hook 保證規則一定在 context〉、L2〈機率性與確定性〉、〈漸進載入〉、動手試試的 SessionStart hook 範例。進階題第 3 題把團隊流程寫成 skill 鏈。

  2. p.16–24 · Caveman 的雙向壓縮

    Caveman 從哪兩個方向壓縮 token？輸入方向為什麼要用 proxy，不用 hook？

    參考答案與重點複習

    答案：輸出方向靠 response skill，讓 model 寫得短；slide 的數字是 output token 少 65%（p.17）。輸入方向靠本機 proxy，壓縮 model 讀到的 log、diff、tool 結果；p.16 的例子把 786 行的 npm test 輸出壓成 1 行。壓縮輸入要改寫送給 model 的每一個 request。Hook 不能透明地改寫 LLM request；proxy 位在 coding agent 和 model provider 之間，每個 request 都經過它（p.24）。

    重點拆解

    Log、diff、tool 輸出會塞滿 context（p.16）。Agent 每一圈 loop 都重送整個 context，所以一份長 log 進來以後，之後每一圈都要再付一次。等 context 快滿才修剪，重要的資訊可能已經被剪掉（p.16）。所以 Caveman 在資料進 context 時就壓，兩個方向都壓，而且保留原文。

    輸出方向用 skill，改的是 model 怎麼寫（p.17）。它保留技術名詞、指令、路徑、程式碼、錯誤、數字、單位和否定詞；刪掉贅字、重複、客套和含糊的保留語（p.20）。結果是 output 少 65%（p.17）。

    輸入方向用 proxy，改的是 model 讀到什麼。這個方向的量更大：C compiler 案例用了 2B input、140M output token（p.47），2B ÷ 140M ≈ 14 倍。Proxy 依內容類型壓縮：log 留錯誤、stack trace、開頭和結尾；diff 留檔案與 hunk 標頭、改動的行（p.24）。Agent 需要細節時，用 MCP tool caveman_retrieve 取回逐 byte 相同的原文（p.23）。

    為什麼一定要 proxy？Hook 綁在事件上。改 tool 的 hook 在單一 tool call 前後執行，只能改那一個 tool 的輸入或輸出，碰不到整個 request。所以一筆 tool 輸出，PostToolUse hook 換得掉（2.3）；system prompt 和之前的對話，它換不掉。MCP 只在 agent 呼叫時執行，也改不了 context。只有夾在中間的 proxy，每個 request 都經過（p.24）。自己寫 harness 的話，也能在 harness 裡改。

    背景補充

    Proxy 是網路系統的老做法：在兩端之間插一層，兩端都不用改。公司常用的 LLM gateway 也是這種 proxy，用來集中管 API key、用量和紀錄。Claude Code 可以用環境變數 ANTHROPIC_BASE_URL 把 request 送到 gateway 或 proxy。

    這也是 L2 的分工：壓縮 log 是確定的程式，交給 engine；回答的風格需要判斷，寫進 skill 交給 model。

    常見誤解

    「Output 少 65%，整個 session 就省 65%。」Output 只占 token 的一小部分；skill 本身還多佔 input token，所以整個 session 省得更少（p.17）。要大幅省 token，重點在輸入方向。進階題第 2 題會用數字比較兩個方向。

    例子

    在終端機輸入 claude plugin marketplace add JuliusBrussee/caveman，再輸入 claude plugin install caveman@caveman 安裝（p.15）。然後開一個 session，輸入 /caveman ultra，再打「Run the tests and explain the failure.」（p.17）。等級有 lite、full、ultra、off，預設 full（p.21）。

    帶走這幾點
    1. 輸出方向：skill 改 model 怎麼寫。輸入方向：proxy 改 model 讀到什麼。
    2. Input 約是 output 的 14 倍 → 大宗在輸入方向，而只有 proxy 管得到每一個 request。
    3. 壓縮要能還原：原文保留，agent 需要細節時用 caveman_retrieve 取回。

    相關：核心觀念〈Caveman：token 要雙向壓縮，輸入方向只有 proxy 管得到〉、L4〈Context 的成本〉、L8〈Input token：留在 context 裡的 token，之後每一步都再付一次〉。進階題第 2 題算省多少，也討論壓縮的風險。

  3. p.27–31 · 三個擴展軸

    擴展的三個軸各買到什麼？Subagent 怎麼保護主對話的 context？

    參考答案與重點複習

    答案：平行的 session（廣度）買到 throughput，縮短牆上時間，答案不會更好；subagent（廣度＋深度）買到 throughput 與專注；長時間執行（時間）買到更大的範圍、更少人工介入（p.27）。Subagent 在自己的 context window 做事，log、搜尋結果、整份檔案都留在那裡。主對話只收到摘要（p.27、p.31）。

    重點拆解

    三個軸回答三個問題：同時跑幾個、交出去多少、一個 agent 跑多久。Agent team 和 workflow 是這三個軸的組合（p.27）。

    平行 session 最直接：一個任務一個 session，各在自己的 git worktree，改動互不影響（p.28）。它只買到時間，每個任務仍是一個 agent 的水準。開幾個 session 是生產力；開到 20 個，你需要一個自己的分身（p.30）。原因有四個：計畫只在你腦中、session 互相看不到、branch 要你自己整合，而且整個過程無法重跑。

    Subagent 靠 context 隔離保護主對話。每個 subagent 有自己的 context window、tool 和權限（p.31）。它讀的檔案、跑的 log 留在自己的 context；做完只交回摘要，主對話看不到中間過程（p.27）。主對話每一圈都重送整個 context，所以少放 30 份檔案，之後每一圈都省。代價是摘要會丟細節；subagent 也看不到對話歷史，要花時間從零收集 context（p.37）。

    背景補充

    Context 隔離很像函式呼叫。被呼叫的函式有自己的 local 變數；return 之後變數就釋放，呼叫者只拿到回傳值。Subagent 的摘要就是回傳值，格式由你定。委派時寫明「每個問題附 file：line」，損失就小。

    主對話乾淨，不只是省錢。Context 越長，model 越容易漏看中間的內容（L4 的 lost in the middle）。內建的 Explore 和 Plan 甚至不讀 CLAUDE.md 和 git status，以求快又便宜（p.32），所以相關規則要寫進任務訊息。

    常見誤解

    「平行的 agent 越多，答案越好。」平行只縮短牆上時間，每個任務仍是一個 agent 的水準（p.27）。協調和 merge 的工作還會隨 session 數增加。要更好的答案，靠的是更專注的 context 和更好的驗證。

    例子

    平行：開兩個 terminal，分別輸入 claude -w feature-payments 和 claude -w bugfix-auth，每個 session 各有一個 worktree（p.28）。Subagent：在 session 裡打「Use the Explore subagent to find every caller of parseConfig. Report file:line only.」。搜尋結果留在 Explore 的 context，你只看到一份清單。

    帶走這幾點
    1. 平行 session 只買到牆上時間；計畫和 merge 仍在你身上，超過幾個就管不動。
    2. Subagent ＝ 新的 context ＋ 只交回摘要 → 中間產物不進主對話，之後每一圈都省。
    3. 摘要是有損壓縮 → 委派時指定回報格式；要頻繁來回討論的工作留在主對話（p.37）。

    相關：核心觀念〈平行與 subagent：各買到一樣東西，也各有代價〉的〈Git worktree〉與〈Context 隔離與摘要〉兩段、〈Agent team 與 dynamic workflow〉、2.6 的〈Amdahl's law〉一段、L4〈Lost in the middle〉。進階題第 1 題替任務選擴展方式。

  4. p.39–45 · Team 與長時間執行

    只要結果時，為什麼用 subagent，不用 agent team？/goal 和 /loop 什麼時候停？

    參考答案與重點複習

    答案：每個 teammate 都是獨立的 Claude Code instance，各有 context window，所以 team 的 token 成本較高（p.39、p.41）。Slide 的規則：只要結果，用 subagent；工作需要討論，才用 team（p.41）。/goal 在可驗證的條件成立時停：每次嘗試後，evaluator 重新檢查條件，沒成立就讓 Claude 繼續；--max-tries 用完也會停（p.44）。/loop 依固定間隔重跑同一個 prompt，直到你叫它停（p.45）。

    重點拆解

    兩者的差別在結果流向哪裡。Subagent 做完，把結果交回呼叫它的 agent；subagent 之間不溝通。Teammate 共用一份任務清單，自己認領工作，還能直接互傳訊息；每個 agent 有一個 JSON 格式的 mailbox（p.39–40）。

    SubagentAgent team
    Context自己的 window，結果交回呼叫者自己的 window，完全獨立
    溝通只回報給呼叫者Teammate 之間直接傳訊
    協調主 agent 管理工作共用任務清單
    適合只要結果的任務需要討論的工作
    Token 成本較低較高

    Team 貴，因為每個 teammate 都是完整的 session。它自己載入 CLAUDE.md 和 skill，再從零讀任務需要的檔案。它也不繼承你的對話，任務細節要寫進 spawn prompt（p.39）。所以 token 用量隨人數線性成長。只要三份獨立的報告，這筆錢換不到東西；要互相挑戰、要整合跨層的改動，才值得付。依序做的任務、改同一個檔案、相依很重的工作，slide 建議用一個 session 或 subagent（p.38）。

    /goal 和 /loop 的差別在停止的依據。/goal 看條件：每一輪結束，另一個小而快的 model 讀對話，判斷條件是否成立。做事的 model 不能自己宣布完成。/loop 看時間：它是觸發器，不是測試（p.45）。Slide 的說法是你叫它停才停（p.45）；〈動手試試〉依官方文件補充：固定間隔的 loop 要請 Claude 取消，或 7 天後自動過期。

    背景補充

    Evaluator 只讀對話，不跑指令，也不讀檔案。所以條件要寫成 Claude 的輸出能證明的形式。「npm run lint exits with zero errors」可以，因為 lint 的結果會印在對話裡；「refactor the code」不行（p.44）。Slide 用 --max-tries 限制次數；〈動手試試〉照官方文件，把「or stop after 15 turns」寫進條件。目的相同：限制花費。

    常見誤解

    「/loop 發現工作做完，就會自己停。」固定間隔的 loop 不判斷完成；CI 早就綠了，它還是照時間再跑一次。要「做到成立就停」，用 /goal。

    例子

    Agent team 預設關閉（p.38）。先在 .claude/settings.json 的 env 加上 "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"。再在 session 裡打：「Spawn three teammates to review PR #142: one on security, one on performance, one on test coverage. Have them challenge each other's findings.」。/goal 和 /loop 的寫法，見〈動手試試〉最後一個範例。

    帶走這幾點
    1. Subagent 把結果交回主 agent；teammate 互相傳訊 → 只要結果用 subagent，需要討論才用 team。
    2. 每個 teammate 是完整的 session，不繼承你的對話 → token 隨人數線性成長。
    3. /goal 由另一個 model 檢查條件才停；/loop 照時間觸發，要你取消。

    相關：核心觀念〈平行與 subagent：各買到一樣東西，也各有代價〉、〈Agent team 與 dynamic workflow〉、〈長時間執行與 16 個 agent〉（含〈可驗證的完成條件〉一段）、L5〈多一個 agent：只換到四樣東西，每一樣都有價格〉。進階題第 1 題替四個任務選做法，並寫出完整的 /goal 條件。

  5. p.52–59 · Programming 3.0

    Programming 3.0 比 2.0 多了哪一層，代價是什麼？結論原則怎麼面對不確定性？

    參考答案與重點複習

    答案：3.0 在人和程式語言之間多了 agent 這一層：人用自然語言說目標，agent 寫程式碼（p.52）。它換來更高的產能，代價是更多的不確定性。結論原則：不要期待 agent 是確定的，要讓 agent 周圍的系統可靠。自主程度要配合風險：自主越多，不確定性與風險越高（p.59）。

    重點拆解

    每一代都在人和硬體之間多一層（p.52）。1.0 是人直接寫機器指令。2.0 是人寫程式語言，compiler 轉成機器指令。3.0 是人用自然語言說目標，agent 產生程式語言。每多一層，人寫的東西更接近目的，所以產能變高。但 compiler 是確定的：同一份原始碼，得到同樣的指令。Agent 不是：同一個目標，兩次可能寫出不同的程式。

    不確定性本身不是新的（p.55）。2.0 就有 32 位元與 64 位元、endianness、並行、不可靠的網路、compiler 版本、相依套件漂移。2.0 的對策是固定寬度的型別、虛擬化、idempotent API、升級前跑完整測試。3.0 在硬體、環境、軟體三列各加一項：GPU 的 nondeterministic kernel、寫 code 時就和環境互動、model 的取樣。

    新的不確定性集中在產生程式的階段（p.57）：自然語言的語意、檢索的漂移、model 的取樣、agent 與 tool 的迴圈。程式寫好以後，除非執行時還呼叫 model 或 tool，通常是確定的。所以 p.58 把對策放在生成的前後：先寫明假設和驗收測試，生成後用頻繁又便宜的檢查驗證。

    背景補充

    Karpathy 的 Software 3.0 是另一種分法，看「程式是什麼」：1.0 是原始碼，2.0 是權重，3.0 是 prompt（p.53）。講者的分法看「人寫什麼」。兩者導向同一個工程能力：決定哪一塊用確定的程式，哪一塊交給 model。

    「自主程度配合風險」對應 Karpathy 講的 autonomy slider：自主程度是一個可以調的滑桿，不是全有或全無。本堂的工具都是這個可靠系統的零件：hook 保證規則在 context 裡，/goal 要求可驗證的終點，測試判斷進度。

    常見誤解

    「把 temperature 設成 0，agent 就確定了。」取樣只是一個來源。p.57 另外列了軟硬體的不確定性：GPU 的加總順序會隨 batch 改變，浮點數沒有結合律，結果就差一點（L1）。Tool 的輸出和環境也會變。所以對策是讓周邊系統可靠，不是追求 agent 確定。

    例子

    在 Claude Code 裡，依風險調整自主程度。修 lint 錯誤：低風險、可驗證，切到 auto mode，再輸入 /goal npm run lint exits 0; no file under tests/ is modified。Security review：只給讀的權限，用〈動手試試〉的唯讀 subagent（tools: Read, Glob, Grep）。Merge 到 main：留給人。

    帶走這幾點
    1. 3.0 多了 agent 這一層：人說目標，agent 寫程式 → 產能變高，不確定性也變高。
    2. 不確定性早就存在；新的部分集中在產生程式的階段，程式寫好後通常是確定的。
    3. 不追求 agent 確定 → 讓周邊系統可靠（可驗證的終點、測試、hook），自主程度配合風險。

    相關：核心觀念〈Programming 3.0：接受不確定性，讓周邊系統可靠〉（含〈Software 1.0 / 2.0 / 3.0〉一段）、2.8 的〈人的角色，變成規劃者和 reviewer〉一段、L1〈浮點數沒有結合律〉、L2〈自主程度要配合風險〉。

4 · 動手試試

照著做一次

每個範例都依 2026 年 10 月的 Claude Code 官方文件。點開才會展開。

用 SessionStart hook 保證規則一定在 context 裡p.11–12

這是 Superpowers 的做法，縮小成一個專案能用的版本。Hook 在 session 開始、/clear 之後、compaction 之後各執行一次，把一份規則檔的內容加進 context。

驗證：開新 session，輸入「你現在的規則是什麼？」。Claude 應該能複述 WORKFLOW.md 的內容。再輸入 /clear，問一次，規則應該還在。

兩個任務，兩個 worktree，兩個 sessionp.28–29

最短的做法是 -w。Claude Code 會在 .claude/worktrees/<name>/ 建 worktree，branch 叫 worktree-<name>。離開 session 時，有改動它會問你要保留或刪除。

想自己控制目錄和 branch 名稱，用 git 指令。三個目錄共用一個 .git，在一個 worktree 的 commit，其他 worktree 立刻看得到。

新 worktree 沒有 .env 和 node_modules。先裝相依套件，或在 .worktreeinclude 列出要複製的檔案。同一個 branch 不能在兩個 worktree 同時 checkout。

定義一個唯讀的 reviewer subagent，再明確委派p.33–36

一個 subagent 就是一個 Markdown 檔。Frontmatter 是設定，body 是它的 system prompt。只給三個唯讀 tool，它就改不了檔案。

委派時寫清楚範圍和回報格式。Subagent 沒有你的對話歷史，也不一定載入 CLAUDE.md 的所有規則，所以相關規則要寫進任務訊息。

一定要它執行時，用 @agent-code-reviewer 開頭。要限制巢狀層數，在 .claude/settings.json 的 env 設 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH；設 1 就關閉巢狀。

寫一個 /goal 檢查得到的條件，和一個 /loop 的 promptp.44–45

好的 goal 條件有三部分：可量測的終點、檢查方法、限制條件。再加一個停止條款，限制花費。條件不必加引號。

/goal 不改權限模式。要讓它無人看管地跑，先切到 auto mode；否則每個沒放行的指令都會停下來問你。輸入 /goal 看狀態，/goal clear 提早結束。

/loop 是觸發器，不判斷完成。固定間隔的 loop 要請 Claude 取消，或 7 天後過期。省略 prompt 時，它跑 .claude/loop.md。

Software 3.0 的脈絡 From Software 2.0 to 3.0

  1. 推薦Software 2.0Andrej Karpathy · 部落格 · 2017 · 約 10 分

    2017 年的起點：神經網路的權重取代手寫程式，成為「軟體」本身。

    導讀問：從 2.0（權重）到 3.0（prompt），「寫軟體」的單位各是什麼？改變的是誰的工作？

    摘要讀約 3 分；原文約 10 分

    一句話：Karpathy 在 2017 年提出：神經網路的權重是一種新的軟體。人不再逐行寫程式，改成給目標與資料，由 optimizer 在程式空間裡搜出程式。

    跟這堂課的關係

    Slides p.53 的 1.0／2.0／3.0 表格，2.0 那一列（程式是權重、用資料加優化產生）就是這篇。本頁 2.7 的〈Software 1.0 / 2.0 / 3.0〉一段說明它和講者 p.52 的分法不同：這篇分「程式是什麼」，講者分「人寫什麼」。〈Programming 3.0：接受不確定性〉談的不確定性，這篇在 2017 年已經寫到。2.8 的〈人的角色，變成規劃者和 reviewer〉一段問人做什麼；這篇的答案是：多數人整理資料集，少數人維護訓練基礎設施。

    壓縮後的重點

    1. 2.0 的「原始碼」是資料集加網路架構，訓練就是 compile。1.0 由人寫 Python 或 C++，每一行把程式釘在程式空間的一個點。2.0 由人給目標與架構骨架，backprop 與 SGD 在這個子空間裡搜尋。
    2. 2017 年已有多個領域換成 2.0。視覺辨識從手工特徵加 SVM 換成 ConvNet；語音辨識丟掉 GMM 與 HMM；AlphaGo Zero 讀原始棋盤直接出手。資料庫索引也開始學：learned index 比 cache 最佳化的 B-Tree 快最多 70%，記憶體省一個數量級。
    3. 好處來自計算同質。網路只有矩陣乘法與 ReLU 兩種操作，所以容易燒進 ASIC。每次 forward pass 的 FLOPS 固定，執行時間與記憶體都是常數。砍掉一半 channel 再訓練，速度剛好快一倍，效果略差。獨立訓練的模組可以接起來一起 backprop。
    4. 最大的好處：它比人寫的程式好。影像、影片、聲音、語音的程式，神經網路寫得比任何人都好。原文把這點標為最重要。

    一句話：Subagent 是一個有自己 context window、自己 system prompt 與 tool 清單的助手。用一個 Markdown 檔定義，主對話只收到它最後的報告。

    跟這堂課的關係

    Slides p.31–37 幾乎逐節取自這份文件：p.31 的五個理由、p.33 的 frontmatter 範例、p.36 的三種叫法、p.37 的「留在主對話還是委派」。本頁 2.4 的〈B Subagent〉一段講的機制，文件寫得更細：subagent 開始時載入什麼、報告回來前經過什麼。一處分歧：p.34 說巢狀最多 5 層；現行文件預設是主對話下 3 層，早期版本才固定 5 層。

    壓縮後的重點

    1. 定義檔就是一個 Markdown。YAML frontmatter 放設定，內文是 system prompt。只有 name 和 description 必填。Claude 依 description 決定要不要委派，所以它要寫清楚什麼時候用；所有自訂 description 合計超過 15,000 token 時，啟動會警告。
    2. 常用欄位：tools、disallowedTools、model、permissionMode、maxTurns。model 可填 sonnet、opus、haiku、完整 model ID 或 inherit。isolation: worktree 讓它在獨立的 git worktree 裡改檔；memory 給它跨 session 的記憶目錄；hooks 與 skills 也能寫在 frontmatter。
    3. 放哪裡決定誰能用。.claude/agents/ 是專案層，進版控全隊共用；~/.claude/agents/ 是個人層，所有專案可用。同名時優先序是：管理設定、--agents 旗標、專案、個人、plugin。
    4. 內建三個：Explore、Plan、general-purpose。Explore 與 Plan 只能讀，不載入 CLAUDE.md 與 git status，所以快又便宜。要關掉某一個，在 permissions.deny 寫 Agent(Explore)。
    5. Subagent 從零開始，主對話只拿到摘要。它收到的是 system prompt、委派訊息、CLAUDE.md、git status 快照與預載的 skill；沒有對話歷史。報告回到主對話前會經過掃描，裡面的指令不具使用者的權限。例外是 fork：它繼承整段對話，並共用 prompt cache。
    6. 上限與叫法。預設同時最多 20 個，巢狀 3 層，兩者都能用環境變數改。叫法三種：自然語言點名、@ 指定（保證執行）、claude --agent code-reviewer（整個 session 用它）。互動模式下 subagent 預設在背景跑，權限提示回到主 session。

    4. 任務清單有三種狀態與相依。pending、in progress、completed；有相依的任務要等前置完成才能認領。Teammate 做完會自己認領下一題。三個 hook 當品質關卡：TeammateIdle、TaskCreated、TaskCompleted，exit code 2 就退回並附回饋。

    6. 限制清單要先看。文件列了五條：
      • /resume 不會把 in-process 的 teammate 找回來。
      • 任務狀態可能卡住沒更新。
      • 一個 session 只有一個 team。
      • Teammate 不能再開 team。
      • Lead 不能換人。

    摘要讀約 3 分；原文約 25 分

    一句話：16 個 Claude agent 平行跑兩週，沒有人介入，用 Rust 從零寫出能編譯 Linux kernel 的 C compiler。成立的條件有兩個：測試接近完美，失敗訊號能切成很多小塊。

    跟這堂課的關係

    Slides p.47–50 直接取材於這篇，見〈長時間執行與 16 個 agent：終點要能檢查，加 agent 有上限〉；lock file 認領對應本頁 2.6 的〈用 git 當鎖〉一段（p.49）。Kernel 卡關的故事是 2.6 的〈任務切不開，加 agent 也沒用〉一段的來源（p.50）。Slides 沒有講的是成本數字、agent 的分工角色，以及作者對「測試通過」的保留態度。

    壓縮後的重點

    1. 規模與成本。16 個 agent、將近 2,000 個 Claude Code session、兩週，model 是 Opus 4.6。API 成本略低於 20,000 美元；input 20 億 token，output 1.4 億 token。Compiler 約 100,000 行 Rust，過程中沒有網路。
    2. 成果與限制。它能編譯 Linux 6.9（x86、ARM、RISC-V）、SQLite、FFmpeg、QEMU 等專案，跑得動 Doom；大多數測試集通過率 99%。但全部最佳化打開，產出仍比 GCC 關掉最佳化還慢。自己的 assembler 與 linker 還有 bug，展示時借用 GCC 的。
    3. 長時間執行靠檔案，不靠記憶。每個 session 在全新的 container 開始，沒有任何 context。所以 prompt 要求 agent 維護 README 與進度檔；卡住時，記錄失敗過的做法與剩下的任務。
    4. 協調只靠 git。每個 agent 在自己的 container 裡 clone 共用的 bare repo。認領任務就是在 current_tasks/ 寫一個 lock file 並 push；兩個 agent 搶同一題，git 會逼其中一個換題。沒有 orchestrator；merge conflict 很常見，agent 自己解。
    5. Verifier 要接近完美。測試有錯，agent 就會解錯的問題。測試來自 compiler 測試集、開源專案的 build script，以及針對新失敗寫的測試。輸出也為 model 設計：只印幾行，細節進 log 檔，錯誤行標 ERROR；預設 --fast 只抽 1% 或 10% 的測試。
    6. 平行要靠獨立的失敗訊號。測試集有很多獨立失敗時，每個 agent 各拿一個。到了 kernel，所有 agent 卡在同一個 bug，互相覆蓋修改，16 個 agent 沒有加速。解法是用 GCC 當 oracle：大部分檔案用 GCC 編譯，少數用自己的 compiler，失敗就縮小範圍。
