先看這裡

Agent 是一個 loop：model 每一圈決定下一步，包在它外面的程式（harness，例如 Claude Code）去執行，再把結果接回去。Model 沒有記憶，所以 harness 每一圈都把整份 context（送進 model 的全部文字）重送一次。這一條事實決定了這堂的所有設計：tool 的輸出、prompt、舊的歷史，都是每一圈要再付一次的文字。所以這堂要帶走的不是第 8、9 章那五種找程式碼、四種改程式碼的方法名，而是判斷什麼值得進 context，進來之後怎麼處理。

  • Agent 做不好，先查 harness，再換 model。同一個 model，只改 harness 處理 context 的方式，解題數可以差 2 倍；但這個倍數只在 window 小到放不下時成立（window 是 model 一次能讀的長度上限）。Window 夠大時差距就沒了，要付的錢和舊資料的干擾還在。
  • 管 context 有順序。能不進來就不進來，進來了先用規則刪，有損又不可逆的摘要排最後。開頭也不要動：provider 會把算過的開頭存起來（prefix cache），下一圈開頭逐字相同才能打折重用，改一個字就整份重算。
  • Tool 的輸出就是 context。Tool 要少而專用、輸出要短；錯誤訊息要告訴 model 下一步怎麼改，失敗要讓 model 下一圈就看得出來，不能回成功卻改錯。Prompt 的技巧（例如叫 model 一步步想）會隨 model 過期，這幾條不會。

1根本的限制：model 沒有記憶，每一圈整份重送

L2 講過，一個 agent 就是 model 加一個 loop：model 每一圈只決定下一步，harness 執行 tool，再把結果放回 context，直到 model 不再提議動作。這堂換成寫 harness 的人的角度，問這個 loop 裡的四項工作怎麼做：

前情Model、harness、context、token 與 ReAct：L2 講過、這堂要用的名字

Model 是語言模型本身，只會讀一段文字、接著產生一段文字。Harness 是包在 model 外面的程式，例如 Claude Code 這個 CLI。Context 是每一次送進 model 的全部文字，長度上限叫 context window。

Token 是 model 計算文字的單位：英文大約 4 個字母是 1 個 token，繁體中文一個字約 0.7 到 0.9 個 token，舊一點的 tokenizer 約 1.4 個（L9〈Tokenizer〉實測），計費和長度上限都用它算。

ReAct 是 2022 年的一篇論文，名字來自 Reason 和 Act：model 輪流寫 Thought、發出 Action、讀 Observation。只推理，沒有東西檢查推理，小錯會累積成自信的幻覺。只行動，動作背後沒有計畫，model 會重複同樣的動作。現在的 API 把 Action 做成原生的 tool call，loop 沒有變。

Agent 的 state 分兩種。Context 只活在這一次 request，下一圈由 harness 重新組一份。Memory 存在 context 外面，例如硬碟上的檔案，要讀進 context 才看得到；CLAUDE.md 就是一例。L2 和 L6 專門講 memory。

這四項工作有同一個前提：model 沒有記憶。上一圈發生過什麼，它只能從這一圈收到的文字知道，所以 harness 每一圈都把整份 context 重新送一次：

注意力機制還沒有定論，量到的是現象：window 越滿，model 越難從裡面找回資訊，放在中間的最容易漏（下面兩組實驗）救不了

Prefix cache 是 provider 把算過的 prompt 開頭存起來，下一次開頭相同就不必重算，第 3 章會講。錢的那一筆有一個要記的形狀：每一圈多 3,000 token 的話，跑 30 圈總共送 1,395,000 token，跑 100 圈是 15,150,000，圈數多 3.3 倍，總量多 10.9 倍，因為總量隨圈數的平方成長。打折之後的實際帳單是 L8 的主題，這裡只要記住：多留一筆大的 tool 結果，要付的次數等於剩下的圈數。

注意力的成本，兩組實驗量過。第一組是 Chroma 的 Context Rot（2025）：18 個 model 做同一種查找，輸入越長結果越不可靠，多放一段干擾內容就更差。第二組是 Liu 等人的 Lost in the Middle（TACL 2024）：只移動答案所在的位置，其他都不變。課程 slide 引的這張圖上，放第 10 份時準確率掉到 55%：

原因還沒有定論，論文也發現專為長 context 設計的 model 同樣有這個現象，所以把 window 加大解決不了。設計上的意義倒是很清楚：關鍵的指示和問題放開頭或結尾，不要埋在一大段資料的中間。Anthropic 的官方指南給的是同一個方向的具體排法：長文件放最前面，問題放最後；指南說，問題放在最後時，回答品質在他們的測試裡最多提升 30%。這兩組實驗都是問答任務，真實 agent 上的結果在下一章。

名詞SWE-bench、消融實驗與 4-bit 量化：這些數字是怎麼量出來的

SWE-bench 是 2023 年普林斯頓提出的 benchmark，從 12 個 Python 開源專案的 GitHub issue 出題，共 2,294 題。Agent 拿到 repo 和 issue 描述，要產出一份 patch。判分是跑該專案的測試，原本失敗、修完要通過的測試都過了才算解出。

SWE-bench Lite 是 300 題的子集，SWE-agent 的 18.0% 就是在它上面量的（54 題）。SWE-bench Verified（2024）是 OpenAI 請人逐題檢查後留下的 500 題。SWE-bench Pro（2025，Scale AI）換成較新、較大的專案，題目更長、更難。Benchmark 本身怎麼讀是 L7 的主題。

消融實驗（ablation）是量「某個零件有多重要」的標準做法：把一個部分拿掉或換掉，其他全部不動，看分數掉多少。

4-bit 量化（quantization）是把 model 的每個權重從 16 bit 壓成 4 bit 存，記憶體少很多，才能在本機跑。代價是 model 的能力通常比原本的精度差一點，所以 Lewis 的數字不能直接套到雲端的大 model 上。

課程由此得出結論：有些看起來是 model 的失敗，根源在 context 和 control loop，也就是 harness 怎麼決定繼續、停止、介入。它寫成 Agent = Model × Harness：model 的能力定上限，harness 決定實際發揮多少。所以 agent 做不好時，先查 harness，再換 model。先查 harness 的理由是兩邊的代價不一樣：換 model 只要改一個設定，但之後每一圈都付更貴的 token，而且它不告訴你為什麼失敗；如果原因在 harness，例如對話放不下就停，換了 model 照樣停。Harness 是你自己的程式，讀一次執行紀錄就看得到哪一步出錯，改完用同一組題目重跑就能驗證。

這個實驗還有三個限制。它用的是本地跑的 4-bit 開源 model，沒有測 frontier model（各家最強、在雲端跑的旗艦 model），所以看不出換成更強的 model 時，差距還在不在。改良版也更貴：agent 跑得更久，Verified 的圈數多了一倍，prompt token 從 37.8M 變成 80.7M。論文也沒有逐項消融，分不出哪一項改動貢獻多少。

本文的判斷：window 大了還是要管，理由換了。2026 年主流 model 的 window 已經到 1M token，放不下的情況少了，Lewis 那種差距不一定會出現。但第 1 章的錢和延遲照付，舊內容也會誤導 model：Less Context 的全歷史組輸給修剪組，主因是舊的表單狀態還留著，agent 引用到舊值；Xia 等人（2026）在長時間搜尋任務上也量到，context 越長，agent 越常放棄，而 window 大小不是主要瓶頸。這兩篇各只測一類任務，所以要當成假設，在自己的任務上量。

Control loop 也是 harness 的工作。Model 不會自己發現它在繞圈，所以 Lewis 用固定的規則看執行紀錄，抓三種型態：同一個失敗的指令重跑、同一個錯誤重複出現、一直讀檔卻不改。規則觸發時，harness 告訴 model 同樣的做法得到同樣的失敗，要它換一個做法。

評估時要固定 harness。反過來推，兩個 model 放進不同的 harness 比較時，差異可能來自 harness。所以要比 model 就固定 harness，要比 harness 就固定 model 與 benchmark，並寫明 window 大小。L7 會把它變成方法。

圖裡有幾個 Claude Code 的名字，後面的章才細講，這裡先各用一句話交代：

  • Skill。一份寫成 markdown 的做法說明，例如「怎麼寫 commit 訊息」。平常只有名字和一行說明放在第 3 格；model 決定用它時，全文才讀進第 8 格。
  • CLAUDE.md 與 auto memory。CLAUDE.md 是你放在專案裡、寫給 Claude Code 的規則檔；auto memory 是 Claude Code 自己替這個專案記下的筆記檔。兩者每個 session 開頭都從硬碟讀進第 4 格。
  • Hook。事件發生時 harness 自動跑的一段程式，例如 session 開始時印出 git 狀態；它印出來的文字可以放進第 6 格。第 4 章有一個實例。
  • Compaction。請 LLM 把舊的對話歷史寫成一段摘要，取代原文，空出 window；摘要放在第 7 格。第 5 章細講。
  • /clear、/compact：Claude Code 裡打的兩個指令。/clear 清空對話重來；/compact 立刻做一次 compaction。

兩件事要記。第一，這個 request 就是 model 看到的全部，上一圈的事它只知道 messages 裡寫了什麼。第二，messages 是 harness 的資料，不是 model 的。Harness 可以在送出前改它，第 4、5 章的四種策略就是改它的四種方式。要看自己的 session 每一格佔多少，在 Claude Code 打 /context。

順序不是隨便排的：cache 只認開頭。Agent 每一圈的 request 幾乎都是「上一圈加一點」，所以開頭那一大段可以讀 prefix cache，只付一小部分的價錢。代價是比對方式很嚴格：

前情Prefix cache（L2）：開頭沒變的部分，不用重算

Model 讀 prompt 時（prefill），每個 token 都算出一組中間結果，叫 KV cache。這些結果只和它前面的 token 有關。所以這一次 request 的開頭和上一次逐字相同時，開頭那段可以直接拿來用，只有後面新的部分要算。API 服務商把這件事做成 prefix cache。

命中的部分打折計價。依 2026-11 的官方文件，Claude 的標準是 0.1 倍（Opus 5.5、Sonnet 5.5 是 0.05 倍），OpenAI 從 GPT-5.6 起也是 0.1 倍（GPT-6.1 Sol、Terra 是 0.05 倍）。寫入 cache 要加價，Claude 的 5 分鐘 cache 是 1.25 倍。太久沒用就過期。

L2 講 Claude Code 怎麼靠它省錢，L8 算它的帳。

課程只提一句，正式產品把它當第一條規則（本文補的）。課程只在 compaction 的提醒裡說要保留開頭。2025–2026 年，三個正式產品的團隊都寫了工程文章，把這件事放在最前面：

  • Manus（2025）。把 KV cache（也就是 prefix cache）的命中率稱為 production agent 最重要的單一指標。
  • Codex（2026）。每一圈都重送整份對話，所以整個 run 送出的 JSON 總量隨圈數的平方成長（第 1 章的算式）。OpenAI 的文章說，cache 命中時，model 每一圈只要算新加的那一段，呼叫 model 產生輸出（文章叫 sampling）的計算量才變成隨圈數線性成長，不是平方。
  • Claude Code（2026）。Anthropic 的文章說他們監控命中率，掉太低就當成事故處理。

這三篇都是各家自己的經驗，不是對照實驗，但規則一致：會變的東西一律往後放，要更新就在尾端加訊息，不要回頭改。

5已經進來的：先用規則刪，最後才摘要

已經進了 window 的內容只有兩條路：harness 用固定的規則刪（transformation），或請 LLM 寫摘要（compaction）。正式產品也是這個順序，Claude Code 快滿時先清舊的 tool 輸出，不夠才摘要。

Transformation：用規則改 messages。Harness 不呼叫 LLM，只把某些 tool 結果的內容換成一行占位文字，或整段不送。規則有三種：

  • Dedup。每筆 tool 結果記一個 key，通常是 tool 名稱加主要參數，例如 read src/auth/retry.ts。Key 第二次出現，舊的那筆就換掉。Agent 很常重讀檔案，所以這一招省得多。
  • Observation masking。只遮 tool 結果，不動使用者訊息、model 的文字和 tool call，所以 model 還看得到自己做過什麼。N 不必調得很準：Less Context 的實驗裡，N = 3、5、10 的完成率是 74.0%、79.0%、80.0%，5 之後就平了。
  • Sliding window。最粗，連 model 的推理也不留，通常和摘要搭配。

Compaction：LLM 當最後手段。LLM 把舊歷史寫成一段摘要，換掉原文。Rolling summary 邊走邊摘要舊的 tool 結果，full summary 等快滿時把整段重寫一次，Claude Code 的 /compact 和自動 compaction 是後者。留什麼由 model 決定，而摘要裡沒有指回原文的 handle：就算完整紀錄還在硬碟上（上圖的 session record），model 也不知道摘要漏了什麼、該去哪裡讀，所以對 model 來說，原文拿不回來。課程給了三個提醒：

  • 預留空間。要留 buffer 給摘要本身的輸出，不能等到全滿。
  • 保持開頭。做摘要的那次 request 也要用相同的 system prompt 和 tool，才讀得到 cache。Anthropic 說換一個 system prompt 來做，整段歷史都要照全價重算。
  • 放回關鍵事實。摘要之後把目前的目標、規則放回去。

回到 compaction：它本身也不便宜，LLM 要讀完整段歷史：Claude API 文件的範例裡，一次 compaction 是 180,000 token 的 input 加 3,500 token 的 output。這次摘要由同一個 model 寫，照它的價格計費，不會換成便宜的小 model。自動 compaction 要等快滿才觸發，那時通常在任務中間，要讀的歷史也最長，所以值得自己挑時機：在自然的斷點做，並指定要留什麼；換不相干的工作時，舊歷史根本用不到，與其花 180,000 token 去摘要它，不如直接清掉重來：

除了原地摘要（/compact）和整個清空（/clear），長時間任務還有第三條路：先把進度、做過的決定和下一步寫進檔案，再開一個新的 session，讓它一開頭就讀回那個檔案。它和 /clear 一樣從空的 context 開始，差別是交接的內容由檔案帶過去，不會失憶。Anthropic 2026 年的 harness 文章把這種做法叫 context reset，拿它和 compaction 比較。Compaction 保住連續性，但 model 還在同一個越來越長的 context 裡；reset 給它一個乾淨的開頭，代價是要多做交接。他們較早用的 Sonnet 4.5 接近 context 上限時會提早收尾（文章叫 context anxiety），光靠 compaction 不夠，所以用 reset；換到 Opus 4.5 之後這個行為大致消失，就拿掉 reset，只靠 compaction（一家公司的經驗，不是對照實驗）。所以對現在的 model，reset 是 compaction 不夠用時的退路，不是預設。多個 session 怎麼交接是 L3 的主題。

為什麼是這個順序。四種策略排的是 model 失去多少：越前面，model 要的東西越拿得回來，拿回來的也越接近它原本看到的；harness 要做的事也越少：

  1. Admission。在門口擋掉的部分，model 從沒看過，所以沒有「當時那一份」要找回；需要時重新呼叫 tool，拿到的就是它第一次看到的版本。Harness 不必存任何東西。
  2. Offloading。原文進過 context，現在由 harness 存著，model 照 handle 讀回來，拿到的就是原文，連 tool 都不用重跑。代價是 harness 要存一份、管 handle，model 也要多花一圈去讀。
  3. Transformation。Model 已經看過、也依它做了決定，遮掉之後重跑 tool 只拿到現在的版本；要拿回當時那一份，得靠 harness 留著完整紀錄（上面的本文判斷）。
  4. Compaction。摘要裡沒有指回原文的路徑，model 不知道漏了什麼，所以有損又不可逆。

這大致也是成本的順序：前三種多半不呼叫 model，例外是 admission 交給 subagent 的那一種；compaction 每次都要。但 transformation 會讓 cache 重建，清得太少反而不划算，帳在 L8。

排在最後不代表不用。Less Context 只修剪時，引用舊狀態的錯誤從 34 次降到 6 次，提早結束卻從 9 次變 18 次，因為看不到任務全貌；再加一段摘要才降到 3 次。規則刪和摘要修的是不同的錯。

Model 每一圈能做的只有一件事：選一個 tool、填好參數。所以 tool 決定它能看到什麼、能改什麼。對 context 來說，tool 進來的路只有兩條，也就是兩筆預算：

Model 眼中的 tool 只有三段文字。Name、description、input_schema，harness 每一次 request 都放進去。Model 看不到 tool 的程式碼，所以 description 就是一段 prompt，要寫什麼時候用、參數的格式、常見的誤用。Input_schema 用 JSON Schema 寫型別和限制，model 填錯會在執行前擋下。

名詞JSON Schema：用 JSON 描述「一份 JSON 該長什麼樣」

JSON Schema 是一個標準，用一份 JSON 描述另一份 JSON 的形狀：有哪些欄位（properties）、每個欄位的型別（type）、哪些一定要有（required）、值只能是哪幾個（enum）、數字的範圍（minimum、maximum）。

Tool 定義用它有兩個好處。Model 在訓練時看過大量 JSON Schema，讀得懂。Harness 也能在執行前用現成的 validator 檢查參數，缺欄位或型別錯就直接退回，不用真的跑 tool。各家 API 都用它，只是欄位名不同：Claude 叫 input_schema，OpenAI 叫 parameters。

設計 tool 時最先要問的：輸出進了 context，下一步會更好嗎？SWE-agent 論文把 agent 與電腦之間的介面叫 agent-computer interface，因為 model 需要和人不同的介面：它沒有滑鼠和語法高亮，讀過的每一行都留在 context。論文把介面的零件逐一換掉，結果比「多給資訊比較好」複雜得多：

預設冪等。冪等的意思是同一個呼叫做兩次，結果和做一次相同。讀檔、查詢、把一個值設成 5 都冪等；轉帳、送 email、在清單尾端加一筆都不冪等。Timeout、網路錯誤、model 以為上一次沒成功，都會讓 loop 再呼叫一次，所以 create_refund(order_id, amount) 這種 tool 很危險，重試一次就退兩次款。改法是加一個 idempotency key：每一筆退款配一個 id（下圖的 r-9），這一筆的每次重送都帶同一個 id，新的一筆退款才換新的 id。Tool 記下做過的 id，看到重複的就不再做，直接回上一次的結果。Id 由發起這筆操作的一方產生：harness 自己重送時沿用原本的 id；model 重發時，id 要是 tool 的參數，model 才能把同一個值帶回來。

Key 要由真正執行動作的系統記住才有用。金流 API 多半支援，例如 Stripe 的請求可以帶 Idempotency-Key；用 SMTP 寄 email 就做不到：協定裡沒有這種 key，回覆逾時時，tool 也不知道上一封到底寄出去沒有。這類 tool 要標成不可重試，讓 harness 遇到失敗時停下來問人。Agent 之間的重試也是同一個問題，L5 有完整的時序。

  • 問使用者。一個便宜的問題，勝過一個自信的錯 patch。
  • Subagent。另一個有自己 context 的 agent，回來的是一份清單，不是 40 次讀檔的結果（L3）。
  • Web search。排最後：先讀裝好的原始碼，再查網路。

Tool 的輸出不一定要進 context。2025 年底多了一種做法：讓 model 寫一段程式去呼叫 tool，中間結果留在執行環境，只有程式最後印出的東西回到 context。Anthropic 介紹這個做法的文章裡，一個示範從 150,000 token 降到 2,000。Claude API 後來也提供同一個做法，叫 programmatic tool calling，在 Anthropic 的內部測試裡平均少 37%（43,588 降到 27,297；廠商自己的數字）。它多了一步：model 要先寫程式，再交給執行環境跑一次。只呼叫一次 tool 時沒有中間結果可省，這一步純粹是多出來的成本；每個中間結果都要 model 看過才能決定下一步時，它們終究要回到 context，也省不到。

7Execution：shell 最強，保護全在 harness

課程把 tool 分成四類：搜尋與讀取、編輯、執行、其他（其他的常見五種在上一章的查閱註）。這一章先講執行，因為它錯了最難挽回。搜尋和編輯在第 8、9 章。執行類的 tool 幾乎就是一個 shell。一次呼叫就能串接、過濾、迴圈；碰得到檔案系統、網路和套件管理員；產生的檔案與 process 在呼叫結束後還在。也就是說，blast radius（一個錯誤動作能波及的範圍）等於 shell 本身。課程列了五個執行上的考量，而 shell 自己一項都不做，全部落在 harness 身上：

前情Guardrail 與 prompt injection（L2）：為什麼保護跟著 tool 走

只會輸出文字的 model 刪不了你的 repo，拿到 shell 的 model 刪得掉。所以風險來自 action，guardrail 也跟著 tool 走：權限（哪些 tool 可以自動執行）、sandbox、人工核准。

Tool 讀回的網頁、檔案或 issue 可能夾帶指令，這段文字進了 context，model 可能照做。所以要把 tool 結果當資料，讀過不可信的內容之後，危險的動作要先問人。L2 講單一 agent 的防法，L5 講多個 agent 之間的。

名詞Exit code、stdout、stderr：一個程式結束時留下的三樣東西

每個程式結束時都回一個整數給呼叫它的人，叫 exit code。0 表示成功，其他值表示失敗，意思由程式自己定：grep 找不到結果時回 1，指令不存在時 shell 回 127。

程式印出來的東西分兩條線：stdout 是正常輸出，stderr 是錯誤與警告。終端機裡兩條都顯示在螢幕上，所以看不出差別。Harness 把它們分開收，就能只把 stderr 的最後幾行放進 tool result。

名詞Container、VM、sandbox：三種「關起來跑」的程度

Sandbox 是通稱：讓程式在受限的環境裡跑，碰不到環境以外的檔案、網路和 process。Container（例如 Docker）用作業系統的隔離機制做到這件事，和主機共用同一個 kernel，所以啟動只要幾百毫秒，隔離也沒有那麼徹底。VM（virtual machine）連 kernel 都是自己的一份，隔離最徹底，啟動要幾秒到幾十秒。

雲端的 agent 通常用 container 或 VM：每個 session 開一個，repo 掛進去，網路只開白名單，結束就丟掉。Claude Code 在本機跑時可以開 OS 層的 sandbox（Seatbelt、bubblewrap），但它只管 Bash；Read、Edit、WebFetch 走權限規則（L2）。

五項的共同點，是把原本交給 model 判斷的事改成由 harness 保證。預算要寫在 harness，不能只寫在 prompt，因為 prompt 裡的「最多試三次」model 不一定會守。這也是第 6 章 Schmid 主張只給 bash 的前提：他砍掉的是 tool 的數量，這五項工作全部搬進了 harness。

既然 shell 都做得到，為什麼還要專用的 read、edit tool？三個理由，都是 tool 輸出和安全的問題：

  • 輸出。Read tool 可以限制行數、附上行號，cat 會把整個檔案倒進 context。
  • 安全。唯讀的 tool 可以自動放行，shell 指令要先檢查，因為它可能是 rm。
  • 錯誤。Edit tool 會回「找不到，請重讀檔案」，sed 對不到時什麼也不說。

8Search：先 grep，名字猜不到才換

Repo 放不進 context，所以 agent 開工的第一件事，是用 tool 找到該看哪一段。L2 講過 Claude Code 這種由 model 自己找的做法叫 agentic search；這一章把幾種找法逐一講清楚。選哪一種，看手上有什麼線索：

先認識兩個字：字面與 symbol。字面（lexical）是檔案裡的字串本身：grep 找 charge，就是逐行比對有沒有這六個字母，不管它是函式名、註解還是一段文字。Symbol 是程式語言裡有名字的東西：變數、函式、class、參數、模組。每個 symbol 有一個宣告的地方（definition）和很多個使用的地方（reference）。Grep 依字面找，semantic search 依意思找，LSP 依 symbol 找。

找法 1：grep 與 glob，依字面找。grep 是 shell 指令，搜尋文字；shell 是終端機裡解讀指令的程式，例如 bash、zsh。Glob 是另一種比對，它比對檔名，用 * 和 ** 當萬用字元，agent 通常把它包成一個 tool。例子是「修 login 的 timeout」，三步：

它們不用建索引，所以永遠反映 repo 的現況。代價有兩個：只比對字面，搜 timeout 找不到叫 deadline 的同一件事；每搜一次就花掉一圈、佔掉一段 context，上面就用了三圈。

找法 2：semantic search，依意思找。它靠 embedding：一個 embedding model 把一段文字轉成一串數字，也就是一個向量，常見的長度是幾百到幾千個數字。意思相近的文字，向量在空間裡的距離也近，所以「rate-limit」和一段叫 throttle 的程式碼會靠在一起。這一整套就是 RAG 的檢索那一步：

名詞RAG、vector database、HNSW：semantic search 背後的三個名字

RAG（retrieval-augmented generation）：model 回答前，先從一堆文件裡檢索出相關的幾段，放進 context，再生成答案。Semantic search 就是其中檢索那一步，只是文件換成程式碼。

Vector database 是專門存向量、依距離查詢的資料庫，例如 pgvector（PostgreSQL 的擴充）、Qdrant、Chroma。一般資料庫查「等於」「大於」，它查「離這個向量最近的 k 個」。

Vector database 能在幾百萬個向量裡很快找到最近的幾個，靠的是索引結構。HNSW（hierarchical navigable small world）是最常用的一種：把向量連成多層的圖，查詢時從最上層粗略的圖開始跳，一層一層往下逼近，不必每個向量都算距離。代價是「近似」：回傳的 k 個不保證剛好最近，但通常夠接近，速度也快很多。

課程的例子是問 where do we rate-limit?，第一次查詢就回 throttle.ts，grep 做不到。代價是索引要跟著程式碼一起同步，索引沒跟上就會回傳舊程式碼。

找法 3：repo map，依結構找。Aider 是 2023 年出現的開源 coding agent。Model 看不到整個 repo，每次都讀幾十個檔案又太貴，所以它給 model 一張地圖：用 tree-sitter（支援幾十種語言的 parser）解析每個檔案，抽出定義和引用的 symbol；把檔案當節點、引用當邊建成一張圖，用類似 PageRank 的方法排名；依排名挑到一個 token 預算為止（預設約 1K token），印成大綱放進 prompt。

名詞PageRank：重要的節點引用你，你就重要

PageRank 是 Google 早期替網頁排名的演算法：連到一個網頁的網頁越多，它就越重要；連過來的是重要的網頁，加分更多。算法是反覆迭代：每個節點把分數平均分給它連出去的節點，再收回別人分給它的，做到分數不再變動。

Repo map 把網頁換成檔案、連結換成「引用了哪個 symbol」。這個排名只看引用結構，不看程式碼的意思，所以不需要 embedding model，tree-sitter 解析完就能算。

所以 model 一開始就知道有哪些檔案、誰是核心，一行本體都沒讀，要改時才把檔案加進對話。它回答「這個 repo 長什麼樣」，semantic search 回答「哪一段和我的問題意思相近」。

找法 4：extrinsic signal，程式碼以外的證據。指 stack trace（程式出錯那一刻的呼叫鏈）、失敗的測試、git 歷史。課程的例子是 checkout 的 crash report：stack trace 指到 cart.ts:88，順著 3 層讀到 tax.ts 的四捨五入出錯，修掉，測試變綠，一次搜尋都不用。有這種訊號時它最準，但寫新功能時沒有。

找法 5：LSP，依 symbol 找。先從你用過的功能講起。在 VS Code 裡，對一個函式名有四個常用的功能：

  • Go to definition。按 F12，跳到它的定義。
  • Find references。按 Shift+F12，列出所有呼叫它的地方。
  • Rename。按 F2 改名，所有呼叫端一起改。
  • Hover。滑鼠移上去，顯示型別。

這些功能都要懂這個語言。早期每個編輯器要替每種語言各寫一套，N 個編輯器乘 M 種語言。2016 年 Microsoft 推出 Language Server Protocol（LSP），把它拆成兩半：編輯器只管畫面，另外跑一個程式叫 language server，一種語言一個，專門負責懂程式碼，例如 Python 的 pyright、Rust 的 rust-analyzer。於是 N 乘 M 變成 N 加 M（L2 的 MCP 也是同一個思路）。兩者之間的訊息格式是 JSON-RPC，也就是用 JSON 寫的請求與回應：

前情MCP（L2）：tool 這一邊的 LSP

MCP（Model Context Protocol）解的是 tool 那一邊的 N 乘 M：N 個 harness 要接 M 種外部系統。它把每個外部系統包成一個 server，用固定的訊息（也是 JSON-RPC）回答「你有哪些 tool」「替我呼叫這一個」。LSP 讓編輯器不用懂每一種語言，MCP 讓 harness 不用懂每一個外部系統。完整的機制在 L2。

9Edit：失敗看不看得見，和省 token 一樣重要

找到之後要改。四種改法的分工相同：model 輸出一段文字，tool 把它套進檔案。差別在 model 輸出什麼，以及套不上時會怎樣。下面統一用一個例子：把 src/auth/retry.ts 裡的 RETRY_MS = 500 改成 2000。

改法 1：整檔重寫。沒有 patch 語法可以寫錯，但在 120 行的檔案改 1 行，model 也要重打 120 行。長檔還會 drift：重打沒要改的行時，model 會漸漸偏離原文，例如少一行註解、換一個變數名。（第 5 章的 drift 是 model 換掉了目標，這裡是文字偏離原文；課程用了同一個字。）

git apply 靠 context 行在附近搜尋定位，所以行號偏移了還能套；但 model 讀檔之後檔案又變了，例如 formatter（自動排版工具，像 Prettier、Black）重排過那幾行，hunk 就套不上。Git 還預設全有或全無，一個 hunk 失敗，整份 patch 都不套用。

改法 4：AST 編輯。前三種改的都是文字，第四種改的是程式的結構。Compiler 處理程式碼之前，會先用 parser 把這串字元讀成一棵樹，叫 abstract syntax tree：每個節點是一個語法單位，子節點是它的組成部分，空格、換行、註解都不在樹上。

AST 編輯讓 model 只點名一個操作和一個 symbol，例如 add_param(fetchUser, "timeout", default: "5s")。Tool 在 params 底下加一個節點，再印回文字，所以印回來的程式碼一定能 parse。這類工具平常叫 codemod，例如 jscodeshift、libcst。代價是每種語言、每一種操作都要有人先寫好，「改寫這段折扣邏輯」沒有對應的操作。

Search/replace 和 unified diff 差在哪。這兩種很容易看成同一件事：資訊幾乎一樣，search/replace 可以看成拿掉行號和前綴符號的 hunk。拿掉行號帶來兩個差別。第一，寫 diff 的 model 要先數對 hunk header 裡的行數，也就是 @@ -11,3 +11,3 @@ 的那兩個 3：這一處舊的有幾行、新的有幾行。數錯了，git apply 直接回 corrupt patch；search/replace 沒有這個欄位可以數錯。第二，定位的方式不同，這在同樣的幾行出現兩次時最明顯，例如設定檔裡 dev 和 prod 各有一段一樣的區塊：

為什麼失敗的方式這麼要緊。Diff 為人設計，人會 review 結果，所以 git apply 容許一點偏移。Agent 沒有人在旁邊看每一處改動，tool 越早報錯越好。Search/replace 成為 Aider 和 Claude Code 的預設，靠的就是這一點：找不到時 model 下一圈重讀再試，失敗只花一圈；整檔重寫的失敗卻很安靜，要等測試壞掉才會發現。所以選 edit tool 時，失敗看不看得見，和省 token、成功率一樣重要。

另一派：沒有行號的 diff（本文補的）。OpenAI 的 apply_patch 也是 diff，但用文字和 context 行定位，不靠行號，套不上時回 failed 和一句說明。它的指南強烈建議照用，理由是 model 就是照這個格式訓練的。所以現在是兩派，共同點才是帶得走的結論：用內容定位，對不上就報錯。自己寫 harness 時，先查你用的 model 是照哪一種格式訓練的。

10Prompt：招式會過期，原則不會

Prompt 只是 context 裡的一小塊，也就是第 3 章十格圖的第 1 格和第 9 格。這堂把它排在最後一章，理由有兩個。改錯的代價最低：改一句話、重跑一次就知道，不像 harness 或 tool 要改程式。過時也最快：prompt 的技巧補的是 model 當下的弱點，新 model 一出來就可能用不著，本章最後一段細講。課程列了八種技巧，依成本分成三層，從上往下試，夠用就停：

  • 第一層只改指令。Zero-shot 只給指令；few-shot 再加幾個輸入和答案的範例；role／persona 給 model 一個身分和讀者，例如「你是資深 SRE，寫給主管看」。
  • 第二層要 model 寫出推理。Chain-of-thought 要它先寫步驟、最後才給答案；tree-of-thought 要它列幾條路、各打分、只展開好的；self-consistency 同一題問好幾次，再投票。
  • 第三層把工作拆成系統。Prompt chaining 一次呼叫只做一件事，前一次的輸出接到下一次；meta prompting 讓 model 依測試結果替你改 prompt。
查閱八種技巧各長什麼樣

第一層只改指令，每件工作呼叫 model 一次。任務常見、規則講得清楚，就用 zero-shot；規則用講的講不清，就加 few-shot；語氣或讀者重要，再加 role。

第二層要 model 寫出推理，輸出變長；self-consistency 還要取樣多次。

第三層把工作拆開。Prompt chaining 一次呼叫只做一件事：第一次從 email 抽出 {vendor, amount, date}，第二次驗證並補上 vendor_id，第三次寫回信；哪一段不合格式就只重跑那一段。Meta prompting 讓 model 替你改 prompt：給它現在的 prompt、10 個測試案例和失敗的那 3 個，要它修好這 3 個又不弄壞另外 7 個。課程的例子裡，新版加了一條明確的拒絕規則，分數從 8 比 10 到 10 比 10（slide 的情境寫失敗 3 個，結果卻從 8 比 10 起算，原文的兩個數字就對不上）。它的前提是有 eval：固定的輸入加上標準答案，改一版就重跑一次看分數。

名詞Temperature：self-consistency 為什麼不能用 0

Model 每產生一個 token，都先算出一個機率分布，再從中取樣。Temperature 控制這個分布的平或尖：T = 0 永遠選機率最高的 token，所以每次都走同一條路；T 越大，低機率的 token 越常中選。

Self-consistency 要的是不同的推理路徑得到相同答案，所以課程的例子用 T = 0.7。T = 0 的 5 票一致沒有資訊，因為那 5 次是同一條路。

哪幾招已經過期。課程說其中幾招過期了，把答案留給作業。原因是新 model 在訓練時已經學會了。這裡直接給本文的判斷（2026 年 11 月，依各家官方指南和公開研究，不是課程的標準答案）：

背景Reasoning model：會先想很久的 model，還是要 tool

Reasoning model 回答前先產生一段 thinking token，在裡面推理，再寫答案。這個能力來自訓練後段的 reinforcement learning：訓練題目是 math、code 這類答案能自動檢查的問題，答對才給 reward。

能推理的 model 多半有 effort 參數，例如 Claude 的 effort、OpenAI 的 reasoning_effort。Effort 越高，thinking token 越多，難題通常答得較好，但更貴、更慢。Claude 4.6 之後是 adaptive thinking：model 自己決定要不要想、想多久（依 2026-11 的官方文件）。

Thinking 再長也還是只推理：它看不到 repo 裡的程式碼，也跑不了測試，所以 agent 仍然要靠 observation 檢查推理。

不會過期的四條原則。課程給的是溝通本身的原則，和 model 的世代無關：

  • 從簡單開始。先寫簡單的，需要時才加。
  • 分段。把 prompt 分成背景資料、指令、tool、輸出格式幾個區塊，用 markdown 或 XML 標籤隔開。背景資料 slide 寫作 context，指的是 prompt 裡的這一段，不是整個 context window。
  • 具體精簡。花俏的措辭換不到東西。
  • 拆任務。大任務拆成小任務。

招式為什麼會過期。一招有效，是因為它補了 model 當時的弱點；新 model 在訓練時把弱點補上，這招就失效，有時還會干擾。所以 prompt 的建議和 model 綁在一起，換 model 就要重調，而且每一招都該有 eval 證明它有用。OpenAI 2026 年的遷移指南就是這個做法：一次拿掉一組指令、範例或 tool，再用同一組 eval 重跑。

    壓縮後的重點

    1. Workflow 與 agent 的分界是誰決定路徑。Workflow：LLM 與 tool 走程式碼預先寫好的路徑，可預測、一致。Agent：LLM 自己決定流程與 tool 用法，有彈性，代價是延遲、成本與錯誤累積。
    2. 基本單位是 augmented LLM。一個 LLM 加 retrieval、tool、memory。Model 自己產生查詢、選 tool、決定留什麼。設計重點是把介面寫清楚，MCP 是一種做法。

      • 透明。把規劃步驟明白顯示出來。
      • ACI。Tool 的文件與測試要像 HCI 一樣投入。

    Slides p.43 右圖的 U 形曲線來自這篇，見〈注意力的成本，兩組實驗量過〉。本摘要的數字取自論文附錄 20 份文件的表，和 slides 標的 5 個值略有出入，趨勢相同。Slides 由此推出「中間的舊 tool 結果最該清掉」，對應 p.49 的 observation masking，見〈已經進來的：先用規則刪，最後才摘要〉。論文沒講 agent，任務是 QA 與 key-value 查詢；套到 agent 的 context 是 slides 的推論。

    壓縮後的重點

    1. 實驗設計：只移動答案的位置，其他不變。NaturalQuestions-Open 的 2,655 題，每題給 k 份 Wikipedia 段落（每份至多 100 token），1 份含答案，其餘 k−1 份是 Contriever 找來的干擾文件。k 取 10、20、30，答案文件輪流放在每個位置。Greedy decoding，輸出含任一正確答案就算對。
    2. 6 個 model，含 3 組加長 context 版本。MPT-30B-Instruct（8K）、LongChat-13B（16K）、GPT-3.5-Turbo（4K 與 16K）、Claude-1.3（8K 與 100K）。
    3. U 形，而且中間可以比不給文件還差。GPT-3.5-Turbo 在 20 份文件時：第 1 份 75.8%，第 5 份 57.2%，第 10 份 53.8%，第 15 份 55.4%，第 20 份 63.2%。它的 closed-book 是 56.1%，oracle（只給答案那一份）是 88.3%。20 與 30 份時，最差的位置低於 closed-book。30 份時 16K 版本第 1 份 73.4%，第 15 份 50.9%，第 30 份 63.7%。
    4. 加長 window 沒有幫助。輸入同時放得進 4K 與 16K 的 GPT-3.5-Turbo 時，兩者的曲線幾乎相同；Claude-1.3 的 8K 與 100K 也一樣。
    5. Key-value 查詢去掉語言後，中間仍最差。輸入是 JSON，key 與 value 都是隨機 UUID，75、140、300 組各 500 題。Claude-1.3 幾乎全對；其他 model 在 140 與 300 組時明顯掉，掉在中間。
    6. 三個可能的原因。架構：encoder-decoder 的 Flan-UL2 在訓練長度 2,048 token 內，最好與最差只差 1.9 個百分點，超過才出現 U 形。Query 位置：把問題放在資料前後各一次，key-value 任務各 model 近乎全對，不放時最差 45.6%；對多文件 QA 沒什麼幫助。Instruction tuning：MPT-30B 有沒有 tuning 都是 U 形，差距從約 10 降到約 4 個百分點。
    7. 多給文件，reader 很快飽和。Open-domain QA 案例：retriever 的 recall 隨文件數上升，但超過 20 份之後 GPT-3.5-Turbo 只多約 1.5 個百分點，Claude-1.3 約 1 個百分點。作者建議把相關文件重排到前面，或截斷排名清單。

    原文怎麼讀

    • 可以跳過：§1 Introduction，slides p.43 已講結論。§2.1 的資料建構細節。§6 Related Work。
    • 值得看原文：Figure 1 一張圖就是全文。§3 的 key-value 實驗，證明問題不在語言理解。§4.1 的 Flan-UL2 對照，是「架構可能有關」的唯一證據。§5 的 recall 與 accuracy 兩條曲線並排。
    • 時間：只讀摘要約 3 分；挑 Figure 1、§3、§4.1、§5 約 15 分。
    別誤讀

    「這是 2023 年舊 model 的問題，新 model 已經沒有」要小心。論文附錄的 GPT-4 在 20 份文件時絕對準確率最高，但仍是 U 形；加長 context 的版本和原版曲線一樣。論文測的是 model 用 context 的方式，不是 window 大小。要確認新 model 沒有這個問題，得用同樣的位置實驗量一次。

  1. 必讀Writing Effective Tools for Agents, with AgentsAnthropic · 工程文章 · 2025 · 約 20 分

    Tool 的描述與輸出都是介面的一部分；tool 定義每一輪都佔 context。

    導讀現場拿你們的一個 tool（或 MCP tool），用文中的原則審一遍。

    摘要讀約 3 分；原文約 20 分

    一句話：Tool 是確定性程式與不確定的 agent 之間的契約，要為 agent 設計，而非把 API 包一層。做法：先建 eval，再讓 agent 自己看軌跡改 tool。

    跟這堂課的關係

    Slides p.8–26 的 tool 設計五條原則多數出自這篇，見〈Tool 設計：tool 的輸出就是 context〉。〈第一個問題：輸出進了 context，下一步會更好嗎〉問的「這個輸出進 context 之後會更好嗎」，就是本文 returning meaningful context 一節的主張。Slides 沒講的部分：怎麼用 eval 與 agent 來迭代 tool。

    壓縮後的重點

    1. Tool 不是 function。Function 同樣輸入給同樣輸出。Agent 同樣的起點可能走不同的路：呼叫 tool、憑記憶回答、或先反問。所以 tool 要考慮 agent 會怎麼誤用。
    2. 先建 eval，量的不只是正確率。用真實資料產生數十組任務，每組有可驗證的答案。同時記錄 runtime、tool call 次數、token 用量、tool 錯誤。重複的呼叫暗示分頁或上限要調；反覆的參數錯誤暗示描述不清。
    3. 讓 agent 改 tool。把 eval 的軌跡貼給 Claude Code，讓它找出問題並一次改一批 tool。作者說內部 Slack 與 Asana 的 tool 經這樣迭代後，held-out 測試的表現超過專家手寫版。
    4. Tool 要少、要合併步驟。list_contacts 把整份名單塞進 context，search_contacts 只回需要的。schedule_event 一次完成查空檔加排程，取代兩個 tool。命名加前綴分組，例如 asana_search；前綴或後綴對 eval 有可量的差異，依自己的 eval 選。
    5. 回傳的內容是給 model 讀的。回 name、file_type 這類有語意的欄位，少回 uuid 與 mime_type。把 UUID 換成名稱或序號，能明顯減少幻覺。給一個 response_format 參數：Slack 的例子裡 detailed 是 206 token，concise 是 72 token。
    6. 輸出要省，錯誤要教。用分頁、過濾、截斷，Claude Code 預設把 tool 回應限在 25,000 token。截斷時提示 agent 改用多次小範圍的搜尋。錯誤訊息要說怎麼修，不要只回 code 或 traceback。
    7. Tool 描述是 prompt 的一部分。像寫給新人一樣說明查詢格式與術語。參數名要無歧義：用 user_id，不要用 user。作者說只修描述，就讓 Claude Sonnet 3.5 在 SWE-bench Verified 上大幅減少錯誤。

    原文怎麼讀

    • 可以跳過：What is a tool? 與 Building a prototype 兩節是鋪陳。Looking ahead 是結語。
    • 值得看原文：Returning meaningful context 的 Slack 兩段回應範例，可以直接對照 token 數。Optimizing tool responses 的三個錯誤訊息範例（無用、截斷、有用）。Running an evaluation 的強弱任務範例。
    • 時間：只讀摘要約 3 分；挑 evaluation 與 principles 兩節約 20 分。
    別誤讀

    「每個 API endpoint 包一個 tool，agent 自己會選」不對。文章說這是最常見的錯誤：tool 越多，重疊越多，agent 越分不清。Tool 定義每一輪都佔 context，數量本身就是成本。

  2. 推薦How Foundational Models Became Superhuman in BashPhilipp Schmid · 部落格 · 2026 · 約 10 分

    主張用一個 shell tool 取代很多原子 tool：模型對 bash 的訓練太充分了。

    導讀這是未量化的實務觀察。問：哪些東西（例如截圖）仍然需要專用管道？

    摘要讀約 3 分；原文約 10 分

    一句話：作者把自己的 harness 砍到只剩 bash 和一個看圖的 tool，任務完成率和原來差不多。結論：model 寫 shell 已經夠強，原子 tool 提供的保護可以搬進 harness。

    跟這堂課的關係

    這篇直接回答 slides p.26 的問題「只給 shell 可以嗎」，答案和 SWE-agent 的 11.0% 對 18.0% 相反，見〈Tool 設計：tool 的輸出就是 context〉的〈只給 shell 行不行〉。兩者不矛盾：p.26 的實驗用 GPT-4 時代的 model，這篇是 2026 年的觀察。p.22–23 的 shell 風險這篇都承認，解法是把 p.23 的五項考量做進 harness。它的 log 範例是 p.47 admission 的實作：中間資料留在環境裡，只有摘要進 context，見〈Tool 的輸出不一定要進 context〉。

    壓縮後的重點

    1. 「Superhuman」的意思很窄。Model 能在幾秒內把 git、rg、jq、Python、暫存檔串成一次性的程式。Bash 在這裡是路由層，重活交給 Python、Git、SQLite 或專案的 CLI。
    2. 範例 1：跨 4 個檔案改名，一次套用。Python heredoc 先數每個舊字串出現的次數，數目不對就不寫入。再一次改完 4 個檔，接著跑 ruff、pyright、pytest、git diff --check。失敗的結果留在 working tree，下一圈再修。
    3. 範例 2：用 git bisect run 找 flaky 測試的起點。在暫存目錄開 detached worktree，不動目前的 checkout。每個 commit 跑 5 個 seed，失敗少於 3 次才算 good。
    4. 範例 3：log 太大進不了 context，就在環境裡算。Python 串流讀 gzip 的 JSONL log，每批 10,000 列灌進暫存 SQLite，用 SQL 算前 5 個失敗 endpoint 的錯誤類別與 P95。回到 model 的只有 5 筆 JSON。
    5. 原子 tool 的保護搬進 harness。作者以前主張不讓 agent 用 cat、sed，因為會灌滿 context、錯誤不透明、引號出錯會弄壞檔案。現在 harness 負責四件事：
      • 截斷大輸出，並提示怎麼縮小範圍。
      • 回報 exit status 與時間。
      • 在 model 外面強制路徑與網路規則。
      • 讓長程序在背景跑。
    6. 仍然需要專用 tool 的地方。多模態輸入：shell 能截圖，但像素要經另一個管道進 model。瀏覽器控制：一個 tool 能導航、點擊、等頁面穩定、回傳截圖，用 bash 要拆成好幾步。服務整合可以用 MCP，或用 CLI 讓 schema 不進 prompt。
    7. 作者的建議。刪掉 micro-tool，先試 bash。用 subagent 當 execution firewall，把雜亂的探索關在外面。

    原文怎麼讀

    • 可以跳過：What "superhuman in Bash" means 的定義；Bitter Lesson 那段。
    • 值得看原文：三個範例的完整 script，尤其範例 1 的「先數再寫」與範例 2 的 bisect wrapper。Why atomic tools were right 一節列出 harness 要接手的四件事。
    • 時間：只讀摘要約 3 分；挑三個範例與 atomic tools 一節約 10 分。

    「只給 bash 就好，tool 設計不重要」不對。作者砍掉的是 model 面對的 tool 數量，截斷、診斷、隔離、背景程序這些工作沒有消失，全部搬進 harness。而且他的對照實驗沒有公開數字，只說「差不多或更好」，是一個人的觀察，不是 benchmark。

  4. 推薦How Skills and MCPs Actually WorkLawrence Jones · 部落格 · 2026 · 約 20 分 · L2 已列過

    L2 的必讀，這一講再次指定：single agent、按需 skills、虛擬檔案系統 tools。

    導讀L2 讀過的話，這次只重看「三個問題」那張表，套用到每一條設定。

    摘要讀約 3 分；原文約 20 分

    一句話：Model 只看到一串訊息。MCP 往裡面加 tool 清單，skill 往裡面加指令，plugin 把兩者打包。一條規則放在 system prompt、skill 或 tool 裡，model 對待它的方式不同。

    跟這堂課的關係

    L2 把這篇當擴充機制的說明書，這堂從 tool 設計者的角度重讀：incident.io 用 Go 寫的虛擬 shell，是 p.22–23 shell tool 的 isolation 做法，見〈Execution：shell 最強，保護全在 harness〉。Skill 只有 name 與 description 常駐 context，body 用到才載入，就是 p.48 offloading 的 progressive disclosure，見〈管理的順序：能不進來，就不要進來〉。Purge tool 用必填參數擋住誤刪，是 p.25 原則的實例：保證做進介面，不靠 prompt，見〈Tool 設計：tool 的輸出就是 context〉。差異：slides 講 tool 的輸出怎麼進 context，這篇講規則放在哪一層，model 才會照做。

    壓縮後的重點

    1. Model 沒有狀態，所有狀態都在訊息串裡。Model 不執行 tool；它提出 tool call，harness 執行後把結果接回訊息串，再整串送回。Agent 就是這個流程跑 loop，直到 model 不再要求 tool。
    2. Coding agent 的 tool 很普通。Claude Code 給 model 的有 Bash、Read、Write、Edit、Grep、WebFetch。Bash tool 不一定真的跑 bash；incident.io 用 Go 寫了一個虛擬 shell，回傳看起來像 bash 的結果就夠了。
    3. MCP 是一個列出 tool 的 server，和 HTTP API 幾乎一樣。Agent 連上時抓 tool 清單，合併進 prompt。incident.io 因此也支援任何有 OpenAPI 規格的 HTTP API。
    4. Skill 是一個資料夾，裡面是 SKILL.md 與參考檔。常駐 context 的只有 name 與 description，約 100 token。Body 有幾千 token，用到才載入。這叫 progressive disclosure。
    5. 規則放在 system prompt，model 服從；放在 skill，model 權衡。案例：system prompt 寫「長時間範圍的查詢要拆小」。使用者明確要求一週的 error log，agent 拒絕。同一條規則改成 skill 後，請求正常完成。
    6. 沒有出路的 prompt 會逼出幻覺。「為文件產生 3 到 5 個 tag」碰到空文件，model 只能捏造無關的 tag。作者認為他看到的前沿 model 幻覺，多數來自這種 prompt。
    7. 不能妥協的保證放在 tool 層。Purge tool 要求 dry_run 或 confirm 其中一個參數，兩者都沒有就拒絕執行。Model 無法用推理繞過必填參數。incident.io 也把多個專用 agent 合併成一個 agent 加多個 skill，因為單一 agent 看到完整 context。

    原文怎麼讀

    • 可以跳過：LLM 101 與 Agents are a loop，slides p.4–7 已經講過。Plugins bundle skills 只有一段。L2 讀過的人，MCP 與 skill 兩節也可以跳。
    • 值得看原文：Skills are just instructions 裡的 token 成本圖；Skills replace system prompts 整節，含時間範圍查詢案例、tag 幻覺案例、purge tool 的參數設計。
    • 時間：只讀摘要約 3 分；照上面挑著看原文約 12 分。
    別誤讀

    「把規則移到 skill，agent 就更聽話。」方向相反。移到 skill 的規則，model 會拿它和使用者的要求一起權衡，所以更有彈性，也更可能不照做。絕對不能違反的事，要做成 tool 的必填參數或 hook。
