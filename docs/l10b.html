導讀

你在自己的 GPU 上跑語言模型（下面叫 model）。Profile 之後看到兩件事：prompt 很長時，attention（model 裡讓每個 token 參考前面所有 token 的運算）最慢；逐字輸出時，GPU 常常做完一小段就停下來等。同事提議自己寫一個更快的 attention，或請 AI 來寫。先別動手：這堂講的最佳化，大多已經在開源的 serving engine 裡（vLLM、SGLang 這類把 model 跑成線上服務的軟體）。多數團隊要做的是選一個做了這些的 engine，再確認它真的生效，不是自己寫。

Model 的每一步運算，在 GPU 上是一段一段的小程式在跑，每一段叫一個 kernel。這堂回答的問題是：瓶頸找到之後，GPU 的時間還能從哪裡省，以及有人說他的 kernel 快了很多時，怎麼驗收。瓶頸怎麼找，是 L10〈GPU Basics & Roofline〉的內容。

  • 寫在哪一層：從最上層開始，確定某個運算是瓶頸才往下。最上層是 graph compiler：你寫 model，它替你產生 kernel。往下是 tile language：把矩陣切成一塊塊 tile，你只寫一塊怎麼算，例如用 Python 寫的 Triton。最底層是 CUDA（NVIDIA 寫 GPU 程式的語言），每個 thread 做什麼都要自己寫。越往下控制越多，要自己維護的也越多：GPU 換一代，底層的 kernel 常常要重寫（第 1 章）。
  • 一個 kernel 之內：少搬資料。GPU 的主記憶體叫 HBM，離運算電路最遠，讀寫也最慢。Fusion 把幾個運算合成一個 kernel，中間的結果不寫回 HBM。FlashAttention 用同一個想法處理 attention：把運算切成小塊，每一塊在晶片上算完，最大的中間結果不進 HBM（第 2 章）。
  • Kernel 之外：少空等。時間還會丟在三個地方：晶片裡有一部分運算電路沒有工作；一個 kernel 跑完，CPU 還沒把下一個送到；等另一張 GPU 的資料。逐字輸出時，每產生一個 token 要跑幾十到上百個小 kernel。CPU 每送一個 kernel 花的時間差不多固定，和 kernel 大小無關，所以kernel 越小，等 CPU 送下一個的空檔占的比例越大。做法是把產生一個 token 要送的 kernel 全部錄下來，一次送出，叫 CUDA Graphs（第 3 章）。
  • AI 寫的 kernel：先驗證正確，再相信加速。2025 年有三個公開報出的大幅加速，事後查出是量錯了，靠的是測試或計時的漏洞。驗收時先算物理下限：照這張 GPU 的規格，搬完這些資料、做完這些運算最少要多久？報出來的時間比下限還短，就是量錯了。再用多組輸入確認，新的 kernel 算出的答案和原本的一樣（第 4 章）。

第 5 章是一張 GPU 以外的限制（網路、故障、電力與水），需要時再查。這堂假設讀過 L10：roofline、memory-bound、SM、Tensor Core、HBM 這幾個詞直接用，第 1 章開頭的〈前情〉有一張對照表。

核心觀念

瓶頸找到之後：選哪一層寫、省哪一種時間、怎麼驗收

五章。第 1 章是寫 GPU 程式的幾個抽象層，以及選哪一層寫。第 2、3 章是兩類最佳化：一個 kernel 之內少搬資料，kernel 之外少空等。第 4 章是 AI 寫的 kernel 怎麼驗收。第 5 章離開一張 GPU，看網路、故障、電力與水。

1GPU 程式的抽象層：從 graph compiler 到 CUDA

L10 講怎麼算出、量出瓶頸在搬資料還是在運算。知道瓶頸在哪之後，下一個問題是：要不要自己寫 GPU 程式，寫在哪一層。這一章先看最底層的 CUDA（NVIDIA 寫 GPU 程式的語言與工具）長什麼樣，因為每一層的名詞都從這裡來；再往上看每一層替你做了什麼，最後給一個選層的流程。

Host 與 device：CPU 發 launch，GPU 跑 kernel，launch 是非同步的。Host（CPU 加它的 DRAM）跑 main()，device（GPU 加 HBM）跑 kernel。兩邊用 PCIe Gen5 x16 連接，約 64 GB/s，比 HBM 慢 75 倍，所以資料要盡量留在 GPU 上。兩邊也是非同步的：CPU 發出 kernel 之後不等它跑完：

非同步有兩個後果。第一，kernel 的錯誤（例如讀到超出範圍的記憶體）不會出現在 launch 那一行，要到下一個同步的呼叫才回報，除錯時常常指錯地方。第二，計時要在同步之後才停，否則量到的只是發指令的時間；第 4 章會看到這一點讓人量出假的加速。

CUDA kernel：為一個 thread 寫，每個 thread 用自己的編號算出要處理哪個元素。在 CUDA 裡，你只寫一個 thread 要做的事，再告訴 GPU 要開幾個 thread：

每個 thread 用自己的編號算出位置：i = blockIdx.x × blockDim.x + threadIdx.x。threadIdx.x 是 thread 在 block 裡的編號，blockIdx.x 是 block 的編號，blockDim.x 是每個 block 有幾個 thread（這裡是 256）；.x 表示第一個維度，處理二維、三維的資料時還有 .y、.z。1M 個元素、每個 block 256 個 thread，就是 4,096 個 block。Block 大小取 32 的倍數，才不會有半個 warp，常用 128 或 256。

它在兩種情況下失效：控制流程（依資料決定的 if、Python 的副作用）把計算圖切斷，或慢的那個 op 本身沒辦法 fuse。這時才需要往下一層。

Tile language（Triton）：為一整塊 tile 寫，不為一個 thread 寫。CUDA 要你管每個 thread；要重複用的資料，還要手動搬進 shared memory，再讓同一個 block 的 thread 互相等（同步），確定大家都搬完了才能讀。Tile language 讓你描述一個 block 的工作（Triton 把它叫 program，一個 program 對到一個 CUDA block）：拿到第幾段資料（一個 tile），對這一段做什麼；coalescing、shared memory 的搬運和這種同步交給 compiler。Triton 是最常用的一個。下面是最簡單的例子 vector add：它用不到 shared memory，但看得出寫法從「一個 thread 一個元素」變成「一個 program 一次一整段」；矩陣乘法這類要重複用資料的 kernel，省下的才是 shared memory 和同步：

2Kernel 之內的最佳化：Fusion 與 FlashAttention

GPU 最佳化的手法名字很多，可以收成四個目標，一個快的 kernel 常常四個一起用：

  1. 少搬資料。Coalescing 把一個 warp 的讀取合併成少數幾個大請求：HBM 一次至少送一小段（例如 32 bytes），散開讀時每段只用到其中幾個 bytes，其餘白搬，合併之後搬進來的 bytes 都用得到；tiling 把一塊資料搬進 shared memory，給很多 thread 重複用；fusion 讓中間值留在晶片上，不寫回 HBM。三者都在減少從 HBM 搬的 bytes。
  2. 藏住等待。Async copy（L10〈記憶體階層的查閱〉裡的 cp.async：發出搬運後不必等它完成，thread 先去做別的）、double buffering（算這一塊時先載下一塊）、warp specialization（第 1 章說的 warp 分工：一些 warp 專門搬資料，提早把下一塊載進來，另一些專門算，不必停下來等）。
  3. 露出更多平行。Split-K 把一個長的加總切給好幾個 block 同時算，最後再加起來。在一個 thread 裡也能這樣做：用好幾個獨立的累加器輪流加，下一個加法不必等上一個的結果。
  4. 用更快的指令。改用 Tensor Core、改用低精度。

例如一個快的 GEMM：合併 load（第一個目標）、用兩份 buffer 輪流載 tile（double buffering，第二個）、矩陣乘法裡被加總的那一維（叫 K，A 的欄數、也是 B 的列數）很長時用 split-K 切給更多 block（第三個）、交給 Tensor Core 算（第四個）。四個目標裡，第一個和 L10〈Roofline〉直接相關：memory-bound 的 kernel 只能靠少搬資料變快。這一章講它最重要的兩個做法：fusion，以及把 fusion 和 tiling 用在 attention 上的 FlashAttention。

Fusion：把幾個運算合成一個 kernel，中間值不回 HBM。把好幾個運算合成一個 kernel，前一步的輸出直接留在 register 給下一步用，叫 vertical fusion。例如對 1 GB 的 FP32 資料依序做三個逐項的運算：scale（乘一個常數）、加 bias（加一個常數向量）、ReLU（負數變成 0）：

三個運算的 FLOP 一樣多，時間卻從 1.25 ms 降到 0.42 ms，因為 elementwise 的運算只付搬資料的錢。torch.compile 會自動把這種直鏈 fuse 成一個 Triton kernel。另一種是 horizontal fusion：好幾個運算讀同一個輸入，就合成一次讀取，例如 attention 的 Q、K、V 三個投影，或 FFN 的 gate 和 up（Llama 這類 model 的 FFN 第一步有兩個矩陣，都乘同一個輸入，結果再相乘）。Model 的程式碼常常直接把 weights 接在一起：

標準 attention 的 HBM 流量：n × n 的中間值占大宗。Attention 對每個 head 算三步：分數 S = QKᵀ，機率 P = softmax(S)，輸出 O = PV。這裡看的是 prefill：n 個 token 的 query 一起算，Q 和 K 都是一個 token 一列、各有 n 列，所以 S 和 P 都是 n × n 的矩陣（decode 只有一個 query，S 是 1 × n，第 3 章再談）。標準的寫法每一步一個 kernel，S 和 P 都要寫回 HBM 再讀出來：

Q、K、V、O 各是 n × d，d 是 128；n 是 8K 時，S 是 8K × 8K，是 Q 的 64 倍。所以這些不屬於 model、也不屬於結果的中間值，占了 attention 大部分的 HBM 流量，而且隨長度的平方成長。Fusion 想把 S 留在晶片上，但 8K 時一個 head 的 S 就有 134 MB，一個 SM 上只有幾百 KB，只能一塊一塊算。這裡碰到一個障礙：softmax 要先看完整列才知道最大值（減掉最大值是為了避免溢位，下面會講）和總和，看起來沒辦法一塊一塊算。

Online softmax：不看完整列也能算對。Softmax 先減掉整列的最大值 m 再取指數，避免 e 的大次方溢位，所以看起來需要整列。Online softmax 改成維護三個累計值：目前看過的最大值 m、指數的總和 ℓ、未正規化的輸出 o。新的一塊進來，如果它的最大值比 m 大，舊的 ℓ 和 o 是用舊的 m 算的，就整體乘上 e 的（舊 m − 新 m）次方換算過去，再加上新的一塊；最後 O = o ÷ ℓ。下面用 numpy 驗證它和一次算完整列的結果相同：

3Kernel 之外的空等：SM 之間、launch 之間、GPU 之間

第 2 章處理一個 kernel 裡面的時間。GPU 的時間還會丟在 kernel 以外：SM 之間（有的 SM 沒有工作）、launch 之間（一個 kernel 跑完，下一個還沒送到）、GPU 之間（等別張 GPU 的資料），這一章依序講。下圖把它們和第 2 章的 kernel 之內並排；第四格是人的成本，每一代 GPU 都要有人重寫 kernel，留到第 4 章：

SM 之間的空等：block 比 SM 多時，最後一輪大半的 SM 閒著（Persistent kernel、Stream-K）。一個矩陣乘法切成很多輸出 tile，最直接的寫法是一個 tile 一個 block。GEMM 的一個 block 要用掉一個 SM 大部分的 shared memory 和 register，一個 SM 一次只放得下一個（和第 1 章 vec_add 那種小 block 不同），所以 block 比 SM 多時要分輪跑。例如 160 個 tile 放到 132 個 SM：

第二輪只剩 28 個 block，104 個 SM 整輪閒著，每個 block 還要各自重做一次準備工作（算位址、初始化累加器這類）。Persistent kernel 的做法是每個 SM 只放一個 block，這個 block 跑一個迴圈，一直領新的 tile，準備工作只做一次；CUTLASS 和 DeepSeek 的 DeepGEMM 都這樣做。它省下的是重複的準備，160 份工作分給 132 個 SM，最後還是只有 28 個 SM 有第二份。要讓所有 SM 一起結束，Stream-K（2023）把工作切得比 tile 更細，平均分下去。

Split-KV：decode 的 attention 把一個請求的 KV cache 切給多個 SM 讀。Prefill 有很多 query，切法很多；decode 每個請求只有一個 query，只按 batch × K、V 的 head 數切（共用同一組 K、V 的 query head 放在同一個 block，K、V 只讀一次）：batch 4、每個請求的 K、V 存 8 組 head（GQA，見〈前情〉的 KV cache）時只有 32 個 block，132 個 SM 大半閒著。請求之間的 KV cache 長度又可能差 100 倍，最長的那個請求的 block 要讀最久，其他 SM 做完只能等它。解法是 沿 KV cache 切：serving engine 把 KV cache 切成固定大小的頁來存（paging 是後面的講次），把一個請求的頁分給好幾個 SM：

這是 Flash-Decoding（2023）的做法。FlashInfer（MLSys 2025）再加上兩件事。第一，頁是用到才配的，一個請求的頁不一定相鄰，散在 HBM 各處；它把「每個請求用到哪幾頁」寫成一個 block-sparse 矩陣：一列是一個請求，一欄是一頁，用到的頁才有值。不管頁怎麼散、每頁多大，kernel 都只是照這張表去讀，所以同一個 kernel 就能處理各種 KV cache 的存法。第二，它的排程把工作平均切給固定數量的 block，不管請求多長，每次 launch 的 grid 大小都一樣。下一節的 CUDA Graph 只能重播形狀固定的 launch，所以是第二件事讓它能放進 CUDA Graph。SGLang 預設用 FlashInfer；vLLM 在 Blackwell 上預設用它，在 Hopper 和 Ampere 上預設是 FlashAttention、FlashInfer 排第二（2026-11 查 vLLM 文件）。

Launch 之間的空等：小 kernel 跑完在等 CPU 送下一個（CUDA Graphs、PDL、Megakernel）。Decode 一個 token 要跑幾十到上百個小 kernel。Launch 雖然是非同步的，每次 launch 還是要幾微秒的 CPU 與 driver 時間；小 kernel 在 GPU 上也只跑幾微秒，跑得比 CPU 送下一個還快，GPU 就跑完在等下一個送到（L10〈Profiler〉說的 overhead-bound 就是這種情況）。Kernel 越小，這段空檔占的比例越大。三種做法一步比一步徹底：

  • CUDA Graphs。把一步 decode 的所有 launch 錄一次，之後每個 token 只送一次。vLLM 和 SGLang 都這樣做，torch.compile 的 reduce-overhead 也是用它。限制是形狀和記憶體位址要固定。
  • PDL。Programmatic Dependent Launch。同一個 stream（GPU 上的一條工作佇列，同一條佇列裡的 kernel 依序執行）裡，下一個 kernel 原本要等上一個完全結束才開始。PDL 讓上一個 kernel 提早通知「可以開始了」，下一個 kernel 先做自己的準備，到真正需要資料時才等待（兩個 API 是 cudaTriggerProgrammaticLaunchCompletion 和 cudaGridDependencySynchronize）。要 Hopper 以上，可以放在 CUDA Graph 裡。
  • Megakernel。整個 model 的一步只 launch 一次。Hazy Research 2025 年的量測：Llama-3.2-1B 的 batch 1 decode 每一層約 7 個 kernel、共 16 層，vLLM 和 SGLang 約用到 H100 頻寬的 50%；他們的 megakernel 用到 78%，每個使用者的速度約是 SGLang 的 1.5 倍。Mirage 的 MPK（2025-12）讓 compiler 自動把整個 model 編成一個 megakernel；論文報告，端到端的推論延遲比一個 op 一個 kernel 的 serving 系統最多快 1.7 倍。

GPU 之間的空等：讓通訊和計算同時進行（FLUX、DeepEP）。Model 大到一張 GPU 放不下時，要切到多張（parallelism，後面的講次）。最常見的 tensor parallelism 把每個矩陣乘法切給 8 張 GPU，每張只放 1/8 的 weights。代價是矩陣乘法前後都要通訊：算之前，每張要先向其他張收齊完整的輸入（這種通訊叫 AllGather）；算完，各張手上只有部分的結果，要加總之後再分回去（叫 ReduceScatter）。寫成分開的 kernel 時，GEMM 要等整個通訊做完：

FLUX（2024）把通訊 fuse 進 GEMM 的 tile：一列資料到了就開始算，每個 tile 的結尾直接寫給負責這一段結果的 GPU，不另外起 kernel。論文報告 最多能藏住 96% 的通訊，8 張 GPU 上 prefill 比 vLLM 快最多 1.66 倍、decode 快 1.30 倍。MoE 有另一種通訊：每個 token 要送到別張 GPU 上的 8 個 expert，算完再收回來（all-to-all）。DeepSeek 的 DeepEP 把一個 batch 拆成兩個 micro-batch，一個在算時，另一個在傳。DeepEP 的 README 量到的傳輸速度，機內（NVLink）和跨機（RDMA：網卡直接讀寫另一台機器的記憶體）都已經接近線路的上限，傳輸本身沒什麼能再快的空間，剩下能做的就是把它藏在計算後面。

Serving engine 的選擇：選已經內建 kernel 最佳化的 engine，不自己寫。這一章的手法幾乎都已經在 serving engine 裡：vLLM 和 SGLang 都內建 FlashInfer 與 CUDA Graphs，DeepEP 和 DeepGEMM 也是開源的。本文的判斷是，讀者要做的決定通常是兩件：選一個做了這些的 engine，再用 Nsight Systems（NVIDIA 的 profiler，畫出每個 kernel 何時開始、何時結束）的 timeline 確認 kernel 之間沒有大空檔、通訊有藏在計算後面。看到空檔，照第 1 章〈抽象層的選擇〉那張流程圖的第一問處理。

4AI 寫的 kernel：先驗證正確，再相信加速

每一代 GPU（TMA、TMEM、FP4）和每一種新的 attention 都要新的手調 kernel，會寫的人很少。一個看法是 agent（會自己寫程式、跑工具、看結果再改的 AI，第 3 章開頭提過）會變成新的 compiler：agent 寫 kernel，編譯，和 PyTorch 的參考實作在很多種形狀上比對，profile，再把結果回給 agent。衡量的指標叫 fast_p，由 KernelBench 定義。KernelBench 是 Stanford 一個研究團隊做的 benchmark：每題給一段 PyTorch 程式，要 model 寫出算一樣結果、跑得更快的 kernel。fast_p 是正確、而且比 PyTorch 快 p 倍以上的題目占多少：

Benchmark 的五類漏洞：計時停太早、沒做該做的工作、正確性測試太弱、動到 harness 的狀態、baseline 太弱。把五個案例的原因，加上下面 AutoMegaKernel 那種比較方式，分成五類（本文的整理）：

  • 計時。停在工作做完之前；或題目小到只量到 launch：參考實作是好幾個 PyTorch op、要 launch 好幾次，新 kernel 只 launch 一次，題目小時時間幾乎都是 launch，量到的加速是少 launch 幾次，不是算得快。少 launch 本身是真的改進（第 2 章的 fusion），但在真正的 model 裡，這個 op 前後的 launch 空檔多半已經被 CUDA Graphs 這類做法藏起來（第 3 章），小題目上量到的倍數搬不到實際的 serving 上。
  • 沒做該做的工作。直接呼叫 torch 或 cuBLAS、寫了 CUDA 卻沒呼叫，或偷偷縮小 batch 這類參數。
  • 正確性。只測一組形狀、一種分布，輸出幾乎是常數。
  • Harness 的狀態。重複使用的記憶體、被改掉的參考實作。
  • Baseline（拿來比的對象，通常是 PyTorch 的參考實作）。太弱，或精度不對等。

最後一類連作者自己都會標明：2026-06 的 AutoMegaKernel 論文寫明，它拿 int8 weights 的 megakernel 和 bf16 的 cuBLAS 比，是不對等的比較。

Speed of light：roofline 給的時間下限。L10〈Kernel 時間的公式〉也是一個下限：任何 kernel 都不可能比 max(bytes ÷ 頻寬, FLOPs ÷ peak) 更快。KernelBench v0.1 把它變成一條檢查：H100 SXM5 上 4096 × 4096 的 BF16 矩陣乘法要做 2 × 4096³ ≈ 137 GFLOP，A、B、C 三個矩陣各 4096² 個數字、每個 2 bytes，共約 100 MB。算力的下限是 137 GFLOP ÷ 989 TFLOP/s（H100 的 BF16 peak）≈ 0.14 ms；頻寬的下限是 100 MB ÷ 3.35 TB/s（H100 的頻寬）≈ 0.03 ms，比算力的下限短，所以這個 kernel 的下限是 0.14 ms。報出來的時間比 0.14 ms 還短，不必看 code 就知道是量錯了：

AI kernel 的驗收：speed of light、多組輸入、同步後計時、強 baseline、讀 code。依上面的案例，本文的判斷是：一個 kernel 要合進 serving 的程式碼之前，至少要過這五關：

  1. 先算 speed of light。比下限還快就停，先查計時和測試。
  2. 正確性用很多組輸入。多種形狀、多種分布，每次用新的輸出 buffer；先確認輸出會隨輸入明顯變化。
  3. 計時在全部工作結束之後。同步整個 device，不只主 stream；先暖機，跑很多次；問題要大到 launch 的 overhead 不主導（KernelBench v0.1 用 1–15 ms）。
  4. 和同精度的強 baseline 比。和 torch.compile、cuBLAS 比，不只和 eager PyTorch 比（一個 op 一個 kernel、照程式一行一行執行，沒經過 torch.compile；fast_p 比的就是它）。
  5. 讀 code。CUDA 真的有執行、沒有偷偷改回 torch、沒有碰 harness 的狀態。分數最高的那幾個一律人看。

第一條最便宜，卻擋得住最誇張的那一類：參考實作離下限不遠時，報出十倍、百倍的加速，新 kernel 的時間就會 比物理下限還短。它擋不住兩種：題目小到時間都花在 launch 上（所以第三條要求問題夠大），以及把參考實作變慢的那種（上表最後一列）。後四條擋的是比較小、比較像真的假加速：數字看起來合理，只看數字的人看不出來，所以 驗收的檢查做得越完整，agent 寫的 kernel 才越能信。

5一張 GPU 之外：網路、故障、電力與水

L10 和這一堂的前四章大多在一張 GPU 裡面，只有第 3 章後半碰到 GPU 之間的通訊。Model 大到一張放不下，或請求多到一台不夠時，瓶頸會移到 GPU 之間的線、機房的電和故障率。AI 硬體有四個挑戰：網路、可靠性、電力、水。它們都不是寫程式能改的，所以要在買硬體、放工作之前就算進去。

Scale-up 與 scale-out：機內走 NVLink，跨機走 RDMA。同一台 server 或同一櫃裡的 GPU 用 NVLink 直接相連，叫 scale-up；跨 server 要經過網卡，用 RDMA（網卡直接讀寫對方機器的記憶體，不經過 CPU，L1 講過），叫 scale-out：

GPU 之外的頻寬：NVLink 比 HBM 少約 10 倍，跨機的 RDMA 再少約 9 倍。H200 的 HBM 是 4.8 TB/s；NVLink 兩個方向合計 900 GB/s，每個方向 450 GB/s，約少 10 倍；跨機器的 RDMA 每張只有約 50 GB/s，又少約 9 倍。拿一個具體的搬運來算：prefill 和 decode 放在不同機器時（L1〈瓶頸不同，就拆到不同的 GPU〉），prompt 的 KV cache 要整份搬過去：

搬的時候只用一個方向，所以 NVLink 要用每個方向的 450 GB/s 算。走網卡比走 NVLink 慢 9 倍，所以需要頻繁交換資料的工作，例如 tensor parallelism，通常放在同一個 NVLink 網域裡；要跨機器的搬運，就要像第 3 章那樣藏在計算後面。怎麼切是後面 parallelism 的講次。

硬體故障：16K 張 GPU 約每 3 小時中斷一次。L1〈故障是常態〉用 MTBF（mean time between failures，平均多久壞一次）算過：GPU 越多，壞得越頻繁。Llama 3 的論文給了實測：最多 16K 張 H100 預訓練 405B 的 model，54 天裡有 419 次非預期的中斷，平均約 3.1 小時一次，約 78% 確認或疑似是硬體問題。

和 GPU 有關的原因合計近六成，而且 HBM 的故障比網路還多（17.2% 對網路交換器與線材的 8.4%）。即使如此，Meta（Llama 3 的開發者）仍維持 90% 以上的有效訓練時間，靠的是 checkpoint（定期把訓練狀態存檔，壞了從最近的存檔重來；和 L10〈MFU〉說的、為了省記憶體而重算的 activation checkpointing 不是同一件事）和自動重啟。對 serving 來說，同樣的頻率代表請求要能在 GPU 壞掉時搬到別處。

電力：一櫃 120 kW，要液冷。GPU 越密，一櫃的功率越高：

本文的判斷：自建機房的團隊，能裝哪一代 GPU，常常先由每櫃的電力和散熱決定，再由預算決定。一般機房一櫃只供得起十幾 kW，NVL72 這種櫃子要改電力和改成液冷，這是以月或年計的工程，比任何 kernel 最佳化都更早定下上限。

用水：消耗量與取用量是兩個數字。散熱也用水。〈Making AI Less Thirsty〉（Li 等）估計：在 Microsoft 美國的資料中心訓練 GPT-3，直接蒸發約 70 萬公升的淡水；全球 AI 在 2027 年可能取用 42 到 66 億立方公尺的水。兩個數字量的東西不同：前者是消耗（蒸發掉，不回到當地水源），後者是取用（抽出來，可能排回去）；同一篇對 2027 年消耗量的估計只有 3.8 到 6.0 億立方公尺，約是取用量的十一分之一，引用時要分清楚。

L10 和這一堂的帳到這裡為止：一個 kernel 卡在 bytes 還是 FLOP，一步 decode 讀多少 bytes，怎麼量，怎麼少搬、少等，以及一張 GPU 之外的限制。後面的講次把這些用在 serving engine 上：怎麼排 batch、怎麼管 KV cache 的記憶體、怎麼切到多張 GPU。
