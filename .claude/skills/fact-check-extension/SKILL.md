# 查證轉來的評論，寫成本文延伸

2026-10-29（L3 2.2 `#x3`，林承慶的 Caveman 評論）與 2026-10-30（L3 2.3 `#x4`，SWE-Shift）各做過一次。James 轉來的東西通常是「一段評論＋它引用的數字」，他要知道：數字從哪裡來、量的是什麼、評論的結論有沒有被數字撐住。

## 1. 找出處

- 記下作者、媒體、日期、網址。他只貼文字沒給來源，就問一次；他不在，就寫「原出處待補」，並寫進 `guide/README.md` 的那一則更新。
- 評論是轉述（簡中轉譯、截圖），一律找到它引用的原始來源再寫，不從轉述取數字。

## 2. 拆成主張，一條一行

把評論改寫成 3–6 條可以查證的主張（「X 讓 output 少 65%」「Y 在主幹變動時掉多少」），加上評論自己的建議。純意見不用查，但要標出它依賴哪一條主張。

## 3. 逐條對回原始來源

| 來源 | 怎麼查 |
|---|---|
| 論文 | WebFetch arXiv 摘要頁與 HTML 全文；記版本（v1、v2）與日期 |
| repo 的數字 | `gh api repos/OWNER/REPO/contents/PATH --jq .content \| base64 -d` 讀 `results.json`、`evals/`；記 tag 或 commit |
| 產品行為 | 官方文件（Claude Code：`https://code.claude.com/docs/en/...`） |
| 之後的量測 | WebSearch 找評論發表後的重跑、反例、同類 benchmark |

每條寫下：原始來源怎麼說、量的是什麼（任務、對照組、指標定義）、評論怎麼用它。查不到的就寫查不到，不推測。所有計算用 `python3` 驗算。

## 4. 判斷

每條給一個判斷：**成立**、**部分成立**（數字對、解讀過頭；或對照組不公平）、**量到了 vs 合理推論**（benchmark 只量到其中一半）、**不成立**、**查不到**。原因一句，指出差在哪：對照組、版本、指標、樣本。

常見的落差（兩次都遇到）：

- 對照組沒有叫 model 做同樣的事（Caveman 65% 的對照沒寫 "Answer concisely."）。
- benchmark 的成功率被拿來當事故頻率。
- 數字是舊版規則或舊版 repo 量的。

## 5. 決定放哪裡，直接寫

James 幾乎不看純文字版（2026-10-30），所以不先回報等 OK：判斷完就決定放在哪一章（評論的數字和哪一章的正文有關），直接寫進 HTML、跑檢查、push，回覆時再列判斷。

## 6. 寫成本文延伸

格式見 `guide/STYLE_ARTICLE.md` 第 4 節「本文延伸」。內容順序：

1. 第一段：評論是什麼（作者、出處、日期）、它的主張一句、本文比對的日期。
2. 每條主張一個粗體小標：先講原始來源量什麼、怎麼算成功，再講評論怎麼用它、判斷。
3. 至少一張圖或表：數據就照 repo 或論文的資料重畫（`figure.diagram`），figcaption 寫「依 … 重畫，本文的整理，YYYY-MM-DD」；建議可以做成具體做法的，附 `figure.file` 案例。
4. 最後一段：結論，以及評論的建議在什麼條件下成立。

規則：

- 引用評論原文一句以內、15 字以內，其餘改寫；一個來源最多引一句。
- 紅字最多 1 處（STYLE_ARTICLE 6c）。
- 正文裡和這個數字有關的那一句，加一句「見本文延伸〈標題〉」；進階題的參考觀點用到同一個數字時也加。
- 數字會隨上游更新的（eval、release），在 `guide/README.md` 那一段寫明「依哪一版，重跑後要更新」。

## 7. 錨點與跨頁連結

`tools/add_anchors.py` 依頁面順序重編 `#xN`，插在中間會讓後面的號碼全部往後移。插入後：

```bash
grep -o 'lXX.html#x[0-9]*' docs/*.html   # 別頁連進來的 x 錨點，逐一對回新的號碼
```

2026-10-29、10-30 兩次都改到 L5、L8 連到 L3 的 `#x`。commit 訊息寫出「#x4–#x9 改成 #x5–#x10」這類對照。

## 不要做的事

- 不要從轉述或截圖取數字；找到原始來源。
- 不要把「benchmark 量到的」和「評論推論的」混成同一個結論。
- 不要大段引用評論或論文原文。
- 查不到的細節不寫。
