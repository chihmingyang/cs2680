  1. p.28 · Agentic coding 的等級

    Slide 把 agentic coding 分成幾個等級？從 Level 3 到 Level 4，你做的事有什麼改變？Level 5 多了什麼？

    參考答案

    6 個等級，Level 0 到 Level 5：no AI、assist（自動補完）、supervised（AI 寫函式，你 review）、scoped（交出一個任務，再 review 程式碼）、goal-driven、parallel agents。

    Level 3 你還是逐行 review 程式碼。Level 4 由 AI 寫全部，改由測試負責驗證。Level 5 用多個 subagent 平行分工。

  2. p.30–31 · AI 系統是什麼

    AI/ML 的視角和 AI systems 的視角，各問什麼問題、各優化什麼？Slide 說 AI 系統的零件和傳統系統有什麼關係？

    參考答案

    AI/ML 問該用哪個 model、怎麼設計，優化 accuracy 與能力。AI systems 問怎麼大規模地訓練與 serve，優化 GPU 使用率（performance）、資源浪費（efficiency）、停機時間（reliability）、碳排（sustainability）。

    零件和傳統系統一樣：scheduling、狀態管理、通訊、caching、fault tolerance、security、observability。p.31 補充：把 model 的能力變成產品，比 AI 本身更難。

  3. p.32 · Prefill 與 decode

    一次 LLM 請求分哪兩個階段？各受什麼限制？為什麼一個請求要跑多久，事先無法預測？

    參考答案

    Prefill 一次處理整段 prompt，受算力限制（compute-bound）。Decode 一次生成 1 個 token，每一步都要讀全部權重和 KV cache，受記憶體頻寬限制（memory-bandwidth-bound）。

    執行時間取決於 model 輸出多少 token，這個數字要等生成結束才知道。所以 scheduler 很難決定先跑誰、要預留多少記憶體。

  4. p.33 · 不確定的運算

    同一個 prompt，為什麼可能得到不同的輸出？Batch size 在這裡扮演什麼角色？Slide 把誤差來源分成哪三類？

    參考答案

    浮點數加法沒有結合律，加總順序一變，結果就差一點點。Model 替每個候選 token 打分數，前兩名很接近時，這一點差異就能換掉下一個 token，後面的文字全部改變。

    Batch size 改變時，GPU 可能換 kernel 或換切法，加總順序跟著變。三類來源：runtime（排程、記憶體存取順序、batch size）、software（FMA、autotuning、subnormal）、hardware（CUDA core 與 tensor core、不同世代的數值格式）。

  5. p.34–36 · 狀態、故障與耗電

    AI 系統的狀態有多大？16K 張 GPU 的叢集多久壞一張？一台 server 的功率從多少升到多少？

    參考答案

    權重從幾 GB 到幾 TB；KV cache 每個 token 要幾十到幾百 KB。瓶頸常在搬資料，GPU 放不下時要搬到 CPU 記憶體或 SSD。

    GPU 的 MTBF 是 50,000 小時、年故障率 9%。16K 張 GPU 的叢集約每 3 小時壞一張。GPU 每張 700–1000 W，一台 server 放 4–8 張，功率從 800 W 升到 6,000 W。

  6. p.38–40 · Agent 是什麼

    Slide 把 agent 的工作拆成哪 5 步？把 agent 比成電腦時，LLM、context window、tool、harness 各對應什麼？哪兩點和傳統電腦不同？

    參考答案

    Plan、act、observe、adapt、deliver。Agent 用 AI model 對目標推理、使用外部 tool、執行多步動作，直到任務完成。

    LLM 是 CPU，context window 是 RAM，tool 是周邊裝置，harness 是 OS，agent 是 application。不同點：programming model 用自然語言，同一份程式每次可能走不同路徑；failure model 以 LLM 出錯為常態，所以 harness 要做隔離與權限控制。

  7. p.41–42 · 為什麼是系統問題

    傳統 serving 和 agent serving 的流程各長什麼樣？Agent 等 tool 的時候，GPU 上發生什麼事？Stack 分哪 6 層？

    參考答案

    傳統是 request → inference → response。Agent 是 infer → tool → infer → retrieval → … 的長鏈，跨過 GPU、CPU、storage、network 與外部服務。每一步都等上一步，整條鏈都在 critical path 上。

    Tool 執行時，這個 agent 用不到 GPU，它的 KV cache 卻還佔著記憶體。6 層由上到下：Application / User、Agent / Harness、Model、Serving System、Runtime / Kernels、Hardware。

  8. p.43–44 · 要優化什麼

    Slide 說哪個目標不適合 agent？要優化的目標是什麼，受哪些限制？TTFT、TPOT、GPU 使用率這些指標，slide 怎麼評價？

    參考答案

    Throughput 不適合當 agent 的目標。目標是讓任務成功率最高，限制是 latency、cost、resources、reliability、security。

    TTFT、TPOT、tool-call latency、GPU 使用率「有用，但不夠」。要看任務成功率、端到端延遲、每個任務的 token 數、每個成功任務的花費與耗能。Tokens/sec 高，agent 仍可能更慢、更貴。

  9. p.45–46 · Observability 與 9 個問題

    Agent 的 trace 是什麼形狀？Slide 用哪一句話說明 observability 的重要？課程要你回答幾個問題，而且要答到什麼程度？

    參考答案

    一棵巢狀的 trajectory：session → turn → agent step → model request、tool call、tool result → subagent → …。那一句是「You cannot optimize what you cannot observe.」

    9 個問題，從 batching 為什麼拖慢 agent，到怎麼優化每個成功任務的成本。Slide 要求課程結束時，你能用數字（quantitatively）回答它們。
