  1. p.6–7 · Memory 的兩層

    Agent 的狀態分哪兩層？Store 裡的內容要經過什麼，model 才看得到？Slide 把 memory 設計拆成哪 7 個問題？

    參考答案

    Context window 是暫時的工作狀態；memory store 在 context 之外，跨 session 保存。LLM 是 stateless，store 的內容要先搬進 context，才會影響下一步。

    7 個問題：誰擁有這份 memory、值得留下嗎、要變成什麼形式、這個任務需要嗎、可以歸納出什麼、還有效嗎、放在哪裡。

  2. p.8 · 何時寫入

    「每次互動都寫」和「只在使用者要求時寫」各有什麼代價？兩端之間，slide 列出哪幾種選擇性寫入的做法？

    參考答案

    每次都寫：recall 最高，雜訊也最多。只在使用者明確要求時寫：precision 最高，但會漏掉很多。

    中間的做法：確定性規則（heuristics），例如使用者糾正時就寫；小型分類器打分數，高於門檻才寫；定期用 LLM 回顧紀錄，挑出值得留的。

  3. p.9–10 · 格式與後端

    同一句「We moved serving from vLLM to SGLang」可以存成哪 4 種格式？摘要和結構化狀態各丟掉什麼？4 種儲存後端各擅長什麼查詢？

    參考答案

    原始 episode（整句原話）、文字摘要、結構化狀態（{"serving_engine": "SGLang"}）、knowledge graph（Project → USES → SGLang）。摘要丟掉「以前用 vLLM」和「何時換的」；結構化狀態只能存 schema 裡有的欄位。

    後端：純文字檔，人能直接看、diff、搜尋；KV 或關聯式資料庫，精確查找、過濾、transaction；vector store，相似度搜尋；graph database，關係查詢與 multi-hop 走訪。

  4. p.11–12 · 使用時機與檢索訊號

    誰決定何時讀寫 memory，有哪 3 種方式？檢索時，除了語意相似，slide 還列出哪 4 個訊號？

    參考答案

    Automatic：每一輪都自動讀寫，可預測但多一段 latency，也帶進無關內容。Runtime-controlled：程式判斷，有效率但要規則或分類器。Model-controlled：model 透過 tool call 自己決定，按需觸發，但可能該查沒查。很多系統混用。

    4 個訊號：scope（同一個使用者、專案、實體或任務）、importance（漏掉或放進來的代價）、validity（對這個任務、在此刻仍成立）、provenance（來源、信心、證據）。

  5. p.13–15 · 歸納、遺忘與有效時間

    遺忘有哪 4 種做法？每條記憶要帶哪兩個欄位？p.15 的時間軸裡，vLLM 和 SGLang 各在什麼時候有效，來源是哪個 episode？

    參考答案

    4 種做法：標記失效、永久刪除、TTL 到期、分層並移出 active memory。兩個欄位：valid time（這個事實在哪段時間成立）和 provenance（從哪裡來）。

    2026 年 4 月用 vLLM，狀態是 superseded；2026 年 6 月用 SGLang，狀態是 current。來源是 Episode 28 的原話「We moved serving from vLLM to SGLang」。p.13 的歸納例子則把 4 個推論相關的問題合成一條 hypothesis，信心 medium。

  6. p.16–17、p.23 · 誰擁有 memory

    Agent-owned 和 dedicated memory system 差在哪裡？3 個 dedicated 系統各以什麼為核心？p.23 的兩種堆疊差在哪一層？

    參考答案

    Agent-owned：memory 是 harness 裡的檔案，harness 直接寫到磁碟。Dedicated：memory 是 agent 呼叫的服務，可以跨 agent、跨 session 共用。

    Mem0 以事實為中心；Graphiti 是有時間軸的 knowledge graph；supermemory 同時管 profile、記憶與文件。p.23 的差別在中間層：獨立的 memory layer 接 vector、SQL、graph 等儲存；memory 在 harness 裡時，runtime 自己管理 Markdown 檔。

  7. p.20–22 · 失敗模式與評估

    Memory 有哪 8 種失敗模式？評估 memory 要從哪 4 個面向量？3 個 benchmark 各有多大？

    參考答案

    Retrieval miss、context pollution、memory hallucination、staleness、isolation failure、overgeneralization、persistent prompt injection、unbounded growth。

    4 個面向：寫入與更新、檢索、系統成本（latency、token overhead、store growth）、治理（deletion compliance、scope isolation）。Benchmark：LoCoMo 1,540 題、10 段長對話；LongMemEval 500 題、5 種記憶能力；BEAM 2,000 題、最長 10M token。

  8. p.24 · 錯誤會相乘

    每步成功率 95% 時，1、5、10、20、50 步全對的機率各是多少？這個計算的假設是什麼？為什麼真實的 run 更差？

    參考答案

    95%、77%、60%、36%、8%。50 步全對約 13 次才有 1 次。一個 run 要每一步都成功才算成功。

    假設每步獨立、成功率 0.95。真實的 run 更差，因為錯誤會往後傳：早期的錯誤讓後面每一步更容易錯。

  9. p.26–32 · 五層失敗與對策

    失敗的來源分哪 5 層？p.32 替每一層給了什麼設計原則？Slide 的結語怎麼說這個領域的現況？

    參考答案

    5 層：使用者與任務規格、agent harness、LLM、tool 層、環境。p.27–31 每層一張表，例如規格的 proxy objective、harness 的 context 截斷、model 的未驗證就宣布成功、tool 的靜默失敗、環境的版本不符。

    原則：規格把「完成」寫成測試；harness 給每個 run 上限並 checkpoint；model 要求證據；tool 失敗要大聲；環境固定並隔離。結語：我們對大規模的 agent 了解不多，正式的最佳實踐很少。
