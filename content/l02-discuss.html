5 · 問題討論

讀書會討論題

這 6 題可以在讀書會前先發給大家回答。每題附情境、回答要點與相關 slide。「參考觀點與追問」給主持人用，建議討論後再展開。

只複製題目、情境與回答要點，方便貼到群組。

  1. 概念 · Agent loop · p.7–17

    用一個具體例子，說明一個 prompt 在 Claude Code 裡從輸入到完成的過程。哪些步驟由 model 決定，哪些由 harness 執行?

    情境：你在一個 Python 專案裡輸入「修好 tests/test_auth.py 失敗的測試」。

    回答時請涵蓋
    • 依序列出每一圈 loop:model 提議什麼、harness 做了什麼、什麼結果放回 context。
    • 指出至少兩個可能出錯的地方，以及錯誤會在哪一層被擋下(model、權限、hook、測試)。
    • 估計這一輪至少有幾次 model inference,並說明理由。
    思考方向

    先畫出 p.11 的鏈:prompt → M₁ → T₁ → M₂ → … → 回答。再把 p.10 和 p.12 疊上去：每個 tool 執行前，都有一次權限檢查。

    可能出錯的地方：讀錯檔案、改錯位置、沒跑測試就宣稱完成。最後一種在 L6 叫 unverified success。

    參考觀點與追問
    • 典型過程：跑 pytest 看錯誤 → 讀測試和相關程式 → grep 呼叫點 → 修改 → 再跑 pytest → 通過後回報。每次 tool 之前有一次 inference,最後回報再一次，所以 5 次 tool 至少 6 次 inference。
    • Model 決定：讀哪個檔、怎麼改、什麼時候停。Harness 執行：檢查權限、跑指令、把輸出放回 context、context 太大時 compaction。
    • 擋錯的層次：權限擋危險指令;hook 擋違反規則的編輯;測試擋錯誤的修改。「沒驗證就宣稱完成」要靠 Stop hook 檢查，或要求附上測試輸出(p.43 的「結束前確認測試」)。

    追問：測試要跑 20 分鐘時,loop 會變成什麼樣子?Model 只看得到 context;哪些資訊不在 context 裡，卻會影響修改是否正確?

  2. 估算 · Context 與成本 · p.8、p.16

    估算一個 50 步的任務，總共送出多少 input token,以及 prefix cache 大約能省下多少。

    情境：固定內容(system prompt、tool 定義、CLAUDE.md)共 15k token。每一步新增約 2k token(model 回覆加 tool 結果)。不考慮 compaction 和 output token。

    回答時請涵蓋
    • 寫出計算方式和結果。
    • 假設 cache read 的價格是一般 input 的 0.1 倍，估算省下的比例。
    • 提出兩個降低成本的做法，並說明各自的代價。
    思考方向

    第 k 步送出的 context 是 15k + 2k×(k−1)。把 50 步加總。有 prefix cache 時，每一步只有新增的部分是新內容，其他都是上一步送過的前綴。

    參考觀點與追問
    • 總 input:k = 1…50 加總 15k + 2k×(k−1),得到 750k + 2,450k,約 3.2M token。
    • 新內容約 15k + 49×2k ≈ 113k token,其餘約 3.09M 是 cache read。以 0.1 倍計價，約等於 422k 個一般 input token,省下約 87%。Cache 寫入另有加價(約 1.25 倍),算進去約省 86%。
    • 這也解釋了 p.16 的「大部分成本來自 cache read」。L8 的課堂資料顯示,cache read 佔所有 token 的 97.6%。
    • 降成本的做法：先規劃再批次執行，減少步數(代價：規劃本身要花 token);tool 只回傳必要的輸出(代價：可能漏資訊);保持前綴穩定(代價：不能隨意改 system prompt)。

    追問：第 30 步發生 compaction,context 從約 73k 壓到 20k,之後的成本怎麼變?有什麼隱藏代價?(提示:L8 p.26 說，被丟掉的檔案會被重讀，摘要也會讓 cache 重寫。)

  3. 設計 · 規則放在哪裡 · p.22–26、p.43

    下面 5 條規則，各該放在 CLAUDE.md、.claude/rules/、hook、權限設定，還是 CI?說明理由。

    情境：(a) 測試一律用 pytest -x。(b) 不准修改 gen/ 底下的生成檔。(c) API 的錯誤回傳格式要一致。(d) 不准把 secret 寫進 log 或 commit。(e) 只有 migration 檔案要遵守的命名規則。

    回答時請涵蓋
    • 每一條給出選擇和一句理由。
    • 說明你用什麼標準，區分「建議」和「必須」。
    • 指出哪一條需要兩層保護，並說明原因。
    思考方向

    依序問三個問題。違反時，後果是品質變差，還是出事?規則和所有檔案有關，還是只和部分檔案有關?它只約束 agent,還是也要約束人?

    參考觀點與追問
    • (a) CLAUDE.md:每個 session 都需要;違反了只是慢一點。
    • (b) PreToolUse hook 擋 Edit 與 Write:違反會破壞生成流程，必須每次擋下(第 6 段有範例)。
    • (c) .claude/rules/,用 paths 指向 API 目錄，再加 lint 或測試：這是品質規則，只和部分檔案有關。
    • (d) 兩層:hook 或權限擋 agent 的動作,CI 的 secret 掃描擋所有人的 commit。後果嚴重，而且人也會犯錯。
    • (e) .claude/rules/ 加 paths:只在碰到 migration 時載入，平常不佔 context。

    追問:CLAUDE.md 已經 300 行時，你會先刪哪些內容(對照 p.25 的「不該放」)?Hook 本身寫錯了，會造成什麼問題?誰來 review hook?

  4. 團隊實務 · Memory · p.20–31

    Slide 說記憶要像程式碼一樣 review 和版本控制;但 auto memory 是 Claude 自己寫、只存在個人電腦上。在團隊裡，你會怎麼管理這兩者?

    情境：團隊 6 個人共用一個 repo。每個人的 Claude 都依自己的糾正，累積各自的 auto memory。

    回答時請涵蓋
    • Auto memory 在團隊裡的一個好處和一個風險，各舉一個例子。
    • 一條規則：什麼留在個人的 auto memory,什麼升級成 repo 裡的 CLAUDE.md。
    • 誰負責 review CLAUDE.md,多久清理一次。
    思考方向

    Auto memory 依 repo 分開，同一個 repo 的 worktree 共用，但只存在本機(p.27)。它適合個人偏好。團隊都該遵守的事放在本機，就會讓每個人的 agent 行為不一致。

    參考觀點與追問
    • 好處：個人習慣不用每次重講，例如常用的測試指令、回覆語言。風險：記錯或過期的事會一直被載入;每個人的 agent 行為漂移;團隊無法 review。
    • 一條可行的規則：同一個糾正，第二個人也需要時，就升級成 CLAUDE.md 的規則，並走 PR。
    • CLAUDE.md 由 repo 的負責人 review,例如每個 sprint 檢查一次，刪掉過期或矛盾的規則。官方文件提醒：規則矛盾時,Claude 可能任選一條。
    • 個人用 /memory 定期檢查 auto memory。看到可疑內容，例如來自網頁的指示，就刪除，避免 persistent prompt injection(L6)。

    追問：新人加入時，他的 agent 沒有任何 auto memory。這是缺點還是優點?你會在什麼情況下關掉 auto memory?

  5. 風險 · 權限政策 · p.12、p.57

    為三種環境各訂一個權限政策：個人筆電開發、CI pipeline、會碰到正式資料的維運工作。

    情境：可選的模式有 manual、acceptEdits、plan、auto、bypass。也可以搭配 hook,以及 MCP token 的權限範圍。

    回答時請涵蓋
    • 每種環境選一個模式，並說明理由。
    • 你用什麼條件判斷「可以放寬」。
    • 至少一個不論哪種模式，都要用 hook 或權限硬擋的動作。
    思考方向

    從兩件事判斷：出錯時能不能復原，以及影響範圍有多大。可丟棄的環境可以放寬。會碰到正式資料或對外系統，就要收緊，並把關鍵動作做成確定性的檢查。

    參考觀點與追問
    • 個人筆電:auto 或 acceptEdits。出錯可以用 git 復原;但 push、大量刪檔、連外部系統仍然要確認。
    • CI:在用完即丟的 container 裡執行，搭配明確的 allowlist。官方文件的 CI 範例是 --permission-mode dontAsk 加 --allowedTools:清單外的動作一律不做。
    • 維運工作:manual 或 plan,先看計畫再執行。寫入動作用 hook 擋，或要求人工核准;MCP token 只給唯讀(p.57)。
    • 不論模式都要硬擋的例子：刪除正式資料、對外發布、把 secret 送出去。

    追問:Auto 模式由另一個 model 判斷;它判斷錯了，誰負責?你會怎麼稽核?Container 如果掛載了你的 ~/.ssh,還算可丟棄的環境嗎?

  6. 應用 · 擴充機制 · p.35–50

    挑一個你們團隊每週都會重複的工作流程，替它設計 skill、MCP、hook 與 plugin。

    情境：例如發版、處理 bug 單、整理測試報告、上線前檢查。選一個你熟悉的流程。

    回答時請涵蓋
    • 用表格列出：流程步驟、使用的機制、理由。
    • 指出哪一步必須用 hook 保證，以及它擋下什麼。
    • 說明這套設定怎麼分享給團隊，版本怎麼管理。
    思考方向

    照 p.37 的發版例子拆：程序寫成 skill;要碰 GitHub、Jira、Slack 的步驟用 MCP;必須保證的檢查用 hook;最後打包成 plugin。有副作用的 skill 要設成只能手動觸發。

    參考觀點與追問

    以「處理 bug 單」為例:

    • Skill /triage-bug:讀 bug 描述 → 找相關程式 → 重現 → 提出修正與測試 → 請人確認。因為會改程式，設 disable-model-invocation: true。
    • MCP:Jira 讀 bug 單、更新狀態;GitHub 開 PR。Token 只給這個專案需要的權限。
    • Hook:PostToolUse 在每次編輯後跑 formatter;Stop 前確認測試跑過;PreToolUse 擋下直接 push 到 main。
    • Plugin:把 skill、MCP 設定、hook 打包，放在團隊的 marketplace 或 repo,用版本號管理。

    追問：這套設定裡，哪一部分最容易過期?誰負責更新?不用 agent 時，這個流程今天卡在哪裡?Agent 真的解決了那個瓶頸嗎?
