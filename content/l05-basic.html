  1. p.7–8 · 為什麼拆、三張圖

    把工作拆給多個 agent 的四個理由是什麼？描述一個 multi-agent 架構要回答哪三個問題，各對應哪一張圖？

    參考答案

    四個理由：specialization（不同的 model、prompt、tool）、isolation（不同的權限）、parallelism（互不相依的子任務同時跑）、context management（不把整條 trajectory 交給每個 agent）。

    三個問題：誰協調（control graph）、怎麼溝通（communication graph）、工作怎麼拆（task graph）。p.10–17 每頁底部的 Task / Control / Comms 那一行，就是這三張圖的答案。

  2. p.10–12 · 三種中心化架構

    Supervisor–worker 的瓶頸在哪裡？Hierarchical 的難處是什麼？Pipeline 最大的弱點是什麼，slide 給的教訓是什麼？

    參考答案

    Supervisor 是瓶頸：它要讀每一份結果，context 長得最快。Hierarchical 的難處是在哪一層拆、每條邊界要傳多少 context；p.19 把它的弱點寫成錯誤放大。

    Pipeline 沒有回頭路，第 4 站不能要求第 1 站給更好的來源；但它最容易 debug。教訓：加一條 retry edge，勝過多加一個 agent。

  3. p.13–16 · 去中心化與競標

    Committee 的失敗模式是什麼？GPU job router 的例子裡誰得標，為什麼？Swarm 的通訊量怎麼成長？

    參考答案

    Committee：意見一致不代表彼此獨立。同一個 model、同一份 context，就有同一個盲點。Market 的例子規定 5 秒內完成、出價最低者得標：T4 最便宜（$0.05）但要 10 秒，出局；A100（$0.20、3 秒）得標；H100（$0.40、1 秒）最快但較貴。

    Swarm 每對 agent 都相連，通訊量 O(n²)，衝突也難解決，產品中很少用。Blackboard 則靠共享狀態協調，難處是 consistency、concurrency、provenance、versioning、garbage collection。

  4. p.17–19 · 動態拓樸與總表

    Dynamic topology 的優點和弱點各是什麼？總表把八種架構分成哪三類？Market 歸在哪一類？

    參考答案

    優點：容量隨難度增加，簡單的 ticket 保持便宜。弱點：每次執行的形狀都不同，失敗很難重現。p.18 說真實系統是混合體：hierarchy、shared memory、pipeline 混用，需要時再重新規劃。

    三類：centralized（supervisor–worker、hierarchical、pipeline、market）、decentralized（blackboard、committee、swarm）、hybrid（dynamic topology）。Market 歸在 centralized，因為結標的 auctioneer 只有一個。

  5. p.21–23 · 拆解軸、規格、粒度

    可以沿哪六個軸拆任務？好的子任務規格要寫清楚哪八件事？T_multi 的估算式有哪四項，20 個 lookup 的例子怎麼拆？

    參考答案

    六個軸：data、expertise、stage、hypothesis、tool、authority。八件事：目標、輸入與 context、邊界與排除項、tool 與權限、輸出 schema、完成條件、預算與期限、相依關係。

    T_multi ≈ T_planning + T_critical_path + T_communication + T_merge。拆太細，排程與溝通的 overhead 會吃掉收益，所以 20 個一行就能查完的 lookup，要打包成 4 個子任務。

  6. p.24–26 · 動態拆解與失敗

    動態、遞迴、機會式拆解為什麼一定要設上限，要設哪四種？六種常見的拆解失敗是什麼，straggler 的例子數字是多少？

    參考答案

    沒有上限時，每個 agent 都可能再開 subagent，委派會遞迴爆炸。四種上限：spawn 數量、預算、深度、終止條件。

    六種失敗：overlap（兩個 agent 摘要同一篇）、gap（2020–2023 加 2025–2026 漏掉 2024）、hidden dependency、unmergeable outputs（自由文字對上 JSON）、lost global context（每節都對、整份矛盾）、straggler（6 個 agent 約 20 秒完成，1 個花了 4 分鐘）。

  7. p.28–32 · 溝通的維度與訊息格式

    溝通有哪四個維度？訊息 envelope 裡哪些欄位給 runtime 讀、哪些給 LLM 讀？Runtime 認得哪幾種 type？

    參考答案

    四個維度：topology（誰能和誰說話）、medium（訊息、shared memory、檔案）、format 與語意、channel（p2p、broadcast、pub–sub、shared state、request–response）。

    Envelope 外層是 id、task_id、from、to、type，給 runtime 路由、重試、停止用；payload 放自然語言的內容，給 LLM 讀。p.31 的結果訊息另有 claim、confidence、evidence、artifact。九種 type：DELEGATE、QUERY、REPORT、HANDOFF、UPDATE、CANCEL、ACK、ERROR、COMPLETE。

  8. p.35–36 · 經驗法則與 timeout

    溝通設計的四條經驗法則是什麼？A 請 B 買 8 台 GPU instance 後 timeout，有哪三種可能？Slide 給的三個對策是什麼？

    參考答案

    四條法則：照相依關係連線；一條連線只用一種媒介；只有所有人都要知道時才 broadcast；依欄位路由，不依內文路由。

    三種可能：請求沒送到、B 買了但回覆遺失、B 還在處理。不重試是 at-most-once，重試到 ACK 是 at-least-once，可能買 2 次。對策：用 task_id 當 idempotency key；準備 compensation 或 rollback；事先決定重複購買時誰付錢。

  9. p.41–47 · A2A 與 MCP

    Agent card 放在哪裡、告訴呼叫者什麼？A2A task 有哪幾種狀態？MCP 和 A2A 的工作單位差在哪裡？

    參考答案

    Card 在 GET /.well-known/agent-card.json，告訴呼叫者身分、skills、端點、capabilities（streaming、push）、security scheme。Task 的狀態：進行中（Submitted、Working）、中斷（Input required、Auth required）、終止（Completed、Failed、Rejected、Canceled）。

    MCP 連接 agent 與服務，單位是一次 tool call；A2A 連接 agent 與 agent，單位是一個長時間的 task，內部最好不透明。兩者可以疊：一個 A2A 遠端 agent 自己可能呼叫 20 個 MCP server。
