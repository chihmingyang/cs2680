  1. p.6–7 · 成本公式

    Slide 把一個 session 分成哪三個層級？成本公式有哪六個乘數？哪些會隨產品成長，哪些是 agent 設計要壓低的？

    參考答案

    Session、turn、step。一個 turn 從使用者訊息開始，到 agent 回覆結束；一個 step 是一次 model call 加上它要求的 tool call。

    Cost = Users × Sessions/User × Turns/Session × Steps/Turn × Tokens/Step × Price/Token。前兩項隨採用度成長；後四項由 agent 的 trajectory 與單價決定，是設計要壓低的部分。本堂只算 LLM 成本。

  2. p.8–11 · Turn 與 step

    為什麼總成本隨 turn 數的平方成長？使用者回來追問的三個原因和對應解法是什麼？先規劃再批次執行，能把 4 次 model call 減成幾次？

    參考答案

    第 k 個 turn 要重讀第 1 到 k−1 個 turn，所以總量約與 k² 成正比。全班資料：單一 prompt 的 session 佔 68%（Assignment 1）與 75%（Assignment 2）。

    原因：沒有計畫、agent 太早停、沒人檢查結果。解法：先規劃（front-load planning）、拆解任務、交回前自我驗證。p.11：一個動作一次 call 要 4 次；先規劃、再平行執行 3 個 tool，只要 2 次。

  3. p.13–15 · 全班的 token 資料

    主 agent 每一步送出多少 token（中位數與 p90）？Subagent 差多少？Cache read 佔全部 token 的幾 %？Slide 給的價格比是多少？

    參考答案

    主 agent 中位數 200K–300K，p90 600K–700K；subagent 中位數約 80K，p90 約 200K。到第 500 步左右，context 約 650K–670K。

    Assignment 1 的 token 有 97.6% 是 cache read。價格比 cache read : input : output = 1 : 10 : 50。Output 比 fresh prefill 少 5 倍，fresh prefill 比 cache read 少 100 倍。

  4. p.16–19 · 減少每一步的 token

    精簡 context 的三個方向是什麼？20K 的測試 log 留在 context 50 步，和只留 500 token 的摘要，各重讀多少？減少 output 有哪三招？

    參考答案

    丟掉過期的（截短、遮掉、摘要舊 turn）、縮小進來的（只留錯誤、大輸出寫進檔案）、只載入需要的（相關 tool 與 memory、探索交給 subagent）。20K × 50 步重讀 1M token；500 token 的摘要只要 25K。

    Prompt 裡限制長度與格式、API 設 output 上限、用 schema 只要求需要的欄位。推理量依步驟調整：查找用 low，除錯用 high。上限的陷阱：回答可能斷在中間，reasoning 也算 output。

  5. p.21–22 · 單價

    Cache read、batch 各是 base input 的幾倍？疊加後是多少？各有什麼前提？Model routing 有哪三種時機？

    參考答案

    Cache read 0.1×，batch 0.5×，疊加 0.05×。前提：prefix 保持穩定（system prompt、tool 定義、早期歷史放最前面且不改），以及工作可以等（eval、backfill）。

    開始前選（router 每個 turn 選定 model）、失敗才升級（便宜 model 先做，檢查沒過再換大的）、每一步重選（trajectory 變長時依歷史與預算重選）。便宜 model 的一個規劃錯誤會浪費後面很多步。

  6. p.25–26、p.27 · 反向成本與預算

    Compaction、routing、subagent、speculation 的反向成本各是什麼？任務的上限怎麼從 trace 定？什麼情況不需要 LLM？

    參考答案

    Compaction：丟掉的檔案要重讀，摘要重寫 cache。Routing：便宜 model 的壞計畫多出很多步或失敗。Subagent：每個都重讀共用的檔案與指示。Speculation：猜錯浪費 token，還搶同一批 tool。淨節省 = 毛節省 − 反向成本，兩者在同一組任務上量。

    上限取成功任務 p95 的 2 倍；示意值是 $10、80 次 model call、15 分鐘 tool 時間、每步重試 2 次。停滯就停下，交出摘要。步驟每次都一樣、輸入格式固定、只要一個標籤時，用 script、規則或小型 model。

  7. p.29–34 · 速度

    序列與平行執行的完成時間各由什麼決定？Orchestration 有哪四個做法？Speculative action 的三個步驟是什麼，什麼時候划算？

    參考答案

    序列：每一步相加。平行：critical path，最長的那條相依鏈。Orchestration：非同步執行、持久的 session、串流與 pipeline、把服務放在一起。Tool 可能比 model 慢，要先量，卡住的 call 要有 timeout。

    Predict（便宜 model 猜下一個 action）、run early（主 model 思考時先執行）、compare（決定後比對）。划算的條件：常常猜中，而且動作可以撤銷；猜錯的代價是一次白跑的 call。

  8. p.40–45 · 三種 harness 架構

    Monolithic、modular、microkernel 的邊界各在哪裡？執行一段 Python 時三者走的路徑有什麼不同？各自的典型用途是什麼？

    參考答案

    Monolithic：memory、tools、context、planning、execution 全在一個 runtime，元件之間是函式呼叫。Modular：一個 controller 透過介面（MemoryProvider、SandboxProvider 等）使用可抽換的元件。Microkernel：核心只留狀態、排程、安全，能力是外部服務，用標準協定溝通。

    p.44：monolithic 直接在本機執行；modular 呼叫 SandboxProvider.run(code)；microkernel 送執行請求給執行服務，由它配置 sandbox。用途：單獨的 agent、agent framework、multi-agent 基礎設施。

  9. p.47–53 · 8 個 harness 的設計

    哪個 harness 先 sandbox 再詢問？哪個用 compare-and-swap 編輯？哪個 compaction 最早，門檻在哪裡，它還在 tool 執行前先做什麼？

    參考答案

    Codex CLI 先在不能連網的 sandbox 裡執行，要越過邊界才問你（p.47）。DeepSeek Harness 的編輯用 compare-and-swap：model 讀過之後檔案變了，這次編輯就失敗（p.48）。

    Hermes Agent 在 context 用到 50% 就 compaction，是 8 個中最早的；它也在 tool 執行前先把 tool call 寫進 session 資料庫（p.53）。其他例子：OpenCode 每一步存快照供 /undo；Pi 保溫 cache 前先算預期省下是否超過 $0.05。
