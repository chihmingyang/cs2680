1 · 架構

成本的乘數，與壓低每一項的槓桿

看這張圖，先記住一件事：這是乘法。任何一項減半，總成本就減半，所以每一項都值得單獨優化。但每個槓桿都有代價。藍框那一行是整堂課的紀律：毛節省要扣掉反向成本，而且要在同一組任務上量。最下面一行提醒你，時間和錢是兩個目標。

2 · 核心觀念

五個觀念串起整堂課

成本是一串乘數，大宗是重讀的 context p.7–8、p.14–16

一個 turn 從使用者訊息開始，到 agent 回覆結束。一個 step 是一次 model call，加上它要求的 tool call。Slide 把成本寫成乘法：Cost = Users × Sessions/User × Turns/Session × Steps/Turn × Tokens/Step × Price/Token。乘法的好處是每一項都能單獨優化。前兩項會隨產品成長，所以 agent 設計要壓低後四項。

全班的 Claude Code 資料給了基準。主 agent 每一步的 token 數，中位數 200K–300K，p90 600K–700K，幾乎都是重送的 context。Assignment 1 的 token 有 97.6% 是 cache read。Cache read 單價最低，但量太大，仍是成本大宗。

Turn 越多越貴，而且是平方；step 要批次 p.9–13

第 k 個 turn 要重讀前 k−1 個 turn 的內容。所以 turn 數加倍，總量約變 4 倍。全班多數 session 只有一個 prompt，從成本看是好習慣。

使用者回來追問，常見原因有三個：沒有計畫、agent 太早停、沒人檢查結果。對應的解法：先規劃、拆解任務、交回前自我驗證。目標是 agent 一次做完。

Step 數的中位數只有 3 到 4，但有長尾，少數 turn 跑了近 1,000 步。每個 step 都重讀整個 context。先規劃再批次執行，4 次 model call 可以變 2 次。

每一步少送一點：context 要精簡，output 要節制 p.17–21

留在 context 裡的 token，之後每一步都再付一次。Slide 給三個方向：丟掉過期的、縮小進來的、只載入需要的。一份 20K 的測試 log 留 50 步，重讀 1M token。只留 500 token 的錯誤摘要，只要 25K。

探索類的工作交給 subagent。Subagent 從乾淨的 context 開始，每一步的中位數約 80K。主 agent 只拿回摘要。

Output 量小，但單價最高。在 prompt 講清楚長度與格式，用 schema 限制欄位，再用 API 的 output 上限當保險。推理量依步驟調整：查找用 low，除錯用 high。

單價可以差 100 倍，但每個省法都有反向成本 p.22–30

同樣的 token，價格可以差 100 倍。Cache read 是 base input 的 0.1×，batch 是 0.5×，疊加是 0.05×。條件是 prefix 穩定、工作能等。Routing 把簡單的步驟交給便宜的 model。

每個節省都有反向成本。Compaction 丟掉的檔案要重讀，摘要改了 prefix，cache 要重寫。便宜 model 的一個壞計畫會多出很多步。每個 subagent 都重讀共用的檔案。Speculation 猜錯就浪費 token。淨節省 = 毛節省 − 反向成本，兩者都要在同一組任務上量。

所以要替每個任務設上限：金額、model call 次數、tool 時間、每步重試。上限從 trace 定，例如成功任務 p95 的 2 倍。進度停滯就停下，交出摘要。最後再問：這一步真的需要 LLM 嗎？格式固定的步驟用 script 或 regex。

完成時間看 critical path；架構決定邊界在哪裡 p.31–61

省錢的手段多半也省時間，但兩者不同。序列執行時，總時間是每步相加。平行時，總時間是最長的那條相依鏈，也就是 critical path。平行與 speculative action 用更多 token 換更少等待。

速度的其他槓桿在 harness：非同步執行、持久的 shell、串流中就開始 tool call、tool 與 model 放在一起。Tool 本身也可能比 model 慢，先量時間。優化要在迴圈裡做：記錄、量測、一次改一件事、同一組任務重測。

後半講三種 harness 架構。Monolithic 把所有元件放在一個 runtime，通訊最快，隔離最難。Modular 用介面抽換 provider，仍在同一個 process。Microkernel 只保留狀態、排程、安全，能力是外部服務；隔離與擴展最強，通訊最貴。最後的 8 個 harness，每個獨特設計都在解決成本、速度、安全、可靠性之一。

3 · 觀念補充

Slide 預設你已經懂的背景

為什麼 turn 數是平方p.10 背後的算式

假設每個 turn 新增 L 個 token。第 1 個 turn 送 L，第 2 個送 2L，第 k 個送 kL。總量是 1 到 k 的和乘上 L，約 k²/2 個 L。10 個 turn 送 55L；20 個 turn 送 210L，約 4 倍 p.10。

Prefix cache 讓重讀便宜 10 倍，但平方關係不變。所以換任務就用 /clear 開一段乾淨的對話。

Cache read 與 batch 的計價兩種折扣怎麼疊

Prefix cache 從第一個 token 開始比對。開頭相同的部分直接讀快取，收 0.1× 的價格。中間改了一個 token，後面全部重算，寫入 cache 還要加價（Claude API 的 5 分鐘 cache 是 1.25×）p.22。

Batch 把能等的 request 排隊處理，input 與 output 都打 5 折，多數在 1 小時內完成。兩種折扣可以疊加，得到 0.05×。Opus 5.5 與 Sonnet 5.5 的 cache read 更低，是 0.05×。

Routing 的三種時機便宜與貴的 model 怎麼分工

開始前選：每個 turn 開始時，由 router 選定一個 model。失敗才升級：先用便宜的 model，verifier 沒過再換大的。每一步重選：trajectory 變長時，依歷史與預算重選 p.23。

隱藏成本：KV cache 由 model 的權重算出，不能跨 model 共用。換 model 後，整個 context 要以 fresh input 的價格重新 prefill。「錯了很貴」的規劃步驟，值得直接用大 model。

Critical path平行時決定總時間的那條鏈

把任務畫成相依圖，最長的那條路徑就是 critical path。例：plan 5 秒、A 20 秒、B 30 秒、merge 5 秒。序列 60 秒；平行 40 秒，路徑是 plan → B → merge p.32。

把 A 加速一倍，總時間不變。把 B 縮短 10 秒，總時間就少 10 秒。所以優化前先找出哪一條鏈最長。

Compare-and-swap 編輯檔案改過就拒絕寫入

名稱來自 CPU 的 compare-and-swap 指令：先比對目前的值是否仍是預期值，相同才寫入。DeepSeek Harness 記下 model 讀檔時的版本，寫入前再比對一次 p.55。

Model 讀過之後，你或另一個 subagent 可能改了檔案。沒有檢查時，這次編輯會蓋掉別人的改動。oh-my-pi 的 hashline 編輯用行號指定位置，同樣需要這種檢查 p.58。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

便宜不一定快，平行不一定便宜

小 model 單價低，卻可能多走幾步，結果更慢。平行與 speculation 減少等待，token 總量變多。

所以 Assignment 3 的三個指標要分開看：解出幾題、每題花費、每題時間。優化一個指標時，另外兩個要一起量。

淨節省只能在同一組任務上量

p.26 的公式簡單，難在量測。Agent 的 trajectory 有隨機性，同一個任務跑兩次，step 數可能差一倍。所以比較兩個設定時，要用同一組任務、跑多次、看分布。

p.42 的「一次只改一件事」是同一個理由。同時改 compaction 門檻和 model，就分不出效果來自哪裡。L7 的評估方法在這裡派上用場。

Harness 的設計把假設寫進結構裡

Codex CLI 先 sandbox 再詢問。它的假設是：隔離比詢問可靠，人問多了會不看就同意。Claude Code 的權限模式把判斷交給人或分類器。它的假設是：環境不一定能隔離。

兩種假設都成立，差別在部署環境。讀 p.53–60 時，可以問每個設計背後假設了什麼。例如 Hermes 在 50% 就 compaction，假設長任務很多。

Microkernel 只在共用基礎設施時回本

Microkernel 的優點是隔離、獨立擴展、集中管理。代價是通訊開銷、更多故障模式、更難除錯。單一 agent 用不到這些優點，只付代價。

團隊有多個 agent 共用 sandbox、memory、tool 服務時，才值得。Slide 的結論一致：單一 agent 用 monolithic，multi-agent 基礎設施用 microkernel。Modular 是常見的起點。

  1. p.7–8 · 成本公式

    Slide 把一個 session 分成哪三個層級？成本公式有哪六個乘數？哪些會隨產品成長，哪些是 agent 設計要壓低的？

    參考答案

    Session、turn、step。一個 turn 從使用者訊息開始，到 agent 回覆結束；一個 step 是一次 model call 加上它要求的 tool call。

    Cost = Users × Sessions/User × Turns/Session × Steps/Turn × Tokens/Step × Price/Token。前兩項隨採用度成長；後四項由 agent 的 trajectory 與單價決定，是設計要壓低的部分。本堂只算 LLM 成本。

  2. p.9–12 · Turn 與 step

    為什麼總成本隨 turn 數的平方成長？使用者回來追問的三個原因和對應解法是什麼？先規劃再批次執行，能把 4 次 model call 減成幾次？

    參考答案

    第 k 個 turn 要重讀第 1 到 k−1 個 turn，所以總量約與 k² 成正比。全班資料：單一 prompt 的 session 佔 68%（Assignment 1）與 75%（Assignment 2）。

    原因：沒有計畫、agent 太早停、沒人檢查結果。解法：先規劃（front-load planning）、拆解任務、交回前自我驗證。p.12：一個動作一次 call 要 4 次；先規劃、再平行執行 3 個 tool，只要 2 次。

  3. p.14–16 · 全班的 token 資料

    主 agent 每一步送出多少 token（中位數與 p90）？Subagent 差多少？Cache read 佔全部 token 的幾 %？Slide 給的價格比是多少？

    參考答案

    主 agent 中位數 200K–300K，p90 600K–700K；subagent 中位數約 80K，p90 約 200K。到第 500 步左右，context 約 650K–670K。

    Assignment 1 的 token 有 97.6% 是 cache read。價格比 cache read : input : output = 1 : 10 : 50。Output 比 fresh prefill 少 5 倍，fresh prefill 比 cache read 少 100 倍。

  4. p.17–20 · 減少每一步的 token

    精簡 context 的三個方向是什麼？20K 的測試 log 留在 context 50 步，和只留 500 token 的摘要，各重讀多少？減少 output 有哪三招？

    參考答案

    丟掉過期的（截短、遮掉、摘要舊 turn）、縮小進來的（只留錯誤、大輸出寫進檔案）、只載入需要的（相關 tool 與 memory、探索交給 subagent）。20K × 50 步重讀 1M token；500 token 的摘要只要 25K。

    Prompt 裡限制長度與格式、API 設 output 上限、用 schema 只要求需要的欄位。推理量依步驟調整：查找用 low，除錯用 high。上限的陷阱：回答可能斷在中間，reasoning 也算 output。

  5. p.22–23 · 單價

    Cache read、batch 各是 base input 的幾倍？疊加後是多少？各有什麼前提？Model routing 有哪三種時機？

    參考答案

    Cache read 0.1×，batch 0.5×，疊加 0.05×。前提：prefix 保持穩定（system prompt、tool 定義、早期歷史放最前面且不改），以及工作可以等（eval、backfill）。

    開始前選（router 每個 turn 選定 model）、失敗才升級（便宜 model 先做，檢查沒過再換大的）、每一步重選（trajectory 變長時依歷史與預算重選）。便宜 model 的一個規劃錯誤會浪費後面很多步。

  6. p.26–27、p.30 · 反向成本與預算

    Compaction、routing、subagent、speculation 的反向成本各是什麼？任務的上限怎麼從 trace 定？什麼情況不需要 LLM？

    參考答案

    Compaction：丟掉的檔案要重讀，摘要重寫 cache。Routing：便宜 model 的壞計畫多出很多步或失敗。Subagent：每個都重讀共用的檔案與指示。Speculation：猜錯浪費 token，還搶同一批 tool。淨節省 = 毛節省 − 反向成本，兩者在同一組任務上量。

    上限取成功任務 p95 的 2 倍；示意值是 $10、80 次 model call、15 分鐘 tool 時間、每步重試 2 次。停滯就停下，交出摘要。步驟每次都一樣、輸入格式固定、只要一個標籤時，用 script、規則或小型 model。

  7. p.32–37 · 速度

    序列與平行執行的完成時間各由什麼決定？Orchestration 有哪四個做法？Speculative action 的三個步驟是什麼，什麼時候划算？

    參考答案

    序列：每一步相加。平行：critical path，最長的那條相依鏈。Orchestration：非同步執行、持久的 session、串流與 pipeline、把服務放在一起。Tool 可能比 model 慢，要先量，卡住的 call 要有 timeout。

    Predict（便宜 model 猜下一個 action）、run early（主 model 思考時先執行）、compare（決定後比對）。划算的條件：常常猜中，而且動作可以撤銷；猜錯的代價是一次白跑的 call。

  8. p.44–51 · 三種 harness 架構

    Monolithic、modular、microkernel 的邊界各在哪裡？執行一段 Python 時三者走的路徑有什麼不同？各自的典型用途是什麼？

    參考答案

    Monolithic：memory、tools、context、planning、execution 全在一個 runtime，元件之間是函式呼叫。Modular：一個 controller 透過介面（MemoryProvider、SandboxProvider 等）使用可抽換的元件。Microkernel：核心只留狀態、排程、安全，能力是外部服務，用標準協定溝通。

    p.48：monolithic 直接在本機執行；modular 呼叫 SandboxProvider.run(code)；microkernel 送執行請求給執行服務，由它配置 sandbox。用途：單獨的 agent、agent framework、multi-agent 基礎設施。

  9. p.54–60 · 8 個 harness 的設計

    哪個 harness 先 sandbox 再詢問？哪個用 compare-and-swap 編輯？哪個 compaction 最早，門檻在哪裡，它還在 tool 執行前先做什麼？

    參考答案

    Codex CLI 先在不能連網的 sandbox 裡執行，要越過邊界才問你（p.54）。DeepSeek Harness 的編輯用 compare-and-swap：model 讀過之後檔案變了，這次編輯就失敗（p.55）。

    Hermes Agent 在 context 用到 50% 就 compaction，是 8 個中最早的；它也在 tool 執行前先把 tool call 寫進 session 資料庫（p.60）。其他例子：OpenCode 每一步存快照供 /undo；Pi 保溫 cache 前先算預期省下是否超過 $0.05。

  1. 概念 · Cache read 為什麼是大宗 · p.14–16

    為什麼 agent 的 token 大多是 cache read？這件事對「先優化什麼」有什麼含意？

    情境：一個主 agent 的某一步送出 500K cache read、5K fresh input、1K output，接近全班的 p90。價格比 cache read : input : output = 1 : 10 : 50。

    回答時請涵蓋
    • 說明每一步的 context 由哪些部分組成，為什麼大部分是前一步送過的內容。
    • 算出這一步三種 token 各佔多少成本，指出哪一項最大。
    • 比較兩個做法：output 減半，或 context 減半。各省多少？
    思考方向

    回到 L2 的 loop：每一步都重送整個 context，只有新訊息是新的。把 token 數乘上單價，再比較。

    參考觀點與追問
    • Context 的組成：system prompt、tool 定義、CLAUDE.md、歷史對話、tool 結果。每一步只新增上一步的回覆與 tool 輸出，其餘都是送過的 prefix，直接讀 cache。
    • 成本（以 input token 為 1 單位）：cache read 500K × 1 = 500K；fresh 5K × 10 = 50K；output 1K × 50 = 50K。合計 600K。Cache read 佔 token 的 98.8%，佔成本的 83%。
    • Output 減半只省 25K，約 4%。Context 減半省 250K，約 42%。所以先縮小 context（p.17），再管 output（p.19）。
    • 反過來看：prefix 改了一個 token，500K 全部以 fresh 計價，這一步變成 5,100K，約 8.5 倍。所以會變的內容放最後（p.22）。
    • 含意：優化順序是 context 大小 → turn 與 step 數 → 單價 → output。隔離探索的 subagent 就是在縮小主 agent 的 context。

    追問：97.6% 是 Assignment 1 的數字。什麼樣的工作負載會讓這個比例下降？比例下降代表更省錢嗎？

  2. 估算 · 一步與一個 session 的成本 · p.10、p.16

    估算一個 session 的花費，再看 turn 數加倍時花費怎麼變。

    情境：以 input $3 / MTok 為基準，依 1 : 10 : 50，cache read 是 $0.30 / MTok，output 是 $15 / MTok。Session 開始時固定內容 20K token。每一步新增 3K fresh input 與 500 output，下一步起進入 cache。一個 turn 10 步。忽略 cache write 的加價與 compaction。

    回答時請涵蓋
    • 寫出第 1 步與第 40 步各花多少，說明哪一項主導。
    • 算出 4 個 turn（40 步）與 8 個 turn（80 步）的總花費，求比值。
    • 比較：8 個 turn 放在同一個 session，和拆成 2 個各 4 turn 的 session，差多少？代價是什麼？
    思考方向

    第 j 步讀的 cache 是 20K + 3K × (j − 1)。把 40 步加總，cache read 的部分是等差級數。用 python 算最快。Turn 加倍時，fresh 與 output 線性成長，cache read 接近平方成長。

    參考觀點與追問
    • 第 1 步：$0.006 + $0.009 + $0.0075 = $0.0225，fresh 與 output 主導。第 40 步：cache 137K → $0.0411，加 $0.0165，合計 $0.0576；cache read 佔 71%。
    • 40 步：cache read 共 3.14M token → $0.94；fresh 120K → $0.36；output 20K → $0.30。合計約 $1.60。
    • 80 步：cache read 共 11.08M → $3.32；fresh $0.72；output $0.60。合計約 $4.64，是 40 步的 2.9 倍；cache read 那一項是 3.5 倍。
    • 拆成 2 個 session：2 × $1.60 = $3.20，比 $4.64 省 31%。代價：第二個 session 不記得第一個做過什麼，要重讀檔案或靠摘要交接（L6）。
    • 這就是 p.10 的結論。換任務就開新 session；同一個任務要一次講清楚，減少追問。

    追問：把 compaction 加回來：第 40 步後把 context 壓到 30K，之後的 40 步省多少？p.26 的反向成本（重寫 cache、重讀檔案、產生摘要那次 call）要怎麼估？

  3. 設計 · Routing 策略 · p.23、p.26

    為一個混合的工作負載選一種 routing 策略。它省下什麼？反向成本是什麼？

    情境：每天 1,000 個任務。70% 簡單（改文案、小修 bug）、25% 中等、5% 困難（跨多個模組）。小 model 每個任務約 $0.02，通過率依序 95%、60%、20%。大 model 每個任務約 $0.10，幾乎都能通過。每個任務都有自動化測試可以當 verifier。

    回答時請涵蓋
    • 在三種時機（開始前選、失敗才升級、每一步重選）中選一種，說明理由。
    • 估算你的策略每天花多少，和全部用大 model 比較。
    • 指出至少兩個反向成本，以及你會用哪個指標量淨效果。
    思考方向

    有可靠的 verifier 時，「失敗才升級」最容易做：測試過了就收工。算期望成本：小 model 的費用一定花；失敗的部分再加大 model 的費用。難題的失敗率高，等於跑兩次。

    參考觀點與追問
    • 選「失敗才升級」：先用小 model，測試沒過再換大 model。不需要訓練 router。
    • 每類的期望成本：簡單 0.02 + 0.05 × 0.10 = $0.025；中等 0.02 + 0.40 × 0.10 = $0.06；困難 0.02 + 0.80 × 0.10 = $0.10。加權：0.7 × 0.025 + 0.25 × 0.06 + 0.05 × 0.10 = $0.0375。每天約 $37.5；全部用大 model 是 $100，省 62.5%。
    • 困難任務沒有省到：$0.10 對 $0.10，而且 80% 跑兩次，latency 變長。失敗率超過 80% 的類別，直接用大 model 更好。Break-even 的失敗率是 0.08 ÷ 0.10 = 80%。
    • 反向成本：verifier 不完整時，錯誤解會通過；小 model 的壞計畫會多出很多步（p.26）；換 model 後 KV cache 不能共用，要重新 prefill。
    • 量淨效果：同一組任務上比較每個解出任務的花費、通過率、p95 時間。只看費用會漏掉通過率下降。

    追問：把 verifier 換成「model 自己說完成了」，策略還成立嗎？L6 的 unverified success 會怎麼影響期望成本？

  4. 團隊實務 · 預算上限與停止規則 · p.27、p.42

    從 trace 資料替每個任務訂出預算上限與停止規則。誰負責調整？多久看一次？

    情境：你們的 agent 上個月跑了 240 個任務，200 個成功。成功任務的花費 p50 $1.20、p95 $4.80；model call 數 p95 是 40 次；tool 時間 p95 是 7.5 分鐘。40 個失敗任務平均花 $7.30，多數在第 20 步之後重複同一個錯誤 3 次以上。

    回答時請涵蓋
    • 用 slide 的規則訂出四個上限（金額、model call、tool 時間、每步重試），寫出數字。
    • 寫出至少三條停止條件，說明停下時交出什麼。
    • 說明誰擁有這份設定、用什麼資料、多久檢視一次。
    思考方向

    Slide 的規則是成功任務 p95 的 2 倍。失敗任務的模式告訴你停止條件該怎麼寫：同一個錯誤重複幾次、幾步沒有新進展。停止不等於放棄，要交出摘要讓人接手。

    參考觀點與追問
    • 上限：金額 2 × $4.80 = $9.60，取 $10；model call 2 × 40 = 80 次；tool 時間 2 × 7.5 = 15 分鐘；每步重試 2 次。這正好是 p.27 的示意值。
    • 停止條件：verifier 通過；10 步內沒有新的測試通過；同一個錯誤重複 3 次；碰到任一上限。停下時交出摘要：做了什麼、卡在哪裡、建議下一步。
    • 效果估算：40 個失敗任務共 $292，佔總支出 $912 的 32%。在第 20 步左右停下，每個失敗任務約省一半，每月約省 $150。
    • 擁有者：維護這個 agent 的團隊，設定放進版本控制。每個 sprint 用新的 trace 重算 p95；model 換版時也要重算。第 6 段示範怎麼把每次 run 的花費記進 trace。

    追問：上限設太低與設太高，各會在哪個指標上看到？你會先量什麼，才知道該往哪個方向調？

  5. 風險 · Speculative action 的取捨 · p.32、p.35、p.37

    哪些動作可以先猜先做？估算 speculation 能省多少時間，再和另一個加速手段比較。

    情境：主 model 每一步平均思考 8 秒才發出 tool call。Tool 的組成與耗時：50% 讀檔或搜尋（1 秒）、20% 跑測試（90 秒）、10% 抓網頁（3 秒）、15% 寫檔（1 秒）、5% 寄通知（1 秒）。便宜的 model 能提前猜中 60% 的下一個 tool call。

    回答時請涵蓋
    • 把五種動作分成「可以 speculate」與「不行」，說明判斷標準（副作用、可否撤銷、是否 idempotent）。
    • 估算 speculation 平均每一步省幾秒，佔一步總時間的比例。
    • 比較另一個手段：把測試時間減半。哪個省得多？你會怎麼量淨效果？
    思考方向

    一步的時間是思考加 tool。Speculation 只能把 tool 的執行和思考重疊，所以每次猜中最多省下兩者中較短的那段。先算一步的平均時間，再算期望節省。再想 p.26：猜錯的 call 浪費 token，還和主流程搶 tool。

    參考觀點與追問
    • 可以 speculate：讀檔、搜尋、抓網頁（唯讀、可丟棄）。抓網頁要小心，有些網址有副作用。不行：寫檔（會改狀態，猜錯要還原）、寄通知（不可撤銷）。Idempotent 的寫入可以考慮，但要有 CAS 或快照保護（p.55、p.56）。
    • 一步的平均時間：8 + 0.5 × 1 + 0.2 × 90 + 0.1 × 3 + 0.15 × 1 + 0.05 × 1 = 27 秒。測試佔 18 秒。
    • Speculation 對讀檔與測試：猜中時各省 1 秒（讀檔只要 1 秒）與 8 秒（測試比思考長）。期望節省 0.5 × 0.6 × 1 + 0.2 × 0.6 × 8 = 1.26 秒，約一步的 4.7%。
    • 測試時間減半省 0.2 × 45 = 9 秒，約 33%。這是 p.35 的重點：tool 常比 model 慢，先量 tool 時間。
    • Speculation 的反向成本：每步約 0.7 × 0.4 = 0.28 次白跑的 call，多付 token；猜錯的測試還會佔住 CPU。淨效果要在同一組任務上量 p50、p95 完成時間與總花費。

    追問：主 model 的思考時間變成 30 秒（例如 high effort）時，speculation 的價值怎麼變？什麼時候反而該減少思考？

  6. 應用 · 替團隊選 harness 架構 · p.44–51

    你們團隊要在半年內做出三個 agent。該用 monolithic、modular 還是 microkernel？給出路線與理由。

    情境：8 位工程師。三個 agent：PR review bot、工單分流、資料 pipeline 修復。三者都要跑程式，都要查共用的知識庫。資安要求：執行必須隔離在 container 裡。第一個 agent 要在 6 週內上線。

    回答時請涵蓋
    • 為「第 6 週」與「第 6 個月」各選一種架構，說明邊界放在哪裡。
    • 列出要先共用的元件，以及用什麼介面或協定。
    • 指出你選的架構的反向成本（通訊、故障模式、除錯），以及怎麼緩解。
    思考方向

    對照 p.51 的表：單一 agent 用 monolithic，multi-agent 基礎設施用 microkernel。三個 agent 共用 sandbox 與知識庫，但第一個 agent 時程緊。想想哪些邊界可以先用介面，之後再換成服務。

    參考觀點與追問
    • 第 6 週：modular。一個 controller，SandboxProvider 與 MemoryProvider 用介面隔開。Sandbox 從第一天就用 container 實作。不選 microkernel：時程不夠，只有一個 agent 也用不到獨立擴展。
    • 第 6 個月：把 sandbox 與知識庫抽成三個 agent 共用的外部服務，核心縮小成狀態、排程、安全。這是 microkernel 的方向。介面先定好，之後換成協定時不用大改。
    • 先共用的元件：執行服務（配置 container、timeout、回收）、知識庫的檢索、tool 定義。Tool 用 MCP 這類標準協定（L2）。Memory 介面要有版本，避免互相蓋掉。
    • 反向成本：每次 tool call 多一段網路來回（p.47）；共用服務掛掉時三個 agent 一起受影響；log 散在多個服務。緩解：tool 與 model 放在一起（p.34）、每個 request 帶 trace id。

    追問：資安要求改成「所有 agent 共用一份稽核 log」時，架構會怎麼變？哪一種架構最容易做到？

自我檢查

一個 session 有 20 個 turn，每個 turn 新增 10K token。總共送出多少 input token？拆成 2 個各 10 turn 的 session 呢？

一個 session：1 到 20 的和是 210，所以 10K × 210 = 2.1M。兩個 session：2 × 10K × 55 = 1.1M，約一半。每個 session 的 turn 數減半，成本降到約四分之一；兩個加起來是一半。

一步有 400K cache read、2K fresh input、2K output。用 1 : 10 : 50 算，哪一項最貴？該先優化什麼？

以 input token 為單位：cache read 400K，fresh 20K，output 100K。Cache read 最貴，所以先縮小 context（p.17），再縮短 output。

plan 5 秒、worker A 20 秒、worker B 30 秒、merge 5 秒，A 與 B 平行。把 A 加速一倍，或把 B 縮短 10 秒，總時間各變多少？

原本 40 秒，critical path 是 plan → B → merge。A 加速一倍：仍是 40 秒，A 不在 critical path 上。B 縮短 10 秒：A 與 B 都是 20 秒，總時間 30 秒。

6 · 動手試試

照著做一次

價格與 Claude Code 的設定依 2026 年 10 月的官方文件。

寫一個 session 成本計算器p.8、p.16

用第 5 段 Q2 的模型：固定 prefix、每步新增的 fresh input、每步的 output。改參數就能回答「turn 加倍會怎樣」。

輸出：40 [0.94, 0.36, 0.3] 1.6 與 80 [3.32, 0.72, 0.6] 4.64。把 prefix_k 改成 100，看 cache read 的比例怎麼變。

替每個任務設上限，並把結果記進 tracep.27、p.42

先把上限寫成設定檔。欄位名稱自訂，重點是四個上限與停止條件都有數字，而且來自 trace。

Claude Code 的 print mode 有兩個對應的 flag。--max-turns 算 tool-use 的來回，接近本堂的 step。--max-budget-usd 用本機估算的花費，可能略超過上限，要留餘裕。

claude -p --max-budget-usd 10 --max-turns 80 --output-format json \
  "修好 tests/test_auth.py 失敗的測試。回報前跑 pytest -x tests/。" \
  | jq '{subtype, total_cost_usd, num_turns, session_id}' >> trace.jsonl

subtype 是 success、error_max_turns 或 error_max_budget_usd。每次 run 追加一行，一個月後就能重算 p95，決定上限要不要調。

要求精簡的結構化輸出p.19–20

三層控制 output：prompt 講清楚、schema 限制欄位、API 的上限當保險。

Claude Code 的 print mode 可以用 --json-schema 直接給 schema。輸出放在 JSON 結果的 structured_output 欄位，不會夾雜說明文字。

查找類的工作另外開一個便宜的 subagent：低 effort、唯讀 tool、精簡輸出。

直接呼叫 API 時，max_tokens 包含 thinking 與回覆。撞到上限時 stop_reason 是 max_tokens，程式要檢查它。

Assignment 3 概觀：三個指標就是本堂主題8_assignment3.pdf

Assignment 3（MadsOpt）是一場 harness 競賽：26 個任務，分屬 3 種 container。評估離線，只連得到 api.cs2680.com。流程：dispatcher 把任務交給 agent → agent 產生 patch → 評估結果回到 agent，最多 5 個任務同時跑。有三種 model：Expert、Standard、Starter。

限制：每次 evaluate() 最多 35 分鐘，總共 4 小時；每天 $30，每次 run $10。26 個任務平均每題只有約 $0.38。三個指標：解出的任務數、每個解出任務的花費、每個解出任務的時間。花在沒解出任務上的錢與時間也會拉高後兩項，所以卡住的任務要早停（p.27）。

評分：leaderboard 80 分、writeup 10 分、影片 10 分。名次 r 決定分數：任一次提交達到 baseline（16 題），得 max(81 − r, 50)；否則 81 − r。最低要求解出 7 題。先穩定解出 16 題，等於保住 50 分。只上傳 src.zip；dispatcher 與評分腳本不要改。
