1 · 架構

多個 agent 怎麼分工：誰協調，context 隔離在哪裡

看這張圖，先找藍框：誰持有計畫。從 A 到 D，計畫依序放在你腦中、主 agent、lead 與共用清單、script 裡。每個 worker 都有自己的 context；差別在結果怎麼交回，以及交回給誰。E 是 slide 的第三個軸：時間，由停止條件決定 agent 什麼時候結束。

2 · 核心觀念

五個觀念串起整堂課

Model 不變，換一套 workflow，結果就不同 p.6–15

Superpowers 沒有換 model，也沒有加新的 tool。它用 9 個 skill 把開發拆成階段：釐清需求、核准設計、寫計畫、測試驅動實作、review、收尾。每個 skill 寫明人工核准的關卡，以及下一個要載入的 skill p.10–11。流程就這樣自己往下接，agent 先問清楚再動手。

只有 skill 還不夠。Model 依 description 自己決定要不要載入 skill，它可能沒查就直接寫 code。所以 Superpowers 加了 SessionStart hook：每個 session 開始時，把「怎麼選 skill」的規則放進 context p.12。Matcher 包含 startup|clear|compact，所以 /clear 和 compaction 之後，規則會再放入一次。

這延續 L2 的分工。Hook 保證規則一定在 context 裡；要載入哪個 skill，仍由 model 判斷。確定的部分交給程式，需要判斷的部分留給 model。

Token 要雙向壓縮，輸入方向只有 proxy 管得到 p.16–27

Log、diff、tool 輸出會塞滿 context。每一圈 loop 都重送整個 context，所以一份 786 行的測試 log，之後每一圈都要再付一次 p.17。Caveman 從兩個方向壓縮：response skill 讓 model 寫得短，本機 proxy 讓 model 讀得少。

輸出方向容易做。Skill 規定保留指令、路徑、數字和否定詞，刪掉客套與贅字；slide 的數字是 output token 少 65% p.18。輸入的量更大：C compiler 案例的 input token，約是 output 的 14 倍。

輸入方向要改寫每一個送給 model 的 request。Hook 只能改單一 tool 的輸入或輸出；MCP 只在 agent 呼叫時執行，也改不了 context p.26。Proxy 位在 agent 和 model provider 之間，每個 request 都經過它。原文也沒有丟掉，agent 需要細節時，用 MCP 的 caveman_retrieve 取回。

三個擴展軸，各買到一樣東西，也各有代價 p.28–47

Slide 把擴展分成三個軸 p.29。第一個是平行：每個任務一個 session，各在自己的 git worktree。它買到 throughput，答案不會更好，每件事仍是一個 agent 的水準。Worktree 只隔離檔案；port、資料庫和最後的 merge，仍要你處理。

第二個是 subagent：子任務在新的 context window 執行，只交回摘要。搜尋結果和 log 留在 subagent，主對話只多一段摘要 p.33。代價是摘要會丟細節，subagent 也要從零收集 context。所以需要頻繁來回討論的工作，slide 建議留在主對話 p.40。

Agent team 和 workflow 組合這些軸。Team 的 teammate 可以直接互傳訊息；每個 teammate 都是完整的 Claude Code session，token 用量隨人數線性成長 p.44。Workflow 讓 script 持有計畫，中間結果存在 script 變數，不進主 context p.47。選擇規則：只要結果，用 subagent；需要討論，才用 team；agent 多到對話協調不了，就用 workflow。

長時間執行的 agent，需要一個能檢查的終點 p.48–53

第三個軸是時間：讓一個 agent 做更久。/goal 給一個條件，Claude 一直做到條件成立。每一輪結束，另一個小而快的 model 讀對話，判斷條件是否成立。做事的 model 不能自己宣布完成。

所以條件要能從對話裡證明。「npm run lint exits with zero errors」可以檢查，因為 lint 的輸出就在對話裡。「refactor the code」無法檢查，因為沒有一個輸出能證明重構完成。/loop 用時間觸發：依固定間隔重跑同一個 prompt，直到你取消，或 7 天後過期 p.49。

C compiler 案例是更長的版本：16 個 agent、約 2,000 個 session、約兩週 p.51。每個新 session 先讀進度文件找回 context，再用自動化測試判斷進度 p.52。狀態放在檔案和測試裡，不靠 model 記住。

Programming 3.0：接受不確定性，讓周邊系統可靠 p.62–70

講者的 Programming 3.0 指：人用自然語言說目標，agent 寫程式碼 p.63。每一代都在人和硬體之間多加一層；產能變高，不確定性也變高。Compiler 是確定的，agent 不是。

Slide 指出，不確定性早就存在 p.66。硬體差異、並行、相依套件漂移，都會讓同一份原始碼產生不同結果。2.0 的對策可以沿用：固定介面、讓操作可重複、測試。

新的不確定性集中在產生程式的階段：自然語言、檢索、model 生成、agent 與 tool 的迴圈 p.68。程式產生後，經過 commit、review、測試，執行時通常是確定的。所以結論原則是：讓 agent 周圍的系統可靠，自主程度配合風險 p.70。前面的 hook、可驗證的終點、測試，都是這個系統的零件。

3 · 觀念補充

Slide 預設你已經懂的背景

Git worktree一個 repo，同時開好幾個工作目錄

一般的 repo 只有一個工作目錄，一次只能 checkout 一個 branch。git worktree add 再開一個目錄，掛在另一個 branch 上；所有目錄共用同一個 .git，歷史和 objects 只有一份。

限制有兩個。同一個 branch 不能同時在兩個 worktree checkout；新目錄裡也沒有 .env、node_modules 這類不在 git 裡的檔案 p.30–31。

Context 隔離與摘要subagent 為什麼能保護主對話

每個 subagent 有自己的 context window。它讀的檔案、跑出的 log，都留在自己的 context；主對話只收到最後的報告。這是有損壓縮：30 份文件換成一頁結論。

有損就會漏掉資訊，所以委派時要指定回報格式，例如「每個問題附 file：line」。每多一層巢狀，結果就再摘要一次，所以 slide 建議 2 到 3 層 p.36。

Lock file 認領沒有 manager，怎麼避免重複做同一件事

C compiler 案例用檔案當鎖。Agent 在 current_tasks/ 寫一個檔案，commit 再 push，就算認領 p.53。兩個 agent 同時認領時，git 拒絕後到的 push；後到的 agent pull 之後看到鎖，就改挑別的任務。

這是樂觀鎖（optimistic locking）：先做，衝突時才處理。Lock file 常見的弱點是 stale lock：agent 中途當掉，鎖就一直留著，所以鎖要能過期，或有人定期清理。

可驗證的完成條件/goal 為什麼需要它

可驗證的條件，要能用一個檢查回答「是」或「否」：exit code、測試數量、檔案是否存在。/goal 的檢查 model 不跑指令，也不讀檔案，只讀對話；所以證據必須出現在 Claude 的輸出裡 p.48。

「所有測試通過」可以靠刪掉失敗的測試達成。所以要加不變量（invariant），例如「不修改 tests/」。這是 Goodhart's law：指標一旦變成目標，就不再是好指標。

Software 1.0 / 2.0 / 3.0兩種分法，不要混在一起

Karpathy 用「程式是什麼」分世代：1.0 是原始碼，2.0 是神經網路權重，3.0 是用自然語言寫的 prompt p.64。講者的 Programming 3.0 用「人寫什麼」分：人說目標，agent 寫原始碼 p.63。

兩種分法導向同一個工程問題：哪一塊用確定的程式，哪一塊交給 model。例如 Caveman 的壓縮 engine 是 1.0 的程式；回答風格寫在 skill 裡，屬於 3.0。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

協調開銷決定平行加速的上限

16 個 agent 不會快 16 倍。規劃、整合、review 這些工作，只能一件一件做。依 Amdahl's law，只有 80% 的工作能平行時，16 個 agent 最多快 1 ÷（0.2 ＋ 0.8 ÷ 16）＝ 4 倍。Agent 再多，也不會超過 5 倍。

協調成本還會隨人數變大。C compiler 案例的 merge conflict 很常見 p.61；agent team 的 token 隨人數線性成長。L5 會把它寫成估算式：總時間約等於規劃、critical path、溝通、合併四項相加，而平行只能縮短 critical path。

人的角色，變成規劃者和 reviewer

Slide 的實務證據指向同一件事：人從執行者，變成委派、監看、review、整合的人 p.72–74。Agent 寫得更快，review 的速度沒有跟著變快。5 個 agent 每小時各交一個 PR，你一小時 review 得完 5 個嗎？

瓶頸因此移到兩端：前端是把任務寫清楚，後端是驗證結果。這正好對應 p.69 的「先定義、最後驗證」。可驗證的終點和自動化測試讓 review 變便宜；它們決定一個人能同時管幾個 agent。

任務切不開，加 agent 也沒用

C compiler 案例有一頁在講失敗 p.61。編譯 Linux kernel 時，所有 agent 都卡在同一個錯誤。原文寫道：每個 agent 都修同一個 bug，再互相覆蓋彼此的修改。

原文的解法，是把一個大的失敗訊號切成很多小訊號。作者用 GCC 當已知正確的 oracle：隨機挑大部分檔案用 GCC 編譯，其餘檔案才用 agent 寫的 compiler。Kernel 能跑，問題就不在那些檔案；壞了，就再縮小範圍。每個 agent 因此拿到不同的失敗檔案，可以平行修不同的 bug。

一般原則：平行需要獨立的子任務，也需要獨立的進度訊號。只有一個大測試失敗時，先把它拆成很多小訊號，再考慮加 agent。

讀 Codex 與 OpenAI 的數字要小心

p.71–79 的數字來自 OpenAI 自己的報告。OpenAI 員工幾乎全部在用 Codex；個人使用者不到 1%，組織使用者是 17.3% p.72。員工是開發這個工具的人，工作內容、熟練度和使用條件，都和一般團隊不同。

「agent-hours」量的是 agent 跑了多久，它沒有量交付的價值。任務大小用「人要做幾小時」估算，這個估算本身就有誤差 p.73。讀這類數字時，問三個問題：樣本是誰、指標量什麼、和什麼比較。L7 講 agent 評估時，也會討論成功率以外該量哪些指標。

只複製題目與頁碼，方便貼到群組。

  1. p.7–12 · Superpowers

    同一個 model，Superpowers 的流程和預設流程差在哪裡？裝好 skill 之後，為什麼還要 SessionStart hook？它在哪三個時機執行？

    參考答案

    預設流程是收到需求就寫 code，出錯再改。Superpowers 走六個階段：釐清問題、核准設計、寫計畫、測試驅動實作、review 與驗證、收尾，分成 PLAN、BUILD、SHIP 三組（p.7）。

    Skill 只是可用，model 依 description 自己決定要不要載入，可能沒查就開始寫 code。Hook 在每個 session 開始時把「怎麼選 skill」的規則放進 context。Matcher 是 startup|clear|compact：新 session、/clear 之後、compaction 之後各執行一次（p.12）。

  2. p.17–26 · Caveman 的雙向壓縮

    Caveman 從哪兩個方向壓縮 token，各靠什麼零件？壓縮輸入為什麼要用本機 proxy，不用 hook？壓掉的原文怎麼拿回來？

    參考答案

    輸出方向靠 response skill，讓 model 寫得短；slide 的數字是 output token 少 65%（p.18）。輸入方向靠本機 proxy，壓縮 log、diff、tool 結果；p.17 的例子把 786 行的 npm test 輸出壓成 1 行。

    壓縮要套用到送給 model 的每一個 request，而 hook 不能透明地改寫 LLM request。Proxy 位在 coding agent 和 model provider 之間，每個 request 都經過它（p.26）。原文沒有丟掉：MCP 的 caveman_retrieve 用 recovery handle 取回一字不差的原文（p.25）。

  3. p.29–32 · 三個擴展軸

    擴展有哪三個軸，各買到什麼？Slide 為什麼說平行「答案不會更好」？手動平行到幾個 session 就撐不住，會卡在哪四個問題？

    參考答案

    廣度（平行的 session）買到 throughput；廣度加深度（subagent）買到 throughput 與專注；時間（長時間執行）買到更大的範圍、更少人工介入（p.29）。3 個 session 做 3 件事，總時間接近 1 件，但每件事仍是一個 agent 的水準。

    每個 session 在自己的 git worktree，共用一個 .git，各有目錄與 branch（p.30–31）。開 3 個 session 還記得住，開 20 個就不行（p.32）：計畫只在你腦中、session 之間看不到彼此、你要自己整合 branch、過程沒有記錄無法重跑。

  4. p.33–36 · Subagent

    Subagent 最大的好處是什麼？三個內建的 subagent 叫什麼？定義一個 subagent 的檔案裡，哪兩個欄位必填？巢狀最多幾層，幾層最好？

    參考答案

    雜訊留在 subagent 的 context，主對話只收到摘要（p.33）。其他好處：限制 tool 與 model、重用、平行（2、3、5 分鐘的工作約 5 分鐘跑完）、便宜的 model 做簡單的事。內建三個：Explore、Plan、general-purpose（p.34）。

    一個 subagent 是一個 Markdown 檔：frontmatter 的 name 與 description 必填，tools 與 model 可選；body 是它的 system prompt（p.35）。Tools 裡要有 Agent 才能再開子 subagent；slide 寫最多 5 層，2 到 3 層最好（p.36）。

  5. p.40–47 · Subagent、team、workflow

    哪些工作該留在主對話？Subagent 和 agent team 的溝通方式差在哪裡，哪一個 token 成本高？Dynamic workflow 和前兩者最關鍵的差別是什麼？

    參考答案

    留在主對話：要頻繁來回討論、幾個階段共用大量 context、快速小修改、在意延遲（p.40）。Subagent 只回報給呼叫者，是星狀；team 的 teammate 從共用 task list 認領任務，也透過 mailbox 互傳，是網狀（p.42–43）。

    Team 的 token 成本較高，因為每個 teammate 都是完整的 Claude instance；只要結果用 subagent，需要討論才用 team（p.44）。Workflow 是一段 script，由 script 持有計畫，中間結果存在變數裡，不進 Claude 的 context（p.47）。

  6. p.48–50 · /goal 與 /loop

    /goal 什麼時候停，由誰判斷？Slide 說什麼樣的條件好、什麼樣的不好？/loop 什麼時候停？它和 /goal 一句話的差別是什麼？

    參考答案

    /goal 給一個可以驗證的終點，Claude 一直做到條件成立；每一輪結束，由另一個小 model 檢查條件，不由做事的 model 自己判斷。好的條件：「all integration tests pass」。壞的條件：「refactor the code」，因為無法驗證（p.48）。

    /loop 依固定間隔重跑同一個 prompt，例如 /loop 5m "check CI, fix whatever broke"，直到你停止它（p.49）。一句話：/goal 在條件成立時停；/loop 在你叫它停時停（p.50）。

  7. p.51–53、p.61 · C compiler 案例

    C compiler 案例用了幾個 session、多少 token、花多少錢？沒有 manager agent，16 個 agent 靠什麼協調？什麼情況下平行就沒用了？

    參考答案

    約 2,000 個 session、約兩週；input 2B、output 140M token；API 成本不到 $20,000；約 100,000 行程式碼，能編譯 Linux 6.9（p.51）。

    協調只靠 container、git 與文字檔。每個 agent 在 current_tasks/ 建一個 lock file 認領任務；做完先 pull、再 push、最後刪掉 lock file（p.52–53）。所有 agent 卡在同一個 kernel 錯誤時，平行不再有幫助；merge conflict 也很常見（p.61）。

  8. p.63–70 · Programming 3.0

    講者的 Programming 3.0 和前兩代差在哪一層？代價是什麼？不確定性有哪四個來源？結論的那句原則怎麼說？

    參考答案

    每一代都在人與硬體之間多加一層：1.0 寫機器指令，2.0 寫程式語言交給 compiler，3.0 用自然語言說目標交給 agent（p.63）。代價是產能更高，不確定性也更高；compiler 是確定的，agent 不是。

    四個來源：自然語言、檢索、model 生成、agent 與 tool 的迴圈；程式一旦產生，通常是確定的（p.68）。原則：不要期待 agent 是確定的，要讓 agent 周圍的系統可靠；自主程度配合風險（p.70）。

  9. p.72–74 · 實務證據

    從對話式 AI 到 agentic AI，人的角色怎麼變？半年內，8 小時以上的委派任務占比從多少升到多少？同時跑 5 個以上 agent 的使用者有多少？

    參考答案

    對話式 AI 裡人自己做事；agentic AI 裡人委派任務，agent 規劃、用 tool、交出成果，人負責 review 與整合（p.72）。

    8 人時以上的任務從 2.1% 升到 25.6%，約 12 倍；1 人時以上從 35.4% 升到 70.2%（p.73）。2026 年 6 月，28.6% 的使用者一週內曾同時跑 5 個以上的 agent；員工中位數每天約 2.5 agent-hours，第 99 百分位約 71（p.74）。

這 6 題可以在讀書會前先發給大家回答。每題附情境、回答要點與相關 slide。「參考觀點與追問」給主持人用，建議討論後再展開。

只複製題目、情境與回答要點，方便貼到群組。

  1. 概念 · Skill 與 hook 的分工 · p.7–15

    Superpowers 沒有換 model，為什麼 agent 的行為會從「直接寫 code」變成「先問清楚再動手」？只裝 skill 為什麼不夠，一定要加 SessionStart hook？

    情境：你的團隊寫了 5 個流程 skill，放進 .claude/skills/。兩週後你發現，agent 大約一半的任務沒有用到任何 skill，直接開始改程式。

    回答時請涵蓋
    • 說明 model 怎麼決定要不要載入一個 skill，以及這個決定為什麼會失敗。
    • 指出 hook 保證了什麼、沒有保證什麼（用 p.12 的 matcher startup|clear|compact 說明）。
    • 提出至少兩個 hook 以外的做法，讓 skill 更常用到，並說明各自的限制。
    思考方向

    先回到 L2 的 loop：model 只看得到 context 裡的東西。Skill 的 description 在 context 裡，SKILL.md 的全文不在。Model 看 description 判斷「要不要載入」，這是機率性的決定。

    再想 hook 的位置：它在 model 動作前執行，每個 session 都執行。它能保證「規則在 context 裡」，不能保證「model 照規則做」。

    參考觀點與追問
    • 行為改變的來源是 context，不是 model。Superpowers 把流程寫成 skill，每個 skill 寫明關卡與下一個 skill（p.10–11）。Model 讀到這些程序，就照程序走。
    • 只裝 skill 的問題：載入與否由 model 依 description 判斷。任務看起來簡單時，model 常跳過查 skill，直接動手（p.12）。這就是情境裡「一半任務沒用到」的原因。
    • Hook 補的是確定性。SessionStart 在 session 開始時執行；matcher 含 clear 與 compact，所以 /clear 與 compaction 後規則會再放一次。它保證規則一定在 context 裡；要載入哪個 skill，仍由 model 判斷（p.14）。
    • Hook 以外的做法：把「先讀 using-superpowers」寫進 CLAUDE.md（每次載入，但 compaction 後可能摘要掉）；把 skill 做成 /名稱 由人手動叫用（確定，但要靠人記得）；用 UserPromptSubmit hook 在每個 prompt 後附上提醒（確定，但每輪多花 token）。
    • 衡量方式：記錄一週內有多少任務載入了流程 skill。只有數字能證明 hook 有效，這是 L7 評估的觀念。

    追問：如果 model 讀了規則，仍決定不載入 skill，你要不要用 hook 強制擋下它的第一次 Edit？這樣做的代價是什麼？

  2. 估算 · Subagent 省下的 context 與成本 · p.33–40

    一次大型程式碼搜尋的結果，直接放進主對話，和交給 subagent 處理，兩者的 token 用量差多少？算出數字，再說明 token 以外的差別。

    情境：主對話目前 60k token，context window 200k。你要搜尋一個 pattern 在整個 repo 的用法，結果約 80k token。這之後對話還會進行 30 輪。Subagent 版本：subagent 用 4 輪讀完結果，交回 2k 的摘要。價格用 Opus 4.6 的定價：base input $5/MTok，cache hit $0.50，cache write $6.25。

    回答時請涵蓋
    • 算出兩種做法在之後 30 輪多送的 input token，以及 subagent 自己花掉的 token。
    • 算出兩種做法的費用，並說明 prefix cache 怎麼影響這個比較。
    • 指出 subagent 版本會丟掉什麼，以及你怎麼在委派時減少損失。
    思考方向

    每一輪都重送整個 context（L2 p.11）。放進主對話的 80k，之後 30 輪每輪都再送一次。Subagent 的 context 在它結束時就丟掉，主對話只多 2k。

    Cache 讓重送變便宜，但不會變成免費。另外看 context window：60k 加 80k 是 140k，離 200k 還剩多少？

    參考觀點與追問
    • 直接放進主對話：之後 30 輪多送 80k × 30 ＝ 2.4M input token。費用約 80k × $6.25 ＋ 2.4M × $0.50 ＝ $0.50 ＋ $1.20 ＝ $1.70（第一次寫入 cache，之後都是 cache hit）。
    • Subagent 版本：4 輪的 context 約 20k、100k、102k、104k，合計 326k input，其中約 104k 是新 token，222k 是 cache hit。費用約 104k × $6.25 ＋ 222k × $0.50 ≈ $0.76。摘要 2k × 30 輪 ＝ 60k，約 $0.03。合計約 $0.79，token 合計約 386k。
    • 比較：token 少約 6 倍（2.48M 對 0.39M），費用省約 $0.91。沒有 cache 時差距更大：2.4M × $5 ＝ $12。L8 會講 cache 怎麼改變這類計算。
    • Token 以外的差別更重要。直接放進去後，主對話是 140k，佔 window 70%。再過幾輪就要 compaction，compaction 會丟細節，而且丟哪些你無法控制（L4 會講 context 管理）。
    • Subagent 的代價：摘要是有損壓縮，subagent 也沒有對話歷史。減少損失有三個做法。在任務訊息寫明回報格式，例如每個命中附 file:line。把相關規則寫進任務訊息，因為 Explore 不讀 CLAUDE.md（p.34）。要求回傳「沒找到什麼」，不只回傳「找到什麼」。

    追問：如果這次搜尋的結果，後面 30 輪裡有 10 輪要逐行引用，哪一種做法比較好？為什麼 slide 說「要頻繁來回討論的工作留在主對話」（p.40）？

  3. 設計 · 替任務選擴展方式 · p.28–50

    下面四個任務，各該用手動平行、subagent、agent team、workflow，還是 /goal？替每一個選一種做法，說明理由，並指出你放棄的選項為什麼不適合。

    情境：（a）把 300 個檔案從 library A 換成 library B，每個檔案的改法相同、彼此獨立。（b）Review 一個大 PR，要從安全、效能、測試覆蓋三個角度看，而且三方的發現要互相挑戰。（c）追一個 flaky test，你要一邊看 log 一邊和 agent 討論假設。（d）一直修到 npm run lint 零錯誤，但不能動 tests/ 底下的檔案。

    回答時請涵蓋
    • 每個任務選一種做法，並用「誰持有計畫」「結果交給誰」「要不要討論」三個問題說明理由。
    • 比較 （a） 用 subagent 和用 workflow 的差別：300 個結果各進哪裡？
    • 替 （d） 寫出完整的 /goal 條件，包含檢查方法、限制條件和停止條款。
    思考方向

    用 p.50 的表：/goal 做到可驗證的終點；subagent 的結果回到 Claude；team 的成員互相傳訊；workflow 由 script 持有計畫。再用 p.40 的表判斷：要來回討論的工作，留在主對話。

    （a） 的關鍵是數量。300 個子任務的結果，如果都回到主對話，主對話會發生什麼事？

    參考觀點與追問
    • （a） Workflow。300 個獨立、做法相同的檔案，計畫可以寫成 script；每個檔案一個 subagent，中間結果存在 script 變數，不進主 context（p.47）。用 subagent 也能做，但 300 份摘要都回到主對話，主對話會撐爆或頻繁 compaction。Agent team 不適合：沒有需要討論的事，token 卻隨人數成長。
    • （b） Agent team。題目要求三方互相挑戰，這需要 teammate 之間傳訊（p.41–43）。只要三份獨立報告的話，3 個 subagent 平行就夠，而且便宜（p.44）。從 3 到 5 個 teammate 開始，官方文件也這樣建議。
    • （c） 主對話。要頻繁來回、幾個階段共用大量 context、在意延遲，三條都命中 p.40 左欄。Subagent 從零開始，每次都要重新收集 context。可以把「跑 100 次測試收集失敗 log」這類輸出很長的步驟交給 subagent，討論留在主對話。
    • （d） /goal。終點可驗證：lint 的輸出會出現在對話裡，評估 model 讀得到。條件範例：/goal npm run lint exits 0; no file under tests/ is modified (git status shows no changes there); or stop after 20 turns。限制條件擋住「刪測試讓 lint 過」這種捷徑；停止條款限制花費。
    • 共同原則：先問任務切不切得開（p.61）。切不開的任務，加 agent 只會多出重複的工作。（a） 切得開，（c） 切不開。
    • 手動平行適合的情境不在這四題裡：你同時有兩三個不相關的任務，各開一個 worktree（p.30）。超過 3 個，計畫只在你腦中就會出問題（p.32）。

    追問：（a） 的 300 個檔案裡，有 20 個會互相 import。Workflow 要怎麼改？只用 Amdahl's law 估：如果 20% 的工作必須循序做，16 個 agent 最多快幾倍？（答：1 ÷（0.2 ＋ 0.8 ÷ 16）＝ 4 倍。）

  4. 團隊實務 · 讓多個 agent 過夜跑 backlog · p.51–61

    參考 C compiler 案例的做法，設計一套讓 4 個 agent 無人看管地處理 issue backlog 的協調方式。只能用 git、檔案和測試，不能有 manager agent。

    情境：Backlog 有 40 個標了 agent-ok 的 issue，大多是小修正。4 個 agent 各在自己的 container，共用一個 remote repo。晚上 10 點開始，早上 6 點前要有結果。每個 issue 都有至少一個對應的測試。

    回答時請涵蓋
    • 說明 agent 怎麼認領 issue、兩個 agent 同時認領時怎麼處理、agent 中途當掉時鎖怎麼辦。
    • 列出每個 agent 開始一個 session 時要讀什麼、結束時要寫什麼，以及為什麼。
    • 說明你怎麼在早上 6 點判斷哪些 issue 真的完成了，哪些只是 agent 宣稱完成。
    思考方向

    p.53 的四步迴圈：讀 repo → 認領 → 實作並測試 → merge、push、解鎖。Git 拒絕後到的 push，這就是鎖。再想 L2 的 memory 觀念：狀態放在檔案，不放在 model。

    「宣稱完成」和「完成」的差別，要靠一個 agent 改不了的訊號。測試是候選，但 agent 能改測試。

    參考觀點與追問
    • 認領：在 current_tasks/ 寫一個以 issue 編號命名的檔案，內容是 agent 名稱和時間，commit 後 push（p.53）。兩個 agent 同時認領時，remote 已有新 commit，git 拒絕後到的 push；它 pull 之後看到鎖，改挑別的 issue。這是樂觀鎖。
    • Stale lock：agent 當掉，鎖會留著。檔案裡寫時間，超過例如 90 分鐘就視為過期，其他 agent 可以接手。或者每個 session 結束時由 harness 清鎖，不靠 model 記得。
    • Session 開始時讀：PROGRESS.md（哪些 issue 完成、哪些卡住、為什麼）、該 issue 的描述、相關測試。結束時寫：這個 issue 的進度、沒解決的問題、下一步。C compiler 案例的每個 agent 都從空 container 開始，進度文件是它唯一的記憶（p.52）。
    • 進度訊號：每個 issue 的測試從紅變綠，整套測試仍然全綠。CI 跑在 merge 之後，agent 改不了 CI 的結果。另外加一條規則，用 hook 或 CI 檢查：不准修改 tests/ 裡既有的測試。
    • 早上的判斷：三類。CI 綠且 PR 已開的 issue 算完成，人只 review diff。有 lock 但沒有 PR 的，看 PROGRESS.md 的紀錄決定重跑或放棄。測試改過的，先當作失敗。
    • Merge conflict 會發生（p.61）。做法：每個 agent 在自己的 branch 工作，push 前先 rebase；衝突解不開就寫進 PROGRESS.md 留給人，不要硬解。40 個 issue 分 4 個 agent，每個 agent 約 10 個，平均每個 issue 不到 1 小時，所以要設每個 issue 的時間上限。

    追問：如果 40 個 issue 裡有 8 個改同一個模組，這套做法會出什麼問題？你會在認領階段還是 merge 階段處理？

  5. 風險與取捨 · 壓縮 model 讀到的內容 · p.17–27

    Caveman 用 proxy 壓縮 model 讀到的每一個 request。這能省多少，會冒什麼風險？什麼情況下值得，什麼情況下不值得？

    情境：你的團隊每個 agent session 平均 1M input token、70k output token（p.51 案例的平均）。有人提議裝一個壓縮 proxy，預估 input 少 40%。另一人提議只用 response skill，output 少 65%。價格：input $5/MTok，output $25/MTok。

    回答時請涵蓋
    • 分別算出兩個提議省下的 token 比例和費用比例。
    • 列出 proxy 壓縮至少三種可能造成的錯誤，每種配一個具體例子。
    • 說明你怎麼在上線前測出壓縮有沒有傷到 agent 的成功率。
    思考方向

    先算 token，再算錢。Output 單價是 input 的 5 倍，所以兩種算法的結論不同。再看 p.22 的保留清單：否定詞、數字、單位、路徑。想一想，壓縮 log 時刪掉其中一個會怎樣。

    Proxy 也是一個新的零件，位在 agent 和 model 之間。所有程式碼和 secret 都經過它。

    參考觀點與追問
    • Token：每個 session 1.07M。Output 少 65% 省 45.5k，占 4.3%。Input 少 40% 省 400k，占 37.4%。以 token 數看，輸入方向重要約 9 倍，這是 p.18 的論點。
    • 費用：每個 session 約 $5.00 input ＋ $1.75 output ＝ $6.75。Output 少 65% 省 $1.14（16.9%）；input 少 40% 省 $2.00（29.6%）。Output 單價高，所以 response skill 的效果比 token 數顯示的好。真實帳單還要算 cache：input 大多是 cache hit，單價更低，proxy 省的錢會再縮小。
    • 風險一，語意翻轉：log 裡的「not found」壓成「found」；保留清單才特別列出否定詞（p.22）。風險二，刪掉 debug 需要的細節：proxy 截掉 stack trace 的中段，agent 修錯層。Caveman 用 caveman_retrieve 取回原文補救（p.25），但 agent 要知道該取回。風險三，diff 的行號或 hunk 標頭改變，agent 改錯位置。
    • 風險四，多一個不確定來源：壓縮本身是程式（確定），但它改變了 model 的輸入，同一個任務的結果變得更難重現（p.68）。風險五，安全：proxy 讀得到所有原始碼、token、secret。自架的 proxy 要管好；第三方的 proxy 等於多一個供應商拿到你的程式碼。
    • 測法：固定一組任務（例如 30 個有測試的 issue），開壓縮和不開各跑幾次，比較成功率、步數、費用。只省錢但成功率掉，就不划算：失敗的 run 要重跑，重跑的 token 全是浪費。這是 L7 的評估方法，也是 L8「一次只改一件事」的原則。
    • 值得的情況：log、測試輸出、搜尋結果很長的工作，例如 CI 修復、大型 refactor。不值得的情況：需要逐字精確的工作，例如 security review、處理法規文件。

    追問：Slide 說 hook 改不了送給 model 的 request（p.26）。如果你自己寫 harness，壓縮該放在哪一層？和 proxy 比，各有什麼好處？

  6. 應用 · 把一個流程寫成 skill 鏈 · p.10–14、p.79

    挑一個你們團隊重複在做的流程，照 Superpowers 的方式，把它寫成 3 個串起來的 skill。寫出每個 skill 的名稱、進入條件、人工核准關卡、下一個 skill，以及一個可以驗證的終點。

    情境：例如「處理一張 bug ticket」：重現 → 找 root cause → 修正並加測試 → 開 PR。每個 skill 用 p.10 的格式寫 5 到 7 步。另外說明：這個流程在 p.79 的委派階梯上是第幾級，哪些步驟要留給人。

    回答時請涵蓋
    • 寫出 3 個 skill 的 frontmatter 與步驟，每個 skill 至少一個關卡或驗證要求。
    • 指出哪一步需要人核准、為什麼，以及這個核准在 Claude Code 裡怎麼發生。
    • 寫出流程結束時的可驗證條件，並說明它能不能用 /goal 檢查。
    思考方向

    p.11 的六種成分：name、description、instructions、checkpoints、references、scripts。流程型 skill 多寫三樣：進入條件、禁止動作、下一個 skill。

    關卡放在「做錯了很貴」的地方。重現錯 bug 只浪費時間；修錯地方會進 production。

    參考觀點與追問
    • 一種拆法：reproducing-bug（讀 ticket → 寫一個會失敗的測試 → 跑它確認失敗 → 關卡：把失敗輸出給人看 → 下一個 skill）；finding-root-cause（從失敗往回追 → 列出候選原因 → 用 log 或 debugger 排除 → 寫下結論與證據 → 關卡：人核准結論 → 下一個 skill）；fixing-and-shipping（最小修改 → 測試從紅變綠 → 跑整套測試 → 禁止修改既有測試 → 開 PR 附上證據）。
    • 人工核准放兩處：root cause 的結論，和 PR 的 merge。前者是因為修錯原因的成本最高；後者是因為 merge 無法輕易回退。核准在 Claude Code 裡的樣子：skill 寫「Wait for user approval」，agent 停下來問；或者用 permission 模式讓 Edit 需要你按確認。
    • 可驗證的終點：「新增的測試通過，整套測試通過，PR 已開，tests/ 既有檔案沒有改動」。這些都會出現在對話裡（測試輸出、gh pr create 的輸出、git status），所以 /goal 檢查得到。
    • 保證 skill 會用到：加 SessionStart hook 注入一條規則，例如「收到 ticket 連結，先載入 reproducing-bug」。Hook 保證規則在 context 裡；model 仍可能判斷錯，所以要量（Q1）。
    • 階梯位置：三個 skill 由一個 agent 依序執行，是第 3 級「agent」。重現和 root cause 交給 subagent 平行跑多個假設，就到第 4 級。整條鏈不用人介入也能跑完，才是第 5 級，但 merge 這一步多數團隊會留給人。
    • 通用原則：先寫人做這件事的 checklist，再把 checklist 拆成 skill。Skill 不是教 model 寫程式，是把團隊的流程知識放進 context。

    追問：這條 skill 鏈跑了 50 張 ticket 之後，你想知道哪一個 skill 最常出錯。要在哪裡記錄什麼，才答得出來？

自我檢查

你輸入 /goal refactor the auth module。為什麼這個條件不好？改成什麼？

評估 model 只讀對話，不跑指令。「refactor」沒有一個輸出能證明它完成。改成可量測的終點加檢查方法，例如「auth 模組每個檔案低於 300 行，npm test exits 0，or stop after 20 turns」。

你和 team lead 在對話裡講好「不要動 legacy/」。Teammate 還是改了。為什麼？

Teammate 不繼承 lead 的對話，只載入 CLAUDE.md、MCP server 與 skill（p.42）。規則要寫進 spawn prompt 或 CLAUDE.md；要強制，用 PreToolUse hook。

兩個 agent 同一秒認領同一個任務，都 commit 了 lock file。誰贏？為什麼不會兩個都贏？

先 push 成功的贏。Remote 有了新 commit，git 拒絕第二個 push；它 pull 之後看到 lock file，改挑別的任務（p.53）。這是樂觀鎖。

6 · 動手試試

照著做一次

每個範例都依 2026 年 10 月的 Claude Code 官方文件。點開才會展開。

用 SessionStart hook 保證規則一定在 context 裡p.12–13

這是 Superpowers 的做法，縮小成一個專案能用的版本。Hook 在 session 開始、/clear 之後、compaction 之後各執行一次，把一份規則檔的內容加進 context。

驗證：開新 session，輸入「你現在的規則是什麼？」。Claude 應該能複述 WORKFLOW.md 的內容。再輸入 /clear，問一次，規則應該還在。

兩個任務，兩個 worktree，兩個 sessionp.30–31

最短的做法是 -w。Claude Code 會在 .claude/worktrees/<name>/ 建 worktree，branch 叫 worktree-<name>。離開 session 時，有改動它會問你要保留或刪除。

想自己控制目錄和 branch 名稱，用 git 指令。三個目錄共用一個 .git，在一個 worktree 的 commit，其他 worktree 立刻看得到。

新 worktree 沒有 .env 和 node_modules。先裝相依套件，或在 .worktreeinclude 列出要複製的檔案。同一個 branch 不能在兩個 worktree 同時 checkout。

定義一個唯讀的 reviewer subagent，再明確委派p.35–39

一個 subagent 就是一個 Markdown 檔。Frontmatter 是設定，body 是它的 system prompt。只給三個唯讀 tool，它就改不了檔案。

委派時寫清楚範圍和回報格式。Subagent 沒有你的對話歷史，也不一定載入 CLAUDE.md 的所有規則，所以相關規則要寫進任務訊息。

一定要它執行時，用 @agent-code-reviewer 開頭。要限制巢狀層數，在 .claude/settings.json 的 env 設 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH；設 1 就關閉巢狀。

寫一個 /goal 檢查得到的條件，和一個 /loop 的 promptp.48–49

好的 goal 條件有三部分：可量測的終點、檢查方法、限制條件。再加一個停止條款，限制花費。條件不必加引號。

/goal 不改權限模式。要讓它無人看管地跑，先切到 auto mode；否則每個沒放行的指令都會停下來問你。輸入 /goal 看狀態，/goal clear 提早結束。

/loop 是觸發器，不判斷完成。固定間隔的 loop 要請 Claude 取消，或 7 天後過期。省略 prompt 時，它跑 .claude/loop.md。
