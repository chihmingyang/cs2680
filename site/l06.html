Agent memory 與可靠性

Agents design III: agent memory and reliability

  • Slides6_agent_design_3.pdf ↗
  • 頁數33
  • 閱讀約 20 分鐘

先看這裡

這堂課分兩半。前半把 agent memory 拆成一條生命週期：觀察、編碼、儲存、檢索、反思、遺忘，每一站都是一個 policy 決策。後半解釋 agent 為什麼不可靠：錯誤會相乘，失敗有 5 個來源。

  • Memory 有兩層，中間是 policy。Context window 是這一次的工作狀態，memory store 跨 session 保存。Store 的內容要先檢索進 context，model 才看得到。
  • 檢索不能只看語意。還要看 scope、重要性、有效時間、來源。遺忘和寫入一樣是正式操作。
  • 錯誤會相乘。每步成功率 95%，50 步全對只剩約 8%。失敗要先找來源層，再在那一層修。

建議順序：先讀第 5 段的基礎題，帶著問題自己一頁一頁看完 slides；再回來讀這篇。讀書會前用第 5 段的進階題。

1 · 架構

Memory 的生命週期，以及錯誤怎麼相乘

第一張圖：store 的內容只有經過檢索（藍色箭頭）才會回到 context；其他五站都在改寫 store。每一格都要有一條寫下來的規則。第二張圖：長條照 0.95ⁿ 的比例畫，50 步只剩 8%。Memory 決定 model 看到什麼；可靠性決定看對了之後，還有多大機會把任務做完。

2 · 核心觀念

五個觀念串起整堂課

Memory 是兩層，加上一串 policy 決策 p.6–11、p.18

Model 沒有狀態。Agent 看起來記得事情，是因為 harness 把 store 裡的文字放進 context。所以 memory 的每個設計問題都在問同一件事：什麼時候，把什麼，從哪一層搬到哪一層。Slide 把它拆成 7 個問題（p.7）。

每個問題都是取捨。每次互動都寫，recall 最高，雜訊也最多；只在使用者要求時寫，precision 最高，但漏很多（p.8）。摘要丟掉「以前用 vLLM」；結構化狀態存不進 schema 沒有的欄位；graph 能表達隨時間的變化（p.9）。p.18 的 checklist 把六站排成一列，每一站都要有明確、可量測的規則。

檢索不能只看語意相似 p.12

問題：使用者問「現在用哪個 serving engine？」，「用 vLLM」和「用 SGLang」兩筆的相似度幾乎一樣。語意分不出哪一筆是現在的事實。

Slide 列出另外 4 個訊號。Scope：同一個使用者、專案或任務。Importance：漏掉它和放進來的代價。Validity：此刻仍然成立。Provenance：來源、信心、證據。

用法不同。Scope 和 validity 要寫成硬過濾條件；只當排序分數時，別人的記憶仍可能進入 top-k，這就是 p.20 的 isolation failure。Importance 和 provenance 適合調整排序，或做成不看 query 的常駐規則。

遺忘、有效時間、來源都是第一級操作 p.13–15、p.20–21

事實會變。專案 4 月用 vLLM，6 月換成 SGLang（p.15）。系統如果只會新增，舊的會蓋過新的，這是 p.20 的 staleness。解法是兩個欄位：valid time 記事實在哪段時間成立，新事實讓舊的 valid_to 關上，但不刪除；provenance 記來源與信心，使用者親口說的和網頁讀到的，信任等級不同。

遺忘有 4 種做法：標記失效、永久刪除、TTL 到期、分層移出（p.14）。歸納是另一種改寫：多筆觀察合成一條較高層的記憶，要附信心值並連回證據（p.13）。證據太少就歸納，一次事件會變成長期偏好。

錯誤會相乘 p.24

一個 run 要每一步都對才算成功。每步成功率 95%，n 步全對的機率是 0.95ⁿ：5 步 77%，10 步 60%，20 步 36%，50 步 8%。約 13 次才有 1 次全對。

這個算法假設每步獨立。真實的 run 更差：第 3 步讀錯檔案，第 4 步就改錯地方，第 5 步再為錯的修改補洞。反過來算，要讓 50 步有 90% 全對，每步要 99.79%。所以三件事要同時做：減少步數、讓每步更可靠、在中途驗證並存 checkpoint。

失敗有 5 個來源，每層一道防線 p.26–32

同一個症狀可能來自不同層。「agent 說測試過了，但測試沒過」：也許 model 沒跑測試，也許 tool 截掉了錯誤輸出，也許環境是舊的 build。Slide 把來源分成 5 層：任務規格、harness、model、tool、環境（p.26）。

每層有自己的失敗型態（p.27–31）：規格的代理目標、harness 的 context 截斷、model 的沒驗證就宣布完成、tool 的靜默失敗、環境的版本不符。p.32 把修法濃縮成 5 個原則：把「完成」寫成測試；每個 run 都有上限；要求證據；tool 失敗要大聲；環境固定並隔離。除錯時先找第一個出錯的步驟，在那一層修。

3 · 觀念補充

Slide 預設你已經懂的背景

Embedding 與 vector searchtop-k 是怎麼算出來的

Embedding model 把一段文字轉成一串數字，也就是向量。意思相近的文字，向量也相近。查詢時把 query 也轉成向量，找出距離最近的 k 筆 p.10。相似度量的是「意思像」，它不知道哪一筆是真的、哪一筆是現在的。

TTL 與 eviction自動遺忘的兩種機制

TTL（time to live）是資料的存活時間，寫入時設定，時間到就自動刪除。Redis 的寫法：SET task:42:notes "..." EX 86400，86,400 秒後消失。Eviction 是空間不夠時挑東西丟，例如最久沒用的先丟。TTL 適合短期狀態；長期事實要用 valid time 標記失效 p.14，這樣還能回答「以前是什麼」。

Precision 與 recall用在 memory 的寫入與檢索

Recall：該記的事記下了多少；該取回的記憶取回了多少。Precision：記下的東西有多少真的有用；取回的有多少相關。寫入 policy 在兩者之間取捨 p.8。評估時要分開量寫入和檢索：retrieval miss 可能是沒寫，也可能是沒找到 p.21。

獨立假設0.95ⁿ 背後的前提

把機率相乘，前提是每步的成敗互不影響。Agent 的步驟有相依性：前一步的輸出是下一步的輸入，錯誤往後傳時，後面步驟的成功率低於 95%，所以 0.95ⁿ 是上界 p.24。

驗證步驟能打斷這個傳遞。Checkpoint 再加一步：在驗證過的狀態存快照，失敗只重跑之後的步驟 p.28。Claude Code 用 /rewind 回到之前的檔案狀態；Bash 指令改的檔案不在追蹤範圍。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

Memory 和任務搶同一個 context

每一條載入的記憶都佔 context，而且每圈 loop 都要重送（L2）。記憶越多，留給任務的空間越少；無關的記憶還會分散注意力（p.20 的 context pollution）。

所以 memory 系統的第一個指標是 token overhead（p.21），不是記了多少。可行的預算：常駐記憶只放索引，細節按需讀取。Claude Code 每個 session 只載入 MEMORY.md 的前 200 行或 25KB，topic 檔按需讀。

Memory 要像任何元件一樣做 eval

p.22 的 benchmark 測的是聊天歷史的回想。Coding agent 的記憶，例如專案慣例，不在範圍內。

要知道自己的 memory 有沒有用，要自己做測試集：一組「應該記得」、一組「應該忘掉」、一組別人的事實，各自查一遍。沒有這組測試，policy 的改動只能靠感覺。L7 會講怎麼建 eval。

可靠性工程的習慣可以搬過來

SRE 有 timeout、retry with backoff、circuit breaker、error budget。Agent 的對應物：步數和成本上限、tool 失敗先重試再下結論、沒進展就停、每種任務有可接受的失敗率。

差別在失敗的型態。服務的失敗大多能偵測；agent 的失敗常常安靜，例如沒驗證就宣布成功（p.29）。所以「要求證據」排在所有習慣之前。

「還沒有最佳實踐」對團隊的意思

Slide 的結語是：我們對大規模的 agent 了解不多（p.32）。這堂的表格是起點，之後會改。對團隊的做法有三件：把每條規則寫成可量測的 policy；記錄每個 run 的 trajectory；定期看失敗來自哪一層。沒有記錄，就不知道該改什麼。

  1. p.6–8 · Memory 的兩層與寫入

    Store 的內容要經過什麼，model 才看得到？「每次都寫」和「只在使用者要求時寫」各有什麼代價？

    參考答案與重點複習

    答案：Store 的內容要先經過檢索，由 harness 放進 context window，model 才看得到（p.6、p.12）。Context window 是這一次的暫時工作狀態；memory store 在 context 之外，跨 session 保存（p.6）。每次互動都寫：recall 最高，雜訊也最多。只在使用者明確要求時寫：precision 最高，但會漏掉很多（p.8）。

    重點拆解

    Model 本身沒有狀態。每次呼叫，它只看得到這一次送進去的 context。所以 p.6 把 memory 分成兩層：context window 是工作狀態，session 結束就消失；memory store 在 context 之外，例如檔案或資料庫，跨 session 保存。兩層之間的搬運，全部由 harness 負責。

    讀的方向是檢索。Harness 用目前的 query 做 vector search，取回 top-k 筆，組進 prompt（p.12）。沒被取回的記憶，對 model 來說等於不存在。所以「store 裡有」和「model 知道」是兩件事，中間隔著一步檢索。p.20 的 retrieval miss 就發生在這一步：記憶存在，但沒被找到。誰觸發檢索也是設計選擇：每一輪自動查、由 harness 判斷，或由 model 呼叫 search_memory() 這類 tool（p.11）。

    寫的方向是寫入 policy。p.8 把寫入畫成一條光譜：一端是每次互動都寫（high recall），另一端是選擇性地寫（high precision）。光譜上有 4 種做法：使用者明確要求、deterministic rules、small classifier、periodic LLM review。每次都寫，該記的都記下了，但 store 裡大部分是雜訊。只在使用者說「記住這個」時寫，記下的幾乎都有用；但使用者沒想到要說的事，全部漏掉。

    背景補充

    這兩層對應 L1 的 OS 類比：context window 像 RAM，memory store 像 disk。CPU 只能直接讀 RAM，disk 上的資料要先載入。MemGPT（2023）把這個類比做成系統：model 自己用 function call 在兩層之間搬資料，像 OS 的 paging。RAG 也是同一個結構：知識放在外部索引，查詢時才取回、放進 prompt。

    寫入的雜訊有兩個成本。第一，取回的每一筆都佔 context，而且每一圈 loop 都要重送。第二，雜訊越多，真正相關的那一筆越難排進 top-k。所以寫入 policy 也決定了之後檢索的品質。

    常見誤解

    「Context window 夠大，就不需要 memory。」Context window 只活在這一個 session，session 結束就清空。而且 context 越長，越貴、越慢，model 也越難找到中間的資訊（L4 的 lost in the middle）。大 window 解決單次任務的容量，不解決跨 session 的保存。

    帶走這幾點
    1. Model 只看得到 context；store 的內容要經過檢索 → 放進 context，才會影響回答。
    2. 「Store 裡有」不等於「model 知道」；中間的檢索可能失敗，這就是 retrieval miss。
    3. 寫入 policy 是 recall 與 precision 的取捨：全寫 → 雜訊多；只照要求寫 → 漏很多。

    相關：核心觀念〈Memory 是兩層，加上一串 policy 決策〉；觀念補充〈Embedding 與 vector search〉、〈Precision 與 recall〉；延伸思考〈Memory 和任務搶同一個 context〉；L1 Agent 是一種新的電腦、L2 Agent 的記憶。進階題第 3 題會替 coding agent 設計寫入 policy。

  2. p.12–15 · 檢索訊號與有效時間

    除了語意相似，檢索還要看哪 4 個訊號？p.15 每條記憶帶的兩個欄位各記什麼？

    參考答案與重點複習

    答案：4 個訊號：scope（同一個使用者、專案、實體或任務）、importance（漏掉或放進來的代價）、validity（對這個任務、在此刻仍成立）、provenance（來源、信心、證據）（p.12）。Valid time 記這個事實在哪段時間成立；provenance 記它從哪裡來。p.15 的例子：4 月的 vLLM 標成 superseded，6 月的 SGLang 是 current，來源是 Episode 28。

    重點拆解

    Vector search 只回答一個問題：這筆記憶的意思和 query 像不像（p.12）。它不知道這筆屬於誰、現在還對不對、從哪裡來。使用者問「現在用哪個 serving engine？」，「用 vLLM」和「用 SGLang」都在講 serving engine，相似度幾乎一樣。語意分不出哪一筆是現在的事實。

    另外 4 個訊號，各補一個語意看不到的缺口。把它們和 p.20 的失敗模式對起來看，就知道缺了哪一個會出什麼事：

    訊號（p.12）它問什麼缺了它，容易出現（p.20）
    Scope是同一個使用者、專案、任務嗎？Isolation failure：別人的記憶跨界進來
    Importance漏掉或放進來，代價多大？Retrieval miss：關鍵規則沒取回；context pollution：無關記憶塞滿 context
    Validity此刻、對這個任務還成立嗎？Staleness：舊事實蓋過新的
    Provenance誰說的？信心多少？證據在哪？Memory hallucination：推論被當成事實

    p.15 用一條時間軸說明 valid time 與 provenance。Episode 28 這段互動提到，serving 從 vLLM 搬到了 SGLang。Store 把它存成一條三元組 Project → SERVES_WITH → SGLang，來源記 Episode 28。舊的 vLLM 那一筆沒有刪除，而是標成 superseded：它只在 4 月到 6 月之間成立。這樣系統能回答兩種問題。「現在用什麼」取 current 的那一筆；「5 月用什麼」取那段時間成立的那一筆。

    背景補充

    Valid time 是資料庫的老概念。Bitemporal 資料模型有兩條時間軸：valid time 是事實在真實世界成立的時間；transaction time 是系統記下它的時間。SQL:2011 標準把 temporal table 納入規格。p.17 的 Graphiti 是 temporal knowledge graph，把同一個想法用在 agent memory 上。

    Provenance 對應資料工程的 data lineage：每一筆資料都能追到來源。對 agent 來說，來源決定信任等級。使用者親口說的，和網頁上讀到的，不該同等對待。這一欄也是防 persistent prompt injection 的基礎（下一題）。

    常見誤解

    「新事實來了，把舊的刪掉就好。」刪掉之後，系統答不出「以前用什麼」，也查不到是誰、在什麼時候改的。新的一筆如果是錯的，也沒有舊值可以還原。所以 p.14 把「標記失效」和「永久刪除」列成兩種操作。永久刪除適合隱私這類資料必須真的消失的情況。

    帶走這幾點
    1. Vector search 只量「意思像不像」；它不知道是誰的、何時的、從哪來的。
    2. Scope、importance、validity、provenance 各補一個缺口；缺了哪一個，就對應 p.20 的一種失敗。
    3. 事實改變時，關掉舊事實的有效時間，不刪除 → 能回答現在，也能回答過去。

    相關：核心觀念〈檢索不能只看語意相似〉、〈遺忘、有效時間、來源都是第一級操作〉；觀念補充〈Embedding 與 vector search〉、〈TTL 與 eviction〉；L4 Embedding 與 semantic search。動手試試有一筆帶 valid time 的 JSON 記錄。進階題第 1 題會用 4 筆記憶實際排一次。

  3. p.16–20 · 擁有權與失敗模式

    Agent-owned 和 dedicated memory 差在哪裡？哪一種失敗模式讓惡意指令一直留著？

    參考答案與重點複習

    答案：Agent-owned：memory 是 harness 裡的檔案，例如 CLAUDE.md，harness 直接讀寫。Dedicated：memory 是 agent 呼叫的服務，例如 Mem0、Graphiti，可以跨 agent、跨 session 共用（p.16–17）。讓惡意指令一直留著的是 persistent prompt injection：惡意的文字寫進 memory，之後每個 session 讀回它，攻擊就再生效一次（p.20）。

    重點拆解

    兩種做法的差別，在「誰管理 memory」。p.23 把它畫成兩種 stack。一種是 runtime 自己管理 memory，storage 就是 Markdown 檔。另一種是在 runtime 和 storage 之間加一層獨立的 memory management，下面接 vector、SQL、graph 或 object store。

    一般的 prompt injection 只活在一個 session 的 context 裡。Session 結束，惡意文字就跟著消失。Persistent 版本多了一步：agent 把讀到的惡意內容寫進 memory。之後每個 session，檢索或自動載入都把它帶回 context。它以「agent 自己的筆記」出現，看起來像可信的指令。所以它一直留著，直到有人發現並刪掉它。

    p.20 的 8 種失敗模式，可以照第 1 段的生命週期圖分組。寫入、整理與歸納時出錯：memory hallucination、overgeneralization、persistent prompt injection。檢索時出錯：retrieval miss、context pollution、isolation failure。沒有遺忘機制：staleness、unbounded growth。

    背景補充

    Persistent prompt injection 很像 web 安全的 stored XSS。Reflected XSS 只影響點了惡意連結的那一次請求。Stored XSS 把惡意腳本存進資料庫，之後每個讀到那一頁的人都會中招。OWASP 的 LLM 應用 Top 10 把 prompt injection 列為第一名（LLM01）。

    選擇 ownership 也是選擇怎麼稽核。Plain files 容易檢查、diff、搜尋（p.10），可以放進 git，每一次寫入都有紀錄。Dedicated 服務能跨 agent 共用、能做過濾查詢；代價是多一個要維運的服務。共用的 store 也必須做好 scope 隔離，不然就是 isolation failure。

    「Memory 是 agent 自己寫的，所以可以信任。」Agent 寫下的，是它讀到的東西。它讀過網頁、README、tool 輸出，這些內容可能被寫進 memory。如果沒有記錄來源，下次讀回來時，已經分不出哪一句來自使用者、哪一句來自外部。

    1. Agent-owned 是 harness 裡的檔案；dedicated 是一個跨 agent、跨 session 共用的服務。
    2. 一般 injection 隨 session 結束消失；寫進 memory → 每個 session 讀回 → 每次再生效。
    3. 8 種失敗模式分屬寫入、檢索、遺忘三段；除錯時先找是哪一段出錯。

  4. p.24 · 錯誤會相乘

    每步成功率 95% 時，50 步全對的機率約多少？為什麼真實的 run 比這更差？

    參考答案與重點複習

    答案：約 8%（0.95⁵⁰ ≈ 7.7%），也就是約 13 次才有 1 次全對。一個 run 要每一步都對才算成功（p.24）。這個算法假設每步獨立。真實的 run 裡錯誤會往後傳：早期的一個錯誤，讓後面每一步更容易錯，所以實際更差（p.24）。

    重點拆解

    一個 run 是一條串起來的鏈。任何一步錯，整個 run 就失敗。每步成功的機率是 0.95，而且互不影響時，n 步全對的機率是 0.95 自乘 n 次。p.24 的數字：1 步 95%，5 步 77%，10 步 60%，20 步 36%，50 步 8%。每多 1 步，剩下的機率再乘一次 0.95。所以它是指數衰減，不是直線下降：約 13.5 步就只剩一半。

    真實的 run 更差，因為 agent 的步驟不獨立。前一步的輸出，是下一步的輸入。第 3 步讀錯檔案，第 4 步就在錯的檔案上修改，第 5 步再替錯的修改補洞。出錯之後，後面每一步的成功率都低於 95%。所以 0.95ⁿ 是樂觀的上界，p.24 也在註腳寫明這個假設。

    每步的可靠度槓桿很大。每步失敗率從 5% 降到 1%，50 步的成功率從 7.7% 升到 60.5%（0.99⁵⁰）。所以設計方向有三個：減少步數、讓每步更可靠、在中途驗證並存 checkpoint，讓錯誤不再往後傳（p.32）。

    例子

    不用計算機算 0.95⁵⁰：一直平方。0.95² = 0.9025；0.95⁴ = 0.9025² ≈ 0.8145；0.95⁸ ≈ 0.6634；0.95¹⁶ ≈ 0.4401；0.95³² ≈ 0.1937。50 = 32 + 16 + 2，所以 0.95⁵⁰ = 0.1937 × 0.4401 × 0.9025 ≈ 0.0769，約 7.7%。倒數 1 ÷ 0.0769 ≈ 13，就是「13 次才有 1 次全對」。

    背景補充

    這是可靠性工程的串聯系統：每個元件都要正常，系統才正常，整體可靠度等於各元件可靠度相乘（Lusser's law）。微服務也一樣：一個請求依序經過 10 個 99.9% 可用的服務，整體約 0.999¹⁰ ≈ 99.0%。

    心算捷徑：每步失敗率 ε 很小時，(1 − ε)ⁿ ≈ e^(−nε)。nε 是一個 run 平均出幾個錯。50 × 0.05 = 2.5 個錯，e^(−2.5) ≈ 0.082，和 7.7% 很接近。所以要控制的是「一個 run 平均出幾個錯」：步數加倍、失敗率減半，結果幾乎不變。

    常見誤解

    「Model 的 tool call 準確率 95%，所以 agent 的任務成功率大約 95%。」單步的準確率不能直接當成任務的成功率。任務要跑幾十步，成功率要用相乘來估；步驟之間還有相依，實際更低。

    帶走這幾點
    1. 每步都要對 → 成功率是 0.95ⁿ，指數衰減；50 步只剩 7.7%，約 13 次 1 次。
    2. 0.95ⁿ 假設各步獨立；錯誤會往後傳 → 真實的 run 更低，0.95ⁿ 是上界。
    3. 要壓低的是 n × 失敗率：減少步數、提高每步可靠度、中途驗證並存 checkpoint。

    相關：核心觀念〈錯誤會相乘〉；觀念補充〈獨立假設〉；延伸思考〈可靠性工程的習慣可以搬過來〉；L1 長時間的 agent run 需要可靠性工程、L7 pass^k。動手試試的 compound.py 可以驗算。進階題第 2 題會反過來算每步要多可靠，並加入 retry。

  5. p.26–32 · 五層失敗與對策

    失敗的來源分哪 5 層？Harness 這一層，p.32 給了什麼設計原則？

    參考答案與重點複習

    答案：5 層：使用者與任務規格、agent harness、LLM、tool 層、環境（p.26）。Harness 的原則是每個 run 都有邊界。具體做法是設定步數、成本、時間上限，並做 checkpoint 與回滾（p.28、p.32）。

    重點拆解

    分層的理由：同一個症狀，可能來自不同層。Agent 說「測試過了」，測試卻沒過。也許 model 沒跑測試，也許 tool 截掉了錯誤輸出，也許環境是舊的 build。p.26 由上往下排出 5 個來源：任務規格（目標模糊）、harness（context、loop、排程）、LLM（推理、規劃）、tool 層（shell、browser、API）、環境（repo、OS、web、服務）。p.27–31 每層一張表，例如規格的代理目標、model 沒驗證就宣布完成、tool 的靜默失敗、環境的版本不符。

    Harness 的失敗，p.28 列了 5 種。Context 截斷：harness 剪掉最舊的對話，「不能改 API」的規則跟著消失。Memory 錯誤：把過期的筆記當事實，去改一個已經搬走的檔案。狀態損壞：留下改到一半的檔案，後面每一步都建在壞掉的狀態上。Control loop 錯誤：沒有設步數或成本上限，跑了 200 步沒有進展。Blocking fan-out：等每一個 sub-agent，一個慢的就卡住整個 run。

    p.32 把 harness 的修法濃縮成一句：每個 run 都有邊界。上限把「跑不停」變成「有限的失敗」：花費有上限，停下來後人可以接手。Checkpoint 在驗證過的狀態存一份快照。後面的步驟失敗，就回滾到快照，只重跑之後的步驟。這正好切斷上一題說的錯誤傳遞。其他四層的原則：把「完成」寫成測試、要求證據、失敗要大聲、環境固定並隔離。

    背景補充

    這套原則和 SRE 的習慣對得上。步數與時間上限就是 timeout。「沒有進展就停」和 circuit breaker 的精神一樣：持續失敗時主動停下，不再浪費資源。Checkpoint 與回滾像資料庫的 transaction：失敗時回到上一個一致的狀態，不留下改到一半的資料。

    在 Claude Code 的非互動模式（-p），--max-turns 限制 turn 數，--max-budget-usd 限制花費，時間上限用外層的 timeout 指令。互動模式可以用 /rewind 回到之前的檔案狀態，但 Bash 指令改的檔案不在追蹤範圍。

    常見誤解

    「Agent 失敗了，換一個更強的 model 就好。」更強的 model 只處理 LLM 這一層。規則在 compaction 時被丟掉、tool 把錯誤包成空結果、環境版本不一樣，換 model 之後一樣會發生。p.32 把「用更強的 model」列在 model 層的修法裡，它只是 5 層中的一層。

    帶走這幾點
    1. 5 層：任務規格、harness、LLM、tool、環境；同一個症狀可能來自不同層 → 先找第一個出錯的步驟。
    2. Harness 的原則是每個 run 都有邊界：步數、成本、時間上限，加上 checkpoint 與回滾。
    3. 上限把「跑不停」變成「有限的失敗」；checkpoint 讓錯誤不再往後傳。

    相關：核心觀念〈失敗有 5 個來源，每層一道防線〉；觀念補充〈獨立假設〉；延伸思考〈可靠性工程的習慣可以搬過來〉；L3 長時間執行的 agent，需要一個能檢查的終點、L5 Partial failure。動手試試有一組 run 預算的設定。進階題第 4 題把 5 個事故歸層，第 6 題用 run 紀錄訂出上限。

    畫出 persistent prompt injection 的攻擊路徑：惡意內容從哪一站進入 memory，從哪一站回來變成指令。再為每一站提出防線，並說明怎麼發現已經中招。

    從過去的 run 紀錄，替一個固定任務訂出每次 run 的步數、成本、時間上限，以及一條不靠上限的停止規則。估算這套預算能省多少，會誤殺幾次成功的 run。

    情境：任務是「找出 flaky test、隔離它、開 PR」。過去兩週跑了 40 次。28 次成功：turn 數中位數 14、p95 27；成本中位數 $0.80、p95 $1.40；時間中位數 6 分鐘、p95 12 分鐘。12 次失敗：7 次跑超過 60 turns 沒有進展，5 次改錯檔案後宣布完成；每次失敗平均花 $6.20、48 分鐘。團隊建議上限訂在 2 倍 p95。

    回答時請涵蓋
    • 寫出三個上限的數字與算式，並說明為什麼用 p95 而不用中位數或最大值。提示：上限 = 2 × p95，三個 p95 都在情境裡。再想：訂在中位數，幾成正常 run 會超過？訂在最大值呢？
    • 估算這套上限能省下多少成本與時間，以及在 28 次成功 run 裡大約會誤殺幾次。提示：每次失敗省下 = 失敗的平均花費 − 上限，再乘 12。誤殺：p95 的定義是幾 % 的成功 run 超過它？
    • 訂一條「沒進展就停」的規則，並說明上限擋不住哪一類失敗、要靠什麼補。提示：「進展」可以從新的檔案變更、新通過的測試裡挑。那 5 次「改錯檔案後宣布完成」碰到上限了嗎？看 p.32。

    上限：＿＿ turns、$＿＿、＿＿ 分鐘（2 × p95）。用 p95，因為 ＿＿。

    每次失敗約省 $＿＿ 與 ＿＿ 分鐘，12 次共省 $＿＿；28 次成功裡約誤殺 ＿＿ 次。

    停止規則：最近 ＿＿ 個 turn 沒有 ＿＿ 就停。上限擋不住 ＿＿，要靠 ＿＿ 補。

    參考觀點與追問
    • 上限：2 × 27 = 54 turns；2 × $1.40 = $2.80；2 × 12 = 24 分鐘。p95 不受單一離群值影響；用最大值等於沒有上限；用中位數會砍掉一半的正常 run。
    • 省下的部分：12 次失敗各花 $6.20、48 分鐘，上限之後每次最多 $2.80、24 分鐘。至少省 12 × $3.40 = $40.8（失敗成本的 55%）與 12 × 24 = 288 分鐘。
    • 誤殺：p95 的定義是 5% 的成功 run 超過它，28 次裡約 1 到 2 次；超過 2 倍 p95 的大約 0 到 1 次，而且會留下紀錄，可以人工接手。
    • 停止規則：最近 8 個 turn 沒有新的檔案變更，也沒有新通過的測試，就停下來回報。它大多在第 20 到 30 turn 就抓到那 7 次沒進展的 run，比 54 turns 早。
    • 上限擋不住的：5 次「改錯檔案後宣布完成」。這是 model 層的「未驗證就宣布成功」（p.29），要靠把「完成」寫成測試（p.32）：PR 附測試輸出，或用 Stop hook 要求測試通過才能結束。

    追問：不同任務的預算應該不同，你怎麼分類？Run 因為上限停下來時，做了一半的結果要保留、回滾，還是交給人？
