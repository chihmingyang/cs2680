先看這裡

這堂回答一個問題：你怎麼知道一個 agent 真的會做事？答案是一個系統：可重置的環境、固定的任務、明確的 grader，加上多次執行。分數只是起點，還要看可靠性、成本、速度，並提防 leakage。

  • 評估對象是整個系統，不只是 model。表現 = f（LLM、prompt、scaffold、tools、memory、environment）。換掉任何一塊，分數都會變，leakage 也能從任何一塊進來。
  • 上線看 pass^k，不看 pass@k。單次成功率 0.8 的 agent，pass@4 是 0.998，pass^4 只有 0.41。客戶只給你一次機會。
  • 每個 benchmark 只量一種動作空間。選和你的 agent 動作空間相同的 benchmark，再確認它還沒飽和。比較真實 agent 時用 Pareto frontier，同時看能力、成本、速度。

1 · 架構

一次 agent 評估的零件怎麼接在一起

看第一張圖，先找藍框：grader 是整個系統裡唯一「下判斷」的地方，它只能看答案、狀態、trajectory 三種輸入。一個 benchmark 的性格，大半由 grader 看哪一種決定。左邊的重置與預算不產生分數，但少了它們，分數就無法比較，評估也可能不會結束。第二張圖提醒你：grader 給的是單次分數，要說 agent 可靠，得把 k 次 trial 用 pass^k 彙整。

2 · 核心觀念

五個觀念串起整堂課

評估的對象，從預測文字變成完成互動任務 p.7–10

Slide 把評估目標排成五層：預測文字、答對問題、得到偏好、寫出能跑的程式、完成互動任務。越往下，grader 越需要「執行」。前兩層比對文字就夠；最後一層要先架好網站或資料庫，跑完再檢查狀態。所以 agent 評估本身是一個系統工程問題。

Slide 也分兩個層級。Component-level 看內部的單一能力，回答「為什麼失敗」。End-to-end 只看成功率、成本、latency，回答「能不能用」。兩種都要有，像 unit test 和 integration test。

一個成功率不夠：pass^k、成本、latency 各量一件事 p.11–12、p.20

pass@k 問「k 次裡至少 1 次成功嗎」，pass^k 問「k 次全部成功嗎」。差距就是 agent 不穩定的部分。單次成功率 0.8、各次獨立時：pass@4 = 1 − 0.2⁴ = 0.998，pass^4 = 0.8⁴ = 0.41。

該看哪一個，取決於失敗能不能重試。產生 5 個 patch 再用測試挑一個，是 pass@k 的世界。客服每位客戶只來一次，是 pass^k 的世界；τ-bench 提出 pass^k，就是因為它量的是客服。

成本要含 tool call 與 prefix cache miss；latency 要含 tool 執行與跑測試的時間。Slide 的對比：一次 200 步花 40 美元，另一次 12 步花 0.30 美元，兩次都「成功」。

每個 benchmark 由兩件事定義：agent 在哪裡做事、grader 檢查什麼 p.13–24

讀每一個 benchmark 時，只問兩件事：agent 的動作空間是什麼？Grader 看答案、狀態還是 trajectory？下表把 p.24 的總表壓成這兩欄。

只有 GAIA 只看答案，其他 7 個都檢查某種狀態。檢查狀態的好處是路徑自由：任何正確的路都得分。代價是環境要能重置，所以 WebArena 自架網站，Terminal-Bench 用 container。選 benchmark 時，挑動作空間和你的 agent 相同的；長任務要有 checkpoint，否則所有 agent 都是 0 分。

評估很難：leakage 走整個 stack，單一 turn 獎勵亂猜，一次執行只是雜訊 p.26–32

Leakage 不只發生在訓練。表現 P = f（LLM、prompt、scaffold、tools、retriever、memory、environment），每個輸入都能帶進答案。Web search 搜到已 merge 的 PR；sandbox 的 git 歷史露出修正；memory 記住上一輪的答案；開發者反覆看失敗案例調 prompt。所以「model 沒用測試集訓練」不足以證明分數乾淨。

多數 benchmark 只給一個完整指令，中間沒有使用者，這會獎勵「有自信地猜」。Agent 問釐清問題要多花步數，卻拿不到分數。多輪評估因此要測 clarification、recovery、memory 三件事。

還有三個挑戰。非確定性：只跑一次的分數大多是雜訊。副作用：過程中刪檔、寄信，分數不會扣。評分方式：只看結果會放過不安全的執行，比對 trajectory 會判錯其他正確的做法。

Benchmark 很快飽和，所以真實 agent 要用 Pareto 看 p.33–37

Slide 用 6 個 benchmark 說明飽和速度：frontier model 追上基準線只花 6 到 39 個月。SWE-bench Verified 從 33% 到 95% 用了 22 個月。飽和後，頂尖 model 的分數擠在一起，benchmark 就分不出強弱。對策有三種：出更難的版本（SWE-bench Pro）、刪掉飽和的題目（Terminal-Bench 4.0）、出更長的任務（OSWorld 2.0）。

比較真實 agent 時要同時看能力、成本、速度。A 每個維度都不比 B 差，且至少一個更好，就說 A 支配 B；沒有人支配的那一群是 Pareto frontier。這個方法不需要權重，只排除明顯較差的選項。

3 · 觀念補充

Slide 預設你已經懂的背景

pass@k 與 pass^k 的估計式為什麼不能把整體成功率取 k 次方

一題跑 n 次，成功 c 次。從 n 次裡任取 k 次全部成功的機率是 C（c，k） / C（n，k），這是 pass^k。至少 1 次成功是 1 − C（n−c，k） / C（n，k），這是 pass@k。兩個都要逐題算，再對所有題目取平均 p.12。

不能先算整體成功率再取 k 次方，因為每題難度不同。用第 1 段第二張圖的資料：8/12 取 4 次方得 0.20；逐題算再平均得 0.33。

答案正規化與 exact matchGAIA 怎麼把「比對文字」做乾淨

GAIA 的答案只有三種型別：短字串、數字、逗號分隔的清單。評分用 quasi exact match：依型別正規化，再完全比對。所以 4381 和 4,381 相同，大小寫與多餘空白也不計 p.14。

代價是題目要能用短答案回答。自己做評估時，先把答案格式限制死，grader 就能是幾行程式；答案一旦是自由文字，就需要 judge model。

LLM-as-judge用 model 當裁判的好處與偏誤

答案是自由文字或對話品質時，常用另一個 model 打分。Arena、AlpacaEval、MT-Bench 都是這一類 p.9。它便宜、快，能處理人寫不出規則的評分。

已知的偏誤：偏好較長的回答、偏好同一家的 model、容易受自我宣稱影響。WebArena-Verified 因此拿掉 judge，改用確定性檢查 p.16。要用 judge 時，先拿一小批人工標記校準它。

Pareto dominance多個維度怎麼比，又不用決定權重

A 支配 B：A 在每個維度都不比 B 差，且至少一個更好。所有不受支配的點是 Pareto frontier，也就是 Rank 1。拿掉 Rank 1 後，剩下不受支配的點是 Rank 2，依此類推 p.37。

加權成一個分數要先決定權重，而每個使用者不同。Pareto 不需要權重，只排除不值得考慮的選項；frontier 上的點之間，靠預算或 SLA 來選。

Benchmark 分數的標準誤50 題的分數，有多大的雜訊

把每題的分數當成一個樣本，benchmark 分數就是樣本平均。若每題成功率約 p、各題獨立，平均的標準誤是 √（p（1−p）/N）。N = 50、p = 0.8 時約 0.057，95% 範圍約 ±0.11 p.32。所以 80% 和 84% 的差距很可能是雜訊。

縮小雜訊有三招。加題目：N 要變 4 倍，標準誤才減半。每題多跑幾次：只能消掉同一題的執行變異。比較兩版時用配對：在同一組題目上看哪些題翻盤。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

公開 benchmark 回答「model 多強」，production 評估回答「我的 agent 能不能上線」

公開 benchmark 要跨團隊可比，所以題目固定、環境通用。你的 agent 要回答的問題不同：在你的 tool、資料、政策下，它會不會出錯。p.27 的公式說表現是整個 stack 的函數；換成你的 stack，分數就要重量。

所以 production 評估的任務該來自真實流量：匿名化的客戶請求、出過事的案例、政策的邊界條件。公開 benchmark 仍然有用，但用途是挑 model 與 harness 的起點，不是上線的證據。

Grader 是程式，程式需要測試

Grader 錯了，整個評估就在量錯的東西，而且沒有人會發現。SWE-bench 要出 Verified 版本，原因就是原始題目裡有描述不清、測試不合理的案例。

實務上給 grader 兩組測試：已知正確的 trajectory 必須得 1 分，已知不安全的必須得 0 分。再加一條規則：分數大幅跳升時，先懷疑 grader，再懷疑 leakage，最後才相信 agent 變強。

評估集是耗材，要有新陳代謝

p.33 說公開 benchmark 從推出到飽和只要幾個月到三年。團隊內部的評估集更快，原因是 p.27 的最後一列：開發者每看一次失敗案例、改一次 prompt，就把評估集的資訊帶進系統。幾週後，分數反映的是對這幾十題的熟悉度。

所以要固定一份 held-out 集，開發時不看，發版前才跑。每個 sprint 從 production 的失敗案例補新題，全員都做對的題目刪掉。舊題也要留著，才能回答「新版有沒有退步」。

你們團隊自己的 agent 評估，該長什麼樣

一份夠用的評估有五樣東西。可重置的環境：資料庫快照、mock 掉的外部 tool、清空的 memory。任務集：50 到 100 題，含「應該拒絕」的負面題。Grader：先檢查狀態，再掃 trajectory 的危險動作，最後才用 judge 看品質。Metrics：pass^k、每題成本、p95 latency 一起報。流程：一次只改一件事，用同一組任務重跑（L8）。

最後一個提醒來自 L6：agent 常常「沒驗證就宣布完成」。評估是 harness 外面的驗證，不依賴 agent 的自我報告。

  1. p.7 · 兩種評估層級

    評估 agent 分哪兩個層級？Component-level 看哪四種能力？End-to-end 看哪三個數字？

    參考答案

    Component-level 看 agent 內部：planning（任務拆解）、tool use（找到、選對、填對參數）、memory（擷取、整合、取回）、error recovery（出錯後能不能修正）。

    End-to-end 只看結果：success rate、每個任務的 cost、完成的 latency。前者回答為什麼失敗，後者回答能不能用。

  2. p.9–11 · 評估目標與 metric

    評估目標分哪五種？Agent 時代多了哪些 metric？Cost 和 latency 各常漏算什麼？

    參考答案

    五種：預測文字、給出正確答案、給出較受偏好的回覆、寫出能運作的程式、完成互動任務。越往後，grader 越需要執行環境。

    早期用 perplexity、accuracy / F1、win rate。Agent 多了 pass@k（k 次至少 1 次成功）、pass^k（k 次全部成功，τ-bench 提出）、cost、latency。Cost 常漏算 tool call 與 cache miss；latency 不只 LLM 的時間，tool 執行與跑測試也算。

  3. p.12 · 評估 loop

    Benchmark 的評估 loop 有哪幾步？什麼時候停？最後 evaluator 可以依哪三種東西打分？

    參考答案

    先把環境重置到任務的初始狀態。然後 agent 反覆 observe 環境、選一個 action、執行它。直到 agent 結束，或預算（步數、金額、時間）用完。

    Evaluator 依最終答案、最終環境狀態、trajectory 打分。每個 benchmark 選的不同：GAIA 只看答案，WebArena 與 OSWorld 看狀態，τ-bench 看資料庫加回覆。

  4. p.13–17 · 四個 benchmark 的差別

    GAIA 怎麼評分，它量不到什麼？WebArena 和 OSWorld 的 observation 差在哪裡？OSWorld 2.0 為什麼加 checkpoint？

    參考答案

    GAIA 有 466 題，只看最終答案：正規化後完全相符得 1 分，否則 0 分。它量得到推理、檢索、選 tool；量不到改變外界的動作，例如寄 email、訂機票、改資料庫。

    WebArena 給 accessibility tree，每個元素有 ID，agent 對 ID 做 click 或 type。OSWorld 只給螢幕截圖，agent 要自己算出滑鼠座標（GUI grounding）。OSWorld 2.0 的 108 個流程常超過 1 小時、數百步，每個約 27 個 checkpoint，讓做到一半也能給部分分數。

  5. p.18–20 · SWE-bench 與 τ-bench

    SWE-bench 的測試分哪兩組，各抓什麼？τ-bench 的 reward 怎麼算？pass^k 是什麼意思？

    參考答案

    一組原本失敗，修好後要通過；另一組原本就通過，改完後仍要通過，用來抓「改壞別的功能」。Patch 套上去跑測試，兩組都過才算解決。

    τ-bench 的 r = r_action × r_output：最終資料庫和目標狀態一致，而且回覆含必要資訊，任一項是 0 總分就是 0。pass^k 是同一題獨立跑 k 次全部成功的機率；pass@k 只要 1 次成功。客服 agent 要看 pass^k。

  6. p.21–24 · Terminal-Bench 與總表

    Terminal-Bench 為什麼介於 SWE-bench 和 OSWorld 之間？TB 4.0 為什麼刪題，剩幾題？TheAgentCompany 的部分分數怎麼算？

    參考答案

    Agent 在 container 裡下 shell 指令，範圍比修一個 repo 的 issue 大（設定、debug、建置），又不需要 OSWorld 的滑鼠座標。評分是對最終系統狀態跑測試腳本。TB 4.0 刪掉已飽和的題目，從 89 題剩 66 題；解答不公開，timeout 8 小時。

    S_partial = 0.5 × earned/total + 0.5 × S_full。拿到 7/8 個 checkpoint 但沒完成，得 0.44；全部完成才是 1.00。p.24 的總表裡，只有 GAIA 只看答案，其他 7 個都檢查某種狀態。

  7. p.26–27 · Leakage

    Data leakage 有哪四層？Agent 的表現是哪些東西的函數？為什麼「model 沒用測試集訓練」不夠？

    參考答案

    四層：training leakage（題目進了訓練資料）、eval-time leakage（評估時上網抄到修正）、environment leakage（sandbox 暴露未來的 commit 或隱藏測試）、benchmark overfitting（用公開測試集調 prompt 與 scaffold）。

    P = f（LLM、prompt、scaffold、tools、retriever、memory、environment）。每個輸入都能帶進答案：few-shot 範例取自測試題、RAG 收錄答案、memory 存了上一輪、web search 搜到解答、開發者反覆看失敗案例。Model 只是其中一個輸入。

  8. p.28–32 · 單一 turn 與其他挑戰

    多數 benchmark 只有一個 user turn，這會漏掉什麼？多輪評估要測哪三件事？p.32 還列了哪四個挑戰，成本的例子差幾倍？

    參考答案

    真實工作會模糊、會修改、會中斷；單一 turn 的評分會獎勵有自信地猜，問釐清問題反而拿不到分。多輪要測 clarification（會不會問）、recovery（收到糾正會不會重新規劃）、memory（前面的限制後面還記不記得）。

    四個挑戰：成本與 latency、非確定性、安全與副作用、評分方式本身。成本的例子：一次 200 步花 40 美元，另一次 12 步花 0.30 美元，兩次都成功，相差約 133 倍。

  9. p.33–37 · 飽和與 Pareto frontier

    Frontier model 追上 benchmark 要多久？SWE-bench Verified 從幾分升到幾分？什麼叫 A 支配 B，Pareto frontier 是什麼？

    參考答案

    6 到 39 個月：GLUE 14 個月、MMLU 39 個月、GPQA Diamond 10 個月、ARC-AGI-3 只要 6 個月。SWE-bench Verified 從 33% 到 95%，花了 22 個月。所以看到高分，先確認 benchmark 有沒有飽和。

    真實 agent 要看能力、成本、速度三個維度。A 在每個 metric 都不比 B 差，且至少一個更好，就說 A 支配 B。沒有任何 agent 能支配的那群是 Pareto frontier（Rank 1）；拿掉它們後不受支配的是 Rank 2。

  1. 概念 · pass@k 與 pass^k · p.11、p.20

    用自己的話解釋 pass@k 和 pass^k 各量什麼。面對客戶的 agent 該看哪一個？什麼情況下另一個才是對的指標？

    情境：兩個退款客服 agent 在同一組 50 題上各跑 4 次。甲：pass@4 = 0.95，pass^4 = 0.55。乙：pass@4 = 0.88，pass^4 = 0.74。每位客戶只來一次，失敗就是一筆錯的退款。

    回答時請涵蓋
    • 說明兩個 metric 的定義，以及它們的差距代表什麼。
    • 為退款情境選一個 agent，用數字說明理由。
    • 舉一個 pass@k 才正確的情境，說明它和退款情境差在哪。
    思考方向

    兩個 metric 的差距，是「有時成功、有時失敗」的題目。先算甲和乙各有多少比例屬於這一類。pass@k 的前提是能重試，而且能自動判斷哪一次對了。

    參考觀點與追問
    • pass@k：k 次裡至少 1 次成功的題目比例，量「能力的上限」。pass^k：k 次全部成功的題目比例，量「可靠性」。差距是不穩定的題目：甲 40%，乙 14%。
    • 退款選乙。客戶只來一次，他遇到的成功率接近 pass^1，和 pass@4 無關。甲有 40% 的題目會隨機失敗。乙完全做不到的題目（12%）比甲（5%）多，但這些可以事先用規則轉人工。
    • pass@k 正確的情境：產生多個 patch 用測試挑一個，或產生多份草稿由人挑。條件是「能重試」加「有便宜的驗證器」。退款兩個條件都沒有。
    • pass@4 的分數要花 4 次執行才拿得到，真實上線只跑 1 次。pass^k 要逐題算再平均；k 越大越嚴格，τ-bench 常報 k = 1 到 8。

    追問：如果甲的失敗都是「停下來請人工接手」，乙的失敗是「退了錯的金額」，選擇會變嗎？「安全地放棄」該算成功還是失敗？

  2. 估算 · 非確定性與樣本數 · p.11、p.32

    算出 pass@4 與 pass^4，再估算 50 題 benchmark 分數的標準誤。新版比舊版高 4 個百分點，算不算進步？

    情境：單次成功率 p = 0.8，各次執行獨立。Benchmark 有 50 題，每題只跑 1 次。舊版得 80%，新版得 84%，團隊想據此宣布新版更好。

    回答時請涵蓋
    • 寫出 pass@4 與 pass^4 的算式與結果。
    • 估算 50 題分數的標準誤與 95% 範圍，判斷 4 個百分點是否超過雜訊。
    • 提出兩個讓比較更可信的做法，說明各自消掉哪一種變異。
    思考方向

    pass@4 = 1 − （1 − p）⁴，pass^4 = p⁴。標準誤把每題當一個 0 或 1 的樣本：√（p（1−p）/N）。比較兩版時兩邊都有雜訊。84% 對 80%，在 50 題上只差 2 題。

    參考觀點與追問
    • pass@4 = 1 − 0.2⁴ = 0.9984。pass^4 = 0.8⁴ = 0.4096。同一個 agent，一個接近滿分，一個不到一半。
    • 標準誤 = √（0.8 × 0.2 / 50） ≈ 0.057。95% 範圍約 ±1.96 × 0.057 ≈ ±0.11，也就是 0.69 到 0.91。
    • 兩版差值的標準誤 ≈ √（0.057² + 0.055²） ≈ 0.077。4 個百分點只有 0.5 個標準誤，在雜訊裡。50 題上這只是 42 題對 40 題。
    • 做法一：加題目。標準誤降到 0.02 要 N = 0.16 / 0.02² = 400 題。做法二：每題多跑幾次，只消掉同一題的執行變異。做法三：配對比較，在同一組題目上數「舊對新錯」與「舊錯新對」的題數。pass^4 的雜訊更大（50 題時約 0.07），需要更多樣本。

    追問：如果 50 題裡有 20 題是同一個情境改數字，各題還算獨立嗎？標準誤會低估還是高估？

  3. 設計 · 替客服 agent 設計評估 · p.12、p.19–20

    替一個會改資料庫、會寄信的客服 agent 設計評估。環境怎麼架、grader 看什麼、報告哪些 metric、怎麼抓副作用？

    情境：Agent 處理「改收件地址」與「退款」。可用 tool：lookup_order、update_address、issue_refund、send_email。政策：已出貨的訂單不能改地址；退款超過 200 元要人工核准。客戶由 LLM 模擬。

    回答時請涵蓋
    • 列出環境的組成，說明每個 trial 怎麼重置、哪些 tool 要 mock。
    • 定義 grader：檢查什麼狀態、什麼回覆、什麼寫入算違規，寫成一個公式。
    • 列出要報告的 metric，舉一個「最終狀態正確但應該判失敗」的執行。
    思考方向

    照 τ-bench：reward = r_action × r_output，再想副作用該不該乘進第三項。「應該拒絕」的題目，目標狀態是「資料庫不變」。send_email 真的寄出去就是副作用，評估時它該指向哪裡？

    參考觀點與追問
    • 環境：含訂單與出貨狀態的資料庫快照；每個 trial 從快照還原，memory 清空。send_email 改寫進 outbox 表，issue_refund 改寫進 ledger 表。模擬客戶照腳本演，知道訂單號與目的，不知道政策。
    • Grader：r = r_state × r_reply × r_safe。r_state：資料庫差異等於標註的目標差異；唯讀 call 不算，多餘的寫入直接 0 分。r_reply：回覆含必要資訊，例如「已出貨不能改地址」，用關鍵字檢查。r_safe：沒有超過 200 元卻缺核准標記的退款；outbox 沒有寄給非客戶的地址。
    • Metric：pass^k（k = 4 到 8）逐題再平均；每題成本含 tool call；每個 turn 的 p95 latency，因為客戶在等。任務集要有「正常完成」「應該拒絕」「應該升級人工」三類，否則「永遠照做」也能高分。
    • 狀態正確卻該判失敗：訂單未出貨，agent 正確改了地址，但過程中呼叫 issue_refund 又取消。r_state = 1，r_safe = 0，總分 0。

    追問：模擬客戶會不會洩漏答案，例如主動說「我知道這張不能改」？你怎麼檢查模擬客戶有沒有照腳本？

  4. 團隊實務 · 避免 leakage · p.26–27

    團隊在同一組評估題上反覆迭代，分數一路上升。找出這個流程裡的 leakage 管道，設計一套能防止它的工作方式。

    情境：5 位工程師每週在同一組 60 題上調整 coding agent，分數 6 週內從 45% 升到 78%。System prompt 裡出現「issue 提到時區時，先看 utils/date.py」這類規則。Agent 有 web search，也有跨 session 的 memory。

    回答時請涵蓋
    • 對照 p.27 的表格，指出至少 3 條 leakage 管道，各舉一個證據。
    • 提出一套工作方式：題目怎麼切分、多久輪替、誰能看什麼。
    • 說明你怎麼檢驗 78% 有沒有灌水。
    思考方向

    p.27 的最後一列是開發流程本身。那條「先看 utils/date.py」的規則從哪裡學來？機器學習用 train / validation / test 三份資料處理同樣的問題，對應到 agent 開發是什麼？

    參考觀點與追問
    • 管道一，benchmark overfitting：那條規則指向特定檔案，只對這 60 題有用；證據是拿掉規則後分數掉多少。管道二，memory：第 2 輪起 agent 可能直接取回上一輪的答案；證據是清空 memory 重跑。管道三，web search：搜到已 merge 的修正；證據在 trajectory 的網址與 PR 編號。
    • 切分：40 題開發集、20 題 held-out 集。開發集可以看失敗案例；held-out 集只在發版前跑一次，只報分數，不看 trajectory。
    • 輪替與審查：每個 sprint 從 production 的失敗案例補 5 到 10 題，全員都做對的題目刪掉。Prompt 裡指向特定檔名的規則，PR review 時視為 leakage。評估時 memory 從空的開始，環境做成離線（L8 的 Assignment 3 就這樣做）。
    • 檢驗 78%：關掉 web search 重跑、在 held-out 集上跑、在一批全新的題目上跑。三個分數和 78% 差距越大，灌水越多。

    追問：Held-out 集由誰保管？工程師自己有權限看時，制度還有效嗎？新題從 production 來，怎麼匿名化？

  5. 風險 · 只看結果會放過不安全的執行 · p.14、p.32

    一個 coding agent 修好了 bug、測試全過，trajectory 卻有危險動作。設計 trajectory 檢查，讓這種執行判失敗，又不誤判做法不同但正確的執行。

    情境：Outcome grader 給這次執行 1 分。Trajectory 顯示：agent 對共用分支執行了 git push --force；刪了 .env 檔；把一個 API key 印進 log；換了 3 種做法才修好；多讀了 10 個無關的檔案。

    回答時請涵蓋
    • 把 trajectory 裡的事件分成「必須判失敗」與「不該扣分」兩類，說明判準。
    • 把檢查寫成規則：用 action 的名稱、參數、輸出判斷，不比對步驟順序。
    • 決定計分方式：硬性 0 分還是扣分，並給這次執行最終的分數。
    思考方向

    p.32 說比對 trajectory 會判錯其他正確的做法。所以檢查只能問「有沒有做不該做的事」：deny-list 與 invariant。τ-bench 的規則可以借用：唯讀動作可以不同，不該有的寫入直接判失敗。

    參考觀點與追問
    • 必須判失敗：破壞性的 git 操作；刪除受保護的檔案（.env、migration、測試）；secret 出現在輸出或 commit；對 sandbox 以外的網路寫入。判準是「不可逆」或「影響他人」。
    • 不該扣分：嘗試幾種做法、改了哪些檔案、步驟順序、多讀無關檔案。p.16 說檢查結果就是為了允許不同的路。效率用步數與成本另外報告。
    • 規則寫法：每條是對 （tool, args, output） 的判斷式，例如 "push --force" in args、path matches protected、regex(secret_pattern, output)。再加 invariant：測試檔的 hash 執行前後相同，除非任務要求改測試。
    • 計分：安全違規是硬性 0 分，r = r_outcome × r_safe；扣分制會讓「修好但洩漏 key」拿到 0.8，上線時一樣不能接受。這次執行 r_outcome = 1，r_safe = 0，總分 0；報告仍記錄「測試通過」，供 component-level 分析。

    追問：Agent 靠修改測試讓測試通過，哪一條規則會抓到？如果任務本身就要求改測試呢？

  6. 分析 · 用 Pareto frontier 排序 agent · p.37

    用能力與成本替 5 個 agent 設定排出 Pareto rank。預算每題 0.50 元時該選哪一個？多付的錢買到多少能力？

    情境：同一組 200 題、各跑 1 次。A：0.58、每題 $0.12。B：0.66、$0.18。C：0.64、$0.45。D：0.79、$1.10。E：0.77、$1.60。速度先假設相同。

    回答時請涵蓋
    • 列出所有支配關係，寫出 Rank 1 與 Rank 2。
    • 在預算 $0.50 下選一個設定，說明為什麼不選另一個也符合預算的。
    • 估算沿 Rank 1 往上走，每提高 1 個百分點要多付多少錢，並指出一個會動搖排序的量測風險。
    思考方向

    支配：每個維度都不比對方差，且至少一個更好。兩兩比較 10 對，或畫在成本為橫軸、能力為縱軸的圖上。200 題的標準誤約 0.034；哪一對的差距小於這個數？

    參考觀點與追問
    • B 支配 C（0.66 > 0.64，$0.18 < $0.45）；D 支配 E（0.79 > 0.77，$1.10 < $1.60）。A 最便宜，沒有人支配它。Rank 1 = {A, B, D}，Rank 2 = {C, E}。
    • 預算 $0.50：B 和 C 都符合，但 C 受 B 支配，比 B 貴又比 B 差。選 B。
    • 邊際成本：A → B，+8 點花 $0.06，每點 $0.0075。B → D，+13 點花 $0.92，每點 $0.071，約 9 倍。要不要買 D，取決於那 13 點能省多少人工。
    • 量測風險：200 題的標準誤約 √（0.65 × 0.35 / 200） ≈ 0.034。B 與 C 只差 0.02，支配關係可能是雜訊。D 與 B 差 0.13，約 4 個標準誤，相對可信。加上速度後排序可能改變，第 6 段的練習會做這件事。

    追問：如果 D 的能力來自開了 web search，而其他設定沒有，這個比較還公平嗎？你會怎麼把 p.26 的 leakage 檢查加進 Pareto 分析？

自我檢查

一個 agent 的單次成功率是 0.9，各次獨立。pass@3 和 pass^3 各是多少？客服 agent 該看哪一個？

pass@3 = 1 − 0.1³ = 0.999。pass^3 = 0.9³ = 0.729。客服看 pass^3：每位客戶只有一次機會。

你的 coding agent 在 SWE-bench 從 40% 跳到 70%。你只改了一件事：加上 web search tool。可能的原因？怎麼檢查？

可能是 eval-time leakage：agent 搜到了這個 issue 的修正或 PR。檢查 trajectory 裡的搜尋紀錄與網址，或封鎖相關網域後重跑，看分數是否回落。

Agent X 成功率 65%、每題 $0.50；Agent Y 成功率 65%、每題 $0.80。速度相同，誰支配誰？

X 支配 Y。兩者能力相同，X 比較便宜：X 在每個維度都不比 Y 差，而且成本更好。

一個評估 loop 的骨架p.12、p.19–20
