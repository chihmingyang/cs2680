先看這裡

這堂把 Claude Code 當成 agent 的標本，拆開來看。它回答三個問題：一個 prompt 背後發生什麼、agent 怎麼記住事情、怎麼擴充 agent 的能力。

  • Agent = model + loop。Model 只負責提議下一步。Harness（Claude Code 本身）負責執行、檢查權限、管理 context。
  • 記憶就是每次都會載入的檔案。它每一步都佔 context、都要付費，所以要精簡、要維護。
  • 要保證發生的事，用 hook。寫在 CLAUDE.md 的規則，model 可能沒照做；hook 是程式，事件發生就一定執行。

1 · 架構

Claude Code 的零件怎麼接在一起

看這張圖，抓住一個重點：model 只負責「想」，所有「做」都經過 harness。Harness 每次呼叫 model 時，model 只看得到 context window 裡的東西。記憶、skill、tool 的定義，都是 harness 放進 context 的文字。Hook 不經過 model，它掛在 harness 執行 tool 的路徑上。

2 · 核心觀念

三個觀念串起整堂課

一個 prompt，很多圈 loop p.7–17

你打一個 prompt，Claude Code 會跑很多圈 loop。每一圈，harness 把整個 context 送給 model。Model 提議一個動作，例如跑 pytest。Harness 檢查權限，在你的電腦上執行，再把結果放回 context。Model 不再提議動作時，這一輪才結束。

這個結構有兩個後果。第一，成本和延遲隨圈數增加，因為每一圈都重送整個 context。第二，context 一直變大，快滿時就要 compaction，把舊的過程摘要起來。摘要會丟掉細節，所以重要的規則不能只靠對話記住。

Agent 的記憶，就是每次都會載入的檔案 p.18–31

Model 沒有狀態。它不記得上一個 session，也不記得上一圈 loop。Agent 看起來記得事情，是因為 harness 每次都把相關文字放進 context。

Claude Code 有兩套持久記憶。CLAUDE.md 是你寫的規則：怎麼跑測試、哪些事不准做、推不出來的專案事實。Auto memory 是 Claude 自己寫的筆記：你的偏好、你給過的糾正。兩者都在 session 開始時載入。

記憶有成本。每一行常駐內容，之後每一圈 loop 都要再送一次。過期的記憶比沒有記憶更糟，因為它會誤導 agent。所以 slide 建議把記憶當程式碼管理：review、刪減、放進版本控制。

四種擴充機制，各管一件事 p.33–50

內建的 tool（Read、Search、Edit、Shell 等）讓 agent 能動手。要擴充能力，有四種機制：skill 教 agent 怎麼做一件事；MCP 讓 agent 碰得到外部系統；hook 在特定事件發生時執行程式；plugin 把前三者打包，讓別人一個指令就能安裝。

最重要的差別：skill 和 MCP 都要等 model 決定使用，hook 不用。Model 的判斷是機率性的，hook 是確定性的。所以「一定要發生」或「一定不能發生」的事，要交給 hook 或權限設定，不要只寫在 CLAUDE.md。

3 · 觀念補充

Slide 預設你已經懂的背景

Prefix cache每圈重送 context 為什麼還負擔得起

Provider 會暫存 prompt 開頭那一段的計算結果。下一個 request 只要開頭完全相同，那一段就直接讀快取，不必重算。讀快取的價格約是一般 input 的十分之一，部分 model 更低（L8 會細算）。

代價是：開頭只要改一個字，後面全部要重算。所以 system prompt、tool 定義、CLAUDE.md 放在最前面，而且不要常改。

機率性與確定性規則寫在哪裡才擋得住

寫在 prompt 或 CLAUDE.md 的規則，是對 model 的要求。Model 大多會照做，但沒有保證。Hook、權限設定、CI 檢查是程式，條件成立就一定執行。

設計 agent 時，先分清楚兩類規則：可以「大多數時候遵守」的，和必須「每次都遵守」的。後者要放進程式。

漸進載入progressive disclosure

Skill 和 MCP 一開始只把名稱和描述放進 context，用到時才載入全文 p.8。這和作業系統的 lazy loading 是同一個想法：先放索引，需要時才讀進來。L1 把 context window 比喻成 RAM；這個做法就是在節省 RAM。

Prompt injectiontool 輸出也是攻擊面

Agent 讀進來的網頁、檔案、MCP 回傳的結果，都會變成 context 裡的文字。文字裡如果藏著「忽略之前的指示…」，model 可能照做。這種攻擊叫 prompt injection。

對策：把 tool 輸出當資料，不當指令；危險動作一律經過權限檢查；MCP 的 token 只給最小權限 p.57。

N×M 整合問題MCP 為什麼需要標準協定

沒有標準時，N 個 AI app 要接 M 個服務，就要寫 N×M 套整合。有了 MCP，每個 app 只實作一次 client，每個服務只提供一次 server p.53。LSP 用同樣的方法，解決編輯器和程式語言之間的整合。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

產品差異在 harness，不只在 model

這堂拆出來的 loop、權限、記憶、擴充機制，全部屬於 harness。L4 會看到一個實驗：model 不變，只改 harness，在小 context window 的設定下，SWE-bench 的解題數接近翻倍。

所以比較兩個 agent 時，要把 model 和 harness 分開看。一個簡單的做法是 2×2 實驗：兩個 model 乘上兩個 harness，看差異來自哪一邊。

CLAUDE.md 會累積技術債

團隊一起用 agent 時，CLAUDE.md 會不斷變長：每個人遇到問題，就加一條規則。規則之間開始矛盾，過期的規則沒人刪。官方文件說，規則矛盾時，Claude 可能任選一條。

所以 CLAUDE.md 需要負責人，也需要 review，和程式碼一樣走 PR。也可以定期用 /doctor 檢查，找出不該放在裡面的內容。

自主程度要配合風險

權限模式是一條光譜：每步都問（manual）、自動同意編輯（acceptEdits）、交給另一個 model 判斷（auto）、完全不問（bypass）。越往後越快，出錯時的代價也越大。

L3 的原則是「自主程度配合風險」。碰到正式資料或受監管的環境，用 hook 和權限設定守住底線，比相信 model 的判斷可靠。

記憶也是攻擊面

Auto memory 會把對話內容寫進檔案，下次自動載入。Agent 如果讀到惡意內容並記下來，攻擊就會延續到之後的 session。L6 把這叫 persistent prompt injection。

所以記憶要能檢查、能刪除。用 /memory 可以瀏覽、修改或關閉 auto memory。

  1. p.7–11 · Agent loop

    你輸入一個 prompt 之後，Claude Code 重複做哪三件事？重複到什麼時候才停？Model 和 harness 各負責哪一部分？

    參考答案

    三件事：收集 context、產生下一個 action、執行 tool。每一步的輸入是上一步的結果，直到 model 判斷任務完成。

    Model 只輸出文字，決定下一步，例如提議 Bash("pytest")。Harness（Claude Code 這個程式）組 context、檢查權限、呼叫 tool，再把結果放回 context。p.11 的例子有 5 次 tool 執行、6 次 inference。

  2. p.8–9 · Context 的起點

    你還沒打第一個字，context 裡已經有哪些東西？Claude Code 為什麼不把整個 repo 送給 model，它怎麼拿到需要的程式碼？

    參考答案

    已經有 10,000 個以上的 token：系統指令、專案資訊、CLAUDE.md 與 memory、tool 定義，以及 skill 與 MCP 的名稱和描述。Skill 和 MCP 的完整內容要等 model 決定用時才載入（progressive disclosure）。

    Repo 可能有幾千個檔案，遠大於 context window。Repo 留在磁碟上，model 用 Grep、Read 這類 tool 按需取一小片。所以 agent 只知道它讀過的部分。

  3. p.12 · 權限

    權限檢查發生在哪兩個步驟之間？四種權限模式差在哪裡？Slide 建議什麼情況才用 bypass？

    參考答案

    在「model 提議」和「harness 執行」之間。Tool call 只是提案，要先通過檢查，結果是 allowed、ask 或 denied。

    Manual 每個動作都問；Accept Edits 自動同意檔案編輯，其他仍問；Bypass 全部放行；Auto 由一個小 model 判斷。Bypass 在 model 判斷錯誤時沒有任何防線，所以只在可丟棄的環境（container、VM）裡用。

  4. p.16 · Compaction

    Context 快滿時會發生什麼事？這個動作會丟掉什麼？哪個檔案在這之後會重新載入，這對你寫規則有什麼意義？

    參考答案

    Claude Code 把舊的過程摘要起來，這叫 compaction。它是有損的，摘要會丟掉細節，包括你在對話裡講過的規則。

    CLAUDE.md 在 compaction 後會重新載入。所以重要的規則要寫進 CLAUDE.md，不要只在對話裡說一次。

  5. p.20–23 · 兩種記憶

    Agent 的記憶分哪兩種？CLAUDE.md 和 auto memory 各由誰寫、適合放什麼？它們能不能「強制」agent 做某件事？

    參考答案

    Context 是 working memory，session 結束就消失；persistent memory 存在檔案裡，下個 session 再載入。LLM 本身每次呼叫都從零開始。

    CLAUDE.md 由你寫，放指令、硬規則、難推得的事實。Auto memory 由 Claude 自己寫，放你的偏好、你給的糾正、專案背景。兩者都只是 context，model 可能沒照做；要一定擋下，用 hook。

  6. p.24–26 · CLAUDE.md 的層級

    CLAUDE.md 有哪四個層級？它們互相覆蓋，還是全部串接？CLAUDE.md 太長時該怎麼拆，paths: 有什麼作用？

    參考答案

    Managed policy（組織）、user（~/.claude/CLAUDE.md）、project（./CLAUDE.md）、local（./CLAUDE.local.md）。它們不互相覆蓋，全部串接進 context；範圍最大的先載入，離你最近的最後讀。

    太長時拆到 .claude/rules/，一個主題一個檔。加上 paths: 的 rule，只在 Claude 讀寫符合條件的檔案時才載入；沒有 paths: 的每個 session 都載入。

  7. p.35–36、p.43 · 四種擴充機制

    Skill、MCP、hook、plugin 各解決什麼問題？四種裡哪一種不需要 model「決定使用」就會執行？為什麼這件事重要？

    參考答案

    Skill 放做事的程序與知識；MCP 連到外部資料與動作；hook 在生命週期事件上自動執行；plugin 負責打包與發佈。

    只有 hook 綁在事件上，不需要 model 同意。Skill 和 MCP 都要等 model 決定使用才生效。所以必須強制的規則要用 hook，例如 PreToolUse 擋下某個指令。

  8. p.50 · 設計練習

    「每次編輯後自動格式化」「從 Jira 讀一張 issue」「禁止寫入 production」各該用哪一種機制？先自己判斷，再看 slide 的答案。

    參考答案

    自動格式化用 hook：綁在「編輯完成」這個事件，每次都要發生。讀 Jira 用 MCP：要碰外部系統。禁止寫入 production 用 hook 或 policy：必須強制，不能靠 model 記得。

    判斷順序：要強制嗎？用 hook。要碰外部嗎？用 MCP。要分享嗎？用 plugin。其餘是程序與知識，用 skill。

  1. 概念 · Agent loop · p.7–17

    用一個具體例子，說明一個 prompt 在 Claude Code 裡從輸入到完成的過程。哪些步驟由 model 決定，哪些由 harness 執行？

    情境：你在一個 Python 專案裡輸入「修好 tests/test_auth.py 失敗的測試」。

    回答時請涵蓋
    • 依序列出每一圈 loop：model 提議什麼、harness 做了什麼、什麼結果放回 context。
    • 指出至少兩個可能出錯的地方，以及哪一層會擋下錯誤（model、權限、hook、測試）。
    • 估計這一輪至少有幾次 model inference，並說明理由。
    思考方向

    先畫出 p.11 的鏈：prompt → M₁ → T₁ → M₂ → … → 回答。再把 p.10 和 p.12 疊上去：每個 tool 執行前，都有一次權限檢查。

    可能出錯的地方：讀錯檔案、改錯位置、沒跑測試就宣稱完成。最後一種在 L6 叫 unverified success。

    參考觀點與追問
    • 典型過程：跑 pytest 看錯誤 → 讀測試和相關程式 → grep 呼叫點 → 修改 → 再跑 pytest → 通過後回報。每次 tool 之前有一次 inference，最後回報再一次，所以 5 次 tool 至少 6 次 inference。
    • Model 決定：讀哪個檔、怎麼改、什麼時候停。Harness 執行：檢查權限、跑指令、把輸出放回 context、context 太大時 compaction。
    • 擋錯的層次：權限擋危險指令；hook 擋違反規則的編輯；測試擋錯誤的修改。「沒驗證就宣稱完成」要靠 Stop hook 檢查，或要求附上測試輸出（p.43 的「結束前確認測試」）。
    • 三種常見錯誤：沒讀測試對應的程式就修改；改測試的期望值來讓測試通過；只跑一個測試檔，弄壞別的測試。對策：CLAUDE.md 寫明「不改測試的期望值」，並要求最後跑整套測試。

    追問：測試要跑 20 分鐘時，loop 會變成什麼樣子？Model 只看得到 context；哪些資訊不在 context 裡，卻會影響修改是否正確？

  2. 估算 · Context 與成本 · p.8、p.16

    估算一個 50 步的任務，總共送出多少 input token，以及 prefix cache 大約能省下多少。

    情境：固定內容（system prompt、tool 定義、CLAUDE.md）共 15k token。每一步新增約 2k token（model 回覆加 tool 結果）。不考慮 compaction 和 output token。

    回答時請涵蓋
    • 寫出計算方式和結果。
    • 假設 cache read 的價格是一般 input 的 0.1 倍，估算省下的比例。
    • 提出兩個降低成本的做法，並說明各自的代價。
    思考方向

    第 k 步送出的 context 是 15k + 2k×（k−1）。把 50 步加總。有 prefix cache 時，每一步只有新增的部分是新內容，其他都是上一步送過的前綴。

    參考觀點與追問
    • 總 input：k = 1…50 加總 15k + 2k×（k−1），得到 750k + 2,450k，約 3.2M token。
    • 新內容約 15k + 49×2k ≈ 113k token，其餘約 3.09M 是 cache read。以 0.1 倍計價，約等於 422k 個一般 input token，省下約 87%。Cache 寫入另有加價（約 1.25 倍），算進去約省 86%。
    • 這也解釋了 p.16 的「大部分成本來自 cache read」。L8 的課堂資料顯示，cache read 佔所有 token 的 97.6%。
    • 降成本的做法：先規劃再批次執行，減少步數（代價：規劃本身要花 token）；tool 只回傳必要的輸出（代價：可能漏資訊）；保持前綴穩定（代價：不能隨意改 system prompt）。

    追問：第 30 步發生 compaction，context 從約 73k 壓到 20k，之後的成本怎麼變？有什麼隱藏代價？（提示：L8 p.26 說，compaction 丟掉的檔案，agent 之後要重讀；摘要也會讓 cache 重寫。）

  3. 設計 · 規則放在哪裡 · p.22–26、p.43

    下面 5 條規則，各該放在 CLAUDE.md、.claude/rules/、hook、權限設定，還是 CI？說明理由。

    情境：（a）測試一律用 pytest -x。（b）不准修改 gen/ 底下的生成檔。（c）API 的錯誤回傳格式要一致。（d）不准把 secret 寫進 log 或 commit。（e）只有 migration 檔案要遵守的命名規則。

    回答時請涵蓋
    • 每一條給出選擇和一句理由。
    • 說明你用什麼標準，區分「建議」和「必須」。
    • 指出哪一條需要兩層保護，並說明原因。
    思考方向

    依序問三個問題。違反時，後果是品質變差，還是出事？規則和所有檔案有關，還是只和部分檔案有關？它只約束 agent，還是也要約束人？

    參考觀點與追問
    • （a）CLAUDE.md：每個 session 都需要；違反了只是慢一點。
    • （b）PreToolUse hook 擋 Edit 與 Write：違反會破壞生成流程，必須每次擋下（第 6 段有範例）。
    • （c）.claude/rules/，用 paths 指向 API 目錄，再加 lint 或測試：這是品質規則，只和部分檔案有關。
    • （d）兩層：hook 或權限擋 agent 的動作，CI 的 secret 掃描擋所有人的 commit。後果嚴重，而且人也會犯錯。
    • （e）.claude/rules/ 加 paths：只在碰到 migration 時載入，平常不佔 context。

    追問：CLAUDE.md 已經 300 行時，你會先刪哪些內容（對照 p.25 的「不該放」）？Hook 本身寫錯了，會造成什麼問題？誰來 review hook?

  4. 團隊實務 · Memory · p.20–31

    Slide 說記憶要像程式碼一樣 review 和版本控制；但 auto memory 是 Claude 自己寫、只存在個人電腦上。在團隊裡，你會怎麼管理這兩者？

    情境：團隊 6 個人共用一個 repo。每個人的 Claude 都依自己的糾正，累積各自的 auto memory。

    回答時請涵蓋
    • Auto memory 在團隊裡的一個好處和一個風險，各舉一個例子。
    • 一條規則：什麼留在個人的 auto memory，什麼升級成 repo 裡的 CLAUDE.md。
    • 誰負責 review CLAUDE.md，多久清理一次。
    思考方向

    Auto memory 依 repo 分開，同一個 repo 的 worktree 共用，但只存在本機（p.27）。它適合個人偏好。團隊都該遵守的事放在本機，就會讓每個人的 agent 行為不一致。

    參考觀點與追問
    • 好處：個人習慣不用每次重講，例如常用的測試指令、回覆語言。風險：harness 會一直載入記錯或過期的內容；每個人的 agent 行為漂移；團隊無法 review。
    • 一條可行的規則：同一個糾正，第二個人也需要時，就升級成 CLAUDE.md 的規則，並走 PR。
    • CLAUDE.md 由 repo 的負責人 review，例如每個 sprint 檢查一次，刪掉過期或矛盾的規則。官方文件提醒：規則矛盾時，Claude 可能任選一條。
    • 個人用 /memory 定期檢查 auto memory。看到可疑內容，例如來自網頁的指示，就刪除，避免 persistent prompt injection（L6）。

    追問：新人加入時，他的 agent 沒有任何 auto memory。這是缺點還是優點？你會在什麼情況下關掉 auto memory?

  5. 風險 · 權限政策 · p.12、p.57

    為三種環境各訂一個權限政策：個人筆電開發、CI pipeline、會碰到正式資料的維運工作。

    情境：可選的模式有 manual、acceptEdits、plan、auto、bypass。也可以搭配 hook，以及 MCP token 的權限範圍。

    回答時請涵蓋
    • 每種環境選一個模式，並說明理由。
    • 你用什麼條件判斷「可以放寬」。
    • 至少一個不論哪種模式，都要用 hook 或權限硬擋的動作。
    思考方向

    從兩件事判斷：出錯時能不能復原，以及影響範圍有多大。可丟棄的環境可以放寬。會碰到正式資料或對外系統，就要收緊，並把關鍵動作做成確定性的檢查。

    參考觀點與追問
    • 個人筆電：auto 或 acceptEdits。出錯可以用 git 復原；但 push、大量刪檔、連外部系統仍然要確認。
    • CI：在用完即丟的 container 裡執行，搭配明確的 allowlist。官方文件的 CI 範例是 --permission-mode dontAsk 加 --allowedTools：清單外的動作一律不做。
    • 維運工作：manual 或 plan，先看計畫再執行。寫入動作用 hook 擋，或要求人工核准；MCP token 只給唯讀（p.57）。
    • 不論模式都要硬擋的例子：刪除正式資料、對外發布、把 secret 送出去。

    追問：Auto 模式由另一個 model 判斷；它判斷錯了，誰負責？你會怎麼稽核？Container 如果掛載了你的 ~/.ssh，還算可丟棄的環境嗎？

  6. 應用 · 擴充機制 · p.35–50

    挑一個你們團隊每週都會重複的工作流程，替它設計 skill、MCP、hook 與 plugin。

    情境：例如發版、處理 bug 單、整理測試報告、上線前檢查。選一個你熟悉的流程。

    回答時請涵蓋
    • 用表格列出：流程步驟、使用的機制、理由。
    • 指出哪一步必須用 hook 保證，以及它擋下什麼。
    • 說明這套設定怎麼分享給團隊，版本怎麼管理。
    思考方向

    照 p.37 的發版例子拆：程序寫成 skill；要碰 GitHub、Jira、Slack 的步驟用 MCP；必須保證的檢查用 hook；最後打包成 plugin。有副作用的 skill 要設成只能手動觸發。

    參考觀點與追問

    以「處理 bug 單」為例：

    • Skill /triage-bug：讀 bug 描述 → 找相關程式 → 重現 → 提出修正與測試 → 請人確認。因為會改程式，設 disable-model-invocation: true。
    • MCP：Jira 讀 bug 單、更新狀態；GitHub 開 PR。Token 只給這個專案需要的權限。
    • Hook：PostToolUse 在每次編輯後跑 formatter；Stop 前確認測試跑過；PreToolUse 擋下直接 push 到 main。
    • Plugin：把 skill、MCP 設定、hook 打包，放在團隊的 marketplace 或 repo，用版本號管理。

    追問：這套設定裡，哪一部分最容易過期？誰負責更新？不用 agent 時，這個流程今天卡在哪裡？Agent 真的解決了那個瓶頸嗎？

自我檢查

你說「修好登入測試」，Claude Code 執行了 5 次 tool。總共至少有幾次 model inference？為什麼後面的比前面的貴？

至少 6 次：每次 tool 前一次，最後回答一次。每次 inference 都送出完整的 context，而 context 每一步都變長。

你在 CLAUDE.md 寫了「不准修改 gen/」，Claude 還是改了。為什麼？怎麼改成一定擋得住？

CLAUDE.md 只是 context，model 可能沒照做。要強制，就用 PreToolUse hook：路徑在 gen/ 底下，就以 exit code 2 擋下（見第 6 段的範例）。

有一條規則只和資料庫 migration 有關。它該放在 CLAUDE.md，還是 .claude/rules/?

放在 .claude/rules/，用 paths: 指向 migration 目錄。Claude 碰到這些檔案時才載入，平常不佔 context。

6 · 動手試試

照著做一次

每個範例都依 2026 年 10 月的 Claude Code 官方文件。點開才會展開。

寫一份夠用的 CLAUDE.mdp.25–26

只放三類：指令、硬規則、推不出來的事實。新專案可以先跑 /init 產生初稿，再刪掉 model 本來就知道的內容。

只和某些檔案有關的規則，拆到 .claude/rules/，用 paths: 指定範圍。Claude 讀寫符合的檔案時，這條規則才載入。

用 hook 擋住對 gen/ 的修改p.43

Slide 上的五個時間點，官方事件名稱依序是 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop。下面用 PreToolUse 擋下對生成檔的修改。

Claude Code 從 stdin 把這次 tool call 的 JSON 傳給腳本。腳本以 exit code 2 結束，這次修改就不會執行；stderr 的內容會回給 Claude 當作原因。記得先執行 chmod +x .claude/hooks/block-gen.sh。腳本用到 jq。

寫一個只能手動觸發的 skillp.39–40

輸入 /release 2.4.0,$ARGUMENTS 會換成 2.4.0。disable-model-invocation: true 讓這個 skill 只能手動觸發。發布、部署這類有副作用的流程，都應該這樣設。

選一個權限模式啟動p.12

新版 Claude Code（v2.1.283 起）預設是 auto 模式：由另一個 model 判斷每個動作能不能執行。在 session 裡按 Shift+Tab 切換；也可以啟動時指定：

claude --permission-mode manual        # 改檔、跑指令、連網前先問你
claude --permission-mode acceptEdits   # 檔案編輯自動同意
claude --permission-mode plan          # 你核准計畫之前，不會改檔

Bypass 模式完全不問，只在可丟棄的環境用，例如 container 或 VM。
