先看這裡

這堂把 Claude Code 當成 agent 的標本，拆開來看。它回答三個問題：一個 prompt 背後發生什麼、agent 怎麼記住事情、怎麼擴充 agent 的能力。

  • Agent = model + loop。Model 只負責提議下一步。Harness（Claude Code 本身）負責執行、檢查權限、管理 context。
  • 記憶就是每次都會載入的檔案。它每一步都佔 context、都要付費，所以要精簡、要維護。
  • 要保證發生的事，用 hook。寫在 CLAUDE.md 的規則，model 可能沒照做；hook 是程式，事件發生就一定執行。

建議順序：先讀第 5 段的基礎題，帶著問題自己一頁一頁看完 slides；再回來讀這篇。核心觀念下面的「深入」區塊預設收合，看 slides 卡住時再展開。讀書會前用第 5 段的進階題。

1 · 架構

Claude Code 的零件怎麼接在一起

看這張圖，抓住一個重點：model 只負責「想」，所有「做」都經過 harness。Harness 每次呼叫 model 時，model 只看得到 context window 裡的東西。記憶、skill、tool 的定義，都是 harness 放進 context 的文字。Hook 不經過 model，它掛在 harness 執行 tool 的路徑上。

2 · 核心觀念

三個觀念串起整堂課

一個 prompt，很多圈 loop p.6–13

你打一個 prompt，Claude Code 會跑很多圈 loop。每一圈，harness 把整個 context 送給 model。Model 提議一個動作，例如跑 pytest。Harness 檢查權限，在你的電腦上執行，再把結果放回 context。Model 不再提議動作時，這一輪才結束。

這個結構有兩個後果。第一，成本和延遲隨圈數增加，因為每一圈都重送整個 context。第二，context 一直變大，快滿時就要 compaction，把舊的過程摘要起來。摘要會丟掉細節，所以重要的規則不能只靠對話記住。

深入｜一次 model 呼叫，實際送出什麼p.6–10

Slides 說「model 提議，harness 執行」，但沒有給你看資料長什麼樣子。看懂這個例子，整堂課大部分的機制就通了。Harness 每一圈送給 model 一個 request，大致如下。

Model 的回覆只有兩種：

  • 一個 tool_use（stop_reason: "tool_use"）。Harness 執行它，把 tool_result 接在 messages 最後，再送一次。
  • 純文字（stop_reason: "end_turn"）。Loop 結束。「model 不再提議動作」就是這個意思。

用這個例子對照 slides：

  • Stateless：API 沒有 session。「對話」只是 harness 手上的 messages list，每一圈都整包重送。
  • Tool call 只是結構化的文字：model 從 tools 清單挑一個名字，填上參數。真正執行的是 harness，所以 model 碰不到你的檔案（p.9）。
  • 成本隨圈數增加：messages 只會變長。p.10 那條鏈上，每一個 M 都比前一個長。
  • Token 的數量感：英文 1 token 約 0.75 個字，一行程式碼粗估 10 token 上下。p.7 的 10k token 約 7,500 個英文字，一份 15 頁的文件，每一圈都在這個 request 裡重送。
  • Prefix cache 有效的原因：每圈 request 的前段完全相同，只有最後面是新的。
  • p.14 的經典 agent 圖：LLM 是 model。Memory 是 system、messages 和記憶檔。Tools 是 tools。Observation 是 tool_result。
深入｜Agent 不會先讀完整個 repop.8

Claude Code 不替 repo 建 index。它用 Grep、Glob、Read 按需讀取。這種做法叫 agentic search。

另一種做法是 RAG：先把 repo 切成小塊，算出 embedding；提問時，用相似度找出最接近的片段。部分 IDE 型工具用這種做法。

Agentic searchRAG（embedding index）
事前準備不用要建 index；檔案改了要更新
讀到的內容磁碟上最新的檔案index 最後一次更新時的版本
搜尋條件model 依任務決定：關鍵字、檔名、呼叫點語意相似度
代價多跑幾圈 loop，多花 token 與時間可能撈到相似但無關的片段

兩者有同一個限制：agent 沒讀到的檔案，它就不知道。在 CLAUDE.md 寫目錄配置和地雷，就是替 agent 省掉幾圈搜尋，對應 p.17 的 Repeated discovery。

深入｜六種權限模式，什麼時候用哪一種p.11

實際的權限由兩部分組成：一份規則清單，加上模式。規則的寫法和比對順序（deny → ask → allow），見第 5 段基礎題第 1 題的重點複習。這裡補上模式：沒有規則符合時，由模式決定。Slide 只列了四種，實際有六種。

--permission-mode沒有規則符合時
default（manual 是別名）唯讀以外的動作，先問你。
acceptEdits檔案編輯自動同意；其他動作先問。
plan只讀不改。先交計畫，你核准後才動手。
auto讀檔和工作目錄內的編輯直接放行。其他動作交給另一個 classifier model 審查。

從 v2.1.283 起，終端機和 VS Code 的互動 session 預設從 auto 開始。

規則和 hook 都是確定性的，差別在能檢查什麼。規則只比對 tool 名稱和參數字串。要看內容、跑邏輯，例如掃描 diff 裡有沒有 secret，就用 hook。

Agent 的記憶，就是每次都會載入的檔案 p.14–26

Model 沒有狀態。它不記得上一個 session，也不記得上一圈 loop。Agent 看起來記得事情，是因為 harness 每次都把相關文字放進 context。

Claude Code 有兩套持久記憶。CLAUDE.md 是你寫的規則：怎麼跑測試、哪些事不准做、推不出來的專案事實。Auto memory 是 Claude 自己寫的筆記：你的偏好、你給過的糾正。兩者都在 session 開始時載入。

記憶有成本。每一行常駐內容，之後每一圈 loop 都要再送一次。過期的記憶比沒有記憶更糟，因為它會誤導 agent。所以 slide 建議把記憶當程式碼管理：review、刪減、放進版本控制。

深入｜每個設定檔放在哪裡p.18–25、p.41

Slides 把檔案位置分散在好幾頁。合起來是這張圖。

兩種檔案的合併方式不同。Slides 沒有講清楚這一點。

  • CLAUDE.md 全部串接：各層級的內容都進 context，彼此不覆蓋（p.20）。子目錄裡的 CLAUDE.md，等 Claude 碰到那個目錄的檔案才載入。
  • settings.json 有優先順序：上層的值蓋掉下層。由高到低是 managed policy、--settings、settings.local.json、.claude/settings.json、~/.claude/settings.json。permissions.allow 這類清單例外，它們會合併。
深入｜什麼時候放進 context？放進去之後呢？p.7、p.12、p.23–24

這個問題要拆成兩半來看。

放進去之後，每一圈都重送。所有東西都一樣。API 沒有狀態，harness 每一圈都把整個 context 重送一次。一段文字只要進了 context，每一圈都付一次租金（p.26），直到 compaction 或 /clear 清掉它。

真正的差別，在第一次放進去的時間點。共有三種：

時間點內容
Session 開始（第一個 request 就有）system prompt、內建 tool 定義、CLAUDE.md、沒有 paths 的 rules、MEMORY.md 前 200 行、skill description、MCP tool 名稱
中途觸發才放（接在 messages 最後面）讀到的檔案、有 paths 的 rule、skill body、memory topic 檔、MCP tool 的完整 schema
從不放進去hook 程式本身（只有它的輸出有時會進來）、subagent 的過程（只回來一段摘要）

開始時放的東西，在 request 裡的位置也不一樣：

  • System prompt 在 system 欄位。
  • Tool 定義在 tools 欄位。
  • CLAUDE.md 和 MEMORY.md 在 messages 開頭，是一則 user message。官方文件明說 CLAUDE.md 不屬於 system prompt。對 model 來說，它就是一段讀到的文字，所以只算建議。

位置的差別，要到 compaction 時才看得出來。Compaction 只摘要 messages：

東西Compaction 之後
System prompt、tool 定義不在 messages 裡，不受影響
根目錄 CLAUDE.md、auto memory 索引跟著摘要掉；Claude Code 從磁碟重讀，再放回去
有 paths 的 rule、子目錄 CLAUDE.md摘要掉；下次碰到符合的檔案才重新載入
用過的 skill body放回去，每個最多 5,000 token
讀過的檔案只重讀最近修改的 5 個
Skill description 清單不重放；只保留用過的 skill

還有一個 cache 的細節。開始時放的東西在最前面，中途載入的東西接在最後面。接在後面不會改到前段，所以 prefix cache 仍然有效。

深入｜Auto memory 什麼時候寫、寫成什麼樣p.23–24

CLAUDE.md 和 auto memory 的比較表，見第 5 段基礎題第 3 題的重點複習。這裡補上 auto memory 的實際運作。

Auto memory 什麼時候寫？Claude 判斷「下次對話還用不用得到」。它不會每個 session 都寫。程式碼裡讀得到的事，它不記，例如架構、檔案路徑。CLAUDE.md 已經寫的事，它也不記。

Auto memory 會一直累積，沒有人天天整理。所以它用索引控制大小：

  • MEMORY.md 是目錄，一行一條。每次只載入前 200 行或 25KB。快到上限時，Claude Code 提醒 Claude 縮短它：合併相近的條目、刪掉過期的、把細節移到 topic 檔。超過上限的部分，下次不會載入。
  • Topic 檔一條 memory 一個檔，開始時不載入。Claude 需要時，用一般的 Read tool 去讀。
  • CLAUDE.md 沒有這個機制，整份載入。它由人維護，所以假設人會讓它保持精簡。

兩者最大的差別是誰看得到。第 5 段進階題第 4 題問的就是這件事：哪些個人筆記，該升級成團隊規則。

四種擴充機制，各管一件事 p.28–42

內建的 tool（Read、Search、Edit、Shell 等）讓 agent 能動手。要擴充能力，有四種機制：skill 教 agent 怎麼做一件事；MCP 讓 agent 碰得到外部系統；hook 在特定事件發生時執行程式；plugin 把前三者打包，讓別人一個指令就能安裝。

最重要的差別：skill 和 MCP 都要等 model 決定使用，hook 不用。Model 的判斷是機率性的，hook 是確定性的。所以「一定要發生」或「一定不能發生」的事，要交給 hook 或權限設定，不要只寫在 CLAUDE.md。

深入｜都是 lazy loading 嗎？看誰觸發載入p.7、p.24、p.35

Skill、auto memory、MCP tool 用同一個模式：常駐一份小索引，完整內容用到才載入。這和作業系統的 demand paging 一樣：page table 常駐，page 用到才讀進記憶體。

內建 tool 是例外。Read、Edit、Bash 的完整定義一直都在。只有 MCP tool 預設延後載入：開始時只放名稱，要用時才透過 tool search 載入完整 schema。

機制常駐的索引按需載入的內容誰觸發
Skillname + descriptionSKILL.md body、references/Model 判斷，或你輸入 /name
Auto memoryMEMORY.md 前 200 行Topic 檔Model 判斷，用 Read 去讀
MCP toolTool 名稱完整 schemaModel 判斷，用 tool search
有 paths 的 rule沒有索引Rule 全文Harness：讀寫到符合的檔案就載入
子目錄 CLAUDE.md沒有索引全文Harness：碰到那個目錄的檔案就載入

誰觸發，決定可靠度。由 model 觸發的載入是機率性的：model 可能沒想到要載入某個 skill 或某條 memory。由 harness 觸發的載入是確定性的。所以「改 migration 時一定要遵守」的規則，要寫成有 paths 的 rule，不要做成 skill。

Lazy loading 只是延後付租金。內容一旦載入，就留在 messages 裡，之後每一圈都重送，直到 compaction。它省下的是沒用到的那些內容。

深入｜Subagent：開一個新的 contextp.28、p.39

p.28 只寫了「回傳摘要的 tool」。它的運作方式如下：

  • 主 agent 呼叫 Agent tool，和呼叫 Read 一樣。參數是一段任務描述。
  • Harness 開一個新的 loop。它有自己全新的 context window、自己的 system prompt 和 tool 權限。
  • Subagent 自己跑很多圈，例如讀 30 個檔案。結束時只回傳最後一段文字，所以主 context 只多這一段。
  • 用途：大量搜尋、平行探索、把雜訊隔離在外面。內建的 Explore 是一個唯讀的搜尋 subagent。
  • 代價：細節留在 subagent 裡。摘要寫錯了，主 agent 也無從檢查。

深入｜Skill 和 CLAUDE.md 怎麼選p.33–35

先問一個問題：十次任務裡，有幾次用得到這段內容？大多數都用得到，就放 CLAUDE.md。只有某類任務用得到，就做成 skill。

description 決定 model 會不會選用這個 skill。它要同時寫「做什麼」和「什麼時候用」：

# ✗ 太短：model 不知道什麼時候該用
description: Release helper

# ✓ 寫出做什麼、什麼時候用
description: Prepare and publish a release. Use when the user asks to cut, tag, or publish a version.
  • 設了 disable-model-invocation: true，連 description 都不常駐。只有你輸入 /release 時才載入。
  • Skill 可以附 scripts/。Model 讀完 SKILL.md，用 Bash 執行裡面的程式（p.34）。固定的步驟交給程式，例如解析 log、轉換格式。這樣 model 不用每次重新推理。
  • 舊的 .claude/commands/ 已經併入 skill。.claude/commands/deploy.md 和 .claude/skills/deploy/SKILL.md 都會產生 /deploy。新寫的請用 skill。
深入｜MCP server 實際上是什麼p.36–37；選讀 p.45–52

MCP server 是一個程式，有兩種跑法。本機 process（stdio）由 Claude Code 啟動，透過 stdin 和 stdout 交換訊息。遠端服務（HTTP）則是 Claude Code 連到一個 URL。

# 本機 stdio server：-- 後面是啟動它的指令（遠端 HTTP 的例子見基礎題第 5 題）
claude mcp add --env AIRTABLE_API_KEY=xxx --transport stdio airtable -- npx -y airtable-mcp-server

# 加上 --scope project，設定會寫進 repo 的 .mcp.json，全隊共用
  • 對 model 來說，MCP tool 和 Read、Bash 沒有差別。它只是 tools 清單裡的一項，名稱像 mcp__github__create_issue。差別在 harness：harness 把呼叫轉給 MCP server 執行（p.37）。
  • 為什麼不直接用 Bash 跑 gh issue create？這樣也可以，而且常常更省 token。MCP 的價值在四個地方：沒有 CLI 的服務、統一的認證與權限範圍、結構化的輸入輸出、集中管理。代價是 tool 定義要佔 context，所以 Claude Code 預設用 tool search 延後載入。

選讀頁的四個重點：

  • 四個角色（p.46）：host 是你用的 app。Host 為每個 server 開一條 MCP client 連線。Server 把一個外部系統包成 tool。
  • 三種元件（p.47）：tools 由 model 決定呼叫。Resources 是可讀的資料，由 host 附加。Prompts 是流程範本，由使用者觸發，在 Claude Code 裡變成 slash command。
  • Gateway（p.50–51）：它是 MCP 版的 API gateway。對 client 來說，它看起來就是一個 server，後面再接很多 server。認證、權限政策、稽核 log 都集中在這一層。
  • 2026-07-28 新規格（p.52）：server 不再保存 session，所以可以放在一般的 load balancer 後面水平擴展。

  • 同一個 repo 的團隊：把 .claude/ 和 CLAUDE.md commit 進 repo 就夠了。
  • 好幾個 repo 要共用同一套 skill、hook、MCP 設定：這時才需要 plugin。

p.42 設計練習的判斷順序：

  1. 必須強制的事：用 hook 或權限。
  2. 要碰外部系統：用 MCP。
  3. 要分享給別人：用 plugin。
  4. 每次都要知道的事：寫進 CLAUDE.md。
  5. 其他程序與知識：做成 skill。

3 · 觀念補充

Slide 預設你已經懂的背景

Prefix cache每圈重送 context 為什麼還負擔得起

Provider 會暫存 prompt 開頭那一段的計算結果。下一個 request 只要開頭完全相同，那一段就直接讀快取，不必重算。讀快取的價格約是一般 input 的十分之一，部分 model 更低（L8 會細算）。

代價是：開頭只要改一個字，後面全部要重算。所以 system prompt、tool 定義、CLAUDE.md 放在最前面，而且不要常改。

機率性與確定性規則寫在哪裡才擋得住

寫在 prompt 或 CLAUDE.md 的規則，是對 model 的要求。Model 大多會照做，但沒有保證。Hook、權限設定、CI 檢查是程式，條件成立就一定執行。

設計 agent 時，先分清楚兩類規則：可以「大多數時候遵守」的，和必須「每次都遵守」的。後者要放進程式。

漸進載入progressive disclosure

Skill 和 MCP 一開始只把名稱和描述放進 context，用到時才載入全文 p.7。這和作業系統的 lazy loading 是同一個想法：先放索引，需要時才讀進來。L1 把 context window 比喻成 RAM；這個做法就是在節省 RAM。

Prompt injectiontool 輸出也是攻擊面

Agent 讀進來的網頁、檔案、MCP 回傳的結果，都會變成 context 裡的文字。文字裡如果藏著「忽略之前的指示…」，model 可能照做。這種攻擊叫 prompt injection。

對策：把 tool 輸出當資料，不當指令；危險動作一律經過權限檢查；MCP 的 token 只給最小權限 p.49。

N×M 整合問題MCP 為什麼需要標準協定

沒有標準時，N 個 AI app 要接 M 個服務，就要寫 N×M 套整合。有了 MCP，每個 app 只實作一次 client，每個服務只提供一次 server p.45。LSP 用同樣的方法，解決編輯器和程式語言之間的整合。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

產品差異在 harness，不只在 model

這堂拆出來的 loop、權限、記憶、擴充機制，全部屬於 harness。L4 會看到一個實驗：model 不變，只改 harness，在小 context window 的設定下，SWE-bench 的解題數接近翻倍。

所以比較兩個 agent 時，要把 model 和 harness 分開看。一個簡單的做法是 2×2 實驗：兩個 model 乘上兩個 harness，看差異來自哪一邊。

CLAUDE.md 會累積技術債

團隊一起用 agent 時，CLAUDE.md 會不斷變長：每個人遇到問題，就加一條規則。規則之間開始矛盾，過期的規則沒人刪。官方文件說，規則矛盾時，Claude 可能任選一條。

所以 CLAUDE.md 需要負責人，也需要 review，和程式碼一樣走 PR。也可以定期用 /doctor 檢查，找出不該放在裡面的內容。

自主程度要配合風險

權限模式是一條光譜：每步都問（manual）、自動同意編輯（acceptEdits）、交給另一個 model 判斷（auto）、完全不問（bypass）。越往後越快，出錯時的代價也越大。

L3 的原則是「自主程度配合風險」。碰到正式資料或受監管的環境，用 hook 和權限設定守住底線，比相信 model 的判斷可靠。

記憶也是攻擊面

Auto memory 會把對話內容寫進檔案，下次自動載入。Agent 如果讀到惡意內容並記下來，攻擊就會延續到之後的 session。L6 把這叫 persistent prompt injection。

所以記憶要能檢查、能刪除。用 /memory 可以瀏覽、修改或關閉 auto memory。

  1. p.6–11 · Agent loop

    Agentic loop 每一圈做哪三件事？Model 提議的 tool call，為什麼不會直接執行？

    參考答案與重點複習

    答案：每一圈做三件事：收集 context、產生下一個 action、執行 tool（p.6）。Model 只發出請求，例如 Bash("pytest")；harness 檢查權限後才執行（p.9）。p.11 說 tool call 只是提案，要經過你或另一個 model 同意。檢查結果有三種：allowed、ask、denied。

    重點拆解

    一個 prompt 不是一次 request。p.10 把它畫成一條鏈：inference → tool → inference → tool → … → 回答。修一個失敗的測試，可能依序是：跑 pytest、讀 session.py、grep create_session、改 session.py、再跑 pytest、回報全部通過。每次 tool 之前有一次 inference，最後的回答再一次。

    三件事由兩個角色分工。產生 action 由 model 做；收集 context 和執行 tool 由 harness 做。Model 的輸出只是一段結構化文字：tool 名稱加參數。真正碰到檔案和 shell 的，只有 harness。

    權限檢查夾在「提議」和「執行」之間（p.11）。同一個 Bash("rm -rf build/")，結果由模式和規則決定。Manual 模式先問你；acceptEdits 自動同意檔案編輯；auto 交給另一個 model 判斷；bypass 完全不問。結果是 denied 時，指令不會執行，拒絕的原因放回 context。Model 下一圈可以換一個做法。

    背景補充

    Model 不能自己執行，是架構決定的。Model 跑在 provider 的 GPU 上，它只輸出 token。各家 LLM API 的 tool use（也叫 function calling）都是同一個模式：API 回傳「想呼叫哪個 tool、帶什麼參數」，由呼叫 API 的程式決定要不要執行。Claude Code 就是這個程式，所以 harness 是唯一能放檢查點的地方。

    除了模式，你還可以寫規則，放在 .claude/settings.json 的 permissions。判斷順序是 deny → ask → allow，先符合的生效。所以 deny 規則一定贏過 allow 規則。

    常見誤解

    「Auto 模式就是不檢查。」不對。Auto 模式仍然會檢查，只是改由另一個 model 判斷，平常不問你。完全不檢查的是 bypass，只適合 container 或 VM 這類可丟棄的環境。新版 Claude Code 預設就是 auto，所以更要知道它在做什麼。

    例子

    這樣設定後，npm script 和 git commit 不再問你；開頭是 git push 的指令一律拒絕。沒有符合任何規則的動作，照目前的模式處理。

    帶走這幾點
    1. 一圈 = 收集 context → model 提議 → harness 執行；一個 prompt 會跑很多圈。
    2. Model 只輸出提案，能碰到你電腦的只有 harness → 權限檢查放在 harness。
    3. 檢查結果三種：allowed 執行、ask 先問你、denied 不執行，並把原因放回 context。

    相關：核心觀念〈一個 prompt，很多圈 loop〉；延伸思考〈自主程度要配合風險〉；第 6 段〈選一個權限模式啟動〉。進階題第 1 題逐圈拆解一輪 loop；第 5 題替三種環境訂權限政策。

  2. p.7–12 · Context 的大小

    還沒打字時，context 已有多少 token、來自哪裡？快滿時，Claude Code 怎麼處理？

    參考答案與重點複習

    答案：還沒打字，context 已經有 10,000 個以上的 token。它們來自系統指令、專案資訊、memory、tool 定義，以及 skill 和 MCP 的名稱與描述（p.7）。快滿時，Claude Code 做 compaction：摘要舊的 trajectory，再重新放入 CLAUDE.md 和 memory（p.12）。

    重點拆解

    這 10k+ 是固定內容，每次 inference 都要整包送出。其中 tool 定義列出 Read、Edit、Bash、Glob、Grep、Web、Agent 等 tool。每個 tool 都要寫清楚名稱、用途和參數格式，model 才知道怎麼呼叫。Skill 和 MCP 只放名稱與描述；全文要等用到時才載入（p.7）。例如一個 api-conventions skill，常駐的只有名稱和一句描述「REST API design conventions」；裡面的規則清單，要等 Claude 用到才讀進來。

    Repo 不會整份送出（p.8）。Repo 留在磁碟上，Claude 用 Grep 或 Read 按需拉一小段。所以 context 變大，是 agent 自己的動作造成的：每一步都加上 model 回覆、檔案內容、指令輸出（p.12）。讀一個大檔，或跑一個輸出很長的測試，context 一次就增加很多。

    p.12 說常見的 context window 是 1M token；今年稍早常見的是 256K。快滿時，harness 做 compaction。舊的過程變成一段摘要，空間就釋放出來。CLAUDE.md 和 memory 從檔案重新放入，因為它們每一圈都要在。代價是摘要會丟細節：只在對話裡交代過的事，可能就不見了。

    背景補充

    每一圈都重送整個 context，還負擔得起，是因為 prefix cache。Provider 會快取開頭相同的那一段；讀快取的價格約是一般 input 的十分之一。但 context 越長、圈數越多，讀快取的量就越大。所以 p.12 說，大部分成本來自 prefix cache 的讀取。

    Context 長也會影響品質。Claude Code 的官方文件提醒：context 越滿，model 越容易漏掉前面的指示，也更容易出錯。L4 的 lost in the middle 是同一個現象：放在長 context 中段的資訊，model 比較難用到。

    常見誤解

    「Context window 有 1M token，就不用管 context。」不對。第一，每一步都重送整個 context，成本跟著長度增加。第二，context 越滿，指示越容易被忽略。第三，compaction 會丟細節。上限大，只代表比較晚才需要 compaction。

    例子

    要在 compaction 之後還留著的規則，寫進 CLAUDE.md，不要只在對話裡講。

    帶走這幾點
    1. 還沒打字就有 10k+ token：系統指令、tool 定義、CLAUDE.md、memory、skill 與 MCP 的描述 → 每次 inference 都要送。
    2. Repo 不會整份送出；context 變大，來自每一步的回覆、檔案內容、指令輸出。
    3. 快滿 → compaction：摘要舊過程，重新放入 CLAUDE.md 和 memory → 只在對話裡講的事會被摘要掉。

    相關：觀念補充〈Prefix cache〉、〈漸進載入〉；L4 Context 是有限資源、L4 Lost in the middle。進階題第 2 題用數字算 50 步的 input token 與 cache 省下的比例。

  3. p.16–19 · 兩種記憶

    Slide 說的 memory，實務上是什麼？CLAUDE.md 和 auto memory 差在哪裡？

    參考答案與重點複習

    答案：Agent 在兩次執行之間沒有狀態，每個 session 從零開始。實務上，memory 就是 session 開始時載入的檔案（p.16）。CLAUDE.md 由你寫，放指令與規則；auto memory 由 Claude 寫，放它學到的事與模式，例如你的偏好和糾正（p.19）。兩者每個 session 都會載入；auto memory 只載入前 200 行（25KB）。

    重點拆解

    p.16 把記憶分成兩種。Context 是 working memory：model 現在看得到的東西，session 結束就消失。Persistent memory 存在檔案裡，下一個 session 再載入。所以「agent 記得」的意思是：harness 每次都把同一份檔案放回 context。p.17 列出沒有記憶的四個問題：指示要一再重講、決定被忘記、同樣的東西要重新摸索、行為前後不一致。

    兩套記憶的差別，整理自 p.19、p.20、p.23：

    CLAUDE.mdAuto memory
    誰寫你Claude
    內容指令與規則：標準、流程、架構學到的事：你的偏好、糾正、專案背景
    位置組織、使用者（~/.claude/CLAUDE.md）、專案（./CLAUDE.md）、本機（./CLAUDE.local.md）~/.claude/projects/<project>/memory/，只在這台電腦
    載入每個 session，整份檔案每個 session，只載入索引的前 200 行（25KB）

    Auto memory 的目錄有一個索引 MEMORY.md，加上多個 topic file（p.23）。200 行的上限只套用在索引。Topic file 要用到時才讀：先看索引，找到相關主題，再讀那個檔案（p.24）。

    背景補充

    「索引常駐、內容按需讀取」和 skill 是同一個設計，也就是漸進載入。記憶可以存很多，每個 session 只付索引的成本。作業系統也是這樣：先載入目錄，需要時才讀檔案。

    CLAUDE.md 的專案層級放在 repo 裡，可以進 git，團隊一起 review。Auto memory 在每個人的電腦上，隊友讀不到。所以團隊要共用的規則，要寫進 CLAUDE.md。

    常見誤解

    「我糾正過 Claude，model 就學會了。」不對。Model 的權重沒有改變。Claude 只是把糾正寫進 auto memory 的檔案，下個 session 再放進 context。換一台電腦，或刪掉那個檔案，它就「忘了」。

    例子

    第一行，Claude 把這件事存進 auto memory。第二行，Claude 把規則寫進 CLAUDE.md。/memory 列出所有記憶檔案；你可以打開來改，也可以關掉 auto memory。

    帶走這幾點
    1. Model 沒有狀態 → memory 就是 session 開始時放進 context 的檔案。
    2. CLAUDE.md：你寫規則，可以進 git 讓團隊共用。Auto memory：Claude 記偏好與糾正，只在你的電腦。
    3. Auto memory 只有索引常駐（前 200 行／25KB），topic file 用到才讀 → 和 skill 一樣是漸進載入。

    相關：核心觀念〈Agent 的記憶，就是每次都會載入的檔案〉；觀念補充〈漸進載入〉；延伸思考〈記憶也是攻擊面〉；L6 Memory 是兩層。進階題第 4 題討論團隊怎麼管理這兩種記憶。

  4. p.21–26 · 記憶的成本

    CLAUDE.md 只該放哪種資訊？Slide 為什麼說常駐的 token 是「租金」？

    參考答案與重點複習

    答案：CLAUDE.md 只放三類：test、build、lint 的指令；硬規則，例如不准直接 commit 到 main；agent 無法便宜推得的事實。每個檔案控制在 200 行以內（p.21）。常駐的 token 像租金，因為每個 session 開始時都要再付一次（p.26）。它和任務搶同一個 context window，送出的每個 token 也都要付費。

    重點拆解

    p.21 也列了不該放的：一般的語言或框架知識、linter 已經強制的 style 規則、長篇說明、changelog、secret。判斷標準只有一個：不寫這一行，agent 會不會出錯？Model 本來就懂 Python；agent 讀一下 code 就知道用什麼框架。這些寫進去，只是付租金，換不到東西。

    CLAUDE.md 裡的一行處理
    - Test: pytest -x tests/指令，留下
    - Money is an integer in cents. Never use float.推不出來的事實，留下
    - Use 4 spaces for indentation.Linter 已經管，刪掉
    - This project uses FastAPI.讀 code 就知道，刪掉
    - Every component in src/ui/ needs a story file.只和部分檔案有關，移到 .claude/rules/

    為什麼叫「租金」：買東西付一次，租房子每個月都要付。CLAUDE.md 在每個 session 開始時放進 context，之後每一圈 loop 都跟著整個 context 重送。一行只寫一次，卻要付很多次。檔案太長時，p.22 建議拆到 .claude/rules/：加了 paths: 的規則，碰到符合的檔案才載入，平常不付租金。p.26 也提醒：過期的記憶會誤導 agent，所以要像程式碼一樣 review、刪減、做版本控制。

    背景補充

    Prefix cache 讓租金變便宜，但不是免費。CLAUDE.md 放在 context 的前段；它一改，後面的快取全部要重算，所以也不要常改。另外，用 @path 把內容 import 進來，不會省 context：被 import 的檔案也在啟動時載入。

    p.25 列了四個維護指令：/init 依專案結構產生初稿；/context 看實際載入了什麼；/memory 打開記憶檔來改；/doctor 會建議刪掉能從 codebase 推得的內容。

    常見誤解

    「CLAUDE.md 寫得越詳細，Claude 越聽話。」相反。官方文件說，檔案太長時，重要的規則會被淹沒，Claude 反而忽略它們。Claude 一再違反某條規則時，先檢查檔案是不是太長。

    例子

    假設 CLAUDE.md 有 2,000 token，一個 session 跑 50 圈。這份檔案共送出 2,000 × 50 = 100,000 token。第 1 圈照一般價格，之後 49 圈讀 prefix cache，以 0.1 倍計價：2,000 + 49 × 200 = 11,800，約等於 11,800 個一般 input token（不計 cache 寫入的加價）。刪掉一半沒用的內容，這份檔案的成本就少一半。

    帶走這幾點
    1. CLAUDE.md 只放指令、硬規則、推不出來的事實；每一行都問「不寫會出錯嗎？」。
    2. 常駐內容每個 session、每一圈都要付 → 是租金，不是一次性成本。
    3. 太長 → 規則被淹沒；只和部分檔案有關的規則，移到 .claude/rules/ 按需載入。

    相關：觀念補充〈Prefix cache〉；延伸思考〈CLAUDE.md 會累積技術債〉；第 6 段〈寫一份夠用的 CLAUDE.md〉；L8 成本是一串乘數。進階題第 3 題決定每條規則放在哪一層。

  5. p.30–31 · 四種擴充機制

    Skill、MCP、hook、plugin 各解決什麼問題？哪一種能在 loop 的任何階段擋下動作？

    參考答案與重點複習

    答案：Skill 管 agent 怎麼做一件事；MCP 管它碰得到哪些外部資料與動作；hook 管生命週期事件發生時自動做什麼；plugin 管打包與發佈（p.30）。能在任何階段擋下動作的是 hook：p.31 說 hook 能在 loop 的任何階段檢查、阻擋或反應。Skill 只提供知識與程序，MCP 只提供外部 tool。

    重點拆解

    p.30 強調四者不能互換。用 p.32 的發版流程看分工：照發版程序一步一步做，用 skill；在 GitHub 建立 release，用 MCP；測試沒過就禁止發布，用 hook；把整套設定分享給團隊，用 plugin。

    Skill 和 MCP 都要等 model 決定使用。Skill 的描述在 session 開始時載入；全文要等 skill 執行才載入（p.35）。所以有副作用的流程，例如發布，要設成只能手動觸發。MCP tool 和本地 tool 幾乎一樣：有名稱、描述、typed schema，只是跑在另一個 process（p.37）。協定只負責傳遞呼叫；要不要呼叫，仍由 agent 決定。

    Hook 不經過 model 的判斷。p.38 列出 hook 能觸發的事件：session 開始、使用者送出 prompt、tool 執行前、tool 執行後、結束前。Model 推理本身不是事件，所以沒有 hook。能「擋下」動作的是 tool 執行前的 hook：它先看到這次 tool call，拒絕時 tool 就不執行。

    背景補充

    Hook 和 git 的 pre-commit hook、web framework 的 middleware 是同一個想法：掛在固定的執行點，條件成立就執行，不需要誰記得。Plugin 像套件管理：一個指令安裝、固定版本、用 namespace 避免名稱衝突，再透過 marketplace 發佈（p.39）。

    常見誤解

    「在 skill 裡寫『發布前一定要跑測試』，就保證會跑。」不對。Skill 只是放進 context 的文字。就算你手動輸入 /release，照不照步驟做，仍由 model 決定。要保證，就用 hook：tool 執行前擋下發布，或結束前確認測試跑過。

新版 Claude Code（v2.1.283 起）預設是 auto 模式：由另一個 model 判斷每個動作能不能執行。在 session 裡按 Shift+Tab 切換；也可以啟動時指定：

claude --permission-mode manual        # 改檔、跑指令、連網前先問你
claude --permission-mode acceptEdits   # 檔案編輯自動同意
claude --permission-mode plan          # 你核准計畫之前，不會改檔

Bypass 模式完全不問，只在可丟棄的環境用，例如 container 或 VM。
