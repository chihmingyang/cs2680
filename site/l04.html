先看這裡

L2 從使用者的角度看 agent。這堂換成設計者的角度：loop 怎麼寫、給 model 哪些 tool、每一步讓 model 看到什麼。主線是一句話：model 只決定下一步，其他都是 harness 的工作。

  • Loop 很短，難在周邊。ReAct loop 寫成程式只有二十幾行。表現取決於 harness 的四項工作：組 context、寫 tool、驗證執行、管理結果。
  • Tool 的輸出就是 context。Tool 要少而正交、輸出精簡、錯誤要能教。只給 shell 解出 11.0%，為 model 設計的介面解出 18.0%。
  • Context 是有限資源。越長越貴、越慢、越不準。依序用 admission、offloading、transformation；compaction 有損且不可逆，留到最後。

1 · 架構

一個 loop，四項設計工作

第一張圖的重點：model 每一圈只做一個決定，其他四件事都在 model 之外。所以同一個 model 放進不同的 harness，表現會差很多。第二張圖把第 4 項工作拆開：context 有一個入口、一個外部儲存、一個會變長的中段，四種策略各守一個位置。

2 · 核心觀念

五個觀念串起整堂課

ReAct：推理要有 observation 來檢查 p.5–8

ReAct 讓 model 輪流做三件事：Thought、Action、Observation。只推理，沒有東西檢查推理，小錯誤會累積成自信的幻覺。只行動，背後沒有計畫，會重複同樣的動作。Observation 把真實的結果放回 context，修正想法。

寫成程式，Action 是 tool call，Observation 是 tool 結果，loop 只有二十幾行（第 6 段）。Model 每一圈只做一個決定：給出最終回答，或發出 tool call。其他事情都在 model 之外：組出 context、寫 tool 定義、驗證並執行、整理結果。

Tool 要為 model 設計：search、edit、shell 的取捨 p.9–27

Agent 看不到整個 repo，要靠 tool 找程式碼。Grep 不用建索引，但只比對字面：搜「timeout」找不到 deadline。Embedding 索引依意思找，repo map 依結構找，代價是索引要同步。LSP 能跟著 import 與別名走，代價是每種語言一個常駐 server。

改程式碼有四種方式，在 token 成本與穩健度之間取捨。整檔重寫每次都套得上，但輸出和檔案大小成正比，長檔會 drift。Unified diff 精簡，但 context 行過期就套不上。Search/replace 靠內容定位，輸出只和改動成正比；anchor 不唯一就失敗。AST 編輯構造上就合法，但只能做工具提供的操作。

Shell 是最強也最危險的 tool：能串接、碰得到網路與檔案系統，blast radius 等於 shell 本身。只給 shell 就好嗎？SWE-agent 的數據說不夠：只給 shell 解出 11.0%，為 model 設計的介面解出 18.0%。顯示整個檔案、保留完整歷史，都比預設差。所以 tool 設計的五條原則，都在管輸出怎麼進 context：少且正交、專用、省 token、錯誤要能教、預設冪等。

Prompt 技巧從簡單開始，夠用就停 p.29–42

八種技巧分三層。先用簡單的：zero-shot、few-shot、role。需要時加推理：chain-of-thought、tree-of-thought、self-consistency。最後才設計成系統：prompt chaining、meta prompting。每往下一層，token 與呼叫次數都增加，所以從上往下試。

每一種技巧都有「該換下一種」的訊號：規則講不清楚，加範例；任務有多個步驟，要 model 寫出步驟；答錯代價高，就取樣多次再投票。

這些建議有保存期限。新 model 在訓練時已經學會其中幾招；要 reasoning model「think step by step」沒有必要，有時反而有害。四條原則不會過期：從簡單開始、分段、具體精簡、大任務拆小。

Context 是有限資源：錢、延遲、注意力 p.43–47

Karpathy 的定義：context engineering 是「為下一步放進剛好需要的資訊」。重點在「下一步」：harness 每圈都要重新決定放什麼、拿掉什麼。Context 有三種成本。錢：每一步都重送整個 window。延遲：prompt 越長，prefill 越久，decode 也變慢。注意力：window 越滿，model 越難找回資訊。

兩組研究量化了注意力的成本。Context rot：輸入越長，準確率越低。Lost in the middle：答案放在 20 份文件的第 1 份，準確率 76%；第 10 份掉到 55%；第 20 份回到 71%。Agent 的 context 中間，正好是舊的 tool 結果。

四種策略有順序，harness 決定發揮多少 p.48–55

四種策略有先後順序。Admission 在門口把關：原始 DOM 48,000 token，擷取後只剩 900，答案相同。Offloading 讓內容留在外面但拿得到：60 個 tool schema 要 42,000 token，改成索引加 3 個只要 3,100。Transformation 刪掉過期或重複的舊內容：96,000 變 24,000。Compaction 用 LLM 寫摘要，有損、不可逆，排最後。

Breunig 把 context 的失敗分成五種：poisoning、distraction、confusion、clash、drift。叫得出名字，修法就很明顯：poisoning 刪掉那段，distraction 用 masking，confusion 用 admission，clash 用 dedup，drift 把目標重新放回。

最後的實驗把整堂收攏：model 不變，只改 harness。SWE-bench Verified 從 43 題變 72 題（1.7×），SWE-bench Pro 從 31 題變 72 題（2.3×）。改良的 harness 做的就是這堂的內容：壓縮舊輸出、保留最近的 observation、偵測停滯。注意：Verified 用 20,480 token 的小 window，window 越小，context 管理的影響越大。

3 · 觀念補充

Slide 預設你已經懂的背景

Embedding 與 semantic searchp.12 的「依意思找」怎麼運作

Embedding model 把一段文字轉成一個向量。意思相近的文字，向量的距離也近。建索引時把程式切成片段，每段算一個向量；查詢時把問題轉成向量，取最近的幾段。所以搜「rate-limit」找得到 throttle.ts。

代價：檔案一改，向量就要重算；索引沒跟上就回傳舊程式碼 p.12。

Language Server Protocol編輯器與編譯器之間的標準協定

LSP 是編輯器與語言分析工具之間的 JSON-RPC 協定。「go to definition」就是送一個 textDocument/definition 請求給 language server。Server 解析過整個專案，知道每個 symbol 的定義、引用與型別。

對 agent，LSP 把「grep 再讀 5 個候選檔」換成一次查詢 p.14。它和 MCP 同一個思路：N × M 變成 N + M（L2）。

Unified diff讀懂 p.19 的 patch

一份 patch 由 file header 與多個 hunk 組成。Hunk header @@ -41,3 +41,3 @@ 說：舊檔從第 41 行起 3 行，新檔同樣。空格開頭的行是 context 行，用來定位；- 刪除，+ 新增。

git apply 依 context 行在附近搜尋，行號偏移了還能套。Context 行對不上就失敗，而且預設全有或全無：一個 hunk 失敗，整份都不套用。第 6 段有實測。

ASTp.21 的結構化編輯站在哪裡

Parser 把原始碼轉成一棵樹：函式節點底下有參數節點、本體節點。結構化編輯工具修改這棵樹，再印回文字，所以結果一定能 parse。

限制：每種語言一套 parser；model 只能做工具定義好的操作，例如改名、加參數。「改寫這段折扣邏輯」沒有對應的操作。

Temperature 與取樣self-consistency 為什麼要 T 大於 0

Model 每一步產生一個機率分布，再從中取樣一個 token。Temperature 控制分布的平或尖：T = 0 永遠選最高機率的 token；T 越大，低機率的 token 越常中選。

Self-consistency 要的是「不同的推理路徑得到相同答案」p.36，所以必須用 T 大於 0。T = 0 的 5 票一致沒有資訊，因為那 5 次走的是同一條路。

Lost in the middlep.45 的 U 形曲線

實驗把含答案的文件放在 20 份文件中的不同位置，量回答的準確率。結果呈 U 形：第 1 份 76%，第 10 份 55%，第 20 份 71%。原因還沒有定論。

對設計的意義：關鍵指示放開頭或結尾。中間的舊 tool 結果，是 model 最看不到、也最先該清掉的。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

Tool 設計就是 context 設計：agent-computer interface

SWE-agent 論文把 agent 與電腦之間的介面叫 agent-computer interface（ACI）。IDE 為人設計：語法高亮、滑鼠、彈出視窗。Model 需要的介面不同：一次看 100 行，錯誤訊息要能讀。

p.27 的表就是證據：顯示整個檔案 12.7%，保留完整歷史 15.0%，都低於預設的 18.0%。所以設計 tool 時先問：這個輸出進 context 之後，model 的下一步會更好還是更差？

評估時要固定 harness

p.55 說，同一個 model 換 harness，解題數差一倍。反過來看：兩個 model 放進不同的 harness 比較，差異可能來自 harness。排行榜多數不區分這件事。要比較 model，就固定 harness；要比較 harness，就固定 model 與 benchmark，還要寫明 window 大小。L7 會把這件事變成方法。

Prompt 的招式會過期，原則不會

一招有效，是因為它補了 model 當時的弱點。弱點補上了，這招就失效，有時反而干擾。所以 prompt 裡的每一招都該有 eval 證明有用；換 model 時，一次拿掉一招，看分數。四條原則（簡單、分段、具體、拆小）針對的是溝通本身，和 model 的世代無關。

無損與有損的排序，就是成本的排序

Admission 和 offloading 在內容進 window 之前動作。資訊還在外面，隨時拿得到，所以無損。Transformation 刪的是 window 裡的內容，但大多可以重新執行 tool 拿回：對目前的任務無損，對之後的引用有損。Compaction 由 model 決定留什麼，原文沒有 handle 可以拿回，所以不可逆。

這個排序也是成本排序：前三種不用呼叫 model，compaction 要先讀完整段歷史。L8 會算它的隱藏成本：丟掉的檔案要重讀，cache 也會重寫。

  1. p.5–7 · ReAct 與 loop

    只推理和只行動的 model 各會出什麼問題？ReAct loop 在什麼時候停止？Slide 標出 harness 設計者的哪四項工作？

    參考答案

    只推理：沒有東西檢查推理，小錯誤累積成自信的幻覺。只行動：背後沒有計畫，model 重複同樣的動作。ReAct 讓 observation 修正下一個想法。

    Loop 在兩種情況停止：observation 已經回答問題，或停止規則（步數、時間、預算）到了。四項工作：組出 context、寫 tool 定義、驗證並執行 tool call、整理結果與管理 context（p.7，第 4 項可選）。

  2. p.11–16 · 找程式碼

    Agent 找程式碼有哪四種做法？Grep 找不到什麼？哪一種做法處理改名時，連別名 import 都不會漏？

    參考答案

    四種：glob 與 grep、semantic search 與 repo map、外部訊號（stack trace、失敗的測試、git 歷史）、language server。Grep 只比對字面，用詞不同就找不到：p.12 問「rate-limit」，程式寫的是 throttle，只有 embedding 找得到。

    Language server。p.14 把 charge() 改名成 capture()：textDocument/references 找到 7 個檔案裡 42 個呼叫點，rename 連別名 import 一起處理。代價是每種語言一個常駐 server。

  3. p.18–22 · 四種編輯方式

    四種編輯方式各有什麼弱點？哪一種的輸出量和檔案大小成正比？Search/replace 為什麼比 unified diff 穩？

    參考答案

    整檔重寫：長檔會 drift。Unified diff：行號或 context 行過期就套不上。Search/replace：需要完全相符、唯一的 anchor。AST 編輯：支援的語言有限。p.22 把它們放在 token 成本與穩健度兩個軸上。

    整檔重寫：p.18 的例子只改 4 行，卻要輸出 120 行。Search/replace 靠內容定位，不靠行號，輸出量只和改動大小成正比。

  4. p.23–24 · Shell

    Slide 說 shell 是最強也最危險的 tool，用哪四個特性說明？設計執行 tool 時要想哪五件事？

    參考答案

    四個特性：composition（一次 call 串接、過濾、loop）、reach（檔案系統、網路、套件）、persistence（檔案和 process 在 call 結束後還在）、blast radius（shell 能做的事 agent 都能做）。

    五件事：失敗訊號（agent 看得懂錯誤嗎）、輸出量、執行時間（長時間與背景 process）、預算（何時停止重試）、隔離（在哪裡跑、碰得到什麼）。

  5. p.26–27 · Tool 設計原則

    Tool 設計的五條原則是什麼？只給 shell 和完整的 SWE-agent 介面，解題率各多少？哪兩個「多給資訊」的設定反而更差？

    參考答案

    五條：數量少且正交、為用途量身打造（search_orders 勝過 run_sql）、輸出省 token、錯誤訊息要能教、預設冪等。

    只給 shell 11.0%，完整介面 18.0%。顯示整個檔案（full-file view）12.7%，保留完整歷史（full interaction history）15.0%，都低於 18.0%。拿掉專用編輯器是 10.3%。

  6. p.31–39 · 八種 prompt 技巧

    八種技巧分成哪三層？什麼情況從 zero-shot 換成 few-shot？Self-consistency 為什麼要 temperature 大於 0，一致度低時怎麼辦？

    參考答案

    先用簡單的（zero-shot、few-shot、role）；加入推理（chain-of-thought、tree-of-thought、self-consistency）；設計成系統（prompt chaining、meta prompting）。每往下一層，token 與呼叫次數都增加。

    輸出格式少見，或規則用說的講不清楚時，換 few-shot。Self-consistency 用 temperature 0.7 取樣 5 次：每次走不同的推理路徑，答案仍一致才代表有把握；p.36 的門檻是 0.8，4/5 回傳 yes，3/5 交給人。

  7. p.41–46 · Context 的成本

    Prompt 技巧為什麼會過時？Context 有哪三種成本？答案放在 20 份文件的開頭、中間、結尾，準確率各多少？

    參考答案

    新的 model 在訓練時已經學會那些技巧要做的事，所以 prompt 的建議依 model 而異，換 model 要重新調整（p.41–42）。三種成本：錢（每一步重送整個 window）、延遲（prompt 越長 prefill 越久）、注意力（window 越滿越難找回資訊）。

    p.45 的 lost in the middle：第 1 份 76%，第 10 份 55%，第 20 份 71%，呈 U 形。p.46 的 window 裡最大的一塊是使用者、LLM 與 tool 結果，約 80K 而且持續增加。

  8. p.48–52 · 四種策略

    四種 context 管理策略的順序是什麼？前三種的例子各省下多少？Compaction 為什麼排最後，slide 給了哪三個警告？

    參考答案

    Admission → offloading → transformation → compaction，從預防、無損排到有損、不可逆。Admission：DOM 48,000 token 變 900，少 98%，答案相同。Offloading：60 個 tool schema 42,000 變 3,100，少 93%。Transformation：96,000 變 24,000，少 75%，沒有做摘要。

    Compaction 用 LLM 摘要舊歷史，有損、不可逆，所以是最後手段。三個警告：留空間給輸出、保留 system prefix、compaction 後重新放入關鍵事實。

  9. p.53–55 · 五種失敗與 harness

    Context 的五種失敗叫什麼？Drift 是什麼症狀？只換 harness 的實驗，兩個 benchmark 的解題數各從多少變多少，harness 改了哪四件事？

    參考答案

    Poisoning、distraction、confusion、clash、drift。Drift：真正的目標埋在歷史裡，agent 換成一個相近的子目標。

    SWE-bench Verified 從 43/169 變 72/169；SWE-bench Pro 從 31/316 變 72/316。四件事：壓縮舊的 tool 輸出、最近的 observation 保持完整、偵測重複與停滯、卡住時介入。結論：有些看似 model 能力不足的失敗，原因在 context 與 control loop。

  1. 概念 · Observation masking · p.51

    解釋 observation masking 為什麼對目前的任務幾乎無損，卻可能讓之後的步驟出錯。哪些 tool 結果不該 mask？

    情境：Harness 的規則是「超過 5 步的 tool 結果，換成一行佔位文字」。Agent 第 3 步 Read 了 src/tax.ts（1,240 行），第 6 步修改 applyTax，第 9 步測試通過。第 20 步，使用者問：「applyTax 原本的進位邏輯怎麼寫？」

    回答時請涵蓋
    • 說明第 3 步的讀檔結果在第 9 步之後變成什麼，以及 model 的決定保存在哪裡。
    • 指出第 20 步 agent 能做什麼、拿不回什麼。
    • 提出一條規則：哪一類 tool 結果不該 mask，或 mask 之前要先做什麼。
    思考方向

    分開兩種東西：tool 結果和 model 自己的回覆，masking 只刪前者。再想：第 20 步重新 Read，拿到的是哪個版本？

    參考觀點與追問
    • 第 3 步的 1,240 行在第 9 步之後變成「[舊輸出已移除；需要時請再 Read]」。Model 第 6 步的決定寫在它自己的回覆與 Edit 的參數裡，這些沒有刪，所以第 9 步不需要原文。
    • 第 20 步要引用原本的寫法。重新 Read 拿到的是改過的版本；原文只存在第 3 步的輸出裡，已經刪掉。能救的是 git show HEAD:src/tax.ts，前提是修改前有 commit。
    • 這就是「對目前任務無損、對之後引用有損」。損失的條件：來源在 masking 之後改變了，例如檔案已修改、網頁已更新。
    • 不該直接 mask 的例子：只能取得一次的輸出（20 分鐘的測試 log、一次性的 API 回應）、使用者貼進來的資料。做法是 mask 前先 offload：寫到檔案，佔位文字放路徑。

    追問：如果 masking 的對象是使用者的原始任務描述，會發生 p.53 的哪一種失敗？你的 harness 怎麼保證它永遠留在 context 裡？

  2. 估算 · 編輯方式與 context 策略的 token · p.18–22、p.49–51

    估算三種編輯方式各要輸出多少 token，再算出 slide 三個 context 策略例子各省下多少。哪一個差距最意外？

    情境：一個 1,200 行的檔案，每行約 10 token。要改 4 行，分散在 2 個地方，每處連續 2 行。三種方式：整檔重寫；search/replace，anchor 多帶 1 行上下文；unified diff，每個 hunk 前後各 3 行 context。Slide 的三個例子：admission 48,000 → 900、offloading 42,000 → 3,100、transformation 96,000 → 24,000。

    回答時請涵蓋
    • 寫出三種編輯方式的算式與結果，以及彼此的倍數。
    • 算出三個策略例子各省下多少 token 與百分比。
    • 用 output 速度每秒 50 token 比較等待時間，並指出哪一種有「改壞沒要改的行」的風險。
    思考方向

    整檔重寫的輸出和檔案大小成正比，另外兩種和改動大小成正比。SEARCH 與 REPLACE 兩段都要算；每個 hunk 有 header、context 行、刪除行、新增行。

    參考觀點與追問
    • 整檔重寫：1,200 × 10 = 12,000。
    • Search/replace：每個區塊 SEARCH 3 行加 REPLACE 3 行，6 × 10 = 60，加標記約 15，共 75；2 個區塊 150 token。整檔重寫是它的 80 倍。
    • Unified diff：每個 hunk 3 + 2 + 2 + 3 = 10 行，100 token，加 header 約 10，共 110；2 個 hunk 加 file header 20，共 240 token。整檔重寫是它的 50 倍。
    • 三個策略：admission 省 47,100 token（98.1%）；offloading 省 38,900（92.6%）；transformation 省 72,000（75.0%）。百分比最高的 admission，絕對數字卻最小，因為它只處理單一 tool 的輸出。
    • 等待時間：12,000 ÷ 50 = 240 秒；150 ÷ 50 = 3 秒；240 ÷ 50 = 4.8 秒。整檔重寫還有 drift 風險：1,196 行要重抄。每行抄錯的機率 0.1%，全部抄對的機率是 0.999 的 1,196 次方，約 30%。

    追問：如果 agent 每一步都重讀這個檔案，20 步要多少 input token？改成只讀 2 處各 40 行，省多少？（240,000 對 16,000，省 93%。）

  3. 設計 · 客服 agent 的 tool 介面 · p.24–26

    為一個電商客服 agent 設計 tool 介面。它要查訂單、查客戶、辦退款、改收件地址。你會給它哪些 tool？錯誤訊息和重試怎麼設計？

    情境：資料在 PostgreSQL，有 orders、customers、refunds、addresses 四張表。第一版提案只有一個 tool：run_sql(query)。Tool 經過 API gateway，timeout 大約每 200 次發生 1 次。退款一旦執行就無法撤回。

    回答時請涵蓋
    • 列出 tool 清單（名稱、參數、回傳欄位），並說明為什麼不用 run_sql。
    • 為「客戶給的是 email 不是 ID」和「訂單不在可退款狀態」各寫一段錯誤訊息，要能教 model 下一步。
    • 說明退款 tool 怎麼做到冪等：timeout 後 agent 重試，為什麼不會退兩次。
    思考方向

    套 p.26 的五條原則：一個查詢一個 tool；參數有型別、enum 與上限；預設只回 10 筆必要欄位。冪等：想想 idempotency key。

    參考觀點與追問
    • 讀取類：find_customer(email | phone)；search_orders(customer_id, status?, limit ≤ 50)；get_order(order_id)。寫入類：refund_order(order_id, reason, idempotency_key)；update_address(order_id, address)。五個 tool，每個只做一件事。
    • 不用 run_sql 的理由：model 要先知道 schema；它什麼都能做，包括 DELETE；輸出沒有上限，一個 SELECT * 就塞滿 context；錯誤訊息是資料庫的，不是給 model 的指引。
    • 錯誤訊息：customer_id 'jane@example.com' is an email. Call find_customer(email=...) first, then pass the ID like 'C-10293'.；order O-5512 is 'shipped'. Refund is allowed only for 'delivered' or 'cancelled'.
    • 冪等：refund_order 要求一個 idempotency_key，例如 order_id 加這次對話的 ID。Server 第一次收到就執行並記錄；同一個 key 再來，直接回傳上次的結果，所以重試是安全的。update_address 用「設成這個值」，也是冪等。

    追問：如果有人要求「agent 要能回答任何資料問題」，你會加回 run_sql 嗎？有沒有折衷，例如唯讀 replica、白名單查詢？

  4. 團隊實務 · 大型 monorepo 的編輯策略 · p.14、p.18–22

    為一個大型 monorepo 的團隊選一組 agent 編輯策略，並說服團隊接受。你的選擇在什麼情況下會失敗？

    情境：monorepo 有 40,000 個檔案、3 種語言。Commit 時 formatter 自動跑。30 位工程師同時用 agent 開 PR，每個 PR 都要人 review。本季有一個大任務：把 charge() 改名成 capture()，7 個檔案 42 個呼叫點，其中幾處用別名 import。

    回答時請涵蓋
    • 為「一般修改」和「跨檔案改名」各選一種方式，說明理由。
    • 指出 formatter 會讓哪一種方式失敗，以及你怎麼處理。
    • 說明 reviewer 看到什麼格式，以及它為什麼可以和 agent 內部用的格式不同。
    思考方向

    分開兩個問題：agent 怎麼「套用」修改，reviewer 怎麼「看」修改。p.22 的取捨是前者；git 會把任何修改變成 diff 給後者看。改名的例子在 p.14。

    參考觀點與追問
    • 一般修改用 search/replace：輸出只和改動成正比，靠內容定位，anchor 不唯一就報錯。Claude Code 的 Edit 就是這種設計。
    • 跨檔案改名用 LSP 的 textDocument/rename 或 AST 工具：它知道 import { charge as c } 的 c 就是 charge，grep 會漏掉。42 個呼叫點用 LSP 只要一次 call。
    • Formatter 的問題：每次 edit 後都跑 formatter，下一個 anchor 可能已經過期。做法：edit 後重新 Read；或把 formatter 放到最後一步統一執行（L2 的 PostToolUse hook）。Unified diff 在這裡最脆弱：行號與 context 行都依讀檔當時的版本，而且全有或全無。
    • Reviewer 看的是 git 產生的 PR diff。所以 agent 內部用 search/replace 或 AST，reviewer 一樣看到乾淨的 diff。會失敗的情況：每種語言的 language server 要各自常駐；40,000 個檔案的索引要一直同步。先在一個子目錄試，量 edit 的失敗率。

    追問：如果有人的 agent 設成整檔重寫，PR 的 diff 會長什麼樣？你會用 hook 或 CI 擋下來嗎？

  5. 風險 · 診斷 context 失敗 · p.49–53

    下面三個症狀各屬於哪一種 context 失敗（poisoning、distraction、confusion、clash、drift）？每一個各提出一個 harness 層的修法。

    情境：（a）任務是「修好結帳的 bug」。Agent 第 8 步看到 lint 警告，之後 25 步都在修 lint，結帳的 bug 沒有碰。（b）Agent 第 5 步把一個不存在的函式 parseAmountSafe() 寫進筆記檔，之後三次都呼叫它，每次失敗就換參數再試。（c）Agent 讀了 config.yaml 四次；第 2 次與第 4 次之間，使用者改過 timeout。Agent 最後用的是第 2 次讀到的舊值。

    回答時請涵蓋
    • 每個症狀寫出失敗類型與判斷依據。
    • 每個症狀提出一個修法，標明它屬於四種策略中的哪一種，或者都不屬於。
    • 指出哪一個症狀用 compaction 會更糟，並說明原因。
    思考方向

    先問：壞的資訊從哪裡進 context？是 model 自己產生的，是目標埋在歷史中間，還是新舊版本同時存在？修法要對準進入點。

    參考觀點與追問
    • （a）drift：真正的目標埋在歷史中間，agent 換成相近的子目標。修法：把原始任務寫進 TODO.md，harness 每 10 步重新放進 context 結尾（offloading 加定期注入）。也可以設停止規則：連續 N 步沒碰相關檔案，就暫停回報。
    • （b）poisoning：幻覺進了筆記，之後當成事實引用。修法：寫入筆記前先驗證，例如 grep 確認函式存在；發現後直接刪掉那段。這算 transformation，但觸發條件是驗證，不是步數。
    • （c）clash：同一個檔案的四個版本都在 context，model 用了舊的。修法：deduplication，每個檔案只留最新一次的讀取結果（transformation）。
    • Compaction 會讓（b）更糟：摘要可能把「parseAmountSafe 存在」寫進去，幻覺就固化了。（a）也可能更糟：摘要寫成「正在修 lint」，原始目標消失。所以 p.52 說 compaction 後要重新放入關鍵事實。

    追問：distraction 與 confusion 沒有出現在情境裡。各寫一個你看過的症狀，以及對應的策略。

  6. 應用 · 選 prompt 技巧 · p.31–39、p.41

    為三個場景各選一種 prompt 技巧，說明理由、估算成本，並說明換成 reasoning model 時你會改什麼。

    情境：（a）每天 300 張客服工單，分成 billing、bug、feature、other 四類，輸出要能直接 parse；有幾條說不清的規則，例如「亂打的字歸 other」。（b）判斷發票是否重複，答案只有 yes/no，判錯會多付一筆錢；每天 80 張。（c）處理供應商 email：擷取 vendor、amount、date，補上 vendor_id，再草擬回信；每段輸出都有 schema。

    回答時請涵蓋
    • 每個場景選一種技巧，寫出為什麼不選更簡單的。
    • 估算每天的 model 呼叫次數，和最簡單的做法比較。
    • 說明換 model 之後，你怎麼確認每一招還有用。
    思考方向

    照 p.39 的三層從上往下：zero-shot 夠不夠？規則講不清楚才加範例；答錯代價高才取樣投票；能拆段、段之間能驗證，才做 chaining。

    參考觀點與追問
    • （a）few-shot：zero-shot 已經能列出標籤和格式，但「亂打的字歸 other」這類 tacit rule，用一個 asdfgh → other 的範例比文字清楚。範例要涵蓋四個標籤。成本：300 次呼叫，和 zero-shot 相同。
    • （b）self-consistency：取樣 5 次、temperature 0.7、多數決；一致度低於 0.8 就交給人。答錯代價高，5 倍成本划得來：80 × 5 = 400 次呼叫，zero-shot 只要 80 次。
    • （c）prompt chaining：三段各一個 prompt，每段輸出用 schema 驗證，不合格只重跑那一段。成本：每封 3 次，80 封 240 次，加重跑約 250 次。
    • 換成 reasoning model：（a）與（c）不用改。（b）先測單次 zero-shot 的準確率，再決定要不要保留 5 次取樣。確認的方法只有一種：一組固定的 eval 案例（p.38），每個技巧一次拿掉一個，比較分數。

    追問：（a）的四個標籤如果變成 12 個，few-shot 的範例要多少個？Context 成本和準確率怎麼取捨？

自我檢查

你的 agent 執行 tool 時拋出例外，整個程式就中止。依 p.6 的骨架，該怎麼改？

捕捉例外，把錯誤訊息當成 tool 結果，附上 tool_call_id 放回 messages。Model 讀到錯誤，下一圈就能修正。

Agent 用 unified diff 連續修改同一個檔案，第二份 patch 常套不上。為什麼？怎麼改善？

第二份 patch 的行號與 context 行，依第一次修改前的內容寫成，已經過期。改善：每次修改後重新讀檔；或改用 search/replace，它靠內容定位。

你用 temperature 0 做 self-consistency，5 次取樣都答 yes。這代表 model 很有把握嗎？

不代表。Temperature 0 時，model 每次都選機率最高的 token，5 次結果本來就幾乎相同。要用大於 0 的 temperature，讓每次走不同的推理路徑，一致度才有意義。
