先看這裡

這堂從一個 agent 走到多個 agent。它回答三個問題：誰協調、工作怎麼拆、agent 之間怎麼傳話。每個答案都碰到分散式系統的老問題。

1 · 架構

Multi-agent 系統的零件怎麼接在一起

架構的名字只是三張圖的一種組合。拿到任何系統，先問：誰能派工和停工、哪些線真的存在、哪些子任務相依。線越多，context 和 token 的成本越高，所以 slide 的原則是「照相依關係連線」。

2 · 核心觀念

五個觀念串起整堂課

拆之前先問：多一個 agent，換到什麼 p.6–8

L2 到 L4 看的是一個 agent。多一個 agent，只有四種東西可以換到。Specialization：每個 agent 用不同的 model、prompt、tool。Isolation：讀網頁的 agent 沒有 shell。Parallelism：互不相依的子任務同時跑。Context management：worker 只拿到自己的子任務，supervisor 只收摘要。

每一項都有價格：多一次交接，就多一次資訊遺失、多一份 context、多一個會失敗的點。所以 p.48 的第一條原則是：先問真的需要 multi-agent 嗎。p.8 的三張圖是描述架構的共同語言；p.10–17 每頁底部那一行就是答案。

八種架構，是三張圖的不同組合 p.9–19

p.19 把八種架構分成 centralized、decentralized、hybrid。中心化的四種好預測、好 debug，弱點都在中心：planner 瓶頸、每層摘要造成錯誤放大、錯誤往下游傳、不實的出價。去中心化的三種沒有單點，弱點變成一致性：狀態過期、groupthink、O(n²) 的訊息量。

弱點都能從線讀出來。Supervisor 的線全部匯到一點，所以它的 context 長得最快。Pipeline 沒有回頭的線，所以加一條 retry edge 勝過多加一個 agent。Committee 的兩個 grader 用同一個 model，兩票同意帶來的新資訊很少。真實系統是混合體（p.18）：Claude Code 的 agent teams 有 lead 派工、共享 task list、直接傳訊，三種都有。

子任務要寫成規格；拆得越細不一定越快 p.20–26

Worker 看不到 supervisor 的 context，規格沒寫的事它都不知道。所以 p.22 要求八個欄位：目標、輸入、邊界、tool 與權限、輸出 schema、完成條件、預算、相依關係。「Research storage systems」是差的規格；寫明年份、回傳欄位、排除項才是好規格。

拆多細，p.23 給了估算式：T_multi ≈ T_planning + T_critical_path + T_communication + T_merge。平行只縮短 critical path（最長那條相依鏈），其他三項隨子任務數量增加。Slide 的 20 個 lookup：不拆 100 秒，拆成 20 份 185 秒，4 份 77 秒。

動態拆解會在執行中生出新任務，所以要設上限：spawn 數量、預算、深度、終止條件。p.25–26 的六種拆錯方式：重疊、缺口、隱藏的相依、無法合併的輸出、失去全局 context、straggler。前四種靠規格預防，後兩種靠最後的通讀和 timeout。

訊息分兩層：欄位給 runtime，內容給 LLM p.27–35

溝通有四個維度（p.28）：topology、medium、format、channel，可以分開選。大型產出放檔案，只傳路徑。Broadcast 的一則訊息會進入 n 個 context，只有所有人都要知道時才用。

p.32 的 envelope 是核心。外層是 runtime 看得懂的欄位：id、task_id、from、to、type（DELEGATE、QUERY、REPORT、HANDOFF、UPDATE、CANCEL、ACK、ERROR、COMPLETE 九種）。路由、重試、停止由 runtime 依欄位決定，不用問 LLM。Payload 才是自然語言：一份子任務規格，或一句 claim 加上 confidence 與 evidence。p.35 的法則因此是：依欄位路由，不依內文路由。

溝通是分散式系統問題；協定只標準化溝通 p.36–47

p.36 的例子：Agent A 請 Agent B「購買 8 台 GPU instance」，然後 timeout。從 A 這一側，三種情況看起來一樣：請求沒送到、B 買了但回覆遺失、B 還在處理。不重試可能一台都沒買；重試可能買 16 台。實務的答案是 at-least-once 加冪等：每次重試帶同一個 task_id，B 查到做過就回傳上次的結果。真的買了兩次，就走 compensation 釋放多出的 8 台。

p.37 列出繼承的六個分散式系統老問題，p.39 再加上黑盒子 LLM 帶來的：摘要丟細節、context 過期、信念衝突、沒人認領的 ownership、繞圈的 communication loop。對策多半是老辦法：每個 task 一個 owner，訊息帶跳數上限，log 用 task_id 串起來。

兩個協定分工明確（p.47）。A2A 連接 agent 與 agent，單位是一個有 ID、有狀態、能暫停的 task（p.43）；對方從 agent card 得知你會什麼。MCP 連接 agent 與服務，單位是一次 tool call。兩者都不負責 orchestration：要不要委派、怎麼拆，仍由 harness 決定。

3 · 觀念補充

Slide 預設你已經懂的背景

Idempotency key重送的請求為什麼不會做兩次

一個操作做一次和做很多次，結果相同，就叫冪等（idempotent）。「設 x = 5」冪等，「x 加 1」不冪等。「購買 8 台 instance」不冪等，所以要靠一把 key：呼叫端每次重試帶同一個 key，服務端用 key 查做過沒，做過就回傳上次的結果 p.36。Key 由呼叫端產生，服務端的紀錄要持久保存。

Delivery semanticsat-most-once、at-least-once、exactly-once

網路會遺失、延遲、重複訊息。傳遞層只能保證兩種事：不重試，每則訊息最多送達一次（可能丟）；重試到確認，至少送達一次（可能重複）。Exactly-once 無法由傳遞層保證。所以設計分兩層：傳遞層做 at-least-once，應用層用冪等處理去除重複，合起來效果等於 exactly-once。

Partial failure分不出對方是慢，還是掛了

單機程式要嘛全部在跑，要嘛全部停了。分散式系統裡，一部分正常、另一部分掛掉，而且你分不出來：沒有回覆，可能是 crash、斷網、或只是慢 p.37。LLM agent 的「慢」特別常見。所以 timeout 之後要有動作：查狀態、開備援、或用部分結果。

Pub/sub 與 request/response兩種 channel 的差別

Request/response 是打電話：你發問，停下來等回答，等待時間算進 T_communication。Pub/sub 是訂閱頻道：發送者發到一個 topic，訂閱者各收一份，發送者不必知道誰在聽，也不等 p.30。新 agent 訂閱就能加入；代價是每個訂閱者的 context 都收到這則訊息。

狀態機task lifecycle 為什麼畫成那樣

狀態機由有限的狀態和允許的轉換組成。A2A 的 task 有進行中（Submitted、Working）、中斷（Input required、Auth required）、終止（Completed、Failed、Rejected、Canceled）三組 p.43。終止狀態沒有出去的箭頭。好處：不合法的轉換由 runtime 擋下；呼叫端可以用 task_id 查狀態，timeout 之後不必盲目重送。

4 · 延伸思考

超出 slide 的推論

這一段是本文的延伸，不是 slide 的內容。

一個 agent 常常就夠了

延伸閱讀的數字支持 p.48 的第一條原則。Towards a Science of Scaling Agent Systems 測了 260 種設定：和單一 agent 相比，表現從 +80.8%（可分解的財務推理）到 −70.0%（循序規劃）。單一 agent 已超過約 45% 準確度的任務，多加 agent 反而變差。Anthropic 說 multi-agent 系統的 token 約是聊天的 15 倍。

Cognition 的立場更強：actions carry implicit decisions。兩個 agent 各做一半，隱含的決定會互相衝突。他們建議從單線程的 agent 開始。設計 review 的第一個問題：拿掉一個 agent，品質掉多少？

彙整節點是細節流失的地方

p.48 說找出資訊遺失點。遺失點很好找：每個把多份輸入變成一份輸出的節點。Supervisor 讀 8 份報告寫一份摘要，hierarchical 的每一層 lead 再摘要一次。每一層都丟細節，而且下游不知道丟了什麼。對策來自 slide：大型產出走檔案，訊息只帶路徑和 claim，claim 附 evidence。

彙整也有另一面。Scaling 論文量到：independent 系統把錯誤放大 17.2 倍，centralized 壓到 4.4 倍。有人在彙整，錯誤才有機會停下來。

Dynamic topology 難重現，也難除錯

p.17 說 dynamic topology 的失敗很難重現。原因有兩層：topology 由 LLM 在執行時決定，而 LLM 的輸出有隨機性。同一個 ticket 跑兩次，形狀可能不同。沒有全域時鐘，兩個 agent 的 log 誰先誰後也說不準。

可行的做法是把 topology 當資料記下來：每個 envelope 都 log，用 task_id 串起來，至少能照同一個形狀重跑。L7 做 agent 評估時會再碰到這個問題。

溝通的價格是 token 和 context

LLM agent 的通訊成本多一項：每則訊息都進入某個 context，之後每一圈 loop 都重送。一則 2k token 的 broadcast 發給 10 個 agent，每個再跑 20 圈，就是 400k token 的 input。這是 p.48 說「密集的 mesh 很少是好的預設」的原因。L8 會算 agent 系統的成本結構。

  1. p.7–8 · 為什麼拆、三張圖

    把工作拆給多個 agent 的四個理由是什麼？描述一個 multi-agent 架構要回答哪三個問題，各對應哪一張圖？

    參考答案

    四個理由：specialization（不同的 model、prompt、tool）、isolation（不同的權限）、parallelism（互不相依的子任務同時跑）、context management（不把整條 trajectory 交給每個 agent）。

    三個問題：誰協調（control graph）、怎麼溝通（communication graph）、工作怎麼拆（task graph）。p.10–17 每頁底部的 Task / Control / Comms 那一行，就是這三張圖的答案。

  2. p.10–12 · 三種中心化架構

    Supervisor–worker 的瓶頸在哪裡？Hierarchical 的難處是什麼？Pipeline 最大的弱點是什麼，slide 給的教訓是什麼？

    參考答案

    Supervisor 是瓶頸：它要讀每一份結果，context 長得最快。Hierarchical 的難處是在哪一層拆、每條邊界要傳多少 context；p.19 把它的弱點寫成錯誤放大。

    Pipeline 沒有回頭路，第 4 站不能要求第 1 站給更好的來源；但它最容易 debug。教訓：加一條 retry edge，勝過多加一個 agent。

  3. p.13–16 · 去中心化與競標

    Committee 的失敗模式是什麼？GPU job router 的例子裡誰得標，為什麼？Swarm 的通訊量怎麼成長？

    參考答案

    Committee：意見一致不代表彼此獨立。同一個 model、同一份 context，就有同一個盲點。Market 的例子規定 5 秒內完成、出價最低者得標：T4 最便宜（$0.05）但要 10 秒，出局；A100（$0.20、3 秒）得標；H100（$0.40、1 秒）最快但較貴。

    Swarm 每對 agent 都相連，通訊量 O(n²)，衝突也難解決，產品中很少用。Blackboard 則靠共享狀態協調，難處是 consistency、concurrency、provenance、versioning、garbage collection。

  4. p.17–19 · 動態拓樸與總表

    Dynamic topology 的優點和弱點各是什麼？總表把八種架構分成哪三類？Market 歸在哪一類？

    參考答案

    優點：容量隨難度增加，簡單的 ticket 保持便宜。弱點：每次執行的形狀都不同，失敗很難重現。p.18 說真實系統是混合體：hierarchy、shared memory、pipeline 混用，需要時再重新規劃。

    三類：centralized（supervisor–worker、hierarchical、pipeline、market）、decentralized（blackboard、committee、swarm）、hybrid（dynamic topology）。Market 歸在 centralized，因為結標的 auctioneer 只有一個。

  5. p.21–23 · 拆解軸、規格、粒度

    可以沿哪六個軸拆任務？好的子任務規格要寫清楚哪八件事？T_multi 的估算式有哪四項，20 個 lookup 的例子怎麼拆？

    參考答案

    六個軸：data、expertise、stage、hypothesis、tool、authority。八件事：目標、輸入與 context、邊界與排除項、tool 與權限、輸出 schema、完成條件、預算與期限、相依關係。

    T_multi ≈ T_planning + T_critical_path + T_communication + T_merge。拆太細，排程與溝通的 overhead 會吃掉收益，所以 20 個一行就能查完的 lookup，要打包成 4 個子任務。

  6. p.24–26 · 動態拆解與失敗

    動態、遞迴、機會式拆解為什麼一定要設上限，要設哪四種？六種常見的拆解失敗是什麼，straggler 的例子數字是多少？

    參考答案

    沒有上限時，每個 agent 都可能再開 subagent，委派會遞迴爆炸。四種上限：spawn 數量、預算、深度、終止條件。

    六種失敗：overlap（兩個 agent 摘要同一篇）、gap（2020–2023 加 2025–2026 漏掉 2024）、hidden dependency、unmergeable outputs（自由文字對上 JSON）、lost global context（每節都對、整份矛盾）、straggler（6 個 agent 約 20 秒完成，1 個花了 4 分鐘）。

  7. p.28–32 · 溝通的維度與訊息格式

    溝通有哪四個維度？訊息 envelope 裡哪些欄位給 runtime 讀、哪些給 LLM 讀？Runtime 認得哪幾種 type？

    參考答案

    四個維度：topology（誰能和誰說話）、medium（訊息、shared memory、檔案）、format 與語意、channel（p2p、broadcast、pub–sub、shared state、request–response）。

    Envelope 外層是 id、task_id、from、to、type，給 runtime 路由、重試、停止用；payload 放自然語言的內容，給 LLM 讀。p.31 的結果訊息另有 claim、confidence、evidence、artifact。九種 type：DELEGATE、QUERY、REPORT、HANDOFF、UPDATE、CANCEL、ACK、ERROR、COMPLETE。

  8. p.35–36 · 經驗法則與 timeout

    溝通設計的四條經驗法則是什麼？A 請 B 買 8 台 GPU instance 後 timeout，有哪三種可能？Slide 給的三個對策是什麼？

    參考答案

    四條法則：照相依關係連線；一條連線只用一種媒介；只有所有人都要知道時才 broadcast；依欄位路由，不依內文路由。

    三種可能：請求沒送到、B 買了但回覆遺失、B 還在處理。不重試是 at-most-once，重試到 ACK 是 at-least-once，可能買 2 次。對策：用 task_id 當 idempotency key；準備 compensation 或 rollback；事先決定重複購買時誰付錢。

  9. p.41–47 · A2A 與 MCP

    Agent card 放在哪裡、告訴呼叫者什麼？A2A task 有哪幾種狀態？MCP 和 A2A 的工作單位差在哪裡？

    參考答案

    Card 在 GET /.well-known/agent-card.json，告訴呼叫者身分、skills、端點、capabilities（streaming、push）、security scheme。Task 的狀態：進行中（Submitted、Working）、中斷（Input required、Auth required）、終止（Completed、Failed、Rejected、Canceled）。

    MCP 連接 agent 與服務，單位是一次 tool call；A2A 連接 agent 與 agent，單位是一個長時間的 task，內部最好不透明。兩者可以疊：一個 A2A 遠端 agent 自己可能呼叫 20 個 MCP server。

  1. 概念 · Supervisor 瓶頸 · p.10、p.19、p.48

    解釋 supervisor–worker 架構裡，為什麼 supervisor 一定是第一個撞到 context 上限的節點。它會在第幾輪撞到？你會怎麼改？

    情境：一個 supervisor 帶 8 個 worker。Supervisor 的固定內容共 20k token，context window 200k。每一輪它派 8 個子任務，每個 worker 回傳約 6k token 的完整報告。任務預計跑 5 輪。

    回答時請涵蓋
    • 用 communication graph 的線，說明為什麼 context 的壓力集中在 supervisor。
    • 估算每一輪結束時 supervisor 的 context 大小，指出哪一輪會超過 200k。
    • 提出兩種改法，各說明省下多少 context，以及付出什麼代價。
    思考方向

    星狀 topology 的每一條線都有一端在 supervisor。先算一輪增加多少，再乘輪數。改法從 p.29 的媒介和 p.11 的 hierarchy 去想。

    參考觀點與追問
    • 每輪新增 8 × 6k = 48k。第 1 輪結束 68k，第 2 輪 116k，第 3 輪 164k，第 4 輪 212k，超過 200k。第 4 輪就會 compaction，第 5 輪的決策依據的是摘要。
    • 為什麼是 supervisor：星狀的 n 條線全部匯到中心。每個 worker 只收一條線，supervisor 收 n 條。
    • 改法一：worker 把完整報告寫進檔案，只回傳約 500 token 的摘要加路徑（p.29–31）。每輪只增加 4k，第 10 輪也只有 60k。代價：supervisor 看不到細節，要靠 evidence 判斷何時回去讀。
    • 改法二：改成 hierarchical（p.11），每個 lead 帶 4 個 worker，先彙整再往上報。代價：多一次摘要，就多一個資訊遺失點；下層摘要錯了會往上放大（p.19）。
    • Anthropic 的 research system 用的就是改法一：subagent 把成果存到外部系統，只交回參照。

    追問：改法一之後，沒有任何一個 agent 讀過全部的細節。p.25 的失敗 05（每一節都對，整份卻矛盾）要由誰來擋？

  2. 估算 · Granularity · p.23、p.26

    用 p.23 的估算式，算出 4 個平行子任務什麼時候贏過 1 個 agent 依序做。有一個 straggler 時，答案怎麼變？

    情境：一個任務可以拆成 4 個互不相依的部分，每部分要 W 分鐘；不拆，一個 agent 依序做完要 4W。拆開的話：T_planning 2 分鐘；每個子任務的派工加讀回報 0.5 分鐘；T_merge 3 分鐘。請算 W = 2 和 W = 6。

    回答時請涵蓋
    • 寫出 T_multi 的完整算式，分別算出 W = 2 和 W = 6 的結果，和 4W 比較。
    • 解出讓 T_multi = 4W 的 W（損益兩平點），並說明它的意義。
    • 假設其中 1 個子任務慢了，花 s × W 分鐘。算出 s = 2 和 s = 3 時的 T_multi，以及損益兩平點怎麼變。
    思考方向

    平行只縮短 critical path：4 個子任務同時跑，critical path 就是最慢那一個。其他三項是固定的 overhead。先把 overhead 加總，再和省下的 3W 比。

    參考觀點與追問
    • Overhead = 2 + 4 × 0.5 + 3 = 7 分鐘。T_multi = 7 + W，T_single = 4W。
    • W = 2：8 對 9，拆開反而慢 1 分鐘。W = 6：24 對 13，省 11 分鐘，約 46%。
    • 損益兩平：7 + W = 4W，W = 7 / 3 ≈ 2.33 分鐘。子任務比這短就不值得拆。Slide 的 20 個 lookup 同理：每個省 5 秒卻付 8 秒 overhead。
    • Straggler：critical path 變成 s × W。W = 6 時，s = 2 得 7 + 12 = 19，仍贏 24；s = 3 得 7 + 18 = 25，輸給 24。一般式 W = 7 / (4 − s)：s = 2 時損益兩平點升到 3.5 分鐘，s = 4 時永遠不划算。
    • 對策（p.26 的失敗 06）：設 timeout，到時間就用部分結果；或像 MapReduce 一樣，為最慢的任務開一份備援。

    追問：T_communication 在 LLM 系統裡也是 token。把每份回報 6k token 算進去，成本面的損益兩平點在哪裡？T_merge 隨子任務數量成長時，公式要怎麼改？

  3. 設計 · 選架構 · p.10–19、p.21

    為下面三個任務各選一種架構。用三張圖（control、communication、task）說明你的選擇，並指出它的弱點和一個補救。

    情境：（a）review 一個改了 200 個檔案的 PR，要同時看 security 和 performance。（b）發票處理：OCR → 擷取欄位 → 比對採購單 → 核准 → 入帳，每天 2,000 張，錯一張就是錯帳。（c）寫一份 30 頁的技術研究報告，分 6 節，各節要一致、術語統一。

    回答時請涵蓋
    • 每個任務：架構名稱，加上三張圖各一句（誰協調、誰和誰說話、沿哪個軸拆）。
    • 每個任務：p.19 總表上的弱點會怎麼出現，以及你加什麼補救。
    • 指出哪一個任務你會先試單一 agent 而不拆，說明理由。
    思考方向

    先看任務的結構：子任務獨立、順序固定、還是要共同產出一份東西？再對照 p.19：獨立用 supervisor–worker，順序固定用 pipeline，共同產出用 blackboard 或 hierarchy。

    參考觀點與追問
    • （a）Supervisor–worker。Task：先依 data 拆成 4 組各 50 個檔案，再依 expertise 拆成 security 與 performance，共 8 個 worker（p.21）。Control：一個 supervisor。Comms：星狀。弱點：supervisor 要讀 8 份清單，兩個角度會回報同一個問題。補救：同一個輸出 schema，合併前去重。
    • （b）Pipeline / DAG。Task：依 stage 拆，設計時固定。Control：順序本身。Comms：站到站，每條邊界一個 typed contract。弱點：OCR 讀錯金額會流到入帳。補救：每個邊界驗證 schema；加一條從核准退回 OCR 的 retry edge；核准那站放人工。
    • （c）Hierarchical 加 blackboard。Task：依 section 拆，planner 先把論點、術語表、大綱寫進共享檔案。Control：planner 派工，最後一個 agent 通讀全文。Comms：worker 讀共享檔案，寫自己那一節。弱點：失去全局 context（p.25 的 05）。
    • 先試單一 agent 的是（c）。Cognition 的論點正是這種任務：每一節都隱含決策，拆開就衝突。一個 agent 加 compaction 做得完 30 頁。

    追問：（a）的兩個角度意見衝突時，誰裁決？這會不會變成 p.14 的 committee？（b）哪一站最可能成為 straggler？

  4. 團隊實務 · 子任務規格 · p.22、p.25–26

    把一句模糊的請求，改寫成 worker 不用猜就能做完的子任務規格。寫完後，對照 p.25–26 的六種失敗，檢查你的規格擋住了哪幾種。

    情境：你的主管說：「幫我看看我們的服務最近為什麼變慢。」你要把它交給幾個 agent 去查。可用的資料有 metrics dashboard、log 查詢系統、最近兩週的 deploy 紀錄。Agent 只能讀，不能改設定。

    回答時請涵蓋
    • 照 p.22 的 8 個欄位，寫出至少一份完整的規格。
    • 說明你沿哪個軸拆（p.21），拆成幾個子任務，以及為什麼不是更多或更少。
    • 逐一對照六種失敗，指出規格的哪一行擋住哪一種。
    思考方向

    先把「變慢」變成可量測的句子：哪個 endpoint、哪個指標、哪段時間。Debug 類任務適合 p.21 的 hypothesis 軸：每個 worker 驗證一個假設。

    參考觀點與追問
    • 一份可用的規格。objective：找出 /search 的 p95 latency 在 10/01 到 10/08 之間上升的原因。inputs：dashboard、deploy 清單、事件時間線。boundaries：只讀 metrics 與 log，不碰其他 endpoint。tools：metrics 與 log 查詢（唯讀）。output：JSON {hypothesis, verdict: supported | ruled_out, evidence[], confidence}。done_when：verdict 有 evidence 支持。budget：25 次 tool call 或 15 分鐘。depends_on：none。
    • 拆法：依 hypothesis 軸拆成 4 個 worker：cache 命中率下降、資料庫慢查詢、某次 deploy 引入、流量型態改變。假設互斥、各自在預算內可驗證；再多就重疊，再少就有缺口。
    • 擋住的失敗。01 重疊：每個 worker 一個互斥的假設。02 缺口：另開一個「以上皆非」的 worker。03 隱藏的相依：deploy 清單由 planner 放進 inputs。04 無法合併：同一個 output schema。05 失去全局：merge 時一個 agent 通讀 4 份 verdict。06 straggler：budget。
    • Anthropic 的 research system 給了反例：任務描述太短時，一個 subagent 查 2021 年的晶片危機，另外兩個重複查 2025 年的供應鏈。結論和 p.22 一樣：每個 subagent 需要目標、輸出格式、tool 指引、清楚的邊界。

    追問：Worker 查完發現「服務沒有變慢，是監控指標的定義改了」。你的規格允許它回報「題目本身有錯」嗎？輸出 schema 要加什麼欄位？

  5. 風險 · Idempotency 與 compensation · p.36–37、p.43

    Agent A 請 Agent B 購買 8 台 GPU instance，60 秒後 timeout，沒有回覆。為這條路徑設計重試、idempotency 與 compensation，讓最壞情況可以接受。

    情境：每台 instance 每小時 4 美元。B 完成一次購買約需 30 到 90 秒。團隊規定：寧可暫時少買，不能多付錢超過一天。重試由 runtime 執行。

    回答時請涵蓋
    • 選 at-most-once 或 at-least-once，說明各自最壞會發生什麼，以及你為什麼選它。
    • 寫出 B 要持久保存什麼，以及收到重複請求時，B 在「處理中」和「已完成」兩種狀態下各怎麼回覆。
    • 設計 compensation 路徑：真的買了 16 台時，誰發現、誰釋放、多久內釋放，以及這條路徑失敗時怎麼辦。
    思考方向

    先列出 timeout 的三種可能（沒送到、做了但回覆丟了、還在做），再問每個設計對三種情況各怎麼反應。A2A 的 task 有狀態可以查（p.43），A 可以先問再重送。

    參考觀點與追問
    • 選 at-least-once 加冪等。At-most-once 最壞是 0 台，任務失敗；at-least-once 沒有冪等最壞是 16 台。多出 8 台一天的成本是 8 × 4 × 24 = 768 美元，兩週就是 10,752 美元。加上 idempotency key 才能同時避免兩種最壞情況。
    • B 以 task_id 當 key，持久保存 {task_id, state: received | working | done | failed, order_id}。沒有紀錄：寫入 received，開始購買。working：回覆「處理中」，不再買。done：回傳原本的 order_id。紀錄要在呼叫雲端 API 之前寫入，否則 B 在購買後、寫入前 crash，重啟就會再買。
    • A 的重試：timeout 60 秒短於 B 的最長處理時間 90 秒，所以第一次 timeout 很可能是「還在做」。A 先用 task_id 查狀態（A2A 的 GetTask），查不到才重送同一個 task_id，最多 3 次。LLM 自己重試可能換掉 task_id（p.36）。
    • Compensation：購買時給 instance 打上 task_id 的標籤。每小時對帳一次，標籤下超過 8 台就釋放多出的；釋放操作也用 key，可以安全重試。對帳也失敗，就發 ERROR 給人，並照事先決定的規則認列誰付錢（p.36）。

    追問：B 存 idempotency 紀錄的資料庫自己掛了，B 該拒絕購買，還是先買再補紀錄？這兩個選擇分別對應 at-most-once 和 at-least-once 的哪一邊？

  6. 應用 · 訊息 envelope · p.31–32、p.35、p.39

    挑一個你們團隊有多個階段的流程，替它設計 agent 之間的訊息 envelope。決定哪些資訊放結構化欄位、哪些放自然語言，並說明 runtime 靠哪些欄位就能行動。

    情境：例如 bug 單處理：分類 → 重現 → 修正 → review → 發版。每個階段由一個 agent 負責，階段之間用訊息交接；流程可能中途取消、失敗、或要回頭補資料。選一個你熟悉的流程。

    回答時請涵蓋
    • 寫出完整的 envelope JSON（至少 6 個欄位），標出哪些欄位由 runtime 讀、哪些由 LLM 讀。
    • 給出一條判斷規則：什麼資訊必須放結構化欄位，什麼可以放自然語言。用你的流程舉兩個例子。
    • 說明 runtime 收到 CANCEL 和 ERROR 時各做什麼（不經過 LLM），以及怎麼用 task_id 把各階段的 log 串成一條。
    思考方向

    從 p.32 的 envelope 和九種 type 出發。問每個欄位：runtime 要不要靠它做決定（路由、重試、停止、去重）？要，就放結構化欄位。再對照 p.39 的 communication loop 和 failure diagnosis。

    參考觀點與追問
    • 一個可用的 envelope：{id, task_id, parent_id, from, to, type, hop, deadline, requires_response, payload}。前 9 個由 runtime 讀；payload 由 LLM 讀：{claim, evidence[], confidence, artifact}。
    • 判斷規則：影響「誰收、要不要做、要不要停、算不算重複」的資訊放欄位；描述「做了什麼、為什麼、信心多高」的資訊放自然語言，並附 evidence。例子：「這張單是 P1」是欄位；「我認為是 race condition，因為 log 2391 顯示…」是 claim。
    • Runtime 收到 CANCEL：依 task_id 停止該階段的 agent，對下游轉送 CANCEL，不問 LLM。收到 ERROR：未達重試上限就依原 envelope 重送，達上限就升級給人。
    • Hop 欄位防止 p.39 的 communication loop：每轉送一次減 1，歸零就丟棄，和 IP 的 TTL 一樣。每個 envelope 都 log，用 task_id 加 parent_id 重建整條鏈，這直接回答 p.39 的 failure diagnosis。大型產出走 artifact 欄位放路徑。

    追問：LLM 填了 type: COMPLETE，但沒有跑測試（L6 的 unverified success）。哪些欄位 runtime 應該驗證而不是相信？Envelope 的 schema 改版時，兩端的 agent 怎麼相容？

自我檢查

兩個 grader 都給這篇作文 A，judge 就採用。這個設計有什麼問題？

兩個 grader 用同一個 model、讀同一份 context，錯誤高度相關，兩票同意帶來的新資訊很少。改用不同的 model 或評分角度，並讓它們先各自作答（p.14）。

20 個 lookup，每個 5 秒；每個子任務的派工與回報要 8 秒。為什麼拆成 20 個子任務，比不拆還慢？

平行只把 critical path 從 100 秒縮到 5 秒，溝通卻要 20 × 8 = 160 秒。打包成 4 個子任務，總時間約 77 秒。

情境一：讓你的 agent 查一筆訂單的狀態。情境二：把「規劃一趟出差」交給別家公司的 agent。各該用 MCP 還是 A2A？

情境一用 MCP：一次明確的動作，一個結果。情境二用 A2A：對方要自己推理，可能反問日期或要求授權，也可能跑很久。
