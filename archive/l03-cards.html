Superpowers 是一個軟體開發用的 plugin。原始碼在 GitHub 的 obra/superpowers。

p.07

同一個 model，不同的 workflow Same Model, Different Workflow

兩個 agent 用同一個 model、同一組 tool，差別只在指示。預設的 agent 直接寫 code；Superpowers 先規劃、再實作、最後交付。

預設流程：收到需求 → 開始寫 code → 出錯再改。

Superpowers 的流程（第 0 步是你輸入 prompt）：

  1. 釐清問題。
  2. 核准設計。
  3. 寫詳細的計畫。
  4. 用測試驅動的方式實作。
  5. Review 並驗證。
  6. 收尾，或把 branch 整合回去。

Slide 把六個階段分成 PLAN、BUILD、SHIP 三組。

架構 Superpowers Architecture

Plugin 是發佈用的容器。決定 agent 行為的，是裡面的 skill 與 hook。

Metadata 讓它可以安裝；hook 在每個 session 開始時執行；skill 提供每個階段的程序。三者合起來，才產生 p.7 的行為。

以 brainstorming 為例：一個資料夾，裡面有 SKILL.md、補充文件與 script。Frontmatter 是 metadata；body 是 agent 要照做的程序。

同一個資料夾還有 visual-companion.md（補充文件）與 scripts/。

p.11

SKILL.md 裝什麼 What a SKILL.md Contains

一份 SKILL.md 有六種成分。流程型的 skill 還會寫明關卡，以及下一個 skill。

NOTE

p.12

只有 skill 還不夠 Why Skills Alone Are Not Enough

裝了 skill，只代表 skill 可用，agent 不一定會去查。Superpowers 用 SessionStart hook，在每個 session 開始時先把規則放進 context。

原因：model 依 description 自己判斷要不要載入 skill（L2 p.40）。它可能直接開始寫 code，完全沒查 skill。

  • matcher（官方文件）：startup 是新 session，clear 是 /clear 之後，compact 是 compaction 之後。Compaction 可能摘要掉注入的規則，所以要重新注入。
  • "async": false：hook 跑完，agent 才開始動作。

Hook 的四個保證：時機確定；每個 session 都執行；在 agent 動作前執行；/clear 與 compaction 後再執行一次。

從頭到尾走一次 End-to-End Walkthrough

以「Add authentication」為例。Hook 先放入選 skill 的規則；你提出需求後，agent 依序載入 brainstorming 與 writing-plans，再走完後面的階段。

  1. Claude Code 開始 session。

  3. Agent 收到「怎麼選 skill」的規則。
  4. 你輸入「Add authentication」。
  5. Agent 載入 brainstorming，先問清楚需求。
  6. 你核准設計。
  7. Agent 載入 writing-plans，產出實作計畫。

p.15

設計心得（選讀）Design Lessons From Superpowers

六個設計問題，以及 Superpowers 的答案。這頁是選讀。

  • 行為複雜：拆成小而可組合的 skill。
  • Agent 要記得用 skill：session hook 載入 bootstrap skill。
  • Context 要精簡：任務 skill 只在相關時載入。
  • 階段要銜接：每個 skill 寫明關卡與下一個 skill。
  • 安裝：打包成 plugin。Command 與 MCP 需要時才加。

案例二：Caveman，雙向壓縮 token

Caveman 用了五種擴充機制，再加一個本機 proxy。目標：agent 讀得少，也寫得少。

p.16

Caveman 是什麼 Caveman Case Study

Caveman 是一個壓縮 token 的 plugin。它用了 skill、command、hook、MCP、plugin 五種機制，再加一個本機 proxy。

EXAMPLE

在 shell 執行 slide 的安裝指令：

claude plugin marketplace add JuliusBrussee/caveman
claude plugin install caveman@caveman

第 1 行把 GitHub repo 加成 marketplace；第 2 行從這個 marketplace 安裝 caveman。這是 shell 的寫法；p.6 是 session 內的寫法。

p.17

為什麼要壓縮 token Why Compress an Agent's Tokens?

Log、diff、tool 輸出會塞滿 context。每一輪都要付 token 與等待時間。等到 compaction 才處理，又會丟掉細節。

原則：兩個方向都壓縮。原文要保留，因為 1 行摘要可能丟掉 debug 需要的資訊（p.25 取回原文）。

p.18

兩個方向 Caveman Compresses Tokens in Two Directions

輸入方向：本機 proxy 壓縮 model 讀到的 log、tool 結果、diff、檔案。輸出方向：response skill 讓 model 寫得更短。

Slide 的數字：output token 少 65%。Skill 本身會增加 input token，所以整個 session 省得比較少。

輸入方向通常更重要：每一步都重送整個 context。p.51 的案例中，input token 約是 output 的 14 倍。

EXAMPLE

Slide 的示範：先輸入 /caveman ultra，再輸入「Run the tests and explain the failure.」。

p.19

走一次例子（選讀）Walk Through an Example

輸入 /caveman ultra 之後，各個機制依序出場：hook 記下模式，proxy 壓縮輸出，model 回簡短診斷，MCP 在需要時取回原文。這頁是選讀。

Slide 的 7 步，對照本段開頭的圖：hook 記下模式、注入提醒（1–2）→ agent 跑測試，proxy 壓縮輸出（3–5，上方箭頭）→ model 回簡短診斷（6，下方箭頭）→ MCP 取回原文（7）。

p.22

Response skill The Response Skill Makes Output Less Verbose

Response skill 規定回答的寫法：保留技術內容，刪掉客套與贅字。它改變 agent 的溝通方式。

保留清單裡有否定詞。刪掉一個「not」，意思就整個反過來。數字與單位也一樣不能刪。

p.23

Command：給使用者明確的控制 Commands Provide Explicit User Control

Command 讓你明確控制模式與操作。/caveman 切換壓縮等級；其他 command 各做一件事。

  • /caveman [lite|full|ultra] 開啟（預設 full，ultra 壓最多）；/caveman off 關閉。
  • 單一操作：/caveman-commit、/caveman-review、/caveman-compress（壓縮 memory 檔）、/caveman-stats、/caveman-help。

argument-hint 是自動完成時的參數提示；$ARGUMENTS 換成你輸入的參數。依官方文件，command 與 skill 已合併，兩者都產生 /名稱。

p.24

Hook 讓模式持續有效 Hooks Make a Prompt-Time Choice Persistent

你在某個 prompt 選的模式，之後每一輪都要有效。SessionStart hook 負責初始化；UserPromptSubmit hook 偵測對話中途的切換。

HookScript做什麼
SessionStartcaveman-activate.js決定並保存模式；注入規則；compaction 後重新注入；清理舊狀態
UserPromptSubmitcaveman-mode-tracker.js檢查每個 prompt；偵測 /caveman ultra 或「normal mode」；更新模式

為什麼要 hook：模式只在一個 prompt 說過一次。幾輪之後或 compaction 之後，model 可能忘記。Hook 每次都執行，模式就不會消失。

CAUTION

Slide 的 hook 設定是簡化寫法。實際寫設定時，用 p.12 的官方格式：事件 → matcher 群組 → hooks 陣列。

p.25

MCP：把壓縮做成 tool MCP Exposes Compression as Callable Tools

Caveman 的 MCP server 提供 5 個 tool。最重要的是 caveman_retrieve：用 recovery handle 取回一字不差的原文。

Tool作用
caveman_compress壓縮內容，並回傳 recovery handle
caveman_retrieve取回 byte-exact 的原文
caveman_stats壓縮統計
caveman_toon_encodeJSON 轉成 TOON（較省 token 的格式）
caveman_toon_decodeTOON 轉回 JSON

Slide 的範例回傳：compressed（「3 tests fail. Root error: timeout.」）、ratio 0.72、recovery_handle ccr_abc123。壓縮結果進 context；agent 需要細節時，拿 handle 呼叫 caveman_retrieve。

p.26

Proxy 壓縮 model 讀到的內容 The Proxy Compresses What the Model Reads

本機 proxy 位在 coding agent 與 model provider 之間。每個 request 都經過它。它依內容類型壓縮，再轉給 provider。

類型保留什麼
Logerror、stack trace、開頭與結尾
Codeimport、signature、type、函式本體
Diff檔案與 hunk 標頭、修改的行
JSONkey、結構、出錯的子樹
搜尋結果高價值的命中、診斷訊息
HTML / 文字標題、相關段落

Proxy 與 MCP 的差別，見本段開頭的圖。

為什麼不用 hook：slide 指出，hook 不能透明地改寫送給 LLM 的 request。官方文件列出的 hook 改寫，也只到單一 tool 的輸入或輸出。自己寫 harness 的話，可以直接在 harness 裡壓縮。

Proxy 怎麼插進去：Claude Code 依 ANTHROPIC_BASE_URL 決定 request 送到哪裡（官方文件）。把它指向本機 proxy 即可。Slide 沒有寫 Caveman 的設定細節。

p.27

各機制的分工 How Capabilities Are Used in Caveman

Caveman 分成四層：打包層（plugin）、機制層（skill、command、hook、MCP）、狀態與壓縮 engine、攔截層（proxy）。

每個零件各管一件事：skill 管回答風格；hook 啟動並維持模式；command 給你控制；MCP 提供壓縮與取回；plugin 負責安裝與更新；proxy 攔截 request。

NOTE

選擇規則（延伸 L2 p.50）：每次都要發生，用 hook。要讓使用者控制，用 command。要讓 agent 主動呼叫，用 MCP。要改 model 讀到的每個 request，只能在 harness 或 proxy 這一層做。

p.29

擴展的三個軸 Three Axes of Scaling

三個方向：平行（同時做多件事）、subagent（子任務交給新的 context）、長時間執行（同一件事做更久）。Agent team 與 dynamic workflow 組合這三個軸。

軸做法買到什麼
廣度平行的 agent：每個獨立任務一個 session，各有自己的 working treeThroughput（牆上時間）；答案不會更好
廣度＋深度Subagent：有邊界的任務在新 context 執行，只回摘要Throughput 與專注
時間長時間執行的 agent：一件大工作跨很多步更大的範圍，更少人工介入

「答案不會更好」：3 個 session 做 3 件事，總時間接近 1 件。每件的品質，仍是一個 agent 的水準。

p.30

手動平行：一個任務一個 worktree Parallel Agents by Hand

每個任務開一個 session，每個 session 在自己的 git worktree 裡。一個 session 改的檔案，碰不到另一個 session 的檔案。

EXAMPLE

開兩個 terminal，各跑一行（slide 的示範）：

# terminal 1：做新功能
claude -w feature-payments

# terminal 2：修 bug
claude -w bugfix-auth

依官方文件（2026-10）：

  • -w 是 --worktree 的縮寫。Worktree 建在 .claude/worktrees/<name>/，branch 叫 worktree-<name>。
  • 離開 session 時，worktree 若有改動，Claude Code 問你要保留或刪除。
  • Desktop app：slide 寫每個新 session 自動建立 worktree；官方文件寫開 session 時選 worktree 選項。
CAUTION

Worktree 是全新的 checkout，沒有 .env、node_modules 這類未進 git 的檔案。先安裝相依套件，或用 .worktreeinclude 列出要複製的檔案。

p.31

Git worktree：一個 repo，多個工作目錄 Git Worktree: One Repo, Many Working Directories

三個目錄共用一個 .git（歷史、branch、objects、remotes）。三個 agent 各在自己的目錄與 branch 工作，不必切 branch，也不必 stash。

Slide 的配置：Agent 1 在 ../repo-main（main）做 review；Agent 2 在 ../feat-auth（feature/auth）做新功能；Agent 3 在 ../fix-flaky（fix/flaky-test）debug。

和 clone 比：worktree 共用 object 與歷史。在一個 worktree commit，其他 worktree 立刻看得到。

CAUTION

同一個 branch 不能同時在兩個 worktree checkout，git 會報錯。Worktree 只隔離檔案；port、資料庫、最後的 merge，仍要你處理。

p.32

手動平行的極限 Where Hand-Run Parallelism Stops

開 3 個 session，你還記得住計畫。開 20 個，你需要一個自己的分身。

Slide 列的問題後面哪個工具處理（本筆記整理）
計畫只在你腦中Subagent：主 agent 持有計畫。Workflow：script 持有計畫
Session 之間看不到彼此Agent team：teammate 直接傳訊
你要自己整合 branch仍要有人整合；C compiler 案例用 git 迴圈（p.53）

p.33

Subagent：為什麼要用 Subagents: Why?

Subagent 是專門的助手，有自己的 context window、tool 與權限。最大的好處：雜訊留在 subagent，主對話只收到摘要。

  • 保護 context：log、搜尋結果、整份檔案，留在 subagent 的 context。
  • 強制限制：限定能用的 tool 與 model。
  • 重用：寫好的 subagent 可以跨專案、跨團隊共用。
  • 平行：style-checker、security-scanner、test-coverage 同時跑。總時間由最慢的一個決定：2、3、5 分鐘的工作，約 5 分鐘跑完。
  • 控制成本：簡單的工作交給較便宜、較快的 model，例如在 frontmatter 寫 model: haiku。
NOTE

比喻：同事翻了 30 份文件，只交回一頁結論。Subagent 是那位同事；摘要是那一頁。

p.34

內建的 subagent Built-In Subagents

Claude Code 內建三個 subagent，Claude 會自動委派給它們：Explore、Plan、general-purpose。

Subagent用途
Explore唯讀的程式碼搜尋；不能用 Write 與 Edit；每次呼叫可設徹底程度（quick、medium、very thorough）
PlanPlan mode 裡的唯讀研究；探索過程不進主對話
general-purpose要探索又要動手的多步驟工作；可用所有 tool

Explore 與 Plan 不載入 CLAUDE.md 與 git status，所以又快又便宜。

CAUTION

這也代表 Explore 看不到你寫在 CLAUDE.md 的規則。主 agent 委派時，要把相關規則寫進任務訊息。

p.35

定義一個 subagent Defining a Subagent

一個 subagent 就是一個 Markdown 檔：YAML frontmatter 加 body。Body 是它的 system prompt。

  • name、description 必填。Claude 依 description 決定何時委派；description 寫「use proactively」，Claude 會更主動委派。
  • tools：只給 3 個唯讀 tool，reviewer 就不能改檔。省略 tools，它繼承所有 tool。
  • model：sonnet、opus、haiku、fable、完整 model ID，或 inherit（同主對話）。
  • 位置：.claude/agents/（專案，放進 git）；~/.claude/agents/（個人，所有專案）。

依官方文件，存檔後幾秒內生效，不必重開 session。例外：在新的 agents 目錄建第一個檔時，要重開一次。

p.36

巢狀 subagent Defining a Nested Subagent

Subagent 的 tools 裡要有 Agent，它才能再開子 subagent。Slide 寫最多 5 層，2 到 3 層最好；官方文件（2026-10）寫預設最多在主對話下 3 層。

  • Agent 是開 subagent 的 tool。列了 tools 卻沒列 Agent，就不能再委派。
  • 調整層數：環境變數 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH。設成 1 就關閉巢狀。
  • 到達上限時，Claude Code 拿掉 Agent tool。這個 subagent 只能自己做完，回傳一段摘要。
NOTE

為什麼 2 到 3 層最好：每往上一層，結果就再摘要一次，細節跟著流失。層數越多，延遲也越長。

Dynamic workflow Dynamic Workflow

Dynamic workflow 是一段 JavaScript script，在背景指揮很多個 subagent。任務需要的 agent 多到一段對話協調不了時，就用它。

例子：整個 codebase 的 bug 掃描、500 個檔案的 migration、交叉查證的研究、從多個角度擬計畫。

關鍵差別在誰持有計畫。Subagent 與 team 由 Claude 一輪一輪決定下一步；workflow 由 script 決定。中間結果存在 script 變數，不進 Claude 的 context。

EXAMPLE

兩種開始方式（slide 與官方文件一致）：

ultracode: audit every API endpoint under src/routes/ for missing auth checks

# 整個 session 讓 Claude 自己決定何時用 workflow
/effort ultracode

用 /workflows 看進度。官方文件提醒：ultracode 讓每個任務用更多 token。

agent() 開一個 subagent；pipeline() 對每個檔案各開一個。Script 就是計畫，可以存下來重跑。

p.48

長時間執行：/goal Long-Running Agents: /goal

給一個可以驗證的終點。Claude 會一直做，直到條件成立。

EXAMPLE

Slide 的示範：

/goal "npm run lint exits with zero errors"

運作方式（官方文件）：每一輪結束，另一個小而快的 model 檢查條件。還沒達成，Claude 繼續；達成或判定不可能，goal 就清除。完成與否由另一個 model 判斷，不由做事的 model 自己判斷。

  • 好的條件：「all integration tests pass」。壞的條件：「refactor the code」，因為無法驗證。
  • 檢查的 model 不自己跑指令，只讀對話內容。條件要寫成 Claude 的輸出能證明的事，例如「npm test exits 0」。
  • Slide 寫：條件成立或 --max-tries 用完時停止。官方文件（2026-10）沒有列出 --max-tries；它建議在條件裡寫「or stop after 20 turns」。
  • 輸入 /goal 看狀態；/goal clear 提早結束。
p.49

長時間執行：/loop Long-Running Agents: /loop

/loop 依固定間隔重跑同一個 prompt，直到你停止它。它是觸發器，不是測試。

EXAMPLE

Slide 的示範：每 5 分鐘檢查一次 CI。

/loop 5m "check CI, fix whatever broke"
  • 間隔單位（官方文件）：s、m、h、d。省略間隔，Claude 自己決定每次等多久（1 分鐘到 1 小時）。
  • 省略 prompt：執行你的 loop.md；沒有 loop.md，就執行內建的維護 prompt。.claude/loop.md（專案）優先於 ~/.claude/loop.md（個人）。
  • 停止：slide 寫在等待下一輪時按 Esc。官方文件（2026-10）寫：Esc 停止由 Claude 決定間隔的 loop；固定間隔的 loop 要請 Claude 取消，或 7 天後自動過期。Session 關掉，loop 也停止。

一句話分辨：/goal 在條件成立時停；/loop 在你叫它停時停。

16 個 agent 怎麼協調 How the Sixteen Agents Coordinated

靠普通的基礎設施協調：container、git、文字檔。沒有特別的協調框架。

  • 每個 agent 有自己的 container 與 git checkout；用 lock file 認領任務。
  • Git 是協調層，也是整合層。
  • 新 session 先讀進度文件，找回 context。狀態放在檔案，不放在 model（L2 的 memory 觀念）。

p.53

Git 當協調層 Git as the Coordination Layer

沒有聊天，也沒有 manager agent。每個 agent 重複同一個四步迴圈，git 處理重複認領。

  1. 讀 repo：clone，掃過文件與 log。
  2. 認領任務：在 current_tasks/ 建一個 lock file。
  3. 實作並測試：在自己的 container 裡做。
  4. Merge、push、解鎖：先 pull 別人的修改，再 push，最後刪掉 lock file。
NOTE

為什麼 git 擋得住重複認領：遠端有新 commit 時，git 拒絕你的 push。後到的 agent 必須先 pull，然後就看到 lock file。這是樂觀鎖（optimistic locking）。

p.62

分隔頁 Programming / Software 3.0

開始講 Programming 3.0 與 Software 3.0。

p.63

Programming 3.0 Programming 3.0

每一代都在人與硬體之間多加一層。3.0 的人只用自然語言說目標；agent 寫程式碼。這是講者自己的用語，和 Karpathy 的 Software 3.0 不同。

世代人做什麼到硬體的路徑

Karpathy 用「程式是什麼」來分世代：1.0 是原始碼，2.0 是神經網路權重，3.0 是用自然語言寫的 prompt。

EXAMPLE

不確定性 Uncertainty in Programming 3.0

不確定性是 Programming 3.0 的核心議題。你要學會和它相處。

p.66

不確定性是新的嗎？Is Uncertainty New?

不是。「同樣的原始碼，不同的輸出」早就存在。Programming 2.0 已經發展出一套對策；3.0 在同樣三個地方加上新的來源。

來源2.0 的問題2.0 的對策3.0 新增的
硬體32 位元或 64 位元、endianness固定寬度型別、cross-compilation、虛擬化GPU 運算：不確定的 kernel、浮點數差異
環境並行、不可靠的網路memory consistency model、idempotent API產生程式碼時就和環境互動
軟體compiler 版本、相依套件漂移升級前完整測試model 的 kernel 不同、sampling

2.0 的對策可以沿用：固定介面、讓操作可重複、測試。

p.67

從意圖到結果 A Bit More Uncertainty: From Intent to Result

從「人的需求」到「程式結果」，1.0/2.0 的路徑經過程式設計師，3.0 的路徑經過 LLM agent。3.0 多了一個問題：只靠一個 prompt，輸入本身就模糊。

Slide 的註解：2.0 也有意圖落差，只是大家常忽略它；formal verification 是一種解法。3.0 的模糊輸入，還需要更多研究。

NOTE

工程師拿到一句話的需求會追問；agent 不一定會。Superpowers 的 brainstorming skill（p.10）先釐清需求，補的就是這個落差。

p.68

和不確定性相處 Live With Uncertainty

四個不確定性的來源：自然語言、檢索、model 生成、agent 與 tool 的迴圈。程式一旦產生，通常是確定的。

  • 自然語言：語意本身有歧義。
  • 檢索漂移：index 更新、chunking 方式、context 截斷。
  • Model 生成：sampling；軟硬體的不確定性。
  • Agent 與 tool 的迴圈：trajectory 與環境不確定、tool 失敗、環境改變。

產生的程式通常是確定的，除非它執行時又呼叫 model 或 tool。所以 commit、review、測試產生的程式碼，不確定性就留在產生階段。

p.69

Programming 3.0 的最佳實踐 Best Practices for Programming / Software 3.0

三組做法：先定義（寫明假設）；再控制（提案與執行分開、管理 context、指定結果）；最後驗證（縮短產生與驗證的迴圈、多量一層）。

組做法在 Claude Code 怎麼做（本筆記整理）
1 定義先寫明假設；模糊處先讓 model 確認Plan mode；brainstorming skill
2 控制Agent 提出計畫，驗證後才 commit權限模式；PreToolUse hook
2 控制明確管理 context；清掉過期資訊CLAUDE.md、/memory、subagent
2 控制指定結果：需求、invariant、限制、驗收測試/goal 的可驗證條件
3 驗證便宜、頻繁的檢查，勝過最後一次大 reviewPostToolUse hook 跑測試
3 驗證多量一層：測試、多個指標、可推理的合成負載verification subagent
p.70

結論原則 Closing principle

不要期待 agent 是確定的；要讓 agent 周圍的系統可靠。自主程度要配合風險：自主越多，不確定性與風險越高。

EXAMPLE

配合風險的例子。改文件：可以用 bypass，事後看 diff。改 production 設定：用 manual 模式，加上 PreToolUse hook 擋掉危險指令。Agent 一樣；周圍的防護不同。

帶走的重點

  • Model 相同，workflow 不同，結果就不同。Skill 定義流程；hook 保證 agent 一定讀到流程。
  • Token 要雙向壓縮：proxy 管 model 讀什麼，skill 管 model 寫什麼。原文要能取回。
  • 平行買到 throughput，不會讓答案更好。Worktree 隔離檔案；整合仍要有人做。
  • Subagent 保護主 context：新 window 做事，只回摘要。只要結果，用 subagent；要討論，才用 agent team。
  • /goal 在可驗證的條件成立時停；/loop 在你停止它時停。
  • Agent 本身不確定。可靠來自周邊系統：可驗證的目標、測試、配合風險的權限。

自我檢查

你已經裝好 Superpowers 的 9 個 skill。為什麼還需要 SessionStart hook？

Skill 只是可用；model 可能沒查 skill 就開始寫 code。Hook 每個 session 一定執行，在 agent 動作前放入選 skill 的規則。Matcher 含 clear 與 compact，所以清除或 compaction 後也會重新放入。

Caveman 為什麼要用本機 proxy 壓縮輸入，不用 hook 或 MCP？

壓縮要套用到送給 model 的每一個 request。Hook 不能透明地改寫 LLM request。MCP 只在 agent 呼叫時執行，也不能改 context。Proxy 位在 agent 與 provider 之間，每個 request 都經過它。

你要同時審查 3 個獨立模組的安全問題，只需要每個模組的問題清單。用 subagent 還是 agent team？

用 subagent。三個任務互不相依，只要結果，不需要討論。Subagent 只把摘要放回主 context，token 成本較低。如果審查者要互相挑戰彼此的發現，才值得用 team。

「/goal refactor the code」有什麼問題？怎麼改？

這個條件無法驗證，檢查的 model 判斷不了何時完成。改成可測試的終點，例如：/goal all tests in tests/ pass, ruff check . reports no errors, and no public function signature changes。

16 個 agent 寫 C compiler 時，兩個 agent 同時認領同一個任務，怎麼解決？

認領就是在 current_tasks/ commit 一個 lock file 再 push。Git 拒絕後到的 push；那個 agent pull 之後看到 lock file，就改挑別的任務。
