這堂課把 Claude Code 拆開，看一個 coding agent 由哪些零件組成。重點有三個：agentic loop、memory、四種擴充機制。

  • Agent = model + loop。一個 prompt 會跑很多圈「model 提議 → harness 執行 tool → 結果放回 context」，直到任務完成。

  • 四種擴充機制各管一件事。Skill 管怎麼做，MCP 管連外部，hook 管事件發生時一定要做的事，plugin 管打包分享。

Agentic loop：一個 prompt 背後發生什麼

p.07

Agentic loop 的三個動作 The Agentic Loop

Agent 重複做三件事：收集 context、產生下一個 action、執行 tool。每一步的輸入，都是上一步的結果。

一個 prompt 不等於一次 API request。Claude Code 會一直跑這個 loop，直到 model 判斷任務完成。

  • Model：決定下一步。它只輸出文字。
  • Harness：Claude Code 這個程式。它組 context、檢查權限、呼叫 tool。
  • 你的電腦：真正執行指令的地方。
NOTE

比喻：model 是一位只能用對講機工作的工程師。他說「幫我跑 pytest」。助手（harness）去跑，再把結果念回來。工程師聽完，再決定下一步。

p.08

還沒打字，context 已有 10k 以上 token Context Before You Type

你輸入第一個字之前，context 已經有 10,000 個以上的 token。

這些 token 來自下面幾塊：

  • System：Claude Code 的系統指令。
  • Project：專案環境資訊。
  • Memory：CLAUDE.md 與其他持久筆記。
  • Tools：Read、Edit、Bash、Glob、Grep、Web、Agent 等 tool 的定義。
  • Skills / MCP：只有名稱與描述。
  • User：你的 prompt，例如「Fix the failing auth test」。

Skill 與 MCP 一開始只放名稱和描述。Model 決定要用時，才載入完整內容。這個做法叫 progressive disclosure（漸進載入）。目的是節省 context。

CAUTION

這些固定內容，每一次 model 呼叫都會再送一次。System prompt 和 tool 定義越長，每一步就越貴。L8 會談怎麼用 prefix cache 降低這筆成本。

p.09

不會上傳整個 repo It Doesn't Send Your Repository

Claude Code 不會把整個 repo 送給 model。Repo 留在你的磁碟上；需要時才拿一小片。

例：model 想找登入相關的程式。它呼叫 Grep("authentication")。Grep 只回傳幾行符合的內容。只有這幾行進入 context。

原因：repo 可能有幾千個檔案，遠大於 context window。按需讀取（on-demand）讓 agent 能處理大型 repo。

CAUTION

常見誤解：「agent 看過整個專案」。實際上，agent 只看過它讀取的部分。它沒讀到的檔案，它不知道。所以 agent 可能漏掉沒被搜尋到的相依程式。

p.10

Model 提議，harness 執行 Model Proposes and then Harness Executes

Model 只輸出一個請求，例如 Bash("pytest")。Harness 檢查權限後，在你的電腦上執行。

  1. Model 輸出 tool call：tool 名稱加參數。
  2. Harness 解析請求，檢查權限。
  3. 你的電腦執行指令，產生 stdout 與 stderr。
  4. Harness 把輸出包成 tool_result，放回 context。

Model 本身碰不到你的檔案。所有動作都要經過 harness。所以安全控制都放在 harness 這一層。

EXAMPLE

簡化後的訊息往來：

model   → tool_use     Bash {"command": "pytest"}
harness → tool_result  "3 failed, 41 passed … test_auth.py:52 AssertionError"
model   → tool_use     Read {"file_path": "src/auth/session.py"}
p.11

一個 prompt，多次 inference One User Prompt Triggers Many LLM Inferences

一個 user turn 會展開成一條鏈：inference → tool → inference → tool → … → 回答。

Slide 的例子：跑 pytest → 讀 session.py → grep create_session → 改 session.py → 再跑 pytest → 全部通過。這裡有 5 次 tool 執行和 6 次 inference。

每次 inference 都送出當下完整的 context。步驟越多，成本和延遲就越高。L8 會把這件事量化。

NOTE

這是 agent 和 chatbot 的根本差別。Chatbot：一問一答。Agent：一問多步，每一步都看上一步的結果。

p.12

權限層在提議與執行之間 Permissions Sit Between Intent and Execution

Tool call 只是一個提案。提案要經過你或另一個 model 同意，才會執行。

模式行為
Manual每個動作都先問你。
Accept Edits檔案編輯自動同意；其他動作仍會問。
Bypass permission全部放行，不問。
Auto由一個小 model 判斷能不能執行。

每次檢查有三種結果：allowed（執行）、ask（先問你）、denied（不執行）。

CAUTION

例：Bash("rm -rf build/")。Manual 模式會先問你；bypass 模式會直接執行。Model 判斷錯誤時，bypass 沒有任何防線。只在可丟棄的環境（container、VM）裡用 bypass。

p.16

Context 一直變大，滿了就 compaction Context Grows, Then Gets Compacted

每一步都讓 context 變大。快滿時，Claude Code 把舊的過程摘要起來，再重新放入 CLAUDE.md 和 memory。這個動作叫 compaction。

  • 讓 context 變大的東西：model 回覆、讀進來的檔案、指令輸出。
  • Compaction 是有損的（lossy）。摘要會丟掉細節。
  • CLAUDE.md 在 compaction 後會重新載入。所以重要規則要寫在 CLAUDE.md，不要只在對話裡講。
  • Slide 的數字：常見的 context window 是 1M token。今年初常見的是 256K。
  • Context 不是免費的。大部分成本來自 prefix cache read：每一步都重讀前面同樣的內容。
NOTE

比喻：context 像一塊白板。寫滿了，就拍照存檔（摘要）、擦掉、只抄回重點。照片會漏掉細節。你在對話中途口頭說過的規則，可能就在這一步消失。

p.17

小結：agentic loop Summary: The Agentic Loop

Prompt 加 context → model 提議 → harness 執行 → 結果併入 context → 重複，直到完成。

一句話記住：model 決定下一步；harness 負責執行、檢查權限、管理 context。

p.19

狀態 + 無狀態的 LLM + tool Agent Memory

Agent = 狀態（context 加 memory）+ 無狀態的 LLM + 會動手的 tool。

LLM 每次被呼叫，都從零開始。它不記得上一次呼叫。Agent 的「記得」，完全來自每次呼叫時送進去的 context。

NOTE

L1 的類比：LLM 像 CPU，context window 像 RAM。CPU 不保存資料；資料在 RAM 和硬碟。對 agent 來說，memory 檔案就是硬碟。

p.20

Context 是一種 memory Context Is One Type of Memory

Agent 的記憶分兩種：context 是 working memory，session 結束就消失；persistent memory 存在檔案裡，下個 session 再載入。

Agent 在兩次執行之間沒有狀態。每個 session 都從零開始。實務上，「memory」就是 session 開始時載入的檔案。

所以每寫入一條 memory，就等於決定未來每個 session 要重讀什麼。寫入前要想清楚。

p.21

為什麼 agent 需要 memory Why Agents Need Memory

沒有 memory，agent 每個 session 都是第一天上班的新人。Memory 讓一次性的指示變成慣例。

問題例子
重複交代每個 session 都要說一次「測試用 pytest -x」。
決策遺失上次決定「不要改 v1 API」。Compaction 之後，原因不見了。
重複探索每次都要重新 grep 一遍，才知道目錄怎麼配置。
行為不一致今天的 session 用一種寫法，明天的 session 用另一種。

Claude Code 有兩套記憶：CLAUDE.md 是你寫的規則；auto memory 是 Claude 自己寫的筆記。兩者在每個 session 開始時都會載入。p.23 與 p.22 內容相同。

p.24

CLAUDE.md 放在哪裡 Where CLAUDE.md Lives

CLAUDE.md 有四個層級。範圍最大的先載入；離你最近的最後讀。

  1. Managed policy（組織）：例如 Linux 的 /etc/claude-code/CLAUDE.md，macOS 的 /Library/Application Support/ClaudeCode/CLAUDE.md。使用者不能排除。
  2. User:~/.claude/CLAUDE.md。你在所有專案的個人偏好。
  3. Project:./CLAUDE.md 或 ./.claude/CLAUDE.md。團隊共用，放進 git。
  4. Local:./CLAUDE.local.md。你在這個專案的個人設定。把它加進 .gitignore。

這些檔案不會互相覆蓋。Claude Code 把它們全部串接進 context。最後讀到的，是離你最近的那一份。

p.25

CLAUDE.md 該放什麼 What Belongs in CLAUDE.md

只放 agent 需要、又無法便宜推得的資訊。每個檔案控制在 200 行以內。

Slide 的對比：context 是暫時租用的空間；memory 是你長期持有的空間。持有的東西，每個 session 都要付一次成本。

該放不該放
指令：怎麼跑 test、build、lintModel 本來就懂的語言或框架知識
硬規則：不准直接 commit 到 main；不准改生成檔Linter 或 formatter 已經強制的風格
難推得的事實：目錄配置、誰負責哪塊、地雷長篇說明、changelog、任何 secret

寫法：Markdown 標題加條列。規則要具體。規則之間不能矛盾，也不能過期。

p.26

太長了？拆到 .claude/rules/ Getting Too Long? Split It Into .claude/rules/

CLAUDE.md 變長時，把細節拆到 .claude/rules/，一個主題一個檔。

在 rule 檔加上 paths: frontmatter。Claude 讀寫符合條件的檔案時，這條 rule 才載入。沒有 paths: 的 rule，每個 session 都載入。

效果：你改 UI 時，API 規則不會進入 context。CLAUDE.md 保持精簡，細節放在 rules。

p.27

Auto memory：Claude 自己的筆記 Auto Memory: Claude's Own Notes

Auto memory 是 Claude 自己寫下的筆記，存在 ~/.claude/projects/<project>/memory/。每個檔案有一個 type。

  • user：你的角色、專長、工作偏好。
  • feedback：你給的糾正、你認可的做法。
  • project：進行中的工作、程式碼裡看不到的決策。
  • reference：存在專案外部的資訊。
  • MEMORY.md 是索引。每個 session 載入它的前 200 行或前 25KB。
  • 存在本機。同一個 repo 的 worktree 共用同一份。
  • 預設開啟。用 /memory 可以關閉。
EXAMPLE

你糾正 Claude：「測試請用 pytest -x，不要跑全部。」Claude 可能把這件事寫成一條 feedback memory。下一個 session，它直接照做。

p.28

用索引找 memory Retrieval Uses an Index

Auto memory 先載入一份小索引。需要時，才讀對應的 topic 檔。

  1. Session 開始。
  2. 載入 MEMORY.md 索引。
  3. 找出和目前任務相關的主題。
  4. 讀取那個主題的 topic 檔。
  5. 把內容用在任務上。

這個設計讓常駐的 context 保持很小。概念和書的目錄一樣：先看目錄，再翻到需要的那一章。

p.31

記憶的成本 The Cost of Remembering

每個常駐的 token 都是租金。每個 session 開始時，都要再付一次。

  • Memory 和任務搶同一個 context window。
  • 過期的 memory 比沒有 memory 更糟。它會誤導 agent。
  • 把 memory 當程式碼管理：review、刪減、放進版本控制。
  • Context 大小有上限。送給 model 的每個 token 都要付費。
NOTE

算一下：一份 2,000 token 的 CLAUDE.md，在一個 100 步的 session 裡會被送出 100 次。Prefix cache 讓重送變便宜，但不是零。

p.33

六個核心 tool Become an Actionable Agent: The Core Tools

六個核心 tool：Read、Search、Fetch、Edit/Write、Shell、Delegate。Model 自己決定用哪一個。

Tool做什麼要注意
Read開檔、看狀態最常用的 tool
Search（grep、glob）不用全讀，就能找到東西結果太多會塞滿 context
Fetch抓網頁或文件會把不受信任的文字帶進 context
Edit / Write修改檔案第一個有後果的 tool
Shellbuild、test、git沒有 sandbox 時，等於整台電腦
Delegate開一個 subagent回傳的是摘要，不是全部過程

CAUTION

Fetch 回來的網頁可能藏有 prompt injection，例如一行「忽略之前的指示」。Agent 要把 tool 的輸出當作資料，不能當作指令。

p.35

四種機制，四種問題 Extending an Agent

Skill 決定怎麼做；MCP 連到外部；hook 在事件發生時強制執行；plugin 負責打包與發佈。

機制解決什麼什麼時候想到它
Skill做事的程序與知識「我想教 agent 一套 SOP」
MCP外部資料與動作「agent 要碰 GitHub、資料庫、Slack」
Hook生命週期事件上的自動動作「這件事每次都要發生，不能靠 model 記得」
Plugin打包、版本、分享「我想讓別人一個指令就裝好整套設定」
p.36

四種機制掛在 loop 的哪裡 Extension Points in the Agent Loop

Skill 影響 model 推理；MCP 擴充可選的 tool；hook 在 tool 執行前後等事件觸發；plugin 把三者包在一起。

關鍵差別：skill 和 MCP 都要等 model「決定使用」才生效。Hook 綁在事件上，不需要 model 同意。所以必須強制的規則，要用 hook。

p.38

Skill 是可重用的程序 Skills as Reusable Procedures

Skill 裝三種東西：領域知識、參考資料、可重複的流程。

  • 兩種觸發方式：model 判斷需要時自己載入；或你直接輸入 /release 2.4.0。
  • Slide 的觀點：skill 是一種 context engineering。Skill 本身不執行任何東西。它在對的時間，把對的指示放進 context。推理仍然在執行時發生。
NOTE

比喻：skill 像新人手冊裡的一章 SOP。平常只看目錄（description）。要做那件事時，才翻到那一章（body）。

p.39

Skill 的檔案結構 Skill Structure

一個 skill 是一個資料夾。SKILL.md 必要；references/ 與 scripts/ 可選。

  • Frontmatter 的 description 決定 skill 何時被找到。
  • Body 是程序本身。
  • references/ 放細節文件，需要時才讀。
  • scripts/ 放確定性的程式。程式能穩定做對的事，不要交給 model 做。

使用方式：輸入 /release 2.4.0。$ARGUMENTS 會換成 2.4.0。

p.40

Skill 的觸發與 context 成本 Skill Invocation and Context Cost

Session 開始時，只載入每個 skill 的 description。Skill 真的執行時，才載入 body。

  • Model-invoked：description 和任務相符，Claude 自己載入。
  • User-invoked：你輸入 /<skill-name>。
  • 有副作用的流程（發布、部署、刪資料）應該只能手動觸發。做法：在 frontmatter 設 disable-model-invocation: true。
  • 每個 description 要清楚，彼此要有差別。描述太像時，model 容易選錯 skill。
p.41

MCP：外部能力層 MCP as an External Capability Layer

MCP（Model Context Protocol）用一個標準協定，把 agent 接到外部服務。

例子：讀寫 GitHub issue、查資料庫、拿監控數據、讀 Figma 設計稿、發 Slack 訊息、操作瀏覽器。

MCP 給 agent 的能力，既不在 model 裡，也不在本機檔案裡。

p.42

一次 MCP tool call 的流程 How an MCP Tool Call Works

MCP tool call 和本機 tool 幾乎一樣。差別只有一個：MCP tool 在另一個 process 執行。

  1. Claude 判斷需要一個動作。
  2. MCP client 呼叫 tool。
  3. MCP server 處理連線。
  4. 外部服務執行操作。
  5. 結構化結果回到 Claude。
  6. Claude 評估結果。

相同點：都有名稱、描述、typed schema；都是「呼叫 → 回傳」。協定只負責傳遞呼叫。要不要呼叫，仍由 agent 決定。

p.43

Hook：生命週期自動化 Hooks as Lifecycle Automation

Hook 綁在 session 的事件上。事件發生，hook 就執行。Model 推理本身沒有 hook，因為推理不是事件。

Slide 上的時間點官方事件名稱典型用途
Session 開始SessionStart載入 context、記 log
送出 promptUserPromptSubmit檢查 prompt、補充 context
Tool 執行前PreToolUse檢查或阻擋
Tool 執行後PostToolUse格式化、跑測試、記 log
結束回覆前Stop確認測試已通過

Hook 可以執行 shell 指令、HTTP request、MCP tool、prompt 或 subagent。官方文件目前列出 30 個以上的事件；上表是最常用的 5 個。

怎麼阻擋：hook 從 stdin 收到一份 JSON，裡面有 tool_name 與 tool_input。PreToolUse hook 判斷後以 exit code 2 結束，這次 tool call 就不會執行。Hook 寫到 stderr 的內容，會回給 Claude 當作原因。

NOTE

Hook 是確定性的（deterministic）。不管 model 怎麼想，hook 都會執行。這是它和 CLAUDE.md 規則最大的差別。

p.45

Plugin：打包層 Plugins as the Packaging Layer

Plugin 是一個可安裝的單位。裡面可以有 skill、hook、subagent 和 MCP 設定。

好處：一個指令就能安裝；版本固定；namespace 避免撞名；團隊可以重用；能透過 marketplace 發佈。

一句話：plugin 讓「在我電腦上能跑的設定」，變成「別人裝得起來的東西」。

p.46

四種機制怎麼組合 How the Four Mechanisms Fit Together

Claude 在中間做推理與 tool use。Skill 提供知識；MCP 連到 GitHub、Slack、資料庫；hook 在每次 tool call 前後觸發；plugin 把三者打包帶到別處。

設計練習：該用哪一種? Design Exercise

判斷每個需求該用 skill、MCP、hook 還是 plugin。先自己作答，再展開答案。

套用公司的 API 規範

Skill。這是知識與程序。

從 Jira 讀一張 issue

MCP。需要碰外部系統。

每次編輯後都自動格式化

Hook。綁在「編輯完成」這個事件上，每次都要發生。

引導一次多步驟部署

Skill。這是一套程序。部署有副作用，建議只允許手動觸發。

任務完成時發通知

Hook + MCP。Hook 抓「完成」事件；MCP 把通知送到外部系統，例如 Slack。

禁止寫入 production

Hook 或 policy。這必須強制，不能靠 model 記得。

在多個 repo 共用整套設定

Plugin。這是打包與發佈的問題。

NOTE

判斷順序（本筆記整理）：要強制嗎？用 hook。要碰外部嗎？用 MCP。要分享嗎？用 plugin。剩下的程序與知識，用 skill。

p.53

MCP 是什麼、為什麼需要 MCP: What and Why

沒有標準時，N 個 AI client 接 M 個服務，要寫 N×M 套整合。MCP 是一個開放協定，把它降成 N+M。

每個 client 只實作一次 MCP。每個服務只提供一次 MCP server。之後，任何 client 都能用任何 server。

NOTE

同樣的想法也出現在 LSP（Language Server Protocol）。LSP 把「M 個編輯器 × N 種語言」變成「M + N」。Slide 也提到 MCP 是 stateless 的協定（見 p.60）。

p.54

MCP 的架構 MCP Architecture

四個角色：host、MCP client、MCP server、外部系統。

  • Host：你在用的 app，例如 Claude Code。
  • MCP client：由 host 執行。每個 server 一條連線。
  • MCP server：把一個系統的能力包成 tool。
  • 外部系統：GitHub、Slack、PostgreSQL，或本機服務。
p.55

三種基本元件 MCP: Three Core Primitives

MCP server 可以提供三種東西：tools、resources、prompts。

元件是什麼例子誰觸發
ToolsClaude 可以呼叫的動作create_issue(…)Model
Resources可讀的資料，例如 issue 或 schemagithub://issues/123Host 決定附加
PromptsServer 提供的 prompt 範本triage_issue(…)使用者

在 Claude Code 裡，MCP prompt 會變成 slash command，例如 /mcp__github__triage_issue 123 high。

p.56

三種元件一起用 How They Work Together

例：「分流 issue #123；如果是嚴重的認證 bug，就指派負責人。」

  • Prompt triage_issue：提供組織的分流程序。
  • Resource github://issues/123：提供這張 issue 的內容。
  • Tool get_related_errors：抓最新的錯誤資訊。

三者各補一塊：程序、資料、動作。

p.57

MCP 安全 MCP Security: The Essential Part

接上一個 MCP server，它就看得到你送的內容，也能用你的憑證做事。

  • Least privilege：token 只開需要的 repo、table、channel。
  • 讀寫分離：寫入動作要經過人工確認。
  • 不信任 tool 輸出：回傳內容永遠不當作指令。
  • 安裝前先審查：第三方 server 可能夾帶 prompt injection。

接之前先問兩個問題：它能讀什麼？它能改什麼？

p.58

MCP gateway 是什麼 What an MCP Gateway Is

MCP gateway 是放在 AI client 與多個 MCP server 之間的控制層。

它像 API gateway，但說的是 MCP 協定（tools/list、tools/call、resources、prompts）。對 client 來說，gateway 看起來就是另一個 MCP server。

Gateway 集中處理 auth、policy、logging、routing、rate limit。

p.59

Gateway 的六項功能 What a Gateway Does

彙整、路由、政策、身分代理、觀測、擴展。

功能說明
Aggregate一條連線、一份有 namespace 的目錄（github.*、jira.*、postgres.*）
Route把每個 call 轉給對應的 server。Mcp-Method header 讓 gateway 不讀 body 就能路由。
Enforce policy誰能連線、哪些 tool 看得到、哪些能呼叫、哪些要人工核准
Broker identityClient 只驗證一次；上游憑證留在 gateway 後面
Observe集中稽核：身分、tool、決策、延遲、結果、成本
ScaleLoad balancing、retry、circuit breaker、目錄快取、quota

適用情境：有很多使用者、agent、server、憑證，或有合規要求，需要一致的管理。

CAUTION

Gateway 本身是信任邊界。風險：憑證權限過大、終端使用者身分遺失、tool 名稱衝突、log 裡出現 secret、單點故障。

p.60

MCP 新版規格（2026-07-28）What is new?

2026-07-28 版是 MCP 推出以來最大的一次修訂。

  • Stateless core：server 不需要保存 session。任何 request 都能送到任何 instance，放在一般 load balancer 後面即可。
  • Routing：Mcp-Method header 讓 gateway 不讀 body 就能路由。List 結果可以用 TTL 快取。
  • Extensions：Tasks（長時間工作）與 MCP Apps（server 渲染的 UI）改成以 extension 提供。

為什麼 stateless 重要：有狀態的連線很難水平擴展。改成無狀態後，MCP server 可以像一般 web service 一樣擴展。

帶走的重點

  • 一個 prompt = 多次 model 呼叫 + 多次 tool 執行。成本與延遲隨步驟數一起成長。
  • Model 提議，harness 執行。權限、安全、context 管理都在 harness。
  • Context 是 working memory，會被 compaction。要長期保留的規則，寫進 CLAUDE.md。
  • Memory 每個 session 都要付費。只放 agent 推不出來的事，並定期清理。
  • 要強制，用 hook。要連外部，用 MCP。要教程序，用 skill。要分享，用 plugin。

自我檢查

你說「修好登入測試」，Claude Code 執行了 5 次 tool。總共至少有幾次 model inference？為什麼後面的 inference 比前面的貴？

至少 6 次：每次 tool 前一次，最後回答一次。每次 inference 都送出完整的 context，而 context 每一步都變長。

你在 CLAUDE.md 寫了「不准修改 gen/」，Claude 還是改了。為什麼？怎麼改成一定擋得住？

CLAUDE.md 只是 context，model 可能沒照做。要強制，就用 PreToolUse hook：檢查 Edit 或 Write 的檔案路徑。路徑在 gen/ 底下，就以 exit code 2 擋下。

有一條規則只和資料庫 migration 有關。它該放在 CLAUDE.md，還是 .claude/rules/?

放在 .claude/rules/db-migrations.md，並用 paths: 指向 migration 目錄。Claude 碰到這些檔案時才載入；平常不佔 context。

為什麼 MCP 的 tool 由 model 觸發，而 prompt 由使用者觸發？

Tool 是單一動作。Model 在推理中判斷何時需要它。Prompt 是一整段工作程序的範本，代表使用者要啟動某個流程。所以 prompt 做成 slash command，由使用者選擇。
