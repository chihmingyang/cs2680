p.26

你熟悉幾個主題 How many of these topics are you familiar with?

六個主題：Transformer 架構、TP / PP / DP / EP、iteration-level scheduling 與 PagedAttention、linear attention、GPU programming、Linux kernel。

每個主題一句話（本筆記補充，Part II 會細講）：

  • Transformer：現在 LLM 的基本架構。核心是 attention：每個 token 都參考前面所有的 token。
  • TP / PP / DP / EP：把工作分到多張 GPU 的四種方式，分別是 tensor、pipeline、data、expert parallelism。p.34 會再提。
  • Iteration-level scheduling：serving 系統每生成一輪 token，就重新組一次 batch。新請求不必等整批結束。
  • PagedAttention：vLLM 的做法。它借用 OS 的 paging，把 KV cache 切成固定大小的 block 來管理。
  • Linear attention：標準 attention 的計算量隨序列長度平方成長。Linear attention 把它降到線性。
  • GPU programming：用 CUDA 或 Triton 寫在 GPU 上執行的 kernel。
  • Linux kernel：作業系統的核心，系統課的常見背景。
NOTE

都不熟也沒關係。這些都是 Part II 的內容。L2 也把 LLM 內部原理往後移了。

p.32

運算：兩個階段，兩種瓶頸 How AI systems differ: compute

一次 LLM 請求分兩個階段：prefill 受算力限制，decode 受記憶體頻寬限制。執行時間取決於輸出長度，事先無法預測。

CPU 與 GPU 分工。GPU 做矩陣乘法（matmul）。CPU 負責其他工作：tokenization、啟動 GPU kernel、搬資料、執行 tool call。叢集裡也常混用不同世代的 GPU 和其他加速器（xPU）。

階段做什麼瓶頸為什麼
Prefill一次處理整段 prompt算力（compute-bound）所有 prompt token 可以平行計算，合成大型 matmul。權重讀一次，就用在幾千個 token 上。
Decode一次生成 1 個 token記憶體頻寬（memory-bandwidth-bound）每個新 token 都要從 GPU 記憶體讀一遍全部權重和 KV cache。讀進來的每個 byte，只做很少的運算。

Decode 只能一個一個來：第 n 個 token 要等第 n−1 個生成後才能算。所以 decode 無法像 prefill 一樣，把很多 token 併成一次大運算。

EXAMPLE

估算 decode 的速度上限。8B 參數的 model 用 BF16 存（每個參數 2 byte），權重約 16 GB。課程叢集的 RTX PRO 6000 Blackwell，記憶體頻寬約 1.6 TB/s。

每生成 1 個 token，GPU 至少要讀完 16 GB：16 GB ÷ 1.6 TB/s ≈ 10 ms。所以單一請求最多約每秒 100 個 token，和 GPU 算力多強無關。這也是 batching 的由來：讀一次權重，同時替 batch 裡的 32 個請求各算 1 個 token。

執行時間無法預測。一個請求跑多久，取決於 model 輸出多少 token。這個數字要等生成結束才知道。所以 scheduler 很難決定先跑誰、要預留多少記憶體。

同一套部署可能撞上三種瓶頸：算力（長 prompt 的 prefill）、頻寬（decode）、容量（KV cache 塞滿記憶體）。

p.33

不確定的運算：加總順序改變結果 How AI systems differ: non-deterministic compute

浮點數加法沒有結合律。加總的順序一變，結果就差一點點；這一點差異可能讓 model 選出另一個 token。

浮點數每做一次運算，就捨入一次。所以數學上相等的兩條算式，在電腦上可能不相等。Slide 舉了分配律：a*(b+c) 和 a*b + a*c 可能不同。Slide 也指出，相等的遞移性可能失效。

EXAMPLE

在 Python（float64）裡自己試：

>>> (0.1 + 0.2) + 0.3
0.6000000000000001
>>> 0.1 + (0.2 + 0.3)
0.6
>>> 10 * (0.1 + 0.2), 10 * 0.1 + 10 * 0.2
(3.0000000000000004, 3.0)

0.1、0.2、0.3 都無法用二進位精確表示。每次加法都要捨入，捨入誤差隨順序落在不同位置。

Batch size 為什麼會改變結果。GPU 把一次 matmul 拆成很多小塊，平行加總；拆法由 kernel 決定。Batch size 改變時，系統可能換一個 kernel，或換一種切法。加總順序跟著改變，結果的最後幾位就不同。

本筆記實測：同樣 4096 個 float32 亂數，分組先加的大小不同，總和分別是 −66.06458、−66.06460、−66.06462。最大差距約 0.00004。

為什麼會換掉 token。Model 每一步替每個候選 token 打一個分數（logit）。Greedy decoding 選分數最高的那個（argmax）。前兩名如果只差 0.00001，加總順序造成的誤差就可能讓兩者互換。

換了一個 token，後面的文字全部跟著改變。這就是 slide 說的蝴蝶效應：matmul 第 7 位小數的變動，可能翻轉下一個 token。

Slide 列出的誤差來源：

  • Runtime：warp 與 block 的排程、記憶體存取順序、非同步 stream、batch size。
  • Software：FMA（乘加一次算完，只捨入一次）和分開算的結果不同；autotuning 可能選到不同 kernel；subnormal（極接近 0 的數）的處理方式不同。
  • Hardware：CUDA core 和 tensor core 的算法不同；Hopper 的 FP8 和 Blackwell 的 micro-scaling（一小塊數字共用一個縮放係數）也不同。
CAUTION

常見誤解：temperature 設成 0，輸出就一定可重現。Temperature 0 只固定了取樣方式。伺服器上同時有哪些請求、batch 多大，你控制不了。對 agent 來說，一個 token 不同，可能換掉整個 tool call。

Slide 的結論：這個領域接受近似運算（approximate computing）。所以評估 agent 時，同一題要跑多次，再看統計結果（L7 談評估）。

p.34

記憶體、儲存與通訊：狀態很大 How AI systems differ: memory, storage and communication

AI 系統的狀態很大：權重從幾 GB 到幾 TB，KV cache 每個 token 要幾十到幾百 KB。瓶頸常在搬資料。

KV cache。Attention 讓每個新 token 參考前面所有 token，所以每個 token 在每一層都要算一組 key 和 value。Model 把它們存起來給下一步重用，這份資料就是 KV cache。

EXAMPLE

每個 token 的 KV cache = 2（K 與 V）× 層數 × KV head 數 × head 維度 × 每個數的 byte 數。

  • Llama 3.1 8B（32 層、8 個 KV head、head 維度 128、BF16）：2 × 32 × 8 × 128 × 2 = 128 KiB。
  • Llama 2 7B（32 個 KV head，沒有共用）：512 KiB。
  • 一個 100K token 的 agent session，在 Llama 3.1 8B 上要約 13 GB 的 KV cache，接近權重的 16 GB。

Prefix cache。很多請求的開頭相同，例如同一份 system prompt。Prefix cache 保留這段開頭的 KV cache 給下一個請求重用，省掉這段的 prefill。Agent 每一步都重送前面整段 context，所以 prefix cache 對 agent 特別重要。

搬資料是瓶頸。GPU 記憶體放不下時，KV cache 要搬到 CPU 記憶體或 SSD，用到時再搬回來。搬運的時間常比計算還長。

多 GPU 通訊。一張 GPU 放不下 model 時，要把工作切到多張 GPU：

  • Pipeline：按層切。GPU 1 跑前半的層，GPU 2 跑後半。
  • Tensor：把每一層的矩陣切開。每張 GPU 算一部分，再合併結果。
  • Expert：MoE（mixture of experts）model 有很多 expert，每個 token 只用其中幾個。不同 expert 放在不同 GPU。
  • Context：把很長的序列切段，分給不同 GPU。

GPU 之間用 NCCL、UCCL 這類 collective 函式庫交換資料。同一台機器內走 NVLink；機器之間走 Ethernet 或 InfiniBand。RDMA 讓網卡直接讀寫遠端記憶體，繞過 CPU 和 OS kernel。

p.35

Model 與 workload 變化快 How AI systems differ: fast-moving models and workloads

Model 架構和使用方式都變化很快。系統要跟著調整；反過來，model 也會配合硬體設計（co-design）。

Slide 列出的 attention 架構：MHA、GQA、MLA、NSA、linear attention。後面幾種的主要目的，是減少 KV cache 或長序列的計算量。例：GQA 讓多個 query head 共用一組 KV。Llama 3.1 8B 用 8 組 KV 配 32 個 query head，KV cache 降為 1/4（對照 p.34 的 512 KiB 與 128 KiB）。

Workload特性對系統的壓力
多輪聊天互動式對延遲敏感
解題（reasoning）輸出很長Decode 時間長
RAG先檢索文件，再回答Context 很長
AgentContext 長，開頭重複Prefix cache 重用很關鍵；需要 routing 與 load balancing

RAG 是 retrieval-augmented generation：先從資料庫找出相關文件放進 prompt，再讓 model 回答。

p.36

可靠性與耗電 How AI systems differ: reliability, power and energy

大叢集裡，故障是常態。Slide 的數字：GPU 年故障率 9%、MTBF 50,000 小時；16K 張 GPU 的叢集，約每 3 小時壞一張。

每 3 小時壞一張的算法。MTBF（mean time between failures）是單一元件平均多久故障一次。叢集裡每張 GPU 都可能故障。所以整個叢集的故障間隔，約等於 MTBF 除以 GPU 數。

EXAMPLE
50,000 小時 ÷ 16,384 張 GPU ≈ 3.05 小時

用年故障率驗算：9% × 16,384 張 ≈ 每年 1,475 張，約每 6 小時一張。兩種算法的量級相同。

對 serving 的意義：GPU 一壞，上面正在跑的請求都要重做。一個跑了 30 分鐘的 agent，可能就斷在這裡（p.46 第 8 題）。

耗電。CPU 約 100–300 W；GPU 約 700–1000 W；一台 server 放 4–8 張 GPU。Server 的功率因此從 800 W 升到 6,000 W，slide 稱為 8 倍。

功率波動。例：訓練時，上萬張 GPU 同時計算，再同時等通訊。整個資料中心的用電跟著一起升高、一起下降。Slide 把「避免功率波動」列為挑戰。

p.38

Agent 是什麼 What is an AI agent?

Agent 是自主運作的軟體系統。它用 AI model 對目標推理、使用外部 tool、執行多步動作，直到任務完成。

Slide 把這個過程拆成 5 步。下面用 L2 的例子「修好登入測試」對照：

  1. Plan：拆解任務。先跑測試，再讀出錯的程式。
  2. Act：呼叫外部 tool，例如 API 或資料庫。這裡用 Bash 執行 pytest。
  3. Observe：解讀 tool 的結果。3 個測試失敗，錯在 test_auth.py 第 52 行。
  4. Adapt：依新資訊修改計畫。下一步改成讀 session.py。
  5. Deliver：測試全部通過，回報最終結果。

Slide 的圖：agent 方塊裡有 LLM、memory、reasoning & planning。Agent 對環境送出 action，環境回傳 observation。L2 p.18 用的是類似的架構圖。

CAUTION

一問一答的 chatbot 不算 agent。它只產生文字，沒有 act 與 observe。判斷方法：系統會不會依照行動的結果，自己決定下一步。

p.39

為什麼需要 agent Why do we need an AI agent?

LLM 在某些事上勝過人類，在另一些事上又很笨拙。Agent 用系統設計補上這些弱點。

LLM 的強項：記得大量事實、語言、pattern matching、寫程式、跨很多領域工作。

LLM 的弱點（slide）Agent 的補法（本筆記整理）
沒有持久的記憶每個 session 開始時，載入 memory 檔案（L2、L6）
不一定讀懂 context管理 context，只放需要的內容（L4）
會 hallucinate用 tool 驗證：跑測試、讀原始碼、查文件

容易受惡意輸入影響Harness 檢查權限；tool 的輸出只當資料（L2 p.12、p.33）

Hallucination 指 model 很有自信地說出錯誤的內容。

Slide 引用 Andrej Karpathy 的演講 Software Is Changing (Again)，從 14:34 開始。他把這種高低不平的能力叫做 jagged intelligence。他也指出：LLM 不會從互動中自己學習，context window 就是它的 working memory。

p.40

Agent 是一種新的電腦 Agents as a new kind of computer

把 LLM 看成一種新的可程式化電腦：LLM 是 CPU，context window 是 RAM，tool 是周邊裝置，harness 是 OS，agent 是 application。

Agent 的零件傳統電腦相似點
LLMCPU負責運算與決策；本身不保存狀態
Context windowRAM / working memory容量有限；session 結束就清空
Tools周邊裝置讓運算碰到外界：檔案、終端機、網路
HarnessOS管理資源與權限；決定什麼進入 context
AgentApplication建在上面幾層之上，完成使用者的任務

OS 負責分配 CPU 時間與記憶體、管理裝置、隔離不同的程式。Harness 對 agent 做同樣的事。

Slide 也強調兩個不同點：

  • Programming model 不同：你用自然語言寫「程式」，例如 prompt、CLAUDE.md、skill。同一份程式，每次執行可能走不同的路徑。
  • Failure model 不同：CPU 算錯屬於硬體故障，很少發生。LLM 出錯是常態：hallucination、誤解指示、受 prompt injection 影響。所以 harness 要像 OS 一樣做隔離與權限控制。
NOTE

這個類比會一直出現。L2 p.19 延伸它：memory 檔案像硬碟。p.39 的影片也把 LLM 比作一種新的作業系統，LLM 像 CPU，context window 像記憶體。

p.41

為什麼 agent 是系統問題 Why are agents a systems problem?

傳統 serving 是 request → inference → response。Agent 是一條長鏈：infer → tool → infer → tool → retrieval → infer → …。這條鏈跨過 GPU、CPU、storage、network 與外部服務。

Critical path（關鍵路徑）是一串前後相依的步驟。它決定整個任務最快多久完成。Agent 的每一步都在 critical path 上：下一次 inference 要等上一個 tool 的結果。

Trajectory 是 agent 完成一個任務的完整紀錄：每次 inference、每次 tool call 與結果。Slide 列出 6 個挑戰，各舉一例：

  • 步驟相依：第 2 次 inference 要等 pytest 跑完，無法提前開始。
  • 每步延遲差很多：讀一個檔案不到 1 秒；跑完整套測試可能要幾分鐘。
  • 卡在等 tool：tool 執行時，這個 agent 用不到 GPU。它的 KV cache 卻還佔著 GPU 記憶體。Serving 系統要決定：留著、搬到 CPU 記憶體，還是丟掉之後重算。
  • 狀態快速變大：每一步都讓 context 變長（L2 p.16）。
  • 並行與預測：多個 subagent 可以同時執行。系統也可以先猜下一步，提前執行（speculation）。
  • 任何一步都可能失敗：tool 逾時、API 回傳錯誤、GPU 故障。失敗後，前面的步驟可能要重跑。
NOTE

對照本段開頭的圖。傳統 serving 追求 throughput：batch 越大，GPU 越不閒置。Agent 的每一步都在 critical path 上。Batch 讓每一步慢一點，幾十步加起來，整個任務就慢很多。這是 p.46 的第 1 題。

p.43

要優化什麼 What are we optimizing?

Throughput 不適合當 agent 的目標。目標是：在延遲、成本、資源、可靠性、安全的限制下，讓任務成功率最高。

Slide 說下面這些指標有用，但不夠：

  • TTFT（time to first token）：從送出請求，到收到第一個 token 的時間。
  • TPOT（time per output token）：之後每個 token 的平均間隔。
  • Tool-call latency 與 GPU 使用率。

這些指標只量一次 inference，或一個元件。它們看不出整個任務花多久、花多少錢、有沒有成功。

真正要優化的：任務成功率、端到端延遲、每個任務的 token 數、每個成功任務的成本（$）與耗能。

EXAMPLE

每個成功任務的成本 = 總花費 ÷ 成功的任務數。

Agent A：跑 100 次，花 $40，成功 50 次 → 每個成功任務 $0.80
Agent B：跑 100 次，花 $60，成功 90 次 → 每個成功任務 $0.67

B 每次比較貴，換算之後反而便宜。

CAUTION

Tokens/sec 高，agent 仍可能比較慢。例（只算生成時間）：Agent X 每秒生成 200 個 token，但繞了遠路，共生成 20,000 個，要 100 秒。Agent Y 每秒只生成 100 個，共 5,000 個，50 秒就完成。

p.45

Observability 是一等問題 Observability is a first-class problem

Agent 的 trace 是一棵巢狀的 trajectory：session → turn → agent step → model request、tool call、tool result → subagent → …。看不到這棵樹，就無法優化。

背景：microservice 系統用 distributed tracing 追蹤一個請求。每個操作記成一個 span，有開始時間、結束時間和上層 span。所有 span 組成一棵樹。

Agent 的樹更深，也更長。一個 session 有很多 turn；一個 turn 有幾十個 step。一個 step 可能開一個 subagent，裡面又是一整棵樹。

EXAMPLE

一棵 agent trace（示意，數字為假設）：

session「修好登入測試」                      312 s
└─ turn 1
   ├─ step 1  model request                2.1 s
   │          tool call  Bash(pytest)       41 s  → 3 failed
   ├─ step 2  model request                1.8 s
   │          tool call  Read(session.py)  0.1 s
   ├─ step 3  subagent   Explore            58 s
   │          ├─ step 1  model request  …
   │          └─ step 2  tool call  Grep(create_session)  …
   ⋮
   └─ step 9  model request  → final answer

有了這棵樹，才答得出「312 秒花在哪裡」：model、tool，還是 subagent？Slide 的結論：「You cannot optimize what you cannot observe.」

NOTE

依課程網站的說明，A1 要你做一個 web UI，即時顯示並檢查 Claude Code 的 session。這就是一個 agent 的 observability 工具。

在 Claude Code 裡，跨 session 的調整靠 memory 檔案，model 的權重不變（L2 p.27）。

帶走的重點

  • Prefill 受算力限制；decode 受記憶體頻寬限制。每生成一個 token，都要讀一遍權重和 KV cache。
  • 浮點數加法沒有結合律。Batch size 會改變加總順序，可能翻轉下一個 token。Temperature 0 也不保證可重現。
  • 大叢集裡，故障是常態。叢集的故障間隔約等於 MTBF ÷ GPU 數。
  • Agent 是一條 infer → tool → infer 的長鏈。每一步都在 critical path 上，所以 throughput 不適合當目標。
  • 要優化的是任務成功率、端到端延遲、每個成功任務的成本。看不到 trajectory，就無法優化。

自我檢查

一個 8B model 用 BF16 存，跑在記憶體頻寬約 1.6 TB/s 的 GPU 上。單一請求的 decode，每秒最多約幾個 token？Batch 變大時，每秒的總 token 數為什麼會上升？

約 100 個。每生成 1 個 token，都要讀完約 16 GB 的權重：16 GB ÷ 1.6 TB/s ≈ 10 ms。Batch 裡的請求共用同一次權重讀取，所以總 token 數隨 batch 上升。每個請求仍要讀自己的 KV cache，也要佔記憶體，所以上升有極限。

你把 temperature 設成 0，同一個 prompt 送兩次，輸出卻不同。可能的原因是什麼？

兩次請求遇到的 batch 不同。Batch size 改變時，kernel 的加總順序可能跟著改變，浮點數的捨入誤差也不同。前兩名 token 的分數很接近時，argmax 就換人。之後的文字全部不同。

一個叢集有 32,768 張 GPU，每張 GPU 的 MTBF 是 50,000 小時。整個叢集大約多久壞一張？

50,000 ÷ 32,768 ≈ 1.5 小時。GPU 數加倍，故障間隔就減半。

Agent A 每次嘗試花 $0.30，成功率 40%。Agent B 每次花 $0.50，成功率 80%。哪一個的每個成功任務成本較低？

B。A：$0.30 ÷ 0.4 = $0.75。B：$0.50 ÷ 0.8 = $0.625。只看每次呼叫的價格，會選錯。

為什麼「提高 tokens/sec」不一定讓 agent 更快？舉兩個原因。

第一，大 batch 讓每一步變慢，而 agent 的幾十步都在 critical path 上。第二，tokens/sec 不管 token 的總數。繞遠路的 agent 生成更多 token，總時間反而更長。Tool 的執行時間也和 tokens/sec 無關。
