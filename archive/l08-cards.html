先看這裡

這堂課回答兩個問題：agent 的錢花在哪裡，時間花在哪裡。後半比較三種 harness 架構，再看 8 個真實 harness 的獨特設計。

  • 成本是一串乘數。Cost = Users × Sessions/User × Turns/Session × Steps/Turn × Tokens/Step × Price/Token。使用量會成長，所以 agent 設計要壓低後四項。
  • 重讀 context 是大宗。每一步都重送整個 context。Assignment 1 的 Claude Code 資料中，97.6% 的 token 是 cache read。Turn 數變 2 倍，成本約變 4 倍。
  • 每個省錢手段都有反向成本。Compaction、routing、subagent、speculation 都可能讓總花費變多。在同一組任務上量淨效果，並替每個任務設上限。
  • 完成時間看 critical path。平行、非同步、speculative action 減少等待，但通常多花 token。
  • 架構決定能換什麼、能隔離什麼。Monolithic 簡單又快；modular 容易換元件；microkernel 的隔離與擴展最好，但通訊成本最高。

Session 的結構 Structure of a session

一個 session 有多個 turn。一個 turn 從使用者訊息開始，經過多次 model call 與 tool call，最後回覆使用者。

本堂用三個層級的詞。後面每一頁都照這個定義：

成本的乘法公式 Where does cost come from?

Cost = Users × Sessions/User × Turns/Session × Steps/Turn × Tokens/Step × Price/Token。前兩項會成長；agent 設計要壓低後四項。

這是乘法。任何一項減半，總成本就減半。所以每一項都值得單獨優化。

p.9–13

減少 turn 與 step

每個 turn、每個 step 都要重送整個 context。減少次數，是最直接的省法。

p.09

全班資料：每個 session 幾個 turn Your Claude Code usage: turns per session

多數 session 只有一個 prompt。單一 prompt 的 session 佔 68%（Assignment 1）與 75%（Assignment 2）。

  • 多數同學每個任務開一個新 session。
  • 少數人跑「馬拉松」session：100 個以上的 turn。

從成本看，這是好習慣。新 session 從乾淨的 context 開始。馬拉松 session 的每個 turn 都重讀前面所有內容（p.10）。

EXAMPLE

換任務時，在 Claude Code 輸入 /clear。它開始一段 context 為空的新對話。想留在同一段對話、只釋放空間，改用 /compact。

p.10

減少使用者的 turn 數 Reduce (user) turns per task

第 k 個 turn 要重讀第 1 到 k−1 個 turn。所以總成本隨 turn 數的平方成長。

算一次。假設每個 turn 新增 L 個 token：

  • 第 1 個 turn 送出 L。
  • 第 2 個 turn 送出 2L：第 1 個 turn 加上自己。
  • 第 k 個 turn 送出 kL。
  • 總共 L × (1 + 2 + … + k) = L × k(k+1)/2，約 k²/2 個 L。

例：10 個 turn 送出 55L，不是 10L。Turn 數變 2 倍（20 個），總量變 210L，約 4 倍。Prefix cache 讓重讀變便宜（p.16），但平方關係不變。

使用者回來追問，常見原因有三個：沒有計畫、agent 太早停下、沒人檢查結果。對應的解法：

  1. 先規劃（front-load planning）：開工前確認一次目標與計畫。
  2. 拆解任務（structured decomposition）：每個子任務都有完成條件。
  3. 交回前自我驗證（self-verification）：先跑測試、檢查輸出，再回報。

目標：agent 自己做完，中途不需要使用者介入。

p.11

全班資料：每個 turn 幾個 step Your Claude Code usage: steps per turn

多數 turn 只有幾個 step。Step 數的中位數是 3（Assignment 1）與 4（Assignment 2）。

  • Slide 的解釋：多數同學把 effort 設在 medium 或 high。
  • 少數 turn 跑了將近 1,000 個 step。

這是長尾分布。看成本時，要同時看中位數與 p90 這類尾端數字。

p.12

減少每個 turn 的 step Reduce steps per turn

每次 model call 都重讀整個 context。先規劃再批次執行，可以把 4 次 model call 減成 2 次。

做法流程Model call
一個動作一次 callModel → tool → model → tool → model → tool → model4
先規劃，再批次Model → 3 個 tool 平行執行 → model2
  • 批次處理獨立的 call：5 個檔案在一個 step 讀完，不要分成 5 個 step。
  • 重用計畫與 skill：重播以前成功的做法，不要每次重新推導。
  • 一開始就載入 context：開頭就讀需要的檔案，不要每一步讀一個。
EXAMPLE

對話這樣打：「先一次讀完 src/auth/ 下的檔案和 tests/test_auth.py，再提出修改計畫。」Model 可以在同一個回覆裡發出多個 Read，harness 在同一步執行完。

p.14–21

減少每一步的 token

每一步送出的 token 大多是重讀的 context。Input 量大但便宜；output 量小但貴。兩邊各有省法。

p.14

全班資料：每一步送出多少 token Your Claude Code usage: tokens per step

主 agent 每一步的 token 數，中位數是 200K–300K，p90 是 600K–700K。Subagent 小很多：中位數約 80K，p90 約 200K。

  • Slide 的圖：主 agent 的中位數是 208K（Assignment 1）與 301K（Assignment 2）。
  • 這些 token 幾乎都是 input：每一步重送的整個 context。

Subagent 從乾淨的 context 開始，所以每一步小得多。p.17 的「隔離探索」利用的就是這一點。

p.15

全班資料：token 隨 step 成長 Your Claude Code usage: tokens over steps

Context 累積得很快。到第 500 步左右，context 約 670K（Assignment 1）與 650K（Assignment 2）。

每一步都加入 model 回覆、tool 輸出、讀進來的檔案，直到 compaction 才清掉。以 1M 的 context window 算（L2 p.16），650K 已用掉約三分之二。

p.16

大部分 token 是 cache read Your Claude Code usage: most tokens are cache reads

Assignment 1 的 token 有 97.6% 是 cache read。Slide 給的價格比：cache read : input : output = 1 : 10 : 50。

  • 量的比例：output 約是 fresh prefill 的 1/5；fresh prefill 約是 cache read 的 1/100。
  • Fresh prefill 是第一次送進 model 的 token，會寫入 cache（cache write）。
  • Cache read 單價最低，但量太大，所以仍是成本大宗。
EXAMPLE

估一步的成本。單位是「input-token 單位」：1 個 base input token = 1 單位。

種類Token單價成本
Cache read300K0.130K
Fresh input5K15K
Output1K55K
合計306K40K

Cache read 佔 token 的 98%，佔成本的 75%。沒有 cache 時，305K 的 input 全以 1 倍計價，加上 output 共 310K 單位，是有 cache 的 7.8 倍。

p.17

減少每一步的 input token Reduce input tokens per step: keep context lean

留在 context 裡的 token，之後每一步都要再付一次。三個方向：丟掉過期的、縮小進來的、只載入需要的。

方向做法
丟掉過期的截短過時的 tool 結果；遮掉用過的 tool 輸出；把舊 turn 摘要成目前狀態（compaction）
縮小進來的壓縮 observation：只留錯誤，不放整份 log；大輸出寫進檔案，context 只放路徑
只載入需要的只載入相關的 tool 與 memory；探索交給 subagent，只拿回摘要（例：Claude Code 內建的 Explore）

算一下：20K 的測試 log 留在 context 50 步，共重讀 1M token。只留 500 token 的錯誤摘要，只有 25K。

EXAMPLE

跑測試時，完整輸出寫進檔案，只把重點放進 context：

pytest -x tests/ > /tmp/test.log 2>&1
grep -nE "FAILED|Error" /tmp/test.log | head -n 20

在 Claude Code 輸入 /context，可以看到哪些內容佔用 context。

p.18

減少 input token：相關論文 Reduce input tokens: related papers

ADVANCED，略讀即可。四類：壓縮歷史、把 context 當外部 memory、壓縮 prompt、讓 tool 資料不進 context。

  • 壓縮 agent 歷史：ACON（2025）把 peak context 降 26–54%；Active Context Compression（2026）少 23% token；TRACE（2026）指出摘要會造成重工。
  • Context 當外部 memory：MemGPT（2023）；Scroll（2026）保留完整的外部 log，由程式決定 model 看到什麼。
  • 壓縮 prompt：LLMLingua（2023）最多少 20 倍 token；LongLLMLingua、LLMLingua-2（2024）；Prompt Compression in the Wild（2026）發現只有長 prompt 才划算。
  • Tool 資料不進 context：Code execution with MCP（2025）在程式裡過濾結果，150K 降到 2K token；Tool Search（2025）少 85% 的 tool token；Programmatic Tool Calling 少 37%。
p.19

減少 output token：要求少一點 Reduce output tokens per step: ask for less

在 prompt 裡講清楚長度、格式、要省略什麼。再用 API 的 output 上限當保險。

  • Prompt 限制：字數上限、只回 JSON、只要前 3 項、不要重述問題、不要解釋推理。
  • 精簡的 system prompt：要求簡潔；使用者沒要求時，省略背景。
  • Output 上限：在 API 設硬上限，例如 max_tokens=300 或 max_output_tokens=300。

Output 上限有兩個陷阱。回答可能在句子中間斷掉，所以要搭配精簡的 prompt。推理（reasoning）也算 output，可能先用完上限。

CAUTION

官方文件（2026-10）：Claude API 的 max_tokens 包含 thinking 與回覆文字。撞到上限時，stop_reason 是 max_tokens。程式要檢查它，不要把截斷的 JSON 當成完整結果。

p.20

減少 output token：schema 與 effort Reduce output tokens per step: schema and effort

用 schema 只要求需要的欄位。推理量依步驟調整：查找用 low，除錯用 high。

Structured output。Slide 的例子只有兩個欄位：{"action": "search", "argument": "KV cache"}。限制 enum 與選填欄位，model 就加不了多餘的內容。對使用 tool 的 agent，tool call 旁邊的說明文字全是成本。

Adaptive effort。查找與格式化用 low；規劃與除錯用 high。可以每個 call 或每一步設定，形式是 reasoning effort 或 thinking token 預算。Claude API 的欄位是 output_config.effort；Claude Code 有 --effort flag 與 /effort 指令。

EXAMPLE

查找專用的 subagent：便宜的 model、低 effort、唯讀 tool、精簡輸出。

---
name: file-finder
description: Finds files and symbols. Use for quick lookups.
tools: Read, Glob, Grep
model: haiku
effort: low
---

Return only matching paths and line numbers. No explanation.

存成 .claude/agents/file-finder.md。這個例子同時用到 p.17（隔離探索）、p.20（effort）、p.23（routing）。

p.22–30

降低單價、控管預算

同樣的 token 數，單價可以差 100 倍。這一段講怎麼買到便宜的 token，以及怎麼替任務設上限。

p.22

降低單價：cache 與 batch Reduce price per token: caching and batching

Cache read 只要 base input 的 0.1×；batch 是 0.5×；兩者疊加是 0.05×。前提：prefix 保持穩定，工作可以等。

  • 保持 prefix 穩定：system prompt、tool 定義、早期歷史放在最前面，而且不要改。
  • 能等的工作用 batch：eval、backfill、大量批次工作。

Prefix cache 從第一個 token 開始比對。中間改了一個 token，後面全部 cache miss。所以會變的內容放最後。

CAUTION

常見錯誤：在 system prompt 開頭放現在時間。每個 request 的開頭都不同，cache 每次都 miss。

NOTE

官方文件（2026-10）：Message Batches 的 input 與 output 都打 5 折，多數 batch 在 1 小時內完成。Cache read 一般是 0.1×；Opus 5.5 與 Sonnet 5.5 是 0.05×。兩種折扣可以疊加。

p.23

降低單價：model routing Reduce price per token: model routing

簡單的步驟交給便宜的 model，難的交給貴的。三種時機：開始前選、失敗才升級、每一步重選。

策略怎麼做判斷依據
開始前選每個 turn 生成前，選定一個 model用偏好資料訓練的 router；也能選 agent 角色
失敗才升級先用便宜的 model；檢查沒過，再換大的Learned scorer、self-verification、執行結果
每一步重選Trajectory 變長時，重新選 model依歷史與預算；orchestrator 把 model 當 tool 呼叫

難處：便宜 model 的一個規劃錯誤，會浪費後面很多步。規劃這種「錯了很貴」的步驟，值得用大 model。

EXAMPLE

「失敗才升級」的骨架。Assignment 3 剛好提供 Starter、Standard、Expert 三種 model（見附錄）。

for model in ["starter", "standard", "expert"]:   # 由便宜到貴
    patch = agent.solve(task, model=model)
    if run_tests(patch).passed:                  # 執行結果當檢查
        return patch
return None
CAUTION

每一步換 model 有隱藏成本。KV cache 由 model 的權重算出，不能跨 model 共用。換到新 model，整個 context 要重新 prefill，用 fresh input 的價格計費。

p.24

系統層的降價手段（後面的課） Price per token: system techniques in later lectures

單價也能靠系統層降低：model、serving engine、硬體。後面幾堂課會講。

  • Model：MoE 與 sparsity、quantization、pruning、distillation、針對工作負載的 fine-tuning。
  • Serving engine：speculative decoding、KV cache 優化、更好的 request 排程。
  • 硬體：更快的 kernel、更好的 kernel 排程、專用加速器。

p.26

每個節省都有反向成本 Every saving has a counter-cost

淨節省 = 毛節省 − 反向成本。兩者都要在同一組任務上量。

手段反向成本
Compaction丟掉的檔案要重讀；摘要改變了 prefix，cache 要重寫
Routing 到便宜 model一個壞計畫多出很多步，或整次失敗
Subagent每個 subagent 都重讀共用的檔案與指示
Speculation猜錯浪費 token，還和主流程搶同一批 tool
EXAMPLE

粗估 compaction 何時回本。單位同 p.16。

  • 壓縮前：每步讀 600K 的 cache，花 60K 單位。
  • 壓縮後：context 剩 100K，每步花 10K 單位。每步省 50K。
  • 一次性成本：新的 100K prefix 要重新寫入 cache，花 100K。丟掉的檔案要重讀，再花 30K。

130K ÷ 50K，約 3 步回本。任務如果 2 步內結束，compaction 反而虧錢。產生摘要的那次 model call 還沒算進去。

p.27

替每個任務設預算，停滯就停 Cap each task's budget; stop when progress stalls

每個任務都設上限。進度停滯就停下，交出摘要。有摘要的停止，比失控的 run 便宜。

上限（slide 的示意值）例
金額$10
Model call 次數80 次
Tool 執行時間15 分鐘

EXAMPLE

claude -p --max-budget-usd 10 --max-turns 80 "修好 tests/test_auth.py"

--max-turns 計算 tool-use 來回，約等於 model call 次數。--max-budget-usd 依本機估算；最後一個回應可能超過上限，要留餘裕。

p.30

真的需要 LLM 嗎？ Do you need an LLM at all?

只有需要推理的步驟，才用 LLM。其他步驟用 script、規則或小型 model，每次呼叫幾乎不花錢。

情況改用
每次步驟都一樣寫 script。讓 LLM 寫一次程式，之後只跑程式。
輸入格式固定用規則解析：regex、parser、template。
只要一個標籤或分數訓練小型分類器，例如 GBM（gradient boosting）。
流程固定、推理很少用 script 跑流程，只在需要的步驟呼叫 LLM。
EXAMPLE

從 CHANGELOG 取出最新版本號。格式固定，一行 regex 就夠：

grep -oE 'v[0-9]+\.[0-9]+\.[0-9]+' CHANGELOG.md | head -n 1

用 LLM 做同一件事，每次都要付 token。這行指令每次執行都是零元。

p.31–42

讓 agent 更快

省錢的手段多半也省時間。但平行與 speculation 用更多 token 換更少等待。先找出 critical path，再決定優化哪裡。

p.31

分隔頁：讓 agent 更快 Make your agent faster

更快的 agent 通常也更便宜，但不一定。五個槓桿：加速 LLM serving、改進 orchestration、加速 tool call、平行化、speculative action。

p.32

完成時間由 critical path 決定 Completion time is the critical path

序列執行時，總時間約等於每一步相加。平行執行時，總時間約等於 critical path：最長的那條相依鏈。

序列的每一步包含 queue、setup、prefill、reasoning、tool、orchestration。平行的例子：plan 之後，worker A 和 B 同時做，最後 merge。

serial:   [plan 5][A 20.......][B 30..............][merge 5]   = 60 s
parallel: [plan 5][A 20.......]
                  [B 30..............][merge 5]                = 40 s

平行時，critical path 是 plan → B → merge。把 A 加速一倍，總時間不變。把 B 縮短 10 秒，總時間就少 10 秒。

CAUTION

省錢和省時間會衝突。小 model 單價低，但可能多走幾步，結果更慢。平行減少等待，但 token 總量變多。

p.33

加速 LLM serving Speed up LLM serving

前半段的每個省錢手段，也會降低 latency：更少 turn、更少 step、更少 token、更便宜的 serving。關鍵工具是 cache 與小 model。

Cache 命中的部分不用重算 prefill，第一個 token 更快出來。Output 一次產生一個 token，越短等越少。

p.34

改進 orchestration Improve orchestration

減少 harness 自己造成的等待。四個做法：非同步執行、持續存在的 session、串流與 pipeline、把服務放在一起。

做法例子省下什麼
Async executionTool 執行時，先開始下一步空等 tool 的時間
Persistent session同一個 shell 或瀏覽器跨步驟使用每步重新啟動的時間
Stream and pipelineLLM 回應還沒結束，就開始 tool call等完整回應的時間
Colocate servicesTool 和 model 跑在同一台主機網路來回的時間

Stream 的機制：回應是串流送出的。Tool call 的參數一完整，harness 就能開始執行。

p.35

加速 tool call Speed up tool calls

Build、test、載入網頁，可能比 model call 還久。優化 model 之前，先量每一步的 tool 時間。

  • Cache tool 結果：重複的讀取與搜尋直接用 cache。
  • 更快的硬體：重的運算放到 server，不要在筆電上跑。
  • 更好的 tool：同樣的工作，換更快、更便宜的 tool。只在需要時呼叫。
  • Fail fast：卡住的 call 要有 timeout。
EXAMPLE
timeout 300 pytest -x tests/   # 5 分鐘沒跑完就中止；-x 遇到第一個失敗就停
rg -n "create_session" src/    # ripgrep，通常比 grep -r 快
p.36

平行化 Parallelize work

讀 A、B、C 三個檔案：序列要等三次，平行只等一次。工作量相同，等待時間是三分之一。

  • 平行 tool call：獨立的 call 在同一步發出。
  • 平行 subagent：把獨立的子任務分出去，最後合併摘要。

只有獨立的工作能平行。共用狀態的工作，需要一個 merge 步驟。

p.37

Speculative action Speculative actions

便宜的 model 先猜下一個動作，趁主 model 還在想時先執行。猜中就省下等待；猜錯就丟掉，損失一次 call。

  1. Predict：便宜的 model 猜下一個 action。
  2. Run early：主 model 思考時，先執行猜測。
  3. Compare：主 model 決定後，比對猜測。

划算的條件：常常猜中，而且動作可以撤銷。所以適合讀檔、搜尋這類唯讀動作。git push、寄信、刪檔不能先做。

Slide 的開放問題：GPU、CPU、API 預算有限時，怎麼排程 speculative call，讓省下的時間大於浪費的工作？

NOTE

同樣的想法也出現在 CPU 的 branch prediction。CPU 先猜分支的方向，往下執行。猜錯就丟掉結果，重新執行。

p.40

預測從哪裡來 Where predictions come from

ADVANCED，略讀即可。三種來源：小 model、同一個 model 的早期分支、過去的 trace。

  • Model-based：小的 draft model 預測大 model 的下一步。Speculative Actions [1]、Speculative Tool Calls [2]。
  • Self-speculative：同一個 model 的早期 fork 預測自己之後的 tool call。SPORK [8]。
  • History-based：過去的 trace 預測下一個 tool，參數取自上一步的結果。PASTE [5]、Speculate with Memory [9]。
  • Lossless 與 lossy：Lossless 保留結果前一定驗證；lossy 的 SPAgent [3] 省略部分檢查。
p.41

兩個例子：PASTE 與 SPORK Two examples

PASTE 用過去的 trace 猜下一個 tool。SPORK 從 model 自己的推理，提早看出它要呼叫什麼。

PASTE：過去的 trace 常出現這個模式。

search(q) → visit(results[0].url) → extract(page)

search(q) 一開始，harness 就預期下一步是 visit。URL 取自 search 的結果。所以 model 還在生成時，visit 已經在跑。

SPORK：model 先推理約 2,000 個 token，才發出 tool call。推理的早期，意圖常已很清楚，例如「要搜尋 q」。一個 fork 出來的 probe 提早發出 search(q)。主 model 正式發出 tool call 時，結果已經準備好。

p.42

在迴圈中優化 Optimize in a loop

跑一次並記錄 → 找出成本與延遲的來源 → 一次只改一件事 → 用同一組任務重新評估。重複。Slide 提醒：Assignment 4 會用到。

  1. Run and profile：記錄每個 call、token、tool 與等待時間。
  2. Measure：找出成本與延遲從哪裡來。
  3. Change one thing：只改一項，例如 compaction、routing、caching 或平行化。
  4. Re-evaluate：用同一組任務，看成功率、花費、p95 latency。

一次只改一件事，才知道效果來自哪裡。

三種 harness 架構

同樣的功能，可以放在同一個程式裡、介面後面，或另一個服務裡。差別在於邊界的位置。

p.43

分隔頁：agent 架構 Agent Architecture

三種架構：monolithic、modular、microkernel。

p.44

三種 harness 架構 Three harness architectures

責任一步步移出 agent：從程式碼，到介面，到服務。

  1. Monolithic：memory、tools、context、planning、execution 全在一個 runtime。
  2. Modular：一個 controller 透過介面使用元件：MemoryProvider、ToolProvider、ContextProvider、SandboxProvider。
  3. Microkernel：核心只保留協調工作（狀態、排程、安全）。Memory、tools、執行都是外部服務，透過標準協定溝通。
NOTE

名稱借自作業系統。Microkernel 只在 kernel 保留排程、process 間通訊等最少功能；檔案系統與驅動程式在 kernel 外，以獨立的 process 執行。

p.45

Monolithic harness Monolithic harness

Agent 在一個 runtime 裡擁有一切。簡單、快，但難以替換元件，也難以隔離。

優點缺點
容易實作、容易除錯很難只換一個元件
通訊開銷最小元件緊密耦合
內部狀態容易共用很難和其他 agent 共用基礎設施
執行開銷低很難強制隔離
p.46

Modular harness Modular harness

一個 controller 透過介面委派工作。元件可以抽換，但 controller 仍掌管整個生命週期。

Agent 只認識介面，例如「有 run(code) 的 sandbox」，不知道背後是 Docker 還是 Firecracker。測試時可以換成假的 provider。

優點缺點
容易替換元件Controller 仍掌管生命週期
容易測試與擴充協調邏輯越來越複雜
責任分得清楚元件仍可能一起當掉
第三方實作可以直接接上要一起調校元件時，還是得改 controller
p.47

Agent microkernel Agent microkernel

Runtime 只負責協調；能力由外部服務提供：記憶服務接資料庫，工具服務接 tool API，執行服務管 sandbox。

每個服務可以跑在獨立的 container 或機器上。Runtime 用標準協定呼叫它們。

優點缺點
每個服務獨立擴展通訊開銷較高
故障隔離較好故障模式更多
確實執行時，隔離更強端到端除錯更難
基礎設施共用、集中管理需要標準的協定與生命週期
NOTE

L2 的 MCP 就是這種標準協定。Agent 不需要知道 GitHub 怎麼連；它只對 MCP server 發出 tool call。

Codex CLI 獨有的設計 Unique to Codex CLI

指令先在不能連網的 sandbox 裡執行；只有要離開 sandbox，才問你。Patch 必須符合一個 Lark 文法。

  • 先 sandbox，再核准。L2 p.12 的 Manual 模式每個動作都問。問太多次，人會不看就按同意。Codex CLI 把防線放在 sandbox：裡面的指令直接跑，最壞情況也出不了 sandbox。要越過邊界時，才需要你核准。

DeepSeek Harness 獨有的設計 Unique to DeepSeek Harness

連 agent loop 都是 plugin。每個 request 是 session log 的凍結 view。編輯採用 compare-and-swap：model 讀過之後檔案變了，這次編輯就失敗。

  • Loop 也是 plugin。Loop、adapter、tool、log、approval 都是 plugin。YAML 設定層可以替換任何一個。想試新的 loop 策略，不用 fork 整個 harness。
  • Request 來自 log。Harness 只往 log 尾端加 entry。所以任何一次 request 都能從 log 重建，方便除錯與重播。Log 只往後加，前一個 request 也就是下一個的 prefix，prefix cache 容易命中。
EXAMPLE

Compare-and-swap（CAS）擋下的情況：

  1. Model 讀取 config.py，這時是版本 v1。
  2. 你在編輯器裡改了 config.py，變成 v2。
  3. Model 依照 v1 的內容提出修改。

沒有檢查時，這次修改可能蓋掉你的改動，或改到錯的位置。CAS 記下 model 讀取時的版本，寫入前再比對一次。名稱來自 CPU 的 compare-and-swap 指令。

def edit(path, old, new):
    if file_hash(path) != hash_at_last_read[path]:
        return "error: file changed since you read it. Read it again."
    apply_edit(path, old, new)
p.56

OpenCode 獨有的設計 Unique to OpenCode

Harness 本身是一個 server。編輯允許模糊比對，但有大小上限。每一步都存快照，/undo 能還原檔案。

  • Harness 是 server。TUI、SDK、web app 都呼叫同一個 OpenAPI HTTP server。Session 存在 server 裡；每個介面都只是 client。
  • 有上限的模糊編輯。Model 寫出的舊文字常和檔案有小差異，例如縮排。OpenCode 依序試 9 種 replacer，從完全相符到只對齊錨點（anchor）。比對越寬鬆，越可能改錯地方。所以模糊比對的範圍太大時，harness 拒絕這次編輯。
  • 每一步一個快照。一個 shadow git repository 記錄每一步的檔案，所以 /undo 也能還原檔案，不只撤回對話。
p.57

Pi 獨有的設計 Unique to Pi

核心很小：4 個 tool，沒有 MCP、subagent、approval。Cache 保溫前先算錢：預期省下 $0.05 以上，才送 keep-alive。

  • 最小核心。其他功能都由 extension 提供。Tool 少，tool 定義就短，每一步重送的固定 prefix 也小（L2 p.8）。
  • 給別的專案用的函式庫。pi-ai 用 10 種 wire API 支援 42 家 provider。Wire API 指 HTTP request 的格式，很多 provider 共用同一種。Slide 提到另有 3 個專案使用 Pi 的程式碼。
EXAMPLE

為什麼保溫要先算錢。Claude API 的 cache 預設存活 5 分鐘，每次讀取重新計時（官方文件，2026-10）。以 200K 的 prefix 和 p.16 的單位計：一次 keep-alive 讀 cache，花 20K；過期後以 1.25× 重寫，花 250K。

使用者 5 分鐘內回來，或再也不回來，保溫都是浪費。所以 Pi 先估預期的節省，再決定送不送。

p.58

oh-my-pi 獨有的設計 Unique to oh-my-pi

Hashline 編輯：用 4 位 hex 的檔案 tag 加行號指定位置，model 不用重打舊文字。IDE 功能在同一個 process 裡。

  • Hashline 編輯。重打舊文字要花 output token，而 output 最貴（5×）。重打錯一個字，編輯就失敗。改用位置指定，兩個問題都消失。但檔案改過之後，同一個行號可能指到別的內容。所以行號編輯要能確認檔案沒變（對照 p.55 的 CAS）。
  • IDE 在 process 裡。一個 shell 跨所有 call 持續開著（p.34 的 persistent session）。原生 tool 提供搜尋、AST、LSP、debugger。LSP 能直接找到定義與引用，不用靠 grep 猜。
  • 特殊的 context 方法。snapcompact 把舊歷史轉成圖片，是另一種 compaction。TTSR 在 regex 符合時停下並重試。可以在生成途中攔下走錯的方向，不用等錯的輸出寫完再修。
EXAMPLE
# 字串取代：model 要重打舊文字（Claude Code 的 Edit）
Edit(file_path="src/auth/session.py",
     old_string="    ttl = 60",
     new_string="    ttl = 3600")

# hashline 的概念（示意，不是真實語法）
edit src/auth/session.py tag=3f9a line=42 -> "    ttl = 3600"

OpenClaw 獨有的設計 Unique to OpenClaw

27 個聊天頻道的訊息，進入每個 session 一條的 queue lane。Compaction 前，先用一個看不見的 turn 寫下有日期的筆記。不可信的文字用 fence 隔開。

  • 有 queue lane 的 gateway。同一個 session 的訊息排在同一條 lane，依序處理。Run 進行中又來新訊息時，queue mode 決定怎麼處理。
  • Compaction 前先存 memory。Compaction 會丟掉細節（L2 p.16）。所以 OpenClaw 先跑一個 silent turn，讓 agent 把重點寫成有日期的筆記。之後同時用全文搜尋與向量搜尋找回筆記。全文搜尋抓精確的名稱與 ID；向量搜尋抓意思相近、用字不同的內容。
  • Fence、taint、sentinel。Fence 把不可信的文字（網頁、email）包起來，標明它是資料。讀過網路的 turn 會帶上 taint 標記；一般的 taint tracking 會對這種 turn 做更嚴的檢查。Sentinel 一般是 canary：放在 secret 旁的假值，出現在輸出裡就代表外洩。Slide 沒有細說 OpenClaw 怎麼處理這兩種訊號。
EXAMPLE

Claude Code 的近似做法：PreCompact hook 在 compaction 前備份 transcript。差別：hook 是固定的程式；OpenClaw 的 silent turn 由 model 挑重點。

p.60

Hermes Agent 獨有的設計 Unique to Hermes Agent

背景的 fork 檢查 nudged turn，再修改 memory 與 skill。Context 用到 50% 就 compaction，是 8 個中最早的。Tool 執行前，先把 tool call 寫進資料庫。

  • 會學習的 fork。主 agent 繼續工作；背景的 fork 檢查每個 nudged turn（slide 的用語），把學到的事寫進 memory 和 skill。風險同 L2 p.31：寫錯的 memory 會誤導之後的每個 session。
  • 最早的 compaction。以 1M 的 window 算，Hermes 在 500K 時就壓縮。早壓縮讓之後的每一步更便宜。但 p.26 的反向成本會更常發生：丟掉的檔案要重讀，cache 要重寫。
  • 執行前先存檔。這是資料庫 write-ahead log 的概念：副作用發生前，先把 tool call 寫進 session 資料庫。Process 在執行中當掉，重啟後 harness 知道哪些 call 已經開始，就能避免盲目重做，例如重複寄出同一封信。

同一堂課發布的作業說明。卡片依主題排序，tab 連到整份 PDF。作業的三個指標正好是本堂主題：解出幾題、每題的花費、每題的時間。

A3.1

作業概觀 Assignment 3: MadsOpt: Harness Competition

一場 harness 競賽：26 個任務，分屬 3 種 container。Agent 和任務在不同的 container，用 HTTP 溝通。

評估是離線的：唯一連得到的主機是 api.cs2680.com。所以評估時，agent 不能上網查資料，也不能下載套件。需要的東西要事先放進你的程式。

A3.2

流程 Framework

Dispatcher 把任務交給 agent；agent 產生 patch；patch 經過評估，結果回到 agent。最多 5 個任務同時跑。

  1. Dispatcher 把任務資訊傳給你的 agent。
  2. Agent 處理任務，產生一個 patch。
  3. 評估 patch，把結果送回 agent。

結果會回到 agent，所以 agent 能依評估結果決定下一步，例如 p.23 的「失敗才升級」。

A3.3

限制 Limits

三種 model：Expert、Standard、Starter。每次 evaluate() 最多 35 分鐘，總共最多 4 小時。花費上限：每天 $30，每次 run $10。

如果一次 run 跑完全部 26 個任務，平均每個任務只有約 $0.38。這就是 p.23 的 routing 與 p.27 的預算上限派上用場的地方。

A3.4

程式結構 Code structure

只有 src 資料夾會上傳：壓成 src.zip。Dispatcher 與評分腳本和 leaderboard 上的版本相同，不要修改。

為什麼不要改後兩個：leaderboard 用自己的版本。你在本機改了，本機的分數就和 leaderboard 對不上。Session log 的規定見 p.4：不能改動。

A3.5

提交到 leaderboard Leaderboard submission

提交 src.zip。提交依序排隊處理；看起來沒希望的，可以取消。指標：解出的任務數、每個解出任務的花費、每個解出任務的時間。

  • 登入資訊在原 slide 上，供修課學生使用。
  • 取消的提交仍然算次數，也會用掉當天的預算。

指標以「解出的任務」為單位。花在沒解出任務上的錢與時間，也會拉高這兩個數字。所以卡住的任務要早點停（p.27）。

A3.6

評分 Grading

Leaderboard 80 分、writeup 10 分、影片 10 分。Leaderboard 分數由名次 r 決定：有任一次提交達到 baseline（16 題），得分是 max(81 − r, 50)；否則是 81 − r。

  • Leaderboard 用 skyline 圖呈現三個指標。最低要求：解出 7 個任務。
  • 名次 r 計算排在你前面的人數，同分同名次，例如 1、1、1、4。

算幾個例子：第 1 名得 80 分，剛好是滿分。第 4 名得 77 分。第 40 名有到 baseline 得 50 分，沒到只有 41 分。所以先穩定解出 16 題，等於保住 50 分。

NOTE

Skyline 是資料庫用語：沒有別的資料在所有指標上都比它好，它就在 skyline 上。Slide 沒有說明三個指標怎麼合成名次。

帶走的重點

  • 成本是一串乘數。使用量會成長，所以要壓低 turn、step、token 和單價。
  • 每一步都重讀整個 context。Turn 數的影響是平方；cache read 是 token 的大宗。保持 prefix 穩定，丟掉過期的內容。
  • 每個省錢手段都有反向成本。在同一組任務上量淨效果，並替每個任務設上限與停止條件。
  • 完成時間由 critical path 決定。平行與 speculation 用更多 token 換更少等待。
  • 架構的邊界越往外，隔離與擴展越強，每次呼叫也越貴。

自我檢查

一個 session 有 20 個 turn，每個 turn 新增 10K token。總共送出多少 input token？拆成 2 個各 10 turn 的 session 呢？

一個 session：10K × (1 + 2 + … + 20) = 2.1M。兩個 session：2 × 10K × 55 = 1.1M，約一半。每個 session 的 turn 數減半，成本降到約四分之一；兩個加起來是一半。

一步有 400K cache read、2K fresh input、2K output。用 p.16 的 1 : 10 : 50，哪一項最貴？該先優化什麼？

以 input-token 單位計：cache read 是 40K，fresh input 是 2K，output 是 10K。Cache read 最貴，所以先縮小 context（p.17），不是先縮短 output。

你把 compaction 門檻從 90% 調到 50%，總成本反而上升。可能的原因？

反向成本（p.26）：丟掉的檔案要重讀；摘要改變 prefix，cache 要重寫；產生摘要本身也要一次 model call。壓縮越頻繁，這些成本越常發生。要在同一組任務上比較淨成本。

DeepSeek Harness 為什麼用 compare-and-swap 編輯？沒有它會怎樣？

Model 讀檔之後，你、另一個 subagent 或 formatter 可能改過檔案。Model 依舊版本提出的修改，可能蓋掉別人的改動，或改到錯的位置。CAS 讓這次編輯失敗，要求 model 先重讀檔案。
