Agent loop：ReAct 與它的程式骨架

p.05

ReAct：推理和行動放在同一個 loop The ReAct loop

ReAct 讓 model 輪流做三件事：Thought（想）、Action（做）、Observation（看結果）。想法決定下一個動作；結果修正下一個想法。

做法每一步做什麼結果
只推理（reason only）一直想，不碰環境沒有東西檢查推理。小錯誤累積成自信的幻覺。
只行動（act only）一直呼叫 tool，背後沒有計畫Model 重複同樣的動作。
ReAct想 → 做 → 看結果 → 再想Observation 修正錯誤的想法。

Loop 在兩種情況停止：observation 已經回答問題，或停止規則（步數、時間、預算上限）結束執行。在程式裡，Action 是 tool call，Observation 是 tool 結果（p.6）。

EXAMPLE

一段 ReAct 過程（示意）：

Thought:     測試說 session 太早過期。先找過期時間在哪裡算。
Action:      grep -rn "expires" src/auth/
Observation: src/auth/session.py:41   expires = now + 60
Thought:     60 秒太短。設定檔寫 3600，要確認設定有沒有讀進來。
Action:      read src/auth/config.py
Observation: SESSION_TTL = int(os.getenv("SESSION_TTL", 3600))

第 2 個 Thought 用上了第 1 個 Observation。只推理的 model 看不到 60 這個數字，只能猜。

p.06

Agent loop 寫成程式 The agent loop (code)

Agent loop 的程式很短：呼叫 model、執行 tool call、把結果加回訊息清單。重複到 model 給出最終回答，或超過步數上限。

  • messages：這就是 context。每一圈都整份送給 model。
  • validate：model 的輸出不可信。JSON 可能壞掉，型別可能不對，路徑可能在 repo 外面。
  • tool_call_id：model 一次可以發出多個 tool call。每個結果都要標明對應哪一個。
  • MAX_STEPS：沒有上限的 loop 可能一直燒錢。到達上限就明確失敗。

Tool 出錯時，程式不中止。錯誤訊息放回 context；model 讀到錯誤，下一圈就能修正（p.26）。

p.07

Loop 的流程與設計者的工作 The agent loop

Model 每一圈只做一個決定：給出最終回答，或發出 tool call。其他事情都是 harness 設計者的工作。

Slide 在 loop 上標出設計者的四項工作，見本段開頭的圖。第 4 項「整理結果、管理 context」是可選的。權限檢查的細節見 L2 p.12。

這四件事都在 model 之外。所以同一個 model 放進不同的 harness，表現會差很多（p.55）。

p.08

Coding agent 的三個元件 Components of a coding agent

Coding agent 有三個元件：model 加 loop、tool 加防護、state。三者共用同一個 context window，所以要一起設計。

元件內容負責
01 Model + agent loopLLM 提議動作，看結果，再重複決定下一步
02 Tools + guardrailssearch、read、edit、跑測試、shell；外加權限、sandbox、人工核准Tool 決定能力；guardrail 保住安全
03 StateContext（現在 window 裡的東西）與 memory（跨步驟保留的東西）組出 context；保留這一輪之後還要用的資訊

為什麼要一起設計：grep tool 一次回傳 5,000 行，tool 的決定就變成 context 的問題。一份很長的 memory，也會擠掉任務的空間。

p.11

Glob 與 grep Tool search and read: glob and grep

Agent 用 ls、glob、grep 一步步縮小範圍。不用建索引，結果永遠反映 repo 的現況。代價是回合數和 context；字面比對也找不到用詞不同的程式。

EXAMPLE

Slide 的例子：「修好登入的 timeout」。每一行是一次 tool call：

Grep  "timeout"  path=src/    → 37 hits in 12 files（太多）
Glob  src/**/auth/*.ts        → src/auth/retry.ts
Read  src/auth/retry.ts       → RETRY_MS = 500，修正
  • 成本：每一次搜尋都是一圈 loop，結果也佔 context。37 筆結果全部讀進來，context 很快就滿。
  • 盲點：grep 只比對字面。搜「timeout」，找不到寫成 deadline 或 ttl 的程式。
  • 技巧：先用 grep -rl 只列檔名，再挑檔案讀。輸出小很多。
p.12

Semantic search 與 repo map Tool search and read: semantic search

事先把程式碼建成索引，查詢時就很快。索引有兩種：用 embedding 依「意思」找，或用 repo map 依「結構」找。代價是要建索引，還要一直重新同步。

  • Semantic（embedding）：把程式切成片段，每段轉成一個向量。查詢也轉成向量，再取距離最近的片段。意思相近、用詞不同的文字，向量也會靠近。
  • Structural（repo map）：列出檔案樹，加上排序過的 symbol（class、函式簽名）。Aider 的 repo map 是代表例子。

Slide 的例子：問「where do we rate-limit」，第一次查詢就找到 throttle.ts。程式用的詞是 throttle。字面比對會漏掉它，embedding 找得到。

Repo map 不列函式內容。幾千個檔案，也能壓成一小段文字，讓 model 先看地圖再決定讀哪裡。

CAUTION

Agent 一直在改檔案。索引沒跟上，查詢就回傳舊的程式碼。

p.13

外部訊號：stack trace、失敗的測試、git 歷史 Tool search and read: extrinsic signals

原始碼以外的證據，常常直接指出問題在哪。Debug 時，這是精準度最高的訊號；但只有部分任務有這種訊號。

Slide 的例子：結帳 crash 的回報。

  1. 讀 stack trace：它指向 cart.ts:88，列出 3 個 frame。
  2. 讀 tax.ts 第 20–60 行：applyTax 有進位（rounding）錯誤。
  3. 修正後跑 pytest tests/tax.py：全部通過。整個過程沒有用到搜尋。

Git 歷史也是外部訊號。git log -S "applyTax" --oneline 列出新增或刪除過這個字串的 commit。git blame -L 20,60 src/tax.ts 顯示每一行最後在哪個 commit 修改。

p.14

Language server（LSP）Tool search and read: language server (LSP)

向編譯器等級的索引查詢定義、引用、symbol、型別。它能正確處理 import、overload、改名；grep 只能猜。代價是每種語言要一個常駐的 server，冷啟動也慢。

Slide 的例子：把 charge() 改名成 capture()。

  1. 呼叫 textDocument/references：找到 7 個檔案裡的 42 個呼叫點。
  2. 呼叫 textDocument/rename：用別名 import 的地方也一起處理。
  3. 跑型別檢查：沒有找不到的 symbol。

Grep 為什麼做不到：寫了 import { charge as c } from "./pay" 之後，呼叫點寫的是 c()。字面上沒有 charge。Language server 解析過程式，知道 c 就是 charge。

NOTE

Claude Code 官方文件建議 typed language 安裝 code intelligence plugin：一次「go to definition」，可以取代 grep 加讀好幾個候選檔。

p.15–16

四種找法的比較 Search and read: a comparison

先用 grep。名字找不到東西時，再用索引或 LSP。p.16 與 p.15 內容相同。

做法靠什麼找適合主要成本
glob / grep字面上的名稱與路徑知道或猜得到名稱每次搜尋的回合數與 context
Semantic index片段的意思（embedding）用詞和程式對不上建索引、重新同步
外部訊號stack trace、失敗的測試、git 歷史回報已經指向程式碼只有部分任務有
Language server編譯器的 symbol graph修改要跟著引用走每種語言一個常駐 server

「名字找不到」：你不知道該 grep 哪個詞，例如只知道症狀「結帳很慢」。這時 semantic search 或 repo map 比較快。

p.17

思考題：agent 該怎麼改程式碼？How should an agent edit code?

課堂投票。答案是 p.18–21 的四種編輯方式。

p.18

整檔重寫 Tool edit: whole-file rewrite

Model 重新產生整個檔案，tool 直接覆寫。沒有 patch 語法會寫錯，每次都套得上。代價：輸出量和檔案大小成正比，沒要改的程式也可能跑掉。

Slide 的例子：幫 API client 加 retry。Agent 讀 client.ts（120 行），再寫回完整的檔案。實際只改 4 行；diff 顯示第一次就套用成功。

  • 成本：改 4 行，卻要輸出 120 行。Output token 一個一個產生，比讀 input 慢，單價通常也較高。
  • Drift：沒改的 116 行也要重新寫出來。檔案越長，越容易漏掉註解、改到縮排，或寫成「其餘不變」的省略號。
NOTE

Claude Code 的 Write tool 就是整檔覆寫，適合建立新檔案。修改既有檔案時，它用 search-replace 的 Edit tool（p.20）。

p.19

Unified diff / patch Tool edit: unified diff / patch

Model 輸出一份 patch，另一個 tool 負責套用。格式精簡、方便 review，人和 CI 本來就在用。代價：行號或上下文對不上，hunk 就套不上去。

Slide 的例子：調高兩個檔案的 retry 上限。Agent 先讀 client.ts 與 api.ts 找定位點。接著輸出一份有 2 個 hunk 的 patch，再執行 git apply patch.diff。

怎麼讀：@@ -41,3 +41,3 @@ 表示舊檔從第 41 行起共 3 行，新檔也是。- 開頭的行要刪除，+ 開頭的行要加入。空白開頭的行是上下文（context 行），用來定位。

為什麼會失敗：header 與 context 行，都由 model 依讀檔當時的版本寫出。

  • 行號：前一個 edit 在上面插入 5 行，第 41 行就變成第 46 行。只認行號的 tool 會失敗；GNU patch 會在附近搜尋 context 行，並回報 offset。
  • Context 行：必須和檔案一字不差。檔案後來改過，或 model 記錯一個空白，就對不上。
  • 行數：header 的行數寫錯，tool 會判定 patch 損壞。
CAUTION

git apply 預設全有或全無：一個 hunk 套不上，整份 patch 都不套用。Agent 要重讀檔案，重寫 patch。

p.20

Search and replace Tool edit: search and replace

Model 給出一段要找的原文（anchor）和要換成的新文字。輸出量和改動大小成正比，和檔案大小無關。代價：anchor 不唯一、過期，或空白不一致，就會失敗。

Slide 的例子：調高 retry 次數。先用 grep -n "retries = 3" 確認只有一處符合。再用一次 call 把 3 換成 5。最後讀回檔案確認，其他部分都沒動。

為什麼比 diff 穩：它靠內容定位，不靠行號。三種失敗情況：

  • 不唯一：retries = 3 出現兩次，tool 不知道改哪一個。解法：anchor 多帶幾行。
  • 過期：formatter 或前一次 edit 已經改過檔案。
  • 空白不符：tab 與空格不同，或行尾多一個空白。
NOTE

Claude Code 的 Edit tool 就是這種設計，參數是 old_string 與 new_string。old_string 不唯一時，edit 直接失敗，除非設定 replace_all。報錯比改錯地方安全。

p.21

結構化編輯（AST）Tool edit: structured / AST edits

Model 指定一個對 symbol 的操作，例如改名或加參數。結果不受排版影響，也不會產生語法錯誤。代價：每種語言都要有工具，能表達的修改種類也有限。

AST（abstract syntax tree，抽象語法樹）是 parser 把原始碼轉成的樹狀結構。工具修改這棵樹，再把樹印回原始碼。所以結果一定能 parse。

EXAMPLE

Slide 的例子：幫 fetchUser() 加一個 timeout 參數，預設 5 秒。

add_param(symbol="fetchUser", name="timeout", default="5s")
→ 工具改寫函式簽名，以及 18 個呼叫點
→ parse 與型別檢查都通過（構造上就合法）

限制：model 只能做工具提供的操作。「改寫這段折扣邏輯」沒有對應的 AST 操作，還是要用 p.18–20 的方法。Slide 附了兩個參考：Abstract syntax trees（影片）、How language servers work。

p.22

四種編輯方式的取捨 How agents apply edits

四種方式在 token 成本與穩健度之間取捨。穩健度指改動有沒有落在想改的位置。每一種都有自己的弱點。

方式Token 成本（p.18–21）弱點（p.22）
整檔重寫高：和檔案大小成正比長檔案會 drift
Unified diff低：只寫改動與上下文行號過期就套不上
Search / replace低：和改動大小成正比需要完全相符、唯一的 anchor
結構化 / AST低：只寫一個操作支援的語言有限

各方式在 slide 圖上的位置，請看原 slide。

NOTE

本筆記整理的選法：新檔案或很短的檔案，用整檔重寫。一般修改，用 search-replace。跨很多檔案的改名，用 LSP 或 AST。要交給人 review 的改動，輸出 diff。

p.23

Shell：最強也最危險的 tool Tool execution: effectively a shell

有了 shell，agent 就能做 shell 能做的所有事。所以 shell 是最強的 tool，也是最危險的 tool。

特性意思例子
Composition一次 call 就能串接、過濾、loop、重試pytest -q 2>&1 | tail -n 20
Reach碰得到檔案系統、網路、套件管理、已安裝的程式pip install、curl、docker
Persistence檔案和 process 在 call 結束後還在npm run dev & 留下一個常駐的 server
Blast radiusShell 能做的事，agent 都能做rm -rf、git push --force
CAUTION

網頁可能藏有 prompt injection（L2 p.33）。Agent 同時有 shell 和網路時，可能把 ~/.ssh 的內容送出去。所以 shell 要放進 sandbox，再加上權限檢查（L2 p.12）。

p.24

設計執行 tool 要想的五件事 Tool execution: things to think about

失敗訊號、輸出量、執行時間、預算、隔離。這五件事都要在 harness 裡明確處理。

項目要回答的問題做法舉例
失敗訊號Agent 看得懂錯誤，並能採取行動嗎？回傳 exit code 與 stderr，不要只回「failed」
輸出量夠用，又不過量嗎？只回最後幾十行；完整 log 存檔，回傳路徑
執行時間長時間或背景的 process 怎麼辦？設定 timeout；dev server 放到背景，之後再讀 log
預算什麼時候停止重試，交回控制？同一個錯誤連續 3 次，就停下來回報
隔離程式在哪裡跑？碰得到什麼？container、只掛載 repo、關閉網路
p.25

另外五種常用 tool Five more tools commonly used

除了 search、edit、shell，還有五種常用的 tool：筆記、subagent、web、瀏覽器畫面、問使用者。

Tool做什麼為什麼需要
A. Memory 與筆記把發現寫進檔案Compaction 之後，計畫還在
B. Subagent把探索工作交出去拿回一份短清單，不是 40 次讀檔的內容
C. Web search 與 fetch查文件與網路資料先讀已安裝的原始碼，再查網路
D. 瀏覽器與畫面回饋截圖渲染結果，回給 model版面錯誤要看畫面才看得出來
E. 問使用者提出一個問題一個便宜的問題，勝過一個自信但錯誤的 patch

C 的原因：網路文件可能是別的版本；已安裝的原始碼才是實際執行的版本。例：pip show -f requests 列出安裝位置與檔案。

p.26

Tool 設計原則 Tool design best practices

五條原則：數量少且不重疊、為用途量身打造、輸出省 token、錯誤訊息要能教、預設冪等（idempotent）。

  • 少且正交：grep_repo、search_code、find_text 功能重疊。Model 會猶豫該用哪一個，甚至每個都試一次。
  • 專用：search_orders(customer_id) 勝過通用的 run_sql。對照見下方。
  • 輸出省 token：截斷、分頁、摘要。Tool 的輸出會進 context，所以 tool 設計就是 context 設計。
  • 錯誤要能教：回傳修正方法，不要只回「invalid argument」。
  • 預設冪等：同一個 call 跑兩次，結果和跑一次相同。Agent 遇到 timeout 時，不知道上一次有沒有成功。Tool 冪等，重試就安全。

差在哪：run_sql 要 model 先知道 table 和欄位，而且什麼都能做，包括 DROP TABLE。search_orders 只能讀一位客戶的訂單。它的參數有型別與上限，輸出最多 50 筆。

EXAMPLE

錯誤訊息的對照：

✗ {"error": "invalid argument"}
✓ {"error": "customer_id 'jane@example.com' is an email. Use an ID like 'C-10293'. Call find_customer(email=...) to get it."}

第一種，model 只能亂猜。第二種，model 下一圈就知道要先呼叫 find_customer。

p.27

只給 shell 就好嗎？Can we just provide the shell tool?

不夠。Slide 的數據（GPT-4）：只給 shell，解出 11.0% 的題目；完整的 SWE-agent 介面，解出 18.0%。為 model 設計的 tool，勝過原始的 shell。

設定（slide 的標籤）解題率和完整設計差在哪

  • 介面設計的影響很大：同一個 model，只換介面，解題率從 11.0% 升到 18.0%。
  • 多給資訊不一定好：顯示整個檔案、保留完整歷史，都比預設差。這和 p.44–45 的 context 問題是同一件事。

p.30

八種技巧 Prompt engineering

Zero-shot、few-shot、role/persona、chain-of-thought、tree-of-thoughts、self-consistency、prompt chaining、meta prompting。p.31–38 一頁講一種。

p.31

Zero-shot：只給指令 Zero-shot prompting: instruction only

只給指令，不給範例。任務常見、格式用文字講得清楚時，用 zero-shot。規則講不清楚時，換 few-shot。

這個 prompt 列出全部標籤，也規定了輸出格式，程式可以直接 parse。「不清楚就選 other」給 model 一個出口，避免它硬選一個標籤。

「規則講不清楚」（tacit rule）的例子：語氣很急、卻沒說問題的工單，該歸哪一類？這種規則用例子示範比較容易。

p.32

Few-shot：指令加範例 Few-shot prompting: instruction plus examples

指令加上幾個範例。輸出格式少見，或規則用示範比用說的容易時，用 few-shot。任務需要多個步驟時，換 chain-of-thought。

Charged twice this month.     → billing
Can you add dark mode?        → feature
asdfgh                        → other
Crashes when I export a PDF.  → ?        ← 留給 model

範例 asdfgh → other 示範了一條沒寫出來的規則：亂打的文字歸 other。三個範例也同時固定了輸出格式。

CAUTION

Model 會模仿範例的表面特徵。範例都很短，或某個標籤特別多，答案也會跟著偏。範例要涵蓋每個標籤，順序要打散。

p.33

Role 與 persona Role & persona prompting

指定一個角色和讀者。語氣、判斷標準或讀者很重要時，用 role prompting。需要推理步驟時，換 chain-of-thought。

Slide 的例子：model 扮演資深 SRE，替主管審閱一份 postmortem。規則：標出證據缺口、不推測、最多 5 點。範例輸出：時間軸漏了 04:12 的 alert 確認（ack）；這是證據缺口，不是事故原因。

為什麼有效：一個角色帶入很多隱含的選擇，例如用詞、重點、細節深度。「給主管看」就代表要短、先講結論。具體限制（最多 5 點）仍要明寫。

p.34

Chain-of-thought：寫出步驟 Chain-of-thought: make the steps explicit

要 model 先寫出中間步驟，再給答案。任務真的有多個步驟，或錯誤來自跳步時，用 CoT。有好幾條可行的路時，換 tree-of-thought。

Q: 3 features/week for 4 weeks, then 5/week for 2 weeks. Total?
   Show each step. End with "ANSWER: <n>".
A: 3 × 4 = 12
   5 × 2 = 10
   12 + 10 = 22
   ANSWER: 22

為什麼有效：model 一次產生一個 token。寫出 12 和 10 之後，最後的加法只要讀前面的結果。不寫出來，model 要在一步之內同時算三件事。固定的 ANSWER: 格式，讓程式能取出答案。

NOTE

對 reasoning model，這招的效果變小。原因見 p.41。

p.35

Tree-of-thought：分支、評分、剪枝 Tree-of-thought: branch, score, prune

先提出幾個方案，每個打分，只展開好的，刪掉差的。有好幾條路、而且評分便宜時，用 ToT。只有一個正確答案時，換 self-consistency。

Slide 的例子：提出 3 個降低結帳延遲的方法，每個依影響（impact）與成本（effort）打 1–5 分。

方案ImpactEffort處理
A. Cache warm-up32刪掉
B. 移除第三方服務54第二個展開
C. Lazy-load 資源41第一個展開

為什麼刪 A：C 的影響比 A 大，成本又比 A 低。和 CoT 的差別：CoT 只走一條路，第一步選錯就一路錯。ToT 保留幾條路，可以比較，也可以回頭；代價是呼叫次數變多。

p.36

Self-consistency：取樣再投票 Self-consistency: sample, then vote

同一個 prompt 取樣好幾次，再多數決。只有一個正確答案、答錯代價又高時，用它。工作能拆成幾個階段時，換 prompt chaining。

prompt: "Is this invoice a duplicate?"   samples: 5   temperature: 0.7
answers:   yes  yes  no  yes  yes
majority:  yes      agreement = 4/5 = 0.8
0.8 ≥ 門檻 0.8   → 回傳 yes
若只有 3/5 = 0.6 → 交給人處理

為什麼 temperature 要大於 0：temperature = 0 時，model 每次都選機率最高的 token。5 次結果幾乎相同，投票永遠是 5/5，沒有資訊。T = 0.7 讓每次取樣走不同的推理路徑；路徑不同、答案仍一致，才代表有把握。

一致度可以當作信心分數：低於門檻，就交給人。代價：5 次取樣就是 5 倍成本。

p.37

Prompt chaining：一次 call 一件事 Prompt chaining: one job per call

把工作拆成幾個階段，每次 call 只做一件事。每段輸出都能驗證時，用 chaining。要調整的是 prompt 本身時，換 meta prompting。

階段輸入輸出
1. 擷取email 內文{vendor, amount, date}
2. 驗證、補資料階段 1 的輸出再加上 vendor_id
3. 草擬回信階段 2 的輸出{subject, body}

某一段的輸出不符合 schema，就只重跑那一段。

為什麼比一個大 prompt 好：每個 prompt 變短。每段輸出都能用程式檢查。出錯時，你知道是哪一段。

p.38

Meta prompting：讓 model 寫 prompt Meta prompting: let the model write the prompt

讓 model 改寫 prompt。你有一組 eval 測試、要調整的是 prompt 本身時，用它。分數不再進步時，回頭重選技巧。

Slide 的做法：把目前的 prompt、10 個測試案例、其中失敗的 3 個交給 model。要求：修好這 3 個，不能弄壞其他 7 個，只回傳新 prompt。結果：v2 多了一條明確的拒答規則，eval 分數從 8/10 變成 10/10。

為什麼 eval set 是前提：沒有測試，就無法確認「沒弄壞其他 7 個」。

CAUTION

10 個失敗 3 個應該是 7/10，但 slide 寫改寫前是 8/10；兩個數字對不上。另外，只用 10 個案例調 prompt，容易過度貼合（overfit）。要另外保留一組不參與調整的測試。

p.39

三個層次：先用簡單的；需要時加推理；最後才設計成系統。

層次技巧什麼時候用

p.42

寫 prompt 的四條原則 Designing prompts: four best practices

從簡單開始；分段；具體而精簡；大任務拆小。Prompt 的建議依 model 而異，換 model 就要重新調整。

  1. 從簡單開始，反覆調整。需要時才加 context。
  2. 分段：背景、指令、tool、輸出規格。
  3. 寫得具體、精簡。巧妙的措辭沒有幫助。
  4. 把大任務拆成子任務。不要一開始就塞滿複雜要求。

Slide 的例子用 ### Instruction ### 標出指令，順序是指令、分隔符號、資料。分隔符號幫 model 分清指令與資料，但擋不住所有 prompt injection。

p.43–47

Context 是有限資源

Prompt engineering 管一段指令怎麼寫。Context engineering 管整個 window：每一步讓 model 看到什麼。

p.43

Context engineering 的定義 Context engineering

Slide 引用 Karpathy（2025）的定義：「filling the context window with just the right information for the next step」。重點是「下一步」：每一步需要的資訊都不同。

Agent 每跑一圈，harness 都要重新決定放什麼、拿掉什麼。這就是 p.7 的第 1 項與第 4 項工作。

p.44

Context 有三種成本 Context is a finite resource

Context 有三種成本：錢、延遲、注意力。放更多 context，不等於得到更好的答案。

成本原因
錢每一步都重送整個 window，每一輪都再付一次。
延遲Prompt 越長，prefill 越久，decode 也變慢。
注意力Window 越滿，model 越難找回資訊；中間的內容最容易漏掉（p.45）。

Prefill 是 model 讀完整個 prompt 的階段。Decode 是一個一個產生輸出 token 的階段。兩個階段都隨 context 變長而變慢。

p.45

長度與位置都會降低準確率 Length and position both cost accuracy

兩組研究：輸入越長，準確率越低（context rot）；答案放在中間，準確率最低（lost in the middle）。

  • Context Rot（Chroma）：輸入的 token 越多，兩條線都越低。兩條線是「簡單查找」與「有干擾項的查找」；干擾項是很像答案、但不是答案的內容。圖上的 73%、46%、40% 屬於哪條線，請看原圖。
  • Lost in the Middle（Liu et al., TACL 2024）：把答案放在 20 份文件中的不同位置，再量準確率。
答案的位置第 1 份第 5 份第 10 份第 15 份第 20 份
準確率76%61%55%59%71%

Slide 的數字呈 U 形：開頭和結尾最好，中間最差。Agent 的 context 裡，開頭是 system prompt，結尾是最新的訊息，中間是舊的 tool 結果。所以重要的指示要放在開頭或結尾。

p.48–53

管理 context 的四種策略

四種策略有先後順序。越前面越便宜、越不會遺失資訊；compaction 排在最後。

p.48

四種策略的順序 Managing the context window

四種策略從預防、無損，排到有損、不可逆：admission、offloading、transformation、compaction。

依序使用：前一層不夠，才用下一層。前兩層在內容進入 window 之前處理，什麼都不會遺失。後兩層處理已經在 window 裡的內容，刪掉的部分越來越難找回。

p.49

Admission：在門口把關 Admission: guard what enters the window

內容進入 window 之前就先篩選。Slide 的例子：原始 DOM 有 48,000 token，擷取後只剩 900 token，小 98%，答案相同。

  • Targeted retrieval：查詢範圍要窄；只取需要的欄位，不取整份文件。
  • Tool output shaping：丟掉 DOM，只留擷取的結果。
  • Truncation：無法 shaping 時，才直接截斷。
  • Isolation：把原始資料交給 subagent，只拿回結果。

為什麼 truncation 排在 shaping 後面：截斷不看內容，答案可能剛好在切掉的那一段。Shaping 依內容挑選，所以答案相同。

p.50

Offloading：拿得到，但不常駐 Offloading: keep it retrievable, not resident

資訊放在 window 外面，要用時再拿。Slide 的例子：60 個 tool schema 常駐要 42,000 token；改成索引加 3 個 schema，只要 3,100 token。小 93%，60 個都還能用。

  • Progressive tool definition：需要時才載入 schema。
  • Tool search：保留一份索引，要用時才查。
  • Tool output offload：回傳一個 handle（例如檔案路徑），需要時再讀。
  • 外部化的任務清單：計畫存在磁碟上。
  • Persistent memory：筆記寫在外面，只留一份小索引。

和 admission 的差別：admission 決定內容要不要進來。Offloading 讓內容留在外面，但保證拿得到。代價是多一次 tool call。

EXAMPLE

Claude Code 的做法（官方文件，2026-10）：MCP tool 的定義預設延後載入，只有 tool 名稱與 server 說明進入 context。MCP tool 的輸出超過上限時，Claude Code 把結果存成檔案，在對話裡只留檔案路徑。L2 的 skill 只先載入 description，也是 offloading。

p.51

Transformation：有選擇地刪掉歷史 Transformation: selectively drop the history

刪掉過期或重複的舊內容，不做摘要。Slide 的例子：96,000 token 變成 24,000 token，小 75%，沒有任何內容經過摘要。

  • Deduplication：每個物件只留最新的狀態。例：同一個檔案讀了 4 次，只留最後一次。
  • Observation masking：超過 N 步的 tool 結果，換成一行佔位文字。
  • Sliding window：只留開頭與最近的幾輪。開頭有 system prompt 與原始任務，不能丟。

為什麼對目前的任務無損：model 讀完舊結果，已經做出決定。決定寫在 model 自己的回覆裡，回覆沒有刪。但之後要引用原文時，例如某一行原本怎麼寫，只能重新執行 tool。檔案已經改過的話，舊版本就拿不回來，所以對之後的引用有損。

p.52

Compaction：LLM 摘要是最後手段 Compaction: LLM as the last resort

用 LLM 把舊歷史寫成摘要，讓 window 重新有空間。這是最後手段：有損、不可逆，本身也要花一次 model 呼叫。

  • Rolling summary：一邊做，一邊摘要舊的 tool 結果。
  • Full summary：到達上限時，重寫整段歷史。
  • Auto memory：把關鍵事實存到 window 外面。

Slide 的三個警告：留空間給輸出；保留 system prefix；compaction 後重新放入關鍵事實。保留 prefix 的原因：指令不會在摘要中走樣，prefix cache 也能繼續命中。

為什麼排最後：

  • 有損：摘要由 model 決定留什麼。它不知道之後會需要哪個細節。
  • 不可逆：原文不在 context，也沒有 handle 可以拿回來。
  • 有成本：摘要要先讀完整段歷史，這本身就是一次大的 model 呼叫。
EXAMPLE

Claude Code 的 /compact 可以加指示，告訴摘要要保留什麼，例如 /compact Keep the failing test names and the list of edited files。也可以在 CLAUDE.md 寫一段「Compact instructions」。CLAUDE.md 在 compaction 後會重新載入（L2 p.16），這就是「重新放入關鍵事實」。

p.53

Context 的五種壞法 Five ways context fails

Breunig（2025）整理出五種 context 失敗：poisoning、distraction、confusion、clash、drift。叫得出名字，修法就很明顯。

失敗症狀對應的策略（本筆記整理）
Poisoning（中毒）幻覺進入 window，之後 agent 把它當成事實引用寫入筆記前先驗證；發現後刪掉那段
Distraction（分心）歷史太長，agent 開始模仿自己過去的動作Observation masking、sliding window（p.51）
Confusion（混淆）不相關的 tool 與文件，把答案帶偏Admission、tool search（p.49–50）
Clash（衝突）新資訊和舊資訊矛盾，兩者都還留著Deduplication，只留最新狀態（p.51）
Drift（偏移）真正的目標埋在歷史中間，agent 改追一個相近的子目標目標寫在檔案，定期重新放入（p.50、p.52）
EXAMPLE

Drift 的例子：任務是「修好結帳的 bug」。Agent 發現 lint 錯誤，開始逐一修 lint，30 步後還在修。解法：把任務寫進 TODO.md，harness 每 10 步把它重新放進 context。

p.54–58

Agent = Model × Harness

Model 決定上限，harness 決定實際表現。最後一頁是選讀：ReAct 以外的 loop。

p.54

Model 決定上限 Agent = Model × Harness

Model 的能力決定上限；harness 決定實際發揮出多少。

p.55

只換 harness，解題數約變 2 倍 Changing the harness improves accuracy by 2×

Slide 引用 Lewis（2026）的實驗：model 不變，只改 harness。兩個 benchmark 的完整解題數都大幅上升。

Benchmark基本 harness改良 harness倍數
SWE-bench Verified43 / 16972 / 1691.7×
SWE-bench Pro31 / 31672 / 3162.3×

改良的 harness 做了四件事：壓縮舊的 tool 輸出；最近的 observation 保持完整；偵測重複與停滯；卡住時介入。前兩件就是 p.51 的 transformation。

Slide 的結論：有些看似 model 能力不足的失敗，原因是 context 或 control loop。p.27 的 SWE-agent 也是同一個結論。

CAUTION

論文摘要寫明：Verified 的比較用 20,480 token 的小 window。Window 越小，context 管理的影響越大。這個倍數不能直接套到所有設定。

p.58

選讀：ReAct 以外的 loop Optional reading: beyond the ReAct loop

四種控制流程，差在什麼時候回頭：ReAct 每一步都回頭；Reflexion 失敗後回頭；plan-and-execute 偏離計畫時回頭；tree search 不回頭，一次展開很多分支。

流程什麼時候回頭步驟
ReAct每一步Thought → Act → Observe
Reflexion失敗之後Attempt → Evaluate → Critique → Retry
Plan-and-execute偏離計畫時Plan → Execute steps → Re-plan
Tree search不回頭分支 A、B、C 平行探索，只留最好的

Reflexion 的 Critique 是一段文字檢討；下一次嘗試會讀到它。Tree search 和 p.35 的 tree-of-thought 一樣，都是「分支、評分、留最好的」。

帶走的重點

  • Agent loop 很短。表現取決於 harness 的四項工作：組 context、寫 tool、驗證並執行、管理結果。
  • Tool 要為 model 設計：少而正交、專用、輸出精簡、錯誤能教、可安全重試。只給 shell 是 11.0%，專用介面是 18.0%。
  • 編輯方式在 token 成本與穩健度之間取捨。Search-replace 靠內容定位；diff 依賴行號與 context 行；整檔重寫要重抄全部。
  • Context 越長越貴、越慢、越不準。依序用 admission、offloading、transformation；compaction 留到最後。
  • Prompt 技巧從 zero-shot 開始，夠用就停。換 model 時，用 eval 重新驗證每個技巧。

自我檢查

你的 agent 執行 tool 時拋出例外，整個程式就中止。依 p.6 的骨架，該怎麼改？

捕捉例外，把錯誤訊息當成 tool 結果，附上 tool_call_id 放回 messages。Model 讀到錯誤，下一圈可以修正參數或換做法。

Agent 用 unified diff 連續修改同一個檔案，第二份 patch 常常套不上。為什麼？怎麼改善？

第二份 patch 的行號與 context 行，是依第一次修改前的內容寫的。第一次修改後，這些內容已經過期。改善：每次修改後重新讀檔；或改用 search-replace，它靠內容定位，不靠行號。

你用 temperature 0 做 self-consistency，5 次取樣都答 yes。這代表 model 很有把握嗎？

不代表。Temperature 0 時，model 每次都選機率最高的 token，5 次結果本來就幾乎相同。要用大於 0 的 temperature（例如 0.7），讓每次走不同的推理路徑，一致度才有意義。

Agent 讀了 20 個大檔案，context 快滿了。你先用哪一種策略？為什麼 compaction 不是第一選擇？

先用 transformation：對舊的讀檔結果做 observation masking 或 dedup，需要時再讀。之後讀檔用 admission：只讀需要的行。Compaction 有損、不可逆，摘要本身又要一次大的 model 呼叫，所以留到最後。
