先看這裡

這堂課回答一個問題：怎麼知道一個 agent 真的會做事？做法是在可以重置的環境裡跑任務，再用明確的 grader 檢查結果。成功率之外，還要看可靠性、成本、速度，並提防 leakage。

  • Agent 評估量的是整個系統。表現 = f（LLM、prompt、scaffold、tools、retriever、memory、environment）。換掉任何一塊，分數都會變。
  • 評估 = 重置環境 → 在預算內跑 loop → grader 打分。Grader 看最終答案、最終環境狀態或 trajectory。每個 benchmark 選的不同。
  • 上線前看 pass^k，不只看 pass@k。單次成功率 0.8 的 agent，4 次全部成功的機率只有 0.41（假設每次獨立）。客服 agent 必須每次都成功。
  • 每個 benchmark 只量一種動作空間。GAIA 量研究型問答，BFCL 量 tool call。WebArena 與 OSWorld 量操作介面，SWE-bench 與 Terminal-Bench 量改程式與系統，τ-bench 量對話加政策。
  • 高分不等於可以上線。Leakage、單一 user turn、成本、非確定性、副作用，都會讓分數失真。Benchmark 也會很快飽和。

p.06

怎麼評估 agent 的能力？How do you evaluate an agent's capability?

本堂從四個角度回答：歷史與趨勢、metric、代表性的 benchmark、挑戰。

先想一個實際的問題：你改了 agent 的 system prompt。你怎麼知道新版比舊版好？

手動試 3 個例子不夠。你需要固定的任務、可以重置的環境、明確的評分規則。每題還要跑很多次。本堂依序介紹這些東西。

p.7–10

評估什麼：層級、歷史、目標

評估的對象從語言模型變成整個 agent 系統。評分方式也從比對文字，變成檢查環境狀態。

p.07

看內部，還是看結果 Different ways to evaluate an agent

Component-level 評估看 agent 內部的單一能力。End-to-end 評估只看結果：任務有沒有完成、花多少錢、花多久。

層級項目問的問題
Component-levelPlanning任務拆解得對嗎？
Component-levelTool use找得到、選得對、參數填得對嗎？
Component-levelMemory能擷取、整合、取回資訊嗎？
Component-levelError recovery出錯之後能修正嗎？
End-to-endSuccess rate任務完成了嗎？
End-to-endCost每個任務花多少錢？
End-to-endLatency多久完成？

兩種評估互補。End-to-end 告訴你 agent 能不能用。Component-level 告訴你它為什麼失敗。

EXAMPLE

訂機票任務失敗了。End-to-end 只回報「失敗」。Component-level 能找出原因：拆錯步驟、選錯 tool、填錯參數，或忘了使用者先前給的條件。p.15 的 BFCL 主要量 tool use 這一項。

NOTE

類比軟體測試：component-level 像 unit test，end-to-end 像 integration test。兩種都要有。

p.09–10

五種評估目標 Evaluation objectives

評估目標分五種：預測文字、答對、得到偏好、寫出能跑的程式、完成互動任務。每種的「成功」定義不同。p.10 和 p.9 內容相同。

目標代表 benchmark怎樣算成功
預測文字PTB、WikiText對真實的文字給出高機率
給出正確答案MMLU、GSM8K、GPQA、HLE（Humanity's Last Exam）和已知答案相符
給出較受偏好的回覆Arena、AlpacaEval、MT-Bench人或 model 給出較好的評價
寫出能運作的程式HumanEval、LiveCodeBench、SWE-bench通過可執行的測試
完成互動任務WebArena、OSWorld、τ-bench、Terminal-Bench環境達到要求的狀態

越往下，grader（評分元件）越需要「執行」。前兩列只要比對文字。最後一列要先架好網站、桌面或資料庫，讓 agent 跑完，再檢查狀態。所以 agent 評估也是一個系統工程問題。

CAUTION

第 3 列用人或 judge model 當裁判。Judge model 有已知的偏誤，例如偏好較長的回答。WebArena-Verified（p.16）因此拿掉 LLM-as-judge，改用確定性的檢查。

Metric 與評估 loop

Metric 決定什麼算成功。評估 loop 決定每一次怎麼跑。下圖用 3 個任務、各跑 4 次，比較 pass@k 和 pass^k。

p.11

除了成功率，還要看什麼 Metrics

早期 benchmark 用 perplexity、accuracy / F1、win rate。Agent 還要看 pass@k、pass^k、cost、latency。

Metric意思要注意
Perplexity在沒看過的文字上，平均 negative log-likelihood 再取指數越低越好；只量語言建模
Accuracy / F1答對的比例；F1 是 precision 與 recall 的調和平均需要標準答案
Win rate兩兩比較時，裁判選中你的比例結果依賴裁判
pass@kk 次嘗試中，至少 1 次成功常見於程式生成評估，例如 HumanEval
pass^kk 次嘗試全部成功τ-bench 提出
Cost每個任務的總花費大多是 LLM 費用；常漏算 tool call 與 cache miss
Latency完成任務的總時間不只 LLM 的時間；tool 執行、跑測試也算

Cache miss 指 prefix cache 沒有命中。這時輸入 token 要用完整價格計費。Agent 每一步都重送 context，所以 miss 一多，成本就上升。L8 會細談。

為什麼 production agent 要看 pass^k。客服 agent 每天服務很多客戶。每位客戶只有一次機會。失敗一次，就是一筆錯的訂單或一位不滿的客戶。使用者不會替你重試 4 次，再挑最好的一次。

pass@k 適合「能重試、又能自動驗證」的情境。例：產生 5 個 patch，跑測試，留下通過的那個。

EXAMPLE

假設每次執行彼此獨立，單次成功率 p = 0.8，k = 4：

pass@4 = 1 − (1 − 0.8)^4 = 1 − 0.0016 = 0.9984
pass^4 = 0.8^4                    = 0.4096

同一個 agent，pass@4 接近 100%，pass^4 只有 41%。k 越大，差距越大。真實的多次執行不一定獨立，所以實務上用實測次數計算（見 p.12）。

CAUTION

不要把整體成功率直接取 k 次方。課程筆記的理由：每題難度不同，要逐題算 pass^k 再平均。用上圖的資料：整體成功率 8/12，取 4 次方得 0.20；逐題算再平均得 0.33。

p.12

Benchmark 的評估 loop Benchmark evaluation loop

每個任務都跑同一個流程：重置環境，在預算內反覆 observe 與 act。最後 grader 依最終答案、最終環境狀態、trajectory 打分。

  1. 重置環境到任務的初始狀態。
  2. 讓 agent 觀察環境，選出一個 action。
  3. 執行這個 action，改變環境。
  4. 重複第 2、3 步，直到 agent 結束或預算用完。
  5. 交給 grader 打分：最終答案、最終環境狀態、trajectory。

Slide 的 pseudocode 把打分的元件叫 task evaluator。本頁統一稱 grader。

  • 為什麼要重置：上一次執行可能改了環境，例如多建了一個 issue。不重置，每次的起點就不同，結果無法比較。
  • 為什麼要預算：Agent 可能陷入 loop，一直重試同一個動作。步數、金額、時間的上限，保證評估會結束。
  • Grader 看什麼：依 benchmark 而定。GAIA 只看答案；WebArena、OSWorld 看環境狀態；τ-bench 看資料庫加回覆。

跑完之後，依任務分組，數出每題成功幾次，再算 pass^k。下表用上圖的資料：

任務4 次結果成功pass^1pass^2pass^4pass@4
A 改航班✓ ✓ ✓ ✓4/41.001.001.001
B 退票✓ ✗ ✓ ✓3/40.750.500.001
C 加行李✗ ✗ ✓ ✗1/40.250.000.001
平均8/120.670.500.331.00

pass^k 隨 k 下降：0.67 → 0.50 → 0.33。掉得越快，agent 越不穩定。pass@4 是 1.00，完全看不出這個問題。

p.13

GAIA：研究型問答 GAIA: General AI Assistant

GAIA 有 466 題人工撰寫的問題。Agent 要上網、讀檔、計算，最後交出一個短答案。

  • 沒有固定的 tool API。每個 agent 自備 search、browser、Python、shell。
  • 所以 GAIA 測的是整個 agent 系統，不只是 LLM。
Level步數Tool

NOTE

「自備 tool」代表分數同時反映 model 與 harness。兩個團隊用同一個 LLM，搜尋 tool 不同，分數就可能不同。

p.14

GAIA 怎麼評分 GAIA: can an assistant research and return the right answer?

GAIA 只看最終答案。正規化之後完全相符得 1 分，否則 0 分。中間步驟不計分。

Slide 的例子：附件試算表列出一些電影。找出符合兩個條件的那一部，查出導演，回報導演的出生地。課程筆記說明這是示意題，不是公開的考題。

Agent 的過程：search → 開網頁 → 下載 PDF → 抽出表格 → 跑 Python → 回答。圖中標示 grader 丟掉中間過程，只對答案打分。圖中的答案 4,381 和題目問的出生地對不上；兩者都只是示意。

score = (1/N) · Σ 1[ normalize(ŷ) = normalize(y) ]

意思：N 題裡，正規化後和標準答案相同的比例。正規化會消除格式差異，例如大小寫、空白、千分位逗號。所以 4381 和 4,381 算相同。

  • 量得到：推理、檢索、選 tool、整合資訊。評分乾淨，可以重現。
  • 量不到：改變外界的動作，例如寄 email、訂機票、改資料庫、送出表單、更新 issue。
CAUTION

只看答案的評分，看不到過程。Agent 可能用錯的方法剛好答對。它也可能在過程中做了不該做的事。p.32 會再談。

p.15

BFCL：tool call 可靠嗎 BFCL: is the model's tool interface reliable?

BFCL（Berkeley Function Calling Leaderboard）測 model 能不能正確呼叫 tool：選對 tool、填對參數、不做多餘的呼叫。

Slide 的例子：「訂下週一從 Boston 到 Chicago 最便宜的航班。」可用的 tool 有三個：

search_flights(...)
book_flight(flight_id, passenger_id)
get_weather(...)
行為判定原因
先 search_flights，挑最便宜的，再 book_flight正確先查再訂
直接填 passenger_id="P123"錯：編造 ID使用者沒給 ID，應該先問
呼叫 get_weather錯：無關的呼叫訂機票不需要天氣

表中的 "P123" 是本筆記的示意值。BFCL 的評分方式：

  • AST 檢查：把 model 輸出的 call 解析成語法樹（abstract syntax tree），比對 function 名稱、參數與值。
  • Execution 檢查：真的執行 call，比對執行結果。
  • Multi-turn 任務：每一輪都檢查狀態和回覆。

V4 加入 web search 與 memory 類別。Slide 建議看各類別的分數，不要只看總分。總分是各類別的平均，會蓋住弱項。

NOTE

為什麼「編造 ID」危險：book_flight 會真的寫入訂單。參數錯了，可能訂到別人名下。缺資訊時，正確的行為是問使用者。

p.16

WebArena：完成網頁流程 WebArena: can the agent complete a web workflow?

WebArena 有 812 個網頁任務，在自架的網站上執行。Grader 檢查最終狀態：做到得 1 分，沒做到得 0 分。

例子：在 GitLab 建立 issue「Update onboarding documentation」，指派給 Alex，加上 documentation label。

  • 網站：購物、管理後台、Reddit 類論壇、GitLab、地圖、Wikipedia，全部自架。自架才能每次重置成相同狀態。
  • Observation：accessibility tree。這是瀏覽器提供給輔助工具的頁面結構，每個元素有 ID、角色、文字。
  • Action：對元素 ID 做 click 或 type，完成時 stop。
EXAMPLE

簡化的 observation 與 action（示意）：

[1201] link 'Projects'
[1342] textbox 'Title'
[1388] button 'Create issue'

type [1342] [Update onboarding documentation]
click [1388]

評分流程：重置網站快照 → 跑 agent 的 trajectory → 用 functional check 檢查最終狀態。Issue 任務檢查三件事：issue 存在、assignee 正確、label 正確。其他任務可能檢查最終 URL、頁面內容、後端狀態或文字答案。

為什麼檢查最終狀態：建立同一個 issue 有很多條路。檢查結果，任何正確的路都能得分。

WebArena-Verified（ServiceNow，2025）要求結構化輸出，拿掉 LLM-as-judge，改用 HTTP trace 上的確定性檢查。

p.17

OSWorld：操作真的電腦 OSWorld: can the agent operate an actual computer?

OSWorld 讓 agent 操作真實的桌面 VM。Agent 看螢幕截圖，用滑鼠和鍵盤動作。共 369 個任務。

例子：在試算表加一個計算欄、排序、存成 result.xlsx。過程：截圖 → 點開 LibreOffice → 截圖 → 點儲存格 → 輸入公式 → … → 存檔。

和 WebArena 的差別：WebArena 給結構化的元素 ID。OSWorld 只給像素。Agent 要從截圖找出按鈕的位置，再算出滑鼠座標。這叫 GUI grounding。

  • 範圍：瀏覽器、Office、檔案、系統 app，也有跨 app 的流程。
  • 評分：設定初始狀態，讓 agent 執行，再由 grader 檢查最終狀態，給出 reward。不是每一步都計分。
  • 檢查項目：試算表的儲存格與公式、檔案位置、設定值、app 設定。
  • OSWorld 2.0（2026）：108 個長流程，常超過 1 小時、數百步。每個流程約 27 個 checkpoint，可以給部分分數。
NOTE

為什麼長流程需要 checkpoint：數百步的任務，很少有 agent 能全部做完。只有 0 或 1 分時，大家都是 0，看不出差別。Checkpoint 讓「做到一半」也能比較。

p.18

SWE-bench：修真實 repo 的 issue SWE-bench: can the agent fix a real repository issue?

SWE-bench 給 agent 一個真實的 repo 和一個 GitHub issue。Agent 產生 patch；patch 套用後通過 repo 的測試，才算解決。

例子：某個 library function 收到空的 index 時會丟 exception。要改成回傳空結果，並保留原有行為。

典型過程：grep repo → 讀實作 → 讀測試 → 跑測試 → 改檔 → 再跑測試 → debug → 產生 patch。

評分：把 patch 套到 repo，跑測試，判斷 issue 是否解決。測試分兩組。一組原本失敗，修好後要通過。另一組原本就通過，改完後仍要通過，用來抓出「改壞別的功能」。

版本特點
Verified人工確認過的題目
Lite300 題的子集
Multilingual9 種程式語言
Multimodalissue 裡有圖片
Pro更難，常要改多個檔案
CAUTION

測試只檢查有寫到的行為。Patch 可能通過測試，寫法卻是錯的，例如只針對測試資料寫特例。Verified 版本請人逐題確認：issue 描述夠清楚，測試也合理。

p.19

τ-bench：對話、政策、改資料 τ-bench: can an agent interact with a user, follow policy, and change backend state?

τ-bench 有兩個角色在互動：LLM 扮演的模擬客戶，和要遵守航空公司政策的 agent。Agent 的 tool 會改變真實的資料庫。

政策的例子：basic economy 機票不能更改。客戶說：「我要把明天的航班改成晚上那班。」典型流程：

  1. 確認客戶身分。
  2. 查詢訂位紀錄。
  3. 搜尋晚上的航班。
  4. 說明票價差額。
  5. 取得客戶確認。
  6. 呼叫 change_booking，更新訂位。

評分：檢查最後的資料庫狀態。這一題同時測三件事：和人對話、遵守政策、正確改資料。

EXAMPLE

換一個情況：這張票是 basic economy（示意）。

客戶 ：我要把明天的航班改成晚上那班。
Agent：請提供您的 user ID 和訂位代號。
客戶 ：（提供資料）
Agent → tool call：查詢訂位
Agent：這張是 basic economy 機票。依政策，不能更改航班。

這時的目標狀態是「資料庫不變」。Agent 若照樣呼叫 change_booking，資料庫就和目標不同，這題得 0 分。

p.20

τ-bench 的評分與 pass^k τ-bench scores end state and consistency

τ-bench 的 reward 是 r = r_action × r_output，兩項都要是 1 才得分。它也提出 pass^k：同一題獨立跑 k 次，全部成功的機率。

  • r_action = 1：最終資料庫和標註的目標狀態一致。
  • r_output = 1：給客戶的回覆包含必要的資訊。
  • 用乘法：任何一項是 0，總分就是 0。

唯讀的 call 可以不同。Agent 多查一次訂位沒關係。不該有的寫入，會直接讓這題失敗。

Slide 的 pass^k 例子：4 次都成功，pass^4 才算這題；pass@4 只要 1 次成功。計算方法見 p.11 的例子與 p.12 的報表。

新版 τ³-bench 修正了有問題的任務，並加入更多領域、知識檢索與語音評估。

NOTE

比喻：pass@k 像考試能考 4 次，取最好的一次。pass^k 像飛機降落，每一次都必須成功。客服 agent 屬於後者。

p.21

Terminal-Bench：用 shell 完成真實工作 Terminal-Bench: can an agent finish a real task through a shell?

Terminal-Bench 讓 agent 在 Docker container 裡用 shell 完成真實工作。結束後，測試腳本檢查系統的最終狀態，給出 pass 或 fail。

任務不只是修 repo 的 bug。領域包括程式開發、系統管理與 server 設定、資料處理、模型訓練、資安、科學計算流程。

每個任務打包成三樣東西。檔名依 slide；內容是本筆記的示意，實際目錄結構以官方 repo 為準。

  • 版本：TB 2.0 有 89 題。TB 4.0 刪掉已飽和的題目，剩 66 題。
  • 解答不公開：每題有人類寫的解答，但不公開。這能降低 leakage 的風險（p.26）。
  • Timeout：8 小時。
  • 代表任務：在運作中的 KV service 上部署新 protocol。過程中不能斷線，latency 也要維持。
NOTE

為什麼刪題：所有 agent 都會做的題目，分不出強弱，只會墊高分數。刪掉之後，分數才能反映差距。p.34 談飽和。

TheAgentCompany 模擬一家軟體公司，有 175 個任務。Agent 要用公司的工具，也要和 LLM 模擬的同事溝通。Checkpoint 讓沒做完的任務也能拿部分分數。

  2. 詢問同事（RocketChat）。
  3. 查看 repo（GitLab）。
  4. 撰寫程式（workspace）。
  5. 執行測試（terminal）。
  6. 更新 issue（Plane）。
  7. 回報結果（RocketChat）。

S_partial = 0.5 · earned/total + 0.5 · S_full

earned/total 是拿到的 checkpoint 比例。整個任務完成時，S_full 是 1，否則是 0。

p.26

Data leakage 的四層 Data leakage: four layers, not just training

Data leakage（資料洩漏）不只發生在訓練。Agent 評估至少有四層：訓練、評估當下、環境、benchmark overfitting。

層怎麼發生例（示意）
Training leakage題目或人類的修正，出現在訓練資料裡Model 背過某個 issue 的 patch
Eval-time leakageAgent 評估時上網，抄到之後才出現的修正搜到已 merge 的 PR，照抄
Environment leakageSandbox 暴露未來的 commit 或隱藏的測試執行 git log --all，看到修正的 commit
Benchmark overfitting用公開的測試集調 prompt 與 scaffold反覆看失敗案例，改到分數變高

Tool 越真實，leakage 的入口越多。Agent benchmark 需要的資訊，常常可以直接搜尋到。

CAUTION

有 web search 的 agent 做 SWE-bench，可能搜到這個 issue 的修正。這時分數反映「找答案」的能力。它沒有量到「解題」的能力。

p.27

Leakage 會從整個 stack 進來 Leakage can occur through the whole agent stack

Agent 的表現 P = f（LLM、prompt、scaffold、tools、retriever、memory、environment）。每一個輸入都可能把答案帶進來。

元件Leakage 怎麼發生
Base modelPretraining 資料含有 benchmark 題目
Fine-tuning用 benchmark 解答當 agent 的訓練 trajectory
PromptFew-shot 範例取自測試題
RetrievalRAG 語料庫收錄了 benchmark 答案
Memory存了先前做這個 benchmark 的紀錄
Web search搜到公開的解答
Environment暴露未來的 git commit 或隱藏檔案
Scaffold針對 benchmark 手寫的規則
Agent 開發流程研究者反覆看失敗案例、調整系統

所以「model 沒有用測試集訓練」不足以證明分數乾淨。Model 只是 f 的一個輸入。其他輸入都能帶入答案，和訓練資料無關。

EXAMPLE

Memory 的例子：agent 有跨 session 的 memory。第 1 輪評估時，它記下「task 17 的答案是 4,381」。第 2 輪跑到同一題，它直接從 memory 取答案。分數變高，能力沒變。對策：每次評估都從空的 memory 開始，也就是 p.12 的重置。

NOTE

最後一列最容易忽略：開發者自己也是 leakage 的管道。你每看一次失敗案例、改一次 prompt，就把測試集的資訊帶進系統。常見的對策：留一份 held-out 測試集，開發時不看，最後才跑一次。

p.28

只有一個 user turn 的問題 Challenges with Agent Evaluation: a single user turn

多數 benchmark 只給一個完整的指令：prompt 進去，最終狀態出來，中間沒有使用者。真實工作會模糊、會修改、會中斷。

真實的情況：條件沒講完、做到一半收到糾正、目標中途改變。

單一 turn 的評分會獎勵「有自信地猜」。Agent 問一個釐清問題，要多花步數，卻拿不到分數。

EXAMPLE

指令：「幫我訂下週一去 Chicago 的機票。」指令沒說幾點、哪個機場、預算多少。

  • Agent 甲：直接訂最便宜的早班機。
  • Agent 乙：先問「您希望幾點出發？」

單一 turn 的 benchmark 沒有人回答問題。乙只能停下來，得 0 分。標準答案若剛好是最便宜的班機，甲得 1 分。真實的使用者可能比較喜歡乙。

p.32

還有四個挑戰 Challenges with Agent Evaluation: there are more

還有四個挑戰：成本與 latency、非確定性、安全與副作用、評分方式本身。

  • 成本與 latency：只看成功率不夠。Slide 的對比：一次跑 200 步、花 40 美元；另一次 12 步、花 0.30 美元。兩次都成功，價差約 133 倍。
  • 非確定性：同一個 agent 做同一題，結果可能不同。只跑一次的分數，大多是雜訊。
  • 安全與副作用：過程中刪了檔案、寄了 email、花了錢，分數都不會扣。
  • 評分方式：只看結果，會放過運氣好或不安全的執行。比對 trajectory，會判錯其他正確的做法。
CAUTION

為什麼 outcome-only 會放過不安全的執行：grader 只看終點。例：agent 修好了 bug，但過程中把 API key 印進 log，還寄測試信給真實客戶。最終狀態正確，grader 給滿分。實務上兩種方式搭配：看結果，也用規則掃描 trajectory 裡的危險動作。

EXAMPLE

非確定性有多大：假設 benchmark 有 50 題，每題成功率 0.6，各題獨立。只跑一次，總分的標準差約 0.07（√(0.6 × 0.4 / 50) ≈ 0.069）。所以一次得 60%、一次得 66%，可能只是運氣。做法：每題跑多次，報告平均與範圍。

p.37

能力、成本、速度與 Pareto frontier More dimensions to consider for a real-world agent

真實的 agent 至少要看三個維度：能力（越高越好）、成本（越低越好）、速度。Assignment 3 會用這三個維度評分。

  • Dominance（支配）：A 在每個 metric 都不比 B 差，且至少一個比 B 好，就說 A 支配 B。
  • Pareto frontier（Rank 1）：沒有任何 agent 能支配的那一群。
  • Rank 2、Rank 3：拿掉 Rank 1，剩下不受支配的是 Rank 2，依此類推。
  • Slide 的圖只畫能力和成本，沒有畫速度。Slide 也提到 agent 的易用性（usability）。
EXAMPLE

三個 agent（示意，假設速度相同）：

Agent成功率每題成本
X70%$1.20
Y72%$0.40
Z80%$3.00

Y 支配 X：更便宜，成功率也更高。Y 和 Z 互不支配：Z 比較強，Y 比較便宜。所以 Pareto frontier 是 Y 和 Z。

為什麼不合成一個分數：把能力和成本加權成一個數字，要先決定權重。每個使用者的權重不同。Pareto frontier 不需要權重，只排除明顯較差的選項。

NOTE

對 Assignment 3 的含意：新版 agent 最好能支配舊版。也就是至少一個維度更好，其他維度不變差。只追成功率，可能換來又貴又慢的 agent。

帶走的重點

  • Agent 評估量的是整個系統。換掉 prompt、tool、memory 或環境，分數都會變。
  • 評估 loop：重置環境 → 在預算內執行 → grader 打分。先弄清楚 grader 看的是答案、狀態還是 trajectory。
  • 上線前看 pass^k。逐題計算再平均，不要把整體成功率取 k 次方。
  • 成功率之外，也要報告成本（含 tool 與 cache miss）、latency，以及多次執行的變異。
  • 選動作空間和你的 agent 相同的 benchmark。同時確認它是否飽和、有沒有 leakage。
  • 比較 agent 時用 dominance：至少一個維度變好、其他維度不變差，才算真的進步。

自我檢查

一個 agent 的單次成功率是 0.9，假設每次執行獨立。pass@3 和 pass^3 各是多少？客服 agent 該看哪一個？

pass@3 = 1 − 0.1³ = 0.999。pass^3 = 0.9³ = 0.729。客服看 pass^3：每位客戶只有一次機會，agent 必須每次都成功。

你的 coding agent 在 SWE-bench 的分數從 40% 跳到 70%。你只改了一件事：加上 web search tool。可能的原因是什麼？怎麼檢查？

可能是 eval-time leakage：agent 搜到了這個 issue 的修正或 PR。檢查 trajectory 裡的搜尋紀錄與造訪的網址。也可以封鎖相關網域後重跑，看分數是否回落。

為什麼「model 沒有用測試集訓練」不足以證明 agent 的分數乾淨？舉兩個其他管道。

表現 = f（LLM、prompt、scaffold、tools、retriever、memory、environment），model 只是其中一個輸入。其他管道例如：memory 存了上一輪的答案；sandbox 的 git 歷史有未來的修正 commit；few-shot 範例取自測試題；開發者反覆看失敗案例來調整系統。

TheAgentCompany 的某個任務有 10 個 checkpoint。Agent 拿到 9 個，任務沒有完成。S_partial 是多少？

0.5 × 9/10 + 0.5 × 0 = 0.45。只差最後一步，分數還不到一半。

Agent X 成功率 65%、每題 $0.50；Agent Y 成功率 65%、每題 $0.80。假設速度相同，誰支配誰？

X 支配 Y。兩者能力相同，X 比較便宜。X 在每個維度都不比 Y 差，而且成本更好。
