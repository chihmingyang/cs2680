先看這裡

這堂課從一個 agent 走到多個 agent。核心問題有三個：誰協調、工作怎麼拆、agent 之間怎麼傳話。每個答案都會碰到分散式系統的老問題。

  • 先問要不要拆。拆開的好處來自專業分工、權限隔離、平行處理、context 管理。代價是溝通、合併與除錯的成本。
  • 架構 = 三張圖。Control graph 決定誰協調，communication graph 決定誰和誰說話，task graph 決定工作怎麼拆。八種架構是這三張圖的不同組合。
  • 子任務要寫成規格。寫明目標、邊界、輸出 schema、完成條件、預算。拆得太細，overhead 會吃掉平行的收益。
  • 訊息分兩層。控制欄位（type、task_id）給 runtime 讀，內容給 LLM 讀。Timeout 後重試時，用 task_id 當 idempotency key，同一件事就不會做兩次。
  • A2A 與 MCP 分工。A2A 讓 agent 把有狀態的 task 交給另一個 agent；MCP 讓 agent 呼叫 tool，一次呼叫一個結果。

p.06

從一個 agent 到多個 From one agent to many

本堂分三塊：架構、協調、溝通。Multi-agent 已有幾十年的研究歷史，本堂不談那段歷史。

架構決定整體的形狀，例如有沒有中心。協調在本堂指 task decomposition，也就是工作怎麼拆。溝通決定 agent 之間怎麼傳話。

p.8 把這些問題整理成三張圖。後面每一段都在回答其中一張。

p.07

什麼時候值得拆給多個 agent When and why split work across agents?

四個理由：專業分工、權限隔離、平行處理、context 管理。

理由意思例子（本筆記）
Specialization每個 agent 用不同的 model、prompt、tool查資料用便宜的 model；寫程式用強的 model
Isolation每個 agent 有不同的權限讀網頁的 agent 沒有 shell；執行程式的 agent 不能上網
Parallelism互不相依的子任務同時跑5 篇論文由 5 個 agent 同時讀
Context management不把整條 trajectory 交給每個 agentWorker 只拿到自己的子任務；supervisor 只收摘要

Isolation 和安全有關。L2 講過，網頁內容可能藏有 prompt injection。讀網頁的 agent 就算讀到惡意指令，也沒有 shell 可以執行。

這個 subagent 用較便宜的 haiku（分工），只有兩個網路 tool，不能改檔或跑指令（隔離）。它有自己的 context window，只把摘要交回主 agent（context 管理）。

CAUTION

每個理由都有代價。多一次交接，就多一次資訊遺失和 token 成本。p.48 的第一條原則就是：先問真的需要 multi-agent 嗎？

p.08

每個架構背後的三張圖 Three questions / graphs behind every architecture

描述一個 multi-agent 架構，要回答三個問題：誰協調（control graph）、怎麼溝通（communication graph）、工作怎麼拆（task graph）。

圖回答的問題常見答案
Control graph誰協調？一個 supervisor、一層層的 hierarchy，或沒有人。執行中可以換手（handoff）。
Communication graph怎麼溝通？直接傳訊、broadcast，或共享工作區。
Task graph工作怎麼拆？Planner 事先拆、靠競標（bidding）分配，或從局部規則自然形成（emergent）。

讀 p.10–17 時，先看每頁底部的 Task / Control / Comms 那一行。那一行就是這三張圖的答案。

NOTE

比喻：在一間公司裡，control graph 是組織圖，決定誰向誰報告。Communication graph 是誰和誰開會、傳訊息。Task graph 是專案的工作分解。三張圖可以不同：組織圖是樹狀，大家卻可能在同一個頻道裡討論。

p.09

八種架構一覽 Multi-agent architecture

八種：supervisor–worker、hierarchical、pipeline/DAG、blackboard、committee、market、swarm、dynamic topology。p.10–17 一頁講一種。

p.10

1. 一個 supervisor 派工與整合 1. Supervisor–worker

一個 supervisor 負責規劃、派工、整合結果。每個 worker 只看到自己的子任務。

  • Slide 的例子：supervisor 帶 Researcher、Coder、Reviewer 三個 worker。
  • 適合：子任務互不相依，可以平行跑。
  • 弱點：supervisor 是瓶頸。它要讀每一份結果，所以它的 context 長得最快。
  • 三張圖：Task = supervisor 事先拆好；Control = 一個 supervisor；Comms = 星狀，全部經過 supervisor。
NOTE

比喻：只有一個 master 的叢集，所有回報都送到 master。這裡 master 的負載是 context。例如 3 個 worker 各回報 5k token，supervisor 的 context 就多 15k token。Supervisor 最先遇到 compaction（L2 p.16）。

EXAMPLE

Claude Code 的主 agent 加上 subagent，就是這個架構。官方文件（2026-10）的說明：subagent 把結果交回呼叫它的主 agent，由主 agent 管理所有工作。Anthropic 的 multi-agent research system 也用這個模式（見延伸閱讀）。

p.11

2. 一層層的 supervisor 2. Hierarchical agents

把 supervisor–worker 遞迴套用：supervisor 底下還有 supervisor。

  • Slide 的例子（做一個 feature）：Feature manager 帶 Backend lead 與 Frontend lead。Backend lead 再帶 API 與 Database；Frontend lead 再帶 UI 與 E2E tests。
  • 適合：本來就能分層拆的任務，例如 storage、query engine、testing。
  • 難處：在哪一層拆？每條邊界要傳多少 context？
  • 三張圖：Task = 每一層再拆一次；Control = 巢狀的 supervisor；Comms = 樹狀，只有上下層之間。
NOTE

比喻：公司的組織層級。工程師的細節經過 lead 摘要，再交給 manager。每多一層，就多一次摘要。p.19 把弱點寫成「錯誤放大」：下層摘要錯了，上層依錯的摘要做決定，錯誤一路往上傳。

p.12

3. 固定階段的流水線 3. Pipeline / DAG

工作分成固定的幾個階段。每個邊界都有 typed contract，規定輸入與輸出的型別。

  • Slide 的例子（發票處理）：OCR → 擷取欄位 → 比對 PO（採購單）→ 核准 → 入帳。
  • 優點：最容易 debug 的 topology。錯誤會停在某一個階段，容易定位。
  • 弱點：沒有回頭路。第 4 站不能要求第 1 站給更好的來源。
  • Slide 的教訓：加一條 retry edge，勝過多加一個 agent。
  • 三張圖：Task = 設計時就固定階段；Control = 順序本身就是控制；Comms = 階段到階段。
EXAMPLE

Typed contract 的寫法（本筆記示意，用 Pydantic）：

class ExtractedInvoice(BaseModel):   # 「擷取欄位」交給「比對 PO」
    invoice_no: str
    po_number: str
    total_cents: int

下一站收到不符 schema 的輸出，就立刻報錯。錯誤停在這條邊界，不會流到入帳。Retry edge 的例子：核准發現金額對不上，就退回 OCR 重掃一次。

p.13

4. 透過共享狀態協調 4. Blackboard and shared memory

Agent 之間不直接傳訊。大家讀寫同一份共享狀態，藉此協調。

  • 共享工作區可以是資料庫、vector store、檔案系統、Git repo 或 task graph。
  • Slide 的例子：Feature、Refactor、Test 三個 agent 共用一個 Git repo，裡面有 task list、commits、history。
  • 優點：agent 可以隨時加入或離開，不必重新接線。共享狀態會持久保存，也能檢查。
  • 難處：consistency、concurrency control、provenance（誰寫的）、versioning、garbage collection。
  • 三張圖：Task = 從共享狀態中浮現；Control = 沒有中央控制；Comms = 間接，經過工作區。
NOTE

Blackboard 就是一個共享資料庫或 Git repo。Slide 列的難處，你都在資料庫遇過：兩個 agent 同時改同一個檔（concurrency）、讀到過期的版本（consistency）。還有查不到某段是誰寫的（provenance）、暫存檔沒人清（garbage collection）。

EXAMPLE

Claude Code 的 agent teams 用一份共享 task list 協調（官方文件，2026-10）。Teammate 認領 task 時用 file locking，避免兩人同時搶到同一個 task。文件也提醒：兩個 teammate 改同一個檔，會互相覆蓋。所以要讓每個 teammate 負責不同的檔案。

p.14

5. 多人提案，judge 裁決 5. Committee / debate

幾個 agent 各自提出答案並討論，再由 judge 或投票解決分歧。

  • Slide 的例子（作文評分）：Grader A 與 Grader B 各自評分，judge 做最後決定。
  • 適合：需要判斷的任務。Slide 說這個架構能提高這類任務的準確度。
  • 失敗模式：意見一致，不代表彼此獨立。同一個 model、同一份 context，就有同一個盲點。
  • 三張圖：Task = 同一個任務平行做多次；Control = judge 決定；Comms = 同儕先討論，再交給 judge。
CAUTION

兩個 grader 用同一個 model、讀同一份評分 prompt，它們的錯誤高度相關。兩票同意，帶來的新資訊很少。這就像找兩個背景完全相同的人做 code review：他們會漏掉同一個 bug。提高獨立性的做法：換不同的 model、給不同的評分角度、先各自作答再看彼此的答案。

p.15

6. 競標分配工作 6. Market and auction

Agent 依能力、成本、latency，對公告出來的任務出價。符合條件又最便宜的 agent 得標。

前提：agent 是異質的。Model、tool、機器、成本、專長都不同。

Slide 的例子是 GPU job router：「誰能跑這個 training job？」規則是 5 秒內完成、出價最低者得標。

節點出價ETA結果
T4$0.0510s最便宜，但超過 5 秒，出局
A100$0.203s得標：5 秒內最便宜
H100$0.401s最快，但比 A100 貴
  • 優點：不需要中央 planner。工作自然落到最便宜、又有能力的 agent。
  • 弱點：出價是自己報的。Agent 誇大能力，就能搶到自己做不好的工作。
  • 三張圖：Task = 公告後以出價認領；Control = auctioneer 結標；Comms = broadcast 公告，出價回傳。
CAUTION

自報的資訊不能全信，這是分散式系統的老教訓。一個做法（本筆記補充）：記錄每個 agent 過去的實際 ETA 與成功率，用歷史表現校正它的出價。

p.16

7. 沒有協調者的群體 7. Swarm

沒有固定的協調者。Agent 直接互相協商、交換發現。

  • Slide 的例子：倉儲機器人 Picker 1–4 互相協商，誰去揀哪一張訂單。
  • 需要的協定：discovery（找到彼此）、addressing（定址）、synchronization（同步）、termination（何時結束）、trust（信任誰）。
  • 優點：沒有協調者，就沒有瓶頸，也沒有單點故障。Peer 加入或離開，工作照常進行。
  • 弱點：通訊量 O(n²)，衝突也難解決。產品中很少用。
  • 三張圖：Task = 局部協商；Control = 沒有固定協調者；Comms = 全對全。
NOTE

算一下：每對 agent 一條線，n 個 agent 有 n(n−1)/2 條。4 個是 6 條，10 個是 45 條，20 個是 190 條。對 LLM agent 來說，每則訊息都要進入某個 context，所以 O(n²) 會直接變成 token 成本。

p.17

8. 執行中改變形狀 8. Dynamic topology

任務執行中，可以加入、移除 agent，或重新接線。

  • Slide 的例子：客服 bot。一般 ticket 只有 support bot 處理。Ticket 升級時，才加入 billing agent 與 log agent。
  • 優點：容量隨難度增加。簡單的 ticket 保持便宜。
  • 弱點：每次執行的形狀都不同，失敗很難重現。
  • 三張圖：Task = 工作變難時重新拆；Control = agent 加入時，控制權跟著轉移；Comms = 執行時動態決定。
CAUTION

難重現的對策（本筆記補充）：把每次執行的 topology 寫進 log，例如幾點加入哪個 agent、誰傳給誰。出問題時，才能照同一個形狀重跑。

p.18

真實系統是混合體 Real systems are hybrids

實際的系統會混用 hierarchy、shared memory、pipeline，需要時再重新規劃。

Slide 的圖有 supervisor、planner agent、一個 dynamic task DAG，以及 Coder、Researcher、Tester、Reviewer 和共用的 Git repo。拆開來看：

  • Supervisor 加 planner：hierarchy。
  • Dynamic task DAG：會重新規劃的 pipeline。
  • 共用的 Git repo：blackboard。
EXAMPLE

Claude Code 的 agent teams 也是混合體（官方文件，2026-10）。Team lead 派工，像 supervisor。Teammate 共用一份 task list，像 blackboard。Teammate 之間還能直接傳訊，像 peer-to-peer。

p.20–26

Task decomposition：工作怎麼拆

架構回答誰協調。這一段回答 task graph：沿哪個軸拆、子任務要寫清楚什麼、拆多細、拆錯會怎樣。

p.20

拆解與合併 Task decomposition

一個複雜任務拆成 3 個子任務，結果再合併成一份。拆和合都有成本，p.21–26 逐一討論。

p.21

六個拆解的軸 Task decomposition

可以依資料、專長、階段、假設、tool、權限範圍來拆。不同的軸可以疊加。

軸每個 agent 負責例子
Data一部分文件或紀錄每個 agent 讀 50 個檔案
Expertise一個專業角度security、performance、correctness、legal
Stage流程中的一個階段plan → implement → test → review
Hypothesis一個互相競爭的解釋「cache 的問題」對上「race condition」
Tool一種 tool 或資料來源web、資料庫、程式執行、內部文件
Authority一個管理範圍（administrative domain）每個 agent 只持有一個系統的權限

Slide 的例子：一個 200 個檔案的 PR。先依資料拆（按檔案分組），再依專長拆（security、performance）。

EXAMPLE

在 Claude Code 裡可以這樣下指令（本筆記示意）：

Review PR #142. Split the 200 changed files into 4 groups of 50.
For each group, spawn one security reviewer and one performance
reviewer. Each reviewer returns a list of {file, line, severity, issue}.
Merge the 8 lists and remove duplicates.

這樣共有 8 個 subagent。每個只讀 50 個檔案，只看一個角度。

NOTE

Hypothesis 軸適合 debug。Claude Code 官方文件（2026-10）的 agent teams 範例：開 5 個 teammate，各自驗證一個假設，再試著推翻彼此的理論。存活下來的理論，較可能是真正的原因。

p.22

每個子任務要寫清楚的事 Things to consider when creating sub-tasks

子任務要寫成規格。規格要寫清楚：目標、輸入與 context、邊界與排除項、tool 與權限、輸出 schema、完成條件、預算與期限、相依關係。

Slide 的對比：

  • 差：「Research storage systems」。哪一年？要幾篇？回傳什麼？什麼時候算完成？Worker 只能猜。
  • 好：找出 2026 年發表、和 storage 有關的論文。每篇回傳標題、日期、系統貢獻、評估規模、一手來源的 URL。排除資料庫 query optimization。

好的版本寫出了目標、輸出 schema、排除項。下面把 8 個欄位都補齊。

NOTE

比喻：一張寫得好的 Jira ticket。接手的人沒參加規劃會議，也能做完，並交出能合併的結果。Worker 看不到 supervisor 的 context，所以規格沒寫的事，worker 都不知道。

p.23

拆多細：granularity 的取捨 Granularity tradeoff

拆太粗，沒有平行；拆太細，排程與溝通的 overhead 吃掉收益。省下的循序時間大於額外成本，平行才划算。

Slide 的估算式：

T_multi ≈ T_planning + T_critical_path + T_communication + T_merge
  • T_planning：拆任務、寫規格的時間。
  • T_critical_path：最長那條相依鏈的時間。平行只能縮短這一項。
  • T_communication：派工、回報、等待的時間。子任務越多，這一項越大。
  • T_merge：讀完所有結果、整合成一份的時間。

用 slide 的例子算一次：20 個一行就能查完的 lookup。下表的秒數是本筆記假設的：每個 lookup 5 秒；supervisor 為每個子任務派工與讀回報，要花 8 秒。

拆法planningcritical pathcommunicationmerge合計
不拆，1 個 agent 依序做010000100 s
20 個子任務，各 1 個 lookup10516010185 s
4 個子任務，各 5 個 lookup1025321077 s

拆成 20 份比不拆還慢。每份只省下 5 秒，卻要付 8 秒的 overhead。Slide 的做法是把 20 個 lookup 打包成 4 個子任務。

NOTE

Claude Code 官方文件（2026-10）對 agent teams 也有同樣的建議。任務太小，協調成本超過收益。任務太大，teammate 太久沒有回報，白做的風險變高。

p.24

事先拆，還是邊做邊拆 Static versus dynamic decomposition

靜態拆解在執行前就確定，好預測、好評估。動態、遞迴、機會式拆解會在執行中產生新任務，所以一定要設上限。

方式新任務從哪來Slide 的例子
Static執行前就全部確定摘要使用者上傳的 5 份 PDF，每份一個任務
DynamicAgent 依新發現建立任務遇到失效的連結，就開一個查詢任務
RecursiveWorker 自己再委派Review agent 為每個子領域開一個 subagent
Opportunistic閒著的 agent 認領新任務閒著的 agent 接手下一份還沒標註的文件

沒有上限時，委派會遞迴爆炸。每個 agent 都可能決定「再開幾個 subagent」。Slide 要求四種上限：spawn 數量、預算、深度、終止條件。

EXAMPLE

Claude Code 的對應設定（官方文件，2026-10）：

# 深度上限：預設 subagent 最多在主對話下 3 層；設成 1 就不能巢狀
export CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1
# spawn 上限：預設同時最多 20 個 subagent
export CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=5

預算：在 subagent 的 frontmatter 寫 maxTurns: 20。跑滿 20 個 turn，subagent 就停下。終止條件：寫進子任務規格的 done_when（p.22）。

NOTE

Agent teams 的 self-claim 就是 opportunistic 拆解（官方文件，2026-10）。Teammate 做完一個 task，就認領下一個沒人認領、相依也已完成的 task。

p.30

溝通通道 Communication channels

六種通道：點對點、broadcast、publish–subscribe、共享 blackboard、request–response、artifact passing。

通道Slide 的例子
點對點（direct point-to-point）Planner 把任務規格交給 coder
BroadcastOrchestrator 通知所有 agent：build 失敗了

p.31

訊息格式 Message format

自然語言有彈性，但有歧義。結構化訊息容易驗證，但表達力較低。實用的設計兩者並用。

  • 給程式讀的欄位：task_id、type、status、requires_response。Runtime 用它們判斷這是哪個任務、做完沒有、要不要回覆。
  • 給 LLM 讀的內容：claim 是一句自然語言的結論。confidence 和 evidence 幫接收者判斷要不要相信它。
  • 大型產出放檔案：artifact 只放路徑。完整分析留在檔案裡，不塞進 context。
CAUTION

只有 claim、沒有 evidence 的結論，接收者無法查證。兩個 agent 結論衝突時（p.39），evidence 讓第三方能判斷誰對。

p.32

控制與內容分開 Messages should carry semantics

內容用自然語言，協調用結構化協定。控制欄位和內容要分開放。

差的設計：全部塞進一個字串，例如 {"message": "some text"}。Runtime 想知道這是派工還是取消，只能問 LLM。

好的設計：一個 envelope（信封）。外層是 runtime 看得懂的欄位，payload 才是內容。

payload 放自然語言的內容，例如 p.22 的子任務規格。Slide 列出 runtime 認得的 9 種 type。下表的說明是本筆記的解讀：

type意思
DELEGATE派出一個子任務
QUERY問一個問題，等回答
REPORT回報進度或結果
HANDOFF把控制權交給另一個 agent
UPDATE更新已派出的任務
CANCEL取消任務
ACK確認收到
ERROR回報失敗
COMPLETE任務完成
EXAMPLE

Runtime 只看 type 就能行動（本筆記示意）：

def on_message(msg):
    if msg["type"] == "CANCEL":
        stop_task(msg["task_id"])          # 不用問 LLM
    elif msg["type"] == "ERROR":
        retry_or_escalate(msg["task_id"])
    else:
        deliver(msg["to"], msg)            # payload 交給收件 agent 的 LLM

這就是 slide 的重點：路由、重試、停止，都由 runtime 依欄位決定。LLM 只處理 payload。

p.36–39

溝通是分散式系統問題

Agent 之間的訊息走網路，所以分散式系統的老問題全部回來。LLM 是黑盒子，又多加一層難度。

p.36

Timeout 之後，對方到底做了沒？ Communication is a hard distributed systems problem

Agent A 請 Agent B「購買 8 台 GPU instance」，然後 network timeout，沒有回覆。A 無法知道 B 有沒有執行。

Timeout 有三種可能：請求沒送到；B 買了，但回覆遺失；B 還在處理。從 A 這一側，三種情況看起來一樣。

語意A 的做法結果
At-most-once不重試最多買 1 次；可能 0 次，任務沒完成
At-least-once重試，直到收到 ACK至少買 1 次；可能買 2 次
Exactly-once只靠重試做不到網路不可靠，傳遞層無法保證。實務上用 at-least-once 加上冪等處理（idempotent）來逼近。

Slide 的對策：用 task_id 當 idempotency key；準備 compensation 或 rollback 的路徑；事先決定重複購買時誰付錢。

EXAMPLE

Idempotency key 怎麼運作（本筆記示意）。A 每次重試都帶同一個 task_id。B 先查這個 task_id 做過沒有：

def purchase(msg):
    key = msg["task_id"]                # idempotency key
    if key in completed:                # 重送的請求
        return completed[key]           # 回傳上次的結果，不再買一次
    order = buy_gpu_instances(count=8)
    completed[key] = order              # 存在持久的儲存
    return order

A 重試 3 次，B 也只買 1 次。completed 要放在持久的儲存，B 重啟後才查得到。

CAUTION

重試要由 runtime 執行，並沿用原本的 task_id。讓 LLM 自己「再試一次」，它可能重寫請求、產生新的 task_id。B 認不出這是重複的請求，就會再買一次。真的買了兩次，就靠 compensation：自動釋放多出的 8 台。

p.37

Multi-agent 繼承的分散式系統問題 Distributed systems are hard

Multi-agent 繼承分散式系統的六個老問題。分別是部分失敗、並行與不確定性、副本的一致性、沒有全域時鐘、不可靠的網路、除錯與可觀測性。

問題經典說法在 multi-agent 裡（本筆記）
Partial failure分不出對方是慢，還是掛了Agent 想了 3 分鐘，還在推理，還是 crash 了？
Concurrency 與 non-determinism很多機器同時修改狀態多個 agent 同時寫 blackboard；LLM 取樣再加一層隨機
副本狀態的一致性在 consistency、availability、partition、latency 之間取捨每個 agent 的 context 都是共享事實的一份副本，會過期
No global clock各機器的時鐘不一致兩則訊息誰先誰後，不能只看時間戳
Unreliable network封包會延遲、遺失、亂序、重複重送的 DELEGATE 可能讓任務做兩次（p.36）
Debugging 與 observability請求多、log 分散、時鐘飄移用 task_id 把各 agent 的 log 串成一條
NOTE

把每個 agent 的 context 看成一份副本，很多問題就清楚了。共享狀態改變時，已經讀進 context 的舊值不會自動更新。這就是 p.39 的 stale information。第三列的取捨，就是 CAP 與 PACELC 討論的問題。

p.38

跑多個 agent 的額外挑戰 More challenges when the system runs multiple agents

還有排程、狀態管理、資源分配三個問題。而且請求的流程無法事先知道。

  • Scheduling：下一個輪到誰跑？跑多久？
  • State management：checkpoint、memory、provenance、versioning。
  • Resource allocation：model、CPU 與其他共享資源。

最根本的是最後一點。一般 web service 的請求路徑是固定的：前端 → API → 資料庫。Multi-agent 的路徑由 LLM 在執行時決定。要開幾個 agent、各跑多久、各用多少 token，事前都不知道。

NOTE

比喻：作業系統的排程器，面對一群會隨時 fork 子 process 的 process。容量規劃和成本估計都變難。L8 會談成本與效能。

p.39

黑盒子 LLM 讓問題更難 Even harder when you consider the black-box LLMs!

LLM 是黑盒子，所以又多出三類問題：context 問題、協調與溝通問題、可觀測性與失敗診斷。

類別問題Slide 的說明或例子對策（本筆記）
ContextInformation loss摘要丟掉 worker 知道的細節傳 artifact 路徑，不只傳摘要
ContextContext pollution雜訊淹沒了重要的資訊只傳收件者需要的內容
ContextStale informationX 已改成 5，B 仍依 X=3 行動共享事實加版本號；行動前重讀
ContextConflicting beliefsA 說安全，B 說有漏洞附 evidence；交給 judge 裁決（p.14）

Lost ownership 就是團隊裡的「我以為你會處理」。Communication loop 和網路的 routing loop 一樣。IP 封包用 TTL 防止繞圈：每經過一個 router，TTL 減 1，歸零就丟掉。Agent 訊息也可以帶同樣的跳數上限。

p.40–47

A2A 與 MCP：兩個標準協定

A2A 處理 agent 與 agent 之間的溝通；MCP 處理 agent 與 tool 之間的呼叫。兩者都只標準化溝通，不負責 orchestration。

p.40

A2A：agent 對 agent 的協定 A2A

A2A（agent-to-agent）讓兩個 agent 互相發現能力、建立 task、回報進度、交回 artifact。

  1. Agent A 讀 Agent B 的 agent card，得知 B 的能力。
  2. A 送出 message，建立一個 task。
  3. B 執行時，送回進度更新。
  4. B 完成後，交回 artifact。

Slide 的例子：「公司 X 該不該把 inference stack 換到 GPU Y？」

  • Research agent 透過 agent card 找到其他 agent。
  • Finance agent 估算 GPU 成本。
  • Search agent 找 benchmark 資料。
  • Coding agent 實際跑 benchmark。
NOTE

比喻：microservice 的 service discovery 加上 RPC。差別在於對方是 agent：一個請求可能跑好幾個小時，中途還會反問你。對方內部怎麼做，你看不到（p.47 的「ideally opaque」）。

p.41

每個 A2A server 都公開一張機器可讀的 agent card，位置是 GET /.well-known/agent-card.json。呼叫者從 card 得知對方是誰、會什麼、怎麼呼叫。

呼叫者得知對應欄位

CAUTION

Skills 是對方自己宣稱的，和 p.15 market 的出價一樣。Card 說會訂機票，不保證訂得好。

p.42

三個抽象：message、task、artifact Three A2A abstractions

Message 啟動 task；task 產出 artifact。後續的 message 加入同一個 task。

抽象是什麼Slide 的例子
MessageClient 與 agent 之間的一個回合「Book a flight to Boston」
Task有 ID、有生命週期的有狀態工作單位task-42：working → completed
ArtifactTask 產出的結果行程 PDF 與訂位資料

NOTE

比喻：客服工單的每次來回是一則 message。工單本身是 task，有編號和狀態。最後寄給你的收據是 artifact。你補充資料時，回覆同一張工單，不會開新的工單。

p.43

Task 的生命週期 A2A task lifecycle

A2A 是有狀態的協定。Task 可以停下來等使用者輸入或授權，之後再繼續。

  • 進行中：Submitted（已收到）、Working（處理中）。
  • 中斷：Input required（等使用者補資料）、Auth required（等授權）。補上之後回到 Working。
  • 終止：Completed、Failed、Rejected、Canceled。

Slide 的例子：「Book a flight」→ Input required：「Which date？」→ 回覆「Oct 3」→ 回到 Working。對照本段開頭的狀態圖。

CAUTION

終止狀態不能重新開始。官方文件（2026-10）規定：task 進入終止狀態後，後續要求要開一個新 task，並沿用同一個 contextId。Rejected 表示 agent 決定不做這個 task。

p.44

追蹤長時間的 task Following a long-running task

Task 可能跑幾秒，也可能跑幾小時。呼叫者選擇追蹤方式：polling、streaming 或 push notification。

方式怎麼運作適合官方規格的方法（2026-10）
PollingClient 反覆查詢，直到完成短的工作GetTask
StreamingServer 持續送出即時更新互動式輸出SendStreamingMessage、SubscribeToTask
Push notification完成時觸發 webhook跑好幾小時的工作設定 push notification config

比喻：polling 是一直重新整理物流頁面；streaming 是看直播；push 是包裹送到時收到一則簡訊。

CAUTION

A2A 只標準化溝通，不負責 orchestration。要不要委派、怎麼拆、何時停止，仍由 harness 決定。p.20–26 的拆解問題，A2A 不會替你解決。

p.45

MCP：agent 的服務邊界 MCP: agent capability

MCP 是 agent 和服務之間的邊界：一次 tool call，一個結果。

Slide 的圖：agent 透過 MCP 接到 filesystem、database、GitHub、browser。MCP 標準化三樣東西：

  • Tools：可呼叫、有型別的能力。
  • Resources：host 可以附加的可讀資料。
  • Prompts：可重用的互動範本。

一個 client 可以接很多個 server。要開放哪些能力，由 host 決定。Model 只能使用 host 開放的能力。

NOTE

L2 p.53–60（選讀）講過 MCP 的細節：host、client、server 的角色，以及 gateway。這一頁的重點是對照。MCP 的基本單位是一次 tool call；A2A 的基本單位是一個能跑很久、能中途暫停的 task。

MCP 與 A2A 的比較 MCP vs. A2A

MCP 連接 agent 與服務，單位是一次 tool call。A2A 連接 agent 與 agent，單位是一個長時間的 task。

MCPA2A
主要抽象Capability / toolAgent / task
關係Agent → 服務Agent → agent
DiscoveryTools、resources、promptsAgent 的能力（agent card）
工作單位一次 tool 呼叫長時間的 task
內部狀態能力介面最好不透明（opaque）
類比裝置或 API 介面服務之間的 RPC

兩者可以疊在一起。Slide 的說法：一個 A2A 遠端 agent，自己可能就呼叫了 20 個 MCP server。

EXAMPLE

一條完整的呼叫鏈（本筆記示意）。你的 assistant 透過 A2A，把「訂下週去 Boston 的機票」交給 travel agent。Travel agent 再透過 MCP 呼叫航班 API、行事曆、付款服務。你只看到 task 的狀態與最後的 artifact。

NOTE

怎麼選：要做一個明確的動作，例如查一筆訂單，用 MCP tool。要交出一個需要對方自己推理、可能跑很久的目標，用 A2A。

p.48

設計原則 Design principles

四條原則：先問需不需要 multi-agent；依相依關係決定 topology；找出資訊遺失點；找出失敗的隔離邊界。

  1. 真的需要 multi-agent 嗎？一個 agent 常常就夠了。多個 agent 會增加 overhead 與複雜度。
  2. 決定 topology。反映任務的相依關係，並減少溝通。
  3. 找出資訊遺失點。彙整節點（aggregation node）就是細節流失的地方。
  4. 找出失敗的隔離邊界。一個 agent 出事時，整個系統不能停住。

Slide 的提醒：密集的 mesh 很少是好的預設。溝通越多，context 壓力越大，有用的資訊卻不一定變多。

NOTE

延伸閱讀的數字支持第 1 條。Towards a Science of Scaling Agent Systems 測了 260 種設定。和單一 agent 相比，表現變化從 +80.8%（可分解的財務推理）到 −70.0%（循序規劃）。Anthropic 的文章則指出，multi-agent 系統用的 token 約是一般聊天的 15 倍。

EXAMPLE

把四條原則變成設計 review 的問題（本筆記整理）：

  1. 拿掉一個 agent，品質掉多少？成本省多少？
  2. 每一條溝通線，對應哪一個任務相依？
  3. 哪個節點在做摘要？它丟掉的細節，下游需要嗎？
  4. 任一個 agent 卡住 10 分鐘，系統會怎樣？

帶走的重點

  • 先問要不要拆。拆開的理由是分工、隔離、平行、context 管理；代價是溝通、合併、除錯。
  • 架構看三張圖：誰協調、誰和誰說話、工作怎麼拆。中心化的架構有瓶頸；去中心化的架構有一致性與 O(n²) 的問題。
  • 子任務要寫成規格，並設 spawn、深度、預算、終止條件的上限。拆太細，overhead 會吃掉收益。
  • 訊息要有 envelope。Runtime 依欄位路由、重試、停止；LLM 只讀 payload。重試時沿用 task_id 當 idempotency key。
  • A2A 交出有狀態的 task；MCP 做一次 tool call。兩者都不替你做 orchestration。

自我檢查

你的 supervisor 帶 8 個 worker。跑到一半，supervisor 開始 compaction，品質下降。為什麼是 supervisor 先出問題？有哪兩種改法？

所有 worker 的結果都回到 supervisor，所以它的 context 長得最快。改法一：worker 把完整結果寫進檔案，只回傳摘要與路徑。改法二：改成 hierarchical，加一層 lead 先彙整。第二種會多一次摘要，要注意資訊遺失。

兩個 grader 都給這篇作文 A，judge 就採用。這個設計有什麼問題？

如果兩個 grader 用同一個 model、讀同一份 context，它們的錯誤高度相關。兩票同意，不代表兩次獨立的確認。改用不同的 model 或不同的評分角度，並讓它們先各自作答。

20 個 lookup，每個 5 秒；每個子任務的派工與回報要 8 秒。為什麼拆成 20 個子任務，比不拆還慢？

平行只把 critical path 從 100 秒縮到 5 秒，省下 95 秒。溝通卻要 20 × 8 = 160 秒，再加上 planning 與 merge。打包成 4 個子任務，總時間約 77 秒（p.23 的表）。

Agent A 送出「購買 8 台 GPU instance」後 timeout。A 該重試嗎？怎樣重試才不會買兩次？

可以重試（at-least-once），但每次都帶同一個 task_id 當 idempotency key。B 先查這個 task_id：做過就回傳上次的結果。重試要由 runtime 執行，因為 LLM 改寫請求時可能換掉 task_id。萬一還是買了兩次，就用 compensation 釋放多出的 instance。

情境一：讓你的 agent 查一筆訂單的狀態。情境二：把「規劃一趟出差」交給別家公司的 agent。各該用 MCP 還是 A2A？

情境一用 MCP：這是一次明確的動作，一次呼叫一個結果。情境二用 A2A：對方要自己推理，可能反問日期或要求授權，也可能跑很久。這正是 A2A task 的生命週期要處理的事。
