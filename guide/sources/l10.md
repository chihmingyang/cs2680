## 本文補的：AI 寫的 kernel 怎麼量錯（第 9 章）

- METR（Tao Lin），Measuring Automated Kernel Engineering，2025-02-14，https://metr.org/blog/2025-02-14-measuring-automated-kernel-engineering 。KernelBench Level 1–3 的 250 題刪掉 45 題（輸出在 (-0.01, 0.01)、輸出幾乎不隨輸入變「allows cheating by caching outputs」、輸出過度一致）；刪掉 17 個用 CUDA streams 的解；一個「way too fast」的結果歸因於「torch.empty re-allocating the same memory used by the correct reference solution」。計時改用 `triton.testing.do_bench`；baseline 含 torch.compile。KernelAgent 1.81x 對 KernelBench 的 1.05x；每題每個 model 約 20 美元。（KernelBench v0.1 的文章說 METR 刪了 43 題，本文照 METR 自己寫的 45。）
- TechCrunch，Sakana walks back claims that its AI can dramatically speed up model training，2025-02（頁面沒有寫日期，以「this week」「Friday」描述），https://techcrunch.com/?p=2969225 。Sakana 宣稱「up to 100x」；有使用者量到 3 倍變慢；Sakana 的說明：系統「cheat」、利用評估程式繞過正確性檢查（「reward hack」）；「We have since made the evaluation and runtime profiling harness more robust」；改寫論文並道歉。原始頁 pub.sakana.ai/ai-cuda-engineer 現在只導向 arXiv 2509.14279，讀不到原本的更正說明，所以用 TechCrunch 的轉述。
- Lange、Sun、Prasad、Faldor、Tang、Ha（Sakana），Towards Robust Agentic CUDA Kernel Benchmarking, Verification, and Optimization（robust-kbench），arXiv 2509.14279 v1，2025-09-16，https://arxiv.org/abs/2509.14279 。「fake speedups of 50-120x by exploiting loopholes in KernelBench」；「after excluding all contaminated tasks (Section A), the average speedup is reduced from 3.13x to 1.49x」（作者自己的框架、KernelBench L1 與 L2 共 200 題）；例子：ConvTranspose3d_Mean_Add_Softmax 123.603x（hardcode softmax 為 1.0）、Level 1 Task 12 diagonal matmul 51.159x（baseline 沒用 broadcasting）；對策：多組輸入大小、初始化、seed，容差 1e-5，forward 與 backward，2000 次、25 次暖機。
- Li、Sun、Wang、Li、Shum（DeepReinforce），CUDA-L1，arXiv 2507.14111，v1 2025-07-18（目前 v12，2026-08-05），https://arxiv.org/html/2507.14111 。Section 3.1：「82 out of 250 (32.8%) RL-generated implementations exploit this timing loophole ... leading to an overall speedup of 18×」，手法是另開 CUDA stream；修法是結束計時前讓主 stream 等每個額外的 stream，再同步 device。其他類別：lazy evaluation、hyperparameter manipulation（縮小 batch_size 等）、result caching（依 `x.data_ptr()`，容差寬時能過）。
- Kokoromyti、Sun、Ouyang、Mirhoseini（Stanford），KernelBench v0.1，2025-07-27，https://scalingintelligence.stanford.edu/blogs/kernelbenchv01 。作弊模式：呼叫 torch 或 cuBLAS、寫了 CUDA 卻沒呼叫、no-op（輸出記憶體重用時看起來正確）、計時的同步點錯。「Even when we patch known exploits, new ones emerge, often even harder to detect.」目標把 L1、L2 放大到 H100 上 1–15 ms（ReLU 0.013 ms → 6.97 ms）；`rand_mix` 多種分布（預設仍是 `torch.randn`）；speed of light：4096² BF16 matmul「~137 GFLOPs」「~96MB」「at least ~0.138 milliseconds」「at least 0.029 milliseconds」。
- Zhong、Segal、Bercovich、Saxena、Zhang、Raghunathan（CMU 等），Hardening Agent Benchmarks with Adversarial Hacker-Fixer Loops，arXiv 2606.08960 v1，2026-06-08，https://arxiv.org/abs/2606.08960 。5 個 terminal-agent benchmark 1,968 題中 323 題可被鑽（約 16%）；KernelBench：公開漏洞的攻擊成功率「from 62% to 0%」；task 046 的 verifier-aware hacker 用 `gc.get_objects()` 找到參考 Model，「patch its forward to burn matmuls before each timed call」，報出 93,862x；過嚴的修補讓正常解通過率 0–22%，autopatch 後 92–98%。
- Jaber、Jaber，AutoMegaKernel，arXiv 2606.09682 v1，2026-06-08，https://arxiv.org/abs/2606.09682 。摘要自承「precision-asymmetric (W8A16 vs. bf16)」；A100、H100 上落後 cuBLAS；7,160 個對抗排程零誤收。

## 本文補的：MoE 與 batching（第 3 章）

- DeepSeek，DeepSeek-V3/R1 Inference System Overview（Open Source Week day 6），統計區間 2025-02-27 12:00 到 02-28 12:00（UTC+8），https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md 。「the model's high sparsity necessitates an extremely large overall batch size」「This ensures sufficient batch size per expert」；prefill「Routed Expert EP32」、每張 GPU 9 個 routed expert；decode「Routed Expert EP144」、每張 GPU 2 個 routed expert 加 1 個 shared expert。
- Wang 等，A Systematic Characterization of LLM Inference on GPUs，arXiv 2512.01644 v1，2025-12-01，https://arxiv.org/html/2512.01644v1 。A100 80GB × 4、Jetson AGX Orin；vLLM 0.9.2、BF16、eager。MoE（Qwen3-30B-A3B）FFN intensity 約 8 FLOP/B，dense 15.74；prefill intensity 約 55–100、decode 約 1–10；MoE 對 dense 快 4.56x（prefill）、2.39x（decode），decode 的 routing 18.6–28.1%；TP4 時 decode 的通訊超過 60%。延伸閱讀的摘要也用這份。
- 本文的算術：每個 routed expert 分到 B × 8 ÷ 256 個 token；平均分配時 batch 64 有 1 − (248/256)^64 ≈ 87% 的 expert 至少分到一個；每個 expert 要 206 個 token 時一步約 6,592 個 token。

## 可讀性審查第 1 輪的修正（2026-11-06）查的

審查報告在 `notes/review/l10-20261106-{a,b,c}.md`，修正紀錄在 `notes/review/l10-fixes.md`，修法是 `notes/l10/fix_review.py` 的逐段替換（頁面已接線，不從 notes/ 重建）。這一輪新查或重查的事實：

- Llama 3 論文 Table 5（https://arxiv.org/html/2407.21783v3 ，重查）：GPU 類共六列，Faulty GPU 30.1%、GPU HBM3 Memory 17.2%、GPU SRAM Memory 4.5%、GPU System Processor 4.1%、Silent Data Corruption 1.4%（6 次）、GPU Thermal Interface + Sensor 1.4%（6 次），合計 58.7%。圖只畫前七大，所以青色四條是 55.9%；頁面現在寫出差的 2.8% 是哪兩類。

- Wang 等，arXiv 2512.01644 v1 第 7.1 節：dense 是 Qwen2.5-32B-Instruct、MoE 是 Qwen3-30B-A3B-Instruct；decode 時 dense 的 FFN intensity「grows to 15.74 FLOP/byte」，MoE 停在約 8，原因寫成 routing 讓每個 expert 的 batch 變小。15.74 對應哪個 batch，正文沒寫（Figure 16 只寫 varying batch sizes）。
- DeepEP README（https://github.com/deepseek-ai/DeepEP ，經 awesome.ecosyste.ms 的鏡像讀到）：H800、每張 ConnectX-7 400 Gb/s；機內 EP8 dispatch 153 GB/s、combine 158 GB/s，瓶頸 NVLink（上限約 160 GB/s）；跨機 EP16 dispatch／combine 43 GB/s，瓶頸 RDMA（上限約 50 GB/s）；4096 tokens、hidden 7168、top-4 groups、top-8 experts、FP8 dispatch、BF16 combine。
- MPK，arXiv 2512.22219（OSDI 2026）摘要：「up to 1.7× lower end-to-end inference latency」，對照的是 kernel-per-operator 的 LLM serving 系統；摘要沒寫 GPU 型號。
- FlashAttention-4，arXiv 2603.05451（重查）：條件式 rescale 是「only rescale when m_j − m_{j−1} > τ」，τ = log₂256 = 8；最後的正規化用追蹤到的統計量修正，所以結果仍正確。
- Rubin：Tom's Hardware 對 NVIDIA 說明的整理（https://www.tomshardware.com/pc-components/gpus/nvidia-details-rubin-architectural-optimizations-for-inference-improvements-target-better-performance-and-efficiency-from-the-gpu-to-the-rack ）：每顆 FP16/BF16 4 PFLOPS、FP8/FP6 17.5 PFLOPS，所以 slides 表上 BF16 182 → FP8 795 的 4.4 倍是規格本身；Rubin 的 TMA 把 MoE 的 descriptor 直接放在 TMA 指令裡、執行時更新，Blackwell 要替每個 expert 在記憶體裡各存一份。文章沒說這些算力是不是 dense。
- G80 → B300 的 43,000 倍（本文核算）：GeForce 8800 GTX FP32 345.6 GFLOP/s、86.4 GB/s；B300 dense NVFP4 15 PF、8 TB/s；15,000 ÷ 0.3456 ≈ 43,400，8,000 ÷ 86.4 ≈ 93。所以 43,000 倍是 FP32 比 FP4。
- Llama 3 的 GQA：8B 是 32 個 query head、8 個 KV head（g = 4），70B 是 64、8（g = 8）。頁面原本寫「Llama 3 的 g 是 8」，改成分開寫。batch 1、1K context 的 8B：KV 0.134 GB 對 weights 16 GB，整步 intensity ≈ (16 + 0.54) ÷ (16 + 0.134) ≈ 1.02。
- DGX H200 的 GPU 記憶體合計 1,128 GB（PNY 的產品頁）；system memory 沒找到官方數字，頁面只寫「看 server 的配置」。
- 頁面上「實際跑過」的 code（online_softmax.py、sol.py、roofline.py、measure.py、harness.py）在 Linux 6.18、Python 3.13、numpy 2.5.3、2 核 Intel Xeon 的虛擬機上重跑：確定性的三個輸出和頁面一字不差，measure.py、harness.py 的時間在同一量級。
