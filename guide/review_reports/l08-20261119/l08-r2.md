BLOCK [#i3 ¶11]
  我讀到的：Cache 的壽命叫 TTL，Claude API 有兩種：5 分鐘的，寫入收 base input 的 1.25 倍，每次 cache hit 把 5 分鐘重新算起；1 小時的，寫入收 base input 的 2 倍。人一停下來，5 分鐘很快就過了。
  靠：後面的單位
  R1 「每次 cache hit 重新計時」只寫在分號前面 5 分鐘的那一種，1 小時的那一種沒寫。有兩種讀法：(a) 只有 5 分鐘的會重新計時，1 小時的從寫入起滿一小時就過期；(b) 兩種都會重新計時。這一段分不出來。
  R13 我是讀到 code1 的「k：超過 5 分鐘、少於 1 小時的停頓次數」和 ¶15 的「TTL 從 request 開始時算」，才推出 1 小時的也是從最後一次 request 算起。照 (a) 讀，一個開超過一小時的 session 就算沒停過也會過期，¶14「互動 session 用 1 小時」的帳就不一樣。

BLOCK [#i3 ¶15]
  我讀到的：Agent 等 tool 的時候不送 request，計時沒有重來，所以等一個跑超過 5 分鐘的測試，cache 也會過期。除了改 TTL，還可以在過期前送一個 request 續命（keep-alive）；這個 request 自己要錢，Pi 估計省得到 $0.05 以上才送。
  靠：只靠主張、例子對不上
  R1 「預期省下 $0.05 以上」有兩種讀法：(a) 不送就要多付的重寫費用達到 $0.05，還沒扣 keep-alive 自己的錢；(b) 扣掉 keep-alive 自己的錢之後，淨省達到 $0.05。前一句「省下的夠不夠付」的「省下」是 (a) 的意思；照同一個意思往下讀，$0.05 就該是拿來和 keep-alive 的花費比的門檻，可是這一段沒寫 keep-alive 一次花多少。
  R16 主張是「要先算省下的夠不夠付」，例子是 Pi 的門檻。例子裡我指得出「省下」的那一筆，指不出「付」的那一筆：keep-alive 一次要多少錢、$0.05 和它是什麼關係，都沒寫。
  R7 「另一種做法」的前一句講的是陷阱，不是做法。「另一種」相對的那一種（改用 1 小時 TTL），要回到 ¶14 才找得到。

NIT [#i3 ¶14]
