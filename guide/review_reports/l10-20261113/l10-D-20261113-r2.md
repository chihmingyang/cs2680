BLOCK [#i4 表2 列5 ‹頻寬›]
  我讀到的：從 GPU 往外搬資料的頻寬，到其他 GPU 走 NVLink 4，每個方向 450 GB/s；到 CPU 走 PCIe 5.0，約 64 GB/s。

  R12 同一格並列兩個數字，450 GB/s 寫了「每個方向」，64 GB/s 沒寫是單向還是兩個方向合計；讀者只能照前一個數字的位置猜它也是每個方向。猜錯的話，兩條路的差距會是約 7 倍或約 3.5 倍，差了一倍。

BLOCK [#i4 註 n-datapath ¶9]
  我讀到的：Blackwell 的 2-SM MMA 讓兩個 SM 合算一個兩倍大的 tile。算 C = A × B 時，兩個 SM 各算 C 的一半，各自要自己那塊 A，但都要同一塊 B。合算時 B 由兩個 SM 各載入一半、互相共用，所以 B 只搬一次，每個 SM 要搬進來、存起來的 bytes 變少。
  靠：只靠主張、例子對不上
  R16 前面的 ¶2 說「下面每一項都在回答同一個問題：一條指令能讓多少 bytes 上路，又少占多少 register」。這一項展示的是「每個 SM 要搬的 bytes 變少」，也就是少搬，不是一條指令讓更多 bytes 上路；它存的地方也沒說是 register。這兩個目標我都對不上。表1 列6 把它列在「新的資料搬運功能」底下，同樣只寫「兩個 SM 合算一塊」，看起來是運算，不是搬運。

BLOCK [#i5 ¶11]
  我讀到的：MBU 是實際每秒搬的 bytes 除以 peak 頻寬。例子：Llama 3 8B、batch 1、H200，每個 token 讀 16 GB 的 weights（KV cache 0.13 GB 先忽略），200 tok/s 就是 3.2 TB/s，MBU 約 67%。規則是 prefill 和訓練報 MFU，decode 報 MBU，因為小 batch 的 decode 的 MFU 只有幾個百分點，分不出改進和誤差。
  靠：我自己的知識
  R9 「分不出是改進還是量測的誤差；MBU 才會……明顯變動」少了一步。照 ¶4 的定義，同一個 model 在同一張 GPU 上，MFU 和 MBU 都等於 tokens/s 乘一個固定的數（¶10 剛說過，在同一張 GPU 上 MFU 和 tokens/s「是同一件事」）。這樣 tokens/s 改進三成，兩者都會變大三成。文章沒說為什麼數值擠在小範圍就分不出誤差，也沒說誤差為什麼只影響 MFU、不影響 MBU。我得自己補一個理由（例如 MBU 才看得出離上限多遠），文章沒寫。

最難讀的三處（即使都過也要列，依難度排）：
1. [#i5 ¶11] MFU 和 MBU 在 batch 1 時都正比於 tokens/s，「MFU 分不出改進、MBU 才會變動」的理由接不上 ¶10 剛建立的比例關係。
2. [#i4 註 n-datapath ¶9]（連帶 [#i4 註 n-datapath 表1 列6 ‹B200 / Blackwell›]、¶2）2-SM MMA 讀起來是「合算」與「少搬」，要自己判斷它怎麼算進「讓更多 bytes 上路、少占 register」這個共同目標。
3. [#i4 ¶15] 一段裡有 slides 數字更正、三種做法、三代 GPU 的 9／14／25 KB 和 register 上限的推理。9／14／25 KB 是用 Little's law 算出來的，但這裡沒說三代都假設同一個 250 ns 的 latency，要回頭對公式才看得出來。
